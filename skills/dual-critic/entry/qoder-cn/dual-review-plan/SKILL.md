**只在用户显式调用本命令时执行。** 本载体没有「禁止模型自行调用」的开关：你若是自己读到这份说明、

#### 参数转抄规约

- **来源**：用户随本命令给出的全部文本就是参数。逐字转抄：不增删、不改写、不翻译，也不「顺手」补全。
- **空参数**：用户什么都没写时，参数就是空的——`<参数>` 处什么都不放。**严禁自行编造**焦点、主题或任务目标；
  CLI 缺参时会退 64 并给出写法提示，原样转述给用户即可（FR-20「缺焦点拒绝启动」靠这一条保住）。
- **拼串**：沿用下文「第 1 步」一节的写法，不另起规则——用户正文整段放进**一个单引号参数**，旗标放在引号之外；
  正文里的单引号写成 `'\''`，其余任何字符一律不转义；**不要改用双引号**（`$`、反引号会被 shell 展开）。
- **样例**（正文与旗标分离，`--` 之后的部分）：
  - 用户输入 `重点看并发 --topic 登录重构` ⇒ `-- '重点看并发' --topic 登录重构`
  - 用户输入 `看 it's 这一处的 $HOME 与 "双引号"` ⇒ `-- '看 it'\''s 这一处的 $HOME 与 "双引号"'`

# 命令 B · 对已有计划做背靠背双审，并产出逐条裁决的修订计划（命令 B）

下文 `TV` 指 `.trivium/bin/trivium`——**一律用这个项目相对路径**，不依赖 `PATH`
也不依赖 `${CLAUDE_SKILL_DIR}`（设计 §5.3 / §10.5）。
若该文件不存在，说明本项目还没初始化：提示用户先运行 `trivium init`，然后**停止**。

## 执行契约（必须严格按序，不得跳步）

**你不得自行调用 `agy` 或 `zcode`。** 并行、超时、指纹、轨迹核验、防覆盖命名、
裁决校验全部在编排器内（设计 §16.2 纪律 4）。你的职责只有三件：按序调用、读文件、写裁决。

**护栏（L2）**：本载体没有 TriviumCode Hook，写入不会被事前拦截。
闸门期不改业务文件、审查进行中不改业务文件、只写自己后缀的原稿与裁决件——这些**靠你自觉**，越界不会被事前拦下。
事后能发现多少，按时点分：
- **审查进行中**改业务文件：跑后漂移复算会发现（被 .gitignore 忽略的文件除外）。改到被审内容，整次运行作废；
  改到 `--context` 或 diff 涉及的文件，缺省也作废；改了别的文件，缺省只记一条告警。
- **闸门期**（命令 B / C / D 等待审批时）改业务文件：**不会让审批失败**——审批前复核只核裁决齐备与本轮审查工件的 sha256，不看工作树；审批时 `approve` 会列出自审查收尾以来改过的文件（只告知，被 .gitignore 忽略的看不见，取不到时如实报原因），由审批人判断。
- **审查工件**：命令 B / C / D 审批之前删改本轮的，审批前复核会发现不符并拒绝审批；审批之后（含更早轮次）的删改，只有带 Hook 的载体在会话里提交时才被核对。
  命令 A 没有审批这一步：它的审查工件被删改，事后防线只剩带 Hook 载体的提交锚。

### 0. 认领本阶段（写原稿之前）

原稿写在 `review --start` 之前，那一刻本阶段还没有运行留痕，护栏只能按**声明**判定这一阶段归谁写。
所以**写原稿之前**先认领；原稿已经写好了也补跑一次（同一声明幂等）：

```
TV topic claim --topic <主题> --stage plan --driver qoder-cn --json
```

`<主题>` 取用户参数里的 `--topic`；没写时用原稿所在（或你打算写进）的主题目录名，即 `.reviews/<主题>/plan/` 里那一段。

- 本阶段已声明为你自己时它退 0、什么都不改，照常继续；
- **退 64 时原样转述并停止**：本阶段已由别家执笔，或阶段目录里已有别家后缀的文件。
  **不要删那些文件来换回认领**——那是刻意的限制，它们的去留请用户在终端处理；
- **退 2 时同样原样转述并停止**：审批正本 task.json 读不出，本次没有写入。恢复由用户在终端做，恢复后再重跑本步；
- 认领是**自声明**：它记下「这一阶段由谁执笔」，证明不了你就是那一家；窗口内的认领次数也不设上限（M10a 边界 ⑥）。

认领之后若原稿还没写，用 Write 落盘 `.reviews/<主题>/plan/<日期>-<主题>-<当轮 Driver>.md`，再进第 1 步。

### 1. 解析主题与被审对象

运行 `TV topic resolve --stage plan --json -- <参数> --driver qoder-cn`。

- 用户什么都没写（既无正文也无 `--focus`）时 `topic resolve` 会退 64 并给出写法提示，
  原样转述即可（FR-20）。
- 若未提供 `--context` → 依据计划内容补一份涉及路径清单再传入。
  你在起草时本就知道涉及哪些模块，这一步能显著提升审查质量（UR-01 / AC-11）。
  **清单不能写到本轮的禁读范围**：对端的审查件或它们所在的目录、运行目录、`.trivium/`（项目配置与 `bin/` 除外）、
  凭据类文件，或罩住这些的目录（如 `.`）——写到了，第 3 步的 `--start` 会退 64 并逐条点名路径、类别与哪几侧。
  撞上时按来源处置：`--context` 是**用户写的** → 原样转述并停止，由用户改；
  是**你自动补的** → 按报错去掉点名的条目后重跑，并在开场播报里写明去掉了哪几条（不要静默去掉）。

**命令后的正文就是审查焦点**（「这次重点看什么」，进 BRIEF 第 2 段，FR-20 / AC-09 的
唯一落点，逐字嵌入）。用户不需要区分「目标」与「焦点」，直接写重点看什么即可。
任务目标（「这次要达成什么」，进第 4 段）**不必**用户提供：编排器会回退到 `task.json`
已记录的目标或同主题计划定稿；用户确实想指定时写 `--goal <任务目标>`。
也兼容显式写法 `<任务目标> --focus <焦点>`：给了 `--focus`，正文就落到任务目标上。
`--focus` 与 `--goal` 都贪婪取到下一个已知旗标为止，带空格无需引号。

**构造这条命令时，把用户正文整段放进一个单引号参数，旗标放在引号之外。**
`--` 之后的内容按 shell 参数逐个解析、不再重新分词：正文里的 `--xxx`、引号、`$`、
反引号、`*` 都是字面量，会逐字进入焦点。不要指望用户在聊天框里自己加引号：
他们不会，也不该被要求这么做。

例：用户说「重点核实 `--plan-file` 透传说明是否准确」，要传成

```
TV topic resolve --stage plan --json -- '重点核实 --plan-file 透传说明是否准确' --topic <主题> --driver qoder-cn
```

正文里若有单引号，写成 `'\''`（关引号、转义一个单引号、再开引号），**其余任何字符一律不转义**：

```
TV topic resolve --stage plan --json -- '看 it'\''s 这一处与 "双引号" 的处理' --topic <主题> --driver qoder-cn
```

**不要改用双引号**（`$`、反引号会被 shell 展开），**不要补字面引号**（新版解析器不剥引号，
补了会原样进 BRIEF）。不包引号就把正文裸露出去，正文里的 `--plan-file` 会成为真旗标、
连同后一个词一起被抠走。`--topic` 被包进了引号里，resolve 会退 64 并指出来；其余旗标字样
被包进去时 resolve 只在 `notes` 里提醒——照原样转述给用户。

### 2. 预检（在解析之后）

```
TV preflight --stage plan --driver qoder-cn --critics <critics> [--profile <名称>] [--model-<审核者 id> <模型> …] [--tier-<审核者 id> <档> …] [--effort-<审核者 id> <值> …] [--profile-<审核者 id> <名> …] --json [--native-<审核者 id>] [--driver-model <模型>] [--driver-provider <供应商>]
```

- `--critics`：第 1 步 resolve 输出的 `critics` 用逗号连接，**无条件传**；
- `profile` 非空时传 `--profile`；`models` 非空时逐个传对应的 `--model-<审核者 id>`；`tiers` / `efforts` / `vendor_profiles` 非空时逐个传对应的 `--tier-<审核者 id>` / `--effort-<审核者 id>` / `--profile-<审核者 id>`； 接入字段缺席表示继承；vendor_profiles 中显式 null 必须传 --native-<审核者 id>，非空传 --profile-<审核者 id>，同侧不同时传。
- **这几样必须与第 3 步传的是同一组**，都取自第 1 步的输出，不要各拼各的。

预检要查的是本轮实际入选的那几侧：用户用 `--critics` 加进来的一侧没登录或缺本阶段模型，
不带 `--critics` 就查不到，要等拉起之后才失败。

**预检退 69 时先看能不能自动校准**（EV-251）。预检失败时 JSON 里有 `recalibration`：

- 退出码不是 69、`recalibration` 键缺席、或 `recalibration.eligible` 不为 `true`：**原样转述**错误（连同 `recalibration.why`）并停止，
  不要自行猜测修复。预检失败时不会产生任何工件，可以放心重试。
- 退出码 69 且 `recalibration.eligible` 为 `true`：**不向用户确认**，按下面四步自动校准一轮。哪些失败项能修、该跑哪几家、
  带什么旗标，全由预检给出——你只照念、照抄，不自行判断、不增删。

1. **第一个动作是发文本，不是调用**（EV-252）：把 `recalibration.announce_before` **原样**作为一条文本发给用户——
   它点名了失败项、要跑几次 doctor、每次时限，并提醒会消耗配额，是用户在不被询问时唯一的事前知情点。
   **在这句话出现在对话里之前，不得发起任何 doctor 调用。**
   （键缺席时——旧版编排器——按格式「预检退 69，以下失败项可由 doctor 重新校准：〈失败项名称〉；将依次在前台跑 N 次 doctor
   （每次至多 `deadline_s` 秒），会消耗少量配额」自拟，同样先发后调。）
2. 逐条执行 `recalibration.invocations`。**命令文本恰好是字面的 `.trivium/bin/trivium` 后接该条 `args` 的各项**
   （以空格连接，含空格或 shell 元字符的项加单引号），**前后不加任何东西**：不加重定向（`>`、`>>`、`2>&1`）、
   不接管道或 `tee`、不用 `;` / `&&` 接后续命令、不加变量赋值或 `cd` 前缀；`args` 的各项也不改、不增删。
   改写过的调用与预检给出的不一致，留痕对不上；装有写入护栏的载体还会把带重定向的整条命令拦下、白耗一轮。
   输出很长（每家数十 KB，含完整探针）也照样不改调用：播报要的字段（退出码、`blockers`、`warnings`、`deadline`）——
   输出已直接返回时就从返回里取；载体把输出截存成文件时，另起一次只读的读取去读那个文件。退出码以工具结果报告的为准。
   **前台调用**，Bash 工具超时设为该条的 `bash_timeout_ms`；不要放到后台，也不要拆成发起与等待两步。
   每条结束后先发一行播报（`only`、退出码、`blockers` 条数；`deadline.hit` 为真时点名 `deadline.sections` 里没探完的段），
   再发下一条。任何退出码（0 / 69 / 76 / 64 / 1，或被工具超时打断）都**继续下一条**——修好没有由重跑预检判。
3. 全部跑完后，用**逐字相同**的旗标重跑同一条预检命令**一次**。
4. 重跑的结果一出来就定性：
   - 通过：**你在这之后写的第一句话就是「预检首次退 69，已自动校准后通过。」**（原文就在这里，照念，不必回去找第一次预检的 JSON），
     然后才念 `warnings`、照常往下走；
   - 仍失败（任何退出码）：**停止**，一并转述：第一次预检的失败项；每次 doctor 的退出码、`blockers`、`warnings`，
     以及 `deadline.sections` 里各段的 `state`、`notes` 与 `rerun`（没探完的段连同 `note` 原文）；第二次预检的失败项。
     请用户在终端跑仍失败那几家对应的 `rerun`。第二次预检的 `recalibration` 即使可校准也**不再**自动校准——每次预检至多一轮。

通过时若 `warnings` 非空，把每一条的 `detail` 原样念给用户，**然后继续**，不停下来等确认——警告不阻断，要不要处理由用户决定。

### 3. 启动双审并等待

先运行：

```
TV review --start --entry B --stage plan --topic <主题> --driver qoder-cn --focus <提示语> [--goal <任务目标>] [--plan-file <路径>] [--max-rounds <n>] [--model-claude <模型>] [--model-codex <模型>] [--model-gemini <模型>] [--model-glm <模型>] [--tier-claude <档>] [--tier-codex <档>] [--tier-gemini <档>] [--tier-glm <档>] [--effort-claude <值>] [--effort-codex <值>] [--effort-gemini <值>] [--effort-glm <值>] [--profile-claude <名>] [--native-claude] [--profile-codex <名>] [--native-codex] [--driver-model <模型>] [--driver-provider <供应商>] [--profile <名称>] [--context …] [--critics <id,…>] [--allow-single] [--driver-model <模型>] [--driver-provider <供应商>] --json
```

`--entry B` 标记本次运行由命令 B 发起，记入 run.json 留痕；它也让 CLI 按 B/C/D 规则
校验焦点必填（缺 `--focus` 退 64）。

Driver 会话声明从 resolve 输出的 driver_model / driver_provider 逐项透传至 preflight 与 review --start 的 --driver-model / --driver-provider；null 则不传。只记录声明，不推断当前会话模型。

若上一步 resolve 输出的 `task_goal` 非空，把它原样传给 `--goal`。它与 `--focus` 是两回事：
前者说「这次要达成什么」，进 BRIEF 第 4 段；后者说「这次重点看什么」，进第 2 段。
省略 `--goal` 时编排器会回退到 `task.json` 已记录的目标或同主题计划定稿。

把 resolve 输出的 `prompt_hint` 原样传给 `--focus`。本步走标准 argv 解析，
按普通命令行写法给带空格的值加引号即可，不涉及第 1 步那套拼串规则。

若 resolve 输出的 `profile` 非空，把它原样传给 `--profile`。它换的是本次运行的
模型档位（`config.yaml` 的 `profiles`），与 `--model-*` 不冲突——后者指定具体模型、
优先级更高，前者只换默认值表。档位不存在会退 64 并列出可用值。

若 resolve 输出的 `subject_path` 非空，把它原样传给 `--plan-file`。
resolve 用它定位被审对象，而 `--start` 会**重新定位一次**——不传就自动取
`plan/` 下最新的一份原稿，用户显式指定的那份会被静默换掉，
而 resolve 阶段的存在性校验反倒让一切看起来正常。

**把 resolve 输出的 `critics` 数组用逗号连接后传给 `--critics`，无条件传。**
它是本轮**入选的审核者集合**，resolve 已经解析并校验完：默认值回落、旧旗标 `--only`
的单元素形态、各项合法性，全都在里面了。照抄即可。
不传不会报错——`--start` 会自己再取一次配置默认值——但用户写的 `--critics` 就此消失，
而留痕里记的入选集合看起来一切正常。这与 `--base` 漏传是同一族缺口：不报错、审的不是
用户以为的那几侧。

**不要传 `--only`。** 它是 `--critics` 的单元素旧写法，用户写了它，resolve 会把结果
并进 `critics` 数组并把 `only` 置为 null——你手上根本拿不到可传的值。
两个旗标同时递给 `--start` 会被判互斥并退 64（那是给**用户**同时写两个准备的拦截，
不是给你的）。

`allow_single` 为 true 时加上 `--allow-single`：那是用户显式要求的降级，
允许一侧失败时不中止、产出结果并留痕（§12.4）。
**漏传的后果是静默忽略用户的要求**——一侧失败就整次失败，
而留痕里看不出用户曾经要求过降级。

**多轮评审循环（EV-247）**：每个审核者给出「通过 / 修改后通过 / 不通过」三档结论，编排器按侧计票——
不通过占半数及以上即本轮判不通过，你按裁决改完计划后**自动重审**（见第 6.5 步），直到通过或到最大轮次。
resolve 输出的 `max_rounds.plan` 非空时传 `--max-rounds <它的值>`，为 null 则不传（编排器取配置 `review.plan_rounds`，没配为 3 轮；上限 10）；
重审的各轮照传同一个值——轮次链中途改上限会退 64。`--start` 返回的 `review_loop` 给出本轮是第几轮、最多几轮，
开场播报里一并念出「评审循环第 k/N 轮」。

若 resolve 输出的 `models` 字段非空，把其中的模型覆盖逐个原样传给对应的
`--model-<审核者 id>`（`models` 的键就是审核者 id：`--model-claude` / `--model-codex` / `--model-gemini` / `--model-glm`）。
**用户指定的模型只在这一步才真正生效**——第 2 步的预检只拿同一组覆盖值做校验，
`--start` 不会沿用它（`--start` 自己再校验一次 slug，见 `review.ts` 的 slug 校验注释），漏传会静默回退到
profile 配置模型，且留痕里记的就是回退后的模型，事后看不出用户曾经指定过。

resolve 输出的 `tiers` / `efforts` / `vendor_profiles`（M11 第 5 步）同理：逐项原样传给对应的旗标。接入字段缺席表示继承；vendor_profiles 中显式 null 必须传 --native-<审核者 id>，非空传 --profile-<审核者 id>，同侧不同时传。
`--tier-<审核者 id>`（`--tier-claude` / `--tier-codex` / `--tier-gemini` / `--tier-glm`）、`--effort-<审核者 id>`（`--effort-claude` / `--effort-codex` / `--effort-gemini` / `--effort-glm`）、`--profile-<审核者 id>`（`--profile-claude` / `--profile-codex`），
与第 2 步的预检同一组。漏传会静默回到档位表与 `default_tier` 的取值，留痕里记的是回落后的档位与来源。思考等级与厂商 profile 随请求下传给各家（M11 第 6 步）；取值不合法（枚举外、该侧没有这个概念、厂商 profile 不在本机名单）由预检退 64、gemini 的 slug 已编码档位时只告警——照样原样传，不要自行去掉，拒绝由编排器给出。

它会冻结送审包、派生工作进程后**立即返回**，输出含 `run_id`、`max_waits`、
`wait_timeout_s`、`bash_timeout_ms`，以及开场播报要用的 `stage_timeout_s`
与两侧生效 `models`。

返回含 `finished_inline: true` 时（FR-23 纯文档跳过），**没有工作进程也没有进度**：
跳过下面的开场播报与 `--wait` 循环，直接把 `notice` 转述给用户并收尾。

**`--start` 返回后立刻向用户播报一条**：主题、阶段、两侧模型（`models`）、
本阶段预算（`stage_timeout_s`）、汇报节奏（约每 `wait_timeout_s` 秒一次）、`run_id`；
并告诉他想看本次运行的实时进度用 `TV review --status <run_id>`，想看全局闸门与
降级记录用 `/dual-status`，想中止用 `TV review --cancel <run_id>`。
这些值**一律取自返回值**，不要写死——模型经 profile 与 `--model-*` 覆盖路由，
写死就会漂移成错误播报。

`--start` 返回的 `warnings` 非空时，在开场播报里逐条原样念出 `detail`，并提醒：想中止就用 `TV review --cancel <run_id>`。
这条警告是按**本轮实际入选侧**、在拉起前复查的（第 2 步的预检已按同一组查过，两步之间配置或探活结论可能变）；
它随返回值到达时审查已经拉起，拦不住拉起，但能让用户立刻决定要不要中止。

然后循环运行：

```
TV review --wait <run_id> --timeout <wait_timeout_s> --json
```

> **每次 `--wait` 的 Bash 调用必须把工具级超时设为返回的 `bash_timeout_ms`。**
> Bash 工具默认超时是 120s，而 `--wait` 会等满 `wait_timeout_s`——不设就必被
> 工具超时杀掉，这一条是本命令能否跑通的前提。
>
> 若某次 `--wait` 因工具超时而拿不到退出码：**按「仍在运行」处理**，
> 计入 `max_waits` 预算后继续下一次 `--wait`。工作进程不受影响，仍在跑。

**每次 `--wait` 返回后，先向用户发一条文本消息，再发下一次 `--wait`。**
这条消息是**给用户看的**，不是工具输出——工具输出在折叠视图下用户看不到，
只打印不等于反馈。内容用返回里的 `progress_brief`，原样念一行即可：不要改写、
不要合并、不要「等下一次一起说」。退出码 `73` 与 `0` 都要说。

若两侧状态较上次有变化（`running`→`ok`、`attempt` 增加、出现 `note`、某侧进入作废重跑），
在那一行后面补一句说明变化。**状态不变时不要补**——每次都写只会淹掉真正的变化。

退出码含义：`73` 仍在运行（播报后继续等）；`0` 两份审查文档与元数据已落盘
（播报总耗时与两份文档路径后进下一步）；其它按原样转述并停止。
循环次数上限以**最近一次** `--wait` 返回的 `max_waits` 为准（`--start` 给的是初值；某侧读到对端产物、
作废重跑时，编排器会追加一个单侧超时的份额），超限则停下求助人工。

### 4. 完整读取两份审查文档

用 Read **读全文**，禁止只读摘要段。两份都要读。

### 5. 写裁决件

依 `trivium.disposition.v1` 写出 `…-revised-<当轮 Driver>.md`（后缀是**你自己的 Agent id**，
不是固定的 `claude`；`role` 字段填同一个值，两者不一致闸门会判 `bad_front_matter`）：

- front-matter 含 `schema` / `topic` / `stage` / `role` / `kind` / `run_id` / `addresses`；
  `addresses` 逐一列出本轮**每个出了结论的审核者**的审查文档文件名（照抄归档里的名字；失败侧不列），**不是意见编号**——
  份数不符、列了别的轮次或编号，闸门判 `bad_front_matter` 并给出期望的文件名；
- 正文含一张裁决表，列名固定：意见编号 ｜ 来源 ｜ 严重度 ｜ 裁决 ｜ 理由 ｜ 落点；
- **每个**意见编号都必须出现且仅出现一次，裁决取值为 接受 / 驳回 / 暂缓；
- 三种裁决**都**要有非空理由；**接受**必须写明落点；
- 禁止静默忽略任何一条（FR-14）。即使全部驳回也必须产出本件并写明「无修改及原因」。

**每一轮都同时写一份新版本的完整计划**（§6.6 规则 9，EV-214；EV-247 起不再只在有「接受」时才写）：

- 文件名 `…-r<N>-<当轮 Driver>.md`，写在本主题的 `.reviews/<主题>/plan/` 下——原稿经 `--plan-file` 来自归档外时也一样（闸门与代码阶段只在那里找新一轮计划）；N 比本轮被审对象的轮次大 1（第 1 轮即 `r2`），后缀同样是**你自己的 Agent id**；
- 开头列「相对上一轮的改动」，**逐条引用**被接受意见的编号（整份回退侧的 `<前缀>-F<n>` 也要写），再给出合入后的完整计划；
  全部驳回或全部暂缓时，开头写明「本轮无改动」及原因，再照抄完整计划——不能省略这份文件；
- 本轮判不通过、要重审时，下一轮送审的就是它；判通过 / 修改后通过时，它就是代码阶段送审的「本主题计划定稿」——代码审查员读的是轮次最大的那份计划。写完之后不要再另写更高轮次的计划而不送审。

闸门对带轮次链（`review_loop`）的轮次核两件事：这份文件存在（不论有无接受项），每个被接受的编号在其中整词逐字出现；缺了判 `missing_next_plan` / `next_plan_missing_ids`，并给出应写的文件名或缺的编号。它只核字面，不核合得对不对。早于 EV-247 的旧轮次仍按「有接受项才要求」判。

### 6. 校验裁决完整性

运行 `TV gate --stage plan --topic <主题> --check --json`。
若返回缺失编号，补齐后重跑本步；重跑最多 3 次（首次校验不计），
仍不通过则向用户说明缺口并停下，交给用户处理。

`failures` 含 `task_unreadable` 时**不是裁决缺口**：审批正本 task.json 读不出，补裁决件无济于事，
也不计入上面的重跑次数。原样转述后停下，由用户在终端恢复正本后再重跑本步。第 7 步的停点命令遇到同样情形也退 2，照此处理。

### 6.5 按计票结论分支（多轮评审循环，EV-247）

第 6 步通过后，先把返回里的 `round_line` 原样念给用户（「第 k/N 轮 · 计票… → 结论 · 下一步」），再按 `next_action` 走：

- **`rerun`**（本轮不通过、还有轮次）：闸门已回 idle，**不要**跑第 7 步停点。回到第 3 步重新 `--start`，
  旗标与本轮同一组（同一个 `--max-rounds`）；被审对象换成第 5 步刚写的新一轮计划——用户最初没给 `--plan-file` 时
  **不传它**（自动取轮次最大的那份），给过时改传归档内新一轮计划的路径，不要再传原稿。每一轮照常读全文、裁决、写新一轮计划、校验。
- **`proceed`**（通过或修改后通过）：进第 7 步停点。第 5 步写的新一轮计划就是定稿，审批后按它实施。
- **`human_review`**（已到最大轮次仍不通过，或本轮有效结论不足：有效票不到入选侧数的一半）：进第 7 步停点，停点话术会注明需人工审核。
- `next_action` 为 null（本轮不在循环里，如旧版编排器）：照旧进第 7 步。

### 7. 停点

运行 `TV gate --stage plan --topic <主题> --await-approval`，
把它输出的停点话术与三份文档路径转述给用户，然后**停止**。

**审批的发起权在用户手里。** 转述完就停下等他，不要自己去跑 `approve`——
技术上你做得到（`approve` 不校验调用来源），正因如此这句才写在这里。

**此后不得开始编写或修改任何业务代码。** 等用户 `/dual-approve` 之后才能继续。
