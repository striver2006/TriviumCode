## 决策内容

### 判据一：旗标按「取值是否必须实测才知道」分层

> **本节是起草时认知，已被两轮代码双审改写，以主设计 §11.1 为准。**
> 下表的三分类已改为**两问式 + 四类**（新增「厂商依赖关系与参数形态」）；
> 「尺度类」一行把成本闸门与轮数写成归 `CriticRequest`，而那两个字段**当时并不存在**。
> 保留原表是刻意的——它记录了「凭旧分类会写出什么」，重写就把这份证据抹掉了。

| 类别 | 归属 | 落点 | 理由 |
| :-- | :-- | :-- | :-- |
| **安全不变量**（只读保障，缺一即失守） | 探针 `readonly_flags` | 适配层经 `readonlyArgsFromProbe` 取 | 厂商漂移会让旗标失效；只有实测能证明它**真被接受**（codex 的值是负对照挣来的，见 `adapters/codex.ts` 的 `readonlyArgsFromProbe` 文档块） |
| **调用形态 / 机制类**（输出格式、`--verbose`、prompt 载入方式、cwd、颜色、跳过 git 检查） | 适配层 `buildXxxArgs` | 硬编码 | 取值由**编排器自己的需求**决定（要事件流才要 `stream-json`），不是厂商能力事实，探针记它没有信息量 |
| **尺度类**（模型、成本闸门、超时、轮数） | `CriticRequest` / 配置 | 适配层按请求拼 | 探针尺度 ≠ M9 尺度；r4 已据此把 `probeArgs` 剥离为探针私有 |

三家现况本就一致，不是「zcode 孤例」：
`adapters/agy.ts` 的 `buildAgyArgs`、`zcode.ts` 的 `buildZcodeArgs`、`codex.ts` 的 `buildCodexArgs`
全部把机制类旗标硬编码在适配层。`ClaudeProbe.readonly_flags` 的字段注释也早写着
「**消费方**：M9 适配器构造命令行（P7）」——代码里的 P7 口径一直是「只读保障走探针」。

### 判据二：`readonly_flags` 有两种形态，决定适配层怎么取

| 形态 | 哪几家 | 适配层做法 |
| :-- | :-- | :-- |
| **可直接使用的 argv 片段** | claude（`READONLY_INVARIANTS`）、codex（`['-s','read-only']`） | **原样透传，不得字面重建** |
| **候选串的接受记录**（前缀形态） | zcode（`--mode plan` / `--disallowed-tools …`） | 取旗标**名**，值另给全集常量（探针试精简版、适配层要全集，理由已在 `adapters/zcode.ts` 的 `readonlyArgsFromProbe` 文档块） |

→ **`adapters/claude.ts` 按 codex 同款透传写**，不是按 zcode 写。这一条同时消除了
EV-12 所说的「zcode 先例与 P7 互相矛盾」——两家做法不同是因为**探针落盘的形态不同**，
不是原则冲突。

### 判据三：P7 的适用面澄清

P7 禁止的是「把设计文档列出的命令行抄进代码」，**不是**「适配层不得出现任何旗标字面量」。
就地纠正两处失实转述（见下方落点表）。
