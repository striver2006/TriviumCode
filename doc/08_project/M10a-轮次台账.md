# M10a 轮次台账

> **用途**：M10a 计划 §7.2 的触发口径落点。每轮双审收尾时追加一行，
> 核对累计轮次与累计墙钟是否触及阈值；触及则按纪律 1 回补估算并向用户报告。
>
> **为什么要有这份文件**：§7.1 给的是**估算**（17～25 轮 / 3～4 周），而估算只有在
> 能与实际比对时才有意义。上一版计划把阈值和估算写在计划里、却没有任何地方记实际值，
> 「超阈值就报告」就无从执行——计划双审 r6 的 CODEX-08 与 GLM-05 两侧独立命中这一点。

## 0. 口径

- **计数论域**：双审轮次，**plan / code 分栏计**，含本计划自身已耗与后续，
  也含**前置小主题**（EV-74 / EV-79）各档。
- **一轮 = 一次 `review --start`**，无论结论如何。**作废轮照计**——
  它消耗的墙钟、配额与人工是真实的，不计会让台账系统性低报
  （本主题 plan r4 就是一次脚本级超时导致的整轮作废）。
- **阈值**：累计轮次 > **33 轮**（§7.1 总计上限 25 的 1.33 倍），
  或累计墙钟 > **6 周** ⇒ 按纪律 1 回补估算并报告。
- **起点**：**r1 当天（2026-09-21）**，不是本计划落笔日。
  > 计划 §7.2 原写「起点写死为本稿落笔日」，同一节又要求「首行播种 r1～r6 的历史行」——
  > 两句并存时以播种为准，否则台账累计恒比论域少 6，阈值比对的两端不同源。
  > 计划双审 r6 GLM-05 算过这笔账：按那个写法，「>28」实际要跑到 33 轮才响，
  > 1.33 倍裕量会被悄悄放大成 1.57 倍。

- **轮次号的两套编号**：本表的「轮次」是**审查轮次**（`run.json.rerun_index`），
  与原稿文件名里的 `-r<N>` **不是同一套**（计划 §3.1.5）。
  例：plan 第 5 轮审的是 `-r4-` 那一稿。
  > 被审对象的**路径**今天不在运行留痕里（`artifacts[]` 只登记 `_meta` 工件与审查文档，
  > 原稿只有 `subject_sha256`、无路径）。第 2 步（EV-55）的 3.1.1 会把它补上，
  > 补上之后本表可加一列「被审对象」。在那之前不手写，避免台账出现不可核对的断言。

## 3. 记账纪律

- **每轮双审收尾时**追加一行——不是每天、也不是收口时补记。
  补记会让「作废轮」这类最该被看见的行最容易漏掉。
- run_id、日期、耗时**从 `run.json` 取**，不凭记忆写。
  取数脚本见本节末；三侧结论与裁决条目数同理，分别取自审查文档与裁决件的 front-matter。
- 触及阈值时：**先报告再继续**，不要自行决定「差不多还行」。
  阈值设在上限的 1.33 倍就是为了让触发本身成为一个信号，
  而不是一个需要判断要不要理会的提示（r4 曾把阈值设成与上限相等，正常进度就会触发，
  那样的提示会被训练成噪声）。

**取数口径**（避免下一次又凭记忆填）：

- 轮次 / 日期 / 耗时：该主题 `plan|code|bug` 各档 `_meta` 下的 `run-*.json`，
  读 `rerun_index` / `started_at` / `finished_at` / `status`。
- 三侧结论与是否回退：各侧审查文档 front-matter 的 `verdict` / `parse_fallback`。
- 裁决条目数：裁决件 front-matter `addresses` 的长度（即 `gate --check` 核对的编号集）。
