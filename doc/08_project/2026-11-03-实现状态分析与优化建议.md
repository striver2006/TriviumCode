## 3. 优先处理的问题

### 3.1 P0：证据达标需要接入失败策略、计票和闸门

**性质：静态确认的实现与设计不一致；完整触发链本轮未动态复现。**

主设计明确要求：证据不足侧不得计为合格审查的一侧，应按策略严格中止或降级。工具调用和项目上下文下限不足还应触发相应重试。依据见[主设计 §11.4](../02_design/2026-09-10-Driver-DualCritic主攻双审流水线设计.md#L3144)。

当前代码却可能形成以下路径：

```text
审核进程 status=ok
  → guard 判 evidenceOk=false
  → decideMode 仍判 full
  → 运行 success
  → 该侧继续计票
```

失败策略主要依据进程结果状态；计票排除了失败、解析回退和泄漏作废，却没有排除证据不足侧；gate 也没有再次消费 `evidence_ok`。落点见 [runner.ts](../../src/trivium/runner.ts#L453)、[review.ts 的失败策略入口](../../src/trivium/review.ts#L1740)和[计票入口](../../src/trivium/review.ts#L2261)。

已有故障注入测试只断言“零工具调用时 `evidence_ok=false`”，没有继续断言中止、降级、计票和闸门结果，因此测试可以通过，而产品承诺仍未闭环。见 [fault-injection.test.ts](../../test/integration/fault-injection.test.ts#L368)。

建议建立统一的“本侧是否可采信”判定，由失败策略、计票和 gate 共用。执行失败、证据不足、解析失败、独立性失效应分别留痕，避免压成一个布尔值。恢复设计要求时应同步核对重试预算、降级语义、轮次计票与历史兼容，不直接修改历史运行件。

同时先细化 `consulted_unverified` 的原因。项目外依赖、搜索输出未采集、路径归一失败都可能造成匹配不足，不能直接解释成模型编造。目前它与 `evidenceOk` 独立计算，详细匹配结果也没有完整保留。见 [guard.ts](../../src/trivium/guard.ts#L448)。

验收至少覆盖严格模式、降级模式、有效侧不足三类完整链路，断言退出码、重试、`review_mode`、排票原因、整轮结论及 gate 后果。未达到编排器证据下限，不等于已经证明模型绝对没有阅读代码。

### 3.2 P1：捕获进度回写的异步异常

**性质：静态确认的异常处理缺口；触发场景本轮未动态复现。**

worker 的进度回调调用 `void patchStatus(...)`，没有捕获 Promise rejection；外层 `try/catch` 只能接住同步异常。磁盘满、权限异常或 Windows 重命名重试耗尽时，可能由一次进度写失败打断整个 worker。见[进度回写](../../src/trivium/run-protocol.ts#L1394)、[外层捕获](../../src/trivium/runner.ts#L117)和[状态写入异常出口](../../src/trivium/status.ts#L173)。

同文件的心跳和 CLI 记录更新已经正确添加 `.catch`，这处属于遗漏。建议统一封装允许失败的进度写入，并保留受限告警，避免高频错误刷屏。

验收应在真实 worker 子进程中注入一次进度落盘失败，确认两侧仍能完成、归档，且没有未处理 rejection。不要只用同步回调抛错来证明异步写盘失败已被接住。

### 3.3 P1：让遗留锁回收受总等待预算约束

**性质：静态确认的预算漏洞；永久失败场景本轮未测。**

遗留锁回收返回 false 后，代码休眠并直接 `continue`，绕过下方重试上限。若认领或 rename 持续失败，有限重试配置仍可能变成无界等待。见 [lock.ts](../../src/trivium/lock.ts#L412)。

建议给整个取锁过程增加统一截止时间，覆盖正常竞争、回收失败和状态反复变化。预算耗尽时保留旧锁，返回明确错误，并报告失败环节，不将安全拒绝改为自动放行。

验收重点是“持续失败也能按时退出”，同时确认不会删除活锁或错误放行。应使用真实跨进程场景验证持续回收失败，不只验证认领稍后释放时最终能够成功。

### 3.4 P1：统一一键安装前检、安装和后验的环境

**性质：静态确认的数据流缺陷；本轮未执行安装复现。**

一键安装在计算 `plan.runtimeRoot` 时使用原环境，随后只给安装子进程删除 `TRIVIUM_ASSET_ROOT`；装后版本检查和自检继续使用旧计划中的路径。见 [quick-install.mjs](../../scripts/quick-install.mjs#L49)，环境来源见 [install.ts](../../src/install.ts#L53)。

这会造成实际安装目标与验证目标不一致：可能安装到默认目录，却检查源码或旧自定义目录；也可能安装成功后错误报失败，或前检使用了与安装不同的目标。

建议五个步骤共用同一份归一化环境，并核对实际安装 bundle 的哈希。隔离测试覆盖变量未设置、指向源码、指向旧版本、指向不存在目录四种情况，不操作用户个人安装或全局配置。

### 3.5 P1/P2：验证并消除 status.json 的跨进程覆盖窗口

**性质：静态竞态风险，尚未复现，应先做故障注入验证。**

`patchStatus` 的队列只在同一进程内串行化，但父进程和 worker 都会读改写同一份状态文件。见 [status.ts](../../src/trivium/status.ts#L150)。

父进程补写身份时的终态检查只能看到已读快照，因此仍存在以下潜在交错：

```text
父进程读 running
  → worker 写 success
  → 父进程写回旧 running
```

相关写入见[父进程身份补写](../../src/trivium/run-protocol.ts#L692)和 [worker 终态写入](../../src/trivium/run-protocol.ts#L1409)。

建议优先用两个真实进程和屏障控制该交错。若复现，可改为 worker 独占状态写入，或采用跨进程锁与单调终态规则。此风险与已经持全局锁的 `state.json` 是两条路径，不应将两者混为一谈。

## 5. 维护成本、性能与故障复盘

### 5.1 按职责逐步收敛大模块

分析快照中，源码约 5.6 万物理行，包含注释与空行；`review.ts`、`run-protocol.ts` 均超过 2500 行，`hooks.ts`、`gate.ts` 等模块也较大。上述数字仅描述规模，不代表可执行代码行数或质量评分。

建议先建立第 3 节失败路径回归，再按“准备冻结、worker 执行、状态存储、取消恢复、归档收尾”逐步拆分。优先收敛重复状态规则，收益会高于单纯搬文件。拆分前后应以真实跨进程测试、冻结路线一致性和失败工件对账证明行为等价。

### 5.2 测量证据体积带来的实际成本

本次按 Git 跟踪文件的工作树内容统计，文件总量约 865 MiB，其中 `.reviews` 约 584 MiB、`doc/05_testing/evidence` 约 259 MiB，合计约占 97%。该口径不是 Git 历史对象库大小，也不是发布包大小。

这些原件有审计价值，但会增加检出、扫描、索引和材料选择成本。建议先测量冻结、漂移比较、审批摘要、脱敏扫描各阶段耗时及读入字节数，再确定优化点；本轮没有性能基准，不能给出已证实的延迟收益。

未来新增大型证据可评估内容寻址存储与仓内哈希清单，但这涉及归档契约调整，需要先形成方案并按既有流程评审；历史原件继续保留，不因体积优化删除或改写受保护工件。

### 5.3 完善重试分类和失败数据

可逐步完善失败分类、受总预算约束的退避，以及重试次数和耗时记录。

当前普通重试后抛异常的出口可能记成一次尝试、零耗时，会影响故障复盘和成本判断。见[异常结果记录](../../src/trivium/runner.ts#L330)。建议异常出口保留实际尝试次数与累计耗时，并覆盖“首次瞬时失败、第二次抛异常”的回归场景。

错误文本分类和立即重试也值得改为适配器归一的失败类型、是否可重试及重试等待提示；退避必须受总预算与取消控制，不能顺带增加默认调用次数或消耗配额。

## 6. 真实验收与保障边界

Windows 已有三审、取消、C/D、A 全流程真实 verify，以及 approve/abandon 的历史实测，不能继续沿用旧章节把这些全部列为未测；人工拒绝分支仍未测。见[扩展验收记录](../05_testing/REPORT_2026-10-29_Windows四家Agent验收.md#L116)。

Claude Windows Hook 复测已取得拒因、同 ID `permission_denials`、目标文件未创建三项关联证据；这证明对应组合成立，不能外推到所有客户端。见 [Hook 复测](../05_testing/REPORT_2026-10-30_W4-S3复测.md#L38)。

以下边界仍需保留：

- L2 不保证审批期业务写入被事前拦截，Hook 文件存在也不等于客户端实际加载并拦截有效。
- GLM/ZCode 子代理轨迹仍有核验覆盖盲区，已登记 EV-189；主会话零命中不能证明子代理未发生读取或执行。后续可先识别委派并标记未覆盖，再实现子会话递归采集。
- `readonly=unavailable` 与未检出写事件不等于证明了只读；正向写事件、漂移与能力缺口应分别表达。
- Windows 某第三方 Codex 路线禁入，不等于所有 Codex 路线不可用；官方路线与其他组合按各自证据标注。
- 当前真实模型路线、新主机、不同客户端和新 CLI 指纹的验收不能继承旧指纹结果。
- Bash Hook 的字面误拦属于明确接受的取舍，优化应落在诊断和结构化工具出口，不为 `git commit` 增加豁免。
- 模型族告警、单侧通过、整轮计票、gate 通过、人工审批和真实 verify 是不同事实，不能彼此替代。

## 7. 建议落地顺序

优先级用于本轮建议排序，不代表已获实施授权。具体工作量需在故障复现与方案确定后评估。

| 批次 | 工作重点 | 完成标志 |
| --- | --- | --- |
| 第一批 | 证据准入闭环、进度异步异常、锁等待上限、安装环境一致性 | 对应故障注入能证明失败处置正确，原正常路径保持通过 |
| 第二批 | status 跨进程验证、两平台回归、当前状态索引 | 同一提交具有两平台完整结果，当前版本与支持信息一致 |
| 第三批 | 模块拆分、性能测量、安装恢复、证据存储演进 | 维护和运行成本有量化改善，历史工件与契约兼容 |

第一批直接改善“审查结果是否可采信、异常后能否可靠退出、交付验证是否指向真实产物”这三个核心承诺。后续如实施，应继续遵循计划、审查、人工批准、实现、验证和 Git 交付各阶段的既有边界。
