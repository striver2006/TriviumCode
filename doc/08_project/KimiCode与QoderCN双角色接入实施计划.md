## 3. 工作包与依赖

### P0：完善受控取证，定位 Kimi 失败原因

主要落点：`scripts/acceptance/kimi-qoder-cn/probe.mjs`、Windows/Git Bash 包装、取证报告及新证据目录。保留已有 15 份证据，不覆盖失败样本。

1. 把 Kimi 权限配置拆成独立对照：无自定义规则、仅 allow、仅工具级 deny、deny 在前加 allow、allow 在前加 deny、仅路径 deny。每次只改变一个因素，记录生成配置的非敏感摘要和 hash。
2. 核对 CLI 真实路径、版本/hash、配置根、cwd、agent 文件、headless 模式及实际加载来源；不把 TOML 合法或 doctor 成功等同于规则已加载。不同版本、不同模式分开留痕。
3. 对 Read/Grep/Glob 分别覆盖普通文件正向、同行文件负向、敏感模拟文件、目录子树、夹具外 canary、相对/绝对/realpath、符号链接、中文空格路径。每组记录实际调用及结果。
4. 固定模型、提示词和夹具形状比较规则；模型没有尝试目标操作时判“未测”，不能判规则有效。运行设时限，先用最小失败对照定位，再扩展矩阵，避免无目标重复调用。
5. 只有在原生正确配置下取得真实拒绝，才把参数组合写入探针。仍泄漏时明确区分已排除假设、剩余假设和厂商限制，不直接定性所有 Kimi 版本不可用。

完成标准：可复跑最小复现、完整正反证据、明确根因或有依据的阻塞结论。官方文档称规则按首个匹配生效，且 `-p` 应保留静态 deny；这些仅作为实验假设，实测优先。[官方配置说明](https://github.com/moonshotai/kimi-code/blob/main/docs/en/configuration/config-files.md)、[CLI 非交互说明](https://github.com/moonshotai/kimi-code/blob/main/docs/en/reference/kimi-command.md)。

### P1：推进独立 Driver 接入与入口资产

主要落点：`agents/registry.ts`、`skills-src/carriers/` 与命令/片段、`entry-render.ts`、`install.ts`、相关安装与入口测试。先读对应设计，行为变化先同步设计。

1. 登记 `kimi`、`qoder-cn`、`KIMI`、`QODER` 及 L2 事实；所有后缀、禁读矩阵、保护集、身份校验继续从注册表派生。默认选侧不变；审核准入不随 Driver 开关自动放开。
2. 逐客户端确认技能目录、共享目录、指令文件、调用语法、参数透传、cwd 和重名处理。只有真实差异才启用 r2 的可选多载体描述；同一物理目录去重，不同内容重名报错。
3. 完整生成四条任务入口和 approve/status/abandon，源文件修改后统一 `npm run render`，同时覆盖安装、更新、卸载；不手改生成物。
4. 补注册表/Schema 对账、默认集合不变、自审拒绝、旧配置兼容、跨进程 Driver 交接、入口渲染零漂移及安装查重测试。

完成标准：自动化通过、入口安装内容一致；真实客户端验收单列，不能以安装成功宣称五入口已验收。Windows 尚无证据时保持该平台“未测”。

### P2：Qoder 模型回退处理与原生模型路由

主要落点：新厂商适配/探针模块、配置类型与 Schema、tiers/路由、worker 请求快照、轨迹解析与模型测试。可先构建受控实现及测试，生产审核接线以 P3 为前置。

1. 从实际官方目录或原生配置解析默认值和来源，验证官方路线；缺失时明确报配置缺失。不能把实验 auto 直接填成产品默认。2026-10-28 P2 实施已取得 1.1.80 隔离官方目录与省略模型时 Auto 标签证据；它可作为已验证原生路由默认，底层身份仍为 null/unverified，不能视作具体默认模型。
2. default/flash/pro 使用同一已解析默认值；显式覆盖优先但必须符合原生路线。请求、配置声明、运行回读分别保存；Auto 仅为路由标签时，底层模型保持 null/unknown。
3. 能从可靠目录判断的无效显式值在启动前失败；目录获取/解析失败也不得猜测或回退到另一模型。运行流检测原生回退警告或明确路线变化后中止，并使编排结果失败，不接受已产生的审查结论。
4. 记录客户端原始退出码、编排失败原因、原请求和可得的生效标签；静默且无法回读的变化不伪称检测成功。验证分块流、stderr/stdout、告警先于/后于工具事件、退出 0、取消和断流。
5. 默认来源在探针期绑定，按 r2 冻结到 requested_routes；worker 逐项核对，不在子进程里重新猜默认。历史 v1/v2 工件不补写新字段。

完成标准：真实无效模型反例在编排层失败，正常原生默认及显式有效覆盖有正对照；任何未知回读如实保留。

### P3：两家审核者的严格只读准入

依赖 P0 对相应侧的隔离结论及 P2 路由结果。主要落点：各侧适配器、探针、轨迹解析、审核镜头、能力记录及准入检查。

1. 生产工具面只开放必要 Read/Grep/Glob；关闭写入、Shell、子代理、MCP、网络和其它外部执行。工具列表回读与实际调用轨迹分别取证。
2. 在可丢弃夹具中建立必要的无害正向执行控制，再用对应拒绝配置验证真实工具调用被拒。正向放开只存在于控制臂，不流入生产配置。
3. 对被裁掉工具，优先使用官方支持的受控调用接口验证实际分发拒绝；没有接口或无法触发实际调用时登记“未测/阻塞”。不以自建模拟分发器、模型口头拒绝或提示词代替。
4. 核验同行工件、敏感路径及临时认证目录隔离；覆盖搜索绕过、共享技能、项目 Hook/MCP/插件和配置叠加。Qoder 已观察到共享技能及 SessionStart hook，必须核清能否引入执行能力。
5. 按实测填写 TraceCapability，覆盖调用、结果、拒绝、终态与缺失事件；轨迹不完整则失败。准入绑定平台、CLI/hash/版本、模型、参数及隔离配置指纹和有效期，变动后重新取证。
6. Node 侧超时/取消沿用公共设施；确认整棵进程树退出后清理凭据，补启动失败、强杀、失联回收、取消重复调用测试。临时文件权限与 Windows ACL 分开真实验证。

完成标准：该侧在该平台所有安全必需项均有真实正反证据；缺一项不启用生产审核路线，不降低标准、不借用另一侧或另一平台结果。

### P4：完整审查、自动化与本机运行时核对

1. 同步设计、协议、开发日志、使用/部署手册、测试报告和目录索引；交付文档使用现行中文名称。保留旧审查工件及配置兼容行为，不自动改产品版本。
2. 使用原定审核集合进入正式代码审，逐条裁决后按 gate 行动。代码审范围需包含本次实际实现及必要取证修改；前置脚本已提交，不能机械地用当前 HEAD 漏掉需复审的相关差异，先核定基线和上下文。
3. 覆盖注册表与 Schema、入口渲染、安装查重、自审、配置兼容、轨迹解析、跨进程交接、归档防覆盖及异常清理。运行 `npm run check`、现有 selftest、正式 verify；三类结果单独记录。
4. 按项目规则构建并重装本机运行时和本次入口，核对 wrapper 目标、版本、bundle hash 和生成入口内容。历史构建 hash 不作为本次运行证明。

完成标准：正式代码审与 gate 闭环，检查及 verify 有真实退出码和工件；失败按状态机处理，不自行审批或扩大轮次。

### P5：macOS 与 Windows 逐客户端验收

每个平台独立覆盖五个 Driver 的完整七技能清单、四任务入口、Driver 身份、参数/cwd、裁决、适用人工停点、恢复及放弃。审批测试只在专用验收主题，且审批由 Bob 明确发起。

macOS：本机执行，桌面控制超时需先恢复可用会话。Kimi VS Code 必须取得 Extension Host 内实际加载和调用日志，终端 CLI 结果不能替代。Qoder 核对 CN 应用身份和原生路线。无法操作或取证的条目保持“未测”。

Windows：交付可复跑 PowerShell 和 Git Bash 脚本、原生进程调用说明、五入口界面步骤及脱敏证据清单，由 Bob 执行回传。验收还包括中文空格路径、进程树取消、临时凭据 ACL/清理，以及同一审核集合的真实预检。核验回传的平台、版本/hash、命令、时间、正反对照和完整事件，缺证不得补推为通过。

完成标准：两平台五个 Driver 和两家审核者逐项有合格证据。Windows 未回传时交付所有可独立完成的代码和材料，整体需求仍标记未完成。
