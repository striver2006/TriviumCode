## 2. 术语扩展（在主设计第 0 章术语表之上**只增不改**）

| 术语 | 含义 |
| :--- | :--- |
| Agent | 一家厂商编程 Agent 的注册项：`claude`（Claude Code）、`codex`（Codex）、`gemini`（Antigravity）、`glm`（ZCode）。Agent id 是配置与 CLI 的命名空间 |
| 注册表（Registry） | `AgentDescriptor` 的唯一登记处，全部后缀/前缀/键名由它派生（§5.1） |
| Driver | **当次运行的属性**：发起四条命令的交互 Agent，记入 `run.json.driver`。不再是系统常量「Claude Code」 |
| Critic / 审核者 | 当次运行被 headless 拉起的只读审查 Agent，集合记 `critics_selected`，基数 1～3 |
| 归档后缀（suffix） | 工件角色后缀，标识**产出方 Agent**，取值与 Agent id 一致：`claude` / `codex` / `gemini` / `glm`。历史三值 claude/gemini/glm 本就是模型名、无需迁移；Codex 取产品名而非模型名——它运行 QWen/DeepSeek 等多个模型家族，模型名做后缀无法唯一标识产出方（2026-09-13 项目负责人裁定，多家族化后此裁定更为必要） |

| 档位（tier） | 「模型 + 思考等级」的预设组合，取值 `low` / `medium` / `high`，配置于 `agents.<id>.tiers`（§5.4） |
| review_mode | `full`（全部入选审核者 ok）/ `partial`（部分失败后降级续跑）。旧值 `dual`/`single` 读取时映射（§6.3） |

### 3.1 Codex（OpenAI Codex CLI，承载 QWen/DeepSeek 等多模型）

| 能力 | 事实 | 置信度 |
| :--- | :--- | :--- |
| 非交互入口 | `codex exec "<任务>"` 无 TUI、无审批交互，最终输出到 stdout；`-C <dir>` 设工作目录；`--ephemeral` 独立不落会话；`-o <file>` 把最终回答写文件 | 官方文档 · 高 |
| 沙箱 | `codex exec` **默认即 read-only 沙箱**；`--sandbox read-only\|workspace-write\|danger-full-access` 三档 | 官方文档 · 高 |
| 结构化事件流 | `--json`（原 `--experimental-json`）输出 JSONL 事件流（含 `thread.started` 等生命周期与工具事件）；`--output-schema <schema>` 可约束最终输出形状 | 官方文档 + 社区实测 · 中高 |

| 配置与隔离 | 配置在 `~/.codex/config.toml`；`model_providers` 支持 OpenAI 兼容端点，**多模型家族并列**（QWen 经 DashScope/千问 Token Plan 兼容模式、DeepSeek 经其 OpenAI 兼容端点，各自一条 provider，目录以此开放）；QWen3.8 系列还需元数据文件 `~/.codex/model-catalog.local.json` 并在 config.toml 设 `model_catalog_json` 指向它（含 `default_reasoning_level` 等）；provider 须 `wire_api = "responses"`（新版 Codex 已不支持 `chat`）；环境变量 `CODEX_HOME` 重定向配置根 | 千问 Codex 接入文档 + 官方文档 · 高（`CODEX_HOME` 对凭据/探针的生效性待实测） |
| 自定义命令 | `~/.codex/prompts/<name>.md` 自定义提示词，会话内以 `/name` 调用；参数展开能力（`$ARGUMENTS` 等）**待实测** | 官方文档 · 中 |
| 路径级 deny | 无已知机制；沙箱管的是「写与网络」而非「读路径」 | 推断 · 中（负对照实测） |

**模型目录与思考模式（2026-09-13 项目负责人指定四模型；枚举为官方文档口径）**：

| 模型 slug | 家族 | 思考开关 | effort 原生枚举 | 默认 | 置信度与备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `qwen3.8-max` | QWen | 混合思考，`thinking` 可开/关 | `low \| medium \| xhigh` | `xhigh` | 千问 Codex 接入文档 · 高（**无 high 档**） |
| `qwen3.8-flash` | QWen | 同上 | `low \| medium \| xhigh` | `xhigh` | 枚举未单独核实，按系列口径推定 · 中（M6 钉死） |
| `deepseek-v4-pro` | DeepSeek | `{"thinking": {"type": "enabled"\|"disabled"}}`，默认开 | `low \| high \| max` | `high` | DeepSeek 官方 thinking_mode 文档 · 高（**无 medium 档**） |
| `deepseek-flash` | DeepSeek | 同上 | `low \| high \| max` | `high` | 官方文档示例即用此 slug；与 v4 系命名的对应关系 · 中（M6 钉死） |

两条对设计有实质影响的官方事实：

1. **两家 effort 枚举不一致，且都不是 trivium 的 `low/medium/high` 字面集**：Qwen3.8 无 `high`（最深思是 `xhigh`），DeepSeek 无 `medium`。trivium 三档到原生 effort 的映射因此**只能在 tiers 组合里显式声明**（§5.4），实现禁止假设统一枚举。
2. **DeepSeek 存在请求值归并映射**：`minimal/low→low`、`medium/high/xhigh→high`、`max/ultra→max`——「请求 medium 实际生效 high」。因此 `effort_effective` 必须与 `model_effective` 一并回读入档，不采信请求值（AC-13 纪律对 effort 的延伸）。另：DeepSeek 思考模式下 `temperature` 等参数不生效、带 `tools` 的请求须回传历史 `reasoning_content`（否则 400）——Codex 作为客户端是否正确处理，列为 M6 观察项。

**结论与对策**：
- 多模型接入的**前提条件**是用户侧在 `config.toml` 的 `model_providers` 按家族逐条完成 provider 配置（QWen、DeepSeek…各一条兼容端点 + 凭据；QWen3.8 系列另需 `model-catalog.local.json`）。本项目的处置遵循「不猜测执行、不动全局配置」：`doctor` 逐家族**探测并展示**可粘贴的配置样例（含 QWen 的 catalog 文件样例），由人写入（同 `verify` 命令的候选确认模式，主设计 14.1）；运行期模型/effort 覆盖优先走 `-m`/`-c` 旗标，旗标不支持时经 `CODEX_HOME` 指向每运行独立副本（拷入凭据、`0600`、跑完即删——同 ZCode `home_copy` 手法）。
- 只读：`--sandbox read-only` 是**默认值且语义正确**（禁写禁网络），比 ZCode 侧更干净；证据靠 JSONL 事件流。风险点在「事件流里能否稳定取到**读取路径**」（对应 `project_reads` 下限与轨迹核验），这是 M6 探针的必测项。

### 3.2 Claude Code headless（作为**审核者**被拉起）

| 能力 | 事实 | 置信度 |
| :--- | :--- | :--- |
| 非交互入口 | `claude -p "<任务>"`；`--output-format text\|json\|stream-json`（stream-json 需配 `--verbose`），每个会话以 init 事件开始（含会话标识） | 官方文档 · 高 |
| 工具裁剪 | `--allowed-tools` / `--disallowed-tools`（如 `"Read,Grep,Glob"` 白名单）；`--max-turns <n>` 限轮数 | 官方文档 · 高 |
| 模型指定 | `--model <slug>` | 官方文档 · 高 |
| 结构化输出 | `--json-schema` 约束最终输出形状 | 官方文档 · 中高 |
| 项目信任 | headless 在未信任目录/未登录态下的行为（信任提示、`hasTrustDialogAccepted` 等）**待实测** | 待探针 · — |
| 轨迹 | `stream-json` 事件含工具调用与参数（读取路径可取）；生效模型自 init/结果事件回读**待实测** | 待探针 · — |
| 项目公约 | 交互态读项目 `CLAUDE.md`（Driver 协议所在）——审核态必须以 BRIEF 首段与 CLAUDE.md 审查员片段压过（§7.4） | 官方文档 · 高 |

**结论与对策**：Claude Code 是四家中唯一「同时具备完整入口 skill、完整 Hook、headless 审查」的 Agent，天然同时具备 Driver 与 Critic 双角色能力。禁用 `--dangerously-skip-permissions`（AD-07 延续）。思考等级控制若无公开旗标，`claude` 侧三档**退化为模型选择承载**（同 GLM-5.3 / GLM-5.3-Flash 先例），探针定。

### 3.3 Driver 入口承载面（四家对照，承载能力待 M6 探针确认）

| Agent | 命令承载物 | 协议片段落点 | 拦截层（护栏等级） |
| :--- | :--- | :--- | :--- |

## 5. 总体方案

### 5.1 Agent 注册表（R-5 的落点）

新增 `src/trivium/agents/registry.ts`（与 `adapters/` 平级），是全部 Agent 差异的**唯一登记处**：

```ts
interface AgentDescriptor {
  id: AgentId;                 // 'claude' | 'codex' | 'gemini' | 'glm'
  display: string;             // 'Claude Code' | 'Codex' | 'Antigravity' | 'ZCode'（Codex 的模型族开放：QWen/DeepSeek…，见 agents.codex.models）
  vendor: string;              // 'anthropic' | 'openai' | 'antigravity' | 'zcode'
  suffix: RoleSuffix;          // 归档后缀：'claude' | 'codex' | 'gemini' | 'glm'
  findingPrefix: string;       // 'CLAUDE-' | 'CODEX-' | 'AGY-' | 'GLM-'
  criticAdapter?: () => CriticAdapter;   // 有则可当审核者
  driverEntry: DriverEntrySpec;          // 入口资产规格（承载物类型 + 安装目标 + 参数展开能力探针键）
  instructionFiles: string[];  // 协议片段落点：['CLAUDE.md'] / ['AGENTS.md'] / ['GEMINI.md'] …
  guardLevel: 'L1' | 'L2';     // 护栏等级（§7.5），L1=有 blocking Hook
  configKey: `agents.${AgentId}`;
  probeSection: `probe.${AgentId}`;
}
```

四家注册值一览：

| id | suffix | findingPrefix | 可为审核者 | 可为 Driver | guardLevel |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `claude` | `claude` | `CLAUDE-` | ✅（新增适配器） | ✅（现状） | L1 |
| `codex` | `codex` | `CODEX-` | ✅（新增适配器） | ✅（新增入口） | L2 |
| `gemini` | `gemini` | `AGY-` | ✅（现状 agy） | ✅（新增入口） | L2/L3 |
| `glm` | `glm` | `GLM-` | ✅（现状 zcode） | ✅（新增入口） | L1（探针通过） |

**使用规则**（实现纪律，M7 落地）：

1. 除 `registry.ts` 与各适配器自身，**任何模块不得出现具体 Agent id/后缀/前缀字面量**。命名、禁读、Hook 字面集、Gate 来源反推、schema pattern 生成、镜头键、安装目标一律从注册表读取。以新增契约测试 `registry-parity.test.ts` 锁定（schema pattern、hooks 字面集、`.reviews/README.md` 角色枚举 ↔ 注册表逐项对账——沿用 `skill-flag-parity` 的手法）。
2. **接入第五家 Agent = 五件套**：①注册项；②`CriticAdapter` 实现（若做审核者）；③`probes/<vendor>.ts` 探针组；④`lenses.yaml` 增键；⑤入口资产与协议片段模板。核心流程（freeze/brief/runner/gate/archive/hooks）零改动——这是 R-5 的验收形态（AC-N5，以桩 Agent 实测）。

### 5.2 Driver 任意化（R-2）

**核心转变：Driver 从「系统常量」降为「运行属性」。**

- 发起：入口资产调 `trivium` 时显式带 `--driver <agent>`（入口资产自己知道身份；缺省 `claude` 兼容旧调用）。`topic resolve` 透传，`review --start` 记入 `run.json.driver`、`task.json.runs[]` 与 `state.json` 闸门项。
- 工件：Driver 的原稿与裁决件后缀 = 当轮 Driver 的 `suffix`。例：ZCode 为 Driver 时，plan 原稿是 `…-<主题>-glm.md`，裁决件是 `…-revised-claude.md`→`…-revised-<driver 后缀>.md`。**同一后缀在不同运行中可能是 Driver 也可能是审核者**——后缀标识「产出方」，`run.json.driver` 记录「发起方」，两者正交（风险 R23 的对策）。
- 唯一写权（FR-01 措辞随之回溯）：「**当轮 Driver** 是唯一有权改业务代码的角色」。审核者集合恒为 `注册表 − {Driver}` 的子集，Driver 不得同时当审核者。
- 兼容：`claude` 为 Driver 时的全部现有工件名、Hook 行为、`.reviews` 布局逐字节不变。

**护栏分级**（诚实边界，详见 §7.5）：L1（claude、glm 探针通过）具备闸门期写拦截与 Stop 阻断；L2（codex、gemini）没有 blocking Hook，靠三层补偿——①编排器侧确定性校验双点（新增：`approve` 迁移状态前**无条件重跑一次** `checkAdjudication`，幂等秒级，把「审批前裁决完整」从 Hook 单点变 CLI 双点）；②`_meta/review-*.json` 是 `gate --check` 唯一事实来源 + `archive` `O_EXCL` 防覆盖，伪造审查文档过不了闸门；③跑后漂移复算与留痕核对（`verify`/`report`）。

### 5.3 审核者动态选择：1～3（R-3）

- CLI：`review --start --critics <id1[,id2[,id3]]>`。校验：去重、互异、`≠ driver`、均为注册 Agent、`1 ≤ n ≤ review.max_critics`（默认 3）；非法退 64 并列可用值。`--only <agent>` 降级为 `--critics <agent>` 的别名；`--allow-single` 更名 `--allow-partial`（别名保留），语义从「允许单审」改为「允许**部分**审核者失败后续跑」。
- 默认值：`review.default_critics`（**建议默认 `gemini,glm` 两审**，与现状成本一致；三审与单审是显式选择——待拍板 #1）。
- **选 1 审 ≠ 降级**：`review_mode` 由「计划 vs 完成」推导——`sides_ok = planned` → `full`；`0 < sides_ok < planned` → `partial`（`degraded_reason` 必填）；`planned = 1` 且 ok → `full`，不带降级标记。旧 `dual/single` 值仅在读取历史 run.json 时映射。
- 并行与超时：`runSides` 对 N 路 `Promise.allSettled`（替换 `runBothSides`，语义同源：单路异常不取消其余）；单侧超时上限不变；`max_waits` 按最慢侧预算计算；`SideProgress`/`status.json` 的 sides 由字面两键改为动态 map。
- 失败策略：`decideMode` N 化——全败 → abort（strict 退 75）；部分败 → strict 中止（幸存侧照留痕标 degraded）、`degrade`/`--allow-partial` 续跑 `partial`。**绝不把 partial 改名冒充 full（AC-06 延续）**。
- 隔离/裁决/归档的 N 方化见 §8/§9/§6。

### 5.4 模型与思考等级：三档组合（R-4）

**数据模型**（配置 v2，全量示例见 §11）：

```yaml
agents:
  codex:
    default_tier: medium
    models:                        # 目录（2026-09-13 项目负责人指定四模型；efforts 为官方口径的原生枚举，经 Codex 透传以 M6 探针为准）
      qwen3.8-flash:   {efforts: [low, medium, xhigh]}   # QWen 家族，默认 xhigh，混合思考可开关；无 high 档
      qwen3.8-max:     {efforts: [low, medium, xhigh]}
      deepseek-flash:  {efforts: [low, high, max]}       # DeepSeek 家族，默认 high；无 medium 档（请求 medium 会被归并为 high）
      deepseek-v4-pro: {efforts: [low, high, max]}
    tiers:                         # 三档 =「模型+思考等级」组合：effort 写模型原生枚举，可跨模型跨家族
      low:    {model: deepseek-flash,  effort: low}      # trivium low  → deepseek low
      medium: {model: qwen3.8-flash,   effort: medium}   # trivium medium → qwen medium（deepseek 无对应档，故此档选 qwen）
      high:   {model: deepseek-v4-pro, effort: max}      # trivium high → deepseek max / qwen xhigh（同深度定位）
```

- **effort 取值是模型原生枚举，不是统一档名（2026-09-13 官方文档核实，§3.1）**：qwen3.8 系列为 `low|medium|xhigh`（无 high），DeepSeek V4 系列为 `low|high|max`（无 medium，且请求值按 `minimal/low→low`、`medium/high/xhigh→high`、`max/ultra→max` 归并）。trivium 三档（low/medium/high）到原生 effort 的映射**只经 tiers 组合显式声明**，代码禁止假设统一枚举；DeepSeek 的归并意味着「请求 medium 实际生效 high」——`effort_effective` 随 `model_effective` 一并回读入档，不采信请求值。

- **档位是组合而非单纯 effort**：延续既有先例——zcode 0.16.5 无思考等级旗标，两档差异由模型选择承载（GLM-5.3 vs GLM-5.3-Flash）；gemini 的 effort 编码在 slug 后缀（P-16）。因此 tier 统一定义为 `(model, effort?)` 组合，`effort` 缺省表示该 Agent 用模型选择承载差异。
- **每模型提供默认三档**：`models.<m>.efforts` 声明可用思考等级；引用某模型而不指定档位时，取 `agents.<id>.tiers` 中该模型所在档；Agent 级 `default_tier` 兜底。此设计同时满足「每个模型提供默认高中低三档」与「组合可跨模型」两种读法（待拍板 #4 确认取舍）。

**路由优先级**（在主设计 11.5 四级之上保持形状、逐级细化）：

```text
--model-<agent> [+ --effort-<agent> | --tier-<agent>]     ① 命令行精确覆盖（最高）
profiles[active_profile].<agent>.<stage>                  ② 档位表（形态：{tier}|{model,effort}|裸 slug 旧形态）
agents.<agent>.tiers[agents.<agent>.default_tier]         ③ Agent 默认档
（无）→ 该 Agent 不可作为审核者，预检失败                     ④ 兜底即失败，不静默
```

- 发起时既可 `--tier-codex high`（选组合档），也可 `--model-codex qwen3.8-max --effort-codex xhigh`（精确覆盖，effort 取该模型**原生枚举**，§3.1）；两者同时出现时精确值优先并告警。
- **Codex 厂商 profile 是基座而非档位（R-6）**：取值 `--profile-codex`（CLI）> `agents.codex.profile`（配置默认）> 不传，最终调用形如 `codex -p <配置> exec …`；tier/精确旗标解析出的 (model, effort) 以 `-m`/`-c` 显式旗标叠加，按 Codex 自身优先级覆盖 profile 内对应项。profile 可能捆绑换模型——`model_effective` 仍以事件流回读为唯一真相，`run.json.critics.codex.profile` 记录请求值。注意与 trivium 自身的 `--profile <档位名>` 是**两个命名空间**（前者厂商配置段，后者本项目档位表）。
- **生效值回读不变（AC-13 延续）**：`run.json.critics.<id>` **自 M11 起**增记 `effort_requested` / `tier_source`（`cli|profile|agent_default`）与 `effort_effective`（四字段在 `run.v2` schema 中**定义为可选**，M7b 不写入，见 §6.2 注 1）；`model_effective` 照旧从运行产物/会话日志回读，回读不到记 `unverified` 不采信。
- **异构校验 N 化（FR-17/AC-18 延续）**：默认各审核者模型族互不相同且与 Driver 模型族不同；**模型族按生效模型判定，不按 Agent**——Codex 目录开放多家族（QWen/DeepSeek/OpenAI…）后该判定只依赖回读值，与 Agent 解耦；显式选成同族时告警 + `heterogeneous: false` + `override_reason`，不阻止。

## 6. 数据契约与命名变更

### 6.1 归档命名（主设计 6.2 的修订点）

## 8. 隔离与安全泛化（主设计第 10 章的 N 方修订）

### 8.1 四道机制的 N 方化

| 机制 | 双侧现状 | N 方形态 |
| :--- | :--- | :--- |
| ① 进程与会话独立 | 两侧独立子进程 | 每审核者独立子进程；四家配置目录（`~/.claude` `~/.codex` `~/.gemini` `~/.zcode`）天然分离，HOME 副本机制按需启用 |
| ② 延迟落盘 + 项目外运行目录 | 两侧都完成后同时落盘 | **全部 N 侧完成后**同时落盘；运行目录 `~/.trivium/runs/<repo_id>/<run_id>/<critic>/` 结构不变 |
| ③ 历史产出屏蔽 | 唯一对方角色的 `-*<peer>.md` | **deny 矩阵**：审核者 c 的禁读 = 后缀 ∈（全部注册后缀 − {c.suffix, driver.suffix}）的全部角色工件 + 敏感 globs + `.trivium/` + `~/.trivium/`；由注册表程序生成，**禁止手工枚举**（R21） |
| ④ 只读指纹 | tree_hash 前后比对 + 写事件扫描 | 不变（指纹是全树性质，与侧数无关） |

deny 矩阵要点：Driver 后缀文件（原稿/裁决件）对全部审核者是**合法输入**（被审对象与上下文），不禁；未入选审核者的历史产出**照禁**（最小知情 + 组合可变）。

### 8.2 泄漏通道清单与检测收口（随 M7；2026-09-13 项目负责人裁定：只做检测收口）

**威胁模型定调**：隔离要防的是**锚定/趋同污染**——好奇或顺手的模型读到对方意见后独立性受损；**不是**防蓄意对抗穿透（执意规避检测的模型总能找到办法，如变量拼接构造路径）。工程目标因此定为「**泄漏必检 + 成本抬升**」：任何一条通道的命中都必然导致该侧作废重跑并留痕，把泄漏从「静默污染」变成「可见失败」。硬隔离（内核级拒绝）已评估并留档为备选（§8.4）。

计划期核实的四条泄漏通道（通道②③④在现实现中存在检测盲区）：

| # | 通道 | 现状约束 | 事后检测现状 | 收口措施 |
| :--- | :--- | :--- | :--- | :--- |
| ① | 工作树内对方历史审查件 `*-<peer>.md` | BRIEF 逐路径禁读（提示级）；路径级 deny 两家 CLI 实测不可用（M0 C-04/C-11） | **可命中**（`checkPeerLeak` 比对轨迹读取路径，`adapters/base.ts:119`）——唯一有效的一层 | 维持；deny 矩阵按 §8.1 泛化 |
| ② | git 对象库：`.reviews/` 进 Git，`readonly_commands` 白名单含 `git log/show/diff/blame` | 仅提示级 | **盲区**：`git show HEAD:.reviews/…-<peer>.md` 不产生文件系统读取，命令文本不进 `read_paths` | 措施 b |
| ③ | `~/.trivium/runs/<repo_id>/…/<peer>/`：对方**本轮**原始输出审查期间就写在那里（延迟落盘只保证项目树内没有） | 仅 BRIEF 提示级 | **盲区**：`~/.trivium` 不在 `deny_paths` 机器集合（`enumerateDenyPaths` 只扫归档根 + 敏感 globs），Read 工具读了不命中、Bash `cat` 路径根本不进轨迹 | 措施 a + 措施 b |
| ④ | `_meta/review-<peer>-<runId>.json`（结构化意见原文）与 fallback 编号件 | 无 | 用 Read 读会进轨迹但不在 deny 集合 → 不命中 | 措施 a |

**措施 a：deny 机器集合补齐，提示与核验同源。** `enumerateDenyPaths` 的对端产物枚举从「`*-<peer>.md` 文件」扩为「**含对方意见内容的全部归档文件**」（`*-<peer>.md`、`_meta/review-<peer>-<runId>.json`、该侧 fallback 编号件），并把 `~/.trivium`（绝对路径）与项目 `.trivium/` 一并纳入 `deny_paths`。BRIEF 第 8 段的禁读清单与机器核验集合**由同一 deny 矩阵生成**——消除现实现「提示语禁了一堆、核验只对其中一部分」的错位（这正是通道③④的成因）。修复后 AC-04 的轨迹核验口径同步扩展（`checkPeerLeak` 比对逻辑不变，deny_paths 变准变全）。该修复纯编排器侧、无 CLI 依赖，先于 codex/claude 适配器合入（双侧桩伪造读取 `_meta/review-<peer>-*.json` 或 `~/.trivium/**` 应判 `peer_leak`，独立可测）。

**措施 b：run_command 命令文本字面扫描。**
> **【独立演进项 · 未排期】**（2026-09-14 定稿修订，依据 r2 裁决件 AGY-02 / GLM-04）：
> 本措施与其验收 **AC-N6b** 已从 M7 的完成判据中移出，改指派为独立演进项，
> 在 [`doc/08_project/BACKLOG.md`](../08_project/BACKLOG.md) 登记认领，决策背景见
> [`ADR_002_multicritic_isolation.md`](./ADR_002_multicritic_isolation.md)。
> 同一节的**措施 a 不受影响**，仍随 M7b 交付（验收 AC-N6a）。
> `run.v2` 的 `guard.peer_leak_via_command` 相应**声明为可选字段**（§6.2 注 1）。

`guard` 对该侧轨迹中每条命令（agy 的 `run_command`、codex 的 shell 事件等）的**命令文本**做 deny 字面量子串匹配，字面集 = deny 矩阵产出的路径及其写法变体（`HEAD:<path>`、`::<path>`、`~/.trivium`）。命中即与路径命中**同等处置**：该侧作废重跑一次、二次命中 `failed(peer_leak)`，strict 下整次中止。误报口径与 hooks 的 `bashTargetsProtected` 同源——命令是审查员自己构造的执行意图，正文出现保护路径字面量没有正当场景；这是通道②③在检测侧的唯一覆盖。`run.v2` 的 `guard` 段增 `peer_leak_via_command`（布尔 + 命中命令原文），供审计区分两类命中。

### 8.3 git 历史通道的取舍（保留能力 + 检测兜底，2026-09-13 拍板）

git 对象库通道**不在沙箱层封死**（本项目不引入沙箱，§8.4）：`git log/blame/show` 是 bug 阶段镜头的重要能力（追溯引入提交、查作者意图），deny `.git` 会实质砍掉它。处置为：能力保留 + 措施 b 的命令文本扫描兜底。**既有配置 `readonly_commands` 即 paranoid 旋钮**——把 `git show`/`git log` 从白名单裁掉即收窄该通道（代价：bug 阶段「第二根因/同模式排查」能力受损），不新增机制。蓄意规避（变量拼接、`git log -p -- .reviews/<主题>/plan/` 这类不带对方文件名的目录级翻阅）命令文本扫描抓不到，按 §8.2 威胁模型定调接受并登记为 R25。

### 8.4 已评估备选路线（暂不采用，2026-09-13 项目负责人裁定）

| 备选 | 要点 | 不采用理由 | 重启触发条件 |
| :--- | :--- | :--- | :--- |
| macOS Seatbelt 沙箱（`sandbox-exec`） | 每审核者子进程套 per-critic profile（`(allow default)` + `deny file-read-data` 对方产物、`.trivium/`、`~/.trivium`，本侧运行目录显式豁免），读取在**内核层**被拒；就地、并行、零拷贝全保留 | Apple 标记 deprecated（至今可用，Chromium 仍依赖）；profile 生成与豁免规则（如 zcode HOME 副本恰在 `~/.trivium` 下）的持续维护成本；检测收口已满足威胁模型 | 出现对抗性泄漏实锤，或检测收口在实践中不够用 |
| 影子工作区 + 红acted git（ADR-002 候选） | 每审核者一个符号链接视图（全树 symlink，仅 `.reviews` 换过滤视图、`.git` 换合成 HEAD 的迷你库，对象经 `GIT_ALTERNATE_OBJECT_DIRECTORIES` 零拷贝共享）；工作树与 git 历史两通道同时封死且 git 能力保留 | 工程量最大、边界多（agy 无 `--cwd`、scratch 白名单按影子根重算）；需立 ADR-002 推翻 ADR-001「唯一就地模式」 | 同上；且 Seatbelt 在未来 macOS 不可用时作为其替代 |
| chmod 000 锁对方文件 + 串行审查 | 文件权限硬拒绝 | 并行两侧可见性**互斥**（各自要读己方历史、禁对方历史），同一棵树做不到，只能牺牲并行、墙钟翻倍 | 不重启（结构性不可行） |

> 根因记录：macOS 上同 uid 的并行进程看同一棵文件系统树，没有 root 就没有 per-process 路径 ACL——硬隔离只有「不同文件系统视图」或「per-process 内核沙箱」两条路（上表前两行即这两条路的代表）。检测收口是第三条路：不阻止读取，但让每次读取必然留下可判定的痕迹。

### 8.5 密钥与安全

`archive` 落盘前密钥扫描**逐家族**增补 provider 凭据形态（QWen/DashScope 与 DeepSeek 均为 `sk-*` 前缀；确切形态以 M6 探针实测为准）；CODEX_HOME 副本与 ZCode HOME 副本同规格（`0600`、跑完即删、不入档）。其余（提示注入包裹、出网、日志位置）不变。

## 9. 闸门与裁决泛化（主设计 8.4～8.6 的修订点）

### 9.1 裁决链 N 方化

- 意见集合 = `Σ critics_selected` 的 findings（前缀不冲突由注册表保证）；fallback 虚拟编号规则不变。
- 裁决件定位：`role === run.driver 的 suffix` 且 `kind`/`rerun_index` 匹配。
- `checkAdjudication` 步骤 4 的 `missingSides` → 遍历 `critics_selected`；差集/语义校验逻辑逐条不变。
- **joint blocker N 化**：由「双方同 location blocker 均驳回」扩为「**任意两个**审核者同 location blocker 均驳回」→ `warn`（默认，`task.json.disputed: true`）/ `hard`（仅 location 精确相同）。三审时两两比对，命中任一对即触发。

### 9.2 闸门状态机与停点

状态机、entry 分流（B/C/D→`awaiting_approval`、A/无→`idle`）、`--await-approval` 前置校验全部不变。`state.json` 闸门项增记 `driver`；停点话术与三份文档路径的「三」改「1～N+1」。

### 9.3 Hook 泛化

- `hooks.json` 的 Hook 命令串增嵌身份参数：`exec "$W" gate hook-pre-write --agent claude`（合并进哪家 CLI 的配置，就嵌哪家的 id；缺省 `claude` 兼容）。
- `isForgedRoleFile` / `bashTargetsProtected` 的字面集按 `--agent` 动态生成：**非本 Driver 后缀**全量保护（`claude` 为 Driver 时即 `codex|gemini|glm` 三后缀，现状两条是它的子集，行为兼容）。已知误拦面扩大登记为 R22，处置口径不变。
- 多目标合并：`mergeHooks` 增 ZCode 配置目标（形态与键名 M6 探针；通过则 glm Driver 拿 L1，同时 ZCode 作为审核者不受影响——Hook 只作用于交互会话）。codex/gemini 无合并目标。
- `hook-pre-commit` 留痕三锚、`hook-session-start` 回收逻辑与 Hook 退出码三档全部不变。

### 9.4 approve 复核加固（对所有 Driver 生效）

`trivium approve` 在状态迁移前无条件重跑一次 `checkAdjudication`（含 `run.json.artifacts` 的 sha256 抽核）。动机：L2 Driver 无 Hook 拦截，审批是最后一道确定性关口；对 L1 Driver 这是零成本冗余（幂等读校验，秒级）。**不加确认码**（已试过并撤销，主设计 v1.2.3 ②），只加复核。

> `process.stdout.write(JSON.stringify(...))`，`util/log.ts` 的铁律是「机读模式 stdout 只允许出现一个 JSON、

### 17.3 「回溯完成」的判据

原清单没有定义完成判据，因而无法被机器或人工核对。本次补上：

1. **唯一记账面**是主设计 §24「演进并入台账」——每条清单项一行，记「目标文档 → 批次 → 目标里程碑 → 状态 → 证据（章节号）」；
2. **对账锚是本节 17.2 表，不是台账自身**。核对方式为「17.2 的每一行在 §24 台账中都能找到对应行」。
   之所以不用「两表条目数相等」：两表若同源，**该判据对共同缺项完全失明**（这正是原清单遗漏 9 类条目却无人发觉的机制）；
3. 每个里程碑的完成判据含一条：「本里程碑在 §24 台账登记的回溯条目已并入**对应目标文档**（落主设计者随之升次版本）」——
   核对面是台账与目标文档，不是「主设计」单一文档：批 B 条目大半（第 7、9、14、17、18 项整文件，第 3、4、5 项部分）落在主设计之外；
4. **M11 的完成判据含「§24 台账全绿」**，即全部条目并入完毕——那时本文的规范性内容已完全迁入主设计，
   本文退化为纯粹的论证与调研归档。
