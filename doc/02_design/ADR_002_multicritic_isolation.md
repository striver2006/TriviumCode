## 一、背景

「背靠背双审」的核心价值在于两位审查员**独立**得出结论：两侧各自查证、各自判断，
收敛处才有信息量。一旦一侧看到另一侧的结论，独立性即失效——收敛变成复读。

演进到 N 方（1～3 个审核者，见设计 FR-29）之后，需要屏蔽的对端产物数量随之增加，
计划期的排查发现**实际泄漏面比此前登记的更大**：除已知的「工作树历史件」之外，
还有三条通道处于**检测盲区**——不是屏蔽弱，是命中了也检测不到。

### 四条泄漏通道（2026-09-13 实测登记）

| # | 通道 | 此前状态 | 性质 |
| :--- | :--- | :--- | :--- |
| ① | 工作树中对端的历史审查文件 | 三层屏蔽已覆盖（禁读清单 + 路径级 deny + 事后轨迹核验） | 已覆盖 |
| ② | **git 对象库**：`.reviews/` 进 Git，而只读命令白名单含 `git show` / `git log`。经对象库取对端文件**不产生文件系统读取**，读取路径核验看不到 | **盲区** | 检测不到 |
| ③ | **项目外运行目录**：对端**本轮**原始输出在审查期间就写在那里（延迟落盘只保证项目树内没有）。该路径只在任务书提示语里，**不在 deny 的机器集合**中 | **盲区** | 检测不到 |
| ④ | **归档元数据目录下的结构化意见原文**：禁读清单的枚举函数只扫 `*-<对端>.md` 形态的 Markdown，漏掉同目录下承载同样内容的结构化 JSON | **盲区** | 检测不到 |

> **⚠️ 勘误（2026-09-14）**：上表「此前状态」列记的是**本决策作出时刻（2026-09-13）**的现状，当时属实。
> 但**措施 a 的路径侧已在同日随 M7a 落地**（`039bdc9`）：通道③④ 现已收口——
> 结构化意见与运行目录均在 deny 机器集合中，且任务书禁读清单与机器核验**同源生成**。
> 落点见 `freeze.ts` 的 `enumerateDenyPaths()`、`brief.ts` 第 8 段渲染、
> `adapters/base.ts` 的 `checkPeerLeak`，正例单测在 `test/unit/deny-matrix.test.ts`。
> **通道② 仍为盲区**（依赖措施 b，未排期）。
> 现状以[设计 10.1](./2026-09-10-Driver-DualCritic主攻双审流水线设计.md) 的通道表为准；
> 本节保留原始登记作为决策依据的史实记录。

③④ 的共同根因是同一个错位：**提示语里禁的集合与机器核验的集合不是同一个**。
提示语禁了一堆，核验只对其中一部分——这个错位本身就是缺陷，不是取舍。

## 二、评估的选项

### 选项 A：只做检测收口（**采纳**）

- **措施 a**：deny 机器集合补齐。对端产物枚举由「`*-<对端>.md` 文件」扩为
  「含对端意见内容的**全部**归档文件」，并把运行目录与项目内运行时目录一并纳入；
  **任务书禁读清单与机器核验集合由同一个 deny 矩阵生成**，从根上消除上述错位。
- **措施 b**：审查员执行的命令**文本**做字面扫描，命中与路径命中同等处置。
  这是通道②③在检测侧的唯一覆盖。

### 选项 B：内核沙箱（Seatbelt / `sandbox-exec`）

按路径粒度事前拒绝读取。**不采纳**：`sandbox-exec` 是 Apple 已标记 deprecated 的 API，
未来 macOS 可能移除；且两家厂商 CLI 在沙箱下的行为需逐一实测，适配成本高、易碎。
**留档备选**，风险另记（设计第 19 章 R26）。

### 选项 C：影子工作区（每侧一份剔除对端产物的工作副本）+ 脱敏 git

真正的「不同文件系统视图」。**不采纳**：它实质是 ADR-001 已经否决的镜像树方案换了名字——
成本（构树时间、磁盘、`.git` 处理）与 ADR-001 当时的论证逐条相同。**留档备选。**

### 选项 D：`chmod` + 串行执行

先跑一侧、改权限、再跑另一侧。**不采纳**：串行使墙钟翻倍，且并行本身是本流水线的核心收益之一；
`chmod` 对同 uid 进程的防护也接近于无。

> **根因记录**：同 uid 的并行进程看到同一个文件系统视图。要做到真正的硬隔离，
> 只有两条路——**给它们不同的文件系统视图**（选项 C），或**用内核沙箱拦系统调用**（选项 B）。
> 其余手段都是提示与检测，不是隔离。这一点必须说清楚，否则容易把「检测」误当成「隔离」。

## 三、决策

**只做检测收口（选项 A），不引入硬隔离。git 通道保留能力 + 检测兜底。**

### 威胁模型定调（这是本决策成立的前提）

本项目要防的是：

- **锚定污染**——审查员看到对端结论后被锚定，独立判断塌缩为复读；
- **非对抗穿透**——模型在没有恶意的情况下「顺手」读到了不该读的东西。

**不要防**：蓄意规避。目标定为「**泄漏必检 + 成本抬升**」，不是「泄漏不可能」。

这个定调不是为省事找的借口，而是对威胁来源的诚实判断：审查员是我们自己拉起的、
读的是我们自己给的任务书，它没有动机去对抗；真要对抗，选项 B / C 也未必拦得住
（变量拼接路径、不带对端文件名的目录级翻阅等形态，命令文本扫描抓不到）。
该风险登记为设计第 19 章 R25，**出现实锤即重启评估选项 B / C**。

### git 通道：保留能力而非封死

`git log` / `blame` / `show` 是 bug 阶段审查镜头的重要能力（追溯引入提交、查作者意图）。
把 `.git` 加进 deny 会实质砍掉它。处置为**能力保留 + 措施 b 兜底**。

**既有配置项 `readonly_commands` 即 paranoid 旋钮**——把 `git show` / `git log` 从白名单裁掉
即可收窄该通道，代价是 bug 阶段排查能力受损。**不新增机制**：已有旋钮能表达的选择，
不要再造一个开关。

同理，**措施 b 的命中不提供 `warn` / `off` 配置开关**：设开关等于创造一条「合法的绕过路径」，
而绕过检测这件事不应该有合法路径。

## 四、影响

### 正面

- ③④ 两条盲区被措施 a 关闭，且**根因**（提示语集合与核验集合分离）被一并修掉，
  而不是逐条打补丁；
- 任务书禁读清单与机器核验同源生成后，新增 Agent 时禁读矩阵**自动正确**——
  不再依赖人工维护清单（设计 16.2 纪律 7 据此写入）；
- 不引入 deprecated 系统 API，不承担镜像树的构树成本。

### 负面（如实登记）

- **对抗形态的泄漏仍可能静默发生**（R25）。这是定调换来的，不是疏漏；
- 措施 b 是启发式，存在**误报**可能——与仓库已有的 Bash 拦截误拦同源同性质，
  出口一致：命令正文不要出现受保护路径的字面量；
- 通道②的覆盖依赖措施 b，而措施 b 已被移出 M7b 为**独立演进项**（见下）。
  在它落地之前，**通道②处于「已登记但未覆盖」状态**——这一点必须如实呈现，
  不能因为已经写进设计就当作已经解决。
  （反向同样要防：**也不能把已经收口的写成盲区**。2026-09-14 的代码双审即查出本文与
  设计 10.1、PRD AC-25 三处把通道③④的现状写成「待实施」，而它们已随 M7a 收口——
  见上方勘误。**凡写「现状」断言，一律以代码为准复核一次**，不得照抄更早的文档。）

### 交付切分

| 措施 | 验收 | 里程碑 |
| :--- | :--- | :--- |
| 措施 a · **路径侧收口 + 同源生成**（两侧形态） | `test/unit/deny-matrix.test.ts` 正例 | **✅ 已随 M7a 落地**（`039bdc9`，2026-09-13） |
| 措施 a · **N 方泛化**（三审时的两两展开与桩用例） | 设计 AC-25 | **M7b** |
| 措施 b（命令文本字面扫描） | 暂不排 AC 号 | **独立演进项 · 未排期**，在 [`BACKLOG.md`](../08_project/BACKLOG.md) 以 EV-01 认领 |

切分理由：措施 a 是纯编排器侧改动、无 CLI 依赖、独立可测；措施 b 涉及各家轨迹中命令事件的
形态差异，需 M6 探针结论支撑。把两者绑在同一个里程碑会让 a 被 b 拖住。

## 五、后续复核触发条件

出现以下任一情况即重启对选项 B / C 的评估：

1. 真实运行中出现**对抗形态**的泄漏实锤（不是误触，是规避）；
2. 审查结论出现无法用「同源查证」解释的高度雷同，且轨迹核验为空；
3. 措施 b 的误报率高到 Driver 开始习惯性绕开流程——那说明这条检测在实践中站不住，
   需要重新评估是收窄它还是换硬隔离。
