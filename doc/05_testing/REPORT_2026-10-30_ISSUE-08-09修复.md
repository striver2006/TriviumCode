### 1.1 ISSUE-08 复现与逃逸机制（P/Invoke 夹具，C# 内联）

夹具建 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job，以 `CREATE_SUSPENDED` 创建 node 父进程（模拟 agy
工具通道里的 `trivium --start`）、assign 进 Job 后恢复；父进程分别以两种形态派生 worker，父进程退出后关闭
Job 句柄（= 通道结束）：

| 派生形态 | worker 在 Job 内 | Job 关闭后 | 结论 |
| :-- | :-- | :-- | :-- |
| `detached: true` 直拉（修复前唯一形态） | **在**（继承父进程 Job） | **死** | ISSUE-08 逐字复现：worker 随通道结束被整树收杀 |
| WMI `Win32_Process.Create` 中继（`([wmiclass]'Win32_Process').Create` 三参，`ShowWindow=0`） | **不在任何 Job**（WmiPrvSE 承载） | **活**，心跳持续 | 逃逸通道成立 |

夹具工程坑（如实登记，均已绕开）：PowerShell 直接封送 `ref struct` 时 `SetInformationJobObject`
返回 True 但标志静默丢失（回读 0x0、Job 不收杀、对照组假绿）——夹具必须整段 C# 内联；
`Invoke-CimMethod` 带 `-ClientOnly` 的 `Win32_ProcessStartup` 实例参数报 0x80041002「找不到
Win32_Process」，改用 wmiclass COM 三参形态即通。

### 1.2 ISSUE-09③ 命令形态实测（Git Bash / PowerShell 双载体）

Claude Code 官方 Hooks 文档（实测版本 2.1.302 行为一致）：Windows 上 shell 形态 hook 命令经
**Git Bash** 执行，**找不到时回退 PowerShell**。候选形态逐个实测：

| 形态 | Git Bash | PowerShell（回退载体） | 结论 |
| :-- | :-- | :-- | :-- |
| `sh -c '…'`（修复前唯一形态） | ✓ | ✗ 解析不到 `sh`，失败即放行 | ISSUE-09③ 原样复现 |
| `cmd /d /s /c '…'` | ✗ MSYS 把 `/d /s /c` 转成路径（ISSUE-07 同族），cmd 进交互态 | ✓ | 不可用 |
| `powershell -NoProfile -EncodedCommand "<b64>"; exit $LASTEXITCODE` | ✓ | ✓ | **采用** |

采用形态的语义验证（两载体 × 四分支，退出码逐格断言）：wrapper 在且放行 → 0；wrapper 判拦截（退 2）→ 2；
config 在而 wrapper 失（护栏被破坏）→ 2 且 stderr 提示；未初始化（协作者克隆未跑 init）→ 静默 0。
两个关键细节均为实测发现：**外层 `powershell -Command` 会把内层原生命令的非零退出码重映射为 1**
（2 → 1，阻断语义丢失），尾句 `exit $LASTEXITCODE` 纠正之（bash 下空参展开退化为 `exit $?`，同样透传）；
b64 必须**加双引号**（裸 token 在双层 PS 重解析下被拆坏）。启动成本 ~0.6 s/次（sh 形态守卫本身也要拉
wrapper 进程链，量级可接受）。

## 4. 如实登记的边界

1. **WMI 不可用的机器**（策略禁用 WMI / PowerShell 受限）：逃逸回退直拉，带收杀 Job 的会话（agy）回到
   修复前形态，worker.log 留痕说明成因——不比修复前更糟；无收杀 Job 的场景（终端、codex/claude 会话）直拉照常成立。
2. **逃逸通道恒走 WMI（不做 Job 探测）**：终端等无 Job 场景每次 `--start` 多付一次 powershell + 一次
   node 启动（秒级），摊在分钟级审查运行上；统一路径换取可测性。
3. **env 快照经运行目录过桥**：规格文件 0600（NTFS 权限位降级同第 7 条限制）、中继读完即删、成败两路都
   清理；极端情况（`--start` 进程在写入与清理之间被杀）由运行目录保留期整删兜底。
4. **跨平台共享的 `.claude/settings.json`**：两平台各自 `init` 渲染各自形态、按 gate 身份原位替换；混用
   团队在「拉到对方平台的提交、自己尚未重跑 init」的窗口内，本机形态不匹配即按 fail-open 退化（与未装
   Hook 同态），重跑 init（装升级时会跑）即恢复。
5. **ISSUE-09 的 ①②（项目 hooks 未注册、Claude 探测不到自定义路径的 Git）是环境侧**：产品侧已把③收口，
   W4-S3（L1 负向）复测仍待环境侧解决（Git 装回默认路径或 Claude 修复探测）后进行。
6. **`--wait` 的行为变化**：worker 确认已死的失联判定现在会**结束它名下的审查 CLI**（此前只推荐
   `--cancel`）。判不了身份的记录照旧一个信号都不发；worker 仍活（heartbeat_stale）的格子照旧不动。
7. **EV-158 d 格不随第 6 条扩大**（§5 补记，2026-10-31 第二批收口）：旧版写下、缺规范化启动时刻的 status.json
   在异 TZ / 区域设置下会把仍活着的 worker 误判 pid_gone。第 6 条落地时这一格还会结束它名下的 CLI；现在
   `--wait` 结束 CLI 前多一道准入：worker 的 pid 上仍有活进程、且不符是按旧版记录比出来的（有环境歧义）就不发
   信号、如实播报一句、也不给 `--cancel` 出口，后果回到修复前的「归档误收尾」。按规范化记录比出的不符只可能是
   PID 复用，照常结束。只出现在「旧版 `--start`、新版 `--wait`」的升级窗口。

任何进程」；失败输出里出现的正是新增的「已按记录结束工作进程遗留的审查员 CLI」，说明新逻辑在 POSIX 上按
