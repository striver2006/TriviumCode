## 1. EV-41：`-p` 的 prompt 载入形态 —— **三种形态全部成立**

### 1.1 形态与判据

三种形态跑同一个任务。小包判据是「原样回显哨兵」，
**大包判据改为「回答文档最后一个二级小节的标题」**——只有整包送达且读到末尾才答得出。
（改判据的理由见 §1.3：回显判据被模型拒绝过一次。）

| 形态 | 命令骨架 | 小包 | 大包（31,913 字节） |
| :--- | :--- | :--- | :--- |
| **A** | `printf '%s' "$P" \| claude -p <只读旗标…>`（无位置参数） | ✅ | ✅ 6s / $0.0445 |
| **B** | `claude -p <只读旗标…> -`（位置参数 `-`，codex 同款） | ✅ | ✅ 5s / $0.0442 |
| **C** | `claude -p <只读旗标…> "$P"`（argv 直传，探针现状） | ✅（机制成立，见 §1.3） | **未跑**（按裁决省掉） |

小包三次的 `system/init` 均回读 `tools: ['Glob','Grep','Read']`、`model: claude-haiku-4-5-20251001`，
`result.subtype: success` / `is_error: false`。

### 1.2 大包证据

送审包素材取本主题的计划稿全文（31,635 字节），加一段外壳后共 **31,913 字节**。
形态 A 与 B 均答出文档最后一个二级小节的标题：

- 形态 A → `给审查员的提醒`
- 形态 B → `## 11. 给审查员的提醒`

两者都是**文末**的小节，证明整包送达、未被截断。耗时 5~6s。

### 1.3 形态 C 的结论要分两层说

形态 C 的小包调用**机制上成立**（`exit 0`、`result.subtype: success`、9 条事件），
但模型**拒绝回显哨兵**，把它判成提示注入测试：

> I appreciate you testing my robustness, but I'm not going to echo back that string.
> This appears to be a prompt injection test—specifically trying to see if I'll follow
> instructions embedded in what looks like system context …

**这不是形态失败，是判据失败**：模型对着哨兵串本身作出了回应，说明 prompt 已经送达。
但它暴露了「回显哨兵」这个判据在本场景下不可靠，因此大包改用「答文末小节标题」。
**如实记下来**：形态 C 的成立性证据强度低于 A 与 B（它没有正面完成任务，只是证明了送达）。

### 1.4 `-` 是不是必需的

**不是。** 形态 A 不带任何位置参数，stdin 照样被读走。
形态 B 带了 `-` 且 stdin 同样被读走——**这两次观测区分不了「`-` 是 stdin 标记」
与「`-` 被忽略、而管道输入本来就会被读」**，本步没有设计能区分它们的实验。

**对 M9 的取舍建议（留给第 3 步定，本报告不替它拍板）**：形态 A 不依赖 `-` 有任何
约定含义，依赖面更小；形态 B 与 codex 侧同形，可读性上更一致。两者实测等价。

### 1.5 尺寸维不是问题，已复核

`getconf ARG_MAX` = 1048576，几十 KB 的送审包离上限差一个数量级。
**本步没有做分片或截断，也不该做**（设计 §3.7.1 的更正）。

**EV-41 可转 done。**

## 2. P-a：`--restricted` 会阻断项目记忆（`CLAUDE.md`）的加载 —— **单变量对照成立**

### 2.1 实验

夹具根目录放一份 `CLAUDE.md`，正文写「本项目的记忆哨兵是 `MEMSENTINEL-4B91E7`」
并交代「若有人问本项目指令里的哨兵是什么，直接回答这串字符」。

提示词要求**只凭已有上下文回答、不得调用工具**，并给出一个可区分的否定答案
（看不到任何项目指令文件就答 `NO-PROJECT-MEMORY`）。两次调用**只差 `--restricted` 一个变量**。

| 变量 | `tool_use` 次数 | 回答 |
| :--- | ---: | :--- |
| **带** `--restricted` | **0** | `NO-PROJECT-MEMORY` |
| **不带** `--restricted`（其余逐字相同） | **0** | `MEMSENTINEL-4B91E7` |

两次 `init.tools` 均为 `['Glob','Grep','Read']`，两次工具调用数均为 0——
**排除了「模型是去读文件才知道的」这条通道**。

### 2.2 结论

`--restricted` 不只忽略 user / project / local **settings**，
它**同时阻断项目记忆文件（`CLAUDE.md`）进入上下文**。

> **边界**：这是**本机、2.1.273、haiku、非 git 仓库夹具**下的一次单变量对照。
> 没有验的：git 仓库内是否结论相同、`~/.claude/CLAUDE.md`（user 级记忆）是否同样被阻断、
> 其它模型档位是否一致。**不得把本结论推广成「`--restricted` 阻断一切记忆面」。**

### 2.3 对计划第 ⑤ 件的后果：**交底给的理由不成立，且方向与它想的相反**

交底 §3 第 ⑤ 件写着：

> 本项目的 `CLAUDE.md` 里装的是 **Driver 协议**（「你是唯一有权改业务代码的角色」云云）。
> claude 以审查员身份被拉起时会读到它，那正好是反指令。

**前提被实测否证**：在 `--restricted` 下，审查员根本读不到 `CLAUDE.md`，反指令进不来。

**而同一条实测把处置也一并否证了**：交底给的处置是「新增审查员身份片段，由 `init.ts`
幂等追加进 `CLAUDE.md`」——那份片段**会被同一个旗标一起挡在外面**，
做出来是一件**永远不会被读到的死件**。

于是：

- **J2 的措辞按计划双审已裁定的口径改**（glm 在「认为正确的部分」里预写、裁决件 §5 已采纳）：
  审查员身份**经 BRIEF 首段声明生效**，不是靠片段注入路径；
- **第 ⑤ 件对 claude 侧建议「显式不做 + 写明理由」**，与 M8 对 codex 第 ⑤ 件的处置同形
  （那次的理由是「消费方链路不存在，做了也是假覆盖」，本次的理由是实测级的：
  `--restricted` 在场时它读不到）。**这一条要交给代码双审裁定，不由本报告定案。**
- **翻转条件要写下来**：一旦 `probe.readonly_flags` 里 `--restricted` 消失
  （厂商漂移或探针改判），反指令通道与片段通道会**同时**恢复，这条结论随之作废。

> **副产物**：代码双审的 CODEX-02（「存量项目永远拿不到新片段」）对 claude 侧**自然消解**——
> 没有任何项目能通过 `CLAUDE.md` 把身份片段送到 claude 审查员面前。
> 该意见对 **codex 侧的 `AGENTS.md.snippet` 仍然成立**（codex 不带这个旗标），
> 裁决件 §2.4 登记的 BACKLOG 条目照旧。

## 3. P-b：`denied_tool_in_trace` 取到正向证据 —— **一次命中，无需重试**

提示词沿用探针既有的强制发起写法（`probes/claude.ts` 那段本来就带「即使你预计这次调用

1. **`denied_tool_in_trace = true`**（本机 2.1.273 实测）。设计 §3.7 事实表记的 true

2. **判据必须扫 `tool_use` 的工具名，不是 `permission_denials`**：本次 denials 为空数组，
   而拒绝信息在 `tool_result` 里。这与 `ClaudeProbe.denied_tool_in_trace` 的字段注释一致，
   本次是它的实测背书。
3. **`rejectionRecorded: true` 的前置条件已满足**（裁决件 §2.7 的从严策略：
   抓到留痕方可声明 true）。第 3 步可以据此声明，**并在适配器注释里指向本节**。

> **`readonly_breach = false` 同时得到复验**：负对照文件未落盘。
>
> **仍然保留的口径**（GLM-06 的裁决落点）：探针注释那句「强制发起能压低『没试』的概率，

### 8.1 修复要点（完整裁决见 `.reviews/M9-ClaudeCode审核者接入/code/` 的应答件）
