## 总判断

环形缓冲下标运算及时钟回拨阈值划分（> windowMs 清空重计、<= windowMs 队尾钳位）与计划裁决严格一致且逻辑正确。

建议调整重插时机仅在放行时触发，并补齐遗漏交付物。

**问题**：「删后重插」在限流拒绝时仍无条件执行，破坏了 Map 插入序与配额时间戳的单调性一致性，造成队头阻塞并阻碍过期 key 的及时回收。

**依据**：在 src/limiter.ts:66-72 中，allow 方法一开始无论请求最终放行与否，均执行 this.hits.delete(key) 与 this.hits.set(key, q)，将 key 移至 Map 队尾。而在 src/limiter.ts:95-110 的 reclaim/sweep 中，遍历 hits 时一旦遇到未过期的 key 便执行 else { break; }。若 key 在被拒时移至队尾，其 q.last() 保持为旧配额时间戳，使得 Map 中队头 key 的配额时间戳反而可能晚于队尾 key。当队头正常 key 尚未过期时，循环直接 break，导致其后所有早已过期的被拒 key 发生队头阻塞（Head-of-Line Blocking），在队头过期前无法被均摊回收或批量 sweep 清理。

**建议**：仅在请求获得放行许可（ok === true）并成功压入新时间戳时，才将 key 删后重插至 Map 队尾；被拒绝的请求不更新其在 Map 中的位置，保证 Map 队头至队尾的 q.last() 单调非降。

### AGY-05 · 吹毛求疵（nit）

**问题**：时钟回拨钳位时直接重写形参 now，导致单 key 的钳位时间戳泄露并污染全局 reclaim 的淘汰基准。

**依据**：在 src/limiter.ts:76 中，小幅回拨分支执行 else now = q.last()，直接改写了入参 now。随后第 86 行调用 this.reclaim(now, RECLAIM_PER_CALL, key)。向全局回收逻辑传入被单个 key 钳位后的未来时间戳，会导致计算全局 cutoff = now - this.windowMs 基准虚高，可能导致其他按调用者实际时间尚未过期的正常 key 被误删。

**建议**：避免直接覆盖 now 参数，引入独立的 effectiveNow 或 clampedNow 变量供当前 key 入队使用，reclaim 维持使用入参原始 now。

## 认为正确的部分

- 环形缓冲 Ring 的头尾下标运算（(head + len - 1) % cap 与 (head + len) % cap）逻辑严谨，容量与非空守卫齐备，消除了大 limit 下 Array.shift 的线性性能退化。

- 保留 FixedWindowLimiter 作为 SlidingWindowLimiter 的 @deprecated 别名，平滑兼顾了对外契约兼容性与语义纠偏。
- 构造函数对 limit（正整数）与 windowMs（正数）的边界校验严密，拒绝了非整数、负数与 NaN 等异常输入。
