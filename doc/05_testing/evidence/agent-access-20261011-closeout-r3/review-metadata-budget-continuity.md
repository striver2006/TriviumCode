# 完整代码审的运行元数据连续性方案

静态读取review.ts确认code收尾以相同base重新生成整个diff；仓内预算ledger/loaded追加会改变subject，而plan阶段此前仅按原稿hash核验。因此不能直接复用仓内动态预算目录启动第8次代码审，也不把编排器元数据任意当作零漂移。

保持原预算实现、计数规则、正式轮数及漂移/只读判据。全部在途调用结束后，逐文件复制预算所需approval、extensions、ledger到新的项目外预算目录，用O_EXCL记录来源/hash及逐文件一致性，复核reserved和completed均相等、两池上限/累计和全部历史原记录一致。旧目录仍原样保留，成为只读历史锚；新目录为明确切换后的唯一连续台账，历史复制项不再另算启动，不清零、不重编号、不双计。仅追加的新运行元数据写在项目外；新入口留存原v3，使用同一生产编排器、预算侧车和当前总8轮授权，薄probe实际入口仍为原冻结文件。

这只改变后续运行元数据的位置，不改变被审业务面、敏感集合、readonly或subject判据，不增Git忽略，不搬走/删除任何漂移文件，不改旧失败状态。审查冻结前保存切换清单和指纹，期间只有既有编排器归档与项目外预算元数据可产生。原台账的旧hash以及cutover连续性证据纳入第8次完整代码审上下文。若两池计数/hash不一致或存在在途记录则拒绝切换；以后不得继续使用旧预算root启动新调用。

依据用户要求的新独立证据目录、旧台账保留和审查期间禁止业务/被审证据新增，按可逆的取证目录组织执行；无需改变guard语义或判据，也没有扩大正式轮数。项目外新增完整台账及当前权威路径须在报告和最终交付列明，不以旧根停止增长掩盖累计启动数。预算扩容继续使用原openBudget.extend机制。
