# 《配置加载重构》实施计划（原稿）

## 1. 背景与现状

`src/config.ts:10` 的 `loadConfig` 目前是 `readFileSync + JSON.parse` 直返，对照 README 需求有三处缺口：

- 任何读失败（含文件缺失）一律抛错，没有默认值回退；
- 返回的是可变对象，调用方改得动；
- 每次调用都重新读盘。

README 需求复述（作为本计划的验收基准）：

- **R1 环境变量覆盖**：`APP_<KEY>` 覆盖同名顶层键，值按原键的类型转换（数字、布尔、字符串）；
- **R2 缺失回退 / 损坏报错**：配置文件缺失时回退到内置默认值而不是抛错；文件存在但 JSON 损坏时仍要报错，并指出文件路径；
- **R3 只读与单次读盘**：加载结果只读（调用方改不动），且同一进程内只读一次文件；
- **R4 签名约束**：调用方式 `loadConfig(path)` 保持不变。

## 2. 目标与非目标

**目标**：`src/config.ts` 单文件改造，满足 R1–R4，附可执行的单测。

**非目标（范围外）**：嵌套键覆盖（`APP_FOO__BAR` 之类）、`.env` 文件加载、异步版 `loadConfig`、引入 schema 校验库、配置热更新/文件监听、全量 schema 校验（文件里 `port` 写成字符串不报错；后果是此时 `APP_PORT` 按 string 规则"原样"覆盖，不做数字转换——明确声明，不留给审查方猜）。

## 3. 设计决策（逐条）

### 3.1 R1：`APP_<KEY>` 环境变量覆盖

- **遍历方向**：遍历配置的顶层键、反查 `process.env['APP_' + key.toUpperCase()]`，而不是遍历 `process.env`。天然只覆盖"同名顶层键"，无大小写歧义，结果确定，不受无关环境变量影响。
- **未知键忽略**：`APP_` 前缀但配置中不存在的变量（如 `APP_TZ`）静默忽略，不报错——保证返回值形状始终是 `AppConfig`。
- **类型转换**按合并后该键的实际类型（`typeof`）：
  - `number`：`Number(v)`，拒绝 `NaN` / `Infinity` / 空串（注意 `Number("") === 0`，须显式拒绝空串）；
  - `boolean`：仅接受 `true` / `false`（大小写不敏感），其余报错；
  - `string`：原样使用。
- **转换失败即抛错**，报错信息含变量名、原始值、期望类型、对应配置键。与 R2"损坏即报错"同一严格取向。→ **决策点 A**（反方案：失败静默跳过覆盖，宽松但易掩盖配置事故，不取）。
- **覆盖层级最高**：无论键值来自文件还是默认值，`APP_*` 一律覆盖（env 是最顶层）。

### 3.2 R2：缺文件回退默认值，损坏报错带路径

- 内置常量 `DEFAULT_CONFIG = { port: 3000, debug: false, name: 'app' }`。→ **决策点 B**：默认值取值需确认，本计划先按此拟定。
- **"缺失"的界定**：仅 `ENOENT` 回退默认值；`EACCES`、`EISDIR` 等其他读错误原样抛出（可包一层 `cause`）。→ **决策点 C**（反方案：任何读失败都回退默认值，会把权限问题伪装成默认配置，不取）。
- **损坏报错**：`JSON.parse` 失败，或内容不是纯对象（数组、`null`、标量）→ 抛 `Error`，**message 内嵌文件绝对路径**并携带 `cause`。`JSON.parse` 的原生报错不含路径，必须包装才能满足"指出文件路径"。
- **部分键文件**：文件是合法纯对象但只含部分键时，逐键浅合并到默认值之上（`{ ...DEFAULT_CONFIG, ...fileObj }`）。→ **决策点 D**（超出字面需求但对调用方更友好；若按"整文件替换"理解需明确，本计划取合并）。

### 3.3 R3：结果只读 + 单进程单次读盘

- **只读**：返回前递归冻结（`deepFreeze`：递归 `Object.freeze` 纯对象与数组，遇原始值终止）。当前 `AppConfig` 是扁平的三个原始类型字段，浅冻即够；递归冻为将来嵌套结构留余量。返回类型放宽为 `Readonly<AppConfig>`（可赋回 `AppConfig`，编译期兼容；`AppConfig` 接口本身不动）。
- **单次读盘**：模块级 `Map<绝对路径, Readonly<AppConfig>>` 缓存；key 用 `path.resolve` 归一化，防止 `./config.json` 与 `config.json` 造成双读。注意：参数名 `path` 遮蔽 `node:path` 模块名，实现时用 `import { resolve } from 'node:path'` 解构导入规避。
- **只缓存成功结果**：损坏文件抛错不进缓存，下次调用重试（文件可能已被修复）。→ **决策点 E**（反方案：连失败也缓存，进程内一锤定音，字面更贴合"只读一次"但操作上更差，不取）。
- **env 求值时机**：环境变量在首次成功调用时求值并固化进缓存，之后修改 env 不影响后续调用（与"只读一次"语义一致）。
- **并发**：`readFileSync` 同步执行 + 单线程事件循环，进程内无竞态，不需要锁。

## 4. 实现步骤（编码轮执行，本阶段不动代码）

1. `src/config.ts`：新增 `DEFAULT_CONFIG` 常量、模块级缓存 `Map`、`deepFreeze` 与 env 值转换辅助函数；重写 `loadConfig` 主体，签名保持 `(path: string) => Readonly<AppConfig>`。
2. 主流程伪码（供审查，非最终代码）：

   ```text
   loadConfig(path):
     key = resolve(path)
     if cache.has(key): return cache.get(key)
     try raw = readFileSync(path, 'utf8')
     catch e:
       if e.code == 'ENOENT': base = { ...DEFAULT_CONFIG }   # 标记来源=defaults
       else: throw wrap(e, path)
     try obj = JSON.parse(raw)
     catch e: throw Error(`配置文件损坏: ${key}`, { cause: e })
     if not plainObject(obj): throw Error(`配置文件损坏: ${key}`)
     base = { ...DEFAULT_CONFIG, ...obj }
     for k of keys(base):
       envName = 'APP_' + k.toUpperCase()
       v = process.env[envName]
       if v !== undefined: base[k] = convert(v, typeof base[k])   # 失败即抛错（决策点 A）
     result = deepFreeze(base)
     cache.set(key, result)
     return result
   ```

3. **测试基建**（前置缺口）：仓库当前没有 `package.json` / `tsconfig`，且 `.trivium/config.yaml` 的 `verify.build` / `verify.test` 均为空（编排器只执行显式声明的命令）。建议零配置路线：`node:test` + `tsx` 跑 TS 测试，用例写 `os.tmpdir()` 真实临时文件、不引 mock。测试命令需登记进 `verify.test`——`.trivium/config.yaml` 属用户配置文件，编码轮修改前先向用户确认。→ **决策点 F**。

## 5. 测试用例清单

1. 文件缺失 → 返回全默认值，不抛错；
2. JSON 语法损坏 → 抛错且 message 含文件路径；
3. 内容为数组 / `null` / 标量 → 抛错且 message 含文件路径；
4. 合法完整文件 → 键值与文件一致；
5. 部分键文件 → 缺的键回落默认值（决策点 D 的行为锚点）；
6. `APP_PORT` / `APP_DEBUG` / `APP_NAME` 三类型覆盖各自生效；
7. `APP_PORT=abc` → 抛错（决策点 A 的行为锚点）；
8. `APP_DEBUG=yes` → 抛错；
9. 未知 `APP_TZ` 被忽略，返回形状不变；
10. `Object.isFrozen(result) === true`；
11. 同路径二次调用返回**同一对象**（`===` 身份相等，佐证未重读）；
12. `./config.json` 与 `config.json` 命中同一缓存项（resolve 归一化的锚点）；
13. 非 ENOENT 读错误（模拟 `EACCES`，macOS 下可用目录代替文件触发 `EISDIR`）→ 原样抛出不回退；
14. 损坏 → 修复文件 → 再次调用成功（验证失败不缓存，决策点 E 的行为锚点）。

## 6. 风险与待确认

| # | 决策 | 本计划取向 | 反方案（未取） |
|---|------|-----------|---------------|
| A | env 值类型转换失败 | 抛错，信息含变量名/原始值/期望类型 | 静默跳过覆盖 |
| B | 默认值取值 | port 3000 / debug false / name 'app' | 待用户确认 |
| C | "缺失"的界定 | 仅 ENOENT 回退，其他读错误抛出 | 任何读失败都回退 |
| D | 部分键文件 | 逐键合并到默认值 | 整文件替换、缺键留 undefined |
| E | 失败是否缓存 | 只缓存成功结果，失败可重试 | 连失败一并缓存 |
| F | 测试基建 | node:test + tsx，命令登记进 verify.test | 引 vitest 等框架 |

风险：R1 的"同名"按"env 后缀大写 == 配置键大写"实现，若未来出现 `appName` 这类驼峰键，`APP_APPNAME` 的映射需再约定（当前 `AppConfig` 无此类键，暂不处理）；R3 的缓存以"进程"为界，测试里如需重置需用动态临时路径规避（不用改内部加 reset 钩子，保持 API 干净）。
