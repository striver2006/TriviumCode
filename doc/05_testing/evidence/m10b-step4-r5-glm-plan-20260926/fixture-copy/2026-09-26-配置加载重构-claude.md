### CLAUDE-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.1 类型转换 / §5 测试用例6-7` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | medium |

**问题**：数字转换只显式排除了空字符串这一个Number()强制转换陷阱（'注意 Number("") === 0，须显式拒绝空串'），但同一函数还有一个同类陷阱没被提及：纯空白字符串（如一个或多个空格、制表符）经Number()同样会被转成0（Number('   ') === 0），因为JS会先trim再转换。如果APP_PORT被意外设成带尾随空格的值（脚本拼接、CI变量注入时很常见），当前设计会静默得到port=0而不是按'转换失败即抛错'的既定严格取向报错，且没有任何测试用例覆盖这一路径。

**依据**：plan 原文：'数字：Number(v)，拒绝 NaN / Infinity / 空串（注意 Number("") === 0，须显式拒绝空串）'；测试用例清单第7条只写了 'APP_PORT=abc → 抛错'，没有空白字符串场景。src/config.ts 当前实现未涉及此逻辑，是纯计划层遗漏。

**建议**：把'拒绝空串'的检查改成对trim后的字符串做空值判断（或显式说明为什么只挡精确空串就够），并在测试用例清单里补一条空白字符串的用例。

### CLAUDE-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.1 遍历方向 / §3.2 决策点D` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | medium |

**问题**：决策点D选择'逐键浅合并到默认值之上'（{ ...DEFAULT_CONFIG, ...fileObj }），但没有过滤fileObj里不在DEFAULT_CONFIG/AppConfig声明范围内的额外键。这些额外键会原样进入合并后的base对象，而§3.1的env覆盖逻辑是'遍历配置的顶层键'——即遍历base的键，不是遍历AppConfig的键。结果是：只要JSON文件里多写了一个陌生字段（比如笔误的历史字段），它就会被一并纳入可被env覆盖的范围，与同一节声称的'保证返回值形状始终是AppConfig'相矛盾——该保证只针对'未知APP_变量被忽略'这一半，没有覆盖'文件带来未知键'这一半。

**依据**：plan 原文3.1：'未知键忽略：APP_ 前缀但配置中不存在的变量...静默忽略，不报错——保证返回值形状始终是 AppConfig'；3.2决策点D：'逐键浅合并到默认值之上'；伪码第4步 'for k of keys(base)' 遍历的是合并后的base而非固定的AppConfig键集合。src/config.ts里AppConfig接口只声明了port/debug/name三个字段，可确认'额外键'确实是接口之外的情形。

**建议**：在合并步骤里显式只取AppConfig声明的键（或至少在计划里说明'文件多余键是否保留、是否参与env覆盖'这一决策，不要留给实现阶段隐式决定）。

### CLAUDE-03 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.3 单次读盘 / §3.2 决策点E` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | medium |

**问题**：决策点E只讨论了'损坏(JSON.parse失败)'这一种失败该不该缓存，没有明确讨论'文件缺失→回退默认值'这条路径本质上也是把一次'非文件内容'的结果永久缓存：如果进程启动早期文件还不存在（回退默认值并缓存），之后该文件被外部进程创建/写入，同一路径的后续loadConfig调用仍会命中缓存返回旧的默认值，永远不会再读到新文件内容。这与'只读一次'字面自洽，但决策表里没有把这个场景单独列出并确认是预期行为，测试用例清单里也只测了'损坏→修复'（用例14），没有测'缺失→之后创建'这一更贴近实际部署时序的场景。

**依据**：plan §3.2决策点E表述聚焦于'损坏文件抛错不进缓存'，未提及ENOENT分支的缓存语义；§5测试用例14验证的是'损坏→修复'而非'缺失→创建'；README R2/R3原文对这一交叉场景没有额外说明，属于计划需要显式补一句的空白。

**建议**：在决策点E或风险小节里补一句：'文件缺失回退默认值这一结果本身即视为成功并永久缓存，同一进程内文件之后被创建也不会被感知'，并考虑补一条对应测试用例作为行为锚点。

### CLAUDE-05 · 吹毛求疵（nit）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.3 单次读盘` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | low |

**问题**：缓存key用'path.resolve(path)'归一化，这依赖调用时的process.cwd()。如果同一进程生命周期内cwd发生变化（比如测试框架切换工作目录、或调用方在不同阶段chdir），同一个相对路径字符串在两次调用里会resolve成不同的绝对路径，从而没有真正命中'同一文件只读一次'的缓存，也可能反过来让两个原本不同的相对路径意外resolve到同一绝对路径。这个前提没有在计划里显式声明（只写了'./config.json与config.json命中同一缓存项'这一顺向验证，用例12），是一个低概率但值得写一句免责声明的边界。

**依据**：plan §3.3原文：'key用path.resolve归一化，防止./config.json与config.json造成双读'；§5测试用例12只验证了cwd不变时的归一化效果，未提及cwd变化场景。

**建议**：在决策点或风险小节里补一句：'缓存key的稳定性假设进程内cwd不变'，把这个隐含前提显式化即可，不必改设计。
