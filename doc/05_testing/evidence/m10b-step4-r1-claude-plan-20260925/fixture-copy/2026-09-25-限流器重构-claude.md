# 限流器重构计划（r1）

## 1. 背景

`src/limiter.ts` 里的 `FixedWindowLimiter` 按固定窗口计数：每个 key 在 `windowMs` 内最多放行 `limit` 次。
现有两个问题：

1. **窗口边界突刺**：在窗口末尾与下一窗口开头各打满 `limit` 次，`windowMs` 的任意一段里实际可放行 `2 × limit` 次。
2. **key 永不回收**：`hits` 只增不减，长时间运行、key 基数大（按 IP 或用户 id 限流）时内存无上界。

## 2. 目标

- 任意长度为 `windowMs` 的时间段内放行次数不超过 `limit`（精确滑动窗口），或给出可证明的上界。
- 内存随活跃 key 数增长，闲置 key 在有限时间内回收。
- 对外接口 `allow(key, now?)` 不变，调用方零改动。

## 3. 方案

### 3.1 算法：滑动窗口日志

每个 key 存一个时间戳队列（升序）。`allow(key, now)`：

1. 从队头弹出所有 `≤ now - windowMs` 的时间戳；
2. 队列长度 `< limit` 时压入 `now` 并放行，否则拒绝。

每个 key 最多存 `limit` 个时间戳，单次调用均摊 O(1)。

### 3.2 回收

- 每次 `allow` 后若队列为空，删除该 key；
- 另设 `sweep(now)`：遍历全部 key，删除队尾时间戳 `≤ now - windowMs` 的项。由调用方定时调用（例如每 `windowMs` 一次），限流器本身不开定时器。

### 3.3 时钟

`now` 缺省取 `Date.now()`。时钟回拨时（`now` 小于队尾）按队尾处理，不压入比队尾更早的时间戳。

## 4. 测试

- 边界突刺：窗口末尾打满后，下一个窗口开头立即请求应被拒绝；
- 回收：`sweep` 后闲置 key 不在 `hits` 中；
- 时钟回拨：回拨后的请求不造成超发；
- 接口兼容：现有调用方式行为不变（`limit` 次内全部放行）；
- 多 key 隔离：一个 key 打满不影响其它 key。

## 5. 风险与取舍

- 内存：每 key 最多 `limit` 个数；`limit` 很大（如 10⁵）时考虑改滑动窗口计数（两段加权近似），本轮不做；
- `sweep` 是全表遍历，key 数极大时单次耗时高；可改为分批，本轮不做。

## 6. 不做

- 分布式限流（多进程共享计数）；
- 令牌桶 / 漏桶等其它算法的可插拔接口。
