## 总判断

计划存在严重逻辑缺陷与架构自相矛盾：§3.2 的「每次 allow 后若队列为空则删除」是永不触发的死逻辑，导致闲置 key 回收完全推给外部 sweep，击穿「调用方零改动」承诺。
若调用方保持零改动，key 永不回收的内存泄漏问题重构后 100% 依然存在。
sweep 同步全表遍历在高基数场景下严重阻塞 Node.js 事件循环，每秒全表扫将引发灾难性 P99 延迟，不做分批的取舍站不住脚。
时钟回拨策略语焉不详，将 now 简单钳位至队尾在时钟回调时会导致窗口长期无法滑动、请求假死饥饿且阻断回收；未考虑单调时钟。
缺少对类名 FixedWindowLimiter 变更与向后兼容导出的明确契约说明。
总体结论：要求修改计划（request-changes），重新设计内存回收闭环与时钟模型后再行实施。

### AGY-01 · 阻断（blocker）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.2` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：§3.2 提出的「每次 allow 后若队列为空，删除该 key」是永不触发的死逻辑。按 §3.1 算法，若旧请求全部过期被清空，队列长度为 0 < limit，必定会追加新时间戳 now，队列长度至少为 1；若未放行，队列长度等于 limit（>= 1）。因此在正常限流场景下，allow 结束时队列永远非空，该被动回收机制完全无法回收任何 key。

**依据**：在 .reviews/限流器重构/plan/2026-09-25-限流器重构-claude.md 中，§3.1 步骤 1 先弹出过期时间戳，步骤 2 在「队列长度 < limit」时压入 now，步骤 3.2 却声称「每次 allow 后若队列为空，删除该 key」。结合 src/limiter.ts 现有使用模式，只要 limit >= 1，allow 执行完毕时队列必然至少包含新压入的时间戳或原有未过期时间戳，队列为空的判定永远为 false。

**建议**：重新审视被动回收触发时机。如需在请求路径上回收，应在清理过期项后、写入新项前判定，但此时新请求即将写入仍不能删；若队列为空代表闲置，则闲置 key 本身不再触发 allow，必须依赖独立的生命周期管理或在其它操作时惰性扫描，不可将回收希望寄托于 allow 后的空队列判断。

### AGY-02 · 阻断（blocker）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2, §3.2` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | high |

**问题**：内存回收机制将 sweep 职责外包给调用方，与「调用方零改动」的目标直接冲突；若调用方零改动，闲置 key 将永远得不到回收，重构目标彻底落空。

**依据**：.reviews/限流器重构/plan/2026-09-25-限流器重构-claude.md §2 承诺「对外接口 allow(key, now?) 不变，调用方零改动」，且目标为「内存随活跃 key 数增长，闲置 key 在有限时间内回收」；但在 §3.2 中却规定「另设 sweep(now)... 由调用方定时调用（例如每 windowMs 一次），限流器本身不开定时器」。由于 AGY-01 中 allow 的空队列删除无法生效，若现有调用方按零改动原则不显式调用 sweep，hits 将依然永不回收，与 src/limiter.ts 现有缺陷毫无区别。

**建议**：明确回收职责与生命周期契约。若坚持调用方零改动，应在限流器内部集成带 unref() 的弱引用定时器或在 allow 路径中引入均摊的分批淘汰（如随机抽样/游标步进）；若将 sweep 暴露给调用方，必须在接口设计与迁移说明中承认这是一项破坏性/新增契约要求，不可宣称调用方零改动。

### AGY-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.2, §5` |
| 类别 | performance ｜ 层次 plan |
| 置信度 | high |

**问题**：sweep 采用同步全表遍历的设计在高基数 key 场景下站不住脚，会严重阻塞 Node.js 单线程事件循环并引发 P99 延迟毛刺。

**依据**：.reviews/限流器重构/plan/2026-09-25-限流器重构-claude.md §1 明确重构背景为「key 基数大（按 IP 或用户 id 限流）」，§3.2 建议调用方每 windowMs（例如 1000ms）调用一次 sweep 全表遍历。在数十万级 IP 的高基数场景下，在单线程中频繁同步遍历整个 Map 并删除失效条目会导致显著的 Event Loop Lag；而 §5 将分批列为「本轮不做」，直接与高基数限流场景产生性能冲突。

**建议**：放弃全表遍历方案。可利用 JS Map 原生保留插入序的特性（或双向链表/分桶轮转）维护按最后活跃时间排序的队列，遍历时一旦遇到未过期项立即终止（耗时降为 O(已过期 key 数) 而非 O(总 key 数)），或采用双 Map/时间轮世代淘汰实现 O(1) 批量回收。

### AGY-04 · 重要（major）

| 项 | 内容 |
| :--- | :--- |

**问题**：时钟回拨处理策略缺乏完整定义，在发生 NTP 步进调整或大幅回拨时会导致限流器长期饥饿拒绝（Starvation）且阻断内存回收。

**依据**：.reviews/限流器重构/plan/2026-09-25-限流器重构-claude.md §3.3 仅说明「时钟回拨时（now 小于队尾）按队尾处理，不压入比队尾更早的时间戳」。未说明步骤 1 清理队头时是否采用队尾时间，若步骤 1 使用回拨后的 now，会导致过期时间窗口被大幅向前压缩甚至无法清理；若直接将时间戳钳位至队尾，当系统时钟发生较大幅度回拨（如系统时间纠偏数秒至数分钟）时，已打满的队列在 now 追赶上队尾前将持续拒绝所有合法请求，同时 §3.2 的 sweep 也会因 now - windowMs 偏小而无法清理该 key，造成业务假死与内存滞留。

**建议**：补充时钟回拨的边界定义与恢复机制。在 Node.js 环境下，建议评估基于单调时钟（performance.now() 计算毫秒差值）替代易受 NTP 跳变影响的 Date.now()；对回拨幅度设定阈值，超过容忍范围时应有重置或警告机制，而非无条件钳位至未来时间戳。

## 认为正确的部分

- 识别并正视了固定窗口算法在边界上的 2 × limit 突刺问题，选用滑动窗口日志能实现严格精确的滑动窗口限流。
- 坚持对外核心限流方法 allow(key, now?) 签名与入参语义兼容，降低业务调用方的迁移负担。
- 清晰识别出固定窗口计数器在海量 key 场景下内存无界膨胀的问题，将内存回收列入核心目标。
- 清醒认识到高 limit 场景下滑动窗口日志的内存放大风险，且明确界定了不做分布式与复杂算法插件的实现边界。
