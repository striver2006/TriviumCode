## 总判断

最危险的一条：§3.2 的第一条回收路径（allow 后队列为空即删 key）在 §3.1 的算法下永不可达。我按计划原文实现并跑了 22 万次调用，该分支触发 0 次——所以全部内存回收都压在 sweep 上，而 sweep 是「由调用方定时调用」、仓库里零个调用方、§2 又承诺「调用方零改动」。三者叠加的净结果是：§1 提出的「内存无上界」按计划做完依然存在，而 §4 的回收测试只覆盖 sweep，全绿也发现不了。
第二条：时钟只写了回拨，且回拨是隐式 fail-closed 且损害无上界。实测回拨后停留会造成 14982 次连续拒绝，直到 now 重新爬过「队尾+windowMs」才恢复，同期 sweep 也回收不了这些卡死的 key；时钟前跳则完全没写，实测可瞬时放行 2×limit，直接击穿 §2 的精确上界目标。
关于审查焦点问的取舍：sweep 全表遍历本身站得住（实测 10 万 key 3.6ms、100 万 key 61.1ms 同步阻塞），但计划没给出预期 key 基数，而这个数字才决定取舍成立与否；又因为它是唯一有效的回收路径，「本轮不做分批」等于把整个内存目标的鲁棒性推迟。
方向（滑动窗口日志 + 全同步 API，不引入外部依赖）我认可；问题集中在计划层面的未决策与未量化，补齐后再实施成本很低。

**结论**：`request-changes`

### CODEX-01 · 阻断（blocker）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.2 第 1 条（对照 §3.1 步骤 1-2）` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：「每次 allow 后若队列为空，删除该 key」在 §3.1 描述的算法下是不可达分支，等于本轮没有任何惰性回收。§3.1 的顺序是「先淘汰队头过期项，再按 len < limit 决定压入或拒绝」：放行时刚压入 now，队列长度 ≥ 1；拒绝时 len == limit ≥ 1。只有 limit ≤ 0 的退化配置才可能出现空队列。于是回收 100% 依赖 sweep，而计划把它写成两条回收路径之一，掩盖了「sweep 一旦没被接线，§1 的内存无上界问题原样保留」这个事实。更麻烦的是 §4 的回收用例只断言 sweep 的效果，实施后测试全绿也暴露不了这条分支是死的。

**依据**：读 src/limiter.ts:6-15 确认现有实现同样是「命中即写回」、没有可继承的惰性删除路径。按 §3.1+§3.2+§3.3 原文用 node -e 在内存中实现并跑随机负载：limit=5/windowMs=1000、20 万次调用、500 个 key，空队列删除分支触发 0 次；limit=1/windowMs=1000、2 万次调用、50 个 key，同样 0 次。两组跑完后 Map 中仍分别驻留 500 / 50 个 key（含大量早已过期的条目）。

**建议**：二选一并写进计划：要么删掉这条 bullet，明确声明 sweep 是唯一回收路径（那么回收目标就完全押在调用方契约上，需配合 CODEX-02 补齐）；要么把惰性回收改成真正能触发的形式——例如每次 allow 顺带回收常数个其它 key 的过期项，把回收成本摊到调用上，这还能一并化解对 sweep 的依赖。不要保留一条永不执行的分支。

### CODEX-02 · 阻断（blocker）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.2 第 2 条 对照 §2 第 3 条` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | high |

**问题**：sweep「由调用方定时调用」与 §2「对外接口 allow(key, now?) 不变，调用方零改动」互相矛盾：新增一个必须被周期性调用的方法就是一项新的调用方义务，不是零改动。而这项契约的要素计划一个都没定义——谁负责调、周期怎么定（只有「例如每 windowMs 一次」）、sweep 的 now 有没有默认值、传入的时钟域是否必须与 allow 同源、从不调用会怎样。仓库里现在没有任何调用方，实施时这条义务极可能被整体漏掉。时钟域尤其危险：若 allow 用缺省 Date.now() 而调用方给 sweep 传别的基准（如进程单调时钟），sweep 会一次性清空全部活跃 key（超发）或永远回收不到东西（泄漏），两个方向都是静默故障。

**依据**：find 全仓（排除 .git/.trivium/.reviews）只有 src/limiter.ts 一个源文件：无调用方、无定时器、无入口文件。src/limiter.ts:6 的 allow 有 now 默认值，而计划 §3.2 的 sweep(now) 未写默认值，两者的缺省语义因此不对齐。README.md 只描述限流器本身，未提任何调度职责归属。

**建议**：补一节「sweep 调用契约」：调用方与接线方式（构造期注入回调 / 显式公开方法 / 限流器内部可选定时器，三选一并说明取舍）、周期与 windowMs 的关系、now 的缺省值、以及「时钟域必须与 allow 同源」的硬性要求；把「从不调用时的行为退化」写成明示的已知限制。同时把 §2 的措辞改为「allow 签名不变；新增 sweep 需要调用方接线」，别让两条目标互相打脸。

### CODEX-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.3` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：「按队尾处理，不压入比队尾更早的时间戳」是一个隐式的 fail-closed 策略，且损害没有上界。当回拨是永久性的（NTP 纠正一个走快的时钟、虚机快照恢复后时钟停在过去），队尾 T 就成了一个「未来时间戳」：此后每次调用都被 clamp 到 T，淘汰线恒为 T-windowMs，队列很快被 T 的重复值填满到 limit，该 key 于是被持续拒绝，直到真实时钟重新爬到 T+windowMs。时钟快了多少，拒绝就持续多久——快 1 小时就是 1 小时的全量拒绝，这是限流器自己造成的可用性事故，而计划既没说这是刻意选择的 fail-closed，也没给任何止损开关。这些卡死的 key 同时回收不掉：sweep 判据是队尾 ≤ now-windowMs，队尾在未来则恒不成立。

**依据**：按 §3.1+§3.3 原文实现后实测：limit=2/windowMs=1000，先在 t=10000、10100 打满（队尾 10100），再把 now 回拨到 5000 并持续递增到 20000——连续拒绝 14982 次，直到 now=11000（淘汰线追上队头）才首次放行；期间 sweep(5000) 回收 0 个 key，卡死的 key 一直驻留。另：src/limiter.ts:8 的现有实现在回拨下走的是另一条路（now-cur.start 为负 → 不重置 → 继续按旧窗口计数），计划没有说明新旧语义差异对现有调用方的影响。

**建议**：把回拨策略作为显式决策写入计划，并给损害加上界：至少区分「小幅抖动」与「大幅回拨」（例如幅度超过 windowMs 即判为时钟故障），并决定大幅回拨时是继续 fail-closed、丢弃该 key 历史 fail-open、还是全局重置。同时评估改用单调时钟源（Node 的 process.hrtime / performance.now）从根上消灭这类问题——但 allow 的 now 是调用方传入的 epoch 毫秒，换时钟域属接口级变更、与 §2 的兼容目标冲突，需一并权衡并写明结论。无论选哪条，都要写出「最坏情况下该 key 会被拒绝多久」。

### CODEX-04 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.3 / §2 第 1 条` |
| 类别 | correctness ｜ 层次 requirement |
| 置信度 | high |

**问题**：§3.3 只处理回拨，时钟前跳完全没覆盖，而前跳同样能击穿 §2 的第一条目标。前跳（NTP 纠正走慢的时钟、虚机挂起恢复、容器迁移）会让淘汰线 now-windowMs 一次性越过整条队列，limit 个名额瞬间恢复满额，紧接着再来 limit 次也全放行：真实时间只过了几毫秒，却放行了 2×limit 次——这正是 §1 指控固定窗口的同一个毛病，在新方案里换了个形式复现。sweep 在前跳下也会一次性清空全表，把内存目标「达成」成一种假象。计划没有写下任何时钟假设，§2 的「任意长度为 windowMs 的时间段内放行次数不超过 limit」因此是一条不可达的无条件承诺。

**依据**：实测 limit=3/windowMs=1000：t=0,1,2 三次放行后 t=3 被拒（队列已满）；把 now 前跳到 100000 后连续三次立即放行，即在远小于 windowMs 的真实时间跨度内放行 6 次 = 2×limit。sweep 侧同理：其判据也是队尾 ≤ now-windowMs，对照实验中把 cutoff 设为 n/2 时，100 万 key 里有 500001 个在一次 sweep 中被删净——now 前跳会让全表一次性满足该判据。src/limiter.ts:8 的现有实现在前跳下同样重置窗口，说明这不是新引入的缺陷，但计划把它写成了「精确滑动窗口」的目标，语义上就变成会被打脸的承诺。

**建议**：在 §2 或 §3.3 明确写出时钟假设（例如「假定 now 单调不减且与真实时间偏差远小于 windowMs；假设被破坏时上界不成立」），把 §2 第一条从无条件承诺改为带前提的承诺；并决定前跳是否需要与回拨对称的处理（如 now 相对队尾前跳超过若干 windowMs 即视为时钟故障）。§4 也要补一条前跳用例，别只测回拨。

### CODEX-05 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.1 末句「单次调用均摊 O(1)」（对照 §5 第 1 条）` |
| 类别 | performance ｜ 层次 plan |
| 置信度 | high |

**问题**：这个复杂度承诺完全取决于队列用什么数据结构，而计划没有指定。「每个 key 存一个时间戳队列」+「从队头弹出」在 JS 里最自然的落地是 Array + shift()，而 shift 不是 O(1)：V8 对小 limit 有快路径，limit 一大就退化为每次淘汰搬移整段元素，恰好落在 §5 自己设想的 limit=10⁵ 区间——也就是计划认为「本轮不做近似算法也能扛」的区间。一个被写进计划的复杂度结论会直接决定实施者选不选 Array，因此必须在计划里定死结构，不能留给实现临场发挥。

**依据**：同一段逻辑分别用 Array+shift 与「数组 + 队头下标」实现，各跑 30 万次调用：limit=1000 时 8.0ms vs 2.4ms（3.4 倍）；limit=20000 时 618.2ms vs 2.0ms（313 倍）。shift 的代价随 limit 线性放大，而 §5 设想的 limit 是 10⁵，比实测值还大 5 倍。另需注意队头下标方案自身会让数组只增不减，必须配合周期性压缩，否则省下 CPU 换来内存泄漏——这也是结构选型必须写进计划的原因。

**建议**：在 §3.1 指名队列结构（环形缓冲 / 队头下标+周期压缩 / 链式 deque，三选一），并把复杂度结论改写成对该结构成立的表述；同时把 §5「limit 很大」的阈值与实测数据挂钩，而不是只写一个 10⁵ 的猜测值。

### CODEX-06 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2 第 2 条 / §3.2 第 2 条` |
| 类别 | performance ｜ 层次 requirement |
| 置信度 | high |

**问题**：回收时机的上界与由此决定的内存上界都没有量化，§2 的「内存随活跃 key 数增长」不准确。按 sweep 每 windowMs 一次推算：key 最后一次命中在 T，要到 T+windowMs 才满足 sweep 判据，而下一个 sweep 点最晚落在 T+2×windowMs，所以死 key 的驻留上界约 2 个 sweep 周期，内存上界是「2×windowMs 内出现过的不同 key 数 × limit × 每个时间戳的字节数」，不是「活跃 key 数」。这个差别在 windowMs 较大时是决定性的：windowMs=1 小时的按 IP 限流、sweep 每小时一次，就意味着高峰一小时的全部不同 IP 都驻留在内存里。计划既没给这个上界，也没说 sweep 周期该怎么选（绑定 windowMs，还是绑定可接受内存），实施者无从判断该不该分批——这正是审查焦点问的那条取舍缺的那块地基。

**依据**：§3.2 只写「例如每 windowMs 一次」，§5 只写「key 数极大时单次耗时高」，两处都没有数字；§1 明确说 key 是「按 IP 或用户 id」，基数由外部流量决定。我实测了 sweep 的扫描成本作为量化基线：10 万 key 全表扫描并删除 50 万项级别的判据命中耗时 3.6ms，100 万 key 耗时 61.1ms（同步、单线程阻塞）。也就是说全表遍历在 10 万量级完全可接受，在百万量级则是每周期约 60ms 的事件循环停顿——但计划没有给出预期基数，这个取舍因此无法被评估。

**建议**：补两个数：预期 key 基数（量级即可）与可接受的内存上界；由此推出 sweep 周期，并把「死 key 驻留 ≤ 2 个 sweep 周期」写成明示的回收延迟上界。同时把 §2 的措辞改成与实际语义一致的「随 sweep 周期内出现过的 key 数增长」。有了基数，§5「全表遍历本轮不做分批」才谈得上站得住。

### CODEX-07 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §1 第 2 条 / §3.2 / §5 风险清单` |
| 类别 | security ｜ 层次 requirement |
| 置信度 | medium |

**问题**：key 基数没有任何硬上界，而 §1 自己说 key 是「按 IP 或用户 id」，即攻击者可控。sweep 限制的是驻留时长，不是一个周期内的峰值数量：两次 sweep 之间，攻击者用大量不同 IP 打进来，每个 key 都要占 limit 个时间戳，峰值内存 = 该周期内不同 key 数 × limit，没有任何东西拦得住。这意味着 §1 的「内存无上界」只是被缓解成「内存上界由攻击者在一个 sweep 周期内决定」，而计划把它当成已解决。缺的是一个容量阀门（key 数上限 + 触顶策略，或按最旧淘汰的 LRU），以及触顶时是拒绝新 key（fail-closed，等于让攻击者把合法用户挤出去）还是放行新 key（fail-open，等于限流失效）——这个策略选择需要人来拍板，不能留给实现。

**依据**：src/limiter.ts:3 的 hits 是裸 Map，无容量限制、无淘汰；计划 §3.1 沿用同一结构（「每个 key 存一个时间戳队列」），全文未出现任何容量上限。§5 的风险清单只列了 limit 过大与 sweep 耗时两条，没有列 key 基数过大——而后者才是 §1 第 2 个问题的主因。

**建议**：在 §5 补上「key 基数由外部流量/攻击者决定」这条风险，并在 §3 做显式决策：是否设 key 数上限、触顶时拒绝新 key 还是淘汰最旧 key、以及该策略对应 fail-open 还是 fail-closed。若本轮决定不做上限，也要写明「本轮不防 key 基数型内存放大」，别让它藏在「内存随活跃 key 数增长」这句话里。
