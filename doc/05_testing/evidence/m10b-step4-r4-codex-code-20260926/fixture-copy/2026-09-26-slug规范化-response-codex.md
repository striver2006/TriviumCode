# slug规范化 · 代码审查应答（第 1 轮）

## 0. 应答总览

共 7 条意见：**接受 5 条、驳回 1 条、暂缓 1 条**。

最要紧的是同一处契约缺口被两侧同时点到（CLAUDE-02 / CLAUDE-03 ≈ AGY-02）：非空标题在某些输入下会静默返回空字符串 `''`，而 JSDoc 只承诺「不切词、不以横线结尾」，调用方按文档读不出这个结果。语义本身不改——README 明令「不在单词中间截断」，所以既不能退回半个词、也不能返回超长串——缺的是把边界写进契约。

其次是 maxLength 异常值的策略分裂（CLAUDE-01 ≈ AGY-03）：有限负数被钳成 0 返回空串，NaN／±Infinity 却走「不截断」，同一类非法入参给出相反结果。

唯一驳回的是 AGY-01：它要求改掉「只保留 ASCII」，而这条是本次任务的既定规格，改它就等于改需求。

## 2. 双方共同指出的问题

- **空串契约缺口（CLAUDE-02 / CLAUDE-03 ≈ AGY-02）**：两侧都指出「非空标题可能静默返回 `''`」。一致结论：语义保留（README 禁止切词），缺的是文档化与调用方兜底，落在 JSDoc。

## 3. 不予采纳的意见及其依据

### AGY-01 · 改 ASCII-only 为 Unicode 属性转义或引入 NFKD 归一化 —— 驳回

1. README「待实现」节把「只保留 ASCII 字母、数字与横线；其余字符视为分隔符」写成明文要求。`slugify` 的保留集合由规格定义、不由实现自选；改用 `/[^\p{Letter}\p{Number}]+/gu` 会把「非英文标题产出空串」从「规格后果」变成「实现违约」。
2. NFKD 分解（`é → e`）实质上改掉了「其余字符视为分隔符」这条判据：变音字母会由分隔符变成字母，`café` 不再产出 `caf`。同样越出本轮范围。
3. 该意见中真正成立的部分是契约提示（「要求调用方提供降级方案」），已并入 CLAUDE-03 的接受项、落点在 JSDoc；本条驳回不影响该诉求被处理。
4. 若确实要做国际化 slug，那是需求变更：应先改 README 规格与调用方契约，再改实现——不该由代码审查的应答绕过规格直接落地。
