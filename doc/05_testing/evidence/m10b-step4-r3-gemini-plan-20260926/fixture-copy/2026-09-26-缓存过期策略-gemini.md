# 缓存过期策略计划（r1）

> 执笔说明：本稿以 gemini 为名义 Driver 认领并落笔（M10b 第 4 步 3-3 夹具轮），正文实际由 Claude 会话代写。

## 1. 背景

`src/cache.ts` 里的 `LruCache<V>` 只按容量淘汰：超出 `capacity` 时删最久未访问的条目，条目本身不会过期。
调用方开始拿它缓存下游接口的响应，出现两个问题：

1. **陈旧数据**：下游数据已更新，缓存里的旧值只要一直被访问就一直命中，永远不会被刷新。
2. **冷数据占位**：访问量低但容量未满时，早已无用的条目长期驻留；容量设大时内存浪费明显。

## 2. 目标

- 每个条目带过期时刻，过期后 `get` 不再返回它（返回 `undefined`，与未命中同形）。
- 过期条目在有限时间内释放，不依赖它被再次访问。
- 现有调用方式 `new LruCache(capacity)`、`get(key)`、`set(key, value)` 不改签名，调用方零改动。

## 3. 方案

### 3.1 数据结构

`Map<string, { value: V; expiresAt: number }>`，仍利用 `Map` 的插入序表达 LRU 序。

- 构造参数增加可选的 `defaultTtlMs`（缺省 `Infinity`，即不过期，保持旧行为）；
- `set(key, value, ttlMs?)`：第三参可选，覆盖默认 TTL；`expiresAt = now + ttl`；
- `now` 由构造时注入的时钟函数取得（缺省 `Date.now`），便于测试。

### 3.2 读路径：惰性过期

`get(key)`：命中后先比较 `expiresAt <= now`，过期则删掉该条目并返回 `undefined`；未过期才按 LRU 规则移到队尾。

### 3.3 释放：写时顺带清理

`set` 在淘汰超容条目之前，从 `Map` 头部（最久未访问端）起连续检查，删掉已过期的条目，遇到第一个未过期的即停。
不开定时器，不做全表扫描。

### 3.4 `size` 的语义

`size` 返回 `Map` 当前条目数，**可能包含尚未清理的过期条目**。文档注明这是上界而非精确的有效条目数。

## 4. 测试

- 过期后 `get` 返回 `undefined`，且该条目被删掉；
- 未过期条目的 LRU 顺序与改动前一致；
- `set` 的第三参覆盖默认 TTL；`defaultTtlMs` 缺省时行为与旧版完全相同；
- 注入假时钟推进时间，验证写时清理只从头部清到第一个未过期条目为止；
- `capacity` 淘汰与过期清理同时发生时，不会多删未过期条目。

## 5. 风险与取舍

- **头部清理不完整**：LRU 序是访问序而非过期序，头部未过期、后面却已过期的条目要等被访问或被挤出才释放。
  换成按 `expiresAt` 排序的最小堆可以精确释放，但每次访问都要维护两套顺序，本轮不做；
- **时钟回拨**：注入的时钟回拨时，已写入的 `expiresAt` 相对变远，条目会晚过期。本轮不处理，只在文档里说明；
- `size` 语义变宽（见 3.4），依赖 `size` 做容量监控的调用方可能读到偏大的值。

## 6. 不做

- 后台定时清理；
- 按值大小计费的容量（仍按条目数）；
- 过期回调 / 事件通知。
