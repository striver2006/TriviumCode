### CLAUDE-01 · 阻断（blocker）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `§2 目标 vs §3.3/§5` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | high |

**问题**：§2 明确承诺「过期条目在有限时间内释放，不依赖它被再次访问」，但 §3.3 的清理只在 set() 时从 Map 头部扫描连续前缀、遇到第一个未过期条目即停。考虑一个只写一次、之后再未被访问过的键（正是 §1 背景里「冷数据占位」的原型场景）：只要容量始终未被撑满（无需淘汰）、且它在访问序上暂时不是最旧的那个（被更旧但 TTL 更长的条目挡在前面），它就既不会被 get() 惰性清理（没人再访问它），也不会被 set() 的前缀扫描清到（扫描在它之前就停了）。在低频写入、容量有余量的场景下，这类条目可以无限期滞留，直接违反 §2 的「有限时间内」承诺，且恰好复现了本计划要解决的第二个问题。§5 用「头部清理不完整」轻描淡写地承认了这一点，但没有回头去改 §2 的措辞，两处陈述互相矛盾。

**依据**：读取被审计划 §2（目标第二条）、§3.3（写时清理规则：'从 Map 头部...连续检查...遇到第一个未过期的即停'）、§5（'头部清理不完整'风险条目）。对照 src/cache.ts 当前 LRU 实现确认 Map 顺序即访问序，验证了头部扫描在遇到未过期条目时会提前终止的逻辑。

**建议**：要么把 §2 的措辞改成如实反映「尽力而为、依赖访问/写入模式，无严格上界」的实际保证；要么加强设计使承诺成立，例如 get() 命中未过期条目时顺带做一次轻量头部清理，而不是只在 set() 时做。两者选一，但不能让 §2 与 §5 继续互相矛盾。

### CLAUDE-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `§2 目标第三条 vs §3.4 / §5 size 条目` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | medium |

**问题**：§2 声称『现有调用方式...不改签名，调用方零改动』，但 §3.4 把 size 的语义从『精确的有效条目数』放宽为『可能偏大的上界』，§5 也承认『依赖 size 做容量监控的调用方可能读到偏大的值』。这是对既有公开属性行为契约的静默改变——调用点语法不变、类型不变，编译期不会报错，但行为变了。这与 §2『零改动』的表述在字面上一致、在精神上冲突：至少应明确『零改动』只保证调用语法层面，不保证既有依赖 size 精确性的调用方行为不变。

**依据**：读取计划 §2（目标第三条：'现有调用方式...调用方零改动'）与 §3.4（'size 返回 Map 当前条目数，可能包含尚未清理的过期条目'）、§5 最后一条风险。检索仓库（Grep 'LruCache|size|capacity'）未发现当前有实际调用方在用 .size，因此这里评估的是设计契约层面的风险而非已确认的现存故障，置信度按此打折。

**建议**：在 §2 里给『零改动』加一个限定：仅保证调用语法兼容，size 的精确性契约有变化；或者在 §3.4 里给出更强的保证（例如提供一个 O(1) 摊还的精确 liveSize，与宽松的 size 并存）供关心容量监控精度的调用方选用。

**依据**：读取计划 §3.1（'now 由构造时注入的时钟函数取得（缺省 Date.now）'）与 §5（时钟回拨条目）、§1 背景（'陈旧数据'问题描述）。

**建议**：至少补一句理由说明为什么可以接受（例如：生产环境墙钟回拨通常幅度很小/不常见），或者建议未来可选注入单调时钟源；不需要在本轮实现，但应该在计划里给出判断依据而不是只留一句『不处理』。
