**C 格的构建对（← CODEX-01 ≡ GLM-01）**：r1 选的 `9cee216` 不成立——`cancelled` 自 run.v2 落地（`5b83e4b`）就在枚举里，`9003a0e` 只加了写侧。用当前构建经桩写出的成功轮与取消轮两份 run.json，拿近 25 个历史版本的 run.v2 schema 逐个校验（ajv，零构建），**18 个版本全部接受**：run.v2 顶层允许未知字段，后加的顶层字段旧版一律忽略。真正的读侧落差在 `additionalProperties: false` 的子树里——`termination` 的第一分支（`by` 枚举 + `exit_code`）：`sync_exception` 由 `e49279a` 加入，其父 `a89a46f` 的枚举只有 `worker_exception`，读到 `by: sync_exception` 两个 `oneOf` 分支都不满足 ⇒ 不合契约 ⇒ `readRunMeta` 返回 null。当前构建能用现成手法写出它：同步路径 `review`、阶段目录置 0555（审查文档写不进、`_meta` 可写）⇒ 骨架收尾为 `failed` + `termination: { by: sync_exception }`（`gate-loop.test.ts` P5 就是这个构造）。所以 C 格：新构建（改前 `14c188b` / 改后工作树）写出这份 run.json 并提交，旧构建 `a89a46f` 读之判 `corrupt`，换回新构建即恢复——而且这一格的 `git status` 是**干净**的，正好覆盖 CODEX-04 指出的第四种形态。正式跑之前先用 ajv 对这一份样本做零构建预判；若 `a89a46f` 在本夹具上另有不兼容（配置、目录布局），在报告里写明并换取 `termination` 第一分支的另一个后加取值（`post_spawn_exception`，`c54091f` 加入）对应的父提交，仍不行就把 C 格记为「只做到 schema 层」并写明证到哪一步。

代码层面再核两件事：

- **本工具自己写不出读不出的 run.json**：所有写入都经 `writeRunMeta`（`meta.ts:373-388`，写前按 run.v2 校验、不合即抛）或事后收尾（`meta.ts:671-700`，先 `validateRunMeta` 再 `writeRunMeta`），落盘走 `writeAtomic`（`util/fsx.ts:26-31`，同目录临时文件再 rename）。所以 B 只可能来自工具之外的改动，或就是 C（写入方比读取方新）。
- **中途打断不会留下半截文件**：rename 之前被打断只留 `run-<id>.json.tmp-<pid>-<ts>`，`latestRunMeta` 的文件名正则 `^run-(.+)\.json$` 不认它；rename 之后就是完整的骨架。所以 D 不进本状态，只在设计文档里写明。

**三档的判别动作（← CODEX-04）**：r1 按 `git status` 的两种形态分 ② / ③，漏了「已提交、工作树干净、内容本身就读不出」——C 格的常态就是它，没有 Hook 的载体下坏内容也能被提交进去。r2 改为：先问「是不是 ①」（用不旧于写入方的版本再读一次）；再问「工作树里的这一份与已提交的版本是否不同」——不同（`git status` 显示 modified）才是 ②；其余（未跟踪，或已提交的版本本身就读不出）一律 ③。

结论：出口按成因只有三档——**① 升级重装、② 用户在终端 restore、③ 工具内没有出口**；重跑在任何一格都不是出口。第 7 处另有自己的前半段：**先恢复、恢复后直接重新 approve**；恢复不了才 abandon，且 abandon 之后能不能重跑取决于该阶段最新一份留痕可不可读（← AGY-01）。

## 2. 设计

### 2.1 共用出口文本（落点 `meta.ts`）

在 `meta.ts` 的 `latestRunMeta` 旁加两样导出：

- `UNREADABLE_RUN_META_EXIT_BODY: string`——固定段，不含任何参数；测试按子串逐字断言它；
- `unreadableRunMetaExit(files: readonly string[]): string`——先列出涉及的文件（每行一份，**绝对路径**，可原样复制给 `git restore`），再接固定段（← CODEX-02、CODEX-07）。路径用绝对路径：七处都拿得到 `ArchiveLayout`（其 `archiveRoot` 是绝对路径），而 `gate.ts` 那两处拿不到项目根，相对路径要么不一致、要么错。

放 `meta.ts` 的理由：七处的共同对象就是 `readRunMeta` 读不出的那份；四个消费点所在文件都已动态 `import('./meta.js')`，不新增依赖方向；`metaDir` 与 `runMetaFileName` 已在这一层，拼路径不需要别处的东西。

草案（定稿以代码为准，测试锚定的是常量本身而不是这里的字面；〈〉是本文的占位写法，代码里用 `<…>`）：

```text
  涉及的运行留痕（逐份判断成因，每份可能不同）：
    · 〈绝对路径〉
  重跑该阶段双审不是出口：review --start 在冻结送审包之前就按同一判定拒绝，新运行落不下来。按成因处置：
  ① 本工具版本落后于写下它的版本（它含本工具不认的 schema 或取值；常见于装好的副本比写入方旧，此时 git status 往往是干净的）：按 MANUAL §3.6「升级」更新并重装本工具后重试。
  ② 它已提交过，工作树里的这一份与提交的版本不同（git status 显示 modified）：由用户在终端执行 git restore 〈上面列出的路径〉 恢复后重试。这一步只能由用户在终端做——会话里的恢复命令会被 Hook 拦下，换写法绕过属于违规。
  ③ 其余情形——从未提交（git status 显示 untracked），或已提交的版本本身就读不出——且排除了①：工具内没有出口。没有可恢复的副本，也没有跳过这条判定的入口（BACKLOG EV-148 的剩余项）；本工具写入前会按契约校验，这一格只可能来自工具之外的改动。请停下，保留文件，交由用户人工判断。
  无论哪种成因，都不要删除或改写这些 run-*.json：删掉后这条判定会放行，但提交时的留痕核对会以「运行清单已丢失」拦下 git commit；改写同样会被拦。
```

① 的落点是 MANUAL §3.6「升级」（`MANUAL_user.md:218`），它按载体写了重新构建与安装两步（← CODEX-05）。② 不再写「或删掉」：第 1～5 处报出来的文件按定义都在磁盘上（← AGY-02）；「文件不在」只出现在第 6、7 处，由第 7 处自己的前半段处理。

## 7. 风险

- **共用文本过长**：Hook 的 deny 理由会进 Driver 上下文，加上文件列表约七行。取舍：按成因给出口本来就需要三档，每档一行；不再复述各处前半句已经说过的「为什么不按缺省」。
- **「删掉后判定会放行」这句是否在诱导删除**：是实情（B 格实测），写出来正是为了说明删除只会把拒绝挪到提交时。
