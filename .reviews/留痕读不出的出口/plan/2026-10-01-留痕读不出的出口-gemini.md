### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.2 表第 7 项（src/trivium/cli.ts:1642-1646 / src/trivium/gate.ts:1108-1123）` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：approve 分叉文案将 /dual-abandon 作为默认首选动作置于前半句，不仅与后半句恢复指引自相矛盾，还会误导用户在留痕可无损恢复时作废正常闸门

**依据**：查阅 src/trivium/cli.ts:1625-1653 与 src/trivium/gate.ts:1108-1123，approve 校验读的是 gate.run_id。若成因属于 ①（工具版本落后）或 ②（工作树已提交留痕被改坏），通过重装工具或终端 git restore 即可使留痕恢复并直接放行 approve，当前轮次完全有效。计划 §2.2 设计的前半句却要求用户「先 /dual-abandon … 解开这道闸门」，紧接着在共用文本中给出「重装工具后重试」「git restore 恢复后重试」。若用户遵循前半句先行 abandon，闸门已遭作废，后续恢复后也无法重试审批，被迫重新执行全量双审。

**建议**：重构 approveForkRecovery 的前半句流序：将恢复手段（排除①更新工具、②终端 git restore）作为优先推荐的自愈出口，明确告知恢复后可直接重新执行 approve；将 /dual-abandon 降级为只有在留痕无法恢复（③）或确认归档分叉时才使用的收尾出口。

**问题**：共用文本草案中将成因 ② 归结为「或删掉（git status 显示它被修改或删除）」，与后文「删掉后这条判定会放行」存在内部自相矛盾，且不符合 1～5 处入口判定机制

**依据**：查阅 src/trivium/meta.ts:488-501 与 src/trivium/driver-claim.ts:118-127，1～5 处判定是通过 fs.readdir 扫描 _meta/ 目录，unreadable 只收集现存但无法解析的文件；若留痕在工作树中已被删除，fs.readdir 根本扫不到，不会进入 unreadable，因而入口判定不会报错（正如草案末尾所言「删掉后这条判定会放行」）。因此在 1～5 处触发留痕读不出报错时，磁盘上必然存在该文件，git status 绝不可能显示为删除状态。草案 ② 声称「或删掉」既与底层判定机制不符，又与末尾说明直接冲突。

**建议**：修正共用出口文本成因 ② 的表述，精准定性为「在工作树里被修改或损坏（git status 显示 modified）」，移除「或删掉 / 或删除」等误导性词句；将文件删除的风险统一定位在提交拦截而非入口触发成因中。
