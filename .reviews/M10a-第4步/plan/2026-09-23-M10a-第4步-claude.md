### 2.2 判据怎么定

**上位设计的要求**：演进设计 §5 写的是「与 Driver 模型族不同；模型族**按生效模型判定，不按 Agent**」。

**审核者一侧做得到**：有生效模型（`model_effective`，回读不到退回请求值），按模型名判族，与今天一致。

**Driver 一侧做不到「按生效模型」**：编排器根本不知道 Driver 用的是什么模型（§1）。
所以 Driver 一侧**只能按身份近似**，这与「不按 Agent」的原则在 Driver 这一侧有张力。本稿不回避这一点：

- 近似方式取 r7 §5 的字面「当轮 Driver 的**厂商**」：假定 Driver 跑的是其厂商的自家模型族。
- 这个假定**在本仓自己的配置里就有反例**：codex 默认跑的是 qwen；Claude Code 可以接兼容端点跑别家模型；Antigravity 可以跑 `claude-*`。
- 根本解是采集 Driver 的生效模型（声明或回读），不在本步范围，登记为 **EV-107**（§2.6）。

**落法**：

```ts
// agents/registry.ts（新增，叶子模块，不引入依赖）
/**
 * 各厂商的**自家模型族**，按模型名判定（EV-62，M10a 第 4 步）。
 *
 * 用途只有一个：`isHeterogeneous` 用它近似「当轮 Driver 的模型族」。
 * 编排器不采集 Driver 的生效模型，只能假定 Driver 跑的是其厂商的自家模型——
 * 这是**启发式**，本仓自己就有反例（codex 默认跑 qwen、Antigravity 提供 claude-* slug），
 * 与演进设计 §5「模型族按生效模型判定、不按 Agent」在 Driver 一侧有张力。见 BACKLOG EV-107。
 *
 * 以 `Record<AgentVendor, …>` 声明：登记第五个厂商而不补这里，编译期就报错。
 */
export const VENDOR_MODEL_FAMILY: Readonly<Record<AgentVendor, RegExp>> = {
  anthropic: /claude/i,
  openai: /gpt/i,
  antigravity: /gemini/i,
  zcode: /glm/i,
};
```

```ts
// adapters/base.ts
/**
 * 审查模型是否与当轮 Driver 异构（FR-17 / AC-18；EV-62 起按当轮 Driver 判定）。
 *
 * 判据：模型名**不落在** Driver 厂商的自家模型族里，即判异构。两层都是启发式：
 * 模型族靠模型名判（`VENDOR_MODEL_FAMILY`），Driver 的模型族靠厂商近似。
 * 所以 `true` 的准确读法是「未检出同族」，不是「确认异构」。
 * 取不到模型名时判 `true`，与改动前一致。
 */
export function isHeterogeneous(model: string | null, driverVendor: AgentVendor): boolean {
  if (!model) return true;
  return !VENDOR_MODEL_FAMILY[driverVendor].test(model);
}
```

`base.ts` 新增一条对 `../agents/registry.js` 的 import。注册表是叶子模块，不成环；`types.ts` 本来就依赖注册表，`base.ts` 经它早已间接依赖。

**行为对照**（落笔时推演，实施时由 U1～U3 实测）：

| Driver 厂商 | 审核者模型 | 改前 | 改后 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| anthropic | `claude-*` | false | false | 不变 |
| anthropic | 其他 | true | true | 不变 |
| 非 anthropic | `claude-*` | **false** | **true** | EV-62 原文的那一格：主脑不是 claude，却判同源 |
| antigravity / zcode / openai | 本厂商自家族（`gemini-*` / `GLM-*` / `gpt-*`） | true | **false** | 新增检出：改前完全看不见 |
| 非 anthropic | 其他 | true | true | 不变 |

**误差方向**（初稿说反了的地方）：`false` 只触发告警与 `override_reason`，不拦闸门（§1）。
所以误报（错判同族）的代价是多一行告警；漏报（错判异构）的代价是把同源审查记成异构。
本方案两种误差都有，因为两层都是启发式（§2.6 列出已知形态）。

**考虑过、没采用的方案**：「Driver 为 anthropic 时照旧，其余厂商一律判异构」（初稿方案）。
它对非 anthropic 的 Driver 放弃检出，误差全落在漏报一侧；而它的依据「只有 claude 系命名可靠」也不成立，
因为 anthropic 一侧同样是按厂商近似，同样有反例。

### 2.3 调用点与文案

```ts
// review.ts
function overrideReasonFor(
  c: CriticId,
  model: string | null,
  modelOverrides: Partial<Record<CriticId, string>>,
  profileRequested: string | null,
  driver: AgentId,
): string | null {
  const desc = agentById(driver)!;
  if (isHeterogeneous(model, desc.vendor)) return null;
  return modelOverrides[c]
    ? `用户经 --model-${c} 显式指定了与当轮 Driver（${desc.display}）同族的模型`
    : `档位 ${profileRequested ?? '（缺省）'} 的默认模型与当轮 Driver（${desc.display}）同族`;
}
```

`agentById(driver)!` 的非空断言依赖的是**「入口已经拦过」这个前提**：`meta.driver` 来自 `opts.driver ?? DEFAULT_DRIVER`，
而 `opts.driver` 在入口经 `resolveDriver` 判定过已登记。本函数自己不做这个判定，注释照这个口径写。

两个写点：

```ts
heterogeneous: isHeterogeneous(r.model_effective ?? requests[c]!.model, agentById(meta.driver)!.vendor),
overrideReason: overrideReasonFor(     // 写点 B 为 override_reason
  c, r.model_effective ?? requests[c]!.model, opts.modelOverrides, r.profile_requested, meta.driver,
),
```

不提局部变量，理由是让 U7 能按字面钉住取值来源，与同文件 `checkAdjudication` 判据钉 `gateDriver` / `runMeta.driver` 同构。

`render.ts` 同源旗标改为：

```ts
flags.push(
  `**与主脑同源**：本侧生效模型落在当轮 Driver 厂商的自家模型族里` +
    `（按模型名判定，启发式）${input.overrideReason ? `：${input.overrideReason}` : ''}。`,
);
```

保留「与主脑同源」这几个字（`render.test.ts` 断言它）；Driver 是谁由 `overrideReason` 带出，`RenderInput` 不加字段。

**文案变化对留痕的影响**：`override_reason` 进 `run.json` 与审查文档 front-matter。本步之后新运行写新文案，历史运行保留旧文案（「落在 Claude 系」）。
这是自由文本，schema 不约束取值，读得回；但读台账的人会看到两种说法并存，测试报告里写明分界。
