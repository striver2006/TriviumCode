| 项 | 内容 |

| 类别 | security ｜ 层次 plan |

**问题**：Bash 侧分层判定（D-2）按 token resolve 判定是否在归档外，导致 RV-B1 负例中至少 4 类绕过形态被误判为「归档外」而静默放行，直接击穿 D-5 准入硬条件

**依据**：查阅 src/trivium/hooks.ts:267-275, 352-378, 554-577 与 test/unit/hooks.test.ts:303-328。RV-B1 负例中的 `git -c core.editor="rm .reviews/t/plan/a-gemini.md" commit --allow-empty`（315 行）、`GIT_EDITOR="rm .reviews/t/plan/a-glm.md" commit`（316 行）和 `sh -c "rm .reviews/t/plan/a-gemini.md" git commit`（313 行），经 tokenize 去引号后生成的 token 包含 core.editor=rm / GIT_EDITOR=rm / rm 前缀；其 path.basename 虽然匹配角色后缀，但 path.resolve(cwd, t) 把它当相对路径拼出 <projectRoot>/core.editor=rm .reviews/...，其相对归档根的路径必然含 ..，从而被 D-2 误判为「resolve 后在归档外 ⇒ 放行」；另外进程替换 `git commit -F <(rm .reviews/t/plan/a-gemini.md)`（318 行）经剥前导 < 后 token 为 (rm ...-gemini.md)，其 basename 尾随 ) 无法匹配 ROLE_SUFFIX_RE，且不含 $ 或反引号，会直接跳过检查被放行。这些形态在现状中全靠 354 行全文匹配拦下，D-2 收窄为 token 判定后将全部漏拦。

**建议**：放弃对未充分解析的 shell 命令行参数盲目做 path.resolve 归档外放行。对包含 =、空格、子命令或非纯路径字符的 token，不得直接作为相对路径 resolve，必须视为「无法确认定位」继续执行 fail-closed 拦截；或者仅对命令语法明确为单文件路径操作且能确定处于归档外的白名单命令形式放行，确保 RV-B1 全量负例坚决不绿。

### AGY-02 · 阻断（blocker）

| 项 | 内容 |

**问题**：D-3 符号链接防护仅对父目录做 realpath，无法防范目标文件本身为软链接的归档覆写攻击，且 macOS 下存在未规范化前缀失配风险

**依据**：查阅 .reviews/护栏判定范围收窄/plan/2026-09-13-护栏判定范围收窄-claude.md §4、src/trivium/hooks.ts:79-83 及 src/trivium/selftest.ts:74。计划 D-3 明确旨在防御「攻击者直接建 doc/x-glm.md 软链指向归档内真审查件」，却设计为「在比较前对父目录做 fs.realpath」。当 doc/x-glm.md 本身是指向 .reviews/t/plan/a-glm.md 的软链接时，其父目录 doc/ 是普通目录，realpath('doc') 仍为 <projectRoot>/doc，导致拼接后的路径完全游离于 archiveRoot 之外而被放行，Write/Edit 工具写入将沿软链直接覆盖真审查件。此外，macOS 上临时目录 /var 与 /private/var 存在系统级软链，若目标路径经 realpath 解析而 archiveRoot 未做对称 realpath，path.relative 会误判为外部路径而失效。

**建议**：路径解析判定必须先检查目标路径本身（若已存在软链接或普通文件，直接 realpath 目标自身；仅当目标文件不存在时才解析现有父目录）；同时 archiveRoot 必须同等进行 realpath 规范化后再执行 path.relative 前缀比对。

**问题**：更改 isForgedRoleFile 签名并限定在归档内，遗漏了 immutableChangeReason 调用点，将导致已提交审查文件的不可变审计锚静默失效

**依据**：查阅 .reviews/护栏判定范围收窄/plan/2026-09-13-护栏判定范围收窄-claude.md §2 与 src/trivium/hooks.ts:117-121, 713-716。在 hooks.ts:120 中，immutableChangeReason 传入 base = path.basename(relFromRoot) 调用 isForgedRoleFile(base) 来守卫 git 提交锚（防止已提交的审查工件被篡改）。计划 D-1 将其改写为需传入 (targetPath, projectRoot, archiveRoot) 且必须在归档内才返回 true。若直接传入裸文件名 base，isInsideArchiveResolved 会认为其在项目根而非归档内而返回 false，导致已提交审查工件被篡改时 immutableChangeReason 返回 null，破坏了 hook-pre-commit 的不可变工件防篡改保障。

**建议**：保持角色后缀识别与归档位置判定的关注点分离（例如分离出单纯检查是否具有审查员角色后缀的辅助函数），或在修改 isForgedRoleFile 时显式修订 immutableChangeReason，传入完整的 relFromRoot 与 archiveRoot，并补全对应单元测试。
