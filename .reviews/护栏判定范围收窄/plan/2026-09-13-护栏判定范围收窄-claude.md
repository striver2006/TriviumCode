### 1.1 为什么收窄不会给伪造审查件开口子

伪造审查件的攻击目标是**骗过闸门**，而闸门的读取面是封闭的：

- `gate.loadRoundReviews` 只从 `metaDir(layout, stage)` 读 `_meta/review-<critic>-<runId>.json`；
- `gate.checkAdjudication` 只从 `listStageArtifacts(layout, stage)` 取工件，`layout.archiveRoot` 即归档根；
- `archive.ts` 是 `.reviews/` 的唯一写出口，`O_CREAT|O_EXCL` 防覆盖。

写在 `doc/` 下的 `x-glm.md` **不进入任何一条读取路径**。这是方案成立的核心论据，审查时请直接核对上述三处代码。

**但这个论据有一个前提**：「写在 `doc/` 下」必须是真的写在那里。软链可以让路径字符串说谎——所以 D-3 是本方案的承重墙，不是附加项。

## 2. D-1：拆分关注点（按 AGY-03 重写）

r1 只打算给 `isForgedRoleFile` 加参数，**漏了 `immutableChangeReason:120` 这个调用点**——它传的是 `path.basename(relFromRoot)`，改签名后位置判定恒为「归档外」，`hook-pre-commit` 的不可变工件锚会静默失效。

按 AGY-03 的建议改为**关注点分离**：

```ts
/** 纯后缀检查：这个文件名是不是审核者角色工件的形态。不问位置 */
export function hasCriticRoleSuffix(fileName: string): boolean {
  return ROLE_SUFFIX_RE.test(path.basename(fileName));
}

/** 位置判定：解析软链与 macOS 前缀后，目标是否落在归档根内 */
export function isInsideArchiveResolved(
  targetPath: string, projectRoot: string, archiveRoot: string,
): boolean;   // 见 §4

/** 组合判定：伪造审查件 = 后缀像 且 落在归档内 */
export function isForgedRoleFile(
  targetPath: string, projectRoot: string, archiveRoot: string,
): boolean {
  return hasCriticRoleSuffix(targetPath) && isInsideArchiveResolved(targetPath, projectRoot, archiveRoot);
}
```

两个调用点各取所需：

| 调用点 | 改法 | 理由 |
| :--- | :--- | :--- |
| `hookPreWrite:155` | `isForgedRoleFile(target, ctx.projectRoot, ctx.archiveRoot)` | 拦的是「写一份伪造审查件」，位置是判据的一部分 |
| `immutableChangeReason:120` | **传 `relFromRoot` 而非 `base`**，用组合判定 | 它有完整相对路径可用；`inMeta` 的算法（`relFromRoot.split('/')`）本就依赖完整路径，此处传 basename 只是历史遗留 |

后缀集由**注册表**生成（审核者子集），不写死 `gemini|glm`——上一里程碑刚把字面表收敛进注册表，`registry-parity` 的 grep 对账会拦下新字面量。

## 3. D-2：Bash 侧改为白名单式放行（按 AGY-01 推倒重写）

### 3.1 r1 方案错在哪

r1 设计的是「能定位就按位置判，定位不出才兜底」。AGY-01 逐条验算了 RV-B1 负例，**至少 4 类会变绿**：

| 负例 | r1 方案下的结果 |
| :--- | :--- |
| `git -c core.editor="rm .reviews/t/plan/a-gemini.md" commit` | `tokenize` 去引号后 token 为 `core.editor=rm .reviews/...`，basename 匹配后缀，但 `path.resolve` 拼成 `<root>/core.editor=rm .reviews/...`，相对归档根含 `..` → **判归档外 → 放行** |
| `GIT_EDITOR="rm .reviews/t/plan/a-glm.md" git commit` | 同上 |
| `sh -c "rm .reviews/t/plan/a-gemini.md" git commit` | 同上 |
| `git commit -F <(rm .reviews/t/plan/a-gemini.md)` | 剥前导 `<` 后 token 尾随 `)`，basename 是 `a-gemini.md)` → **不匹配后缀正则 → 跳过 → 放行** |

根因：r1 把「`path.resolve` 得出一个归档外的路径」当成了「目标确实在归档外」的证据。但 `resolve` 对**任何**字符串都会返回一个路径，它不校验这串是不是合法路径。于是「解析成功」与「解析正确」被混为一谈——这正是 RV-B1 教训的同构形态：**用一个不可靠的信号去做放行决策**。

### 3.2 重写：默认拦，只在极严格条件下放行

判定方向倒过来。对命令里每个 token：

```
basename 不匹配角色后缀        → 本规则不管（交给既有 ②③）
basename 匹配角色后缀：
  ├─ token 是「干净纯路径」 且 cwd 已知 且 realpath 解析后确定在归档外  → 放行
  └─ 其余一切情形                                                      → 拦
```

「干净纯路径」的判据（**全部满足**才算）：

| 条件 | 挡掉的形态 |
| :--- | :--- |
| 不含空格 | `core.editor=rm .reviews/...` |
| 不含 `=` | `--output=x-glm.md`、`core.editor=…` |
| 不含 `(` `)` `<` `>` `&` `;` `\|` | 进程替换 `<(rm …)`、重定向残留 |
| 不含 `$` 反引号 `"` `'` | 变量展开、命令替换、引号残留 |
| 不以 `-` 开头（见 D-6 的例外处理） | 选项误判 |
| `cwd !== null` | `cd $VAR` 之后 |

任何一条不满足 ⇒ **按「无法确认位置」拦下**，与现状等价。

**关键性质**：放行是需要**举证**的，拦截是默认的。r1 反过来了。

### 3.3 重写后 RV-B1 负例的走向

| 负例 | 判定 | 依据 |
| :--- | :--- | :--- |
| `core.editor=rm .reviews/…-gemini.md` | 拦 | 含 `=` 与空格 |
| `GIT_EDITOR="rm …-glm.md" git commit` | 拦 | 含 `=`、空格、引号 |
| `sh -c "rm …-gemini.md" git commit` | 拦 | 含空格与引号 |
| `git commit -F <(rm …-gemini.md)` | 拦 | 含 `(` `)` `<` |
| `git commit -m x` + 换行 + `rm .reviews/…-gemini.md` | 拦 | 干净路径，但 realpath 后**在归档内** |
| `git commit -m x > .reviews/…-glm.md` | 拦 | 同上 |
| `git commit -m "$(rm …-gemini.md)"` | 拦 | 含 `$` 与引号 |
| `cd $VAR && rm x-glm.md` | 拦 | `cwd === null` |
| **`git mv doc/a-glm.md doc/b.md`** | **放行** | 干净路径、cwd 已知、归档外 ← 本次要修的 |

D-5 的准入条件据此逐条实测，不靠推演。

## 4. D-3：软链与路径规范化（按 AGY-02 推倒重写）

r1 写的是「对**父目录**做 realpath（文件本身可能尚不存在）」。AGY-02 指出这挡不住**目标自身是软链**的情形：`doc/x-glm.md` 若是指向 `.reviews/t/plan/a-glm.md` 的软链，其父目录 `doc/` 是普通目录，realpath 后仍是 `<root>/doc`，拼接结果游离在归档外 → 放行 → Write 沿软链**直接覆写真审查件**。

它还指出第二个坑：macOS 上 `/var` 是指向 `/private/var` 的系统软链。若目标路径做了 realpath 而 `archiveRoot` 没做，`path.relative` 会把同一个位置判成两处。**这个坑项目里已经踩过**——`adapters/base.ts` 的 `normalizeAbs` 专门抹平 `/private` 前缀就是为此。

### 4.1 重写后的解析顺序

```
isInsideArchiveResolved(target, projectRoot, archiveRoot):
  1. abs      = path.resolve(projectRoot, target)
  2. root     = realpathSync(archiveRoot)            ← 对称规范化，缺一不可
  3. resolved = 目标自身存在 ? realpathSync(abs)
                            : realpathSync(dirname(abs)) + basename(abs)
     · 目标存在（含软链）→ 解自身，软链被跟到真实位置
     · 目标不存在        → 解父目录（新建文件的正常情形）
     · 任一步 realpath 抛错（父目录也不存在等）→ **按在归档内处理**（fail-closed）
  4. return isInside(root, resolved)
```

三点说明：

- **软链跟随是刻意的**：Write 沿软链写入会落到真实目标，所以判定必须跟到真实目标。
- **fail-closed 的位置**：realpath 失败时判「在归档内」。代价是极端情况下多拦一次（有 Write/Edit 之外的出口），收益是不会因为解析失败而放行。
- **`archiveRoot` 的 realpath 只需算一次**，可在 `Ctx` 构造时缓存，避免每次 Hook 都做 I/O。

### 4.2 Bash 侧的同步问题

`bashTargetsProtected` 目前是**同步**函数。两个选项：

| 选项 | 取舍 |
| :--- | :--- |
| 用 `fs.realpathSync` | 改动面最小；Hook 是短命进程、无并发收益损失 |
| 把调用链改 async | `hookPreBash` 本就是 async，但 `bashTargetsProtected` 及其下游要一并改 |

**倾向前者**，请审查员评估。两侧必须调**同一个**判定函数（D-1 的 `isInsideArchiveResolved`），否则又会出现「改一漏一」。

## 6. D-6：`candidatePathTokens` 的 `-` 开头盲区（AGY-04）

`candidatePathTokens:271` 有 `if (t.length === 0 || t.startsWith('-')) continue;`。对通用路径提取这是合理的（跳过选项），但对角色后缀判定会留盲区：`cat > .reviews/t/plan/-gemini.md`、`--output=x-glm.md` 之类被直接丢弃。

**处置**：D-2 的角色后缀规则**不复用** `candidatePathTokens`，改为自己遍历 `tokenize(seg)` 的全部 token（含 `-` 开头的），只剥重定向前缀。理由：这条规则的取向比通用路径提取更保守，共用会把通用逻辑的宽松带进来。

`candidatePathTokens` 本身不动——它服务的 ②③ 规则有各自的取舍，不在本次范围。

## 8. D-7：文档纪律（AGY-05）

D-2 收窄后，commit message 里提及角色后缀的误拦会减少，但**不会消除**：`git commit -m "改了 x-glm.md"` 经 `tokenize` 仍会切出一个 basename 匹配的 token，且它含空格/引号 → 按 §3.2 仍被拦。

因此 `CLAUDE.md` 的既有纪律**不变，且要在实施说明里重申**：提交说明写进文件、用 `git commit -F <文件>`。不得因本次收窄而暗示「现在可以在 commit message 里随便提了」。
