## 1. 现状核对（3b2626c）

### 1.1 代码事实

- `initFixtureRepo` 六条裸 `await run('git', …)`：`init -q -b main`（30 s）、三条 `config`（**无超时**）、`add -A`（30 s）、`commit -q -m 'probe fixture baseline' --no-verify`（30 s），返回值一个都不看。
- `run`（`util/exec.ts:168`）：spawn 失败走 `child.on('error')`，stderr 追加 `[spawn error] <消息>` 后 `finish(null, null)`——`code`、`signal` 都是 null；超时 `timedOut: true`；被信号杀 `signal` 非空；都只 resolve、从不 reject。
- **`git commit` 无内容可提交时，那句「nothing to commit」在 stdout，不在 stderr**（本机实测，git 2.54.0）：取「输出头几行」要 stderr 为空时退回 stdout，否则这一种失败报出来是空原因。
- 探针夹具：`createFixture`（`probes/fixture.ts:71`）与 `createMemoryFixture`（:146）先 `makeTempDir`、写文件，再 `initFixtureRepo`、`workTreeHash`；中间任一步抛出，已建目录无人删（EV-199 残余 ①）。
- 五个调用点都在各自 try 之外：`probes/agy.ts:324`、`probes/codex.ts:832`、`probes/zcode.ts:1407`、`probes/claude.ts:1082`（主夹具）、`probes/claude.ts:1481`（记忆夹具，在主夹具的 try / finally **之后**、`probeClaude` 的最后一段）。
- 四个探针都在建夹具**之前**把 `probe.probed_at` 打戳（agy :290、codex :748、zcode :1320、claude :1077），且建夹具之前已经算出了版本、模型目录等静态结论——这些只在返回值里，doctor 拿到返回值后才赋给 `probe.cli[name]` 并 `checkpoint`。
- `runDoctor`（`doctor.ts:424`）：git 不可用只 `blockers.push('git 不可用或版本过低')`（:471），不早退；四段探针调用（:554、:573、:631、:662）都没有 try，抛出就穿过 `runDoctor` 到 `cli.ts:2025` 报「内部错误」。末尾「已登记但尚无探针实现」那一圈（:695 起）按「本次没探过、盘上也没有 `probed_at`」判。
- 自检 `buildFixture`（`selftest.ts:124`）在 try 里（:253），失败落「创建夹具仓库」步骤、删 `made.dir`（EV-204 / EV-207）；夹具里有 `src/payment.ts`、`README.md`、`.gitignore`、`.trivium/config.yaml` 与计划原稿，**不是空目录**。

### 1.2 甄别：谁在空目录里建仓、谁依赖「没有 HEAD」

任务目标「现状二」说 `hooks.test.ts` 的 `gitCtx` 对空目录建仓。**实测不成立**：`fakeCtx`（`hooks.test.ts:35`）先往项目根写了 `.trivium/config.yaml`，基线提交有内容、退 0。

甄别方法（不改源码）：scratchpad 里放一个记录型 git 包装（只在参数含基线提交信息的那一次记下 cwd 与真实退出码，其余原样透传 `/usr/bin/git`），`PATH` 前置它跑一遍全部单测（`node --test "dist/test/**/*.test.js"`，`--with-tests` 构建）。读数：

- 全量 2708 / 通过 2706 / 失败 0 / 跳过 2，退 0（与 EV-208 收尾时的读数一致，包装没有改变任何结果）；
- 基线提交共被调 **535 次：534 次退 0，1 次退 1**，那一次的 cwd 是 `trivium-hookcfg-*`。

口径边界：用例自己改写子进程 `PATH` 的（如钉一个不含包装目录的 `PATH`）记不到；打包 CLI、子进程跑的自检都继承 `PATH`，记得到。

结论：

- 唯一退非零的是 `hook-config.test.ts:193`「配置被 .gitignore 忽略时如实说…」的 `ignored=false` 一轮——`scratchDir` 新建的空目录、不写 `.gitignore` 就建仓，基线提交退 1、得到没有 HEAD 的仓库。这格只断言 `mergeAgentHooks` 的提示里有没有「不随仓库分发」（判据是 git 的忽略规则），与有没有 HEAD 无关。
- `hooks.test.ts` 的 5 次（`gitCtx` 4 个用例 + :1079 一次）全部退 0；`gitCtx` 之后的 `commitAll` 在有 HEAD 时照常追加提交，不依赖首个提交由它来建。
- 生产侧三处（自检、两个探针夹具）建仓前都写了文件，退 0。

### 1.3 实测：空目录与 `--allow-empty`

本机 git 2.54.0：空目录里 `init` + `add -A` + `commit -q -m x --no-verify` 退 1（stdout「nothing to commit」）；同样序列加 `--allow-empty` 退 0、`rev-parse HEAD` 有值、树为空树。有内容时加不加 `--allow-empty` 产出的提交树相同。

## 2. 改法

### 2.1 `initFixtureRepo` 逐步查结果（决策一）

六步写成一张表（步骤名 + 参数），逐条跑、逐条判，第一步失败即抛，后面不再跑：

| 序 | 步骤名 | 参数 |
| :--- | :--- | :--- |
| 1 | 初始化仓库 | `init -q -b main` |
| 2 | 配置提交者邮箱 | `config user.email probe@triviumcode.local` |
| 3 | 配置提交者名称 | `config user.name trivium-probe` |
| 4 | 关闭提交签名 | `config commit.gpgsign false` |
| 5 | 暂存全部文件 | `add -A` |
| 6 | 提交基线 | `commit -q -m 'probe fixture baseline' --no-verify --allow-empty` |

- **六步一律 30 s 超时**：原先三条 `config` 不设超时（`timeoutMs` 缺省 0 即不限），git 卡住会让夹具工厂永远等下去；统一成 30 s，与另三步一致。
- 判据：`r.code === 0` 才算这一步成功。其余四种形态各给一句原因：
  - 启动失败（`code`、`signal` 皆 null 且未超时）：「git 启动失败（〈spawn 的错误消息〉）」——消息从 stderr 里 `[spawn error]` 那一行取，取不到就写「原因不明」；
  - 超时：「30 秒内未结束，已终止」；
  - 被信号终止：「被信号 〈信号名〉 终止」；
  - 非零退出：「退出码 〈N〉」，后接输出头几行。
- **输出头几行**：stderr 去首尾空白后非空就取 stderr，否则取 stdout（§1.1 第三条）；按行切、丢空行、取前 3 行、每行截 200 字符，用「 / 」连接。启动失败那一支不附（stderr 里只有 spawn 错误本身，已在原因里）。
- 错误文案：`建仓第 〈序〉/6 步「〈步骤名〉」失败：〈原因〉[：〈头几行〉]`，抛普通 `Error`。导出步骤表与成文函数（`fixtureRepoStepError(step, r)`）供单测逐字比对，不在用例里复制文案。
- 不带路径：调用方知道在哪建的（探针夹具失败后目录已删，路径无意义；自检的失败步骤只需要原因）。

### 2.2 空目录：`--allow-empty`（决策二，取主选）

甄别（§1.2）没有一处调用方依赖「没有 HEAD」，备选「空目录不提交、保持无 HEAD」就没有服务对象；而要区分「空目录不提交」与「有内容却提交失败」，得在提交前多问一次 git 有没有暂存内容、或解析「nothing to commit」这句随语言环境变化的输出，都比加一个旗标脆。故取主选：基线提交恒加 `--allow-empty`。

影响面：有内容的调用方（生产三处与测试侧除 1 处外全部）提交树不变；`hook-config.test.ts` 那一格从「没有 HEAD」变成「有一个空树提交」，它的断言与 HEAD 无关（§1.2），不改。

### 2.3 探针夹具工厂（决策三）

- 新增 `export class ProbeFixtureError extends Error`（`probes/fixture.ts`），`name = 'ProbeFixtureError'`，带 `kind`（`'main' | 'memory'`）与 `residue: string | null`。
- 两个工厂改为：`makeTempDir` 到 `workTreeHash` 整段包进 try；catch 里——若目录已建（`makeTempDir` 的返回值已拿到）就 `removeFixtureRoot(kind, root)`（既有，经 `tryRemoveTempDir`、只删 mkdtemp 的返回值），然后抛 `ProbeFixtureError`：
  - `message` = `建探针夹具失败：〈原错误的 message〉`，删不掉时再接 `；〈fixtureResidueText(kind, root, code)〉`（既有的残留提示整句，上界措辞对「建到一半」同样成立：剩下的只会是探针写的夹具文件与本次探测的临时文件——这次没有探测，上界仍真）；
  - 原错误挂 `cause`。
- `makeTempDir` 自己失败（临时目录不可写）也包成 `ProbeFixtureError`，没有可删的目录、`residue` 为 null。
- 成功路径一个字节不变（返回的 `Fixture` 与 `cleanup` 照旧）。

### 2.4 doctor：接住、落 blocker、其余侧照常（决策四）

**落点选 doctor 层统一接住，不进各探针改返回值**（claude 记忆夹具例外，§2.5）。理由：

- 主夹具失败时，各探针还没跑任何模型调用；已算出的只有版本、模型目录等静态结论与提前打的 `probed_at`。把它们落盘会让该侧出现「`probed_at` 是新的、能力结论是旧的」的混合段，读的人无从分辨；整侧不落盘、保持上一次，最诚实。
- 四个探针不用各自加返回字段；doctor 一处 helper 处理四段。

做法：

- `runDoctor` 里加 `const fixtureFailed = new Set<string>()` 与 helper `guardFixture(name, fn)`：`await fn()`；抛的是 `ProbeFixtureError` 就 `fixtureFailed.add(name)`、`blockers.push(probeFixtureBlocker(name, e))`、返回 null；**别的异常原样重抛**（内部错误照旧是内部错误，不被它吞掉）。
- 四段改成 `const r = await guardFixture('agy', () => probeAgy(…)); if (r) { …原段落… }`。段落正文只多一层缩进（diff 请以忽略空白看）；`r` 为 null 时该侧既不赋 `probe.cli[name]`、也不 `checkpoint(name)`——落盘的该侧结论一个字节不动。
- 末尾「已登记但尚无探针实现」那一圈加一条 `if (fixtureFailed.has(name)) continue;`：否则一个从没探过的侧建夹具失败时，会在 blocker 之外再收到一条「尚无探针实现、这是确定答复而非失败」的 note，两句自相矛盾。
- 措辞（导出 `probeFixtureBlocker(cli, err)`，单测逐字比对）：
  > `〈显示名〉（〈cli〉）本轮没有探测成：〈err.message〉。该侧落盘的探针结论保持上一次不变，修好后重跑 trivium doctor --only 〈cli〉`

  显示名取注册表 `agentByCliName(cli)?.display`，取不到用 cli 名。`err.message` 已以「建探针夹具失败：」开头，原因与残留提示都在里面。
- **不分档**：不按 `criticEnabled` 降成 note（不同于 `codexSeverity` 的「没装」）。建不起夹具是本机环境问题（git 坏、临时目录不可写），与该侧启不启用无关，且四侧共用同一个夹具工厂。
- git 不可用时：环境段那条「git 不可用或版本过低」照旧，四段各再多一条本条 blocker（共 5 条）。不在 git 不可用时早退或跳过探针段——决策四定的是「其余侧照常探」，`--no-model-calls` 下各探针在建夹具之前就返回，本来就不受影响。

### 2.5 claude 记忆夹具：只作废那一格（决策四的细化）

记忆夹具在 `probeClaude` 的最后一段，建它之前主夹具那一段已经跑过若干次真实模型调用。若让它的 `ProbeFixtureError` 也穿到 doctor 层，这些已花配额的结论会被整侧丢弃，blocker 里「本轮没有探测成」也不实。所以：

- `probeClaude` 在 `createMemoryFixture()` 处接住 `ProbeFixtureError`（别的异常照旧上抛）：notes 推一句、`project_memory_blocked` 保持上一次（`probe` 是由 `existing` 起的，这一格不赋值即保持），然后照常 `return`，返回值新增 `memoryFixtureFailure: string | null`（其余各条 return 都给 null）。
- doctor 的 claude 段：`r.memoryFixtureFailure` 非空时 push 一条 blocker（导出 `memoryFixtureBlocker(msg)`）：
  > `Claude Code（claude）项目记忆一格本轮没有探测成：〈msg〉。其余各格已刷新，project_memory_blocked 保持上一次不变，修好后重跑 trivium doctor --only claude`
- 该侧照常 `checkpoint('claude')`。

### 2.6 自检（决策五）

不改代码。`initFixtureRepo` 一抛，`runSelftest` 既有的 catch（`selftest.ts:255`）就把它落成 `{ name: '创建夹具仓库', ok: false, detail: <新文案> }`、删 `made.dir`；输出其余部分不变。用例在 §3 S 组用打包 CLI 加假 git 端到端核。

## 3. 用例

新文件 `test/unit/fixture-repo-init.test.ts`（U、P、D 三组）；S 组加在 `test/integration/selftest.test.ts`（它已有打包 CLI 的跑法与私有 `TMPDIR` 工具）。临时目录一律走 `scratchDir`（EV-208 守卫）；每格钉 `TMPDIR` 到私有根，残留断言只数私有根。

**假 git**：每格在私有根 `bin/` 下写一个 `git`（`#!<process.execPath>` 的 Node 脚本）。按环境变量决定行为：`FAKE_GIT_FAIL=<步骤键>`（`init` / `config` / `add` / `commit`；`config` 再按第二个参数区分三条）命中时往 stderr 写三行以上的固定文字、按 `FAKE_GIT_CODE` 退出（缺省 1）；`FAKE_GIT_NTH=<n>` 只让第 n 次命中失败（计数文件放私有根）；`FAKE_GIT_LOCK=1` 失败前在 cwd 摆只读锁 `locked/`（给 P 组造「删不掉」）；`FAKE_GIT_HANG=1` 命中时睡 60 s（超时格）。其余调用 `execFileSync` 透传到测试启动时从 `PATH` 解析出的真实 git 绝对路径。工作树哈希的 `add -A -- .` 带 `GIT_INDEX_FILE`，假 git 据此区分「建仓的暂存」与「工作树哈希的暂存」。

**D：doctor 层（四侧假入口，照 EV-199 的 E 组装置）**

假入口沿用 `probe-fixture-cleanup.test.ts` 的四份替身（agy、codex、claude 的 Node 脚本，zcode 经 `zcodeProbe` 注入口）；codex 替身按坑清单吐最小 header、钉 `CODEX_HOME` 放 profile 配置。`config` 用 `defaultConfig()` 填 agy / zcode 的入口路径，codex / claude 放进 `PATH` 的 `bin/`。每格 `triviumDir` 是私有根下新目录，`config.probe.cli.<侧>` 预置一份可辨认的旧结论（如 `version: 'old-<侧>'`）。
