## 0. 范围与不做

**做**：把「只读失守 ⇒ 闸门必败」改成「只读失守且跑后复算确证改动 ⇒ 闸门失败；其余失守降为告警放行」。判据收成 `gate.ts` 里一个导出函数，`checkAdjudication` 与两处 Hook 共用；同步改准运行时告警、任务书第 7 节、处置句与各处注释；桩加一个真落盘的失守形态；翻转既有断言并新增三格；文档按任务目标列的落点同步。

**不做**（决策五）：

- 不动 guard 的失守判定（`judgeSide` 的 `write_events.length > 0`、`breached_files`、各家写事件口径）；
- 不动 run.v2 契约（不加字段，因此不触发 BACKLOG EV-75 ② 的逐侧留痕）；
- 不动 `review` 的退出码与 `meta.status`、待裁决拒绝重跑（`review.ts` 的比较-交换）、`on_drift` / `on_drift_related` 两项策略；
- 不动 `report.ts` 的 `guardFlags`（只推「只读失守」四个字，`report.ts:288`）与 `summarizeRun`（`meta.ts:1063` 只出「⚠️ 只读失守」）——两处已核**没有拦截措辞**，决策六的「若有则同步」不触发。是否给它们加「未确证」区分不在本题（见 §8 D1 待议）。

## 1. 现状（`80ff60b2`，已核）

### 1.1 失守判据与闸门

- 失守 = 轨迹里出现写事件：`guard.ts:444` `const readonlyBreach = result.write_events.length > 0`，`judgeRun`（:809）折成整跑布尔，`review.ts` 收尾写进 `meta.guard.readonly_breach` 与 `breached_files`。与工作树是否真被改无关。
- `gate.ts:394-424`：`checkAdjudication` 对 `input.readonlyBreach?.hit` **无条件**推 failure `readonly_breach`，文案 = 首句 + `READONLY_BREACH_TRIAGE`（:33-36）+ 调用记录（`breachRecordsText`，:39-41）。
- `loadRoundReviews`（:1340-1343）只带出 `{ hit, files }`，不带 `snapshot.drift`。
- 三个出口都经 `checkAdjudication`：`gate --check`（`cli.ts:1412`）、`--await-approval` 与 `approve`（都经 `verifyRoundForApproval`，`gate.ts:1525`，调用点 `cli.ts:1305` / :1700）。failure 即退 2。
- 待裁决时 `review --start` 拒绝重跑，唯一出口是 abandon（EV-98 文案部分 r2 §7 已核）。

### 1.2 跑后复算（`snapshot.drift`）的取值

`review.ts:1797-1806`：`changed = verdict.drift.kind !== 'none'`；`files = verdict.fingerprintChangedFiles`；`policy` 按种类取 `on_drift` / `on_drift_related`；只在 `kind === 'unknown'`（比不了，EV-139）时写 `unknown_reason`。`DriftVerdict`（`freeze.ts:495-500`）五种：

| 种类 | changed | unknown_reason | files | 缺省配置下运行结局 |
|---|---|---|---|---|
| none | false | 无 | [] | success → 待裁决 |
| subject_drift | true | 无 | []（`fingerprintChangedFiles` 只收 related/unrelated） | failed（`review.ts:2047`），不进待裁决 |
| related | true | 无 | 改动文件，或 []（无法归因时挪去 `guard.unattributed_drift_files`） | `on_drift_related: fail`（缺省）⇒ failed |
| unrelated | true | 无 | 同上 | `on_drift: warn`（缺省）⇒ success → 待裁决 |
| unknown | true | 有 | [] | 按 `on_drift_related`（缺省 fail）⇒ failed |

`judgeDrift`（`freeze.ts:598-647`）是 git 树比对：`workTreeHash` 含已跟踪与未被忽略的未跟踪文件，剔除 scratch 白名单、归档根与 `.trivium/`。看不见被 `.gitignore` 忽略的文件、改了又改回、项目外写入；MCP 执行型调用的写入若落在上述盲区同样看不见。

**由此得出两件可达性事实**（影响测试设计，§6）：缺省配置下，进得了待裁决的失守轮只有 `none`（放行格）与 `unrelated`（拦截格）两种；「比不了 + 写事件」只在 `on_drift_related: warn` 时进待裁决——这是第三格要在夹具里改配置的原因。`subject_drift` 恒判运行失败、不进待裁决，判据对它给「确证」只是保持一致，不是可达格。

### 1.3 两处 Hook

`hooks.ts:1296-1302` `roundBreach` 按闸门项 `run_id` 直读 run.json，`guard.readonly_breach === true` 即归入失守组；`splitByBreach`（:1305-1318）据此拆组。失守组的文案说「这道闸门靠补裁决件解不开」（`BREACH_UNFIXABLE`，:1324-1325），逐项列调用记录、快照漂移（`driftText`，:1328-1340，三档：未检出 / 比对未完成 / 检出 N 个）、作废出口，末尾是 `READONLY_BREACH_TRIAGE` 与「都须先作废这一轮」（:1347-1374）。`gate.ts:20-31` 与 `hooks.ts:1320-1323` 两段注释互指「gate --check 对只读失守一律判失败」。

## 2. 判据（单点，决策一、四）

### 2.1 导出判定函数（`gate.ts`，放在 `READONLY_BREACH_TRIAGE` 旁）

```ts
/** 只读失守成立之后，按跑后复算分三档（用户决策 2026-10-06，原始需求 20261005 第 1 条） */
export type ReadonlyBreachVerdict = 'confirmed' | 'unconfirmed_unchanged' | 'unconfirmed_unknown';

export function judgeReadonlyBreach(
  drift: Pick<SnapshotMeta['drift'], 'changed' | 'unknown_reason'>,
): ReadonlyBreachVerdict {
  if (drift.unknown_reason !== undefined) return 'unconfirmed_unknown';
  return drift.changed ? 'confirmed' : 'unconfirmed_unchanged';
}
```

- 只在失守成立时调用；「失守是否成立」仍只看 `guard.readonly_breach`（决策五）。
- 先判 `unknown_reason`：写侧只在 `changed: true` 时写它（§1.2），两种次序拦截集相同；先判它是为了「`changed: false` 却带 `unknown_reason`」（手改留痕才可达）时按「比不了」说，不说成「复算无变化」——说法更弱、方向保守。
- 不给 `drift` 缺席设分支（决策一）：run.v2 契约必填，`readRunMeta` 校验不过即 null，null 时 `hit` 本就为 false。

### 2.2 接线：类型收紧让漏传编译不过

`loadRoundReviews` 的返回与 `checkAdjudication` 的入参 `readonlyBreach` 改为判别联合：

```ts
type ReadonlyBreachInput =
  | { hit: false; files: string[] }
  | { hit: true; files: string[]; drift: Pick<SnapshotMeta['drift'], 'changed' | 'unknown_reason' | 'files'> };
```

`loadRoundReviews`（:1340）在 `runMeta.guard.readonly_breach === true` 时把 `runMeta.snapshot.drift` 一并带出。`hit: true` 而不带 `drift` 的字面量（单测里的 `{ hit: true, files }`）编译期即红，逼着每个调用点表态——与 `planFinal` / `reviewDocs`「必填、漏传静默不校验」那个教训同向。入参本身仍是可选（缺省不拦，既有 ③ 格语义不变）。

### 2.3 `checkAdjudication` 分流（:394-424）

```
if (input.readonlyBreach?.hit) {
  const v = judgeReadonlyBreach(input.readonlyBreach.drift);
  if (v === 'confirmed') failures.push({ code: 'readonly_breach', message: … });
  else warnings.push({ code: 'readonly_breach_unconfirmed', message: … });
}
```

`GateWarning['code']` 加 `'readonly_breach_unconfirmed'`。位置不动（仍在降级显形之前），所以缺件早退的次序事实不变：裁决件没写时 `gate --check` 仍先报 `missing_disposition`，看不到这一条（与现状相同）。

### 2.4 文案（决策三）

共用常量（`gate.ts`）：

- `BREACH_BLIND_SPOTS` = 「被 .gitignore 忽略的文件、归档根与 .trivium/、改了又改回、写到项目外、MCP 执行型调用的任意写」——决策二的清单，告警与注释同源。

**failure `readonly_breach`（确证）**：

> 本轮轨迹记录到审查员调用了白名单外的工具（写事件记录），且跑后复算确证审查期间工作树有改动，裁决不得进入审批。复算检出：〈改动摘要〉。〈`READONLY_BREACH_TRIAGE`〉调用记录（非文件路径）：〈`breachRecordsText`〉

- 〈改动摘要〉由新导出的 `confirmedDriftText(drift)` 给：`files` 非空写「N 个文件改动：前 8 个…」；为空写「有改动，文件清单未记入 snapshot.drift.files（本轮有侧无法归因时清单在 guard.unattributed_drift_files）」。Hook 的 `driftText` 改调它（§3），两处同源。
- `READONLY_BREACH_TRIAGE` 改为：「处置：用 git status / git diff 核对这些改动是否出自审查员并清理。复算只能确证『有改动』、归不了因——审查期间别处的手改同样会落进这一格，拦截照旧。要重跑须先作废这一轮。」去掉「drift 为 false 不足以判误报」那半句：确证格里 drift 恒非 false，那句话在这里已无对象；它的实质（盲区）挪进放行告警。

**warning `readonly_breach_unconfirmed`（放行）**，两种说法：

- 复算无变化：「本轮轨迹记录到审查员调用了白名单外的工具（写事件记录），但跑后复算未检出工作树改动（snapshot.drift.changed 为 false）。按『只有确证改动才拦』放行，本轮结论照常进入审批。未检出不等于没写：〈`BREACH_BLIND_SPOTS`〉，复算都看不见，由审批人自行斟酌。调用记录（非文件路径）：〈…〉」
- 比不了：「……但跑后复算比不了（〈`describeDriftUnknown`〉），未能确证改动。按『只有确证改动才拦』放行，本轮结论照常进入审批。比不了即不知道改没改，〈`BREACH_BLIND_SPOTS`〉之外，连一般的项目文件改动也没有核过，由审批人自行斟酌。调用记录（非文件路径）：〈…〉」

告警在 `--await-approval` 停点上已有渲染通道（`cli.ts:1330` 的 `preWarnings` 逐条「⚠️ [code] message」），审批人能在表态那一格看到；`approve` 是否也出告警按现状不动（§8 R3）。

### 2.5 注释改写（决策二、四）

## 3. 两处 Hook（决策四）

- `roundBreach`（`hooks.ts:1296`）：`meta?.guard.readonly_breach === true && judgeReadonlyBreach(meta.snapshot.drift) === 'confirmed'` 才返回失守项；判定函数经已有的 `await import('./gate.js')` 取（与 `breachLines` 同法，不新增静态依赖）。未确证的失守轮因此落进 `normal` 组，**按普通轮逐字出原文案**（未裁决就说未裁决——此时补裁决件确实解得开）。
- `BREACH_UNFIXABLE`：「这道闸门靠补裁决件解不开——跑后复算确证审查期间工作树有改动，gate --check 对这类只读失守判失败，裁决件写得再齐也不放行」。互指注释（:1320-1323）同改。
- `driftText`：确证格里 `changed` 恒 true、无 `unknown_reason`，原「未检出」「比对未完成」两档成死分支，删去，改调 `confirmedDriftText`。
- `breachLines` 末行（:1366-1372）：「不论确有改动要清理后重跑，还是核实为误报想重跑」改为「要重跑须先作废这一轮：闸门停在待裁决时 review --start 拒绝重跑，而这一轮的 gate --check 不会通过」。
- `hooks.ts:1270-1278` 段首注释补一句：失守项只收确证格。其余（首句、调用记录行、作废命令、`READONLY_BREACH_TRIAGE` 引用）不动。
