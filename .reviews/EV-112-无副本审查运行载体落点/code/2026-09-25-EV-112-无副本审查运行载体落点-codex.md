**问题**：无副本支的反向核只核 rollout：`leaked_to_home = exists(<realHome>/.zcode/cli/rollout/model-io-<sid>.jsonl)`，日志这一半既不核也不由合取蕴含。当厂商漂移只打掉日志键、仍采纳存储根（补丁自己给出的理由——「日志工厂直读 / 存储根经配置层，两条互不相干的代码路径可各自漂移」——正说明这种半采纳是可达的）时，本轮留痕是 `{log:false, rollout:true, leaked_to_home:false}`。而 0.16.9 里日志目录的唯一兜底是 `join(homedir(),".zcode","cli","log")`，无副本支的 HOME 就是真实 HOME ⇒ 含送审包全文的日志落在真实 `~/.zcode/cli/log` 并留存，但：①归档里「有没有写进真实 HOME」那一格答 false；②guard 的泄漏句不响（它只判 `leaked_to_home === true`），只出「运行目录里缺本次会话的日志……CLI 产物可能留在别处」；③RUNBOOK 第 268 行排查第③步只让人去 `~/.zcode/cli/rollout/` 找 `model-io-<sessionId>.jsonl`。审计与排查两边都会得出「没泄漏」。这正是 EV-112 登记的那类载体（日志），不是 rollout。

**依据**：读 src/trivium/adapters/zcode.ts：checkZcodeCarriers 末尾 `if (realHome === null) return { log, rollout };` 之后仅一行 rollout 存在性，日志只参与 `log` 布尔；调用点 `home.homeDir === null ? os.homedir() : null`。读 src/trivium/guard.ts:883-895：落点缺失句判 `(!log || !rollout)`，泄漏句只判 `leaked_to_home === true`。读 doc/06_deployment/RUNBOOK_pipeline_ops.md:268（新增行）：泄漏句只对应 rollout，第③步只写 rollout 路径。读 test/unit/zcode-carriers.test.ts:33-58 的假入口：`useLog = mode==='follow'||mode==='half'`、`useStore = mode==='follow'`，四个 mode 里没有「只认存储键、不认日志键」这一格，故镜像形态无用例；U8 half 格断言的是 `{log:true, rollout:false, leaked_to_home:true}`，方向相反。日志兜底路径核对自包内 `function N6s(){return join(homedir(),".zcode","cli","log")}`（/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs，0.16.9，2026-09-22 安装）。设计 6.7.1 行与 skills/dual-critic/schema/run.v2.json 的该属性描述也确实只写「rollout 出现在真实 ~/.zcode/cli/rollout 下」，字面没错，但字段名 `leaked_to_home` 会被下游读成「真实 HOME 没有本次改动」。

**建议**：让反向核覆盖日志这一半。判定不需要读真实 HOME 的内容：无副本支 + `log === false` 已足以断定日志落在真实 HOME 的缺省位置（0.16.9 只有这一个兜底），可直接并入泄漏结论，或另出一格（如 `log_fell_back_to_home`）并让 guard 补一句点名 `~/.zcode/cli/log`；同步把 RUNBOOK 第 268 行排查第③步写成「rollout 与日志各按对应路径自查」、并回补 6.7.1 与 schema 描述的措辞。另补一条「只认存储键」的漂移用例锁住这一格。触发条件是被厂商漂移打到，概率不高，但一旦发生这正是本主题要防的事，故按 major 报；若认为该残留形态可接受，请显式降级并把上述三处措辞一并收窄。

**问题**：「一律」比机制与自检覆盖面宽。三键只管到日志目录、存储根与会话库；包内至少还有一条状态路径解析不经它们（workspace-hook trust store：`yas` 按 `homedir()` 或用户配置文件自己的 `storage.dir` 推 `<…>/security/workspace-hook-trust-v1.json`），rollout 也另有一条 `homedir()` 兜底解析（`e4s`，在 modelIoDir 未传入时生效，写 `<homedir()>/.zcode/cli/{rollout|debug}`）。自检只观测 log 与 rollout 两项，而 run.json 是运行目录过期后唯一能回答「这次把什么留在了真实 HOME」的载体，读者容易把「两项为真」当成「CLI 产物一律落在运行目录」。这些残留载体不含送审内容，故只是宣称与文档准确性问题。

**依据**：读 src/trivium/adapters/zcode.ts:346-360、871-880 与 checkZcodeCarriers 仅核两项；读 doc/06_deployment/RUNBOOK_pipeline_ops.md:267 的「审查运行的 CLI 产物一律落在运行目录（EV-112 起）」；读 src/trivium/probes/zcode.ts:1370-1377 的 note「审查运行的 CLI 产物不再留在真实 ~/.zcode」。包内核对：`function yas(e={}){… a?kas(a,t):join(t,".zcode") … join(l,pas,fas)}`，同模块 `pas="security", fas="workspace-hook-trust-v1.json"`；`function e4s(e){return join(homedir(),".zcode","cli",e?"debug":"rollout")}` 与 `JWr(…, t ?? e4s(n ?? false), …)` 的兜底关系（/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs）。我未验证这两条链在 `--prompt` 形态下是否真被走到（见 not_covered），故 confidence 记 low——即便它们不被走到，把宣称收窄到「三键覆盖的载体」也是零成本的准确化。

**建议**：把「一律」改成按载体列举（日志、rollout、存储根下的 artifacts / sessions / memories / plugins / 会话库），并在设计残余段与 RUNBOOK 注明「落点自检只覆盖 log 与 rollout 两类」；doctor 的那句 note 同改。不必为此扩自检范围。
