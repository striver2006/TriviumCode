## 2. 问题重述

无副本的审查运行（C1 两种成因）用真实 HOME 跑完整一轮，P1～P7（含 P5b）全部写进真实 `~/.zcode`，不进清扫面、跑后持久留存；
跑后回读（C4）也读真实目录：日志与桌面端、其他 CLI 会话共用，只能靠 `sessionId` 过滤。
EV-110 之前，宿主还能用 `ZCODE_LOG_DIR` 把日志挪去临时卷；EV-110 把它一律清掉以后，连这条退路也没了（CODEX-04 原话）。

**r2**：第 1 轮另核出，**副本支**的落点也能被带偏，途径有三：宿主预置 beta 开关（P9 ②）、宿主预置运行档位 `development`（P9 ①，rollout 改进 `cli/debug`）、
副本源里写了 `storage.*`（P3，副本源就是 CLI 的用户层配置）。三者都让回读落空、让 `redactUnder` 失效。

### 4.1 覆盖面（决策 D1：(b) 设三键）

- (a) **只设 `ZCODE_LOG_DIR`**（CODEX-04 原建议）。**不取**：只收口 P1，rollout 与日志同样逐字含送审包；
- **(b) 设三键（采用，第 1 轮三侧认可）**：`ZCODE_LOG_DIR`（P1）、`ZCODE_STORAGE_DIR`（P2、P5、P5b、P6、P7）、`ZCODE_SESSION_DB_PATH`（P4），值取自同一个根：

  | 键 | 值（`root = zcodeHomeUnder(sideDir)`） | 与「`HOME=<root>` 时的缺省值」 |

  | `ZCODE_STORAGE_DIR` | `<root>/.zcode` | 相同（`"~/.zcode"`） |
  | `ZCODE_SESSION_DB_PATH` | `<root>/.zcode/cli/db/db.sqlite` | 相同（`"~/.zcode/cli/db/db.sqlite"`） |
  | `ZCODE_LOG_DIR` | `<root>/.zcode/cli/log` | 相同（`N6s()`） |

  三个值写成一个纯函数 `zcodeStorageRedirectEnv(root)`，用例锁住它与副本布局逐字相同。E0 已用同一组值实测（§1.5）；
- (c) 无副本也建一个 HOME。**不取**：改了 HOME，模型选择要么走 legacy 导入（撞 EV-82 的运行期回落），要么要把凭据根一起搬，都得花配额实测；副本源缺失那一格也无从拷；
- (d) 无副本一支拒跑、glm 判不可用。**不取**：可用性回退。

(b) 的代价（**r2** 改写，GLM-03）：无副本一支的**存储根每次都是空的**，用户装在真实 `~/.zcode` 下的 plugins、agent profiles、skills、MCP 配置对审查员不可见（P7），
每次运行在运行目录里重新铺一遍 builtin plugins（E0 实测 385 个文件，实验组约 2.3 秒跑完）。
**主 agent 的生效模型不受影响**（§1.2 第三条）；变化的是无副本一支**子代理**的模型选择：原先可能吃到用户 profiles 的覆盖，改后回落内置缺省。
副本路径 133 次运行一直就是这个形态，不是新的行为类别，但它是无副本一支的行为变化，写进设计文档与 RUNBOOK。

### 4.2 哪一支设（决策 D2，**r2 改选 (a)**，CODEX-04、CODEX-01）

- **(a) 审查运行两支都设同一组值（采用）**：副本支 `HOME=<root>`，三键取值与该支缺省逐字相同，布局不变；有了这三个 Env 层值：
  ① `RMi` 见 `ZCODE_STORAGE_DIR` 非空即早退，宿主 beta 开关不再改写存储根（P9 ②）；
  ② 副本源里的 `storage.*` 被 Env 层（40）压过（P3），不再能把副本支的 rollout 带到用户指定的位置。
- (b) 只在无副本一支设（r1 推荐，**弃**）：理由是「副本支是 EV-82 刚验收过的路径，不改它的子进程环境」。第 1 轮 gemini、glm 认可这条理由；
  codex 指出三键在副本支取值与缺省相同，「不改」只买到「不新增取值来源」，代价是上面 ①② 两个洞留在 133 次运行的那一支上。改选 (a)。
- **(a) 的验证**：E1 在同一个 HOME 下对副本支做「设 / 不设三键」对照，断言两者落盘布局逐字相同（§6.3）；U5 锁副本支子进程拿到的三个值。

接线：`ZcodeInvokeOptions` 加 `storageRedirectRoot?: string | null`（显式参数，不复用 `homeDir` 当魔法值）；`zcodeAdapter.run` 两支都传 `zcodeHomeUnder(sideDir)`。其余调用方（L1～L7）一律不传。
**入参层级约定**（**r2**，AGY-02）：`storageRedirectRoot` 与 `zcodeStorageRedirectEnv(root)` 的入参是 **与 HOME 同层的根**（`<sideDir>/home`），不是 `.zcode`；函数内部才拼 `.zcode`。
JSDoc 写明这一点；入参以 `.zcode` 结尾时函数抛错，防止 `.zcode/.zcode` 嵌套（U1）。

### 4.3 清除面：四键扩为十一键（决策 D3，**r2** 扩充，CODEX-01、CODEX-02）

全部拉起路径（`zcodeProviderEnv` 与 `probeZcodeEntry`）一律清，宿主值进不了子进程：

| 组 | 键 | 来由 |
| :-- | :-- | :-- |
| 目录 / 路径键（`ZCODE_DIR_ENV_KEYS`，四键 → 七键） | `ZCODE_DATA_BASE_DIR`、`ZCODE_HOME`、`ZCODE_STORAGE_DIR`、`ZCODE_LOG_DIR` | 原有（r3 CODEX-02、EV-110） |
| | `ZCODE_SESSION_DB_PATH`、`ZCODE_SESSION_DB` | P4：宿主预置任一个，会话库落到清扫面外；两个别名映射同一字段、后出现的赢（`aun` 按 `Object.entries` 顺序），键序由 C8 决定、编排器控制不了，清掉别名后设的那个才唯一 |
| | `ZCODE_MAILBOX_ROOT` | P10：宿主预置时 mailbox 落到清扫面外 |
| 落点开关键（新常量 `ZCODE_LANDING_SWITCH_ENV_KEYS`） | `ZCODE_RUNTIME_ENV` | P9 ①：`development` 把 rollout 改进 `cli/debug`，两支都受影响、(a) 挡不住 |
| | `ZCODE_BETA`、`ZCODE_ENV` | P9 ②：审查运行两支已由 (a) 挡住；探针臂（L2～L4）不设存储根，仍靠清 |

方向都是 fail-safe：清掉只会把落点拉回各自 HOME（或关掉可选功能）。清掉 `ZCODE_RUNTIME_ENV` 后 CLI 按入口路径推断，`.cjs` 入口得 `production`。
两个常量分开，是因为「目录 / 路径键」只能清或设成路径，「开关键」只能清；`ZCODE_DIR_ENV_KEYS` 沿用原名，文档块改成「目录与路径键」并逐键写来由。

### 4.4 「先清后设」与 EV-110 的口径

EV-110 的「一律清」防的是**继承宿主值**；本题的「设」是**编排器自己指定落点**。二者不冲突，但有先后：

1. `invokeZcode` 先展开 `zcodeProviderEnv`：十一个键全部 `undefined`（清，所有走它的路径都一样）；
2. **然后**，仅当 `storageRedirectRoot` 给了，才用 `zcodeStorageRedirectEnv(root)` 覆盖其中三个（设）；
3. `HOME` 仍只在 `homeDir` 为真时设。

顺序写死在 `invokeZcode` 一处，用例锁住：宿主预置诱饵值时，审查运行子进程看到的是编排器的值，探针与探活子进程看到的是 `undefined`（变异 M2 专咬反序）。
EV-110 的判据「子进程拿不到宿主值」在所有路径都成立；「子进程的落点只由 HOME 决定」改成「只由 HOME 或编排器显式指定的落点决定」，
`zcodeProviderEnv` 与 `ZCODE_DIR_ENV_KEYS` 的文档块跟着改。

### 4.6 落点自检（**r2** 新增，CODEX-03）

落点键被 CLI 采纳是从压缩产物读出来的厂商事实，ZCode 随桌面端自动更新。键被改名或映射变了，无副本一支会悄悄回到真实 HOME，
唯一症状是 `model_effective` 变 null，而那会被读成「未回读到」。所以加一条零配额自检：

- `run()` 在 CLI 成功返回 envelope 且有 `sessionId` 时核两项：`cliDir/log` 下日志里有本次 `sessionId` 的行；`cliDir/rollout/model-io-<sessionId>.jsonl` 存在。
  **两项都不成立** ⇒ `CriticResult` 新增可选字段 `carriers_landed: false`；至少一项成立 ⇒ `true`；没走到这一步（失败早退、无 sessionId）⇒ 字段缺席；
- 守卫对 `carriers_landed === false` 出播报（与 `model_override_applied === false` 同一条通道，C9；**不判失守、不阻断**）：
  「glm 侧运行目录里没有本次会话的 CLI 日志与 rollout：ZCode 可能不再采纳落点键（EV-112），CLI 产物可能留在真实 `~/.zcode`，生效模型也读不回。先看 doctor 的 `cli_version` 是否变了」；
- trace.json 的 `modelSelection` 旁记同一事实（`carriersLanded`）；字段不进 run.json（与 `model_override_reorder` 同口径）。

副本支的 HOME 就是落点根，键被忽略时产物照样落进 `cliDir`，自检不会误报；它实际只对无副本一支有鉴别力，这是预期内的。
