## 2. 问题重述

无副本的审查运行（C1 两种成因）用真实 HOME 跑完整一轮，P1～P7 全部写进真实 `~/.zcode`，不进清扫面、跑后持久留存；
跑后回读（C4）也读真实目录：日志与桌面端、其他 CLI 会话共用，只能靠 `sessionId` 过滤。
EV-110 之前，宿主还能用 `ZCODE_LOG_DIR` 把日志挪去临时卷；EV-110 把它一律清掉以后，连这条退路也没了（CODEX-04 原话）。

## 4. 改动

### 4.1 覆盖面（决策 D1，本稿推荐 (b)）

- (a) **只设 `ZCODE_LOG_DIR`**（CODEX-04 原建议）。**不取**：只收口 P1。rollout 与日志同样逐字含送审包，会话库与 artifacts 也含送审内容，修完仍是「同类载体留在真实 HOME」；
- **(b) 设三键（推荐）**：`ZCODE_LOG_DIR`（P1）、`ZCODE_STORAGE_DIR`（P2、P5、P6、P7）、`ZCODE_SESSION_DB_PATH`（P4），值取自同一个根：

  | 键 | 值（`root = zcodeHomeUnder(sideDir)`） | 与副本路径缺省值的关系 |
  | :-- | :-- | :-- |
  | `ZCODE_STORAGE_DIR` | `<root>/.zcode` | 副本路径 `HOME=<root>` 时 `"~/.zcode"` 展开的就是它 |
  | `ZCODE_SESSION_DB_PATH` | `<root>/.zcode/cli/db/db.sqlite` | 同上，`"~/.zcode/cli/db/db.sqlite"` |
  | `ZCODE_LOG_DIR` | `<root>/.zcode/cli/log` | 同上，`N6s()` |

  三个值写成一个纯函数 `zcodeStorageRedirectEnv(root)`，用例锁住它与副本布局逐字相同。E0 已用同一组值实测（§1.5）；
- (c) 无副本也建一个 HOME（空的或拷一份）。**不取**：改了 HOME，模型选择要么走 legacy 导入（撞 EV-82 的运行期回落），要么要把凭据根一起搬，都得花配额实测；副本源缺失那一格也无从拷；
- (d) 无副本一支拒跑、glm 判不可用。**不取**：这是可用性回退。副本源缺失而个人配置完整的机器，今天 glm 能跑，改完就不能了。

(b) 的代价：无副本一支的**存储根每次都是空的**，用户装在真实 `~/.zcode` 下的 plugins、agent profiles、skills、MCP 配置对审查员不可见（P7），
每次运行还要在运行目录里重新铺一遍 builtin plugins（E0 实测 385 个文件，实验组约 2.3 秒跑完）。副本路径 133 次运行一直就是这个形态，所以这不是新的行为类别。
但它**是**无副本一支的行为变化，写进设计文档与 RUNBOOK。唯一想得到、可能碰到模型选择的是 `XVo` 读出的 profiles 带
`builtInModelSelectionOverrides` / `pluginAgentModelSelectionOverrides`（P7）。它们作用于主 agent 还是只作用于子代理，我没核到底，列为 §9 第 2 条请审查员判断。

### 4.2 哪一支设（决策 D2，本稿推荐 (b)）

- (a) 审查运行两支都设同一组值：副本一支的取值与缺省值逐字相同，结构上最整齐，还顺带堵上「副本 `cli/config.json` 里写了 `storage.dir`」这一格（Env 层压过 User 层）；
- **(b) 只在无副本一支设（推荐）**：副本一支是 EV-82 刚验收过的路径（run `20260924T104357Z`），本题不改它的子进程环境，只多清两个别名键（§4.3）。
  两支同形靠 `zcodeStorageRedirectEnv` 与 `zcodeHomeUnder` 共用同一个根来保证，用例锁布局。
  副本 `cli/config.json` 里的 `storage.*` 那一格本机计数为 0，登记为残余（§8 R1）。

接线：`ZcodeInvokeOptions` 加 `storageRedirectRoot?: string | null`（显式参数，不复用 `homeDir` 当魔法值）；
`zcodeAdapter.run` 在 `home.homeDir === null` 时传 `zcodeHomeUnder(sideDir)`，否则不传。其余调用方（L1～L7）一律不传，行为不变。

### 4.3 清除清单补两个别名键（决策 D3，本稿推荐并入）

`ZCODE_DIR_ENV_KEYS` 增加 `ZCODE_SESSION_DB_PATH`、`ZCODE_SESSION_DB`（四键 → 六键）。理由两条：
1. **副本路径的同构缺口**：宿主预置任一个，副本路径的会话库就落到副本 HOME 与清扫面之外，与 EV-110 当初并入 `ZCODE_LOG_DIR` 的理由逐字同构，方向同样 fail-safe（清掉只会把会话库拉回各自 HOME）；
2. **无副本一支设 `ZCODE_SESSION_DB_PATH` 的前提**：`aun` 按 `Object.entries(env)` 顺序处理，两个别名都映射到同一字段，**后出现的赢**。
   子进程环境的键序由 C8 决定：宿主已有的键保留原位，编排器新加的键追加在末尾。宿主若预置 `ZCODE_SESSION_DB`，谁赢取决于宿主环境里键的插入次序，编排器控制不了。
   别名清掉，设的那个才唯一。

常量名仍叫 `ZCODE_DIR_ENV_KEYS`（改名要动全部消费方，收益只是字面准确），文档块改成「目录与路径键」并逐键写来由。

### 4.4 「先清后设」与 EV-110 的口径

EV-110 的「一律清」防的是**继承宿主值**；本题的「设」是**编排器自己指定落点**。二者不冲突，但有先后：

1. `invokeZcode` 先展开 `zcodeProviderEnv`：六个目录 / 路径键全部 `undefined`（清，所有走它的路径都一样）；
2. **然后**，仅当 `storageRedirectRoot` 给了，才用 `zcodeStorageRedirectEnv(root)` 覆盖其中三个（设）；
3. `HOME` 仍只在 `homeDir` 为真时设。

顺序写死在 `invokeZcode` 一处，用例锁住：宿主预置诱饵值时，无副本子进程看到的是编排器的值，副本子进程看到的是 `undefined`（变异 M2 专咬反序）。
EV-110 的判据「子进程拿不到宿主值」在两支都成立；「子进程拿到的值只由 HOME 决定」这句话要改成「只由 HOME 或编排器显式指定的落点决定」，
`zcodeProviderEnv` 与 `ZCODE_DIR_ENV_KEYS` 的文档块跟着改。
