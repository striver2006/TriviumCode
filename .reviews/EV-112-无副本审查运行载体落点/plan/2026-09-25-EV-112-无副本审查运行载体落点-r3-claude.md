## 2. 问题重述

无副本的审查运行（C1 两种成因）用真实 HOME 跑完整一轮，P1～P7（含 P5b）全部写进真实 `~/.zcode`，不进清扫面、跑后持久留存；
跑后回读（C4）也读真实目录，只能靠 `sessionId` 过滤。EV-110 把宿主的 `ZCODE_LOG_DIR` 一律清掉以后，宿主用它把日志挪去临时卷的退路也没了（CODEX-04 原话）。

**副本支**的落点也能被带偏：宿主预置 beta 开关或 argv 含 `/zcode-beta` 段（P9 ②）、宿主预置运行档位 `development` / `test`（P9 ①）、副本源里写了 `storage.*`（P3）。三者都让回读落空、让 `redactUnder` 失效或让 rollout 不写。

### 4.1 覆盖面（决策 D1：(b) 设三键）

- (a) **只设 `ZCODE_LOG_DIR`**（CODEX-04 原建议）。**不取**：只收口 P1，rollout 与日志同样逐字含送审包；
- **(b) 设三键（采用，两轮三侧认可）**：`ZCODE_LOG_DIR`（P1）、`ZCODE_STORAGE_DIR`（P2、P5、P5b、P6、P7）、`ZCODE_SESSION_DB_PATH`（P4），值取自同一个根：

  | 键 | 值（`root = zcodeHomeUnder(sideDir)`） | 生效机制 | 与「`HOME=<root>` 时的缺省值」 |
  | :-- | :-- | :-- | :-- |
  | `ZCODE_STORAGE_DIR` | `<root>/.zcode` | Env 层（40）→ `storage.dir` | 相同（`"~/.zcode"`） |
  | `ZCODE_SESSION_DB_PATH` | `<root>/.zcode/cli/db/db.sqlite` | Env 层（40）→ `storage.sessionDbPath` | 相同（`"~/.zcode/cli/db/db.sqlite"`） |
  | `ZCODE_LOG_DIR` | `<root>/.zcode/cli/log` | 日志工厂直读（**r3**，CODEX-04） | 相同（`N6s()`） |

  三个值写成一个纯函数 `zcodeStorageRedirectEnv(root)`，用例锁住它与副本布局逐字相同。E0 已用同一组值实测（§1.5）；
- (c) 无副本也建一个 HOME。**不取**：改了 HOME，模型选择要么走 legacy 导入（撞 EV-82 的运行期回落），要么要把凭据根一起搬，都得花配额实测；
- (d) 无副本一支拒跑、glm 判不可用。**不取**：可用性回退。

(b) 的代价：无副本一支的**存储根每次都是空的**，用户装在真实 `~/.zcode` 下的 plugins、agent profiles、skills、MCP 配置对审查员不可见（P7），
每次运行在运行目录里重新铺一遍 builtin plugins（E0 实测 385 个文件，实验组约 2.3 秒跑完）。
**主 agent 的生效模型不受影响**（§1.2）；变化的是无副本一支**子代理**的模型选择：原先可能吃到用户 profiles 的覆盖，改后回落内置缺省。
副本路径 133 次运行一直就是这个形态，不是新的行为类别，但它是无副本一支的行为变化，写进设计文档与 RUNBOOK。

### 4.2 哪一支设（决策 D2：(a) 两支都设，第 2 轮三侧认可）

- **(a) 审查运行两支都设同一组值（采用）**：副本支 `HOME=<root>`，三键取值与该支缺省逐字相同。效果：
  ① `RMi` 见 `ZCODE_STORAGE_DIR` 非空即早退，宿主 beta 开关与 argv 触发都不再改写存储根（P9 ②）；
  ② 副本源里的 `storage.*`（User 层 10）被 Env 层（40）压过（P3）。
- (b) 只在无副本一支设（r1 推荐，第 1 轮 CODEX-04 后弃）：「不改副本支子进程环境」只买到「不新增取值来源」，代价是上面 ①② 两个洞留在 133 次运行的那一支上。
- **(a) 不改副本支行为的机制论证**（**r3**，CODEX-04；glm 第 2 轮补证）：三键里只有两键进 Env 层，`ZCODE_LOG_DIR` 由日志工厂直读、不进配置层。
  Env 层在全包只有两个消费方——优先级表 `eyr`（108 行）与装层处 `Object.keys(_).length > 0 && t.push(…Ek.Env)`（2110 行），没有任何代码观察「Env 层在不在」；
  `storage` 只有 `dir` / `sessionDbPath` 两个字段、全包 `"~/.zcode"` 字面只在缺省对象一处，不存在按字面比较缺省路径的逻辑；日志工厂的所有调用点都不传 `logDir`，环境值不会被配置压制。
  所以取值相同时，「多一个非空 Env 层」本身不切换任何行为。E1 的副本支对照（§6.3）是这条论证的旁证，不是唯一依据。

接线：`ZcodeInvokeOptions` 加 `storageRedirectRoot?: string | null`；`zcodeAdapter.run` 两支都传 `zcodeHomeUnder(sideDir)`。其余调用方（L1～L7）一律不传。
**入参层级约定**：`storageRedirectRoot` 与 `zcodeStorageRedirectEnv(root)` 的入参是 **与 HOME 同层的根**（`<sideDir>/home`），不是 `.zcode`；函数内部才拼 `.zcode`。
JSDoc 写明这一点；**r3**（AGY-r2-01）防嵌套判断用 `path.basename(path.resolve(root)) === '.zcode'`，命中即抛错（`resolve` 顺带去掉尾部分隔符）。

### 4.3 清除面：四键扩为十一键（决策 D3）

全部拉起路径（`zcodeProviderEnv` 与 `probeZcodeEntry`）一律清，宿主值进不了子进程：

| 组 | 键 | 来由与副作用（**r3** 逐键写，CODEX-05） |
| :-- | :-- | :-- |
| 目录 / 路径键（`ZCODE_DIR_ENV_KEYS`，四键 → 七键） | `ZCODE_DATA_BASE_DIR`、`ZCODE_HOME`、`ZCODE_STORAGE_DIR`、`ZCODE_LOG_DIR` | 原有（r3 CODEX-02、EV-110） |
| | `ZCODE_SESSION_DB_PATH`、`ZCODE_SESSION_DB` | P4：宿主预置任一个，会话库落到清扫面外；两个别名映射同一字段、后出现的赢，键序由 C8 决定、编排器控制不了，清掉别名后设的那个才唯一 |
| | `ZCODE_MAILBOX_ROOT` | P10：宿主预置时 mailbox 落到清扫面外 |
| 落点开关键（新常量 `ZCODE_LANDING_SWITCH_ENV_KEYS`） | `ZCODE_RUNTIME_ENV` | P9 ①：`development` 把 rollout 改进 `cli/debug`，`test` 让 rollout 不写；两支都受影响、(a) 挡不住。清掉后按入口路径推断，`.cjs` 入口得 `production` |
| | `ZCODE_BETA` | P9 ②：只有 `RMi` 一处读点。审查运行两支已由 (a) 挡住；探针臂（L2～L4）不设存储根，仍靠清。**清键挡不住 argv 触发**（P9 ②，§8 R7） |
| | `ZCODE_ENV` | 同上 beta 一路；**另有副作用**：`YL` 读它选测试控制面端点，并进遥测的环境名。清掉即走生产控制面，审查运行本该如此，仍 fail-safe |
| | `ZCODE_MESSAGE_ENABLED` | P10：子进程里 mailbox 恒关，审查员用不到会话间消息（包内只有 `Hzo` 一处读点） |

方向都是 fail-safe：清掉会把落点拉回各自 HOME、关掉审查员用不到的可选功能，或回到生产控制面；副作用逐键见上。
两个常量分开，是因为「目录 / 路径键」可清可设，「开关键」只能清；`ZCODE_DIR_ENV_KEYS` 沿用原名，文档块改成「目录与路径键」并逐键写来由。

### 4.4 「先清后设」与 EV-110 的口径

EV-110 的「一律清」防的是**继承宿主值**；本题的「设」是**编排器自己指定落点**。二者不冲突，但有先后：

1. `invokeZcode` 先展开 `zcodeProviderEnv`：十一个键全部 `undefined`（清，所有走它的路径都一样）；
2. **然后**，仅当 `storageRedirectRoot` 给了，才用 `zcodeStorageRedirectEnv(root)` 覆盖其中三个（设）；
3. `HOME` 仍只在 `homeDir` 为真时设。

顺序写死在 `invokeZcode` 一处，用例锁住（变异 M2 专咬反序）。「子进程的落点只由 HOME 决定」改成「只由 HOME 或编排器显式指定的落点决定」，`zcodeProviderEnv` 与 `ZCODE_DIR_ENV_KEYS` 的文档块跟着改。

### 4.6 落点自检（**r3** 改写，CODEX-01 ≡ GLM-02、CODEX-03）

落点键被 CLI 采纳是从压缩产物读出来的厂商事实，ZCode 随桌面端自动更新。三键分属两条互不相干的代码路径（P1：日志工厂直读；P2 / P4：`aun` 后缀映射进配置层），可以**各自**漂移。
r2 的析取判据（日志在**或** rollout 在）在「只丢存储键」时报 true，而逐字含送审包的 rollout、db、artifacts、sessions 已回到真实 HOME，自检主动给出 OK——比不报更坏。r3 改为：

- **正向核（两支）**：`run()` 在 CLI 成功返回 envelope 且有 `sessionId` 时，分别记两项：`log`（`cliDir/log` 下任一日志文件里有本次 `sessionId` 的行）、`rollout`（`cliDir/rollout/model-io-<sessionId>.jsonl` 存在）。
  **合取**：任一为 false 即播报。合取不会误报的依据：CLI 成功返回时模型已被调用，而 `recordModelIO` 在运行档位非 `test`、请求不带 `skipTranscript` 时恒真（P2），运行档位已被清为 `production`（§4.3），所以 rollout 必写；日志同理必写启动事件；
- **反向核（无副本支）**：真实 HOME 下 `~/.zcode/cli/rollout/model-io-<sessionId>.jsonl` 存在 ⇒ `leaked_to_home: true`，并播报。只查文件名、不读内容。副本支的 HOME 就是落点根，反向核无意义，不做；
- **字段**：`CriticResult` 新增可选 `carriers_landed: { log: boolean; rollout: boolean; leaked_to_home?: boolean }`；没走到这一步（失败早退、无 sessionId）⇒ 字段缺席；
  其它三侧适配器不产出。**进 run.json**：`review.ts` 与 `model_override_applied` 同处条件展开写进逐侧段；`run.v2.json` 在 `$defs.critic.properties` 补该字段的说明（可选）。trace.json 的 `modelSelection` 旁记同一事实；
- **播报**（守卫，C9 同一通道，**不判失守、不阻断**）：`log` 或 `rollout` 为 false ⇒「glm 侧运行目录里缺本次会话的 <日志 / rollout>：ZCode 可能不再采纳对应的落点键（EV-112），CLI 产物可能留在别处，生效模型也可能读不回。先看 doctor 的 `cli_version` 是否变了」；
  `leaked_to_home` 为 true ⇒ 另起一句「本次会话的 rollout 出现在真实 `~/.zcode/cli/rollout` 下：送审内容已写进真实 HOME，需人工清理（文件名见 run.json）」。

副本支的 HOME 就是落点根，键被忽略时产物照样落进 `cliDir`，正向核在副本支对键漂移没有鉴别力；它在副本支能抓的是 P9 / P3 一类把落点带出 HOME 的情形。

### 6.3 验收

**E0（零配额，已于送审前完成，读数见 §1.5）**。r1 原设想「闭端口 + 白名单副本」，实际改成「本地 401 服务 + 合成副本」。

**E1（零配额，代码提交后）**（**r3** 改写，CODEX-02、GLM-05、GLM-03、CODEX-06）：干净工作树 `npm run build`、`npm run install:local` 各一条；
在 evidence 目录新写一个脚本，经 `dist` 的函数驱动（合成副本与本地 401 服务照 E0），所有目录来自 `mkdtemp`，不含删除调用。脚本先记录宿主 `ZCODE_*` 键名并**断言为空**，不为空即停止、不出读数。

- **无副本支**：经 `zcodeAdapter.run`，`HOME=` 假 HOME、`model: null`、`out_dir` 在 `mkdtemp` 的 C 下 ⇒ 载体落在 `C/glm/home/.zcode/cli/…`，假 HOME 下没有；
- **副本支对照**（D2-(a) 的旁证）：**同一份新代码**，`invokeZcode` 调两次，只差 `storageRedirectRoot` 给不给（清除面完全相同）；两次的副本都由 `prepareZcodeHome(…, { requestedFirst: true })` 各造一份、只读参数都取 `readonlyArgsFromProbe`。
  判据：两次**模型调用之前写出的落盘集合**（相对路径集合）相同，且本次 sessionId 的 rollout 落在同一前缀下；
- **观测面声明**：401 让 CLI 非零退出，E1 只观测得到模型调用之前与失败请求写出的载体（log / rollout / db / plugins / HOME 侧 v2 文件）；artifacts / sessions / memories 要走到工具调用，不在观测面内。
  「整份布局不变」挂到副本支下一次真实双审的实跑读数（每次含 glm 的双审都经过 (a) 的新环境：核 run.json 的 `carriers_landed` 两布尔为 true、`model_effective` 照常）；
- **argv 约束**（CODEX-06）：E1 的所有 argv 元素（入口路径、提示语、`--cwd`）不含 `/zcode-beta` 路径段；
- **重复取样**（GLM-03）：每组 3 次，**每次用新的 `mkdtemp` HOME**（排除冷热缓存），两组**交替**执行（ABABAB，排除固定先后顺序）；
  每次记录两组 HOME 侧 `zcode-builtin*.json` 的存在性与 mtime、脱敏后的 stderr 全文。判读三档：稳定只在一组出现 ⇒ 定位机理写进报告；不稳定 ⇒ 登记「未观察到稳定关联」；定位不了 ⇒ 登记「未解释的观测差」。不下「与三键无关」一类的因果结论；
- **真实 HOME 与假 HOME 都按内容核**：日志逐文件查本次 `sessionId` 是否出现、会话库文件里 `sessionId` 计数（二进制，尽力判，含 WAL），只输出文件名与计数；另核 `~/.zcode-beta`、`~/.zcode/mailbox` 的存在性与 mtime；
- **E1 到不了回读分支**：`run()` 在失败早退处返回，`cliDir` 回读与落点自检走不到。回读与自检由 U3 / U3b / U8 的假入口覆盖，报告写明。

`trivium doctor --only zcode --no-model-calls` 的 note 文案按 §4.5 核（宿主不预置、入口不在 beta 路径时应无这两条 note；预置与 beta 由 U7 覆盖）。输出留进 `doc/05_testing/evidence/ev112-acceptance-<日期>/`。
`npm run typecheck && npm run build && npm test` 全绿；`trivium doctor --selftest` 全绿。

**E2（真实配额，可选，由用户决定并发起）**：要让 `routeModel` 对 glm 返回 null（例如当前 profile 暂时去掉 glm 该阶段的模型），怎么做由用户定。
