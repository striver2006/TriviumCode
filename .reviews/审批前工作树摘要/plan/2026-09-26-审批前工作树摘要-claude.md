## 2. 改法

### 2.1 新增模块 `src/trivium/worktree-summary.ts`

只读，不抛错（内部任何失败都转成 `available: false`）：

```ts
export interface WorkTreeSummary {
  available: boolean;
  /** 不可用的原因（基线缺席 / 基线对象不在对象库 / git 失败），available 为 true 时为 null */
  reason: string | null;
  run_id: string;
  baseline: 'review_end';            // D1 取 ② 时只有这一种
  baseline_tree: string | null;
  current_tree: string | null;
  files: Array<{ status: string; path: string }>;   // 全量，按路径排序
  excluded_prefixes: string[];       // diffExcludePrefixes 的结果
}
export async function summarizeWorkTree(i: { projectRoot; archiveRootRel; runMeta }): Promise<WorkTreeSummary>;
export function renderWorkTreeSummary(s: WorkTreeSummary, limit = 20): string;
```

流程：取 `runMeta.snapshot.after_tree_hash`（D1）→ 缺席即 `available: false`（D1 的旧留痕处置）→ `git cat-file -e <基线>^{tree}` 核对象在不在 →
`workTreeHash` 取当前 tree → 两者相等直接出「无改动」→ 否则 `diff-tree -r --name-status --no-renames -z <基线> <当前>` →
按 `diffExcludePrefixes(archiveRootRel)` 剔除归档根、`.trivium/`、`.git`。

- `-z` 输出不加引号，路径里的空格、引号、中文原样拿到，不走 `unquoteGitPath`。
- 不剔 scratch 路径：基线取审查收尾时，审查员的 scratch 已在基线里；闸门期审查员不在跑。
- 只列文件名，不读内容；敏感文件（`review.sensitive_globs`）同样只出现名字。

### 2.2 `util/git.ts` 新增两个严格助手

- `treeExists(cwd, tree): Promise<boolean>`：`cat-file -e`。
- `diffTreesNameStatus(cwd, a, b): Promise<Array<{status, path}>>`：**非零退出即抛**。
- **不改 `diffTrees`**：它是 `judgeDrift` 的依赖，改它的失败语义等于改漂移判定（§6.3 另登 BACKLOG）。

### 2.3 收尾落盘 `snapshot.after_tree_hash`（D1 取 ② 时）

- `review.ts` :1339 写 `meta.snapshot.drift` 的同一处加 `meta.snapshot.after_tree_hash = afterTreeHash`。没走到复算的出口不写，字段缺席。
- `run.v2.json` 的 `snapshot.properties` 加 `after_tree_hash: { type: string, description: "审查收尾复算时的工作树 tree（与 tree_hash 同法）；只供审批时的工作树摘要作基线，不参与任何判定；缺席 = 本字段之前的旧留痕或运行未走到复算" }`，不进 `required`。
- `types.ts` `SnapshotMeta`（:1218 一带）加可选字段。run.v1 不动。
- 写入时点与 `drift` 相同，都在收尾时写。之后 run.json 不再更新，S14 的不变量不受影响。

### 2.5 摘要文案（D3、D4）

有改动：

```
工作树改动摘要（只告知，不影响本次审批）：自审查收尾（run <run_id>）以来，3 个文件有变化
  M  NOTES.md
  A  src/new.ts
  D  src/old.ts
  （比对范围：未被 .gitignore 忽略的文件，不含 .reviews/ 与 .trivium/；闸门期提交过的改动同样列出）
  若这些改动不该发生：本次审批照常记录；请自行 git diff 核对，必要时 <dual-abandon 写法> --topic <主题> 作废本轮后重跑。
```

- 超过 20 条：列前 20 条，再加一行「……另有 N 个，完整列表：`git diff-tree -r --name-status <基线> <当前>`」。两个 tree 都在对象库里，这条命令照抄就能跑。
- `await-approval` / `--check` 停点上，首句换成「（只告知，不影响审批）」，末句换成「审批时会再打印一次」。
- 无改动（D4）：`工作树改动摘要：自审查收尾（run <run_id>）以来，未被 .gitignore 忽略的文件无改动（不含 .reviews/ 与 .trivium/）。`
- 不可用（D5）：`⚠️ 工作树改动摘要取不到：<原因>。这不影响本次审批；请自行 git status 核对。`

原因分三种，逐字区分，不与「无改动」同形：
- 本轮留痕早于此功能，没有审查收尾的基线。
- 基线对象已不在对象库（可能被 git gc 清理）。
- git 调用失败：<stderr 首行>。

## 4. 性能与失败面

- 代价 = 一次 `workTreeHash`（与送审冻结同量级：临时索引 `add -A` 要重读工作树）+ 一次 `cat-file` + 一次 `diff-tree`。每次 git 调用沿用 120 s 超时（`git.ts` :25）。
- 只在三个 CLI 出口算，**不进 Hook**：Hook 有 15 / 30 s 超时，大仓的 `add -A` 可能碰到。L1 上闸门期写入本来就由 Hook 事前拦。
- 失败一律 `warn`，不改退出码。JSON 模式下 `available: false` 带 `reason`。

## 6. 风险与边界

### 6.1 摘要不是判据

它不保证「闸门期没人改过」：
- 被忽略的文件看不见；
- 改了又改回的文件，tree 相同，不会列出；
- 基线被 gc 清掉时只能报「取不到」。

文案按这三条如实写，不说「未发现越界」。

### 6.2 `approve` 没有确认步骤

摘要出现时这次审批已经在落笔。出口是事后的：核对后 `abandon` 作废本轮（S15）。
「看了再批」在 L2 上的时点是停点那次打印（W4）。想要「审批前单独看」的只读入口，登进 §6.3，不在本主题做。

### 6.3 新登 BACKLOG（只登记，不做）

- `diffTrees` 失败时返回 `[]`，`judgeDrift` 因此会把「比不了」判成「无漂移」（S7）。改它等于改漂移判定，要单独走计划。
- 审批前单独看摘要的只读入口（`approve --dry-run` 或 `status` 带摘要），由用户定要不要。
