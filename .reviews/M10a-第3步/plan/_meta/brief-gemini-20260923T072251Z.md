## 3. 块二 · 审批链路（r7 §4.3 / §4.4）

### 3.1 抽出的复核函数：`gate.ts` 新增 `verifyRoundForApproval`

```ts
export async function verifyRoundForApproval(i: {
  cfg: Config; layout: ArchiveLayout; stage: Stage;
  runId: string | null;   // null ⇒ 抛错拒绝，绝不跳过
  runIdPinned: boolean;
  runIdSource: string;    // 报错里说明 run_id 是从哪儿推断的
}): Promise<{ ok: boolean; runId: string; result: GateCheckResult; tampered: TamperedArtifact[] }>
```

按顺序执行，**任何一步都没有跳过路径**：

1. `if (!runId) throw TriviumError(EXIT.MISSING_ARTIFACT, …)`。
   `cli.ts:1134-1145` 的注释与文案**原样搬过来**，包括「推断不出来时**不会**跳过校验」这一句。
   **这一条是抽取函数的验收项**（r7 §4.3），由 §3.3 的单测直接锁住。
2. `readRunMeta(layout, stage, runId)` 返回 null 时同样抛错：取不到 driver 与轮次就拒绝，
   **不回落到缺省 Driver**。这一点比 `loadRoundReviews` 的宽松口径更严，理由是审批停点不该按猜测放行。
3. 执行 `loadRoundReviews` 和 `checkAdjudication`，driver 与 `rerunIndex` 取自该 runMeta。
   与 `--await-approval` 现有写法等价：那里的 `latest` 就是同一份 meta。
4. **sha256 抽核**：`checkRecordedArtifacts(layout, [{ run_id, stage, artifacts: runMeta.artifacts }])`。
5. `ok = result.ok && tampered.length === 0`。

**抽核范围如实表述**：只核**本轮** run.json 的 `artifacts[]`。更早轮次的登记由 `hook-pre-commit`
的锚②在每次提交时全量核对。注释与报告都按「本轮抽核」写，**不写成「全部工件一致」**。

**会不会误拦合法流程**：锚②在每次提交时全量核对全部已登记工件，历次提交都通过了，
这说明已登记的工件里没有合法可变的。`changes.diff` 便利副本每轮覆盖写，**不登记**；
登记的是 `changes-<runid>.diff`。实施时再加一条 code 阶段的审批正例实测确认（§3.3）。

**篡改清单的渲染**放在函数旁边，不去动 `hooks.ts`：改那里会把安全关键文件拖进本轮审查面。
代价是与 `hooks.ts:1341-1344` 有两行同义文案，已登记为 §5 偏差 3。

### 3.2 两处调用

**`--await-approval`**（`cli.ts:1120-1173`）：
- 改为 `verifyRoundForApproval({ runId: latest?.run_id ?? null, runIdPinned: Boolean(pinnedId), runIdSource: … })`。
- 失败时渲染 `renderGateResult` 和篡改清单，然后 `fail`，退 `GATE_BLOCK`。
- 通过时 `preWarnings` 的透传保持不变（r3 CODEX-03 的落点）。
- **这一处现在也补上了 sha256 抽核**（r7 §4.4：「同源抽成一个函数会把缩窄原样继承，两处一起补齐」）。

**`cmdApproval`**（`cli.ts:1439`），只在 `decision === 'approved'` 时执行，且在任何 `recordApproval` 之前：
- **先全部复核，再逐一落审批**，避免出现「一个阶段已放行、另一个阶段复核失败」的半截状态。
  （approved 今天强制要求 `--stage`，实际只有一个阶段；这样写是为了不依赖这个前提。）
- 每个阶段先 `getGate`，再调用 `assertGateDecidable(gate, …)`。
  这个函数从 `recordApproval` 里抽出，覆盖无闸门、running、非 awaiting_approval 三格，
  **只会抛错、不会跳过**。放在复核之前，是为了让这三种状态仍报原来的准确文案，
  而不是报一串「裁决缺口」。running 的闸门去跑复核，得到的是误导性的输出。
- 接着 `verifyRoundForApproval({ runId: gate.run_id ?? null, runIdPinned: true, runIdSource: '闸门记录' })`。
  `approve` 没有 `--run-id`，传 true 是为了不出现「用 --run-id 指回更早轮次」这句不适用的提示。
- 不通过时打印缺口，退 2（`GATE_BLOCK`）。
- `rejected` / `abandoned` **不复核**，**不加确认码**（v1.2.3 ② 撤销过，理由见 `approval.ts:25-28`）。

### 3.3 绑定「核过的就是批的」（超出 r7 §4.3 字面，见 §5 偏差 1）

复核在 `cmdApproval` 里执行，`recordApproval` 随后**自己再读一次闸门**，并按那次读到的 `gate.run_id` 做比较-交换。
两次读之间若有别的运行把同一阶段置成 awaiting_approval，就会批到一个没核过的轮次。
这个窗口在同一进程内只有毫秒级，但它正是「复核」与「批准」之间的缝。

- `ApprovalInput` 增加 `verifiedRunId`。`decision === 'approved'` 时，
  若 `verifiedRunId !== gate.run_id` 就拒绝；未传也按不一致处理。
- **注释如实写明它保证什么**：只证明调用方给出的 run_id 与闸门一致，
  **不证明复核真的跑过**。后者由 `cmdApproval` 的代码结构和 §6.2 的变异来守。
