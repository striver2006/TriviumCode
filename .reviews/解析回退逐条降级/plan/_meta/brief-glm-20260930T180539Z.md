## 2. 核心判断

- **逐条降级的前提是「根对象拿得到且合法」**。根合法 = 剥掉允许的回显字段后，把 `findings` 换成 `[]` 能过整份 schema，且原 `findings` 是数组。根不合（缺 `verdict`、`schema` 值错、多带非回显字段、`findings` 不是数组）说明这份输出连「审查结论」的外形都没立住，整份回退是对的（用户决策）。
- **降级意见不改写**：不补缺失字段、不映射表外值。它进裁决靠的是**编号**，所以编号必须可用；编号本身不可用的意见（非对象、缺 `id`、`id` 不合 schema 形状）没法单独裁决，只能让整份回退（§3.1 成因 `finding_unaddressable`）。普查 0 例，这一格是防御。
- **失去阻断资格 = 不进 `Review.findings`**。`Review` 类型、`_meta/review-<侧>-<run>.json`、共同阻断、分歧度量、严重度计数全都只看合格意见——这些消费方一行不改就自动满足「降级意见不参与阻断」。降级意见另走一条旁路进裁决期望集与渲染。
- **两类修复都是无损的**：剥回显字段——这些字段的值编排器自己会写，审查员填的值没有任何消费方；还原非法转义——`\|` 在 JSON 里非法，审查员要表达的就是字面的反斜杠加竖线，按字面保留比丢掉整份结论更忠实。两类都在校验**之前**、都留痕。

## 3. 修法

### 3.1 `parseReview` 的新结构（`parse.ts` :17～:19、:130～:193）

`ParseOutcome` 只取加法：

- 成功支加 `degraded: DegradedFinding[]`（合格时为 `[]`）与 `repairs: ParseRepairs`；
- 失败支加 `cause: FallbackCause`。

```text
DegradedFinding = { index, id, problems: { field, kind: 'missing'|'invalid'|'extra', message }[], raw }
ParseRepairs    = { stripped_fields: string[], unescaped_backslashes: number }
FallbackCause   = 'no_json_object' | 'json_syntax' | 'root_invalid' | 'finding_unaddressable' | 'foreign_prefix'
```

（`foreign_prefix` 由 `review.ts` 的既有前缀硬失败给出，见 §3.3，解析器本身不产出。）

逐候选的步骤：

1. `JSON.parse`；失败 ⇒ 试 §3.2 的转义还原，修后仍失败 ⇒ 记 `json_syntax`（错误文本取**原始**报错），跳下一候选；
2. 非对象（数组、标量）⇒ 跳过；
3. 剥 §3.2 的两张清单（厂商注入 + 编排器回显），剥到的键名进 `stripped_fields`；
4. 整份 ajv 过 ⇒ **全合格**，立即返回（`degraded: []`）；
5. 根校验：`findings` 是数组，且 `{ ...剥后对象, findings: [] }` 过整份 schema；不过 ⇒ 记 `root_invalid`（带根错误），跳下一候选；
6. 逐条用 `findings.items` 子 schema（同一个 ajv 实例从同一份 `review.v1.json` 编译，不抄第二份）校验；不合格者若编号不可用 ⇒ 记 `finding_unaddressable`，跳下一候选；否则该候选是**部分合格**，记为候选结果、**继续看后面的候选**。

选取：首个全合格候选 > 首个部分合格候选 > 整份回退。继续看后面的候选是为 agy 的「首个对象是截断片段、后一个完整」那一形态（:84～:92 的注释）：前一个部分合格不应压过后一个全合格。回退时 `cause` 取**走得最远**的那一格（`finding_unaddressable` > `root_invalid` > `json_syntax` > `no_json_object`），`reason` / `errors` 同取那一格——改前的 `lastReason` 取的是「最后一个候选」，逐行候选常把更有信息量的围栏候选的错误盖掉。

`problems` 的来源：ajv 的 `required` ⇒ `missing`、`enum` / `const` / `pattern` / `type` / `minLength` ⇒ `invalid`、`additionalProperties` ⇒ `extra`；`field` 取 `missingProperty` / `additionalProperty` 或 `instancePath` 的首段。`message` 沿用 `formatSchemaErrors` 的口径。

### 3.2 两类无损修复（`parse.ts`）

**其一，剥回显根字段**。新常量 `ECHOED_ORCHESTRATOR_KEYS` = `render.ts` 的 `renderFrontMatter`（:113～:194）能写出的全部键，减去 `review.v1` 的根属性（`schema` / `verdict` 与 schema 同名同义，不剥）：

`topic` `stage` `role` `vendor` `agent_cli` `model_requested` `model_effective` `model_effective_source` `effort` `model_route` `run_id` `rerun_index` `snapshot_hash` `blind` `started_at` `finished_at` `duration_s` `tool_calls` `evidence_ok` `findings_count` `degraded` `parse_fallback` `peer_deny` `drift` `consulted_unverified` `readonly_verification` `path_verification` `peer_leak` `joint_check` `heterogeneous` `override_reason` `session_id`

论证：

- 样本里出现过的回显键（`topic` / `stage` / `role` / `run_id` / `rerun_index` / `evidence_ok`）**全部**是这份 front-matter 的键——审查员是照着落盘文档的形态反推、以为结论 JSON 也该带（EV-10 原判）。按「样本里见过的」列清单会漏掉同族的其余键，下一次换一个键又整份回退；按 front-matter 键集列，判据是「编排器自己会写的」这一条可核的事实；
- **不剥** `reviewer` / `addresses`：它们不是编排器写进审查文档的字段（`addresses` 属于 Driver 写的裁决件 front-matter）；唯一带它们的样本（EV-122 code glm）同时缺 `verdict`，剥与不剥都整份回退，结论不受影响；
- **拼错的键照旧不合格**：清单是精确键名匹配，`toppic`、`findings_cnt` 之类仍撞 `additionalProperties: false`；
- 清单与 `renderFrontMatter` 用契约测试绑定（§5.1 P9）：全开条件分支渲染一份 front-matter，取键集减 schema 根属性，断言与清单**逐项相等**——front-matter 加字段而清单没跟，当场红。

`VENDOR_NOISE_KEYS` 保留原样，两张清单都在校验前剥；剥到的键**一并**进 `stripped_fields`。这把厂商字段从「静默剥」改成「剥了留痕」——agy 侧 run.json 的 `parse_repairs.stripped_fields` 会常态出现 `toolAction` / `toolSummary`，这是如实，不是新问题。

**其二，还原非法转义**。只在 `JSON.parse` 失败时才试。按字符扫描，只在字符串字面量内部动手：反斜杠后跟 `" \ / b f n r t` 或 `u` + 四位十六进制 ⇒ 原样；否则把这个反斜杠改成 `\\`（值里保留字面的反斜杠与后随字符），计数。修后再 `JSON.parse`，仍失败 ⇒ `json_syntax`，错误文本取修前的原始报错。计数进 `unescaped_backslashes`。不处理其它语法错（缺逗号 / 括号、字符串里的裸换行）——普查里剩下的 2 份就是这一类，修它们要猜结构，不是无损修复。

### 3.3 `review.ts` 的接线（:1165～:1220、:1376～:1392、:1525～:1606）

- `checkReviewIntegrity(review, critic, degradedIds = [])`（`parse.ts` :216）：前缀归属与重复编号改为对「合格 + 降级」的编号集判；`emptyWithoutExplanation` 在有降级意见时不成立。**降级意见的编号前缀不属于本侧 ⇒ 仍走既有的整份回退硬失败**（:1175～:1206 注释论证的那道后盾对降级编号同样必要），成因记 `foreign_prefix`；
- 部分合格 ⇒ `reviews[c] = 合格部分`，**该侧 `status` 仍为 `ok`**，另存 `degraded[c]` 与 `repairs[c]`，并 `warn` 一行点名降级编号与不合格字段；
- 整份回退 ⇒ 行为不变，`fail_reason` 前缀加成因（`[root_invalid] …`），另存 `fallbackCause[c]`；
- **降级旁路文件** `_meta/review-<侧>-<run>.degraded.json`（只在有降级意见时写）：`{ critic, run_id, findings: DegradedFinding[] }`，原样保留审查员给的对象；进 `run.json.artifacts` 保护集。`_meta/review-<侧>-<run>.json` 保持**纯 `review.v1`**（只含合格意见），不往里加键——这份文件是 gate 的事实来源、也是 schema 合法的审查结论，混入不合格对象会打破这两点；
- `run.json.critics[c]`（`run.v2` 的 `critic` 定义本就 `additionalProperties: true`，新增三格同时进 schema 的 `properties`，只取加法）：
  - `findings_degraded: string[]`——**解析成功的侧恒写**（无降级即 `[]`）；
  - `parse_repairs: { stripped_fields, unescaped_backslashes }`——**解析成功的侧恒写**；
  - `parse_fallback_cause`——**`status === 'parse_fallback'` 的侧恒写**；
  - 失败 / 超时侧三格都不写。三态落在结构上：键缺 = 没走到解析（或早于本主题的留痕），`[]` / 零值 = 解析过、没有——与 :1548～:1553 的「恒写」口径一致；
- `empty_review`（:1585）改为「合格 0 条且降级 0 条」。改前的式子在「全部意见都降级」时会记 `true`，而那一侧明明交了意见。

### 3.4 gate（`gate.ts`）

- `loadRoundReviews` 返回加 `expectedDegradedIds: string[]`：取 `run.json.critics[c].findings_degraded`；`run.json` 读不出时退而读各侧 `.degraded.json`（尽力，读不到即空，这一格已由 `missingSides` 与审批路径的「留痕读不出即拒」兜底）；
- `GateCheckInput` 加 `expectedDegradedIds: readonly string[]`，**必填**（`voidedSides` / `reviewDocs` 两处注释记着「可选参数让漏传静默成功」，照同一教训做）；
- 期望集 = 合格编号 ∪ 降级编号：缺裁决报 `missing_findings`、多余报 `unknown_findings`；降级行与合格行同一套逐行校验（**接受要写落点**——它是一条完整的具体意见，只是缺了某个字段，不是 F 单元那种不可分的原文块）；
- 共同阻断：`reviews` 里没有降级意见，`findJointRejectedBlockers` 与 `jointCheckState` 一行不改即自动排除；
- 新告警 `degraded_findings`（有降级意见时恒出）：「下列意见不合 `trivium.review.v1`，已逐条降级：仍须逐条裁决，但不参与阻断与共同阻断判定——其中声称 blocker 的，被驳回不会触发共同阻断告警」，`ids` 列全；
- `GateCheckResult` 加 `degradedIds`；`gate --check --json` 加 `degraded_ids`（`cli.ts` :1363～:1372）；`renderGateResult` 的通过行加「含 N 条逐条降级」；
- `isFallbackId`（`disposition.ts` :289）与 F 编号校验不变：F 编号现在只属于整份回退。

### 3.5 渲染（`render.ts`）

- `RenderInput` 加 `degradedFindings?`、`parseRepairs?`、`parseFallbackCause?`；
- front-matter 只取加法、条件展开（与 `consulted_unverified` / `verification` 同口径，常态不出现）：`findings_degraded: <N>`（N > 0）、`parse_repairs`（剥过字段或还原过转义时）、`parse_fallback_cause`（整份回退时）。`findings_count` 仍只数合格意见；
- 横幅：有降级意见 ⇒「**逐条降级**：本侧有 N 条意见不合 schema，单列在『不合格意见』一节，保留原编号、须逐条裁决，但不参与阻断与共同阻断判定」；有修复 ⇒「**解析前做了无损修复**：剥掉回显字段 …；还原非法转义 N 处」；整份回退的横幅加成因一句（没有 JSON 对象 / JSON 语法修不好 / 根字段不合 / 有意见编号不可用 / 编号前缀不属于本侧）；
- 新节「## 不合格意见（逐条降级，共 N 条）」，放在合格意见之后、「认为正确的部分」之前。每条 `### <编号> · 不合格`，列出 `problems`（缺哪个字段、哪个字段的什么值不在枚举内、多了哪个字段），再按合格意见的同一版式列出**审查员给的原值**：字符串原样、非字符串 `JSON.stringify`、缺失写「（缺失）」、不合法的值后标「（不合法）」；
- 合格 0 条而有降级意见时，「审查意见」一节不再说「本侧**未发现问题**」，改说「合格意见 0 条，见下方『不合格意见』」。

### 3.6 旧留痕与 gate 的重试（用户决策：重试的既有行为保留，影响由计划论证）

`loadRoundReviews` :881～:893 对回退侧用当前解析器重试原文。新解析器下重试结果有三种：

| 重试结果 | 处置 | 理由 |
| :-- | :-- | :-- |
| 全合格（含靠两类修复才合格的） | 按结构化校验（**既有行为**） | 与改前「重试成功」同义 |
| 部分合格 | **仍按 F 编号校验**，note 写明「重试得到 N 条逐条降级；该轮没有逐条降级留痕，维持回退口径」 | 旧 run.json 没有 `findings_degraded`，若按结构化校验，降级意见会**静默掉出期望集**——正是本主题要防的那一类 |
| 仍失败 | 按 F 编号校验（既有行为） | — |

影响面（普查预测，改后以 §5.2 实测为准）：只有「全合格」这一行会改变历史轮次的判定，预测 9 份，其中 2 份（M2 / M4 gemini）改前就已按结构化校验、判定不变；其余 7 份里改前闸门为 `ok` 的 5 轮（CLI进程组记录 code、M8 plan `20260915T105915Z`、M8 code `20260915T024740Z`、M9-Hook当轮Driver保护集 code、M9-裁决件角色契约放宽 plan）若当时按 F 编号裁决，对它们手工跑 `gate --check --run-id` 会翻成缺裁决。这些都是已审批、已提交、已结案的轮次：审批复核只对**最新一轮**跑（`verifyRoundForApproval`），提交锚只核 sha256、不跑裁决校验，所以日常流程碰不到；只有手工对历史轮次钉 `--run-id` 复核才会看到。**不为它们加豁免**：按裁决件实际用的编号体系反推该怎么校验，等于让被校验对象决定校验口径；重试本就是为了「解析器修好后让历史归档变成机读的」（:811～:814 注释），翻转是这条既有行为在更好的解析器下的必然结果。note 文案补一句「若该轮当时按 `<前缀>-F<n>` 裁决，这里报的缺裁决是口径差，不是漏裁」，§5.2 把实测翻转的轮次逐一列进报告。

## 7. 风险

- **把「部分合格」当「合格」的地方漏改**：`Review` 只含合格意见，凡是「这一侧有没有意见」的判断（`empty_review`、`emptyWithoutExplanation`、渲染的「未发现问题」、report 的意见数）都要另看降级集——§3.3 / §3.5 / §3.9 逐处列了，编码时再 grep `findings.length` 全仓核一遍；
