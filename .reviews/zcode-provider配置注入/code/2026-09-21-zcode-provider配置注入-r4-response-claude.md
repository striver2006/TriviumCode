## 二、修改方案

### 2.1 旗标探针改用**正向证据**判据（CODEX-01，minor·correctness）

**属实，且是本轮唯一改变判断的一条。** 现判定链是：`r.code !== 0 && 命中定位失败正则` → indeterminate；
否则看 `Unknown option '<flag>'` → rejected；**再否则一律 accepted**。最后那个「否则」是否定式：
它把「没有证据证明被拒」当成「有证据证明被接受」。`exec.run` 在 spawn 失败时 `code` 为 `null`
（`null !== 0` 成立）、stderr 拼 `[spawn error]`，既不命中定位正则也不命中 `Unknown`，
**直落 accepted**——七个候选全记成接受，与 P-29 同一类结论文件污染，只是换了成因。
r3 补的退出码门控解决的是「误放成功调用」，这一条解决的是「误放崩溃」，是同一课的另一半。

落点：`probeReadonlyFlags` 的判定链改成三分且**接受需要正向证据**——
① stderr 命中 `Unknown option '<flag>'` → rejected；
② 有证据表明参数解析**已经发生**（`r.code === 0`，或 stderr 命中模型/凭据层的已知停点：
`Model creation failed` / `Model config is missing` / provider 鉴权那组）→ accepted；
③ 其余一切（含 `code === null`、`[spawn error]`、`Cannot find module`、未识别形态）→ indeterminate，
并把该候选的退出码与 stderr 首行摘要进 note。
方向保守：判不出就不写结论（保留旧值 + `warnings` 告警），代价是新机器上遇到未登记的停点文案时
该侧会判为不可用——那正是应该有人去看一眼的情形，比静默写一份失真结论好。

### 2.2 宿主预置值被清除这件事要说出来（CODEX-02，minor·maintainability）

**意见属实**：这两个变量是 CLI 官方承认的定位通道，非标准安装布局下用户自设曾是唯一可行方案；
本轮之后派生路径在就覆盖、不在就删除，两条路都不再尊重用户的显式配置。而这个独占口径
**只活在代码注释里**，面向用户的 RUNBOOK / QUICKSTART 一个字都没说。

**接受「记录」这一支**，落点两处：
① `probeZcode` 增一条 note——探测时若 `process.env` 里存在这两个键之一，写明「发现宿主预置
`ZCODE_*_PROVIDER_CONFIG_FILE`，编排器独占这两个变量，本次按派生路径注入或删除」；
② RUNBOOK 排障表加一行「自设这两个变量对编排器拉起无效」。

**驳回「删除前判用户值指向的文件是否存在，存在即保留」这一支**：它把宿主环境重新变成
能改变编排器行为的输入，与 r2 CODEX-01 ≡ AGY-02 的裁决直接冲突——那条的整个论证就是
判据必须是「子进程拿不到」而不是「我没主动注入」，而旗标探针正是「宿主有值就烧七次配额」
的那个位置。保留用户值等于把 fail-closed 改回 fail-open，且开口处恰好是已经出过事的地方。
独占是有意的，本轮把它写到用户看得见的地方，不改行为。

### 2.3 `warnings` 档补测试守卫（CODEX-03，minor·test-gap）

**属实**：`grep -rn flagsIndeterminate test/` 零命中，新档位的唯一住户与「不影响退出码」这条
档位定义都没有用例钉住，r3 的实施留痕自己也写了「未验到」。这个档位存在的理由恰恰是
防误用，而它现在只靠接口注释——本仓纪律明令这类约定要换成机制。

落点：复用 provider-env 测试已有的假入口装置（`layout()` 能摆出「内置文件不在 → 旗标全第三态」），
补 doctor 层 2 条：① 该形态下 `runDoctor` 的 `warnings` 恰含一条「本轮未判定」，且 `blockers`
**不含**旗标那条；② 同形态下 `blockers` 为空 ⇒ `ok` 为真、退出口径不变。
若 `runDoctor` 在单测里驱动成本过高（它要 config / triviumDir / 多侧探针），退一步只做第 ① 条，
并在用例注释里写明第 ② 条改由对 `cmdDoctor` 返回码的最小集成断言覆盖——**不接受「不做」**。

### 2.4 名词正则的非零退出侧角落（CODEX-04，nit·correctness，其自评 confidence low）

**意见属实**：退出码门控只挡住了「退 0 + 诊断行」那一半；「因别的原因退非 0 + stderr 带成功形态的
诊断行」仍会被判成定位失败，四处同源文案齐指安装布局，而真因可能在凭据或模型面。

**接受「登记观察项」这一支**，落点：M0 报告 P-28 补一条观察——该判据依赖「这个英文名词只在定位失败时
出现」这一 **n 很小**的实测前提（本机只见过失败形态一种），版本漂移会打破它。

**驳回「收紧正则」这一支**：r2 AGY-01 已经裁过同一件事——英文措辞是猜的（本机只见中文前缀），
在退出码门控之后再收紧正则「收益为零、误杀风险为正」。本轮没有新证据推翻那条裁决，
真实 CLI 也未观测到该形态。记为观察项，等真出现了拿实测原文改，不拿猜测改。

### 2.5 EV-83 的清单改成 grep 锚（CODEX-05，nit·doc）

**属实**：EV-83 人工枚举的位置清单漏了本轮新增的 `invokeZcode` 里 `opts.userHome ?? os.homedir()`。
行为层面无分叉（默认值与各处相同、生产调用方无人传值），纯登记面；但 EV-83 想防的正是
「按清单改，只改一处让两套口径并行」，而清单自己漏项就是这个症状。
落点：EV-83 的位置清单改成 grep 锚形态（`adapters/zcode.ts` 内全部 `os.homedir()` 字面 +
`probes/zcode.ts` 的 `ZCODE_CLI_DIR` / 入口候选），不再人工枚举。

## 三、本轮暴露的编排器问题：解析降级不记原因（拟登记 EV-84）

`_meta` 下的 `review-codex-<run>.json` 在降级时**只有** `{ parse_fallback: true, raw }` 两个字段，
渲染件的降级横幅也只说「未能解析为结构化结论」。于是「为什么解析不了」这件事，
Driver 与人都只能自己把原文喂回 `parseReview` 才知道——我本轮就是这么查的，
而在查之前我已经先对用户说了一个**错误的**成因（「围栏」）。

手动复跑的实测结论（两轮成因**不同**，都不是围栏——`fence` 档提取本来就支持）：

| 轮次 | 候选提取 | 真实成因 |
| :--- | :--- | :--- |
| r3 | 1 个，`fence` | 5 条 findings **全缺必填的 `confidence`** |
| r4 | 1 个，`fence`，8041 字节 | `findings[2].layer = "test"`、`findings[4].layer = "doc"`，不在允许集 `requirement\|plan\|code\|rca` |

两轮都是审查员的 schema 符合性问题（且 r4 已按 r3 学会补 `confidence`，又撞上另一条约束），
**不是** `qwen3.8-flash` 输出质量崩坏——这一点也更正我在等待期间对用户说的「连续两轮降级说明这一档不行」。

拟登记 **EV-84**：`parseReview` 失败时把 `reason` 与 `errors` 落进 `_meta` 的 review JSON，
并在渲染件的降级横幅里摘要一两条。理由：降级会让该侧**失去阻断资格**（本轮共同阻断档位因此
连续两轮未执行），而失去资格的原因目前不可见——这正是 P5「不可伪装」要防的形态。
**本轮不实施**，登记后按主题排期；实施前需确认 schema 错误文本里不含被审内容片段（避免留痕夹带）。
