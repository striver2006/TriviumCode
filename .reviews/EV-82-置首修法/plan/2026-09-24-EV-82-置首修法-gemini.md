### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §4.1 与 src/trivium/guard.ts:858-864` |
| 类别 | contract ｜ 层次 plan |
| 置信度 | high |

**问题**：guard 模块与适配器之间存在数据流断层：计划要求 guard 在「置首生效仍判 false」时输出特定告警，但置首状态只保存在 trace.json 中，未进入 CriticResult 或 SideVerdict，guard 在运行时根本无从得知置首是否生效。

**依据**：被审计划 §3.4 声明「run.json 不加字段」、§4.1 声明「置首生效仍判 false 时，guard 的告警加一句『置首也没挡住…』」；但审查 src/trivium/types.ts:1502-1544 发现 CriticResult 仅包含 model_override_applied，src/trivium/guard.ts:858-864 仅能依据 s.modelOverrideApplied === false 判定，完全无法访问 trace.json 内的 reorder 字段。

**建议**：明确置首生效状态的跨模块传递机制：或者在 CriticResult/SideVerdict 中显式透传该状态，或者由适配器在 note 中合成相应上下文由既有通道透传，避免 guard 产生无依据的条件判断分支。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §4.2 表格与正文第 1 点` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：新事实 zcode.runtime_selection 的取值定义不互斥不穷尽：若未置首对照回落到非首位的其他模型而置首支生效，所有分支均不匹配；表格中将恒等排除在 null 之外与正文冲突，且会导致请求在首位时被严重误判为 honored。

**依据**：被审计划 §4.2 表格第 2 行将 reorder_needed 限定为「未置首对照 = 首位 ≠ 请求，置首支 = 请求」；表格第 4 行将 null 定义为「...或置首支 applied:false（恒等除外）」；而表格下方正文又写「请求恰在首位时两支不可分，记 null」。结合 src/trivium/probes/zcode.ts:835 的恒等返回逻辑，表格规则存在漏网与自相矛盾。

**建议**：将 reorder_needed 的判据泛化为「未置首对照 ≠ 请求 且 置首支 = 请求」以消除状态漏网；删除表格中针对恒等的除外说明，与正文对齐，明确规定请求恰在首位时一律记 null。
