## 3. 改动一：审查臂置首（M1）

### 3.1 函数搬到适配层（**r3 修正**：GLM-r2-02）

`reorderRequestedFirst` 与 `VariantOutcome` 从 `probes/zcode.ts` 搬到 `adapters/zcode.ts`；`probes/zcode.ts` 改为从适配层导入并**原名再导出**，现有用例与实验脚本不用改。
搬的目的是让审查臂与同形臂的置首走**同一个构造函数、同一个选项**，而不是两条代码路径各自保证行为一致。

**搬迁之外唯一的行为扩展**：`VariantOutcome` 增结构化成因

```ts
kind: 'applied' | 'identity' | 'not_movable' | 'qualify_failed'
```

| `kind` | 对应现有分支 |
| :--- | :--- |
| `applied` | 挪成功 |
| `identity` | 请求本就在两级首位 |
| `not_movable` | 找不到 provider / 成员、provider 键 trim 后重名、重建后仍不在首位（整数样键名） |
| `qualify_failed` | 请求模型限定失败，无从置首（同形臂现有的那一支） |

`reason` 保持纯人读，不参与任何判定。判定一律按 `kind` 做，不对文案做子串匹配。

### 3.2 `prepareZcodeHome` 的新选项

```ts
prepareZcodeHome(runDir, model, { srcConfig?, transformCopy?, requestedFirst?: boolean })
```

- 限定成功（`q.qualified !== null`）且 `requestedFirst` 为真时，在写 `model.main` 之后、`transformCopy` **之前**调 `reorderRequestedFirst`；
  `transformCopy` 收到的是置首后的对象，残余扫描面对的就是最终落盘的那份；
- 返回值 `ZcodeHomePrep` 增 `reorder: VariantOutcome | null`：没请求置首、或限定失败时为 `null`；
- **挪不动不中止**：`applied:false` 时照常写副本、照常拉起，`kind` 与 `reason` 记下原因。最常见的是 `identity`，此时本来就不需要挪；
- **缺省值**：`requestedFirst` 缺省为 `false`；不传该选项时输出与现在逐字相同（沿用第一段「不传时逐字相同」的用例锁）。

### 3.3 谁传什么（**r3 修正**：CODEX-04）

| 调用方 | `requestedFirst` | `variant` 从哪来 |
| :--- | :--- | :--- |
| 审查臂 `zcodeAdapter.run` | `true` | —（结论经 §3.4 的守卫通道与 trace.json 留下） |
| 同形臂 · 缺省（`variant` 不传或 `'as-is'`） | `false` | 同形臂**自行合成** `{ variant: 'as-is', applied: true, kind: 'applied' }`，与现状一致。这是 doctor 的原样支，继续供 `model_override_full_copy` 与 EV-94 ② 比对 |
| 同形臂 · `variant: 'requested-first'` | `true` | **唯一来源是 `prep.reorder`**（限定失败时由同形臂按 `kind: 'qualify_failed'` 合成）。这是 doctor 的置首支：审查臂的零配额替身，给 §4.2 新事实供数 |
| 白名单臂 | 不适用 | 白名单重建、不经 `prepareZcodeHome`；维持原判据，不置首 |

- **删除**同形臂 `transformCopy` 里的置首分支，置首统一走 `prepareZcodeHome({ requestedFirst })`。两处并存时，第二处必然走恒等分支，把如实的 `applied:true` 覆盖成 `false`；
- **doctor 拉起两支**：原样支 1 次（沿用现调用），置首支 1 次（新增，显式传 `variant: 'requested-first'`）。两支都零配额；
- `model_override_full_copy`、EV-94 ② 不一致告警、设计文档第 287 行的用途说明**只取原样支**，语义不变；
- 与第二段 r2 AGY-02「置首不进 doctor」的偏离：第二段置首只是观测变体；第三段它成了审查臂的行为，doctor 需要它的零配额替身。偏离只限「doctor 多拉起一支」，同形臂缺省不变。

### 3.4 写进留痕与交给守卫（**r3 修正**：GLM-r2-02、GLM-r2-03）

- `trace.json` 的 `modelSelection` 增 `reorder: { applied, kind, reason? }`（`reorder` 为 `null` 时不写）；
- 置首生效（`kind: 'applied'`）且 `model_override_applied: true` 时，`modelSelection.note` 追加「本次靠置首达成」；
- **守卫通道**：`CriticResult` 增可选字段 `model_override_reorder?: { applied: boolean; kind: …; reason?: string }`，由适配器从 `prep.reorder` 填；
  guard 的 `SideVerdict` 增 `modelOverrideReorder?`，原样透传后按 `kind` 判定（§4.1）；
- **加字段不等于进 run.json**：`review.ts` 不透传它，`run.v2` 不改。它只供 guard 当轮判定，持久留痕在 trace.json。
  由于 `run.v2` 的 `$defs.critic` 不拦多余字段（C8），这条边界用 §7.1 的负向用例与 §7.2 的变异锁住，不只靠实现纪律；
- 其它三家适配器与 stub 不产出该字段，缺席即「本侧无置首」。

## 4. 守卫口径 (a′)

**背景**（第二段 r2 §6，CODEX-03）：置首后，「副本默认被采信」与「回落到首项」得到同一个结果。
审查臂上 `model_override_applied: true` 从此只能说明「跑的就是请求模型」，说明不了「副本默认被采信」，这一维在审查臂上归零。

### 4.1 取舍与审查臂守卫（**r3 修正**：GLM-r2-02、CODEX-06）

- **(a) 条件置首**（先不置首跑，判 `false` 才置首重跑）：不取。当前版本下每次都会判 `false`，等于每次审查跑两遍，配额与耗时翻倍，第一遍的结论本来就要丢掉；
- **(b) 明说放弃这一维**：不取。代价是失去「当前 CLI 是否仍需置首」的持续信号，而它正是 M3 上游修复的结案信号；
- **(a′) 两层分开判**（本段采用）：
  - 审查臂守卫**只判结果**：`model_override_applied` 的含义收窄为「生效模型的 modelId 段 = 请求」，`decideModelOverride` 不改；
  - 「副本默认是否被采信」这一维移到 doctor，落新事实 `zcode.runtime_selection`（§4.2），零配额，每次 doctor 都重判；只播报、不阻断。

**guard 的 `false` 告警**：`modelOverrideReorder` **缺席**时维持现文（「对照 run.json 的 `model_requested` 与 `model_effective`」），不追加任何句子。
桩适配器与其它家都走这一支，不会指向一份不存在的 trace.json。
**在场**时，先追加「先看 trace.json 的 `modelSelection.reorder`」，再按 `kind` 追加一句：

| `kind` | 追加句 |
| :--- | :--- |
| `applied` | 置首已生效仍回落：CLI 的回落规则可能变了，先看 doctor 的 `zcode.runtime_selection` |
| `identity` | 请求本在首位，未做置首（不加推断） |
| `not_movable` / `qualify_failed` | 置首没做成：`<reason>` |

### 4.2 新事实 `zcode.runtime_selection`

**材料**：doctor 两支（原样支 `as`、置首支 `ro`）的运行期读数，只比 modelId 段，与请求 `req` 比。不引入「首位」，也不看配置层结论。
两支用同一个请求值（`pickNonFirstModel` 的结果）。

**按序判定，首命中即止**：

| 序 | 条件 | 值 |
| :-- | :--- | :--- |
| ① | 任一支运行期读数不是 `ok`；或置首支 `kind` 不是 `applied`（**全部成因，含 `identity`**）；或两支请求值不同 | `null` |
| ② | `as = req` 且 `ro = req` | `honored`：副本默认被采信，置首不再必需 |
| ③ | `as ≠ req` 且 `ro = req` | `reorder_needed`：当前形态（E2），置首在起作用 |
| ④ | `as ≠ req` 且 `ro ≠ req` | `reorder_ineffective`：置首也没挡住，审查臂的覆盖会失败 |
| ⑤ | `as = req` 且 `ro ≠ req` | `null`：两支冲突，不收录 |

- ②～⑤ 穷尽了两支读数与请求的四种组合；`as` 取到第三个模型值时落进 ③ 或 ④，不会漏网；
- `null` 一律**不覆盖旧值**，与 `model_override_full_copy` 同口径；
- 配置层状态不进本事实：原样支的配置层结论照旧由 `model_override_full_copy` 与 doctor note 播报；
- **类型与契约**：`types.ts` 的 `ZcodeProbe` 增可选字段 `runtime_selection?: 'honored' | 'reorder_needed' | 'reorder_ineffective' | null`（旧结论文件没有它，按「未探过」读）。
  `config.v2.json` 不改（`commonProbe` 为 `additionalProperties: true`），`run.v2` 不涉及；设计文档探针表新增一行；
- doctor note 按三值各一句，与现有的「运行期 ⚠️」对照合并，不重复出；
- preflight 只在 `reorder_ineffective` 时给一条警告（glm 侧的模型覆盖大概率不会生效），不拒跑。

## 8. 凭据面与风险

- 置首只调顺序。审查臂副本本来就含真实凭据（0600、跑完即删），凭据面不变；同形臂的凭据替换、结构兜底、残余扫描照旧。
  置首放在 `transformCopy` 之前，残余扫描看到的是最终落盘的那份；
- **依赖 CLI 行为**：置首依赖「回落取第一个可见 provider 的第一个模型」。CLI 升级改了规则时，审查臂守卫会判 `false` 并带「置首已生效仍回落」一句，
  doctor 同时给出 `reorder_ineffective`，两道都能看见；
- **多 provider 未验**（E5）：请求 provider 挪到首位后，若有别的规则（可见性、启用状态）让另一个 provider 排在前面，置首会失效。
  守卫能看见，但本段不在多 provider 副本源上实测；用户本机副本源只有一个 provider；
- `model.lite` 本来就写成请求模型，置首不改变它；
- 审查臂未建副本时日志落真实 `~/.zcode/cli/log`、不进清扫面：既有残余，见 §5。
