## 3. 改动一：审查臂置首（M1）

### 3.1 函数搬到适配层

`reorderRequestedFirst` 与 `VariantOutcome` 从 `probes/zcode.ts` 搬到 `adapters/zcode.ts`，行为逐字不变；
`probes/zcode.ts` 改为从适配层导入并**原名再导出**，现有用例与实验脚本不用改。

### 3.2 `prepareZcodeHome` 的新选项

```ts
prepareZcodeHome(runDir, model, { srcConfig?, transformCopy?, requestedFirst?: boolean })
```

- 限定成功（`q.qualified !== null`）且 `requestedFirst` 为真时，在写 `model.main` 之后、`transformCopy` 之前调 `reorderRequestedFirst`；
- 返回值 `ZcodeHomePrep` 增 `reorder: VariantOutcome | null`：没请求置首、或限定失败时为 `null`；
- **挪不动不中止**：`applied:false` 时照常写副本、照常拉起，原因进 `reorder.reason`。挪不动的常见情形是「请求本就在首位」（恒等），此时不需要挪；
- **缺省值**：`requestedFirst` 缺省为 `false`，`prepareZcodeHome` 不传该选项时输出与现在逐字相同（沿用第一段「不传时逐字相同」的用例锁）。

### 3.3 谁传什么

| 调用方 | `requestedFirst` | 理由 |
| :--- | :--- | :--- |
| 审查臂 `zcodeAdapter.run` | `true` | 修法本体 |
| 同形探针臂 · 缺省（doctor 跑的那一支） | `true` | **保持「与审查臂同形」**：审查臂改了，同形臂跟着改，才仍是审查臂的零配额替身 |
| 同形探针臂 · `variant: 'as-is'` | `false` | 变成**未置首对照**，给 §4 的新事实供数 |
| 白名单臂 | 不适用 | 白名单重建、不经 `prepareZcodeHome`；维持原判据，不置首 |

同形臂的 `variant` 选项语义随之改名：缺省由 `as-is` 变为 `requested-first`（与审查臂同形），`as-is` 仍可显式传。
这是第二段 r2 AGY-02「置首不进 doctor」的**有意偏离**：第二段置首只是观测变体，第三段它成了审查臂的行为，doctor 的同形臂要跟上。

### 3.4 写进留痕

- `trace.json` 的 `modelSelection` 增 `reorder: { applied, reason? }`（`reorder` 为 `null` 时不写）；
- 置首生效且 `model_override_applied: true` 时，`modelSelection.note` 追加「本次靠置首达成」；
- `run.json` 不加字段（守卫字段见 §4）。

## 4. 守卫口径（二选一，交双审定）

**背景**（第二段 r2 §6，CODEX-03）：置首后，「副本默认被采信」与「回落到首项」得到同一个结果，
审查臂上 `model_override_applied: true` 从此只能说明「跑的就是请求模型」，说明不了「副本默认被采信」——这一维在审查臂上归零。

### 4.1 候选

- **(a) r2 原案：条件置首**。先不置首跑，现守卫判 `false` 才置首重跑。**本稿不取**：当前版本下每次都会判 `false`，
  等于每次审查跑两遍，配额与耗时翻倍，而第一遍的结论本来就要丢掉。
- **(a′) 本稿推荐：两层分开判**。
  - 审查臂守卫**只判结果**：`model_override_applied` 的含义收窄为「生效模型的 modelId 段 = 请求」，`decideModelOverride` 不改；
    置首生效时 trace 注明「本次靠置首达成」；**置首生效仍判 `false` 时**，guard 的告警加一句「置首也没挡住：CLI 的回落规则可能变了」；
  - 「副本默认是否被采信」这一维**移到 doctor**：同形臂的未置首对照（`variant: 'as-is'`）与置首支各拉起一次，
    按运行期读数落一个新的探针事实 `zcode.runtime_selection`（见 4.2）。零配额，每次 doctor 都重判；
  - 新事实**只播报、不阻断**：preflight 在它为 `reorder_ineffective` 时给一条警告（glm 侧的模型覆盖大概率不会生效），不拒跑。
- **(b) 明说放弃这一维**：验收口径降为「跑的就是请求模型」，doctor 不加事实。代价：上游修好（或改坏）回落规则时，
  我们只能从「置首还有没有必要」这件事上看不出任何信号。

**推荐 (a′) 的理由**：代价只是 doctor 多拉起一次（零配额，几秒）；换来的是「当前 CLI 是否仍需置首」有持续的零成本观测，
正好也是 M3 上游修复的结案信号（`honored` 出现即说明上游已修，可以考虑撤掉置首）。

### 4.2 新事实 `zcode.runtime_selection`（仅 (a′)）

| 值 | 判据（同形臂两支的运行期读数，比 modelId 段） | 读法 |
| :--- | :--- | :--- |
| `honored` | 未置首对照 = 请求 | 副本默认被采信，置首不再必需 |
| `reorder_needed` | 未置首对照 = 首位 ≠ 请求，置首支 = 请求 | 当前形态（E2），置首在起作用 |
| `reorder_ineffective` | 置首支已生效但 ≠ 请求 | 回落规则变了，审查臂的覆盖会失败 |
| `null` | 任一支读数不是 `ok`，或置首支 `applied:false`（恒等除外），或配置层未判 `config_copy` | 本轮判不出，**不覆盖旧值**（与 `model_override_full_copy` 同口径） |

- 请求值用同一个非首位模型（`pickNonFirstModel`），两支相同；请求恰在首位时两支不可分，记 `null`；
- 写进 `ProbeSection` 的 `zcode` 段（可选字段，旧结论文件没有它按「未探过」读），类型、设计文档探针表、`run.v2` 不涉及（不进 run.json）；
- doctor note 按三值各一句；与现有「运行期 ⚠️」对照合并，不重复出。

## 5. 改动二：EV-110

- `ZCODE_LOG_DIR` 并入 `ZCODE_DIR_ENV_KEYS`（四键）。理由与 `ZCODE_DATA_BASE_DIR` 当初进清单同构：CLI 自写的文件（这里是日志）
  会落到副本 HOME 与清扫面之外；清掉它只会把日志拉回 `<HOME>/.zcode/cli/log`，方向 fail-safe；
- 删掉 `ZCODE_PROBE_EXTRA_CLEARED_ENV`（并入后多余），两条模型探针臂的展开随之去掉；实验脚本不受影响（它不引用该常量）；
- **影响面**（C5）：旗标探针、两条模型探针臂、审查臂、探活全部经 `ZCODE_DIR_ENV_KEYS` 清。旗标探针与探活若用真实 HOME，
  宿主预置时它们的日志从宿主目录改落 `~/.zcode/cli/log`——这是行为变化，在设计文档里写明；
- doctor 的宿主预置 ⚠️ 改为信息级 note：「宿主预置了 `ZCODE_LOG_DIR`，所有拉起路径都已清掉它」；
- 用例：审查臂在宿主预置时仍能从副本日志读到生效模型、宿主目录不被写；`ZCODE_DIR_ENV_KEYS` 集合断言改为四键。

## 8. 凭据面与风险

- 置首只调顺序，审查臂副本本来就含真实凭据（0600、跑完即删），凭据面不变；同形臂的凭据替换、结构兜底、残余扫描照旧，
  置首放在 `transformCopy` **之前**，残余扫描看到的是最终落盘的那份；
- **依赖 CLI 行为**：置首依赖「回落取第一个可见 provider 的第一个模型」。CLI 升级改了规则时，审查臂守卫会判 `false`，
  (a′) 下 doctor 同时给出 `reorder_ineffective`，两道都能看见；
- **多 provider 未验**（E5）：请求 provider 挪到首位后，若有别的规则（可见性、启用状态）让另一个 provider 排在前面，置首会失效；
  守卫能看见，但本段不在多 provider 副本源上实测。用户本机副本源只有一个 provider；
- `model.lite` 本来就写成请求模型，置首不改变它。
