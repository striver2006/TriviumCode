**结论**：`request-changes`

### GLM-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §4.2` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | medium |

**问题**：新事实 zcode.runtime_selection 的四值判据不穷尽、判序未定义。reorder_needed 要求「未置首对照 = 首位 ≠ 请求」：若未置首读数是第三模型（既非请求也非首位——多 provider 或选择规则再变时可能出现），两支读数都 ok、置首 applied:true、配置层 config_copy，四个值没有一个落得进，null 的三个条件也全命中不了，判据表没有兜底分支。同时 honored（未置首=请求）与 reorder_ineffective（置首支已生效但 ≠ 请求）的字面判据可以同时满足（未置首=请求而置首≠请求的形态），按哪条先判没有写。

**依据**：plan §4.2 表格；src/trivium/probes/zcode.ts:461-495（readRuntimeSelectedModel 只给出 ok/非 ok 与模型串，判据层拿到的是任意模型值，不保证落在「请求或首位」二选一里）

**建议**：把判据表改成按序判定的决策表（例如：未置首=请求 → honored；否则置首=请求 → reorder_needed；置首≠请求 → reorder_ineffective；两支不可比 → null），并写明「落不进任何一格一律记 null、不覆盖旧值」的兜底；或显式把「未置首 ≠ 首位 ≠ 请求」归进 null 条件。
