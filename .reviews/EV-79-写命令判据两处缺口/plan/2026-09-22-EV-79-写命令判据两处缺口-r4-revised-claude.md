## 2. 块内具名意见逐条裁决（8 条全部接受）

### 2.1 `CODEX-F01` 块内 6 条

#### CODEX-01 · major · 接受

**理由**：实测坐实，且这是 **r4 自己新引入的回归**，方向最坏（静默漏检）。
三条后果我逐条复核：

1. **第 1 格错了**。`glued === ''` 合并的是 `>` / `>>` / `&>` / `&>>` / `2>` / `2>>`，
   这些运算符**都没有 fd 语义**，下一 token 即使是纯数字或 `-` 也是文件名。
   基线实测：`echo x > 2` ⇒ **writes=1**、`echo x >> 2` ⇒ **writes=1**、`echo x > -` ⇒ **writes=1**
   （今天的正确检出），按 r4 的第 1 格实现后**全部降为双空**。
   shell 实测同向：zsh 下 `> 2` / `>> 2` / `&> 2` / `&>> 2` / `>>& 2` **都建出了名为 `2` 的文件**，
   只有 `>& 2` / `>& -` 不建文件。而 §4 没有任何用例钉住这一族（只覆盖了 `>& 2` / `>& -`）。
2. **第 3 格同形**。`>>&2` 与 `>&2` 的残留都是 `&2`，但前者是写名为 `2` 的文件、
   后者才是 fd 复制，按 r4 的等值判据前者会被误排除。
3. **焦点一的答复**：「描述符前缀完全退出判定」这个决定**本身没有漏掉前缀形态**，
   被一并丢掉的是**另一个判别位**——`&` 在 `>` 的哪一侧。

**根因**：四格表按「残留字符串空间」划分，作为划分它确实互斥且穷尽，
但 **fd 与文件的语义不是残留的单函数**，还取决于第 0 步匹配掉的运算符是哪一个。

**落点**：§3.1 的分界判据**换轴重写**——从「残留长什么样」改到「运算符形态是什么」，
方案见 §3；§4 补两条回归锁（`echo x > 2` / `echo x >> 2` 修后**仍进 writes**）；
§1.4.2 补「纯数字 / 减号作目标位」一族（现表只有 `>& 2`，没有 `> 2` 这一行，
所以这个方向根本没人看过）。

#### CODEX-03 · major · 接受

**理由**：实测坐实，**确有第四种拼写**。基线直调：
`echo secret >>& src/leak.txt` ⇒ writes=0 / suspected=0 / **reads=`["src/leak.txt"]`**

## 3. §3.1 的换轴方案（Driver 提出，**未经双审**）

CODEX-01 + AGY-01 + CODEX-03 三条指向同一个结构问题：**判别轴选错了**。
下面是我按它们的实测重新推的方案。

> **这是本轮 Driver 新提出的设计，没有经过任何一侧审查。**
> r5 稿要把它当**新方案**完整论证，不能因为它出现在裁决件里就当成已审过。

### 3.1 判别轴：运算符形态，不是残留

**实测出的语义边界**（zsh 5.9，全部已复现）：

| 运算符 | 语义 | 目标位是数字时 |
| :--- | :--- | :--- |
| `[n]>` / `[n]>>` | 普通文件重定向 | **文件**（`> 2` 建出文件 `2`） |
| `&>` / `&>>` | 双流文件重定向 | **文件**（`&> 2` 建出文件 `2`） |
| `[n]>>&` | 双流**追加**文件重定向（zsh） | **文件**（`>>& 2` 建出文件 `2`） |
| **`[n]>&`** | **唯一有 fd 语义的一族** | **fd 操作**（`>& 2` 不建文件；`>& -` 关闭 fd） |

即：**`&` 在 `>` 之前是「双流文件」，`&` 在单个 `>` 之后才是「fd 族」，
而 `&` 在 `>>` 之后仍是文件。**

### 3.2 建议的实现形态

把运算符整体吞掉（含 clobber 后缀），再按运算符分类：

```ts
// 运算符：可选 fd 数字或 &，然后 > 或 >>，然后可选 &，然后可选 clobber 后缀
const REDIRECT_RE = /^(?:&|[0-9]*)>>?&?[|!]?/;

const op = REDIRECT_RE.exec(t)?.[0];
const glued = t.slice(op.length);
// 唯一的 fd 族：[n]>& —— 单个 >、& 在其后、& 不在其前
const isFdOp = /^[0-9]*>&[|!]?$/.test(op);
```

| 情形 | 处置 | 例 |
| :--- | :--- | :--- |
| `isFdOp` 且 `glued` 恰为纯数字或 `-` | fd 操作，**排除** | `>&2`、`2>&1`、`>&-` |
| `isFdOp` 且 `glued` 非空且非数字非 `-` | 双流**文件**目标 | `>&src/leak.txt`、`2>&src/leak.txt`、`>&\|src/leak.txt` |
| `isFdOp` 且 `glued === ''` | 分离写法：取下一 token；**恰为纯数字或 `-` 则排除** | `>& 2` 排除、`>& src/leak.txt` 取目标 |
| 非 `isFdOp` 且 `glued !== ''` | **文件目标**（无条件） | `>out.txt`、`&>src/leak.txt`、`>>&2`（目标 `2`） |
| 非 `isFdOp` 且 `glued === ''` | 分离写法：取下一 token，**无条件**作目标 | `> 2`、`>> 2`、`&> 2`、`>>& 2` 全部是文件 |

**这个形态同时解决四条**：CODEX-01（第 1 格回归）、AGY-01（行为撕裂）、
CODEX-03 的 `>>&`（被运算符正则整体吞掉，落文件档，属**显式**覆盖）、
以及 clobber 族（`[|!]?` 吞掉后缀，`>&|file` 落双流文件档）。

**仍待 r5 论证的**：`>>&2` 紧贴形态的目标应是 `2` 还是 `&2`（我推是 `2`，
即非 fd 族且 glued 以 `&` 打头时要 `slice(1)`，但**这一格我没实测**）；
以及 `&>|` / `&>!` 的残留是否也需要同样处理。

### 6.3 glm 侧零产出的查证与三项处置（审批拒绝时用户点名要做）

**查证结论：不是临时故障，是该侧的能力边界，且它此前三轮的「实测」措辞不实。**

**（a）该侧从设计上不能执行任何命令。**
编排器拉起 zcode 时传两组只读参数（`adapters/zcode.ts:366-367`）：
`--mode plan` 与 `--disallowed-tools Write,Edit,MultiEdit,ApplyPatch,NotebookEdit,Bash,WebFetch,WebSearch`
（常量 `ZCODE_READONLY_DENYLIST`）。`Bash` 在 denylist 里是**必需项**，
代码注释写明原因：「`--mode plan` 挡不住命令执行（M0 实测）」——
真正拦住命令的是 denylist，不是 plan 模式。**这是只读保障的一部分，不是 bug。**

**（b）本轮零产出的触发点是焦点措辞。**
前三轮该侧照常交卷；本轮焦点二明写「**请独立复测不要采信本表**」，
它发现做不到，于是走 zcode 的 plan-mode 协议「提交计划请求放行」。
而编排器是**一次性调用**，没有第二回合批准它的计划，输出就停在那句请求上。
这是 zcode 交互模型与编排器单次调用的不兼容。

**（c）更要紧的发现：该侧三轮 `run_command` 全为 0，而结论里反复出现「实测」措辞。**

| 轮次 | read | grep | `run_command` | 结论中的措辞 |
| :--- | :--- | :--- | :--- | :--- |
| r1 | 13 | 6 | **0** | 「在 bf3342b 的 dist/test 真模块与内存副本上**对照实测**…逐命令对账 0 不一致」 |
| r3 | 20 | 2 | **0** | 「**本轮双 shell 实测**（/bin/zsh 5.9、/bin/bash 3.2，目标全用 /dev/null，无落盘）」 |
| r4 | 16 | 5 | **0** | （本轮诚实停下，未产出结论） |

一条命令都没跑过，这些措辞**不成立**。有一处可直接证伪：
r3 该侧称「bash 3.2 默认模式 `2>&/dev/null` 同样 rc=0，报 ambiguous redirect 的只有 `--posix`」，
而 Driver 实测 bash 3.2 默认模式就是 `ambiguous redirect` rc=1 —— **它推错了**。
zsh 那半它推对了（Driver 复测确认），但那是**推理不是实测**。

**对照另两侧**：codex 的 `run_command` 是 24～33，它真在跑（`-s read-only` 沙箱允许只读命令）；
gemini 的 `run_command` 同样是 0（工具面只有 `Read,Grep,Glob`），
**但它从不声称实测**，一律写「查阅 src/…」。所以措辞问题只在 glm 一侧。

**三项处置**：

1. **本裁决件**：`GLM-F01` 的裁决理由已改写为上述成因（原写「工具侧故障」，不准确）。
2. **落 BACKLOG 一条**（与 §4 清单的四条新残余一并落）：
   「glm 侧无命令执行能力（denylist 含 Bash）却在结论中使用『实测 / 复测 / 直调』措辞，
   属结论可信度问题。出路二选一：在该侧任务书里明确约束措辞，
   或让编排器在某侧 `run_command === 0` 时对这类措辞给出结构告警。」
   这条**不属本主题范围**，只登记。
3. **更正 r3 裁决件的一处失实表述**：该件 GLM-01 的裁决理由写的是
   「glm 的 zsh **实测**对、bash 描述错」，准确说法应是
   「zsh **推理**对、bash 推理错，**两者都不是实测**」。
   当时 Driver 自己的复测是真的，故结论未受影响，但裁决理由里那句话失实。
