### GLM-01 · 重要 —— 接受

### GLM-02 · 次要 —— 接受

（**接受的是问题**：审计面确实少了一份。**建议的修法不采纳**，理由见下；
落点改为文档明示边界 + 应答件列出该文件。）

**核实**：事实成立。本轮实际改动 15 份文件，被审补丁 `files: 14`，
差的是 `.reviews/README.md`（我确认它已改且内容与主张相符）。

**但成因是刻意设计，不是缺陷**。`code-stage.ts:96-108` 的注释写得很清楚：

> 归档根尤其关键：`.reviews/` 是刻意纳入版本管理的，对方的审查产出刚落盘还没 commit 时
> 处于未跟踪状态，若被收进补丁就会经**被审对象本身**递给审查员——
> BRIEF 禁读清单、CLI 路径 deny、事后轨迹核验三道全被绕过。

且该行为**早已写进规范**：设计 9.2 的 code 阶段行「无条件剔除 `.reviews/` `.trivium/` `.git/`」、
PROTOCOL 第 86 行「补丁**无条件剔除**归档根……与 `.gitignore` 写了什么无关」。

**驳回其建议修法的理由**：glm 建议「改为排除运行产物目录、保留对已跟踪文件的修改」。
这会把一个 **fail-closed** 的隔离边界，改成**需要按跟踪状态区分安全与否**的 fail-open。
本项目在这个方向上栽过两次并都已撤回（RV-B1、v1.2.7 的 Bash 侧收窄），
教训逐字同构：**判定一旦从「一律排除」变成「满足某些条件才排除」，
就需要穷举「哪些条件下不安全」，而那个集合穷举不完。**
具体到这里：跟踪状态是可变的（`git add` 一下就变），把它当安全边界等于把边界交给攻击面。

代价是「审计面比实际变更集少一份」，而这个代价有**零成本出口**：在应答件里如实列出来。

**落点**：

1. 主设计 9.2 的 code 阶段行补一句**审计面边界**的明示：
   「因此**被审补丁不等于本轮全部改动**——归档根内对已跟踪文件的修改不在补丁中，
   需由 Driver 在应答件中显式列出供人工复核。这是隔离优先于审计完整性的**刻意取舍**。」
