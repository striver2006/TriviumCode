## 2. 规范链裁定（本轮的三条核心决策）

### D-1 · 规范关系：主设计仍是唯一准绳，演进设计定稿为「受控增量规范」

**问题**：负责人裁定「演进设计定稿升版，完成回溯后它才成为实现依据」。
若直接把两份都叫「实现依据」，就正好落进它自己禁止的「两套规范并行」。

**裁定**：

```
主设计（v1.3.0）  = 唯一实现依据（准绳）。任何冲突以它为准。
演进设计（v1.0.0）= 已批准的演进增量规范，主设计的**受控附件**。
                    其规范效力由主设计 §16.1 里程碑表与 §24 台账**逐条显式授予**，
                    不自带效力；条款并入主设计正文后，以主设计文字为准，
                    演进设计对应章节标注「已并入主设计 §x（v1.x.y）」。
```

这样全仓仍是**一条**规范链：主设计 →（显式指针）→ 演进设计受控条款。
读者永远从主设计入口，不会出现「该信哪份」。

**为什么不把演进设计全文并进主设计**：它有大量调研过程、置信度标注、备选路线留档与风险论证，
这些是**论证材料**不是规范；全量并入会让主设计从 1909 行膨胀到 2600 行以上，且把
「以 M6 探针为准」的未定事实写成规范条款，直接违反 P7。

### D-2 · 纪律 1 的颗粒度：不改写纪律，改正它的适用单位（焦点一的答案）

**纪律 1 原文**（主设计 §16.2）：

> 任何与第 3 章记载不一致的实测结果，改适配层，不改外部产品，也不改本文的验收口径
> （本文相应事实条目需回补修订）。

以及文档头「后续任何与本文不一致的**改动**，仍须先回溯修订本文」，
§18.2 尾「后续实现若采用与本文不同的命名或平台口径，必须先回溯修订 PRD 与本文」。

**三处措辞的触发条件一致：都是「不一致的改动」，不是「计划存在」。**
因此演进设计头部那句「实施前须回溯修订主设计与 PRD」，
本轮明确解读为「**每个里程碑的实施前**」，而非「整个演进开工前一次性写完 M6～M11 的全部细则」。

三条依据：

1. **字面依据**：纪律 1 的对象是改动，未实施的里程碑不构成与主设计不一致的改动。
2. **原则依据**：M6 未跑时把 3.6 / 3.7 事实表写进主设计，等于把「待探针钉死」的推定
   写成规范条目，直接违反 P7（「实现代码只读探针结论，不得把文档命令行硬编码进代码」）。
   主设计是验收口径的来源，写进去就会被照着实现和验收。
3. **先例依据**：M0 的探针结论正是「先登记里程碑、实测后回填（v1.2.1）」这个节奏落地的，
   §16.1 的「状态」列就是为此存在的。本轮沿用既有做法，不发明新规则。

**落地形式**（不动纪律 1 的文字，在其下增补一条纪律 6）：

> 6. **回溯修订的颗粒度是里程碑**：跨里程碑的演进方向、术语、契约骨架与路线图在立项时
>    一次性登记进本文（含状态标记）；需要实测或实现才能定稿的细则，在**其所属里程碑开工前**
>    并入本文正文并升次版本。每个里程碑的完成判据须包含「本里程碑的回溯条目已并入」。
>    未并入的条款以「待实施 · M<n>，细则见演进设计 §x」的指针行占位，正文不得写成既成事实。

**给焦点一的直接回答**：既不延后（方向与骨架本轮必须落，否则 M7b 无依据开工），
也不改写纪律（纪律本身没错，错的是把「实施」读成了「整个演进的实施」）。

### D-3 · 状态标记制度（焦点二的答案）

> 本文正文凡**未加状态标记**的条目，均为 M0～M5 已实现基线（2026-09-11 定稿，`npm run check` 712 例全绿）。

## 5. 五处设计文字修订的具体落法（焦点四）

### 5.1 修订① stdout → stderr（演进设计第 573 行）

```
原：…（critics.*→agents.*、profiles 裸 slug 包装为 {model: slug}、allow_single_flag→allow_partial_flag），stdout 告警一次；
改：…，**stderr 告警一次（每次 CLI 调用最多一次，派生 worker 各自一次，不引入跨进程状态）**；
```

理由随行标注：`cli.ts:559` 在 `--json` 模式下 `process.stdout.write(JSON.stringify(...))`，
`util/log.ts` 的铁律是 stdout 只允许单个 JSON、`warn` 恒走 stderr；写 stdout 会破坏 Hook 的 JSON 协议输出。

### 5.2 修订② 措施 b / AC-N6 / `peer_leak_via_command` 改指派

- §14 M7 行完成判据**删去**「命令文本伪造命中作废（AC-N6）」；M7 内容列删去「措施 b」（措施 a 保留）；
- §8.2 措施 b 段首加标注：**【独立演进项 · 未排期】**，并指向 ADR-002 与 BACKLOG 登记；
- §6.2 run.v2 行的 `peer_leak_via_command` 标注「**schema 可选字段**，随独立演进项接线」；
- §13.2 AC-N6 拆为 AC-N6a（`_meta` / `~/.trivium` 路径通道，随 M7b 的措施 a）与
  AC-N6b（命令文本通道，随独立演进项）。

> 拆 AC 是我加的一步，裁决件只说「移出」。理由：AC-N6 原文把路径通道与命令文本通道写在同一条里，
> 整条移出会把措施 a 的验收一并带走，而措施 a 是 M7b 要做的。**请审查员重点核这一步是否越界。**

### 5.3 修订③ run.v2 四字段分期

§6.2 run.v2 行内加注：`effort_requested` / `effort_effective` / `tier_source` / `profile`
四字段 **schema 定义为可选，M7b 不写入，M11 随档位全链路接线**；
§5.4 第 277 行的「增记」表述同步改为「M11 起增记」。

### 5.4 修订④ profiles `{tier}` 形态

§11 配置示例（第 562～565 行）**保留 `{tier}` 形态不变**（它是 M11 的目标形态），
但在示例上方新增一段分期说明：

> **分期取舍**：M7b 的 `config.v2` schema **只接受裸 slug**，不接受本示例中的 `{tier}` / `{model, effort}` 形态。
> 理由：`config.v1.json:382` 现只收裸 slug，`review.ts:441` 拿不到模型即退 69——
> 接受一个 schema 层合法、运行期必然失败的形态，正是本项目反对的「schema 允许但运行时不可用」。
> 本示例的完整形态在 **M11** 随档位全链路一并生效。

选「保留示例 + 加分期说明」而非「改示例为裸 slug」：示例是目标态的表达，改了 M11 还得改回来；
而用户按示例写出的配置在 M7b 会被 schema 拒绝——**拒绝是安全的**（预检即报错），
不是运行期静默失败。分期说明就在示例旁边，看不到的概率很低。

### 5.5 修订⑤ v1 读侧映射补 verify 分支

§6.2 run.v2 行的读侧规则改为分阶段表述（照抄裁决件 AGY-01 的落点块）：

```
审查阶段（plan/code/bug）：run.v1 → v1 校验器后映射为内存 v2 形状；run.v2 → v2 校验器；其余 → 不可读
verify 阶段：           verify-run.v1 → 照常可读；run.v1 → 照常可读且**不施加审查元数据契约校验**
                        （archive.ts:431 注释所载的历史形状）；其余 → 不可读
```

并加一句根因注记：**这不是宽容，是按写入时的规范解读留痕**。
实测依据：归档 26 份 `run-*.json` 中命中 5 份（4× `verify-run.v1` + 1× verify 目录下的 `run.v1`），
