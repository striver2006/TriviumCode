## 2. 设计

### 2.1 能力字段：挂 `CriticAdapter`，与 `TraceCapability` 并列，不并进去

```ts
// adapters/base.ts
/** 该侧审查员能否执行命令（EV-95）。不是轨迹形状：今天碰巧 command-trace ⇔ readonly-shell，但两者独立 */
export type CommandExecution = 'none' | 'readonly-shell';

export interface CriticAdapter {
  readonly critic: CriticId;
  readonly capability: TraceCapability;
  /** 该侧能否执行命令——任务书第 7 节据此二选一（设计 §9.4 第 7 条）；与工具面事实源的对账见 command-execution-parity 用例 */
  readonly commandExecution: CommandExecution;
  …
}
```

**为什么不并进 `TraceCapability`**：

1. 语义不同。`TraceCapability` 回答「这一侧的**轨迹**长什么样、判定层怎么分档」（六个消费点全在 `guard`）；命令执行能力回答「这一侧的**审查员**能做什么」，消费方是任务书。并进去，判定层的类型就多了一个它不该读的字段；
2. 并进去就得改那两个共享常量。三家共用 `TOOL_TRACE_CAPABILITY` 一个对象，在常量里加 `commandExecution: 'none'` 等于**按轨迹形状批发**能力——正是决策一说的「不从轨迹形状推导」。要各自声明，就得把常量拆成 `{ ...TOOL_TRACE_CAPABILITY, commandExecution: 'none' }`，常量的类型也随之变成 `Omit<…>`，`doctor.capabilityParity` 的入参类型连带变动，牵动面比并列一个字段大，换来的只是名字上的「同一个对象」；
3. 并列字段是**必填**的 `readonly`：漏声明的适配器编不过（`tsc --noEmit` 即红），不靠缺省值兜底。缺省值本身就是一次推导。

取值只有两个：`none`（只能读文件与检索）、`readonly-shell`（能执行命令、受只读沙箱约束）。不预留 `shell`（可写 shell）——任何一家能写都已违反只读保障，不该有一个合法取值来表达它。
