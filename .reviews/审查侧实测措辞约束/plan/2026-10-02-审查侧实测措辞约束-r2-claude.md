## 2. 设计

### 2.1 能力字段：挂 `CriticAdapter`，与 `TraceCapability` 并列，不并进去

```ts
// adapters/base.ts
/** 该侧审查员能否执行命令（EV-95）。不是轨迹形状：今天碰巧 command-trace ⇔ readonly-shell，但两者独立 */
export type CommandExecution = 'none' | 'readonly-shell';

export interface CriticAdapter {
  readonly critic: CriticId;
  readonly capability: TraceCapability;
  /** 该侧能否执行命令——任务书第 7 节据此二选一（设计 §9.4 第 7 条）；与工具面事实源的对账见 command-execution-parity 用例 */
  readonly commandExecution: CommandExecution;
  …
}
```

**为什么不并进 `TraceCapability`**：

1. 语义不同。`TraceCapability` 回答「这一侧的**轨迹**长什么样、判定层怎么分档」（六个消费点全在 `guard`）；命令执行能力回答「这一侧的**审查员**能做什么」，消费方是任务书。并进去，判定层的类型就多了一个它不该读的字段；
2. 并进去就得改那两个共享常量。三家共用 `TOOL_TRACE_CAPABILITY` 一个对象，在常量里加 `commandExecution: 'none'` 等于**按轨迹形状批发**能力——正是决策一说的「不从轨迹形状推导」。要各自声明，就得把常量拆成 `{ ...TOOL_TRACE_CAPABILITY, commandExecution: 'none' }`，常量的类型也随之变成 `Omit<…>`，`doctor.capabilityParity` 的入参类型连带变动，牵动面比并列一个字段大，换来的只是名字上的「同一个对象」；
3. 并列字段是**必填**的 `readonly`：漏声明的适配器编不过（`tsc --noEmit` 即红），不靠缺省值兜底。缺省值本身就是一次推导。

取值只有两个：`none`（只能读文件与检索）、`readonly-shell`（能执行命令、受只读沙箱约束）。不预留 `shell`（可写 shell）——任何一家能写都已违反只读保障，不该有一个合法取值来表达它。

### 2.2 五处声明

| 适配器 | 声明 | 依据（写进声明处的注释） |
| :-- | :-- | :-- |
| `agy.ts`（gemini） | `'none'` | `trivium-critic.md` 的 `tools:` 不含 `run_command` |
| `zcode.ts`（glm） | `'none'` | `ZCODE_READONLY_DENYLIST` 含 `Bash` |
| `claude.ts` | `'none'` | `READONLY_INVARIANTS` 的工具白名单是 `Read,Grep,Glob` |
| `codex.ts` | `'readonly-shell'` | `CODEX_READONLY_INVARIANTS` = `-s read-only` |
| `stub.ts` | 缺省按 `spec.mode`：`command_trace` ⇒ `'readonly-shell'`，其余 ⇒ `'none'`；`StubSpec` 新增可选 `commandExecution` 显式覆盖 | 见下 |

**桩为什么有缺省、又要能覆盖**：桩是「可配置的侧」（`stub.ts:351-357` 的既有说法）。缺省让两种形态分别模拟今天的 codex 与 agy/zcode，既有集成用例（`command-trace.test.ts` 等）不用改配置；显式覆盖让「`tool-trace` + `readonly-shell`」「`command-trace` + `none`」这两种**今天没有真实侧、将来可能出现**的组合能在集成测试里被走到——这是证明「渲染跟的是 `commandExecution` 而不是 `traceShape`」的唯一机器判据（与 r2 把 `capability` 挂适配器的理由同构）。桩的缺省是**桩自己**的约定，不是对真实适配器的推导；对账用例不覆盖桩。

### 2.3 渲染接线

- `BriefInput` 新增**必填** `commandExecution: CommandExecution`（不给缺省：漏传编不过）；
- `review.ts` 调用点（`:906`）传 `adapters[critic]!.commandExecution`——`:646-664` 已对每个入选侧判过非空，这里的 `!` 有前置保证；不另起一份「按侧名查表」；
- `brief.ts` 只按取值选文案，不按侧名、不按厂商、不看 `capability`。`registry-parity` 用例对 `brief.ts` 的「不得出现具体 Agent id 字面量」约束不受影响。

### 2.4 第 7 节的两种说法（原文）

第 7 节既有五条一字不动，在第三条（「**必须**填写 `not_covered`……」）之后插入按能力渲染的条目——放在 `not_covered` 那条后面，是因为 `none` 说法要引用它。

`none`（两条）：

> - **你这一侧没有执行命令的能力**，只能读文件与检索。不要用「实测」「复测」「直调」「跑了」「执行结果」一类说法描述你的判断；需要运行才能确认的结论写明是推理，并在 `not_covered` 里列出没能验证的部分。
> - 第 2 节的焦点若要求实测或复测而你做不到，如实说明后照常交付结论，**不要停下来等放行**。

`readonly-shell`（一条）：

> - 你这一侧可以执行只读命令。凡写「实测」「复测」的判断，`evidence` 里写出你本轮实际执行的命令；没执行、靠推理得出的写明是推理。

与决策二原文的差异只有一处：「第 2 段」写成「第 2 节」——任务书正文自称各段为「节」（`brief.ts:232`「请按第 5 节的审查镜头」），保持同一称呼，避免审查员以为是两套编号。

`none` 第一条与第 6 节 zcode 专属行（不要调用 ExitPlanMode）互补、不重复：后者管收尾形态，本条管诱因。两句都留。

### 2.5 不改的东西逐一点名

第 1 节、第 2～6 节、第 8 节逐字不变；第 7 节既有五条逐字不变、顺序不变；`lenses.yaml`、`prompts/`、`trivium-critic.md` 正文、`TraceCapability` 两个常量、`doctor.capabilityParity`、`guard.ts` 不动。改前改后任务书对照（§3.1 ④）机器核对这一条。
