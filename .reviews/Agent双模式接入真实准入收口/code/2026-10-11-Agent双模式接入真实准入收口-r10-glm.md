### GLM-01 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `scripts/agent-access-closeout.mjs:282-284` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：新增的 catch 失败留痕链自身没有兜底，且取证不对称：(1) catch 内先执行 save('failure.json', ...) 再 throw error，若 save 自身抛错（saveEvidence 的 scanSecrets 拒绝落盘、或 out 目录 IO 失败，见 scripts/agent-access-evidence.mjs:6-10），新异常会从 catch 块直接冒出，原始错误被完全替换且无 cause 链，failure.json 两头皆空——而这条链路正是为罕见失败路径的可见性而加的；(2) failure.json 只记录 write_contract_after，不记录 readme_after，read 臂失败时读取采样丢失；且 writeContractAfter 为 null 时无法区分「合同未创建」与「已创建但采样前失败」；(3) try 之外的预检段（selection/版本/指纹校验，第 56-118 行）与夹具创建段（第 119-124 行，fx 与 scratch 在 try 外）失败仍无 failure.json，后者的 mkdtemp 失败还会跳过 finally 清理造成夹具残留（该窗口是既有结构，本轮未顺手收口）。这些只影响失败路径的取证可见性与排障，不影响准入判定面（失败本就不通过）。

**依据**：scripts/agent-access-closeout.mjs:282-284 的 catch 块为 save('failure.json', { failed: true, name: ..., message: ..., write_contract_after: writeContractAfter ?? null }); throw error;，save 定义于同文件第 55 行指向 saveEvidence；scripts/agent-access-evidence.mjs:6-10 的 saveEvidence 在 scanSecrets 命中时 throw '脱敏扫描失败，拒绝落盘'，writeFileSync 亦可能 IO 失败；同文件第 257 行 readmeAfter 仅在成功路径进入 result.json/fixture-after.json。

**建议**：catch 内用内层 try/catch 包住 save('failure.json')，保证任何情况下原始 error 优先冒泡（内层失败最多记 console 警示）；failure.json 补 readme_after 字段并在合同场景区分「未创建/已创建未采样」；或至少在注释中写明预检段失败不留痕与 fx/scratch 位于 try 外是既定取舍。
