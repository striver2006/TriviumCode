### AGY-01 顺出了一条比它本身严重得多的缺陷

gemini 断言「白名单漏删 `init.ts`，守卫用例**必然断言失败**」。
我先复跑实测：`npm run check` **772/772 全绿**，该用例通过。结论与实跑不符，本该到此为止。

但我去查了**为什么**它没失败——`init.ts` 里到底哪一行还在命中。查出来的东西让整条意见改变了性质：

**我的注释剥离器把字符串字面量里的 `/*` 当成了块注释开头。**

`init.ts` 有一行 `'.claude/*',`（`.gitignore` 白名单写法）。`/\*[\s\S]*?\*\//g` 见到其中的 `/*`
就开始吃，一直吃到下一个 `*/`——**整整吞掉 32 行真实代码**。
残留的片段 `'.claude` 末尾没有路径分隔符，于是命中属性访问模式，
`init.ts` 被判成「仍需要」，守卫因此变绿。

**gemini 的结论是对的（`init.ts` 确已无真硬编码），但机制完全不是它说的那样，
而真正的问题也不是「漏删一条」。** 这个 bug 有两个后果，一个比一个重：

**后果一：扫描器本身有漏报洞。** 全仓实测 **7 个文件**的字符串里含 `/*`
（`config.ts` 10 次、`freeze.ts`/`hooks.ts`/`init.ts`/`selftest.ts`/`util/exec.ts`/`util/git.ts` 各 1 次）。
每一处都会让后续一段代码对扫描器**隐形**。这不是新引入的——
`/\*[\s\S]*?\*\//g` 是 M7a 那个带引号扫描器就在用的，**我只是照抄了它**。
也就是说「白名单外无字面量」这个结论，从 M7a 起就带着这个洞。

**后果二：我据此删错了一条白名单。** 我用同一个坏剥离器判定「过期」，
把 **`config.ts` 删掉了**——而它实际有 **8 处**真硬编码
（v1 配置默认值里的 `gemini: {…}` / `glm: { vendor: …, entry: …, max_turns: 40 }`、
`glm: { plan: 'GLM-5.3', … }`），全被吞在那 10 个 `/*` 后面。
**我亲手把一个本该受监控的文件移出了监控**，还在上一条消息里把「白名单从 20 条收敛到 10 条」
当成本步的成绩报了出来。

用修好的状态机剥离器复核全部 10 条删除：**9 条删对了，`config.ts` 这条删错了。**

这件事的教训比它的修法重要：**我为了查「白名单有没有过期条目」造了一件工具，
却没有验证工具本身。** 而这轮我自己刚在扫描器的误报/漏报边界上栽过一次
（加点号排除治误报、造出漏报），当时把「宁可误报、不可漏报」写进了注释——
**写下了，然后在同一个文件里用一个会漏报的剥离器把结论建了起来。**

## 1. 逐条应答

### AGY-01 · 重要 —— 接受（修法与意见所述不同）

**核实**：见 §0。三点实测——

1. 守卫用例**当前通过**（772/772），意见所述「必然断言失败」不成立；
2. 未失败的原因是剥离器 bug 造出的假命中，`init.ts` 在正确剥离下**确实过期**；
3. 同一 bug 让我**误删 `config.ts`**（实有 8 处真硬编码）。

**修改方案**（三件，缺一不可）：

```
① 剥离器改为引号感知的状态机：逐字符扫描，进入 ' " ` 后到闭合前不识别注释起始，
   处理转义；块注释按行保留换行，维持行号对齐。
② 白名单：删 init.ts（真过期），补回 config.ts（v1 配置的厂商专属默认段，M7b 第 4 步收敛）。
③ 负例锁死：构造一个「字符串里含 /* 且其后有真硬编码」的夹具，
   断言扫描器**能**发现那处硬编码——即剥离器不再吞代码。
```

第 ③ 件是关键。只修 ①② 的话，下次有人把剥离器改回正则、测试依然全绿，
而这正是本条揭示的失败模式：**工具自身没有守卫时，用它得出的结论一律不可信。**

### AGY-02 · 次要 —— 接受

**核实**：属实。`propPattern` 要前置点号、`keyPattern` 要后置 `:` / `?`，
而 `{ gemini, glm }` 与 `const { gemini } = reviews` 两者皆无。

**修改方案**：补第三个模式匹配简写形态。
边界照 GLM-03 的提醒把握：**只加能明确判定的形态，不追全覆盖**。

### AGY-03 ≡ GLM-01 · 次要 —— 接受

**核实**：属实。`divergence.test.ts` 全文 155 行，`import` 里没有 `measureAllPairs`。
glm 给的判据可直接当验收：**把双重循环改回写死一对，n=2 输入下除 `report.test.ts`
的 length 断言外依旧全绿**——也就是说本步的核心交付几乎没有防回退锚点。

glm 另有一句说服了我：计划 §6 把三审用例排在第 6 步（桩夹具），
但 `measureAllPairs` 是**纯函数**，当下即可单测，不必等夹具。这条我原先按计划的分期理解错了——
分期是给**集成**用例的，不是给纯函数单测的。

**修改方案**：`divergence.test.ts` 补四例——三侧齐备 → 3 对；一侧 null → **恰好 2 对**
（能同时排除「漏跳」与「整体放弃」两种错法）；单侧 → 0 对；逐对校验 `a`/`b` 身份传播。

### AGY-04 ≡ GLM-02 · 次要 —— 接受

**核实**：属实。`checkStageArtifacts` 在测试中共 14 处调用，全部不传 `critics`；
两个集成用例（`bug-stage` / `gate-loop`）都是双侧轮次、无 `--only`。

**修改方案**：`archive.test.ts` 补**正负成对**的窄测——
单侧轮次传 `roundCritics` 时不报缺件、不传时报缺件。
成对写是有意的：只写正例的话，把实现改成「永远不报缺件」也能过。

### GLM-03 · 次要 —— 接受

**核实**：属实。三类盲区我逐一验过：`仅 gemini `（散文）、
`!/claude/i.test(model)`（`adapters/base.ts` 的正则字面量，且该文件不在白名单）、
USAGE 模板串里的 `--model-gemini` / `--only gemini|glm`。三者都不命中任何模式。

**最该认的是注释口径**：我在注释里把「`divergence.ts` 的『仅 gemini / 仅 glm』文案」
写成了新扫描覆盖的对象——**它不是**。那处是我重构成 `${d.a} × ${d.b}` 顺手修掉的，
对账并没有守住它。举例举错，会让后来者高估这道对账的覆盖面。

**修改方案**：注释显式列出不覆盖的形态并撤回该举例。
**不加散文模式**——采纳 glm 的判断：追全覆盖会滑向误报海洋，
而误报的代价是每次都要有人去判断要不要加白名单，那反过来会稀释白名单的严肃性。

### AGY-05 · 吹毛求疵 —— 接受

**核实**：属实，计划第 289 行明写「六件套，不是五件套（第一稿漏了模型路由）」。
我在新建文件时按脑子里的旧印象写了「五件套」。

**修改方案**：`adapters/index.ts` 的报错文案与注释统一为「六件套」。

### GLM-04 · 吹毛求疵 —— 接受

**核实**：属实，三处术语各不相同（演进设计「多审退化」/ 主设计「双审退化」/ 实现「审查退化」）。

**选「多审退化」而不是我自造的「审查退化」**：演进设计 v1.0.0 已定稿并写明
「文档层面统称**多审**」（主设计第 0 章术语表同），我另造第三个词属于无依据的偏离。
这正是刚立的纪律要防的——**实现与已定稿的规范不一致时，先回补规范或改实现，
不能悄悄引入第三种说法**。

**修改方案**：实现全链统一到「多审退化」；主设计 §9.3 与 `LLD_orchestrator.md:99`
的「双审退化」按纪律回补（主设计升补丁版本）。

### GLM-05 · 吹毛求疵 —— 接受

**核实**：属实。`--check-artifacts` 分支在本轮之前不读 `run-id`，是我新增的能力，USAGE 没跟上。

**修改方案**：USAGE 补 `[--run-id <id>]`；并按 `AGENTS.md` 的同步清单核对
PROTOCOL 与 SKILL.md 是否需要同句（该清单点名「CLI 参数或退出码」要三处同步）。

## 2. 两侧共同确认、无需改动的部分

四个焦点两侧独立核实后均判成立：

- **接线守卫恰当**。glm 逐一核对了 `report`/`gate`/`doctor`/`status`/`verify`/`preflight`/`topic`/`approve`
  的调用链**均不经过** `realAdapters()`，正常只读路径零误伤；失败点在可用性检查、送审包冻结
  与任何配额消耗**之前**；错误文案给出两条出路且点名 `display` 名；
  经 `main` 兜底退 1 而非 69/64，与「源码级配置错误 = 程序缺陷」的定性相称。
  另确认守卫与桩机制的相互作用正确：`resolveAdapters` 以 real 表为底逐 id 替换，
  `TRIVIUM_STUB_CRITIC` **不会绕过守卫**——配置错误在测试里也该炸。
- **分歧度逐对化无遗漏消费点**。全仓 grep 确认旧单数字段的全部消费方都已迁移；
  两侧时与旧行为逐字段等价；论域取 run.json 的 `meta.critics` 而非当前启用集合，
  对历史轮次复盘是正确取向。
- **`report --json` 形状变更可接受**：报告输出无 JSON Schema 契约（四份 schema 是
  config/review/disposition/run），仓内 skills 与文档不解析报告字段。
- **「只排路径分隔符」的边界划对了**：再排点号会把 `cfg.critics.<id>` 这类最常见真阳性全数漏网，
  为治误报造出更糟的漏报；误报有零成本出口。
- **无越界**：diff 逐项对应计划第 2 步欠账清单，未触碰 schema / config v2 / `--critics` / run.v2 / 桩夹具。
  `Lenses` 类型泛化行为中性且为第 6 步铺路；
  **`CriticId` 字面收窄保留的理由成立**——glm 核实了 `CriticRunMeta.vendor` 的两值枚举
  与 run.v1 线契约耦合，放开必然拖入 run.v2 的枚举改造，缓放到第 3 步是对的，
  且上一轮 GLM-03 的裁决已把 vendor 链路登记进该步清单。
- **两处设计判断稳妥**：`criticLabel` 未登记时回落 id 而不抛异常；
  `label` 进注册表而非渲染时数下标（避免启用第三家后既有两侧的字母漂移）。
