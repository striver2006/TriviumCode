① 第 ⑦ 件作为套件一部分的取舍完全站得住，严密保障了启动期校验与 ajv strict schema 约束；
② review.v1.json 放开后身份保证被实质削弱，缺少阻断闭环且生成约束放松存在死锁副作用；

### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/guard.ts:68-75` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：review.v1.json 放开前缀正则枚举后，guard.ts 对非法/冒充前缀仅记录告警而不作任何阻断处理，导致异常前缀在下游引发死锁或冒名冲突

**依据**：在 skills/dual-critic/schema/review.v1.json:33 中，前缀正则放开为 ^[A-Z][A-Z0-9]*-...，不再限制具体前缀；在 src/trivium/parse.ts:213 中 checkReviewIntegrity 负责校验前缀是否属于本侧。然而在 src/trivium/guard.ts:68-75 与 src/trivium/review.ts:816-838 中，checkReviewIntegrity 返回的 badIds 仅被推入 integrityIssues 并最终经由 renderGuardWarnings 格式化为日志警告，既不改变 result.status（仍为 ok），也不将运行置为 failed 或 parse_fallback。带有非法前缀的结论照常落盘到 _meta/review-<critic>-<runId>.json。下游调用时产生严重缺陷：① 若某一侧（如 gemini）生成了未登记的大写前缀（如 FINDING-01，Gemini 受限解码在放开正则后完全允许此输出），gate.ts:241 要求对其裁决，但 disposition.ts:206 的行匹配正则仅识别已登记前缀，导致 Driver 无论如何填写裁决表都会被忽略，使 gate --check 陷入无法解开的 missing_findings 死锁；② 若某一侧生成了另一侧的前缀（如 gemini 生成了 GLM-01），gate.ts 的 Set 去重将其与 glm 侧合并，Driver 只需裁决一次即可通过闸门，导致跨侧意见静默碰撞与遗漏。设计声称「guard 记 integrity 问题比 schema 枚举更强」，但目前仅为无拦截动作的弱告警。

**建议**：当 checkReviewIntegrity 发现前缀不属于本侧（!i.prefixOk）时，应当具有阻断性闭环：在 review.ts 消费端直接将其判定为解析异常，转入 parse_fallback 降级逻辑（由 enumerateFallbackFindings 重新分配带有合法前缀的虚拟编号），或者在 guard 中将 integrityIssues 升级为阻断状态（将该侧标记为 failed），严禁未校验合法前缀的结构化结论进入落盘与 gate 裁决流。

## 认为正确的部分

- 两层判据（自报清单 === 全树哈希差集 ∧ 差集 === 套件白名单全集）以及在重打包产物上先跑 tsc --noEmit 再跑五环节的整套验收装置设计非常精彩，切实破除了计划阶段指出的「夹具树自比按构造恒真」的同义反复缺陷。
- 第 ⑦ 件作为接入套件一部分的取舍完全成立：坚持了 ajv strict schema 校验防止配置拼写错误静默失效，并守护了启动期参数与环境校验（退 64 零工件）的不变式，避免将配置缺失推迟到运行期甚至 worker 进程崩溃。
- registry-parity 的 schema 对账从手维护显式清单升级为全目录兜底扫描，彻底斩断了「白名单过期条目 → run.v2 → config.v2 → review.v1」第四次同形遗漏的记性依赖，机制优于纪律。
- CriticId 由 Extract 字面收窄放开为 AgentId，以及 effortFor、checkModelSlugs 改按 vendor 查表并引入「无法校验」可见第三态，干净利落地清除了新增 Agent 时的编译期死锁与静默欺骗。
