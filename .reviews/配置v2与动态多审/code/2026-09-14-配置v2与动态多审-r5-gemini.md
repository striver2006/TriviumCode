**问题**：三份 SKILL.md 步骤 3 的透传说明存在指令冲突，导致 --only 场景下 Driver 会同时拼接 --critics 与 --only，直接触发 review --start 退 64 互斥阻断

**依据**：阅读 skills/dual-review-code/SKILL.md、skills/dual-review-plan/SKILL.md、skills/dual-review-bug/SKILL.md 的步骤 3：第 88 行规定「把 resolve 输出的 critics 数组用逗号连接后传给 --critics，无条件传」；第 92-95 行又规定「若 resolve 输出的 only 非空，把它传给 --only；--only 是 --critics 的单元素旧写法，两者不能同时传（resolve 已经挡住了这种组合，照抄它的输出不会撞上）」。而在 src/trivium/topic-args.ts 的 resolveTopicArgs 实现中，TopicResolution 的 critics 是恒非空数组（第 185 行及 232-236 行），用户即便传 --only glm，resolve 输出亦同时包含 critics: ['glm'] 与 only: 'glm'。Driver 依说明照抄输出，将向 review --start 同时传递 --critics glm 与 --only glm。此时 src/trivium/cli.ts:354 调用的 resolveCriticSelection 在 src/trivium/critics.ts:49-55 硬性拦截两者共存并抛出 EXIT.USAGE（退 64），整条流水线在启动阶段直接硬报错崩溃。

**建议**：在三份 SKILL.md 的步骤 3 中彻底废弃对 resolve 输出中 only 字段的透传逻辑，改为一律仅透传 --critics（因为 --critics 完全支持单元素），并明确向 Driver 声明严禁拼接 --only，防止互斥报错。
