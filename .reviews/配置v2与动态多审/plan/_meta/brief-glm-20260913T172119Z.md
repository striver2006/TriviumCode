### 2.1 单侧运行被标记为 `dual`（严重，违反 AC-06）

`runner.ts:216` 的注释写着铁律「**绝不**把单审改名冒充双审（AC-06）」。

调用链：

- `review.ts:303` `const sides = opts.onlyCritic ? [opts.onlyCritic] : [...CRITICS]`
- `review.ts:424` 请求只为 `sides` 构建
- `runner.ts:158` `const sides = Object.keys(input.requests).filter(...)`，`results` 只含这些键
- `runner.ts:221` `const all = Object.keys(results) as CriticId[]`
- `runner.ts:227` `if (failedSides.length === 0) return { mode: 'dual', ... }`

`decideMode` **只看「跑过的都成功了吗」，从不看「本该跑几侧」**。

**复现（真实执行，非推断）**，对 `dist/test/src/trivium/runner.js`：

```

双侧全成功                    ： {"mode":"dual","abort":false,"degradedReason":null,"okSides":["gemini","glm"],"failedSides":[]}
```

1. `review.ts:837` `meta.review_mode = mode.mode` → `run.json` 记 `dual`；
2. `review.ts:798` `degraded: mode.mode === 'single'` → `false` →

   于是只要求一侧的意见被裁决——闸门正常放行。

即：`--only gemini` 跑出来的留痕，从 `run.json` 到文档头到闸门结论，
**没有任何一处显示这不是双审**。唯一的提示是 `review.ts:312` 那句 `warn()`——

## 3. 设计

### 3.1 config v2 的形状

**约束一：审核者配置是按 vendor 异构的，不是按 Agent 同构的。**

现状两侧字段集合完全不同：

```
gemini: { vendor: 'antigravity', bin, agent, effort, readonly_commands }
glm:    { vendor: 'zcode',       entry, max_turns, unsupported_override }
```

所以 v2 **不能**简单写成 `Record<AgentId, CriticConfig>`。设计为
**以 `vendor` 为判别式的可辨识联合**：

```yaml
schema: trivium.config.v2

critics:                    # 键 = 注册表 AgentId，值按 vendor 判别
  gemini:
    vendor: antigravity
    agent: trivium-critic
    bin: null
    effort: { plan: high, code: high, bug: high }
    readonly_commands: [...]
  glm:
    vendor: zcode
    entry: null
    max_turns: 40
    unsupported_override: reject

active_critics: [gemini, glm]   # 新增：不给 --critics 时的默认集合，1～3 个
```

JSON Schema 侧：

- `critics`：`propertyNames: { enum: <ALL_AGENT_IDS 派生> }`，
  `additionalProperties: { oneOf: [antigravityShape, zcodeShape, openaiShape, anthropicShape] }`，
  `minProperties: 1`；
- `active_critics`：`{ type: array, items: { enum: <派生> }, minItems: 1, maxItems: 3, uniqueItems: true }`。

**约束二：有两条规则 JSON Schema 表达不了**，必须落在 `validateConfig` 的
代码侧交叉校验（与 `config.ts:243` 既有的「非法值明确报错，不静默落回默认」同纪律）：

1. `critics` 的每个键必须是注册表中 `criticEnabled: true` 的 Agent。
   登记了但未启用（当前的 codex / claude）出现在配置里 → **报错**，
   不是忽略。理由：静默忽略会让用户以为配了三审实际跑两审。
2. `critics[k].vendor` 必须等于 `agentById(k).vendor`。
   配置里写 `glm: { vendor: antigravity }` 必须当场炸——vendor 是适配器路由
   与禁读矩阵的依据，错配等于路由到错误的 CLI。
3. `active_critics` 的每一项必须在 `critics` 里有对应配置项。

**约束三：`maxItems: 3` 是需求给的硬上限**，不是实现限制。写进 schema 而非
代码判断，使超限在配置加载处即失败，而不是跑到一半才发现。

### 3.2 硬拒绝与迁移

`CONFIG_SCHEMA_ID` 升为 `trivium.config.v2`。

拒绝点选在 **`loadCtx` 的 `validateConfig` 之前**，而不是 preflight：

- `loadCtx` 是**所有**命令的必经路径（`gate`、`status`、`report`、Hook 全部经过），
  只在 preflight 拦会让其余入口拿着 v1 配置按 v2 语义跑；
- 早于 `validateConfig`，否则用户先看到一堆 schema 不匹配的细节噪声，
  而真正的原因是「版本旧了」。

```ts
if (cfg.schema !== CONFIG_SCHEMA_ID) {
  throw envError(
    `配置 schema 为 ${cfg.schema}，当前要求 ${CONFIG_SCHEMA_ID}。\n` +
    `  执行以下命令迁移（会先备份到 config.yaml.v1.bak）：\n` +
    `    trivium migrate-config\n` +
    `  改动内容：critics 段按 Agent 注册表重排、新增 active_critics、schema 升版。`
  );
}
```

**`deepMerge` 的行为需要专门确认**（`config.ts:148`）：内置默认已含
`schema: 'trivium.config.v2'`，用户 v1 文件里的 `schema: trivium.config.v1`
会**覆盖**它，所以检测成立。但有一个不对称：`config.local.yaml` 由
`persistProbeUnlocked`（`config.ts:296`）写出，它**只保留已有字段、不写 `schema`**。
因此：

- `config.local.yaml` 通常没有 `schema` 字段 → 合并后 `schema` 取自 `config.yaml` → 检测正确；
- 但若 `config.local.yaml` 里有旧形态的 `critics:` 覆盖，迁移 `config.yaml`
  后它仍是旧形状，会在 schema 校验处报错而非在版本检查处。

**结论：`migrate-config` 必须同时处理两个文件**，且对 `config.local.yaml`
要保留 `probe:` 段原样（它是 doctor 的实测结论，重跑代价高）。

`migrate-config` 的写入纪律：先备份（`config.yaml.v1.bak`），YAML 往返会丢注释
（`.trivium/config.yaml` 里有大量解释性注释，包括刚提交的超时理由），
所以**不做 YAML 解析后重序列化**，而是：读取 → 解析 → 仅在内存里算出 v2 结构 →
**写新文件并把原文件的注释块原样保留在对应段落之上**。若这一点做不到，
退路是「生成 `config.v2.yaml` 供人工对照替换，不原地改」，如实告知用户。
这一条我判断为本轮**实现风险最高**的一处，请审查者重点看退路是否够诚实。

### 3.4 run.v2 与 `review_mode` 的泛化

`'dual' | 'single'` 在 N ≥ 3 时无意义，且正是 §2.1 缺陷的载体。改为：

```
critics: { <id>: CriticRunMeta }      # 既有：实际跑出结果的侧
```

`decideMode` 签名增加 `requested: CriticId[]` 入参，判定改为
「`requested` 的每一侧都在 `okSides` 里」才算 `full`。这样单侧请求且成功
= `full`（它确实完成了请求的全部），但 `critics_requested.length === 1`
是**机器可判**的单审信号，不再需要靠 `mode` 编码两件事。

- `GateCheckInput.degraded` 从死字段变成真判定——闸门在
