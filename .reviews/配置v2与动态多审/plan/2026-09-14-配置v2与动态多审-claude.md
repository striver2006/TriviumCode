### 2.1 单侧运行被记为 `dual`（严重，违反 AC-06）

`runner.ts:216` 的注释写着铁律「**绝不**把单审改名冒充双审（AC-06）」，行为相反。

`decideMode`（`runner.ts:218`）只看 `Object.keys(results)`，即「跑过的都成功了吗」，
**从不看「本该跑几侧」**。`--only gemini` 时 `review.ts:303` 只为一侧建请求，
`runner.ts:158` 的 `results` 因此只有一个键，`failedSides` 为空 → 返回 `dual`。

**复现（真实执行 `dist/test/src/trivium/runner.js`，非源码推断）**：

```
单侧（--only gemini，该侧成功）： {"mode":"dual","abort":false,"degradedReason":null,"okSides":["gemini"],"failedSides":[]}
双侧全成功                    ： {"mode":"dual","abort":false,"degradedReason":null,"okSides":["gemini","glm"],"failedSides":[]}
```

逐字段相同。沿链传播：`review.ts:837` 写 `run.json.review_mode = dual`；
`review.ts:798` 的 `degraded: mode.mode === 'single'` 为 false，
故 `render.ts:116` 的降级横幅不打；`gate.ts` 的 `criticsOf` 只从
`runMeta.critics` 取键，于是只要求一侧被裁决，闸门正常放行。

唯一提示是 `review.ts:312` 的 `warn()`——控制台一行，不入档、不影响任何判定。

**既有测试为何全绿**：`test/unit/runner.test.ts:126/134/146/157` 四个
`decideMode` 用例**全部传入两侧**，单键 `results` 没有任何用例。

> 注意与 §3.4 的区别：本条的错不在「允许单审」，而在「**留痕里查不出来**」。
> 设计 AC-N3 明确「计划 1 审且成功 → 正常 full，无降级标记」，
> 所以修法是让参与者集合机器可判，**不是**给单审打降级横幅。第一稿在这里也搞错了。

### 2.4 run.json 读侧对未知 schema **零校验**（第一稿在此写反）

`archive.ts:437` 的真实条件：

```ts
if (stage !== 'verify' && meta.schema === 'trivium.run.v1' && validateRunMeta(meta).length > 0)
```

`meta.schema` 一旦不是 `trivium.run.v1` 字面量，**第一个合取项为 false，
整个校验被跳过**，随后 `artifacts` 原样 `out.push`。

升 v2 后若沿用 `if (schema === v1) … else …` 形态，这个洞会被放大。

### 3.2 config v2 形状与内存迁移

```yaml
schema: trivium.config.v2

agents:                     # 由 critics.* 迁移；键 = 注册表 AgentId
  gemini: { vendor: antigravity, bin, agent, effort, readonly_commands }
  glm:    { vendor: zcode, entry, max_turns, unsupported_override }

review:
  default_critics: [gemini, glm]   # 不给 --critics 时的默认集合
  max_critics: 3
  allow_partial_flag: true         # 原 allow_single_flag
  # …其余键原样…
```

**约束一：审核者配置按 vendor 异构**（现状两侧字段集合完全不同），
故 `agents` 的值是**以 `vendor` 为判别式的可辨识联合**，不是同构 record。

**约束二：有三条规则 JSON Schema 表达不了**，落在 `validateConfig` 代码侧
（与 `config.ts:243`「非法值明确报错、不静默落回默认」同纪律）：

1. `agents` 的每个键必须是注册表中 `criticEnabled: true` 的 Agent；
   登记未启用（当前 codex/claude）出现在配置里 → **报错**，不是忽略。
2. `agents[k].vendor` 必须等于 `agentById(k).vendor`——vendor 是适配器路由
   与禁读矩阵的依据，错配等于路由到错误的 CLI。
3. `default_critics` 每项必须在 `agents` 中有配置，且 `1 ≤ 长度 ≤ max_critics`。

**内存迁移**（`loadCtx`，设计 §11）：

```
检测 cfg.schema === 'trivium.config.v1'
  → critics.* 搬到 agents.*
  → allow_single_flag 搬到 allow_partial_flag（两者同时在场时以新名为准并告警）
  → 补 default_critics = Object.keys(agents)、max_critics = 3
  → cfg.schema 改写为 v2（仅内存）
  → stdout 告警**一次**
```

迁移**在 `validateConfig` 之前**完成，使校验只面对 v2 形状一种。

`trivium init` 检测到磁盘上仍是 v1 时提供一次性改写，备份到 `.trivium-backup`
（设计 §11 指定的备份位置，不是我第一稿自创的 `.bak`）。

**磁盘改写的失败路径纪律**（第一稿完全没写）：
- 备份用 `O_CREAT|O_EXCL`，已存在即拒绝——与 `archive.ts:7` 的防覆盖铁律同纪律；
- 已是 v2 则幂等 no-op；
- 新配置走临时文件 + `rename` 原子替换，不留半份；
- 与 `persistProbe` 的全局锁纪律（`config.ts:269`）互斥——那里已有
  「读-改-写全局单文件必须加锁」的教训注释；
- YAML 往返会丢注释（`.trivium/config.yaml` 里有大量解释性注释）。
  **如实定位：注释保留是尽力项，不是验收项**；原注释完整保留在 `.trivium-backup` 中。
  因为有内存迁移兜底，用户**不改配置也能跑**，磁盘改写是可选优化——
  这正是内存迁移路线相对硬拒绝的关键优势。

**告警只打一次的落点需要确认**：`loadCtx` 在一次进程里可能被调用多次
（Hook 子命令、worker 重建）。若按进程级去重，`--start` 派生的 worker
是独立进程会各打一次。请审查者判断这是否可接受，或是否该按「每次 CLI 调用
最多一次」实现。另：Hook 语境下 stdout 有协议含义，**告警必须走 stderr**，
否则会污染 Hook 的 JSON 输出——这一条我没有实测，标注为**推断**，请核。

### 3.4 run.v2 与 `critics_selected`

按设计 §6.2：

```
driver: AgentId                       # 新增
critics_selected: AgentId[]           # 本轮**入选**的审核者（区分「计划跑但失败」与「压根没入选」）
critics: { <id>: CriticRunMeta }      # 既有：实际跑出结果的
review_mode: 'full' | 'partial'       # 取代 dual|single
```

`decideMode` 增 `selected: CriticId[]` 入参，判定改为「`selected` 每一侧都在
`okSides` 里」才是 `full`。于是：

- 显式请求 1 侧且成功 → `full`，`critics_selected.length === 1`，
  **不打降级横幅**（设计 §12 / AC-N3）；
- 请求 3 侧其中 1 侧失败 → `partial` + `degraded_reason`（设计 §12）。

这样 §2.1 的缺陷被修掉，而修法与 AC-N3 一致：
**单审的可见性靠机器可判的 `critics_selected`，不靠横幅**。

`render.ts:116` 的现有文案「另一侧未能完成」对 `selected.length === 1` 是**假话**
（没有任何一侧失败）。区分两种标记：

- **参与者事实**（中性陈述，始终渲染）：「本轮审核者：gemini」；
- **降级警示**（仅 `review_mode === 'partial'` 时）：沿用现有文案。

`GateCheckInput.degraded` 从死字段接上真实判定：闸门按
`review_mode === 'partial'` 判，而不是按参与者数量。

**读侧按 schema 精确分发**（修 §2.4）：

```
schema === 'trivium.run.v1'  → v1 校验器，再按 §6.2 映射为内存中的 v2 形状
schema === 'trivium.run.v2'  → v2 校验器
其余任何取值（含缺失）        → 按「不可读」处理，进 manifests 违例清单
```

关键是**最后一条**：现状是「非 v1 即放过」，改为「非 v1 非 v2 即不可读」。
这比改动前**更严**——伪造 schema 字符串不再能让清单脱离校验。
需补用例：`schema: "trivium.run.v3"` 的 run.json → 不可读且被计入违例。

历史 v1 留痕**必须继续可读**：它们是不可变工件，按写入时的规范解读是
审计系统的基本要求。这与「配置做内存迁移」不矛盾——两者都是「认旧、不拒旧」。

### 3.5 桩 Agent 接入夹具：放弃环境变量方案

第一稿提的 `TRIVIUM_TEST_AGENTS` **撤回**。我自己在第一稿列的两点存疑都成立：

1. 它**增加**一侧（而 `TRIVIUM_STUB_CRITIC` 只是替换已在名单内的一侧），
   于是能让 `critics_selected` 凑够数，把「真 1 + 桩 1」记成双审——
   这正是 §2.1 所论证危害的变体，而 `run.json` 无任何字段可区分；
2. 给 M7a 刻意建立的唯一事实源开环境变量入口，就是在制造第二事实源。
   既有 `STUB_ENV_VAR` 的告警只在控制台、不入档，撑不起事后审计。

**改用**：夹具在临时仓库里跑一份**注册表加桩后重新打包**的构建产物。
生产注册表与生产代码路径完全不接受任何环境变量改写。
构建是 esbuild 单文件（`scripts/build.mjs`），改注册表重打包成本低。
