| 项 | 内容 |

**问题**：「不覆盖的只有 Claude Code 的 matcher 分发那一层」少算了至少两层。hooks.json 的 matcher 命令是一条 sh -c 守卫串：先解析 CLAUDE_PROJECT_DIR 得到 $D、再 test -x wrapper 后 exec——CLI 直喂 `./.trivium/bin/trivium gate hook-pre-write` 覆盖的是守卫 exec 的目标二进制与子命令（这半句成立），但「wrapper 缺失而 config 在场 → 退 2」这一支与 CLAUDE_PROJECT_DIR→$D 的解析不在直喂覆盖面内（前者在二进制缺失时无法由二进制自身覆盖）。验收报告若照「只差 matcher 一层」写，覆盖边界会说过头——而 EV-71 的交付物恰恰是「拍板＋实测＋边界如实写」。

**依据**：skills/dual-critic/hooks/hooks.json:41（matcher 命令全文：sh -c 'D=…; W=…; test -x "$W" && exec "$W" gate hook-pre-write; test -f "$D/config.yaml" || exit 0; … exit 2'）；src/trivium/hooks.ts:22-26 与 1538-1548（runHook 只实现「config.yaml 不存在 → exit 0」这一支，「wrapper 缺失退 2」由 sh -c 层承担，且注明由 test/contract/hook-guard.test.ts 实跑守住）；计划 §二末段原文。

**建议**：报告口径把未覆盖面写全：matcher 分发、sh -c 存在性守卫（特别是「wrapper 缺失退 2」支）、CLAUDE_PROJECT_DIR 解析三层；并注明后两层分别由 hook-guard 契约测试与本仓日常运行覆盖。「无 config 退 0」那支由二进制内部 runHook 同样实现，直喂可覆盖，不必列为缺口。
