## 二、现状与约束

### 三条路各自撞墙

非缺省 Driver 今天写裁决件，三种写法**全部失败，且失败点各不相同**：

| 写法 | 失败在哪 | 谁拦的 |

前两条是第 2/3 轮**刻意堵上**的。堵完之后，schema 这一条成了唯一还开着的口，**而它是死的**。

### 与 `run.v2` 的口径冲突（这是本条的根因）

同一个概念（Agent id），隔壁文件的处理是：

```json
"driver": { "type": "string", "minLength": 1,
  "description": "…取值是否为已登记 Agent 由代码层按注册表校验——此处不枚举…" }
```

而 `role` 在 schema 里**抄了一份 id**，与纪律 7「Agent id 的唯一来源是注册表」直接相抵。
本步就是把 `role` 拉回同一口径——**不是发明新做法，是消除一处偏离**。

### 存量影响：实测为零

- 归档 **72 份**裁决件，`role` **全为 `claude`**，文件名后缀与之逐份一致（第 2/3 轮两侧独立核过，我也核过）。
- `claude` 是已登记 Agent ⇒ 放宽 + 注册表校验后**照样通过**。
- 方向是**放松**约束，不是收紧 —— 与「契约演进不得锁死老主题」那条纪律同向，不逆向。

### 3.2 补注册表身份校验 — [src/trivium/schemas.ts:312](src/trivium/schemas.ts#L312)

`validateDispositionFrontMatter` 现在是纯 ajv 一段式：

### 3.4 用例：两处**必须同改**，否则静默失效

**(a) `config-schema.test.ts:105` 的负例会当场失去意义。** 现状：

```ts
const bad = validateDispositionFrontMatter({ …, role: 'gemini', …, addresses: [] });
assert.ok(bad.some((m) => m.includes('role')), …);
assert.ok(bad.some((m) => m.includes('addresses')), …);
```

放宽之后 `gemini` 是**合法**取值，role 那条错误消失 ⇒ 第一条断言直接红。
**正确修法不是删它**，而是把负例换成一个**真未登记**的 id（如 `'nobody'`），
让它继续守「未登记 id 必须被拒」——那正是 3.2 新加的校验。
同时补一条**正例**：`role: <某个非缺省的已登记 id>` 必须返回 `[]`。

> 这一格是本步最容易做错的地方：红了之后顺手删断言，就把 3.2 的校验变成了没人看的代码。

**(b) T-11 第 3 格** [gate-loop.test.ts:1339](test/integration/gate-loop.test.ts#L1339)：


翻成「期望通过」（`assert.equal(after.code, EXIT.OK)`），并**删掉**那条 `/bad_front_matter|role/`
