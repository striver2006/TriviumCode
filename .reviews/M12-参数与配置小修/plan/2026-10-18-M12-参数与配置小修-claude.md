## 0. 与上位计划文字相比多出的一处（先说清，请审查判断该不该纳入）

上位计划 §5 与用户给的任务目标把 EV-228 的改动面写成 `topic-args.ts` 一处，并说「`cli.ts` 的 `flagString` 对同一情形退 64」。核源码后，**`cli.ts` 这条入口只有「后面紧跟另一个旗标 / 位于末尾」两种形态会退 64，`--model-〈id〉=`（显式写等号、值为空）同样被静默丢弃**：

- `cli.ts:425-434` `flagString`：值为 `true`（没取到值）时退 64；值为空串时返回 `null`。
- `cli.ts:397-404` `collectModelOverrides`：`if (v) out[id] = v;`——`null` 被跳过，模型覆盖消失，不退非零。
- 同文件 `cli.ts:411-414` 的 `tierFlagGetter` 对三类档位旗标已经把这个形态补上了（`flagString(...) ?? ''`，再由 `assertTierFlags` 按空串退 64）——也就是说 `cli.ts` 里档位旗标与模型旗标对 `=` 空值的口径今天就不一致。

本计划**把这一格一并纳入**（§2.3），理由：任务目标的判据是「空值退 64，文案与档位旗标同源」，只修 `topic resolve` 一个入口、留下 `review` / `preflight` / `doctor` 的同一形态，正是 EV-53 那一族「收口一个入口、另一个原样丢参数」的形状（`tier-flags.ts` 文件头与 `topic-args.ts:615-628` 的注释都记着这条教训）。它同样是**行为变化**（原先静默丢弃的 `--model-〈id〉=` 改为退 64），与 EV-228 一并写进设计与说明。若审查认为超出用户拍板的范围，应改为暂缓并另登 BACKLOG，请明说。

## 1. 问题与现状（源码核实）

### 1.1 EV-228：`topic resolve` 下 `--model-〈id〉` 写了不给值被静默丢弃

- `topic-args.ts:111-171` `splitArguments`：取值旗标缺值（后面紧跟另一个**已知**旗标，或位于末尾）记空串 `''`（`:167`）；`--k=` 形态同样记 `''`（`:140-143`）。
- `topic-args.ts:638`：`const written = ALL_AGENT_IDS.filter((id) => named[\`model-${id}\`]);`——按真假过滤，`''` 判假被当成「没写」，**不报错、不退非零**，`models` 里没有这一侧，模型覆盖无声消失；之后命令 A 的 S0.6 / S2 / S6 照抄 resolve 输出，配置档位悄悄顶上。
- 同文件 `:647-657` 的三类档位旗标（M11 第 5 步）已按「键在不在」判：`collectTierFlags` 收 `undefined` 与 `''` 分开，`assertTierFlags`（`tier-flags.ts:106`）对 `''` 退 64：`--〈前缀〉-〈id〉 需要一个值，但没有给出。`
- 判定次序（档位旗标）：**先键**（`assertCriticFlagKeys`：该 id 是不是本轮入选审核者），**再空值**，再取值形状。

### 1.2 EV-228 关联：`cli.ts` 的 `=` 空值（见 §0）

- `review --start`（`cli.ts:666` 起）、`preflight`（`:842` 起）、`doctor`（`:815`）三处都经 `collectModelOverrides` 收集；`review` / `preflight` 之后 `assertModelOverrideKeys`（只判键），`doctor` 不判键（它不按本轮入选集合，见 `:814` 档位旗标那一行用的是 `CRITIC_AGENT_IDS`）。
- `--model-glm --focus x` / 末尾 `--model-glm`：`flagString` 退 64（文案「需要一个值，但它后面跟的是另一个旗标（或什么都没有）」）——**不变**。
- `--model-glm=`：静默丢弃——**本计划改**。

### 1.3 EV-227：`profiles.〈表〉.〈id〉.effort`（Agent 级）无读取点、与阶段格子里的 `effort` 同名不同层

- `types.ts:1132`：`ProfileEntry = Partial<Record<Stage, StageModel>> & { effort?: 'low' | 'medium' | 'high' }`——Agent 级 `effort` 是 v1 时代遗留（`config.v1.json` 的 `profiles.*.gemini|glm` 也收它）。
- 读取点：全仓 `src/` 对档位表只有一处按阶段的读取 `adapters/base.ts:2018`：`cfg.profiles[cfg.active_profile]?.[critic]?.[stage]`；`config.ts:600-601` 只看表名。**没有任何代码读 Agent 级 `effort`**。
- `config.v2.json:533-540`：`profiles` 的格子对象（`additionalProperties: false`）在 `plan/code/bug` 之外收一个 `effort`（`low/medium/high` 枚举），无 `deprecated`；`profiles` 描述（`:519`）末句写着「Agent 级 effort 键无读取点，见 BACKLOG」。
- M11 第 4 步之后阶段格子可写 `{model, effort}`（`$defs/stageModel`，`:896-930`），阶段格子里的 `effort` 是思考等级、第 6 步起下传；Agent 级这个什么都不做——读配置的人容易以为它是阶段格子的缺省。
- 废弃键表 `config.ts:444-463` `DEPRECATED_CONFIG_KEYS` 未收它；通配走查 `deprecatedConfigKeysIn`（`:467-483`）对 `'*'` 展开当层全部键、按键名排序，路径 `['profiles','*','*','effort']` 只命中**第三层**的 `effort`，阶段格子里的 `effort` 在第四层（`profiles.〈表〉.〈id〉.〈阶段〉.effort`），**差一层、不会命中**。
- 本仓 `.trivium/config.yaml` 只有阶段格子里的 `{model, effort}`，没有 Agent 级 `effort`（`grep` 核过），本仓 doctor / preflight 不会因本批多出提示。

## 2. 方案

### 2.1 EV-228 主改动：`topic-args.ts` 按键存在判定

1. `:638` 改为按键存在收集：`ALL_AGENT_IDS.filter((id) => named[\`model-${id}\`] !== undefined)`。
2. 次序与档位旗标一致：**先** `assertModelOverrideKeys`（键判定，不变），**再**空值判定，空值退 64。
3. 赋值只在两步都通过之后（`models[id] = named[...]`，值必非空）。
4. 改 `:647-651` 那段注释里「既有 `--model-〈id〉` 的同一缺口另登记 BACKLOG，本步不改」一句（本步就是收口它）。

### 2.2 文案同源：空值判定只此一份

在 `tier-flags.ts` 抽出一个导出函数（暂名 `assertFlagValuesGiven(prefix, raw)`，`prefix ∈ {'model','tier','effort','profile'}`，`raw: Record<string,string>`）：任一值为 `''` 即 `usageError(\`--${prefix}-${id} 需要一个值，但没有给出。\`)`。

- `assertTierFlags` 现有的空值循环（`tier-flags.ts:104-108`）改为对三类各调一次这个函数——**文案逐字不变**（现有 `tier-flags.test.ts:80-82` 与 `tier-flags-cli.test.ts` T2 照旧通过，作为不变的证据）。
- 模型旗标的空值判定调**同一个函数**、前缀 `model`。这样「文案与档位旗标同源」由代码结构保证，不靠两处字面碰巧相同。
- 遍历次序：按 `ALL_AGENT_IDS` 注册表序（`raw` 由注册表序收集，`Object.entries` 保持插入序）——多侧同时空值时报第一个，与档位旗标现状一致。

### 2.3 EV-228 关联：`cli.ts` 的 `=` 空值（§0）

1. `collectModelOverrides`：`args.flags.has(name)` 且 `flagString` 返回 `null`（即 `--model-x=`）时记 `''`，不再跳过；没写仍不出现；`true` 形态仍由 `flagString` 退 64（文案不变）。
2. `review --start` 与 `preflight`：在 `assertModelOverrideKeys` 之后调 `assertFlagValuesGiven('model', modelOverrides)`——次序同 §2.1。
3. `doctor`：它不判键（现状），只在收集后调 `assertFlagValuesGiven('model', …)`；**不新增键判定**（那是另一件事，不扩大）。
4. `review --start` 的 `modelOverrides` 还经交接文件 / `reviewOpts` 下传——空值在进入任何落盘前已退 64，下游拿到的值必非空，与今天相同。

### 2.4 EV-227：Agent 级 `effort` 进废弃键表

照 EV-30 ①～⑦、`agents.codex.effort`（M11 第 4 步）的先例：

1. **`config.ts` `DEPRECATED_CONFIG_KEYS`**：在表尾追加 `{ path: ['profiles', '*', '*', 'effort'] }`，注释写明：①两层 `'*'` 依次匹配档位表名与 Agent id；②**只命中 Agent 级那一层**，阶段格子里的 `effort` 在下一层、不会命中（与 `agents.gemini.effort` 那条精确路径的理由不同：这里通配不会误伤，因为同名键在别的层级）；③v1 配置迁移后带着它也会被提示（迁移不删内容，13.1.1 已有约定）。
   - 文件头注释 `:441`「路径里的 `'*'` 匹配 `agents` 下任一 Agent id」改准：`'*'` 匹配当层任一键（`agents` 下是 Agent id，`profiles` 下依次是表名与 Agent id）。
   - 输出形态沿用 `deprecatedConfigKeysIn`：点分路径 `profiles.default.gemini.effort`，按表序、同条内按键名排序；多张表、多侧各列一条。提示正文 `deprecatedConfigNotice` 不改（「从未生效（没有任何代码读取），现已删除；schema 仍接受……」对它同样成立）。
2. **`types.ts:1132`**：`ProfileEntry` 删去 `& { effort?: … }`，加注释（同既有废弃字段的格式：删除日期、EV 号、理由、「schema 仍接受它（标 deprecated），见 `DEPRECATED_CONFIG_KEYS`。不要加回来。」）。删字段后 `tsc` 若在某处报错，说明存在读取点，与 §1.3 的核实冲突——届时停下重核，不硬改。
3. **`config.v2.json`**：
   - `profiles` 格子里 Agent 级 `effort` 加 `"deprecated": true` 与 `description`（写明「已废弃（2026-10-18，M12 批次 4，EV-227）：从未被读取；与阶段格子 `{model, effort}` 里的思考等级同名不同层……保留属性与原类型约束只为旧配置照常通过校验；出现时 doctor / preflight 提示一条」），**枚举不放宽**（仍 `low/medium/high`）、不改 `additionalProperties`。
   - `profiles` 描述（`:519`）末句「Agent 级 effort 键无读取点，见 BACKLOG」改为指向该属性的 deprecated 说明。
   - 它本不在任何 `required` 里，不涉及移出 `required`。
   - `$defs/stageModel` 里的 `effort` **不动**。
4. **默认值与 `init`**：默认配置的 `profiles` 本就不带 Agent 级 `effort`（`config.ts:351` 起核过），无需删；`init` 不写它。
5. **不改的**：`config.v1.json`（历史契约）、`migrateConfigV1`（迁移不删内容）、`resolveTier` 与适配器透传（阶段格子的 `{model, effort}` 照常下传）、`ATOMIC_CONFIG_NODES`（`['profiles','*','*','*']` 只管第四层）、doctor / preflight 的提示通道本身。

### 2.5 不做的

- 不给 `--model-〈id〉` 加取值形状校验（如去空白、不收纯空白）：档位旗标今天也不 trim，保持对称；纯空白值的处置不在本批。
- 不给 `doctor` 补模型覆盖的键判定（§2.3 第 3 条）。
- 不改 `flagString` 的 `true` 形态文案（两个入口对「紧跟旗标 / 末尾」两种形态的文案今天就不同：`topic resolve` 记空串走 §2.2 的文案，`cli.ts` 走 `flagString` 的文案；本批只保证**同一入口内**模型旗标与档位旗标逐字同源，见 §3 的断言口径）。

## 8. 风险与自查

- **行为变化面**：原先能跑通、只是覆盖丢了的命令，改后在开跑前退 64。用户入口资产（四份 `/dual-*`）的 S0.5 / 第 1 步是 `topic resolve`，退 64 时按既有指引「原样转述并停止」，零工件。不影响任何不带空值的写法。
- **同一入口内同源、跨入口不同文案**：`topic resolve` 与 `cli.ts` 对「紧跟旗标 / 末尾」两形态文案不同，这是两个解析器的既有差异（resolve 不能区分「紧跟旗标」与「`=` 空」），本批不统一；§3 已逐格写明，审查若认为必须跨入口统一，请指出要统一到哪条。
- **废弃键通配**：两层 `'*'` 在 `profiles` 下会展开所有表与所有键——若有人在表下写了非 Agent id 的键，schema 的格子层就会拒，走不到走查；走查只在合并结果上做，对 schema 已拒的配置不可达。
- **删类型字段**：若 `tsc` 报某处读了 `ProfileEntry.effort`，说明 §1.3 的「无读取点」核实有误，停下重核。
