### GLM-01 · 重要（major）

| 类别 | contract ｜ 层次 code |

**问题**：每条路线的落盘指纹在写入时嵌入的是「经该路线启动器实测的版本」（doctor 探测时 probeClaudeBin 经 route.bin 跑 --version，snapshot.version 随即成为顶层 version），但读取侧 claudeProbeForRoute 重算指纹时 version 分量取 cfg.probe.cli.claude.version——即「最后一次探测的任意一条路线」的版本，不是被校验路线自己的版本。当两条路线的下层 CLI 版本不同（例如 cld 钉了与原生入口不同的 claude 构建）时：①后探一条会让另一条的指纹恒不匹配，routes 字典里条目还在、读取侧却静默返回 undefined，availability 报「尚未探测」，下次 doctor 只能整段重探、花过真实预算的结论作废，且无任何告警指出差因是 version 分量，形成两条路线互相作废的乒乓；②反之路线自身的下层 CLI 升级而顶层 version 仍等于其旧值时，checkCliVersions 每次预检跑的是 probe.entrypoint（原生入口）的版本核对，看不见 cld 下层的变化，「底层 CLI 版本变化即使旧结论失效」在这一窗口不成立。与设计 11.6「各路线能力由底层 CLI 版本、原生路径、包装脚本哈希、对应配置哈希绑定；改变即失效」的口径不符。probeAuth 的缓存校验对 claude 用同一顶层 version，同源。当前本机各路线均报 2.1.295，该机制尚属潜伏状态，故置信标 medium。

**依据**：实读 src/trivium/adapters/claude-route.ts：resolveClaudeRoute 第 86-89 行指纹的 version 取 probe?.version（即 cfg.probe.cli.claude 顶层字段）；claudeProbeForRoute 第 96-101 行以该重算指纹与 entry.fingerprint 比对，不匹配即返回 undefined。实读 src/trivium/doctor.ts 第 786-802 行：写入时 routes[key].fingerprint 以嵌入本轮 snapshot（含该路线实测版本）的 cfg 计算，随后顶层 probe.cli.claude 被整体替换为该 snapshot，多路线共存时顶层 version 随最后探测的路线走。实读 src/trivium/preflight.ts 第 887 行 version 取 cfg.probe.cli[cliName]?.version、第 132-151 行 authCacheValid 以它做缓存版本比对、第 197-239 行 readCliVersion 只按 probe.version_probe 跑 probe.entrypoint（原生入口）。证据文件 doc/05_testing/evidence/agent-access-20261009/batch-1/summary.json 显示 native 与 cld 当前同报 2.1.295。

**建议**：校验侧按路线各自取版本：routes 条目落盘时可显式保存该路线实测版本（或启动器实测版本的哈希），claudeProbeForRoute 比对时用条目内版本参与重算，而不是顶层字段；或把预检的版本核对扩展到「按解析出的 profile 路线经 route.bin 各跑一次 --version」与条目版本比对。至少应在指纹不匹配且差异仅在 version 分量时输出告警，避免「已探路线静默变未探」让人误以为需要整段重烧预算。

**问题**：双模式接入后，claude 适配器的轨迹能力声明仍是单值 TOOL_TRACE_CAPABILITY，对所有 native 与 profile 路线一体适用。探针字段 trace_path_structured 与 denied_tool_in_trace 已按路线经 cld 实测（routeContext 使全部探臂走所选路线），但这两个字段既不进 claudeAvailability 的门槛，也没有像 codex 那样在 doctor 里做 capabilityParity 对账。若某条 profile 路线实测 denied_tool_in_trace 为 false（被拒操作不留痕），guard 仍按 rejectionRecorded 为 true 信任阴性证据、把指纹变化归因给开发者手改——这正是 capabilityParity 注释自己点名的失效形态（「实测更悲观：阴性结论不可信，而声明说它可信」）。证据里三条 Claude 路线该格均为 null（模型未尝试写工具，未测到），报告已如实披露；但「未测到」同样不构成对原生官方结论（M9 正向样本）在新路线上的证实，设计 11.6「未实测能力不能视为已准入」在判定层这一格没有机制承接。

**建议**：给 claude 补能力对账：按路线把探针实测的 denied_tool_in_trace、trace_path_structured 与声明比对（复用 capabilityParity 或按路线条目比对），实测为 false 时进 doctor 告警或 availability 判据；null 维持现状不拦即可。重点是让「实测证伪而声明仍说可信」这一格有出口，与「未知轨迹能力不能套用旧官方结论」的焦点对齐。
