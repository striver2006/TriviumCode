### 1.2 「比不了」落进哪一格

送审快照的 `tree_hash` 是临时索引 `write-tree` 写出的**不可达对象**。审查期间它被删、或 git 本身出错 / 超时，`diffTrees` 返回 `[]`，3.b 判 `none`，`driftAction` 给 ok，run.json 记 `changed: false`，审查文档不带漂移旗标、`--wait` 不播任何告警。工作树确实变了（3 步前提就是两棵 tree 不同），护栏却说「无漂移」。

**本机实测（git 2.54.0，scratchpad 一次性仓库，不进 evidence）**：`write-tree` 写出一棵不可达 tree 后，缺省 `git gc` 与 `git maintenance run --task=loose-objects` 之后对象**仍在**（`cat-file -e` 退 0）；`git gc --prune=now` 之后**不在**（退 1），此时 `git diff-tree -r --name-only <它> HEAD^{tree}` 打 `fatal: bad object …`、退 128。即：缺省维护不会触发这一格（`gc.pruneExpire` 缺省两周宽限），触发它要「立即清理不可达对象」一类的操作（`git prune`、`gc --prune=now`、宽限被调成 now），或 git 出错 / 超时。编码阶段在 evidence 里重做这组读数（§5.4 V0）。

## 2. 设计

### 2.1 新结论

```ts
export type DriftUnknownCause = 'object_gone' | 'git_error' | 'timeout';

export type DriftVerdict =
  | { kind: 'none' }
  | { kind: 'subject_drift' }
  | { kind: 'related'; files: string[] }
  | { kind: 'unrelated'; files: string[] }
  | { kind: 'unknown'; cause: DriftUnknownCause; detail: string };
```

名称取 `unknown`（BACKLOG 候选原文的写法）。三种原因对应任务目标的「对象已不在、git 出错、超时」：

| `cause` | 何时 | `detail`（单行，人读） |
| :-- | :-- | :-- |
| `object_gone` | 比对失败后 `treeExists` 判送审快照 tree 或跑后 tree 不在对象库 | `送审快照的 tree 对象 〈前 12 位〉 已不在对象库`（跑后那棵不在时措辞换成「跑后复算的 tree 对象」） |
| `timeout` | 比对或随后的 `treeExists` 抛 `GitTimeoutError` | `git diff-tree 超时`（或 `git cat-file 超时`），取 `GitTimeoutError.message` |
| `git_error` | 其余：比对非零退出但两棵 tree 都在、`treeExists` 抛非超时错误、`-z` 输出段数为奇数 | 比对报错的首行；`treeExists` 也抛了时追加「；核对对象时：〈首行〉」 |

`object_gone` 不叫 `baseline_gone`：两棵 tree 里任一不在都算，跑后那棵虽然刚写出、实际几乎不会被删，但判据要对称，不能让它掉进 `git_error`。

### 2.2 `judgeDrift` 改法（`freeze.ts`）

只动 3.a：

```ts
let entries: Array<{ status: string; path: string }>;
try {
  entries = await diffTreesNameStatus(projectRoot, before.treeHash, afterTreeHash);
} catch (e) {
  const u = await classifyCompareFailure(projectRoot, before.treeHash, afterTreeHash, e);
  return { kind: 'unknown', ...u };
}
const changed = entries.map((c) => c.path).filter((f) => !matchesAnyGlob(f, scratchGlobs) && !isOwn(f));
```

- **快乐路径的 git 调用次数不变**（仍是一次 `diff-tree`）；只有失败后才多一次到两次 `cat-file -e`，用于分原因；
- 不传 `timeoutMs`：沿用缺省 120 s、不按进程组收尾，与 `workTreeHash` 在漂移复算里不传同一口径（`util/git.ts` :25～:31 的注释）；
- `classifyCompareFailure(projectRoot, beforeTree, afterTree, err)` 导出，单测直接喂 `GitTimeoutError` 与非 git 目录（超时在真实仓库里造不出来）。次序：`err` 是 `GitTimeoutError` ⇒ `timeout`，不再查对象；否则 `treeExists(before)`、`treeExists(after)`；任一 false ⇒ `object_gone`；`treeExists` 抛 `GitTimeoutError` ⇒ `timeout`；抛别的 ⇒ `git_error`（带两段首行）；都在 ⇒ `git_error`；
- **判别用 `instanceof GitTimeoutError`**，不用 `worktree-summary.ts` 里按 `timedOut` 字段鸭子判型的 `isTimeout`——那个函数是该文件私有的；二者等价（`GitTimeoutError` 恒带 `timedOut = true`），这里没必要为一处 `instanceof` 把它导出。

**严格助手带来的一处顺带变化（如实写出，不是改口径）**：旧 `diffTrees` 用 `--name-only` 不带 `-z`，含制表符、换行、双引号、反斜杠的路径会被 git 用 C 风格加引号输出，而 `diffTrees` **没有**像 `statusPorcelain` 那样过 `unquoteGitPath`——这类路径带着引号进 scratch 白名单与「相关」匹配，永远匹配不上，于是本应判 `related` 的会落进 `unrelated`（缺省只告警），方向是放松。`diffTreesNameStatus` 走 `-z`，路径原样，这一格随之变对。`--no-renames` 与旧调用等价：`diff-tree` 是底层命令，不读 `diff.renames`，旧调用本来也不做改名检测（编码阶段在 evidence 里各跑一次核对两者在普通路径上输出同集）。删除、类型变化在两种输出里都列出，集合相同。

### 2.4 处置的代价与出口文案

**代价**：一次「立即清理不可达对象」就让整轮按 `fail` 收尾（`status: failed`、退 1）；审查结论照常落盘、可读，但这一轮不能当作有效审查，要重跑本阶段——重跑花一轮配额。

**为什么仍取最严一档**（论证，不是重新讨论用户决策）：

1. 比不了 ⇒ 不知道哪些文件被改，自然也排除不了「被审范围内的文件被改」，而那一格缺省就是 `fail`。按 `on_drift`（缺省 warn）处置等于假设改动都在范围外，这正是「判不了就放行」换个形态；
2. 触发面窄：§1.2 实测缺省 `gc` 与 maintenance 都不删两周内的不可达对象，落进这一格要么是有人在审查期间做了立即清理，要么 git 出错 / 120 s 超时——后两种情形下仓库本身就不健康，判失败比放行合理；
3. 有出口：用户确认审查期间没动工作树后，重跑即可；确实想只告警，可以把 `on_drift_related` 改成 `warn`，但那同时放宽真实的相关漂移——文案里写明这一点，不让人误以为是专门关这一格的开关。

**人读告警（`renderGuardWarnings` 新增 `case 'unknown'`）**，`fail` 时：

```text
审查期间工作树有变动，但比不了改了哪些文件（〈原因标签〉：〈detail〉）——
无法排除被审范围内的文件被改，按 on_drift_related 处置（策略 fail）。
  审查结论已落盘，但本轮不能当作有效审查。处置：用 git status / git diff 核对审查期间是否动过工作树，
  确认后重跑本阶段审查；审查进行中不要执行会立即清理不可达对象的 git 命令（如 git prune、git gc --prune=now）。
  若只想告警，可把 review.on_drift_related 设为 warn——它会同时放宽真实的相关漂移。
```

`warn` 时首段相同、策略写 warn，第二段换成「本轮照常结束，但漂移是否涉及被审范围无从判断，请人工核对：git status / git diff」。原因标签：`object_gone` ⇒「送审快照的对象已不在对象库（可能在审查期间被 git 清理）」，`timeout` ⇒「git 超时」，`git_error` ⇒「git 出错」。三个标签与 `detail` 的拼法集中在 `freeze.ts` 一个导出常量表里（`DRIFT_UNKNOWN_LABEL`），guard、report、summarizeRun、render 都从它取，不各写一份。

`fingerprintChangedFiles` / `unattributedDriftFiles` 对 `unknown` 都为 `[]`（`guard.ts` :699～:700 现有写法已经如此，不改）：没有文件清单就不归因，告警正文已说明「比不了」。

### 2.5 run.json 与 schema（只取加法）

`snapshot.drift` 新增可选字段：

```json

```

- 既有三个字段的写法与含义**不变**：`changed` 仍是「结论不是 `none`」（`review.ts` :1445 现有表达式原样，`unknown` 下自然为 true——与 `subject_drift` 已有的「changed 真、files 空」同形）；`files` 仍是已归因的变更文件，`unknown` 下为空；`policy` 仍是「本轮实际适用的那个配置键的值」，`unknown` 下取 `on_drift_related`（:1447 的条件由 `kind === 'related'` 改为 `related` 或 `unknown`）；

- **旧版本读新留痕**：`drift` 子对象未禁额外键、根 :26 为 true，旧构建的 ajv 校验照过；旧 `report` 看到 `changed: true, files: []` 走 `shown === 0` 不推旗标、旧 `summarizeRun` 打「漂移：0 个文件（策略 fail）」——信息不全但不出错，且 `status: failed` 本身已说明这一轮不成立；

## 6. 暂缓（默认不做，登记 EV-180）

**降低成因本身：让送审快照的 tree 对象在审查期间不被清理。** 候选做法是 `--start` 冻结后建一个 ref（如 `refs/trivium/runs/〈run_id〉`）指向送审 tree，收尾删除；或把对象写进 `.keep` 包。不做的理由：

1. **触发面窄**：§1.2 实测缺省 `gc` 与 maintenance 都不删两周内的不可达对象；
2. **改的是用户仓库**：ref 会出现在 `git for-each-ref`、`push --mirror` 里，是本系统第一次往用户的 ref 命名空间写东西；
3. **收尾面大**：正常收尾、worker 异常、失联、`--cancel`、会话启动清扫，每条路径都要删 ref，漏一条就在用户仓库里留永久 ref（反向把对象钉住、永不回收）——这正是近几个主题反复在修的「各收尾路径口径不一」那一类；
4. 本主题修完之后，成因发生时已不再放行，而是响亮失败、有出口，降低成因只是减少一次重跑的成本。

触发条件：实测或用户反馈中出现「比不了」导致的失败轮（run.json 带 `unknown_reason`）。

## 7. 风险

| 风险 | 处置 |
| :-- | :-- |
| 严格比对在某些仓库里比旧调用更容易失败（`-z` 输出段数为奇数等） | 失败一律判 `unknown` 并说明原因，方向是不放行；`parseNameStatusZ` 的成对解析已有单测 |
| 失败后多出的 `cat-file -e` 调用在坏仓库里再等 120 s | 只在已经失败之后发生；最坏多等两次超时，换来的是原因分得清。超时那一格不再查对象（§2.2 次序），不会叠加 |
| 新字段让旧版本 `report` 打出「0 个文件」的信息不全 | §2.5 已核不出错；`status: failed` 本身说明问题 |
| 变异装置被无超时等待挂死（09-30 撞过） | 新用例里没有「等桩触发」的 Promise；集成用例走既有 `runInjected`，有其自身超时；仍按坑清单先逐条带超时预跑 |
