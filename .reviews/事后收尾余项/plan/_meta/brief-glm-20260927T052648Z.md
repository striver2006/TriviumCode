### 2.3 ② 派生后失败（C2b）——实测推翻了 BACKLOG 的前提

BACKLOG EV-145 ② 写的是「派生成功后才失败时 worker 可能仍在跑，前提要另论」。实测是：**worker 一定在跑，而且锁与闸门都已被放掉**。

| 格 | 读数 |
| :--- | :--- |
| ok 桩 | `--start` 退 1（EISDIR `worker.pid`）；刚返回时 run.json `running`、闸门 `idle`、锁已放。**孤儿 worker 照常跑完**：run.json `success`、登记 `success`、两份审查文档与原稿登记齐全；它收尾时 `setGateChecked(expect: { runId })` 命中 `idle` 且 run_id 相符的条目，**闸门被置成 `review_done_awaiting_disposition`**——Driver 看到的是「启动失败」，闸门却在等一轮审查的裁决 |
| hang 桩 | `--start` 退 1；孤儿 worker 活着（`ps` 可见）、status.json `phase: running`、`worker_pid: null`（记 pid 的 `patchStatus` :397 没走到）；锁已放、闸门 `idle` |
| hang 桩，孤儿还活着时再 `--start` | **退 0，起了第二个 worker**：同主题同阶段两个 worker 并发，两份 run.json 都是 `rerun_index: 1`、都 `running`；闸门与锁归第二个 |
| 杀掉孤儿后 `--cancel <孤儿 run>` | 退 0，但「凭据副本未抹：运行处于 running 却拿不到 worker_pid」「归档 run-….json 未回写：工作进程未确认退出」「闸门未回收：闸门当前记着另一次运行」——**它杀不到、也收不了尾**（status.json 没有 pid，`worker.pid` 没写成） |

结论：这一格 run.json 并不必然停在 `running`（worker 是活着的写者，正常跑完会自己写终态），在这里写 `failed` 反而会与它互相覆盖。真正的缺陷是 `startRun` 主 `catch` 在 worker 已派生时照样放锁、回收闸门并报失败——属另一件事，**新登 BACKLOG**（§6.4 第 2 条），本主题不改这一段。

附记：探针第一版在这一格的第二次 `--start` 也落进了预建目录的时间窗，又留下一个孤儿 hang worker（pid 18387），我在读数后按 run_id 核对命令行结束了它；第二版改为第一次 `--start` 后撤掉多余的预建目录，并在收尾按观测到的 run_id 扫一遍残留 worker。这件事本身就是上表第二行的实例。

## 3. 改法（按建议项）

### 3.1 `termination.by` 扩值（D1）

- **两个新取值**，形状与 `worker_exception` 相同（带 `exit_code`）：
  - `prepare_exception`：审查员**一个都没拉起**就失败——①（`prepareRun` 写完骨架之后）与②派生前（`startRun` 主 `try` 在调用 `spawnDetached` 之前）。
  - `sync_exception`：同步路径 `executeRun` 抛错（③），审查员可能已经跑过、配额可能已经花了，与 `worker_exception` 同义，只是不在 worker 里。
- **类型侧单一来源**：`types.ts` 导出运行时常量 `EXCEPTION_TERMINATION_BY = ['worker_exception', 'prepare_exception', 'sync_exception'] as const`，`RunTermination` 改为
  `{ by: (typeof EXCEPTION_TERMINATION_BY)[number]; exit_code: number } | { by: 'worker_lost'; reason: WorkerLostReason }`。`types.ts` 已有运行时常量（`STAGES` 等），不另开模块。
- **schema**：第一个 `oneOf` 分支的 `by` 由 `const: worker_exception` 改为 `enum: [三值]`，其余不变（`exit_code` 整数、`additionalProperties: false`）；description 同步。
- **守卫用例 S3**：从 schema 的两个分支收集 `by`（`const` 或 `enum`），与 `[...EXCEPTION_TERMINATION_BY, 'worker_lost']` 逐项相等。另加 V9：对每个 `by` 取值，`report` 的说明都不落进兜底分支——`report` 这一侧也守住。
- **`report` 说明**：`prepare_exception` →「准备阶段失败，未拉起审查员（退出码 N）」；`sync_exception` →「同步路径异常（退出码 N）」。`worker_exception` 那句不动。
- `exit_code` 与抛出的错误同源：`TriviumError` 取其 `code`，否则 `EXIT.FAIL`（与 worker `catch` :536-537 同一表达式，抽成一个小函数供三处用）。

### 3.2 ① `prepareRun` 的 `catch`

```ts
  const holdsGate = !skipVerdict?.skipped;
  let skeletonWritten = false;                       // 【新】
  try {
    …
    await writeRunMeta(ref.layout, stage, meta);     // :1014
    skeletonWritten = true;                          // 【新】紧跟在骨架写成之后
    …registerRun / 任务目标落盘（:1016-1033）原样…
  } catch (e) {
    if (holdsGate) await releaseRunningGateEntry({ … });                 // :1043-1048 原样，排第一
    if (skeletonWritten) {                                                // 【新】
      const fin = await finalizeFailedRunMeta({
        layout: ref.layout, stage, runId, lock: taskLock,
        workerGone: true,   // 还没派生任何 worker；写者就是本进程（§3.5）
        termination: { by: 'prepare_exception', exit_code: exitCodeOf(e) },
      });
      for (const line of finalizeLines(fin, runId)) warn(line);          // §3.6
    }
    throw e;
  }
```

- **只在骨架写成之后收尾**：之前的失败（重置计数、补丁 / brief 的密钥扫描、骨架自己的写前校验）没有 run.json 可收，调了也只会得到「归档里没有」的跳过，徒增一行噪声（B7 顺带守住）。
- **闸门回收排在收尾之前**：进程若死在两步之间，闸门停在 `running` 会拦住全部业务写入直到 TTL（清扫读不到 status.json 就要过 TTL，P8），run.json 停在 `running` 只是留痕不准；两害取轻。与 worker / `--wait` 那两条「收尾排在 status.json 之前」不冲突：这里没有 status.json，也没有「下一次调用补齐」的入口（§2.2 的 `--wait` / `--cancel` 都够不着），收尾只有这一次机会。
- task.json：登记失败那一格里本次条目不存在，第二步按 C3「找不到不新建」跳过；任务目标落盘失败那一格里条目在，第二步同步为 `failed`（登记与目标写的是同一个文件，多半同样失败，转成带异常的跳过、告警照打）。
- `taskLock` 就是 :1015 那个，挪到 `try` 之前声明。

### 3.3 ② `startRun` 主 `try`：只收派生前那一段

```ts
  let spawnAttempted = false;                        // 【新】
  try {
    …:360-377 原样（副本源复查、运行目录、交接文件、status.json、定位脚本）…
    spawnAttempted = true;                           // 【新】紧贴在调用 spawnDetached 之前
    const spawned = await spawnDetached(…);          // :378
    …:383-428 原样…
  } catch (e) {
    await releaseRunningGate(ctx, rc.runId, rc.ref.topic, rc.stage);   // :431 原样，排第一
    if (!spawnAttempted) {                                             // 【新】
      const fin = await finalizeFailedRunMeta({ …, workerGone: true,
        termination: { by: 'prepare_exception', exit_code: exitCodeOf(e) } });
      for (const line of finalizeLines(fin, rc.runId)) warn(line);
    }
    await lock.release();                                              // :432 原样，挪到收尾之后
    throw e;
  }
```

- **判据取「调用之前」而不是「返回之后」**：P4——`spawnDetached` 在子进程已起之后还可能因 `handle.close()` 抛错。把它内部的失败（建日志目录、开日志文件、`spawn` 本身）一律按「可能已派生」处理，宁可少收一格也不与活着的 worker 双写。
- **派生之后（`spawnAttempted` 为真）一行不改**：§2.3 实测 worker 活着并会自己收尾，这里写 `failed` 会被它的 :1660 覆盖、或反过来覆盖它；主 `catch` 放锁、回收闸门的既有缺陷另登 BACKLOG（§6.4 第 2 条）。
- **放锁挪到收尾之后**：收尾期间仍持主题锁，同主题的新 `--start` 进不来，不会在收尾的同时起新一轮。收尾自身不抛（C1），不会让锁漏放。
- 纯文档跳过分支（:325-344）不改（§2.4）。

### 3.4 ③ 同步路径 `runReviewLocked` 的 `catch`

内联的闸门回收（:1762-1769）之后、`throw e` 之前加一次 `finalizeFailedRunMeta({ …, workerGone: true, termination: { by: 'sync_exception', exit_code: exitCodeOf(e) } })`，结果同样 `warn`。「仍为 running 才写」挡住 P7 那种「终态已写、之后的登记或闸门写入才抛」的情形，不追溯改写。`prepareRun` 在这条路上的失败由 §3.2 在它自己的 `catch` 里收尾，这里不重复（`prepareRun` 在 `try` 之外，P6）。

### 3.5 写入前提逐格论证（`workerGone: true` 的依据）

事后收尾第一步的前提 1 是「没有另一个写者」。三格都传 `true`，理由逐格如下：

| 格 | 写者 | 其它可能的写者 | 为什么这一刻没有 |
| :--- | :--- | :--- | :--- |
| ① | `prepareRun`（`--start` 进程或同步 `review` 进程），持主题锁 | worker；`--cancel`；`--wait`；会话启动清扫；下一次 `--start` 回收遗留锁 | 还没派生任何 worker；`--cancel` 与 `--wait` 要靠 status.json / 交接文件拿身份，这两份此时都不存在（§2.1、§2.2 实测：退 65 / 不调收尾）；清扫只碰 state.json；主题锁由本进程持有且进程活着，`judgeStale` 不会回收它 |
| ② 派生前 | `startRun`，持主题锁 | 同上 | `spawnAttempted` 为假 ⇒ 没有 worker（P4 的边界见 §3.3）；交接文件可能已写而 status.json 未写：`--cancel` 取到身份，但拿不到 pid，`workerConfirmedGone(null, null)` 判「否」、第一步跳过（C6）；`--wait` 同样 `goneForArchive` 为假 |
| ③ | 同步 `review` 进程，持主题锁到 `finally` | 同上 | 同步路径从不写 status.json 与交接文件（§2.5 实测），`--cancel` / `--wait` 够不着；没有 worker |

另两条共性：①三格的第一步都在主题任务锁里判与写（C2），即使上表哪一格论证漏了，两个写者也只会「谁先到记谁」，不会互相覆盖；②「仍为 running 才写」让晚于终态写入的异常（P5、P7）一律跳过。`meta.ts` `FinalizeInput.workerGone` 的文档块（:548-552）补第三类调用方：「准备阶段与同步路径在本进程里调用时恒传 true——还没有、也不会有 worker」。

### 3.6 播报

- 三格都以原错误抛出收场，CLI 顶层打印报错正文、退出码不变。收尾结果在 `throw` 之前用 `warn` 各打一行（stderr），`--start --json` 的 stdout 不受影响；skill 对 `--start` 的非零退出是「按原样转述并停止」，这两行随之转述。
- 文案：写了 ⇒「已把归档里的 `run-<id>.json` 收尾为 failed（准备阶段失败 / 同步路径异常）」；按前提跳过 ⇒「归档 `run-<id>.json` 未回写：`<原因>`」；异常转成的跳过 ⇒ 同一句加「这一步没有第二次机会，请人工核对归档 run.json 与 task.json 的运行登记」。
- `run-protocol.ts` 的 `describeFinalizeStep`（:870-876）写死了「status.json 随后落终态」，这三格没有 status.json，不能照搬。做法：把「一步 → 一句」的骨架挪进 `meta.ts` 导出（`review.ts` 不依赖 `run-protocol.ts`），后果那半句由调用方传入；`describeFinalizeStep` 改为委托它、字面输出不变（EV-142 的 W1 / L1 断言照旧绿）。

## 6. 风险与边界

### 6.1 对既有不变量

- **EV-133「收尾后不再更新」**：三格都只在仍为 `running` 时写，且都是那份 run.json 走不到 worker 收尾时的唯一一次终态写入；第一步在主题任务锁里，保证至多一次。
- **提交锚**：HEAD 为 `running` 的 run.json 只查 `run_id` 与已登记条目（`hooks.ts` :544 `runningRewriteViolation`）；三格只改三格加 `termination`，`artifacts[]` 原样。
- **`runTerminal` 翻转**：这些运行的主题锁判定由「未终态」变「终态」。三格的锁都由本进程在收尾之后自己放掉，翻转不改变任何回收结果。

## 7. 决策点（2026-09-27 送审前已定：用户定全部取建议项）

**D1 `termination.by` 取几个值、叫什么、要不要带 `exit_code`、要不要补同步守卫** — **已定**（取建议项）：两个新值 `prepare_exception`（①与②派生前）与 `sync_exception`（③），都带 `exit_code`；schema 第一个分支的 `by` 改为三值枚举；`types.ts` 导出 `EXCEPTION_TERMINATION_BY` 派生类型；补 S3（schema ↔ 常量）与 V9（`report` 不落兜底）。

- 为什么分两个：`report` 的读者最想知道的是「审查员拉起过没有、配额花了没有」。①②派生前一个都没拉起；③已经跑过审查员（与 `worker_exception` 同义），合成一个值就分不开。
- (b) 一个通用值（如 `orchestrator_exception`）加 `phase` 字段：多一个字段、多一层 schema，信息量与 (a) 相同。
- (c) ③复用 `worker_exception`：少一个值，但 `report` 会把同步路径说成「worker 异常」，字面失实。
- (d) 不带 `exit_code`：`EXIT.LOCKED`（任务锁争用）与 `EXIT.FAIL`（写盘失败）分不开，而形状也会与 `worker_exception` 不同，schema 反而多一个分支。
- 守卫：只守 schema 不守 `report`，将来加第五个值时 `report` 会静默落兜底；V9 顺带守住。
- 代价：旧代码读不懂新取值（§6.3），回滚只回退代码。

**D2 第 ② 格怎么切、第 ① 格与纯文档跳过分支** — **已定**（取建议项）：①做；②只做**调用 `spawnDetached` 之前**那一段，派生之后一行不改、新登 EV-150；纯文档跳过分支不改，只改准描述。

- 派生前：没有 worker，写者就是 `startRun` 自己，`--cancel` / `--wait` 够不着（§3.5），前提成立。
- 派生后：实测（§2.3）worker 一定在跑、会自己收尾；此时写 `failed` 会与它互相覆盖。真正的问题是锁与闸门被提前放掉、孤儿可与第二个 worker 并发，那要改的是 `--start` 的失败语义，不属事后收尾。
- 切分判据取「调用之前」：`spawnDetached` 在子进程已起之后仍可能抛（P4），「返回之后」会在那一格与活着的 worker 双写。
- 纯文档跳过分支：终态写在第一步，后续失败时 run.json 已是 `success`；停在 `running` 只剩终态写入本身失败一种，收尾会调同一个写入函数、面对同一个失败面，零配额也造不出（§2.4）。
- 子项：三格留下的空运行目录**不顺带清理**。清理是在 `~/.trivium/runs/` 下删目录的破坏性动作，会话启动提示本身准确（「请人工检查后删除」），为它加删除路径得不偿失。

**D3 第 ③ 格同步路径做不做** — **已定**（取建议项）：做。

- 前提最容易成立（同步路径不写 status.json 与交接文件，没有别的写者），改动一处 `catch`、一条用例、一条变异。
- 它是手工调试入口（skill 不走），但本仓的探针、验收脚本和不少用例都走它；`by` 的取值趁这次一并定，免得日后再改一次 schema（D1 的回滚成本对每次加值都成立）。
- 不做的代价：D1 只加 `prepare_exception` 一个值，③留在 BACKLOG。

**D4 第 ④ 格 worker 猝死没人收尾** — **已定**（取建议项）：本主题不做，新登 EV-151（§6.4 第 3 条）。

- 实测（§2.6）缺口比 BACKLOG 写的窄：会话启动已提示 `--wait`，照做即可收尾；剩下的是「先起新一轮、遗留锁被回收」与「运行目录过了保留期」。
- 两个候选挂载点都要新的论证：会话启动清扫里收尾，意味着 Hook 写归档（今天 `sweepDeadRunningGates` 只碰 state.json），要论证 Hook 的时间预算、在别的会话里改出一处归档改动、清扫与 `--wait` 的并发（任务锁兜得住，但要写）；遗留锁回收时收尾，意味着 `lock.ts` 的通用获取逻辑要知道运行目录与归档，且持锁 pid 已死不等于 worker 已死（锁改写成 worker pid 之前 `--start` 就死了、worker 却已派生——与 EV-150 同一个窗口），判据要换成按运行目录复核 worker。
- 若要顺带：取「遗留锁回收时收尾」，判据与 `--wait` 的 `goneForArchive`（`run-protocol.ts` :697-700）同源、抽成共用函数；估计多一节论证、两条集成用例、两条变异。

**D5 收尾后要不要让 `latestRunMeta` / `gate` 跳过「没开跑就终止」的运行** — **已定**（取建议项）：不改。

- 波及面（R2、R3）：`latestRunMeta` 只有两个调用点，但 `resolveStageDriver` 同时决定 `review --start`、`topic resolve` 与 Hook 保护集。只在 `latestRunMeta` 里跳过，首轮失败那一格（C1a）会变成「扫到 1 份、一份都没取到」，`resolveStageDriver` 判 `corrupt`（:127），`cmdGate` 退 65「一份都读不出来」（:1120）——`--start` 被自己拒掉，出口循环（EV-148 同形）。要跳过就得同时改 `scanned` 的语义，碰 M10a 第 1 步的 Driver 判定纪律。
- 只在 `cmdGate` 跳过：C1b 那一格会让不带 `--run-id` 的 `gate --check` 校验第 1 轮并判通过，可闸门项记的是失败那一次，比较-交换不写、打「本机闸门指向另一次运行」——换来的是另一种让人困惑的读数。
- Driver 判定不受影响：骨架的 `driver` 按构造等于权威值（R5），跳不跳过取到的 Driver 相同。
- 现状的代价（§6.2）：窗口期内不带 `--run-id` 的 `gate` 指向终态骨架、报 `missing_disposition`，文案里有「用 --run-id 指回更早的完整轮次」兜底（`gate.ts` :214），下一次成功重跑同号覆盖即自愈；`report` 的说明会写清「准备阶段失败，未拉起审查员」。

**D6 EV-146 顺不顺带** — **已定**（取建议项）：不顺带，维持 todo。它碰 `cancelRun` 终态早退「不追溯改写」的语义，写者是 `--cancel`、对象是 `heartbeat_stale` 之后仍活着的进程；本主题四格的写者都是本进程或已退出的 worker，没有一格经过 `cancelRun` 的终态分支，合并只会让两件各需论证的事互相牵连。

**D7 BACKLOG** — **已定**（取建议项）：EV-145 结案；新登 EV-150（②派生后的孤儿 worker）与 EV-151（④遗留锁回收时不收尾）；纯文档跳过分支不另立条目（§6.4）。
