## 0. 结论速览

1. 新增一个模块 `src/trivium/tier-flags.ts` 承担三类旗标的**收集、键校验、取值校验、合并**，`cli.ts`（review / preflight）与 `topic-args.ts`（topic resolve）共用它——判定只有一份（EV-53 的教训）。
2. 命令行三值以「逐审核者的精确值」形态并入 `resolveTier` 的第四个参数；`checkModelSlugs` / `checkTierCombos` / `review` 准备阶段 / `--start` 告警复查四处传同一组。
3. 命令 A：`topic resolve` 输出加 `tiers` / `efforts` / `vendor_profiles` 三个字段，入口资产要求 S0.6、S2、S6 三处照抄。
4. 起草时核出一处计划外连带面（§1.5）：worker 交接文件不带档位旗标，`run.json` 的 `override_reason` 会把经 `--tier-〈id〉` 选出的同族模型说成「档位表默认模型」。本稿把档位旗标随交接文件带过去、改那一句文案——**不改 run.v2 的字段与形状**，只改一个既有字符串字段的取值措辞。请审查员核这是否越界（§6 第 3 条）。
5. **没有新的待拍板项**。

- `resolveTier(cfg, critic, stage, cli: TierOverrides)`：`TierOverrides = { tier?, model?, effort?, vendorProfile? }`（`adapters/base.ts`）。命令行一级目前只有 `model` 在生产路径上传。

### 1.3 对账测试

- `skill-flag-parity`：送审 skill 的 `argument-hint` 声明的旗标 ⊆ 第 3 步 `--start` 模板的槽位（豁免表为空）。

- `registry-parity`：白名单外模块不得出现 Agent id 字面（`src/trivium/` 内）。

### 1.4 本仓配置

本仓 `.trivium/config.yaml` 没有任何 `tiers`。本步上线后，在本仓写 `--tier-〈id〉` 会以「未定义 tiers」退 64——这是正确行为，不是缺陷；真实使用前需要用户先配 tiers（不在本步）。

### 1.5 起草时核出：`override_reason` 的归因

`review.ts:497-509` `overrideReasonFor`：模型与当轮 Driver 同族时，`modelOverrides[c]` 有值就写「用户经 `--model-〈id〉` 显式指定」，否则写「档位 〈表名〉 的默认模型」。worker 只拿得到交接文件里的 `modelOverrides`。于是经 `--tier-〈id〉` 选出的同族模型会被归因成档位表默认值——命令行的选择被记到配置头上，与第 4 步 P-6 要防的是同一类失实。

## 2. 方案

### 2.1 新模块 `src/trivium/tier-flags.ts`

```ts
type FlagKind = 'tier' | 'effort' | 'profile';
export interface TierFlagValues {           // 逐审核者的命令行精确值（不含 model）
  tier?: TierName; effort?: string; vendorProfile?: string;
}
export function tierFlagNames(): string[]   // tier-〈id〉 / effort-〈id〉 / profile-〈id〉，id 取 ALL_AGENT_IDS
export function collectTierFlags(get: (name: string) => string | null): Record<FlagKind, Record<string, string>>
export function assertTierFlags(cfg, driver, raw, picked): Partial<Record<CriticId, TierFlagValues>>
export function mergeCliOverrides(models, flags): Partial<Record<CriticId, TierOverrides>>
```

- **收集面 = 全部已登记 Agent**（与 `collectModelOverrides` 同理：写了但不可用的要落到明确报错上，不能被 `topic resolve` 当正文吞进焦点）。`profile-〈id〉` 同样按全部已登记收集。
- **键校验**：三类旗标的键都走与 `--model-〈id〉` **同一份判定**——把 `assertModelOverrideKeys` 的旗标前缀与「为它指定的 X」措辞参数化（`flag: 'model' | 'tier' | 'effort' | 'profile'`），既有 `--model-〈id〉` 的报错文案逐字不变（集成用例拿「当前可用」截字符串）。
- **`--profile-〈id〉` 的额外一格**：键通过后，该侧适配器未实现 `vendorProfilesFor` ⇒ 退 64，「〈id〉 没有厂商 profile 概念；`--profile-〈id〉` 不是 `--profile 〈档位表名〉`」。钩子取 `realAdapters()`，与预检同一份；源码不写任何 Agent id。
- **`--tier-〈id〉` 取值**：只收 `low` / `medium` / `high`，其余退 64 并列三档。
- **`--effort-〈id〉` / `--profile-〈id〉` 取值**：这里只查非空；是否在原生枚举 / 本机名单里由 `checkTierCombos` 判（与配置来源同一处、同一文案）。
- `realAdapters()` 的引入让本模块依赖适配器表；`critics.ts` 不引（避免它反向依赖适配器），参数化后的键判定仍住在 `critics.ts`。

### 2.2 三个入口

- `cli.ts` 的 review（`:620` 后）与 preflight（`:788` 后）：`collectTierFlags(name => flagString(args, name))` → `assertTierFlags(...)`（在 `assertModelOverrideKeys` 之后）→ 进 `reviewOpts.tierFlags` / `runPreflight({ tierFlags })`。help 两处补三行，写明「`--effort-〈id〉`、与 `agents.〈id〉.profile` 不同的 `--profile-〈id〉` 在 M11 第 6 步之前被预检拒绝（思考等级与厂商 profile 尚未透传）」。
- `topic-args.ts`：`NAMED_FLAGS` 并入 `tierFlagNames()`；`resolveNamedFlags()` 随之扩大（`entry-render-parity` 自动覆盖）；键校验后输出三个新字段：`tiers: Record〈id, 档〉`、`efforts: Record〈id, 值〉`、`vendor_profiles: Record〈id, 名〉`，没写时为 `{}`（与 `models` 同形，恒存在）。

### 2.3 接到解析与校验

- `ReviewOptions` 增可选 `tierFlags?: Partial<Record<CriticId, TierFlagValues>>`（缺省 `{}`）；`PreflightOptions` 同。
- `checkModelSlugs` / `checkTierCombos` 增第五个可选参数 `tierFlags`（缺省 `{}`），内部 `resolveTier(cfg, c, stage, { model: overrides[c], ...tierFlags[c] })`。既有调用与用例不动。
- 四个调用点传同一组：`preflight.ts:1032/1034`、`review.ts:816/822`、`review.ts:1145`（路由取模型——**`--tier-〈id〉` 选出的模型从这里进请求**）、`run-protocol.ts:491`（`--start` 告警复查）。
- **过渡闸**：不改判据（命令行来源已在内）；文案里「来自命令行」时点名旗标名（`--effort-〈id〉` / `--profile-〈id〉`）。
- **留痕空窗告警**（已定 ②）：`checkTierCombos` 对 `tierFlags[c].tier` 有值的侧追加告警「〈id〉：本轮档位名与来源尚未入档（M11 第 6 步起），事后只能从请求模型反推」；进预检 `warnings` 与 `--start` 的 `warnings`。

### 2.4 交接文件与 `override_reason`（§1.5）

- `run-protocol.ts` 交接 `options` 增可选 `tierFlags`（读侧缺席即 `{}`，旧交接文件可读）。
- `overrideReasonFor` 增一档：`modelOverrides[c]` 无值而 `tierFlags[c]?.tier` 有值 ⇒「用户经 `--tier-〈id〉 〈档〉` 选出了与当轮 Driver（…）同族的模型」。字段名、类型、出现条件都不变。

### 2.5 命令 A 与 B/C/D 的入口资产

- `src/entry-render.ts` 派生三个变量（与 `MODEL_HINT` 同论域：已启用审核者减本载体）：`TIER_HINT`（`[--tier-〈id〉 〈档〉]` 逐侧）、`EFFORT_HINT`（`[--effort-〈id〉 〈值〉]` 逐侧）、`VENDOR_PROFILE_HINT`（只列适配器实现了 `vendorProfilesFor` 的侧，今天渲染为 `[--profile-codex 〈名〉]`，codex 载体上为空）；以及对应的 `*_FLAGS` 反引号列表。`entry-render` 因此引入 `realAdapters()`——构建期渲染多一条依赖，请审查员核是否可接受（§6 第 4 条）；不可接受的退路是由注册表 vendor 推导，但那违背已定 ③「从钩子派生」，届时停下问用户。
- 四份命令契约的 `argument-hint` 在 `{{MODEL_HINT}}` 后追加三个提示变量。
- `run.contract.md`：S0.5 字段说明加 `tiers` / `efforts` / `vendor_profiles`；S0.6、S2、S6 三处「非空时逐个传对应的 `--tier-〈id〉` / `--effort-〈id〉` / `--profile-〈id〉`」，并写明「这几样与 `models` 一样必须三处同一组」；「本命令收到的…要一并传下去」那段补三类旗标与丢失后果（静默回退到配置档位，留痕看不出）。
- `partials/review/body.md`（命令 B/C/D）：第 2 步预检与第 3 步 `--start` 两处同样补；`--start` 模板加三个槽位（`skill-flag-parity` 要求）。
- 渲染产物 `npm run render` 同步；入口资产变了，提交后由用户重装。
