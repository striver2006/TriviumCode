## 3. 修法（论证取舍）

### D1 `readLock` 区分「不存在」与「不可解析」——采纳候选①

新增模块内函数 `readLockFile(p)`：`fs.open(p, 'r')` → `fh.stat({ bigint: true })` → `fh.readFile('utf8')` → `JSON.parse`，**同一个文件描述符**取内容与元数据，返回三态：

- `{ state: 'missing' }`：`open` 得 ENOENT；
- `{ state: 'present', content, identity, mtimeMs }`：`content` 为解析结果或 `null`（内容坏了）；`identity` 是 bigint 形态 `fstat` 的 `dev`、`ino`、`mtimeNs` 三段以冒号连接的字符串；
- `open` 的其他错误（EACCES、EISDIR…）：`{ state: 'present', content: null, identity: null, mtimeMs: null }`——与今天「读不了 ⇒ unparsable」同义。

`readLock(p)`（`release` / `inspectLock` 用）改为薄包装：`missing` 与 `content: null` 都返回 `null`，**对外行为逐字不变**。

`acquireLock` 撞 EEXIST 后改读 `readLockFile(p)`：**`missing` ⇒ 立刻 `continue` 重试 `link`，不告警、不判定、不回收、不查 `runTerminal`、不睡**。与今天 ENOENT 那一路的实际结局相同（今天是告警 → 回收失败 → `continue`），只去掉失实告警与那次会挪走活锁的回收；循环结构与预算不变（今天的回收分支同样 `continue` 且不查预算）。

### D2 不可解析锁的年龄取自同一次 `fstat`——候选③「改准」的落法

`unparsable` 的 2 s 防御改用 D1 同一描述符的 `mtimeMs`（与判为「不可解析」的是同一个 inode，不再二次按路径 `stat`）。`fileAgeMs` 只留给 `mtimeMs === null`（`open` 非 ENOENT 失败）那一格兜底，并改为：ENOENT ⇒ 返回 `null`，调用方按 `missing` 处理（`continue`）；其余失败仍 `+∞`（「存在但连 stat 都不行」与今天同样可回收，否则永久锁死）。

### D3 回收前按「身份」预检，不再挪走活锁——本稿新增，EV-149 的主修法

`reclaimStaleLock(p, expected, identity?)` 增加可选第三参：判定时那份锁文件的身份（D1 的 `identity`）。

1. **预检**：`rename` 之前先 `readLockFile(p)`：`missing` ⇒ 返回 false（别人已回收）；给了 `identity` 就要求相等，没给（F8 的外部调用方）就按今天的复验谓词比内容（`expected === null ⇒ content === null`；否则 `content === null` 或 pid 与 `acquired_at` 相符）。不符 ⇒ 返回 false，**不动 `p`**。
2. `rename(p, tmp)`；失败 ⇒ false。
3. **复验**改为同一谓词作用在 tmp 上（给了 `identity` 比身份，否则比内容）。相符 ⇒ 删 tmp、返回 true。

入口 B 的慢回收者在第 1 步看到的是新锁（身份不同）或空（`missing`），不再 `rename`。身份用 `dev:ino:mtimeNs` 而不是只用 inode：ext4 等文件系统会把刚释放的 inode 号立刻分给下一个新文件，只比 inode 在 Linux 上会把新锁认成旧锁；新锁由 `writeFile` 新写，`mtimeNs` 必然不同；`rename` 不改 inode 与 mtime，所以第 3 步比得上。

外部调用方（F8）不传身份、走内容预检：它们本来就在调用前按 run_id + pid 复核过，预检只是把「复核 → rename」之间换了人这一格挡在 rename 之前，行为只会更保守（多一种「不回收」结局，三处调用方对 false 都已有处理：两处忽略、:1558 播报「已被别的进程动过」）。

### D4 放回改用 `link`（目标已存在就原子失败）——采纳候选②，但定位是「可察觉」而非「可防止」

复验不符时：`link(tmp, p)` 放回，成功与今天等价；EEXIST ⇒ 说明预检与 `rename` 之间的残余窗口被命中、空档里已有人建锁——此刻已是两个持有者（§2.1 P2 的论证），放回方式救不回来；**不再覆盖**对方，删 tmp，并 `warn` 一句「回收主题「X」的锁时挪走了一把新建的锁且放不回，可能有两个持有者」，让这一格从「静默」变成「留痕」。其他错误同今天：删 tmp。

### D5 告警改在回收成功之后打，文字不变

F4 先告警后回收：回收因预检不符 / 别人先动手而放弃时，告警就是失实的（「回收了」而实际没回收）。改为 `reclaimStaleLock` 返回 true 才 `warn`，**文字逐字不变**（「回收主题「…」的遗留锁（原因 …，原持有者 pid …）」）。后果：多个进程同判一把遗留锁时，只有真回收的那一个告警（EV-149 用例的输家不再各打一条 `pid_gone`）。

### D6 tmp 名加随机段

F6：tmp 名改为 `${p}.stale-${pid}-${randomUUID()}`（模块已 import `randomUUID`）。D3 之后同进程并发回收者在预检后 `rename` 撞同名的格极窄，但同名会让后来者的 `rename` 覆盖前一个 tmp、复验读错文件；改名零成本。

| :--- | :--- | :--- |
| ① ENOENT 直接重试、不告警不回收 | 采纳（D1） | 堵 EV-173，同时切断 EV-149 的实测主因（入口 A） |

## 4. 残余与暂缓

- **R1 预检与 `rename` 之间的残余窗口**：一个回收者通过预检后被调度出去，另一回收者在此期间完成「`rename` → 复验 → 删除 → `link` 新锁」，前者醒来 `rename` 走的就是新锁。窗口从「一次 `ps` 派生」缩到「两次异步系统调用之间」；命中后 D4 让它留痕。关死它需要回收者之间的互斥（守卫文件 + 守卫的遗留判据），暂缓，BACKLOG 新登一条，编码后以 §6.3 的读数说明残余的实际频率。
- **R2 `release()` 的「读 → 比 → 删」窗口**（F7）：持有者被判遗留、锁被回收并由别人重建之后，若 release 恰在「读到自己 → rm」之间被别人重建，会删掉别人的锁。只在「活持有者被判遗留」时可达（`heartbeat_dead`、`runTerminal`），与本主题两条红无关；不并入，写进 BACKLOG 的 R1 同条作为同族残余。
- **R3 外部调用方不传身份**：F8 三处走内容预检，内容相同而 inode 不同（同一进程把同一份内容写了两遍）的格分不出；它们都在 worker 收尾、按 run_id + pid 复核，内容撞车需要同 pid 同毫秒 `acquired_at`，不改。
