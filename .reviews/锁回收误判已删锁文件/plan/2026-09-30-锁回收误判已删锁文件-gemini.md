## 总判断

最危险问题是 D3 预检在未传 identity 时沿用旧复验谓词，允许 content === null 匹配非空 expected，会导致外部调用方误挪损坏锁文件。
此外 D4 放回改用 link 时未明确成功分支必须删除 tmp，易导致孤儿硬链接残留。
D1 需补充文件描述符在 finally 中安全关闭，并保证内容损坏时保留 fstat 元数据供 D2 的 2s 防御复用。
方案核心路线（D1 missing 直接重试、D3 身份预检、D5 成功后告警）精准正确，探针实验扎实，所提问题仅需在计划修订中加固边界。
针对 §8 的重点关切均已在详细推演中给出明确正面结论（POSIX rename 不改 mtime，无活锁风险，R1 暂缓理由成立）。

## 审查意见（共 4 条：重要 2 ｜ 次要 1 ｜ 吹毛求疵 1）

### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `§3 D3 第 1 步` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：D3 回收前预检在未传 identity 时沿用旧复验谓词，若 expected !== null 却允许 content === null 通过预检，会导致外部调用方（如 worker 正常收尾放锁）在磁盘锁文件损坏时误判相符，从而把损坏文件误挪走。

**依据**：查阅 src/trivium/lock.ts:171-174 与 src/trivium/run-protocol.ts:745-750, 1556-1562, 1872-1877。旧代码 expected !== null 时允许 got === null 是针对已 rename 到 tmp 后的复验容错；但在预检阶段（未 rename 之前），当外部调用方传入非空 expected 时，磁盘内容为 null 绝不代表属于自身。

**建议**：修改 D3 预检谓词规范：当 expected !== null 时，预检必须严格要求 content !== null 且其 pid 与 acquired_at 与 expected 一致，禁止在 expected 有值时放行 content === null。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `§3 D4` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：D4 将放回操作由 fs.rename 改为 fs.link，但仅说明在 EEXIST 与其他异常时删 tmp，未明确在 link 成功后同样必须删除 tmp，会导致放回成功后在磁盘永久遗留孤儿硬链接文件。

**依据**：查阅 src/trivium/lock.ts:186-191。旧代码使用 fs.rename(tmp, p)，源路径自动移走；而 POSIX link 系统调用创建硬链接后源文件 tmp 依然存在。若 link 成功后不显式 rm(tmp)，.trivium/lock/ 目录将泄漏 .stale-* 孤儿文件。

**建议**：在 D4 中明确放回后的资源清理契约：无论 link 成功、报 EEXIST 还是抛出其他错误，最后必须无条件执行 await fs.rm(tmp, { force: true })（如放入 finally 块中）。

### AGY-03 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `§3 D1, D2` |
| 类别 | maintainability ｜ 层次 plan |

**问题**：D1 未明确 fs.open 返回的文件描述符的关闭保证（try...finally），且未明确 JSON.parse 语法错误时应保留已由 fstat 拿到的 identity 与 mtimeMs。

**依据**：查阅 src/trivium/lock.ts:93-99 及计划 D1、D2。若 fh.close() 未由 finally 保证，异常时会发生描述符泄漏；若解析失败将 mtimeMs 归为 null，D2 的 2s 防御将退回到按路径 stat，破坏描述符复用初衷。

**建议**：明确 readLockFile 内部使用 try...finally 确保 fh.close()；当文件存在但内容损坏（JSON.parse 抛错）时，返回保留有效的 identity 与 mtimeMs，仅 content 为 null。
