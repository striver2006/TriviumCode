## 2. 探针读数与定性（零配额，不改 `src/`）

### 2.1 同进程确定性复现 `probe-inproc.mjs`

给 `fs.promises` 的 `readFile` / `rename` 打桩控制 `lock.js` 内部时序（`lock.ts` 取的是同一个对象，调用时按属性查找）。读数 `probe-inproc-3e38d29.json`：

| 格 | 构造 | 读数 |
| :--- | :--- | :--- |
| P1 | 活着的临界区锁；`acquireLock` 撞 EEXIST 后**读锁之前**把锁文件删掉（= 持有者恰在此刻释放） | 打出「回收主题「探针抢锁」的遗留锁（原因 unparsable，原持有者 pid ?）」；随后拿到锁 |
| P1c | 对照：同样的活锁、不删 | 抛 70，无告警 |
| P2 | 遗留锁（pid 已死）；回收者 B 判定后、rename 前被扣住；A 回收并建好新锁 LA；放开 B：B 把 LA 挪走，B 复验期间 C 抢锁 | **C 在空档里拿到句柄，那一刻 A 仍持有**（`double_holder: true`）；B 随后 `rename` 放回 LA、覆盖 C 的锁；B 自己抛 70 |

**P2 的要点**：双持有在「放回」**之前**就已成立——C 拿到句柄的那一刻，A 的锁文件躺在 B 的 tmp 里。所以候选②「放回改用目标已存在就原子失败」**单独不能消除双持有**：C 链进来之后，放回无论覆盖（今天：A 的文件留下、C 的丢失）还是原子失败（改后：C 的留下、A 的丢失），A 与 C 都自以为持锁。放回方式只决定**哪一份文件留在原位**、以及**能不能察觉**。

### 2.3 定性

- **EV-173 的成因坐实**（P1 + x1）：ENOENT 被读成「不可解析」、年龄取 `+∞` 越过防御，打出失实告警；x1 形状下没有双持有、没有丢更新，只有告警失实。
- **EV-149 不是用例误判**：200 轮里「先后两次合法获取」0 轮、晚就绪 0 轮，唯一的双赢家区间重叠。它是真缺陷，有**两条入口**，共同点是「回收者把一把**活锁**挪走、在 `p` 上开出空档」：
  - **入口 A（实测主因）**：EV-173 的 ENOENT 误判把 `reclaimStaleLock(p, null)` 送到一把刚建好的活锁上（idx 125；F11 中在场）；
  - **入口 B（P2 确定性复现；F11 中不能排除）**：两个回收者对同一把遗留锁各自判定，慢的那个在快的那个建好新锁之后才 `rename`。
- 用户决策「若查明是用例误判就改用例、不硬改 `lock.ts`」的前提不成立，故按缺陷修 `lock.ts`；用例同时加持锁区间与告警断言（§5.2），把「真双持有」与「合法先后获取」从读数上分开。

## 3. 修法（论证取舍）

### D1 `readLock` 区分「不存在」与「不可解析」——采纳候选①

新增模块内函数 `readLockFile(p)`：`fs.open(p, 'r')` → `fh.stat({ bigint: true })` → `fh.readFile('utf8')` → `JSON.parse`，**同一个文件描述符**取内容与元数据，描述符在 `finally` 里关闭。结局：

- `{ state: 'missing' }`：`open` 得 ENOENT；
- `{ state: 'present', content, identity, mtimeMs }`：`content` 为解析结果；**解析失败时 `content: null`，`identity` 与 `mtimeMs` 照给**；`identity` 是 bigint 形态 `fstat` 的 `dev`、`ino`、`mtimeNs` 三段以冒号连接的字符串；
- `open` 成功后 `stat` 失败：`{ state: 'present', content: null, identity: null, mtimeMs: null }`；`stat` 成功而 `readFile` 失败：`content: null`，`identity` / `mtimeMs` 照给；
- `open` 的其他错误（EACCES、EISDIR…）：`{ state: 'present', content: null, identity: null, mtimeMs: null }`。

后三格都与今天「读不了 ⇒ unparsable」同义，**不抛异常**。

`readLock(p)`（`release` / `inspectLock` 用）改为薄包装：`missing` 与 `content: null` 都返回 `null`，**对外行为逐字不变**。

`acquireLock` 撞 EEXIST 后改读 `readLockFile(p)`：**`missing` ⇒ 立刻 `continue` 重试 `link`，不告警、不判定、不回收、不查 `runTerminal`、不睡**。与今天 ENOENT 那一路的实际结局相同（今天是告警 → 回收失败 → `continue`），只去掉失实告警与那次会挪走活锁的回收；循环结构与预算不变（今天的回收分支同样 `continue` 且不查预算）。

### D2 不可解析锁的年龄取自同一次 `fstat`——候选③「改准」的落法

`unparsable` 的 2 s 防御改用 D1 同一描述符的 `mtimeMs`（与判为「不可解析」的是同一个 inode，不再二次按路径 `stat`）。`fileAgeMs` 只留给 `mtimeMs === null` 那一格兜底，并改为：ENOENT ⇒ 返回 `null`，调用方按 `missing` 处理（`continue`）；其余失败仍 `+∞`（「存在但连 stat 都不行」与今天同样可回收，否则永久锁死）。

### D3 回收前按「身份」预检，不再挪走活锁——EV-149 的主修法

`reclaimStaleLock(p, expected, identity?)` 增加可选第三参：判定时那份锁文件的身份（D1 的 `identity`）。「相符」谓词：

- 给了 `identity`：读到的 `identity` 相等（非 null）；
- 没给（F8 的外部调用方）：`expected === null` ⇒ 内容为 null；`expected` 非空 ⇒ **内容可解析且** pid 与 `acquired_at` 都相符（AGY-01：不再容忍 `null`——预检时读不出说明有人正在改写这份锁；rename 之后读不出说明有人正往这个 inode 里写，删它等于删一把正在改写的活锁，放回更保守）。

步骤：

1. **预检**：`rename` 之前 `readLockFile(p)`：`missing` ⇒ 返回 false；不相符 ⇒ 返回 false，**不动 `p`**。
2. `rename(p, tmp)`；失败 ⇒ false。
3. **复验**：同一谓词作用在 tmp 上。相符 ⇒ 删 tmp、返回 true；不符 ⇒ D4。

入口 B 的慢回收者在第 1 步看到的是新锁（身份不同）或空（`missing`），不再 `rename`。身份用 `dev:ino:mtimeNs` 而不是只用 inode：ext4 等文件系统会把刚释放的 inode 号立刻分给下一个新文件；新锁由 `writeFile` 新写，`mtimeNs` 必然不同；`rename` 不改 inode 与 mtime，所以第 3 步比得上。适用范围是本地文件系统（APFS / ext4）；网络卷不在支持面内，其上属性缓存若回吐旧值，退化结局是「预检不符 ⇒ 不回收 ⇒ 等待者最终 70」，不是双持有（LLD 写明）。

外部调用方不传身份、走内容谓词：三处本来就在调用前复核过，预检只是把「复核 → rename」之间换了人这一格挡在 rename 之前。

### D4 放回改用 `link`（目标已存在就原子失败）——采纳候选②，定位是「可察觉」而非「可防止」

复验不符时：`link(tmp, p)` 放回；EEXIST ⇒ 残余窗口被命中、空档里已有人建锁——此刻已是两个持有者（§2.1 P2 的论证），放回方式救不回来；**不覆盖**对方，并 `warn` 一句「回收主题「X」的锁时挪走了一把新建的锁且放不回，可能有两个持有者」，让这一格从「静默」变成「留痕」。**无论 `link` 成功、EEXIST 还是其他错误，最后都在 `finally` 里删 tmp**（AGY-02：`link` 不像 `rename` 会顺带移走源）。

### D5 告警改在回收成功之后打，文字不变

F4 先告警后回收：回收因预检不符 / 别人先动手而放弃时，告警就是失实的。改为 `reclaimStaleLock` 返回 true 才 `warn`，**文字逐字不变**。后果：多个进程同判一把遗留锁时，只有真回收的那一个告警。已核（三侧同结论）：「回收主题」告警只被 `lock-cross-process.test.ts` :300 的 `doesNotMatch` 消费，没有调用方或用例依赖「每个判定者都告警」。

### D6 tmp 名加随机段

F6：tmp 名改为 `${p}.stale-${pid}-${randomUUID()}`（模块已 import `randomUUID`）。

### D7 `--cancel` 收尾按回收结果播报（CODEX-01）

`run-protocol.ts` :1876-1877 改为与 :1558-1562 同形：返回 true ⇒ `say('已回收主题「…」的锁')`（原句不变，`run-protocol.test.ts` :874、:1170 仍成立）；false ⇒ `step('主题锁在回收时已被别的进程动过，未回收')`。复核条件（只核 `run_id`）不改——那是既有行为，D3 的内容谓词已按 pid 与 `acquired_at` 兜住。:745 的 `soft` 标签只在抛错时出现，不改。

| 候选 | 结论 | 理由 |
| :--- | :--- | :--- |
| ① ENOENT 直接重试、不告警不回收 | 采纳（D1） | 堵 EV-173，同时切断 EV-149 的实测主因（入口 A） |
| ② 放回改用原子失败 | 采纳（D4），但**不作为 EV-149 的修法** | P2 证明双持有成立在放回之前；它换来的是可察觉 |

## 4. 残余与暂缓

- **R1 预检与 `rename` 之间的残余窗口**：一个回收者通过预检后被调度出去，另一回收者在此期间完成「`rename` → 复验 → 删除 → `link` 新锁」，前者醒来 `rename` 走的就是新锁。窗口从「一次 `ps` 派生」缩到「两次异步系统调用之间」；命中后 D4 让它留痕。关死它需要回收者之间的互斥（守卫文件 + 守卫的遗留判据），暂缓，BACKLOG 新登一条，写进 §6 的实测频率。
- **R2 `release()` 的「读 → 比 → 删」窗口**（F7）：持有者被判遗留、锁被回收并由别人重建之后，若 release 恰在「读到自己 → rm」之间被别人重建，会删掉别人的锁。只在「活持有者被判遗留」时可达（`heartbeat_dead`、`runTerminal`），与本主题两条红无关；不并入，写进 R1 同条作为同族残余。
- **R3 外部调用方不传身份**：F8 三处走内容谓词，「内容相同而 inode 不同」的格分不出；需要同 pid 同毫秒 `acquired_at`，不改。
