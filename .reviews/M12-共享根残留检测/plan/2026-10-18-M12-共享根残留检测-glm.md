**问题**：计划把 sharedResidueNames 定为必填字段（未写问号，与同段的 exemptPaths? 形成对照），但既有用例 test/unit/entry-collisions.test.ts 第 49-52 行与 61-63 行手写了 EntryScanTarget 字面量、不含该字段。仓库用 tsc --strict 做静态检查，对象字面量缺必填属性会直接编译失败，实施时这两处既有用例必须补 sharedResidueNames: []——这与 §3.1「既有用例一条不改」（也是任务目标「既有用例逐条不变」的落点）字面冲突。断言本身确实不受影响（两处都是构造输入而非断言），但计划没有说明「补字段不算改用例」，代码审阶段会对这条承诺是否兑现产生争议。

**依据**：test/unit/entry-collisions.test.ts:49-52 手写目标 { agent: 'codex', skillsRoot: install, readRoots: [install, shared], names: […], residueNames: ['dual-critic', 'entry'] }，61-63 行另一处同样手写且 residueNames 为空；计划 §2.1 写「sharedResidueNames: readonly string[]」无可选标记、「exemptPaths?: readonly string[]」有可选标记；AGENTS.md 常用命令节写明 npm run typecheck 是 tsc --noEmit（strict），缺必填属性的测试文件过不了这道闸。

**建议**：在计划里二选一定清：把 sharedResidueNames 也设为可选（缺省按空数组处理，不查），或在 §3.1 明确「既有用例仅补 sharedResidueNames: [] 这类构造字段、断言一条不动」不算改用例。两个方向都行，但要写下来，避免实施与代码审对「逐条不变」的口径各执一词。

### GLM-02 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `计划 §0 D-6、§2.1（exemptPaths 求值）；对照 src/trivium/asset-root.ts:17-23 与 doctor.ts:583-586` |

**问题**：豁免路径按扫描当下的 env/home 求值（resolveAssetRoot(undefined, se.env, se.home)），存在一个时序性误报边界：用户安装时设了 TRIVIUM_ASSET_ROOT 指到共享根下的 dual-critic（正是 D-6 列举要保护的场景），之后在不带该变量的 shell 里跑 doctor 或 preflight 时，豁免求值为缺省位置 ~/.claude/skills/dual-critic，共享根里那份正在服役的活运行时（doctor 进程本身就是从它跑起来的）会被报成 shared-residue 残留。只进 warnings 不阻断，但告警内容失真（那份随安装更新，并非「不随安装更新的历史拷贝」）。A-1/A-2 的「TRIVIUM_ASSET_ROOT 指到共享根下的 dual-critic」格都在同一进程内设变量再跑，暴露不出这个差异。

**依据**：src/trivium/asset-root.ts:17-23 的求值序是 override ?? env['TRIVIUM_ASSET_ROOT'] ?? 缺省位置，环境变量不在时回落 ~/.claude/skills/dual-critic；entry-collisions.ts 的 entryScanEnv（:128-132）生产取 process.env 与 os.homedir()，shell 未设该变量时 D-6 的豁免即与安装时的 plan.runtimeRoot 错位；计划 §5 A-1/A-2 的对应格均为子进程内显式设置变量后运行，不存在跨 shell 的时序差。

**建议**：不必为此改实现（读 wrapper 指向之类的解法复杂度不成比例），但应在 §7 判据边界里登记这条：豁免按扫描时环境求值，安装时装了 TRIVIUM_ASSET_ROOT、扫描时未设的 shell 里活运行时会被误报为残留（仅告警、不阻断、不影响安装器——安装器在安装场景内 env 一致）。如愿意，可顺手在 A-2 加一格「变量只在安装时设、doctor 不带变量」的读数，把边界的实际表现留痕。
