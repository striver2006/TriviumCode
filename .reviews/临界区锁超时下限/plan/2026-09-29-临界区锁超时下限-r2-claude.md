## 2. 下限的语义与后果

### 2.1 判定矩阵（阈值记 T，下限 F = 30 s，锁为 `critical`、持有者是同一活进程、`runTerminal` 不为真）

| T | 改前：何时判 `heartbeat_dead` | 改后 | 变化 |
| :--- | :--- | :--- | :--- |
| T ≥ F（含 30、120） | `age > T` | `age > max(T, F) = age > T` | 无 |
| T < F（如 0.05、2、29.5） | `age > T` | `age > F` | 持有时长落在 (T, F] 的活持有者不再被回收 |

其余判据与 `run` 锁不经年龄判据，两列相同。**持有者已死**（崩溃、被杀）走 `pid_gone`，与年龄无关，改后仍是**立即**回收——下限只推迟「活着但卡住」的持有者被回收的时刻。

### 2.2 代价：T < F 时卡住的活持有者

改前 T = 2 s 时，一个活着但卡住（例如被 SIGSTOP、磁盘挂死）的临界区持有者，等待者约 2 s 后就会回收它；改后要等 30 s。
`withTopicLock` / `withGlobalLock` 的重试预算约 3 s / 4 s（L4），用尽抛 70——**这正是缺省配置（120 s）今天的行为**：
改后小阈值用户在这一格得到的，与缺省用户一模一样，不会比缺省更差。换来的是 (T, 30 s] 内的正常慢写不再被判死、不再出现两个持有者。

### 2.3 为什么 30 s 足够、又不会过头

- 足够：临界区的正常时长是毫秒到数十毫秒（L6），30 s 高出三个数量级以上；
- 不过头：它不高于任何「阈值 ≥ 30 s」的配置，这些配置判定逐字不变；而缺省 120 s 下卡住的活持有者要等 120 s，30 s 只会更早。
- 取值与语义由用户决策定为「worker 心跳间隔」：它是这个系统里「多久没有进展才值得怀疑」的最小单位，`heartbeat_stale_s` 本来就是按它的倍数设计的（缺省 = 4 个周期）。

### 2.4 剩余风险（不在本主题消除）

临界区真的持有超过 30 s（活着），等待者仍会判 `heartbeat_dead` 回收——两个持有者并存的窗口仍在，只是阈值从「用户可配到亚秒」变成「至少 30 s」。
缺省 120 s 下同一风险今天就存在（> 120 s）。彻底消除要给临界区引入租约续期或 fencing，属锁语义重设计，超出 EV-161；不另登 BACKLOG（没有观察到的失效形态，只是理论窗口）。

## 3. 改法

### 3.1 落在 `judgeStale` 一处（单一来源）

```ts
// lock.ts
import { WORKER_HEARTBEAT_MS } from './status.js';

/**
 * 短临界区锁的持有超时（EV-161）：max(heartbeat_stale_s, worker 心跳间隔)。…
 */
export function criticalHoldTimeoutMs(heartbeatStaleMs: number): number {
  return Math.max(heartbeatStaleMs, WORKER_HEARTBEAT_MS);
}

// judgeStale 的年龄判据（:133）
if (Number.isFinite(age) && age > criticalHoldTimeoutMs(opts.heartbeatStaleMs) && lock.kind === 'critical') {
```

- **不另起常量**（用户决策）：下限就是 `WORKER_HEARTBEAT_MS`，在 `lock.ts` 里只通过这一个函数出现；导出这个函数是为了让单测直接钉住「下限 = `WORKER_HEARTBEAT_MS`」与 `max` 的形状，它不是第二个常量。
- **判据的书写顺序不动**：只把 `opts.heartbeatStaleMs` 换成 `criticalHoldTimeoutMs(opts.heartbeatStaleMs)`；`Number.isFinite(age)`、`lock.kind === 'critical'` 与前面三条判据原样。
- 非有限值语义不变：`Math.max(NaN, F)` 为 NaN、`age > NaN` 为假，与改前 `age > NaN` 同为「不回收」；`Infinity` 同理。配置契约保证 T > 0，这两格只是防御，与改前一致。
- `judgeStale` 的文档块、`AcquireOptions.heartbeatStaleMs` 的注释补一句「对 `critical` 锁按 `criticalHoldTimeoutMs` 取下限」；年龄判据旁那句「持有超过心跳阈值说明持有者卡死了」改成「持有超过持有超时（阈值与心跳间隔取大）」。

### 3.2 为什么不落在调用方

1. **调用方有 29 处**（L7），各自 `heartbeat_stale_s * 1000`；落在调用方要么改 29 处、要么新增一个包装函数让它们都改调——任何一处漏改、或以后新增的调用方忘了调，都是一个静默回到旧行为的口子，达不到「单一来源」。
2. **同一个值还要原样给 worker 失联判定**（L7 末句）：在「读配置」那一层（`ctx` / `Config`）把阈值抬到 30 s，会连带改掉 `interpretStatus` 与 `--wait` 的行为——违反用户决策。能区分「锁」与「失联」的地方只有锁模块本身。
3. `lock.ts` 内 `heartbeatStaleMs` 只有 `judgeStale` 一个消费点（L2），而年龄判据只对 `critical` 生效（L1）——落在那一行，恰好只影响「`critical` 锁的年龄判据」这一件事，`run` 锁与其余判据**在代码上**就碰不到。
4. **没有旁路**（计划双审 r1 codex 补）：`src` 内 `kind: 'critical'` 只出现在 `lock.ts` :289（`withTopicLock`）与 :319（`withGlobalLock`），两条入口的回收全经 `acquireLock → judgeStale`；
   `review.ts` 里的「同形内联回收」指的是闸门状态回收，经 `setGateChecked → withGlobalLock` 同一判据；`bumpStopBlockCount` 用唯一文件计数、不经锁。

### 3.3 导入方向

`lock.ts` 新增 `import { WORKER_HEARTBEAT_MS } from './status.js'`。`status.ts` 的依赖闭包（`types`、`util/fsx`、`run-files`、`util/exec`）不含 `lock.ts`（H2），不成环；
`config.ts` 对 `lock.js` 的动态导入不受影响。构建是单 bundle，运行时无新增文件。

`gate-loop.test.ts` :951「心跳过期但进程仍在的 worker_lost」（阈值 2，:957）：桩 `timeout` 立即返回、超时不重试，worker 看到 `phase: running` 后被 SIGSTOP 的那一刻，
有**小概率**正处在收尾的 `registerRun`（任务锁）或 `setGateChecked`（全局锁）里、拿着 `critical` 锁被冻住（`review.ts` :1688 / :1696）。

- 改前：冻 2.5 s 后，`--wait` 的 `releaseRunningGateEntry` 把这把锁按 `heartbeat_dead` 回收；
- 改后：回收不了——全局锁约 4 s 重试后抛 70，被 `releaseRunningGateEntry` 吞掉（`state.ts` :281-290）；任务锁那一步约 3 s，转成 skipped。
- 用例只断言：非 0、`heartbeat_stale`、凭据副本未抹、载体仍在、无 `scrub.json`——都不依赖闸门回收或登记收尾，**照常成立**；这一分支多耗约 3～7 s，远小于 `--wait` 的 60 s 上限。
- 顺带说明：改前这一分支里，被冻的 worker 与 `--wait` 事实上是两个 `critical` 持有者并存（worker 被 SIGCONT 后会继续写）——正是 EV-161 要消除的形态；改后 `--wait` 不再越权回收，闸门留给后续清扫。**不改构造**。
