## 3. 改法

### 3.1 新原语：`fsx.ts` 导出 `renameOverwriting`

```ts
export interface RenameRetryOptions {
  /** 判定平台；缺省 process.platform。测试注入 'win32' 即可在 macOS 上跑 win32 分支 */
  platform?: NodeJS.Platform;
  /** 重试间隔表（毫秒）；缺省 [25, 50, 100, 200, 400]。测试注入小值避免真实等待 */
  delaysMs?: readonly number[];
  /** 被测改名函数；缺省 fs.rename。回归锚的故障注入点 */
  rename?: (from: string, to: string) => Promise<void>;
}

/**
 * 改名覆盖目标。win32 上对 EPERM / EACCES / EBUSY 做【有界短重试】（EV-260）：
 * 间隔按 delaysMs 指数退避，耗尽后抛最后一次的原始错误；其余错误码与非 win32
 * 平台单次、立即抛出（POSIX 行为与原先逐字相同）。onExhausted 在 win32 三码
 * 耗尽、抛出之前回调（writeAtomic 用它清本次临时文件）；其自身异常不再捕获、
 * 顶替原错误抛出（清不动比吞错更该被看见——写入侧 onExhausted 自带兜底吞错）。
 */
export async function renameOverwriting(
  from: string,
  to: string,
  opts?: RenameRetryOptions & { onExhausted?: () => Promise<void> },
): Promise<void>
```

实现轮廓（细节编码时定，语义以此为准）：

- 平台取 `opts?.platform ?? process.platform`；**非 `win32`：`await rename(from, to)` 一次、直接返回 / 抛出——不进任何循环**。
- `win32`：循环尝试；捕获后取 `code`，`EPERM` / `EACCES` / `EBUSY` 之外**立即 `throw e`**（不清理、与今天行为一致）；可重试码若还有剩余间隔则 `sleep(delays[i])` 后再试；间隔用尽 → `await onExhausted?.()` → `throw` **最后一次捕获的原始错误对象**（引用不换、不包装）。
- 成功即返回；不改动 mtime 之类任何额外语义。

**参数取值理由（D1，用户要求在计划里给）**：缺省 `delaysMs = [25, 50, 100, 200, 400]`，共 6 次尝试、**总睡眠上界 775 ms（< 1 s）**。依据：

1. **争用窗的现实尺度**：自家双写者（`--start` 与 worker 各自的 `writeAtomic`）争用的是对方 rename 的一瞬，毫秒级——首个 25 ms 档即解；杀毒 / 索引服务对刚写文件的实时扫描通常几百毫秒内放开——100 / 200 / 400 ms 档覆盖。F2 的失败是**单发**的（同文件单跑全过），说明争用窗远小于秒级。
2. **上界对预算的占比**：Hook 预算 15 s（B1），775 ms 占 5%，不会把 Hook 拖到「超时即放行」；心跳 / 临界区判定 30 s 级（B2），单次写 +775 ms 不影响任何判定；`--start` 的用户可感延迟在「偶发 +775 ms」与「直接内部错误退出」之间取前者。
3. **每次调用独立计界**：上界按**单次 `writeAtomic`** 计，不设全局预算——`--start` 一次最多写几个状态文件，极端全撞也就几秒；满负载下不会叠加成无界等待（每写的重试只由自己的争用触发，争用消失重试即停）。
4. **不采 graceful-fs 的零延迟紧循环**：满载下空转烧 CPU；指数退避以最少的尝试次数覆盖最长的现实争用窗（6 次尝试覆盖 775 ms，线性 25 ms 档要 32 次才等效）。
5. `EBUSY` 在 rename 上的本机实测样本没有（F2 只见过 EPERM）——纳入它是与 graceful-fs 同列的前瞻口径，任务书点名三码，照办。

### 3.2 `writeAtomic` 接线

```ts
export async function writeAtomic(target: string, content: string | Buffer, opts?: RenameRetryOptions): Promise<void> {
  await ensureDir(path.dirname(target));
  const tmp = `${target}.tmp-${process.pid}-${Date.now()}`;
  await fs.writeFile(tmp, content);
  await renameOverwriting(tmp, target, {
    ...opts,
    onExhausted: async () => {
      // win32 三码耗尽：清掉本次 tmp（尽力而为，清不动不吞掉原始错误），POSIX 与非三码不进这里
      await fs.rm(tmp, { force: true, maxRetries: 3 }).catch(() => undefined);
    },
  });
}
```

行为面：

- **POSIX / 非 win32**：`renameOverwriting` 单次直通——单次 rename、错误原样抛、tmp 不清，与今天逐字相同（F1）。
- **win32 + 三码 + 耗尽**：清 tmp（`fs.rm` 自带 maxRetries 3，应对 AV 也按着 tmp 的边角）后抛**最后一次的原始错误**。清不动时 `onExhausted` 内部已吞（`.catch(() => undefined)`），原始错误照抛——「抛原错误」优先级高于「tmp 必清」，残件只留警告级后果（既有 `*.tmp-*` 形状，消费者都认得，F5）。
- **win32 + 非三码**：立即抛、tmp 不清（与今天一致；任务书只把「清 tmp」绑在重试最终失败上）。
- **并发「后写者胜」不变**：两个写者各持独立 tmp（pid+时间戳），rename 覆盖语义不因重试改变；重试只是把**同一个**覆盖动作延后，最终内容 = 最后一次成功 rename 的内容（§4.1 T6 钉住）。
- `fs.writeFile(tmp)` 一步不加任何重试（§0 不做栏的口径）。

### 3.3 三个调用点逐个结论（D2，用户点名必须逐个写明）

| 调用点 | 结论 | 理由 |
| :-- | :-- | :-- |
| **A. `lock.ts:289` `renameAndVerify` 的 `fs.rename(p, tmp)`** | **不加重试，保持原样** | 这是回收仲裁步：rename 的原子性保证「只有一个回收者能成功」，**失败是合法结局**（`catch → return false`＝「别人先动手了」），不是暂时性错误。给它加三码重试会把「仲裁输了」误读成「再试试」，拉长认领文件（`RECLAIM_CLAIM_STALE_MS` 10 s 语义）与「挪走的可能是活锁」窗口的时间面；而短暂 EPERM 在现语义下只是**本轮不回收**，`acquireLock` 上游有自己的重试预算（`retries × retryDelayMs`，C1），下一轮自然再试——fail-closed 且无丢失。锁**获取**（C2）走 `link` 的 O_EXCL，不经 rename，不在讨论面 |
| **B. `review.ts:2547` `stashVoidedOutput` 的 `fs.rename(outDir, target)`** | **与 writeAtomic 同口径**：换成 `renameOverwriting(outDir, target)`（缺省参数即 win32 三码重试） | 普通挪移、非判定步：失败不走仲裁而走「warn + 尽力整删 + 照样重跑」的尽力路径（C3）。但它的目的是防重跑侧读回作废输出，win32 上同样的句柄争用会让这道防护偶发失效——提高它在 win32 上的成功率与 `writeAtomic` 同理。目录 rename 与文件 rename 走同一 `fs.rename` 语义，原语通用。耗尽后**照旧落入既有 catch**（warn + `tryRemoveTempDir(outDir)` 兜底 + 重跑），外层行为面零变化；不传 `onExhausted`（清理决策归既有 fallback，不由改名原语代删 `outDir`） |
| **C. `doctor-deadline.ts:239` `TempDirLedger.update` 的手写 tmp+rename** | **与 writeAtomic 完全同口径**：整段改调 `writeAtomic(this.file, JSON.stringify({...}))`，删掉手写 tmp 与 `fs.mkdir`（writeAtomic 自带 `ensureDir`） | 它就是 `writeAtomic` 的形状（C4）：同目录 tmp + rename 覆盖 + 吞错 chain。改后获得 win32 重试与耗尽清 tmp；台账清扫 `LEDGER_RE` 不认 `.tmp-*` 后缀（C4），tmp 名变化（`.tmp` → `.tmp-<pid>-<ts>`）不影响任何读取面。外层 `this.chain` 串行与 `.catch(() => undefined)` 吞错语义逐字保留。顺带修掉「rename 失败留 `.tmp` 残件」的既有小残件面 |

### 3.4 注释与文案

`fsx.ts` 头部「原子写」注释补一行 win32 重试口径（EV-260）；`writeAtomic` 的 JSDoc 写明三种结局（成功 / win32 三码耗尽清 tmp 抛原错误 / 其余立即抛）与 POSIX 零变化。`review.ts`、`doctor-deadline.ts` 改动处各留一行指向 EV-260 的短注（对齐仓库注释密度，不展开）。
