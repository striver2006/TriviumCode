### 5.2 两个候选

**① 按设计回写。** `--check` 通过时把 `adjudication_complete` 置 `true`。E6、E7 迫使它带三条限制：

1. 只写这个布尔，**不写** `warnings`。否则要新开一个字段，那就是改 schema。
2. 只在该轮 run.json **尚未被 git 跟踪**时写（`readAtHead` 为 null），已跟踪就跳过并提示一句。
3. 写入要在主题锁里做，与 `updateTask` 同一纪律。

- 字段语义变成两个时代：本主题之前的轮次恒为 `false`，之后的轮次视「`--check` 发生在提交之前还是之后」而定。读者仍然要看注记才敢信它。
- 往「不可变锚」旁边加了一个带时间窗条件的写入者，这正是锚规则最怕的形态。
- 字段没有读者，收益只在人读留痕。

**② 不回写，改注明语义。** 字段保留，因为它是 schema 必填项，删掉就要改两版 schema，还牵涉历史读者。把语义写实：

- 落点：run.v1 / run.v2 schema 的 `description`；`types.ts` :1438 注释；主设计 §7 第 6 步改成「通过 → 按 entry 分流闸门（不回写 run 元数据，见 6.7 注记）」；§6.7 示例改成实现里真实出现的组合，旁注 EV-133。

**建议 ②**。①要绕开两个陷阱（E6、E7），加完限制后字段仍然不可信、仍然没有读者；② 零风险，而且让设计与实现一致。
EV-128 同属「run.json 收尾后不再更新」这一类，②的注记顺带写明这是一条**有意的**不变量（锚规则的推论）。EV-128 的处置到时就有了依据，但本主题不处理它。
