## 2. 改动一：构建标识（r5 §3.3.2，EV-82 所有分支共用的第一项）

**目的**：让「安装副本与仓库 HEAD 同版」有机器证据，T2 假阴性时先核它（r5 §3.3.2 排查次序）。

- **写入**：`scripts/build.mjs` 构建主包时，取 `git rev-parse HEAD` 与 `git status --porcelain -- src scripts package.json` 是否为空，
  经 esbuild `define` 注入一个常量（形如 `__TRIVIUM_BUILD__ = { git_head, dirty, built_at }`）。
  **取不到 git**（例如 M10b §7.3.2.1 用 `git archive` 导出的基线树，没有 `.git`）时注入 `null`，**不报错**。
  测试构建（`--tests-only`）注入固定的测试值。
- **读出**：`meta.ts` 组装 `snapshot` 时加可选字段 `build`（上述三项或 `null`）。
- **比对**：`review.ts` 收尾时若 `build` 为 `null`、`build.git_head ≠ snapshot.git_head`、或 `build.dirty === true`，
  往 `meta.gate.warnings` 追加一条「安装副本与仓库不同版」并打到收尾 stderr；**只告警、不阻断、不改 `evidence_ok`**（与守卫同一姿态）。
- **schema**：`run.v2.json` 的 `snapshot` 增可选属性 `build`，不进 required。
- **doctor**：显示当前编排器的构建标识一行。

> **不做**：不校验安装副本内容（那是 M10b r5 §6.2 登记的内容层边界，不在这里补）。

## 3. 改动二：同形第二臂（EV-94 ②；M10b r5 §3.3.3 T1 ②(a) 的实现）

**目的**：在**配置读取层**，用与审查臂**同形**的副本再判一次；与白名单臂并排比较，区分 H2（副本形态差异）与 H3（运行期注册表配不上）。

- **新函数** `probeModelOverrideFullCopy(entry, node, cwd, { cliConfigPath?, timeoutMs?, readonlyArgs? })`，放在 `probes/zcode.ts`：
  1. `makeTempDir` 建临时根（**清理只认这个返回值**，2026-09-20 事故 R1）；
  2. 请求模型取 `pickNonFirstModel`（与白名单臂同口径，非首位）；
  3. **直接调用** `prepareZcodeHome(<临时根>, <请求模型>, { srcConfig: cliConfigPath })` 造副本，**与审查臂同一个构造函数**，不另写一份准备逻辑；
  4. 在造好的副本上**只替换凭据**：每个 provider 的 `options` 里，除 `baseURL` 与布尔值外的字符串值一律换成哨兵常量；`options.headers` 的每个值换成哨兵。
     **键一律保留**（「保键骨架、字符串值换哨兵」），顶层其它键原样不动：它们正是 H2 的嫌疑面，动了就测不到；
  5. 环境与审查臂同形：`zcodeProviderEnv(entry, …, { omitPersonal: true })` + 清 `ZCODE_CREDENTIAL_ENV_KEYS` + `HOME` 指向副本 HOME；带只读参数；
  6. 读 `v2/provider_config.json` 的 `defaultModelSelection`，**判定与 `probeModelOverride` 共用同一段逻辑**（抽出一个纯函数，两臂都调它），三态 `config_copy / global / null`；
  7. `finally` 里 `fs.rm(<临时根>, { recursive: true, force: true })`；**不调** `scrubZcodeHome`（清理助手的安全边界靠调用方守，R2）。
- **凭据面**：副本在临时根里，生命周期是一次拉起；与审查臂整份拷贝（含真实凭据）相比，本臂的凭据面**更小**（已换哨兵）。
  哨兵写法沿用计算属性键，避开 `fixture-credentials` 扫描器的形态判据。
- **机读落盘**：`ProbeSection` 的 zcode 段增 `model_override_full_copy`（三态 + `requested` / `observed` / `why`），与现有 `model_override` 并列。
  **运行期消费方**：doctor 在两臂结论不一致时打印 EV-94 ② 的触发告警（满足 M10b r5 §4.6「有消费方才进机读」）。
- **doctor 展示**：两臂并排一行一格，写明「本臂只判配置读取层，判不了运行期注册表层」。

## 4. 实验与判读（零配额）

改动合入并 `npm run build` + `npm run install:local`（各单独一条）后，跑一次 `trivium doctor`（它会刷新两臂），读两臂结论：

| 白名单臂 | 同形臂 | 读出什么 | 下一步 |
| :--- | :--- | :--- | :--- |
| `config_copy`（写出 Flash） | `config_copy`（写出 Flash） | 两种副本在**配置读取层**都成立 ⇒ **H2 排除**；真实运行却回落首位 ⇒ 问题在配置层之后，**H3（运行期注册表配不上）按排除法成立** | **停下向用户报告**（M10b r5 §2.2、R-s）：「形态换源」是否纳入由用户定 |
| `config_copy` | `global` 或写出首位 | **H2 成立**：整份拷贝里有某个键让配置层结果不同 | 第二段：零配额二分副本的差异键（每次只去掉一组键，仍用同形臂），定位后修审查臂的副本构造 |
| `global` | 任意 | 白名单臂本身不成立了：09-22 入口文件替换后，CLI 的导入流程可能变了（环境漂移） | 登记环境变化，两臂读数原样报告，不猜归因 |
| 任一为 `null` | — | 本轮未判定（拉起未完成、定位失败、未识别形态） | 照实登记，报告后再定 |

**层级边界**（M10b r5 §3.3.1 纪律 5）：本实验看得见配置读取层与两臂副本形态差异，**看不见运行期注册表层**。
第一行的「H3 成立」是排除法结论，不是直接观测。报告里照这句写。

**可选佐证（不作判据）**：对 `zcode.cjs` 做只读的静态检索，定位 `isSelectable` 与注册表的建立路径，看 legacy 导入的 custom provider 成员以什么 id 形态进注册表。
按设计 §3.3 的纪律，包内字面要注明「哪条调用路径上验过」，未验的标「待实测」，**不得作为改动依据**。

- **构建标识**：

## 9. 给审查员的重点

1. 第 3 节的同形臂是否真的「同形」：直接调 `prepareZcodeHome` 后只换凭据值，还有没有哪一处与审查臂不同（环境、参数、拉起方式）会让两臂在配置层结果不同、而与副本形态无关？
2. 凭据替换规则（`options` 内非 `baseURL` 非布尔的字符串 + `headers` 全部值）会不会漏掉凭据、或误换掉导入要用的值，从而让同形臂假阴性？
3. 第 4 节判读表是否互斥、穷尽；第一行「H3 按排除法成立」有没有别的解释（例如配置层写出 Flash、但运行时另有一处按首位覆盖）。
4. 构建标识的 dirty 判据只看 `src scripts package.json`，够不够；`git archive` 导出的树注入 `null` 只告警，这个取舍对不对。
5. 同形臂进 `ProbeSection` 的理由（doctor 的一致性告警作消费方）是否成立。
