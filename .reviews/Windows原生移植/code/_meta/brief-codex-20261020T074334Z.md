+### 7.1 Windows 平台模型
+
+**进程身份。** `util/platform.ts` 是平台差异的唯一落点之一：`enumerateProcesses()` 以一条 PowerShell（`Get-CimInstance Win32_Process`）取全量 `pid,ppid,CreationDate`，结果按 ~400 ms TTL 缓存（实测单查与全量枚举同价约 0.7–0.9 s，终止轮询不得每拍新起一个 PowerShell）。规范化启动时刻在 Windows 写 CreationDate 的 UTC ISO 形态（`yyyy-MM-ddTHH:mm:ss.ffffffZ`，显式格式化、与环境无关）；盘上字段名与 macOS 复用同一组——记录不跨机器/平台，Windows 上不存在旧形态记录，写读两端同平台同形态，故不违反「规范化形态是盘上契约、变更须换字段名」的纪律；macOS 的 `ps lstart` 形态逐字不变。
+
+**组员判定。** macOS 的 `ps -axo pgid=,stat=` 在 Windows 无对应物。等价判据：以全量枚举建 `pid→ppid` 父链图，从记录的组长 pid 沿后代 BFS 计数仍在表的进程——覆盖原进程组语义（组长其后代即原组员），且覆盖 EV-163/168 记录过的孙辈盲区。组长退出后子进程的 PPID 残留仍指向它，与 POSIX 组号语义同样可判「组长已退、组员仍在」；枚举失败返回 null（`unverifiable`，不去猜）。
+
+**终止阶梯。** `killProcessTree` 在 Windows 分派 `taskkill`：SIGTERM 位映射 `taskkill /PID <pid> /T`（WM_CLOSE，控制台进程常无效——如实保留），SIGKILL 位映射 `/T /F`。worker 活着时 detached 子进程父链完整，`taskkill /T` 连带清理；此为硬步兜底，不承诺厂商 CLI 自行收尾。

+**worker 优雅取消。** Windows 跨进程发不出可捕获 SIGTERM（TerminateProcess 即强杀）。`run-files.ts` 登记 `cancel.requested` 运行目录文件：`--cancel` 在软步之前写标记；worker 的取消处理器主体抽为 `beginWorkerShutdown`，POSIX 仍由 SIGTERM 触发，Windows 另装 250 ms 轮询 watcher 读标记触发，随后走同一条 `shutdownTrackedTrees` 路径并按 143 退出。我方凭据抹除由 worker 代码执行，受此路径保护；不依赖厂商 CLI 的优雅收尾。
+

## 5. 审查要点与你这一侧的镜头

被审对象是**一段补丁**（`_meta/changes.diff`），不是一份文档。据此调整读法：

- **先读补丁，再读被改文件的完整上下文。** 补丁只给了变更行，
  而绝大多数真问题出在「这一行在它所处的完整函数/调用链里是否成立」。
  只看 diff 上下文几行就下结论的审查，会漏掉几乎所有竞态与契约漂移。
- **顺着调用链向上下游各走一层。** 改了签名，谁在调？改了返回形状，谁在解？
  改了错误处理，谁依赖那个异常？这些文件不在补丁里，但必须读。
- **补丁头部记了 `base` 与 `head`。** 你看到的是相对那个基线的变更；
  若正文与基线看起来不一致，如实写进 `not_covered`，不要自行推测。
- **实现偏离已批准的计划，本身不一定是错误**，但必须是显式的。
  发现偏离就指出，让 Driver 去裁决是「计划错了」还是「实现跑偏了」。
- **不要给出大段可粘贴的补丁。** 指出位置与方向即可。

判断标准：**这个问题会让线上出错、让后来的人误解、还是让下一次改动变难？**
三者之一即值得提；纯风格偏好不提。
