## 0. 范围与不做

**做**：

1. `probeAuth`（`src/trivium/preflight.ts:699-740`）一处兜住适配器的三个调用点：`authProbe()` 构造、`fingerprint()`、`probe()`（决策一、二）。不逐家改适配器。

7. 文档：BACKLOG EV-202 结案（补写 agy 同形与缓存 null 一格）、EV-197 / EV-200 残余一按实改写、新登 EV-203；主设计 §8.1 一句 + 版本记录一行；RUNBOOK 一行；测试报告与 `doc/05_testing/README.md` 登记（决策五）。

## 1. 现状核对（d6404d6）

1. **codex 指纹**（`codex.ts:334-357`）：对 `<profile>.config.toml` 与 `auth.json` 先 `exists` 再 `sha256File`，对基底 `config.toml` 先 `exists` 再 `fs.readFile`，均无 try。`exists`（`util/fsx.ts:16-23`）只判 F_OK；`sha256File`（:51-53）是裸 `fs.readFile`。权限 000、`EISDIR`、两步之间被删都会抛出。
2. **agy 指纹**（`agy.ts:202-208`）：`exists(f) ? sha256File(f) : null`，同形无兜底。claude 指纹（`claude.ts:740-742`）恒返回 null、无读盘；zcode（`zcode.ts:1132-1144`）读盘已兜成 null。
3. **缓存判据**（`preflight.ts:117-136`）：`entry.fingerprint !== fingerprint` 全等比较。指纹为 null 的侧（claude 恒为 null；codex 三份都不在、agy 的 `agent.md` 不在时也是 null）缓存只由 TTL 与 CLI 版本约束——这是 `AuthProbe.fingerprint` 的契约原文（`adapters/base.ts:99-102`：「`null` = 无从计算，此时缓存只由 TTL 与 CLI 版本约束」），不是缺陷。但若照 zcode 先例把「读不了」也折成 null，就把「读不了」混进了「无从计算」：上次指纹为 null 时会命中缓存、跳过探活。
   **zcode 现写法的那一格**（r1 推导漏了一支，AGY-01）：zcode 的指纹在文件可读时恒带 `|model=`、非 null；读不了与文件不在都是 null。null 缓存条目的来源有三：①上次文件不在、探活通过；②上次读不了、**档位没给模型**——`prepareZcodeHome`（`zcode.ts:1027`）在 `model` 为空时直接走真实 HOME 退路、不读副本源，探活可以通过并写入 null；③上次读不了、指纹与 `prepareZcodeHome` 之间文件恰好变得可读（竞态）。有了 null 条目后，只要这次仍读不了（或文件仍不在），TTL 内就命中缓存、跳过探活、无任何提示。档位给了模型时，`prepareZcodeHome` 读同一个文件（:1033），读不了即落成可读失败、不写缓存，所以②只在档位无模型时成立。本题不改 zcode（决策一），登 EV-203（§8 第 1 条）。
4. **穿透路径**：`probeAuth` 里 `adapter.authProbe?.(…)`（:712-715）、`await auth.fingerprint()`（:723）、`await auth.probe()`（:730）都没有 try；`runPreflight` 用 `Promise.all`（:832-836）收各侧，任一 reject 即整个 `runPreflight` 抛出，经 `cli.ts` 末尾 `.catch` 打「内部错误：消息」、退 1（`EXIT.FAIL`），`TRIVIUM_DEBUG` 置位时另打原始异常。同批其余各侧已探完的结论（包括已花掉的配额）一并丢弃。
5. **probe() 抛出面**：EV-197 / EV-200 已在 zcode / codex 两家把副本准备与删除兜住；剩下的抛点是 `mkdtemp` 本身、`attempt` 里未兜的路径、agy / claude 的 `invoke*` 里的同步异常。面窄，但「崩整个预检」的后果比「该侧失败」重得多。
6. **注入口**：`runPreflight` 的 `adapters` 选项只喂 ④″（注释 :104-109 写明，防用例忘了 `skipAuthCheck` 真去探活花配额）；⑧ 恒用 `realAdapters()`。`probeAuth` 未导出。预检层要零配额地测兜底，需要一个入口。
7. **退出码**：环境类失败是 `EXIT.ENV`（69），`runPreflight` 取第一条失败项的 `exitCode`。

## 2. 设计

### 2.1 `probeAuth` 改写

```ts
/** 适配器抛出的原因：家目录归一 ~（路径里常带用户名）。TRIVIUM_DEBUG 置位时另把原始异常打到 stderr，与 cli.ts 出口口径一致 */
function thrownText(e: unknown): string {
  if (process.env['TRIVIUM_DEBUG']) console.error(e);
  return tildeHome(e instanceof Error ? e.message : String(e));
}

export async function probeAuth(ctx, critic, adapter, opts): Promise<AuthOutcome> {
  …（name / version 不变）
  const internalFail = (e: unknown): AuthOutcome => ({
    critic,
    result: { name, ok: false, exitCode: EXIT.ENV, detail: `探活内部失败：${thrownText(e)}` },
    cache: null,
  });

  let auth: AuthProbe | undefined;
  try {
    auth = adapter.authProbe?.({ cfg, nodePath: … }, ctx.projectRoot);
  } catch (e) {
    return internalFail(e);
  }
  if (!auth) { …（不变） }

  // 指纹读不了 ≠ 无从计算（null）：不查缓存、不写缓存，原因进详情
  let fp: string | null = null;
  let fpError: string | null = null;
  try {
    fp = await auth.fingerprint();
  } catch (e) {
    fpError = thrownText(e);
  }
  if (fpError !== null) {
    step(`[${critic}] 指纹读不了（${fpError}），不查缓存，执行最小 headless 探活`);
  } else if (!opts.refreshAuth) {
    …（authCacheValid 一段不变）
  }

  let r: { ok: boolean; detail: string };
  try {
    r = await auth.probe();
  } catch (e) {
    r = { ok: false, detail: `探活内部失败：${thrownText(e)}` };
  }
  const note = fpError === null ? '' : `；⚠️ 指纹读不了：${fpError}，本次未用缓存、也不写缓存`;
  return {
    critic,
    result: r.ok
      ? { name, ok: true, detail: r.detail + note }
      : { name, ok: false, exitCode: EXIT.ENV, detail: r.detail + note },
    cache: r.ok && fpError === null
      ? { checked_at: …, cli_version: version, fingerprint: fp, ok: true }
      : null,
  };
}
```

要点：

- **构造也兜**：`authProbe()` 构造里各家都只读配置（codex `codexConfig(ctx)`、zcode `zcodeProbeModel(cfg)`），抛出面近于空；但它与另两个调用点后果相同（崩整个预检），兜它不加分支、只多一个 try。文案与 `probe()` 抛错同一句「探活内部失败」——都是适配器内部异常，用户的处置相同：看详情里的原因；要栈就设 `TRIVIUM_DEBUG=1` 重跑（栈经 `thrownText` 打到 stderr）。
- **`fpError` 用单独变量，不折成 null**：§1 第 3 条——折成 null 会在上次指纹为 null 时命中缓存。读不了时干脆不进 `authCacheValid`，与 `refreshAuth` 走同一条「不查缓存」的支，判据本身不动。
- **`refreshAuth` 与 `fpError` 同时成立**：step 照打指纹那一行（原先 `refreshAuth` 时不打 step，这里多一行 stderr 进度提示，不进 `--json`）；注明照接（本次确实没用缓存、也不写）。
- **注明接在详情末尾**，与 EV-197 / EV-200 的残留提示同一接法（`；⚠️ …`）。两段可能同时出现：适配器拼的残留提示（或「探活内部失败：…」）在 `r.detail` 里、指纹注明恒在最后（G9 钉住）。
- **`probe()` 抛错兜成 69**（决策二的代价）：这条路径原先退 1、打「内部错误：消息」；现在退 69、该侧详情「探活内部失败：消息」。`TRIVIUM_DEBUG` 的排障能力不丢——兜住处照打原始异常。其余各侧结论保留——原先一侧抛出会连带丢掉另两侧已花配额探出的结论。
- **正常路径逐字不变**：指纹不抛、`probe()` 不抛时 `note` 为空串、`cache` 条件与原先等价，详情与缓存条目逐字节同原。用例 G1 钉住。
- `tildeHome` 从 `util/fsx.ts` 引入（EV-200 已挪到那里）。

### 2.2 `probeAuthAll`

```ts
/** ⑧ 探活：按入选侧并行探。`adapters` 恒由 runPreflight 传 realAdapters()；导出只为可测性（假适配器零配额） */
export async function probeAuthAll(
  ctx: Ctx, selected: readonly CriticId[], adapters: AdapterTable, opts: PreflightOptions,
): Promise<AuthOutcome[]> {
  return Promise.all(selected.filter((id) => adapters[id]).map((id) => probeAuth(ctx, id, adapters[id]!, opts)));
}
```

`runPreflight` 的 ⑧ 改成 `const probes = await probeAuthAll(ctx, selected, realAdapters(), opts);`，循环不变。`AuthOutcome` 随之导出。`probeAuth` 也导出（单格用例直接调它更清楚，见 §3）。

### 2.3 为什么不给 `runPreflight` 加探活注入口

决策三的二选一：选「导出」。理由：
- `runPreflight` 层的用例要过 ①～⑦，其中 ② 会真去跑各家 `--version`，摆出一个全过的现场成本高、且与本题无关；
- 加注入口就是给「⑧ 误花配额」再开一个口子（§1 第 6 条那段注释防的正是这个），而导出函数本身不带缺省真实表，调用方必须显式给表；
- `probeAuthAll` 是 `runPreflight` 原样抽出的那一段，测它就是测生产组合（`Promise.all` + 过滤），不是在测试里另写一份。

代价：`runPreflight` 里「⑧ 调的是 `probeAuthAll`」这一接线本身没有用例咬（变异 M9 预计存活，如实记）。

### 2.4 不动的部分

`authCacheValid`、`commitAuthCache`、`AuthCacheEntry`、`AuthProbe` 接口、四家 `authProbe()` 实现、`cli.ts` 出口，全部不动。

## 7. 风险

- **退出码口径变化**（决策二）：脚本若按「1 = 内部错误」判别预检崩溃，这条路径改退 69 后会被当成普通环境失败。仓里没有按 1 判别预检的消费方（编码时 grep `preflight` 的调用点核一遍并在报告里记）。
- **读不了期间重复花配额**（CODEX-02）：原先读不了就崩预检、一次都不探；现在每次预检该侧都真探一次且不写缓存，直到文件修好。codex 侧多数读不了的形态会在副本准备那一步就落成失败、到不了真实调用（R1 / R2 即此形态）；agy 侧会真拉起。这是决策一的有意取舍（不可知的指纹不入缓存），写进 RUNBOOK 与报告成本节。
- **详情变长**：注明接在详情末尾，人读输出多一段；`--json` 的 `detail` 同步变长，无字段增减。
- **测试改 `HOME`**：`os.homedir()` 在 POSIX 下读 `HOME`，用例在 finally 复原；同文件内用例串行，无并发污染。

## 8. 残余与后续

1. **zcode 指纹读不了折成 null 的窄格**（§1 第 3 条，新登 EV-203）：档位无模型（或竞态）时读不了的探活可通过并写入 null 缓存，之后 TTL 内读不了仍命中、跳过探活且无提示。本题按决策一不动 zcode 既有写法（输出逐字不变）。修法方向：去掉 zcode 指纹里的 catch、让它抛给 `probeAuth` 统一兜——zcode 读不了时的详情会多出本题的注明，属输出变化，需单独决策。
2. **残留提示随异常丢失**（EV-197 / EV-200 残余一）：适配器 `attempt` 抛错且临时目录删不掉时，删除函数算出的提示在 finally 里、抛出路径不带它。本题之后不再崩预检（该侧落成「探活内部失败」），但提示仍丢。修它要改适配器的异常形状，不在本题。
3. **两条接线无用例咬**：M9（⑧ 改回内联）、M11（`TRIVIUM_DEBUG` 打印）预计存活，如实记入报告。
