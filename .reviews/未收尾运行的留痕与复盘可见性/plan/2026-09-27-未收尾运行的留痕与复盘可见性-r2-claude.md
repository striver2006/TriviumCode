### 3.1 归档侧收尾的通用函数（D4 取 (a)）

`meta.ts` 把第一、二步改成按「目标终态」参数化的内部函数，对外两个薄导出：

```ts
/** 这一次终态由哪条路收的尾（D5；只由两条失败路写，取消轮不写） */

  | { by: 'worker_exception'; exit_code: number }
  | { by: 'worker_lost'; reason: WorkerLostReason };   // WorkerLostReason 由 status.ts 的 WORKER_LOST_REASONS 派生（§3.5）

async function finalizeUnfinishedRunMeta(i: {
  layout: ArchiveLayout; stage: Stage; runId: string; lock: TaskLock;
  /** 没有另一个写者：别的进程调用时传「确认已退出」的结论；worker 自己调用时恒真（它就是那个写者） */
  workerGone: boolean;
  terminal: UnfinishedTerminal;
  termination?: RunTermination;
}): Promise<{ runMeta: FinalizeStep; task: FinalizeStep }>;

/** 签名与行为不变（EV-128） */
export const finalizeCancelledRunMeta = (i: {…同今天…}) => finalizeUnfinishedRunMeta({ ...i, terminal: 'cancelled' });
/** EV-142 */
export const finalizeFailedRunMeta = (i: {…; termination: RunTermination }) =>
  finalizeUnfinishedRunMeta({ ...i, terminal: 'failed' });
```

- **第一步**（run.json）：四个前提不变；写入时 `status`、`gate.state` 取 `terminal`，`finished_at` 取当前时刻，给了 `termination` 才写这一键；其余键原样。
  **读 → 判 → 写整段放进主题任务锁**（与 task.json 同一把 `taskLockName`，经 `withTopicLock`；两步不嵌套、各取一次；C10），保证每份 run.json 至多一次终态写入（§3.4）。
- **第二步**（task.json 登记）：判据由「run.json 已是 `cancelled`」改为「run.json 已是**本次目标终态**」，其余不变；跳过原因里的「不是 cancelled」改成带目标终态的同一句（R 系列没有断言这一句，C4）。
  **不放宽成「run.json 是任一终态就照抄」**：那会让 R2（run.json 已是 `success` ⇒ task.json 不改）换语义；W2 与 §3.4 第三行那两种「run.json 已终态、登记停在 running」是另一类不一致，登记在 §6.2，不在本主题修。
- 跳过原因、`FinalizeStep` 形状、「自身不抛」「两步各自可重入（对进程中断）」的口径不变。
- 内部函数与两步辅助函数改名（`cancelRunMetaStep` → `unfinishedRunMetaStep` 一类）；`finalizeCancelledRunMeta` 的名字与签名不动，`cancelRun` 调用点、R1～R7、E1 / E3 / E6 都不用改。

### 3.2 worker 异常那条路（D1）

`workerMain` 的 `catch` 在 `patchStatus`（:541）**之前**插入：

1. 取身份：与 `finally` 同一个表达式（status.json 的 `topic` / `stage`，读不到则 `readHandoffIdentity`）；取不到就跳过这一步，照旧往下走。
2. 调 `finalizeFailedRunMeta({ …, workerGone: true, termination: { by: 'worker_exception', exit_code } })`，`exit_code` 与写进 status.json 的同源（`TriviumError` 取其 code，否则 `EXIT.FAIL`）。
3. 两步的结果各拼一句，**追加进 status.json 的 `message`**（`｜` 分隔）——worker.log 没人看，`--wait --json` 会原样带出 `message`（L4）。异常转成的跳过照样说明「这一步没有第二次机会、请人工核对」。

前提与理由：
- **`workerGone: true`**：此刻的写者就是 worker 自己；另一个事后写者 `--cancel` 只在确认 worker 已退出时才写（C1 前提 1），`--wait` 的新写入同样要求确认退出（§3.3），所以 worker 活着的这段时间里它是唯一写者。
- **「仍为 running 才写」照搬**：W2 已核出异常可能晚于 :1627 的终态写入，那时 run.json 是 `success` / `failed`，前提 4 挡下、不追溯改写。
- **排在 `patchStatus` 之前**：worker 若死在两次写之间，status.json 仍非终态，之后 `--wait` 会判 `pid_gone` 走 §3.3，看到 run.json 已是 `failed` 跳过第一步、第二步补齐登记；反过来排（先落 status.json 终态）则 `--wait` 直接按终态返回、`--cancel` 在 :821 早退，run.json 永远 `running`——与 EV-128 同一个理由。

### 3.3 `worker_lost` 那条路（D2）

`waitRun` 的 `worker_lost` 分支改成：

```text
【新】pre = readStatus(runDir)                                   // 改写之前
【新】goneForArchive =
        pre !== null        ? workerConfirmedGone(pre, fallbackPid)                    // 有 status.json：照旧
      : fallbackPid !== null ? processAlive(fallbackPid, null) 不存在 ⇒ 已退出（pid_gone） // 与情形 A 同源
      :                        未确认（no_status_file：连 pid 都没有）
【新】identity = pre 的 topic/stage ?? last ?? readHandoffIdentity(runDir)
【新】fin = identity ? finalizeFailedRunMeta({ workerGone: goneForArchive,
                         termination: { by: 'worker_lost', reason: reading.reason } }) : null
:656 patchStatus(failed)               — 不变
:666 meta0 / :667 回收闸门             — 不变
:680 gone = workerConfirmedGone(meta0) — 不变，仍只决定抹不抹凭据副本
:691 throw — 报错正文追加两步结果各一句（唯一的播报通道）
```

- **写入前提用「改写之前」的事实判**：此时 phase 非终态，`workerConfirmedGone` 走不到「终态且从未记下 pid」那一支，判「已退出」就只剩一种依据——有 pid 且进程确已不在（L3）。改写之后那次（:680）判的不是同一件事：它会把 `waitRun` 自己刚写的 `failed` 当成「终态」，在拿不到 pid 时下「已不在」的结论。
- **status.json 读不到但 worker.pid 已知**（计划双审 r1 CODEX-01 ≡ GLM-01 ≡ AGY-02）：`workerConfirmedGone(null)` 首行即判「否」、不看 `fallbackPid`（L3），而 `interpretStatus` 情形 A 恰恰是拿 `fallbackPid` 判出「已死」才报 `pid_gone`——证据在手。这一格是「worker 在第一次写 status.json 之前就死了」（派生 → `rebuildContext` → 首次 `patchStatus` 之间），不收尾的话 status.json 随即被 :656 写成终态，此后再没有写者。所以在调用点单独判：用与情形 A 同源的 `processAlive(fallbackPid, null)`，**不存在才算已退出**；进程在（含 PID 被复用成别的活进程，L5）照样不写。`workerConfirmedGone` 本体与 :680 的 EV-20 抹除判定都不动。
- **确认不了的那部分不写**，按真实形态是三格：`heartbeat_stale` 且进程在；status.json 读不到且连 pid 都没有（`no_status_file`）；status.json 在、非终态却拿不到 pid。第一步都跳过，报错正文写明「工作进程未确认退出，归档 run.json 未回写」。进程若之后自己恢复，它会照常写收尾；若一直挂着，这份 run.json 留在 `running`——与 EV-128 对「未确认退出」的处理同一口径，§6.2 与 §6.3 第 2 条如实登记。改后 `pid_gone` 的每一格都会写，报错正文不会再同时出现「失联（pid_gone）」与「未确认退出」（r1 GLM-01 指出的矛盾）。
- **凭据副本的判定（:680）不动**：它的准入判据属 EV-20，改输入会改抹除行为；本主题只新增一次改写前的判定供归档写入用，两处各自注释用途。
- **排在 `patchStatus` 之前**：`waitRun` 进程若死在两次写之间，下一次 `--wait` 仍会判 `worker_lost`，第一步因已是 `failed` 跳过、第二步补齐；反过来排，下一次 `--wait` 按终态直接返回，没有第二次机会。
- **播报只走报错正文一个通道**（r1 AGY-01）：`--wait` 失联本来就以抛错收场，CLI 顶层会打印报错正文，所以两步结果只拼进正文，异常转成的跳过带「这一步没有第二次机会，请人工核对归档 run.json 与 task.json 的运行登记」。**不调 `reportFinalizeStep`**，它维持只服务 `--cancel`，措辞不动。

### 3.4 与 `--cancel` 撞车（D3）

逐个序列核过：

| 序列 | 结果 |
| :--- | :--- |
| 先 `--wait` 判 `worker_lost`（pid_gone，含 status.json 读不到的那一格），后 `--cancel` | `--wait` 写 `failed`（带 `termination`）；`--cancel` 读到 status.json 已终态，在 :821 早退（P3 实测），run.json 不再动 |
| 先 `--cancel`，后 `--wait` | status.json 已是 `cancelled`，`--wait` 走 `terminal` 分支返回，不进 `worker_lost`；run.json 为 `cancelled` |
| `--cancel` 杀进程期间 worker 正在 `catch` 里 | worker 无 SIGTERM 处理器，立即退出；`writeAtomic` 是临时文件 + rename，run.json 要么已是 `failed`、要么仍 `running`。`--cancel` 在确认退出**之后**才读，前者跳过、后者写 `cancelled`——**run.json** 不会两边都写。**task.json 那一侧**：worker 若死在它自己的第一步（run.json → `failed`）之后、第二步之前，`--cancel` 的第二步按「目标终态 cancelled」跳过，此后 status.json 落 `cancelled`、再无写者，**登记停在 `running`**（r1 CODEX-02；窗口极小，`report` 与提交锚以 run.json 为准，§6.2 登记、不修） |
| **两个事后写者同时读到 `running`**：用户在终端 `--cancel` 的同时，skill 的 `--wait` 轮询到 `pid_gone`；或两个会话各跑一个 `--wait` | 今天的第一步不在锁里（C5），两者都会写，后写者覆盖前者的 `status` / `finished_at`——违反「至多一次终态写入」。**§3.1 把第一步放进主题任务锁后**，后到者读到终态、按前提 4 跳过；谁先到记谁，`status` 与 `termination` 如实反映那一方 |

- 另两类写者不构成新的双写：worker 活着时心跳新鲜，`--wait` 不会判失联；worker 正常收尾（:1627）不进锁，但两个事后写者都要求 worker 已退出，与它在时间上不重叠（计划双审 r1 glm 独立枚举四类写者两两组合，结论相同）。
- 锁争用的后果：`withTopicLock` 重试 20 × 150 ms 用尽即抛，第一步转成带异常的跳过、告警要求人工核对——与 task.json 那一步是同一风险面；持锁者猝死由 `judgeStale` 按 pid 回收（C10），不会卡死。
- status.json 那一侧仍可能与 run.json 不一致（两边的 `patchStatus` 都无条件写，后写者赢）。这是既有行为，`report` 与提交锚都以 run.json 为准，本主题不动，登记在 §6.2。
- 附带核出的缺口：`heartbeat_stale`（进程还在）判失联后，status.json 已被写成 `failed`，此后 `--cancel` 在 :821 早退——**挂住的 worker 没有工具化的杀法**，只能手工 `kill`，而手工杀掉之后也没人再收 run.json 的尾。属 `--cancel` 终态早退的语义，本主题不动，新登 BACKLOG（§6.3 第 2 条）。

### 3.5 失败原因记在哪（D5 取 (a)）

run.v2 新增**可选**顶层字段 `termination`，只由 §3.2 / §3.3 两条路写：

```json
"termination": { "by": "worker_exception", "exit_code": 1 }
"termination": { "by": "worker_lost", "reason": "pid_gone" }
```

- schema：`oneOf` 两个形状，各自 `additionalProperties: false`；`by` 为常量，`exit_code` 整数，`reason` 三值枚举。description 写明：只由事后收尾写；缺席 = 正常收尾（`success` / `failed` 由 worker 写）、取消轮（`status` 已说明）、或本字段之前的留痕。
- **失联原因单一来源**（r1 CODEX-04）：`status.ts` 导出 `WORKER_LOST_REASONS = ['no_status_file', 'pid_gone', 'heartbeat_stale'] as const`，`StatusReading` 里 `worker_lost` 的 `reason` 与 `RunTermination` 都由它派生。schema 是 JSON、不能引用 TS 常量，所以由用例 S2 守住「schema 的 `reason` 枚举与该常量逐项相等」——将来给 `interpretStatus` 加第四种原因而漏改 schema，S2 当场红，而不是等写出一份不合契约、被 `readRunMeta` 读成 null 的 run.json。schema description 与 `types.ts` 注释写明这层同步关系。
- **不记自由文本**：异常首行会把本机绝对路径带进会提交的归档（P2 的 message 就是一条 `/private/var/folders/…` 路径），也可能撞上 `writeMeta` 的密钥扫描——扫描一拦，整次终态写入都跳过，run.json 又停在 `running`（§2.1 那份历史留痕的异常正是密钥扫描）。详情仍在本机 status.json 与 worker.log。
- `types.ts` `RunMeta` 加同形可选字段与文档注释。v1 不动（事后收尾只写 v2）。
- 取消轮不写这一键：`status: cancelled` 已说明来路；R1「其余逐键不变」因此保持成立，也充当本条的回归守卫。

## 6. 风险与边界

### 6.1 新写入对既有不变量

- **EV-133「收尾后不再更新」**：两条新路都只在 `status === 'running'` 时写，且都是那份 run.json 的第一次终态写入（worker 没走到 :1627）；写完即终态，此后同样不再更新。每份 run.json 仍是「一份骨架 + 至多一次终态写入」，§3.4 的锁把「至多」从约定变成保证。
- **提交锚**：C6——HEAD 为 `running` 时只查 `run_id` 与已登记条目，本步只改三格加一个新键、`artifacts[]` 原样，「运行中途提交过、之后失败」照样能提交（X1 / A2 钉住）；HEAD 已是终态时前提 4 挡下、不写。
- **`runTerminal` 的结果翻转**：这两类运行的主题锁判定由「未终态」变「终态」。worker 异常时 worker 自己的 `finally` 会删锁；`worker_lost` 时持锁 pid 已死，`judgeStale` 本来就按 `pid_gone` 回收。实际不改变任何回收结果。
- **其余读者不变**：`gate`、当轮 Driver 判定、Hook 读的最新留痕都不看 `status`（C8）。
- **回滚成本**（r1 CODEX-03）：本变更对留痕是纯追加——可选字段 `termination` 与读侧新表。回滚即 revert：已写入 `termination` 的 run.json 在旧代码下仍合契约（顶层 `additionalProperties: true`，C7），被自然忽略；已写成 `failed` 的 run.json 是合法终态；旧 `report` 不读 `unlistedRuns`。无数据迁移、用户无需操作。

## 7. 决策点（2026-09-27 送审前已定：用户授权按最优原则拍板，全部取建议项；计划双审第 1 轮三侧均认同，不变）

**D1 worker 异常那条路的写入前提** — **已定**：照搬「v2 且仍为 running 才写」，「工作进程已确认退出」这一条由「写者就是 worker 自己」替代（传 `workerGone: true` 并注释）；位置在 `catch` 的 `patchStatus` 之前；结果追加进 status.json `message`。

- 理由：W2 核出异常可能晚于 :1627 的终态写入，不照搬就会把 `success` 改写成 `failed`。
- 不取「worker 异常就无条件写」：同上，会追溯改写。

**D2 `worker_lost` 那条路的写入前提** — **已定 (a)**（r2 按计划双审补全 status.json 读不到的那一格，§3.3）：

- **(a)** 用**改写之前**的事实判断工作进程是否确认退出，确认才写；status.json 读不到而 worker.pid 已知时按 `processAlive` 判；确认不了（`heartbeat_stale` 且进程在、连 pid 都没有、非终态却拿不到 pid）一律不写、报错里写明，不补；凭据副本的判定（:680）原样不动。
- (b) 复用 :680 那次判定：拿不到 pid 时会因 `waitRun` 刚写的 `failed` 走进「终态且从未记下 pid ⇒ 已不在」，替没确认的事作证（L3）。
- (c) `heartbeat_stale` 也写：进程还活着，恢复后会自己写收尾，两个写者。

**D4 复用还是另写** — **已定 (a)**：内部通用函数按目标终态参数化，`finalizeCancelledRunMeta` 名字与签名不动，新增 `finalizeFailedRunMeta`。碰到的既有面：两个内部辅助函数改名；上一主题变异规格的 find 锚点（内部名与 `'cancelled'` 字面量）失效——那是历史证据、不再重跑，本主题新写一份规格；R1～R7、E1 / E3 / E6、`cancelRun` 调用点、文档里的函数名都不用改。
