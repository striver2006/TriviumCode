## 1. `preflight`（最要紧，当前是硬阻塞）

**为什么最要紧**：七个入口 skill 的执行契约第 1 步就是 `TV preflight --stage <s> --json`，
而这个命令**不存在**。skill 现在跑不通。同理 `TV topic resolve` 也缺（见 §2）。

按设计 §8.1 实现八项检查，全部通过才继续。**失败时不得创建主题目录、
不得写任何 `_meta/`、不得产生任何双审标记**（AC-16）。

| 检查 | 判定 | 失败处理 |
| :--- | :--- | :--- |
| 探针结论存在且未过期 | `probe.generated_at` 在 `probe_ttl_days`（默认 7）内，且两侧 CLI 版本与探针记录一致 | 自动触发一次 `doctor`；仍失败则中止 |
| Antigravity 可调用 | `agy --version` 成功 | 中止（69） |
| Antigravity 已认证 | 最小 headless 探活；结论带 TTL 缓存（`preflight.auth_cache_ttl_h`，默认 1h，写 `config.local.yaml` 的 `probe.auth.agy_checked_at`） | 中止，提示先交互登录一次 |
| ZCode 可调用 | `node <entry> version` 成功 | 中止（69） |
| ZCode 已认证 | 同上带 TTL 缓存 | 中止，提示 CLI 配置独立于桌面端 |
| 模型 slug 合法 | 在 `probe.agy.models` / ZCode 模型目录内 | 中止（64）并列出可用值 |
| 只读能力可用 | `probe.zcode.readonly_flags` 非空、`trivium-critic` Agent 定义存在 | 中止 |
| 归档与 git | 归档根可写、`git rev-parse` 成功、工作区可快照 | 中止（69） |

**探活的成本问题**：两侧各跑一次最小 headless 会消耗配额并耗时数十秒。
TTL 缓存是必须的，否则每次 `/dual-review-*` 都白烧两次配额。缓存键要含 CLI 版本——
`agy` 在 M0 期间自升级过一次（坑 P-02），版本变了缓存必须失效。

**命令 A 的额外检查**：`verify.build` 与 `verify.test` 皆空时拒绝启动（§14.1），
避免跑完全流程却无法收口。

## 2. `topic resolve` 子命令

skill 的第 2 步调用 `TV topic resolve --stage <s> --args "$ARGUMENTS" --json`，
期望它返回主题、被审对象路径与 run 上下文。目前 `topic.ts` 有函数但没有 CLI 子命令。

需要实现的是**参数解析**：从 `$ARGUMENTS` 这一整串里切出提示语与具名参数。
这一步不能交给模型做——它是确定性工作（原则 P1）。

- 具名参数：`--topic` / `--context` / `--plan-file` / `--rca-file` / `--base`
  / `--model-gemini` / `--model-glm` / `--profile`；
- 其余正文即提示语（命令 A 是任务目标，B/C/D 是审查焦点）；
- 主题缺省时按任务目标推导候选并**回显**，经 `validateTopic` 校验后确定；
- 输出 JSON 含 `topic` / `prompt_hint` / `subject_path` / `context_paths` / `models`，
  供 skill 原样传给 `review --start`。

## 3. 三处补齐

### 3.1 `preflight` 失败时的零工件保证（AC-16）

现在 `prepareRun` 里 `resolveTopic` 会**创建阶段目录**。若预检在它之后失败，
会留下空的主题目录——违反 AC-16 的「零工件」。需要把目录创建推迟到
「预检通过且送审包即将落盘」之时。

### 3.2 `guard` 的 `readonly_breach` 与开发者手改的区分（§9.2 第 4 步）

现有实现已能区分「轨迹有写事件 → 审查员失守」与「仅指纹变化 → 开发者手改」，
但**没有把受影响文件清单打进人读输出**。§10.3 要求「仅打印受影响文件清单与建议命令，
编排器不自动 `git checkout` 回滚」。需补上建议命令的输出。

### 3.3 双审退化的可观测指标（§9.3）

两侧 `findings` 位置集合的 Jaccard 相似度 > 0.8 时提示「双审退化」。
这属 `report`（M4），但计算函数可在 M3 落地并写进 `run.json`，供 M4 直接用。
M1 首次双审实测 Jaccard = 0.43，作为基准参考。

## 4. 完成判据

设计 §16.1 要求 AC-04 / 05 / 06 / 08 / 11 / 13 / 16 / 17 / 18 全部可演示。
逐条给出可执行的验证方式：

| 验收 | 验证方式 |
| :--- | :--- |
| AC-04 背靠背隔离 | 审查进行中 `find` 项目树只命中历史文件且都在 `run.json.deny_paths` 内；两份 brief 不含对方内容；轨迹读取集合与 `deny_paths` 交集为空 |
| AC-05 禁止纯 LLM 冒充 | `run.json.critics.*.tool_calls` 与 `evidence_ok`；桩适配器造零工具调用应判 `insufficient_evidence` |
| AC-06 单审不可伪装 | 人为杀掉一侧进程，检查 `review_mode: single` + `degraded_reason` + 幸存侧文档头 `degraded: true`，且文件名未被改名冒充 |
| AC-08 只读失守可检出 | 桩适配器让审查员向项目写文件，应判 `readonly_breach` 并列出文件 |
| AC-11 结合全项目评审 | `project_reads ≥ min_project_reads`；`consulted` 与轨迹交叉核对通过 |
| AC-13 按任务指定模型 | `run.json` 两侧 `model_effective` 不同且与指定一致；ZCode 侧另核 `model.source=config` |
| AC-16 预检失败即中止 | 改坏 `critics.gemini.bin` 后启动，检查**无任何文件生成**（含主题目录） |
| AC-17 送审材料固定 | 审查中改被审对象 → `subject_drift` 整次作废；改无关文件 → warn 并列出 |
| AC-18 模型异构默认 | 默认跑一次 + 显式指定 Claude 系跑一次，检查 `heterogeneous` 与 `override_reason` |

其中 AC-05 / AC-06 / AC-08 需要**桩适配器**（可注入零调用、超时、脏输出、写文件），
这是 §17.1 集成层要求的，M3 一并交付。

## 6. 风险

| # | 风险 | 对策 |
| :--- | :--- | :--- |
| R-A | 预检探活消耗配额，用户会觉得每次命令都变慢 | TTL 缓存（默认 1h）+ 缓存键含 CLI 版本；`--skip-auth-check` 供调试 |
