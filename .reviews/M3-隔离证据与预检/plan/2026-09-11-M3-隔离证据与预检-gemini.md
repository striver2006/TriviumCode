| 项 | 内容 |

**问题**：计划将零工件保证仅局限于 prepareRun 中推迟目录创建，遗漏了 TV topic resolve 与 preflight 本身的可写性检查等提前返回路径，导致在真实 skill 流水线中仍会产生孤立目录或污染。

**依据**：读了 .reviews/M3-隔离证据与预检/plan/2026-09-11-M3-隔离证据与预检-claude.md §1~§3、skills/dual-review-plan/SKILL.md 与 src/trivium/topic.ts。在 skill 执行契约中，第 1 步调用 TV preflight（不带 --topic），第 2 步调用 TV topic resolve，第 3 步才调用 TV review --start（触发 prepareRun）。当前 topic.ts 中的 resolveTopic 内部调用了 ensureDir。如果 TV topic resolve 沿用该逻辑，在第 2 步就会提前建好阶段目录；若第 2 步因参数校验失败、提示语为空（FR-20）或被审原稿不存在（locateSubject 抛 65）而提前退出，或用户在第 2 步后中断，磁盘上已遗留空主题目录。此外，preflight 检查 8 检查「归档根可写」时，若在干净仓库直接创建 .reviews/ 进行探测且后续认证检查失败，同样破坏 AC-16。

**建议**：将「零工件」防御前移并贯穿所有入口：① topic resolve 必须设计为纯查询与解析命令，严禁调用 ensureDir 或创建任何目录；② preflight 的可写性探测在 .reviews/ 尚不存在时只探测父目录权限，不得提前 mkdir；③ 在 prepareRun 中将目录创建收敛至 writeMeta 落盘前的唯一临界点，并为准备阶段的异常（如 locateSubject、freeze、routeModel 失败）增加清理兜底。

**问题**：探活 TTL 缓存键仅含 CLI 版本不足以防止探针与凭据失效后被误用，且缓存数据结构在计划中未显式绑定版本与环境指纹。

**依据**：读了 .reviews/M3-隔离证据与预检/plan/2026-09-11-M3-隔离证据与预检-claude.md §1 及 doc/05_testing/REPORT_2026-09-11_m0_probe.md §6.1、§6.3、§7（P-03、P-08、P-10）。计划在 §1 中提出「结论带 TTL 缓存……写 config.local.yaml 的 probe.auth.agy_checked_at」且「缓存键要含 CLI 版本」。然而：① 若仅写入 agy_checked_at 时间戳字段，并未在数据结构中持久化版本号，无法比对 CLI 版本漂移；② ZCode 侧 CLI 版本（0.16.5）相对固定，但其可用性强依赖于 ~/.zcode/cli/config.json（模型提供商、API Key）与 OAuth 凭据，当 Key 失效、配额耗尽或文件被修改时，CLI 版本毫发未变，1 小时 TTL 缓存会假阳性放行，导致后续审查中途崩溃；③ Antigravity 侧无头读取可用性依赖 ~/.gemini/config/agents/trivium-critic/agent.md 自定义 Agent（绕过 issue #548 软拒绝），若该文件丢失或被改动，即使 CLI 版本未变，探针结论 headless_read_ok 也会彻底失效。

**建议**：补全缓存键与失效判定维度：① 探活缓存结构应显式持久化为结构化条目（含 checked_at、cli_version、状态及配置校验指纹）；② ZCode 侧缓存有效性应叠加 ~/.zcode/cli/config.json 的 mtime/hash；Antigravity 侧应叠加只读 Agent 定义文件的存在性与指纹；③ 增加 --refresh-auth 显式穿透开关，供用户在排错或轮换密钥后主动刷新。

### AGY-03 · 重要（major）

**问题**：预检中探针过期自动触发 doctor 的降级策略存在逻辑矛盾，且在非交互式 headless skill 下会导致严重超时风险。

**依据**：读了 .reviews/M3-隔离证据与预检/plan/2026-09-11-M3-隔离证据与预检-claude.md §1 与 §6 R-B、src/trivium/doctor.ts、src/trivium/probes/agy.ts。计划中检查 1 规定探针过期时「自动触发一次 doctor」，并在 R-B 中提出「触发前明确告知并给出预计耗时；doctor --no-model-calls 作为降级路径」。但：① 七个 skill 的执行契约是在 Bash 工具中非交互式运行 TV preflight --stage <s> --json，编排器无法与人交互并在终端中「明确告知并等待确认」；② 完整 doctor 耗时数分钟，极易击穿 Driver 的 Bash 默认 120s 超时；③ 若降级执行 doctor --no-model-calls，probes/agy.ts 会跳过模型探针，将 headless_read_ok、json_schema_ok 设为 null，导致后续预检项因探针缺失而依然无法通过。

**建议**：消除自动触发长时 doctor 的隐式行为：预检在探针过期时应直接快速失败（退出码 69），并在输出的 JSON/人读信息中明确指引开发者手工执行 trivium doctor（或提供带明确超时保护与只刷新静态版本的机制），不要在非交互调用中隐式拉起耗时数分钟的全局探测。

**问题**：topic resolve 命令的入参和出参契约未适配全流程（命令 A）与代码审（命令 C）的差异，导致状态机早期断裂。

**依据**：读了 .reviews/M3-隔离证据与预检/plan/2026-09-11-M3-隔离证据与预检-claude.md §2 与 skills/dual-run/SKILL.md、skills/dual-review-code/SKILL.md。计划在 §2 声明 topic resolve 输出 JSON 必须包含 subject_path。但在命令 A（/dual-run）执行时，stage 为 all，Driver 在 S0 预检之后才在 S1 起草方案，调用 topic resolve 时计划原稿物理上根本不存在；在命令 C（/dual-review-code）中，审查对象是工作区或指定分支的 git diff，没有单一的 subject_path 文档。若强行要求 topic resolve 定位被审文件，命令 A 与 C 在第 2 步就会报 missingArtifact 中止。

**建议**：规范 topic resolve 在各阶段的契约分支：针对 stage: all，允许 subject_path: null，仅解析主题与任务目标；针对 stage: code，解析目标分支/base 并输出 diff 目标而非单个文件路径；仅在 plan 与 bug 阶段强制校验 subject_path。

**问题**：桩适配器的注入机制未在架构中澄清，无法支撑工作进程（worker）派生模式下的故障注入测试。

**依据**：读了 .reviews/M3-隔离证据与预检/plan/2026-09-11-M3-隔离证据与预检-claude.md §4、§5，以及 src/trivium/review.ts（line 126）与 src/trivium/run-protocol.ts（line 221-225）。代码中 adapters 对象在 review.ts 和 rebuildContext 中硬编码引用了 agyAdapter 和 zcodeAdapter。而在真实的 review --start / --wait 链路中，实际执行测试的是独立的子进程 trivium review --worker <runId>。如果仅在进程内替换 CriticAdapter.run，派生出的独立 CLI 进程将无法获得桩适配器注入，导致 §17.2 的集成测试与 AC-06、AC-08 无法跨进程验证。

**建议**：在计划中明确桩适配器的跨进程注入机制（如通过受控的环境变量 TRIVIUM_STUB_CRITIC 或测试专用的 adapter registry 派发），确保派生的 worker 进程也能复现注入的故障。
