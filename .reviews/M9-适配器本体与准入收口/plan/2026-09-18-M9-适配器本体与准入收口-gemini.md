### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §8.1 / §7.1 / §6.1` |
| 类别 | contract ｜ 层次 plan |

**问题**：§8.1 的「分解形 token 加强判据」与 §7.1 的 ownsAdapterFile 组合后，会误杀纯事件流解析器 adapters/claude-trace.ts 中的合法工具名统计与覆盖率常量。

**依据**：计划 §8.1 提出将 Read,Grep,Glob 切分为分解形并在归属家适配器上判红；计划 §7.1 定义 ownsAdapterFile 包含 startsWith('<cliName>-')，使 adapters/claude-trace.ts 被判定为归属文件；而计划 §6.1 行 343 明确规定 adapters/claude-trace.ts 须导出 CLAUDE_MUST_HAVE_PATH = new Set(['Read']) 且 countTools 需匹配 toolUse.name === 'Read' 等。这导致 registry-parity.test.ts 契约测试 6 扫描时，claude-trace.ts 必定命中分解形 token 'Read' 被判红，触发「字面重建安全不变量」错误，且无法按纪律走 PROSE_EXCEPTIONS 豁免（见 test/unit/registry-parity.test.ts:1179-1186）。

**建议**：将 §8.1 分解形 token 的适用范围收窄为仅针对 argv 构造入口（即 adapters/<cliName>.ts），或在 ownsAdapterFile 校验分解形 token 时显式排除 *-trace.ts 与 *-events.ts。

**问题**：EV-43 形态无关清单中的复合条目 entrypoint/version 与 types.ts 导出的真实键集粒度脱节，会导致对账用例断言失败。

**依据**：计划 §4.1 列举形态无关 12 项时将 entrypoint 与 version 复合写作 entrypoint/version；但计划 §4.4 明确规定新增对账用例断言「清单并集 === ClaudeProbe 全部键（从 types.ts 源码 grep）」。查阅 src/trivium/types.ts:264-286，CommonProbe 中 entrypoint 与 version 是两个独立的顶级键名。若测试从源码直接提取键集，包含 entrypoint/version 的清单在并集全等比对时必将报错。加上 EV-44 的 project_memory_blocked（形态相关，共 8 格）后，ClaudeProbe 共有 21 个键，形态无关项应为 13 项。

**建议**：在 §4.1 与对账用例清单中将 entrypoint 与 version 分别作为独立项展开（形态无关项调整为 13 项），确保与 types.ts 提取出的键集合 1:1 精确匹配。

### AGY-03 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §6.2 行 390 / §3.4` |

**问题**：buildClaudeArgs 中 --settings 的注入前置条件仅判断 supported，未与 file_shape_verified 联动，在逐文件否定结案路径下行为割裂。

**依据**：计划 §6.2 行 390 规定 --settings 注入条件为「supported !== true 或外壳解析不出 ⇒ 不传并记原因」，未检查 file_shape_verified；而计划 §3.4 与 §6.3 行 425（及契约测试 A14）明确规定否定结案时 file_shape_verified 为 false 且 peer_deny_applied 必须读 file_shape_verified === true（见 test/unit/claude-events.test.ts:761）。若 EV-42 发生否定结案（逐文件规则不生效），supported 仍可能为 true（目录 glob 生效），按 §6.2 会依然强行注入单文件 deny 规则，造成参数注入行为与安全判定状态割裂。

**建议**：在 §6.2 中明确 --settings 的注入前置须为 supported === true 且 file_shape_verified === true，在逐文件未验（null）或否定结案（false）时同属不注入分支。
