## 1. 现状核实（`32dd96d`）

### 1.1 计划定稿的取法（现状一）

`resolvePlanFinal`（`review.ts:284`）：`resolveStageDriver(layout, 'plan')`（`driver-claim.ts:114`）判计划阶段执笔方——最新一份可读 run.json 的 `driver`，比它新的有读不出的即 `corrupt`；没有运行时按声明、再按缺省。`corrupt` ⇒ 不列、返回 `PLAN_FINAL_UNLISTED_WARNING`（`review.ts:269`）。否则 `locateSubject`（`topic.ts:76`）按该后缀取：文件名可解析、主题相同、后缀为该执笔方、无中缀，按轮次降序、同轮次文件名降序，剔除审查件后取第一份。抛出（没有计划目录或没有原稿）⇒ 不列、无告警。

### 1.2 告警的三个出口（现状二、三）

`prepareRun`（`review.ts:891`）只在 `stage === 'code'` 时调 `resolvePlanFinal`。`review.ts:1072～1074`：`planFinalWarnings`（至多一条）拼在剔除告警之前，`mustReadPrunedAll`（全量）进 run.json `gate.warnings`（`review.ts:1235`，经 `plainWarningText` 去掉 `⚠️ ` 前缀），`mustReadPruned`（剔除部分封顶 5 条）进 `RunContext`：

- `review --start`：`run-protocol.ts:414` 把 `rc.mustReadPruned` 并进返回的 `warnings`（`{ name, detail }`）；
- 同步 `review --stage`：`review.ts:1493` 并进 `warnings`（纯文本）；
- run.json：`gate.warnings`。`loadRoundReviews`（`gate.ts:1211`）读出、`checkAdjudication` 排在一切早退之前推为 `run_warning`（`gate.ts:250`）——所以代码阶段还没写应答件时 `gate --check` 也看得见。

跳过轮（文档类变更 `skipVerdict.skipped`）同样记 `gate.warnings`（`review.ts:1225` 注释，代码双审 CODEX-03）。

## 2. 设计

### 2.1 时点与位置（决策一）

`prepareRun` 计算段、`resolvePlanFinal` 之后：`stage === 'code'` 且 `planFinal.path` 非空时调复核（`review --start` 与同步 `review --stage code` 共用 `prepareRun`，一处即覆盖两条入口）。只读、置闸门与一切落盘之前；复核本身任何异常都不上抛（§2.4 第 ⑥ 格），保持「自动条目不拒跑」。

`planFinal.path` 为空时不复核：留痕读不出那一格已有「必读清单未列计划定稿」（现状一），没有计划阶段那一格无从谈起。两条告警因此互斥。

### 2.2 抽出接受集合（决策二）

`gate.ts` 新增导出：

```ts
/** 计划阶段裁决件里要求新一轮计划逐字引用的接受编号（§6.6 规则 9）：期望集内、裁为接受；去重排序 */
export function acceptedIdsForNextPlan(
  rows: readonly DispositionRow[],
  expectedIds: ReadonlySet<string>,          // 合格 ∪ 逐条降级
  expectedFallback: readonly string[] | null, // .fallback-items.md 的虚拟编号；null = 不按清单
): string[]
```

函数体就是 `gate.ts:650～659` 的表达式原样搬过去；`checkAdjudication` 第 6 步改为 `acceptedIdsForNextPlan(rows, idsSet, expectedFallback)`。注释（AGY-02 的「只收期望集内」）随之搬到函数上。

### 2.3 取哪一轮（决策二待定项的定案）

新增 `gate.ts` 导出 `recheckPlanFinal(layout, finalFileName)`，按下列步骤取「最新一轮有裁决件的运行」：

1. **执笔方取定稿文件名的后缀**（`parseArtifactName(finalFileName).role`）——不再调一次 `resolveStageDriver`：定稿就是按那一家的后缀取的，这样「核的是哪一家的候选」与「列的是哪份定稿」同源，两次判定之间也不会有竞态。
2. 计划阶段 `_meta/` 下的 `run-*.json` 按 run_id **从新到旧**逐份读（`readRunMeta`）；对每一份，在 `plan/` 根下找裁决件：文件名可解析、主题相同、后缀为**该轮 run.json 的 `driver`**、中缀 `revised`、轮次等于该轮 `rerun_index`——与 `checkAdjudication` 第 2 步的定位同一口径（`gate.ts:262`）。
3. **找到即停**；找不到就继续往旧里找。理由（§1.5）：没有裁决件的运行在实践中只有失败轮与崩溃骨架，它们不产生新的接受集合，此前那一轮裁下的接受项仍是定稿要兑现的承诺。若选「最新一次没有裁决件就不复核」，任何一次超时失败的计划双审都会让复核整个失效——而这正是 Driver 最可能「闸门过不了、索性改计划直接编码」的时刻。
4. 同一轮次被两次运行共用（崩溃骨架 + 正式运行，§1.5）时，从新到旧找，先遇到的那一份 run.json 即被采用；两者的 `driver` 与 `rerun_index` 相同，接受集合由裁决件决定，结果一致。不按裁决件 front-matter 的 `run_id` 认领：那是闸门的失败项（`bad_front_matter`），复核不重复判它。

### 2.4 判定（决策二）

找到那一轮之后：

| 格 | 条件 | 结果 |
|:---|:---|:---|
| ① | 计划阶段没有 `run-*.json` | 不复核、无告警 |
| ② | 有运行但没有一轮有裁决件 | 不复核、无告警 |
| ③ | 那一轮没有 `plan_final_check`（旧运行） | 不复核、无告警（决策二） |
| ④ | 那一轮接受集合为空（全部驳回 / 暂缓 / 零意见） | 不复核、无告警（决策七「全部驳回 ⇒ 不复核」） |
| ⑤ | 接受集合非空 | `checkNextPlan` 判：无失败 ⇒ 通过、无告警；有失败 ⇒ 告警（§2.5） |
| ⑥ | 无从复核：往旧里找的途中遇到读不出的 run.json；那一轮的 `driver` 与定稿后缀不同；复核过程抛出异常 | 告警（§2.5 的「无从复核」形态），不拒跑 |

第 ⑤ 格的输入：

- 接受集合：`loadRoundReviews(layout, 'plan', runId)` 给出 `reviews` / `expectedFallbackIds` / `expectedDegradedIds`，按 `checkAdjudication` 第 1、5 步同样拼出期望集（结构化编号 ∪ 逐条降级），读裁决件 `parseDisposition` 取 `rows`，交 `acceptedIdsForNextPlan`——与闸门的输入派生同一条路径。
- `checkNextPlan({ layout, driver, rerunIndex: 该轮 rerun_index, acceptedIds, planFinal: { subjectRerunIndex: 该轮标记的 subject_rerun_index, laterSubjectRerunIndexes: [] } })`。

**`laterSubjectRerunIndexes` 恒传空数组——这一处偏离了决策二「按它的标记与后续运行判定」的字面，请审查员判断。** 理由：闸门在「本轮已被后续运行接手」时核最小候选，是为了回看早期轮次时逐环各核其后一份；代码阶段问的只有一件事——**代码审查员此刻读到的那份定稿**合没合入最新一轮的接受项。按 §2.3 取到的那一轮之后若还有运行，它们都没有裁决件（失败轮或骨架），但其标记里的被审对象轮次可能更高（例如第 2 轮送审 r2 后超时）；照传会让 `checkNextPlan` 转去核最小候选 r2，而代码阶段读的是最大的那份（可能是此后又写的、没送审的 r3）——正是本题要堵的窗口。传空数组让它恒核最大候选，按 §1.3 第 4 点即 `resolvePlanFinal` 列出的那份。

`checkNextPlan` 一次至多给一条失败（两条失败分支都 `return`），复核取它即可；告警不需要 `warnings`（`planFinal` 非 null 时它不出 `next_plan_unchecked`）。

返回形状：

```ts
export type PlanFinalRecheck =
  | { kind: 'skipped' }                                                      // ①～④
  | { kind: 'passed'; runId: string; rerunIndex: number }                    // ⑤ 通过
  | { kind: 'failed'; runId: string; rerunIndex: number; failure: GateFailure } // ⑤ 不通过
  | { kind: 'unverifiable'; reason: string };                                // ⑥
```

`skipped` 不细分原因：四格的处置相同（不出声），细分只给测试用——测试改按「无告警」与变异断言（§3），不为它扩接口。

### 2.5 告警（决策三待定项的定案）

`review.ts` 新增 `PLAN_FINAL_RECHECK_WARNING = '计划定稿未通过复核'`，与 `PLAN_FINAL_UNLISTED_WARNING` 同形（`{ name, detail }`，`detail` 以 `WARNING_MARK` 开头）。组装函数 `planFinalRecheckWarning(...)` 放 `review.ts`：判据在 `gate.ts`，措辞在送审侧，与 `resolvePlanFinal` 的告警同处。

**文案**（`failed` 两种、`unverifiable` 一种；方括号内按实际填）：

- `failed`：
  「本主题计划定稿 [定稿项目相对路径] 没有通过复核：计划阶段第 [N] 轮（run [id]）有被接受的意见，按 §6.6 规则 9 的同一份判据核对——[checkNextPlan 失败消息原文]　涉及编号：[ids 顿号连接]。本轮照常审查，代码审查员读到的仍是这份定稿。处置二选一：① 把这些接受项合进计划定稿（没有新一轮计划时按上面的文件名写一份；编号逐条写进开头的「相对上一轮的改动」）后，重跑代码双审；② 把这份定稿送一轮计划双审（[entryCommandOf(代码阶段 Driver, 'dual-review-plan')]），按那一轮的裁决定稿后再跑代码双审。」
  - 失败消息原文复用 `checkNextPlan` 的 `message`：判据只有一份，措辞也只留一份，两处说法不会分叉；两种消息分别给出「应写的文件名」与「核对的文件 + 身份（代码阶段会读的计划定稿）」，正是决策三要的「点名定稿文件、缺的编号或缺的新一轮计划」。
  - `missing_next_plan` 的消息里「请写 …」那半句对复核同样成立（处置 ① 就是写它）。
- `unverifiable`：
  「本主题计划定稿 [路径] 无从复核：[原因，如「计划阶段运行留痕 [id] 读不出」「计划阶段第 [N] 轮的执笔方是 [x]，与定稿后缀 [y] 不同」「复核出错：[message]」]。本轮照常审查；定稿是否合入了计划阶段最新一轮被接受的意见，需人工核对。」

**排序与封顶**：`planFinalWarnings = [未列入?, 未通过复核?]`——两条互斥（§2.1），合起来至多一条；排在剔除告警之前、**不计入剔除封顶**（剔除告警的封顶管的是「按侧 × 条目」可能很长的那一串，这一条是主题级的单条事实，与「未列入」同理）。三个出口不用改：`mustReadPrunedAll` / `mustReadPruned` 自动带上。

**同一主题反复跑代码双审时**：每一轮都现算、都出（只要定稿仍不一致）。不做「已告警过就不再出」——那需要状态，而这条告警的意义恰恰是「这一轮读的定稿仍没合入」。

### 2.6 任务书第 4 段不标注（决策四的定案）

不加标注，任务书在任何复核结果下都与改前逐字相同。理由：

1. **处置不在审查员手里**。不一致要由 Driver 改定稿或送计划双审；审查员读到「定稿未通过复核」能做的只有两件事——自己去核计划（越出代码审的被审对象），或把计划的残缺当成代码的问题报出来。两者都把一个流程缺口变成审查噪声。
2. **带编号会推送裁决信息**（决策四的顾虑）。编号本身不含内容，但「AGY-01、GLM-03 被接受」告诉 codex 侧另两家提了什么、执笔方采纳了哪些——与 §9.4 第 4 条「裁决件不列入：列为必读等于把对方意见推进每一侧（FR-10）」同一个顾虑。不带编号的标注又没有信息量。
3. **告警已经到了该到的人**：`--start` 的 warnings 由 skill 要求逐条念给用户；run.json `gate.warnings` 在代码阶段 `gate --check` 以 `run_warning` 再出现一次，裁决时看得见。

## 6. 风险与边界

1. 复核也只在代码双审开跑那一刻成立：开跑之后再改定稿，本轮审查员读到的是冻结时的文件，下一轮代码双审才会再复核。
2. 最新一轮全部驳回时不复核（决策七）：此后另写的、不含早先轮次编号的定稿不会被发现。按「最新一轮」口径这是有意的——早先轮次的接受项已由那一轮的闸门核过其后一份。
3. 字面判据的两条边界（规则 9 边界①②：只核字面、跨轮同名编号）原样继承，EV-216 未定。
4. 每次代码双审多读计划阶段全部 run.json 直到命中一份有裁决件的：计划阶段通常 1～6 份、每份几 KB，可忽略。
