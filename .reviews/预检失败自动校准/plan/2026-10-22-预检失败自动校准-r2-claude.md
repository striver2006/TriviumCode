## 〇、要解决的问题

用户 2026-10-22 新需求：「预检没通过（退出码 69）：自动运行 trivium doctor，然后继续进行双审，无需确认。」

现状有三道墙，缺一道都做不成：

1. **skill 侧**：四条命令的预检步骤都写着「失败则原样转述并停止」——`skills-src/partials/review/body.md:73`（三条 `/dual-review-*` 共用）与 `skills-src/commands/run.contract.md:80`（`/dual-run` S0.6）。
2. **预检侧**：失败项只有人读的 `detail`，没有机读字段说「这条 doctor 能不能修、该跑哪一家、用什么组合」。skill 若要自己从文案里猜，就违反「skill 不自行判断」的纪律，也会跟着文案改动静默漂移。
3. **doctor 侧**：没有总时限。各家探针单次调用的超时是 agy / codex / claude 180 s、zcode 300 s（`probes/agy.ts:27`、`probes/codex.ts:58`、`probes/claude.ts:101`、`probes/zcode.ts:73`），一家要调若干次；会话里 Bash 工具上限 600 s（设计 §2 表 206 行，只登记了 Claude Code）。工具超时杀掉 doctor 时：
   - 探针以 `killTree` 拉起的子进程自成进程组，够不到、过继给 init；
   - 不带 `killTree` 的那些（`--version`、`models`、git 辅助调用等）与 doctor 同组，按缺省处置也未必一起结束；
   - 现行前台中断转发（`run-protocol.ts:1188`）走冻结式 `shutdownTrackedTrees`，探针的 `finally` 不跑，临时目录——其中 codex、zcode 两家放的是**含真实凭据的副本**（`probes/codex.ts:778`、`probes/zcode.ts:1590`）——留在系统临时目录里。

手册与源码里有两句说法随之过时，需改写：
- 「`doctor` 必须在终端里跑……会击穿 Bash 工具的 600s 超时——届时配额已烧而结论未落盘」（`doc/07_manuals/MANUAL_user.md:193`、`:945`；`doc/02_design/LLD_orchestrator.md:243`；`src/trivium/preflight.ts:9-12` 注释与 `:169-170` **面向用户的报错正文**）。
- 其中「结论未落盘」早已不成立：doctor 每探完一段就 `checkpoint`（`doctor.ts:690-746`，GLM-08 起分段落盘）。丢掉的只会是**撞上超时那一家**的结论。

本主题不改：预检的检查项与判据本身（含「全部过期才失败」的现行口径）、doctor 各家探针的探测内容、`review` 的任何行为、不带 `--deadline-s` 时 doctor 的行为。

## 一、设计决定

### D1 · 哪些失败项归「doctor 能修」

**判据**：失败说的是「**落盘的探针结论**缺失、过期、或与现场对不上」，而现场本身大概率是好的——doctor 重探一遍就会写入新结论。反过来，**探针已经实测到的否定结论**（读不到、沙箱失守、没登录）与**环境本身坏了**（权限、git、配置未填）都不归 doctor：重探只会再测出同一个否定、白花配额。

拿不准的一律归「不能修」（fail-closed）：错判为「能修」的代价是白花一轮 doctor 配额再停下；错判为「不能修」的代价只是退回今天的行为。

逐项（`runPreflight` 的检查顺序，`preflight.ts:1031-1145`）：

| 检查项（name） | 退出码 | doctor 能修 | 目标 |
| :--- | :--- | :--- | :--- |
| Driver 会话声明 / 当轮 Driver | 恒通过 | — | — |
| 模型 slug 合法、档位组合合法（`bad`） | 64 | 不在本主题范围（非 69） | — |
| 档位组合合法（`unavailable`：路线配置或入口读不了，`:525-527`） | 69 | 否（权限 / 配置问题） | — |
| 探针结论存在（`generated_at === null`，`:163-172`） | 69 | 是 | 入选各侧的本轮组合 |
| 探针结论未过期（全部过期，`:174-183`） | 69 | 是。该项只在**全部**登记 CLI 都过期时失败，失败即入选各家必在过期之列；目标只取入选侧 | 入选且过期各侧的本轮组合 |
| `${cli} 路线探针`（所选路线无有效探针，`:302-306`） | 69 | 是 | 该侧该路线的本轮组合 |
| `${cli} 路线探针新鲜度`（`:308-313`） | 69 | 是 | 同上 |
| `${label} 可调用`（探针记录的入口不在，`:324-329`） | 69 | 是（入口可能挪了；真卸载了 doctor 会给出「未找到可执行文件」的明确结论，下一轮预检照样失败、停下） | 该侧的本轮组合 |
| `${label} 可调用`（取版本失败，`:338-339`） | 69 | 否（CLI 本身跑不起来） | — |
| `${label} 版本与探针一致`（版本漂移，`:340-347`） | 69 | 是（最典型的一类：CLI 自升级） | 该侧（入选侧按路线）的本轮组合 |
| 只读能力可用（`checkReadonlyCapability`，`:660-698`） | 69 | 按侧收集，见下 | 标可修的那几侧的本轮组合 |
| 归档与 git 可用 | 69 | 否 | — |
| 编译测试命令已配置 | 69 | 否（需人确认后写配置，§14.1） | — |
| `${display} 已认证`（探活失败 / 探活内部失败） | 69 | 否（用户已定：认证失败照旧停下） | — |

**「本轮组合」**：入选侧 × 本次 scope 的各阶段，经与预检同一次的 `resolveTier`（同一组命令行覆盖、档位旗标）解析出（模型、思考等级、厂商 profile），按侧去重。有路线概念的侧（适配器实现 `probeFor`，今天是 codex、claude）同一侧不同厂商 profile 是不同目标；显式原生（vendor profile 为 null 且来源是显式 `--native-*` 或配置 `profile: null`）照样作为目标、带 `--native-<id>`。这样「探针结论存在 / 全部过期」把后面的路线检查短路掉时，第一次校准也已经覆盖本轮要用的路线（CODEX-04）。

**只读能力一格**：各适配器 `availability()` 的每个 `ok: false` 分支自己声明——返回值加可选字段 `fix?: 'doctor'`，**缺省即不能修**（`adapters/base.ts:151` 的签名扩一个可选键，旧实现与桩不改也安全）。`checkReadonlyCapability` 不拆项（拆了会改检查名、波及既有输出与用例），内部按侧收集：**每个**不可用侧都标了 `fix: 'doctor'` 时该项才可修，目标为这几侧；任一侧不可修整项即不可修（AGY-04）。逐分支初判（实施时逐条核对、在测试里钉住）：

- 「尚未探测，请先运行 trivium doctor --only X」「探针未找到 X 可执行文件」「探针尚未实测 headless 读取能力」 ⇒ `fix: 'doctor'`；
- `readonly_flags` 为空（沙箱 / 白名单失守或未判定）、headless 读不到文件、agy 只读 Agent 未安装、zcode provider 配置定位不到、claude 路线配置或指纹读不了、入口不可执行 ⇒ 不标（不能修）。

**混合失败的处理**：一次预检里只要有**任一**失败项不能修，整体就不自动校准——doctor 修好其余各项，预检照样会卡在那一项上，配额白花。预检有短路（前一项失败后面的不跑），所以第一次预检看不到的失败项可能在重跑时才露出来——这由 D4 的「至多一轮」兜住。

### D2 · 预检输出的机读字段

两层，都只在 `--json` 输出里出现，人读输出只多一行提示。

**逐项**：失败项（`ok: false`）带 `recalibrate`：

```json
{ "name": "Codex 版本与探针一致", "ok": false, "detail": "…",
  "recalibrate": { "fixable": true, "targets": [
    { "only": "codex", "flags": ["--profile-codex", "〈名〉", "--model-codex", "〈模型〉", "--effort-codex", "〈等级〉"] } ] } }
{ "name": "Codex 已认证", "ok": false, "detail": "…", "recalibrate": { "fixable": false } }
```

- `only` 是 doctor `--only` 的取值（cliName，由注册表派生，`doctor.ts:82-88`）。
- `flags` 是让 doctor 探到**本轮组合**所需的旗标（CODEX-05）：doctor 的 codex / claude 段固定按 code 阶段解析模型（`doctor.ts:838`、`:879`），只给路线不给模型时，plan 阶段换了家族的路线会被发 code 阶段的模型。所以：
  - 消费覆盖的侧（doctor 里经 `overridesFor` 读覆盖的段，今天是 codex、claude）带路线旗标（`--profile-<id> <名>` 或 `--native-<id>`），模型非空时带 `--model-<id>`，思考等级非空时带 `--effort-<id>`——doctor 已接受这几个旗标（`cli.ts:195`）；
  - 不消费覆盖的侧（探测用固定口径，今天是 agy、zcode）只给 `--only`，否则 doctor 末尾会报「覆盖没用上」（EV-245）。
  - 哪一侧消费覆盖，按 doctor 的段是否经 `overridesFor` 判，由 `doctor.ts` 导出一个按 cliName 查询的函数，预检调用它；不在预检里写 Agent id 或 CLI 名字面量。
- 通过项不带这个键；`CheckResult` 内部加可选字段 `recalibrate`，由产出该项的代码置位，**不看文案**（同 EV-123 `warn` 的做法）。

**汇总**（顶层，预检失败时恒在、通过时不出）：

```json
"recalibration": {
  "eligible": true,
  "why": "全部失败项都可由 doctor 重新校准",
  "invocations": [
    { "only": "codex", "args": ["doctor","--only","codex","--profile-codex","〈名〉","--model-codex","〈模型〉","--deadline-s","480","--json"],
      "deadline_s": 480, "bash_timeout_ms": 540000 }
  ]
}
```

- `eligible` 为真的充要条件：退出码为 69，且每个失败项都 `fixable: true`，且合并后的调用清单非空。否则 `eligible: false`、`invocations: []`，`why` 说明是哪一条拦下的（「Codex 已认证 不能由 doctor 修复」/「退出码 64 不在自动校准范围」）。
- `invocations` 按（`only`、`flags`）去重，按 `ALL_CLI_NAMES` 的顺序排，**同一侧两个组合就是两次调用**。skill 只照抄 `args`，不拼、不改、不去重。
- 预检**根本没走到输出**的 69（`loadCtx` 抛出的未初始化等受控错误）没有这个键——skill 按「键缺席 ⇒ 不自动校准」处理（fail-closed，写进 skill 正文）。

### D3 · doctor 的总时限

**新旗标** `doctor --deadline-s <秒>`：整数，取值 30～540，越界退 64。不给时行为逐字不变（含前台中断转发）。

**1. 段作用域**：`runDoctor` 把每一段（agy / zcode / codex / claude）包进 `exec.ts` 新增的段作用域 `withProbeSection(cliName, fn)`（`AsyncLocalStorage`，与现成的 `withTreeTag` 同一机制；作用域内同时设树标签）。作用域只在给了时限时启用；不给时段照旧直接调用。

**2. 段级进程组记录与按组结束**（CODEX-01）：作用域内每次派生把（组号、父进程句柄、标签）记进**段级记录**，组长退出也**不删**——这与 `liveTrees`（组长 exit 即删，`exec.ts:292-300`）不同，后者原样保留给 worker 与前台中断转发。到点时对记录里的每个组：
   - 组长未退出（按父进程句柄判）⇒ 按组发 SIGTERM；
   - 组长已退出，但 `processGroupMemberCount` 报非僵尸成员数大于 0 ⇒ 同样按组发（组内还有成员时组号不会被复用；判据与 `--cancel` 按记录结束 CLI 的「组长已退出但组号下还有非僵尸成员」一格同源，EV-165）；
   - 成员数为 0 或取不到 ⇒ 不发（取不到时如实记进输出）；
   - 宽限 `WORKER_TREE_GRACE_MS` 后对仍有成员的组 SIGKILL，至多再等 `WORKER_TREE_KILL_WAIT_MS`，按成员数为 0 确认；确认不了的组号列进输出 `residue`。
   - 计成员数的 `ps` 在段作用域**之外**发，不受下一条「中止派生」拦截。
   - 实现上把 `shutdownTrackedTrees`（`exec.ts:964`）的按组终止部分与这里共用 `terminateProcessGroup`，冻结位只由原函数置，worker 与前台中断转发的行为逐字不变。

**3. 覆盖面按作用域兜**（CODEX-02）：段作用域内的 `run()` **一律**按 `killTree` 派生（`detached`、进段级记录、计数），不论调用点有没有写 `killTree`。这把 r1 列的 9 处不带 `killTree` 的调用（`--version`、`models` 等）与 git 辅助调用（`util/git.ts` 缺省 120 s、只有显式传超时才 `killTree`；`probeScratchPaths` 等收尾调用都不传，`probes/agy.ts:241-245`、`probes/zcode.ts:335-339`）一并纳入，不逐个改调用点。

**4. 停止派生、在跑的那一段作废**：到点时置进程级、不可撤销的「中止派生」标志。段作用域内的 `run()` 此后不再 `spawn`，**立即兑现**一个合成结果（`spawned: false`、`code: null`、新增 `aborted: true`），让探针沿自己的错误路径走到 `finally`、删掉临时目录；作用域外（成员计数、收尾）不受影响。与冻结（`treeShutdown`）互不相干。
   - `runDoctor` 在每一段返回后先看中止标志。置位后返回的段一律当作「未探完」：不赋 `probe.cli[x]`、不 `checkpoint`、不进 severity——合成结果与被杀的调用会被探针读成各种否定结论，落盘就是把「被我们打断」写成「能力缺失」。尚未开始的段记为 `not_started`。
   - 段包装在中止标志已置位时**接住该段抛出的任何异常**（截断输出的解析错误之类），记为未探完、不重抛（AGY-01）；未置位时照旧（夹具失败归 `guardFixture`，其余原样重抛）。
   - 已探完的段此前已 `checkpoint`，原样保留；收尾的 `checkpoint(null)` 照常执行（补 `generated_at`）。这一点之所以安全，依赖既有不变量：`cliProbeIsFresh`（`config.ts:995` 起）按**各家自己的 `probed_at`** 判新鲜、不看全局 `generated_at`——被作废那一家下一次预检仍按路线探针新鲜度退 69（GLM-02，用例与变异咬住）。

**5. 时限控制器是独立路径**（AGY-02）：控制器是与 `runDoctor` 并行的计时器回调，到点后的全部收尾都在它自己的异步链里：置中止标志 → 按组结束（第 2 条）→ 若此刻有一次 `checkpoint` 在写，等它写完（`patchProbe` 不经 `run()`）→ 至多等 `DEADLINE_UNWIND_MS`（拟 20 s）让 `runDoctor` 返回。`runDoctor` 先返回就由 CLI 正常出结果；等不到时控制器按自己记的段状态出结果、补删台账目录（第 7 条）、执行 `checkpoint(null)`，然后 `process.exit(76)`——不依赖挂住的 await 返回。事件循环被**同步**代码堵住时任何计时器都打断不了，写进第五节边界。

**6. 宿主先发信号**（CODEX-03）：带时限的 doctor 不装 `installForegroundInterruptForwarding`，改由控制器接 SIGINT / SIGTERM：首个信号即按「到点」处置（第 4、5 条，结果里 `deadline.reason` 记 `signal`），第二个信号立即退出（同现行前台转发的「再按一次立即退出」）。宿主给了宽限期，协作式收尾就能把临时目录删掉；宿主直接 SIGKILL 时进程内什么都做不了，由第 7 条补。

**7. 临时目录台账**（CODEX-03、GLM-01）：段作用域内经 `makeTempDir` 建的目录，同步记进 `<run_root>/doctor-temp-ledger.json`（`runtime.run_root`，缺省 `~/.trivium/runs`；写入走临时文件加改名），`tryRemoveTempDir` 删成功即注销。`probes/codex.ts:778`、`probes/zcode.ts:1590` 两处裸 `fs.mkdtemp` 改走 `makeTempDir`。补删在两个时点：本次 doctor 收尾时（台账里本进程登记、仍在盘上的条目），与**下一次** doctor 启动时（台账里任何仍在盘上的条目）。补删只认台账里的路径，并核对它的真实路径落在系统临时目录下、目录名是 `makeTempDir` 的前缀形态——不按前缀扫系统临时目录（违反「只删 mkdtemp 返回值」的 R1，2026-09-20 事故规矩）。删不掉的列进输出 `residue`。

**输出**：`--json` 新增 `deadline` 段（只在给了 `--deadline-s` 时出现）：

```json
"deadline": {
  "limit_s": 480, "hit": true, "reason": "deadline",
  "sections": [
    { "only": "codex", "state": "finished", "launches": 6, "notes": ["…"],
      "rerun": "trivium doctor --only codex --profile-codex 〈名〉 --model-codex 〈模型〉" },
    { "only": "claude", "state": "in_progress", "launches": 3, "notes": ["…"],
      "rerun": "trivium doctor --only claude --profile-claude 〈名〉 --model-claude 〈模型〉",
      "note": "在时限内没探完，本段已拉起 3 次子进程，结论未落盘（其中调用模型的那几次配额已花）。会话里拉起的厂商 CLI 有过间歇挂满单次探针超时的先例（EV-243），请在终端单独跑上面这条命令。" }
  ],
  "residue": []
}
```

- `sections` 覆盖本次要探的**每一段**（CODEX-06）：`state` 取 `finished` / `in_progress` / `not_started`；`notes` 是该段的 notes 原文（`[cli]` 前缀那些）；`rerun` 是给用户在终端复制的完整命令（含 `--only`、路线与模型旗标，不含 `--deadline-s` 与 `--json`），由 doctor 按本次收到的旗标原样拼出。
- `launches` 是段作用域内派生的子进程数（含 git 辅助调用），不区分其中哪几次调了模型——按上界交代配额，`note` 就这么写。
- `note` 只出现在未探完的段；EV-243 一句**不写 Agent id 或 CLI 名字面量**（`registry-parity` 纪律）：它对哪一家都成立，是「会话里拉起」这件事的先例。
- 人读输出在末尾多一段「本次时限 N 秒，已到点（或：收到信号）：已探完 …；未探完 …（请在终端单独跑：…）」。

**退出码**：到点或收到信号（`hit: true`）退新增的 `EXIT.DOCTOR_PARTIAL = 76`（`exit-codes.ts` 登记，与 64 / 69 / 73 / 75 均不冲突），**优先于** blockers 的 69——「没探完」与「探完了有问题」要分得开；已探完各段的 blockers 照样列在输出里。未到点时退出码规则逐字不变（有 blockers 退 69，否则 0）。

### D4 · skill 的自动校准流程（四条命令同一口径）

新增公共片段 `skills-src/partials/preflight/recalibrate.md`，在 `partials/review/body.md` 第 2 步与 `commands/run.contract.md` S0.6 两处以 `{{> preflight/recalibrate}}` 引入，替换「失败则原样转述并停止」那一句。四家载体的渲染产物（`skills/*/SKILL.md`、`skills/dual-critic/entry/*/…`）随构建重生成。正文要点：

1. 预检退 0：照旧。
2. 预检退 69 且 `recalibration.eligible === true`：**不向用户确认**，先发一行文本「预检退 69，以下失败项可由 doctor 重新校准：…；将依次在前台跑 N 次 doctor（每次至多 `deadline_s` 秒），会消耗少量配额」，然后逐条执行 `recalibration.invocations`：
   - 命令为 `TV` 加 `args`（逐个照抄，不改、不增删）；**前台调用**，Bash 工具超时设为该条的 `bash_timeout_ms`；不用后台运行，不拆成发起与等待两步；
   - 每条结束后先发一行播报（家名、退出码、阻断项条数、`deadline.hit` 时点名未探完的段），再发下一条；
   - 任一条退出码非 0（69 / 76 / 64 / 1，或被工具超时打断）都**继续下一条**——是否真修好由重跑预检判，不由 doctor 的退出码判。
3. 全部跑完后**重跑同一条预检命令一次**（旗标逐字相同）：
   - 通过：照旧往下走（`warnings` 照旧念），并在同一条消息里说明「预检首次退 69，已自动校准后通过」；
   - 仍失败（任何退出码）：**停下**，一并转述：第一次预检的失败项；每次 doctor 调用的退出码、`blockers`、`warnings`，以及 `deadline.sections` 里各段的 `state`、`notes` 与 `rerun`（未探完的段连同 `note` 原文）；第二次预检的失败项。明确请用户在终端跑仍失败那几家对应的 `rerun`。第二次预检的 `recalibration` 即使 `eligible` 也**不再**自动校准。
4. 退出码不是 69、或 `recalibration` 键缺席、或 `eligible` 为假：照旧原样转述并停止（`why` 一并念出）。

`/dual-run` 只有 S0.6 一次预检，所以一次命令至多一轮自动校准；`/dual-review-*` 同理（第 2 步）。

### D5 · 时限取值：统一缺省 + 配置键可调

- 新增配置键 `preflight.recalibrate_deadline_s`（整数，缺省 480，取值 30～540；schema、`config-consumers` 对账、手册 §5 同步，AGY-05）。预检按它给出 `deadline_s`，并推出 `bash_timeout_ms = min(600000, deadline_s×1000 + 60000)`——与 `--wait` 的 `bashTimeoutFor`（`run-protocol.ts:387-389`）同一公式、同一 60 s 余量；实施时把这个函数挪到一个不引入环依赖的位置共用。
- **统一取值、不按载体取值**：注册表与载体配置里**没有**任何一家工具超时上限的实测登记（`skills-src/carriers/*.yaml` 无此键；设计 §2 只登记了 Claude Code 的 120 s / 600 s）。按载体取值就得先登记一份没测过的事实，违反 P7「能力靠探针，不靠记忆」。`--wait` 现行也是统一取值。某家载体的上限低于缺省值时，用户把配置键调小即可；宿主先发 SIGTERM 的情形由 D3 第 6 条兜住，宿主直接 SIGKILL 由 D3 第 7 条在下一次 doctor 补删。**四家载体工具时限的实测**要在各家载体里起真实会话、花配额，本主题不做，登记进 BACKLOG EV-251 残余。
- **480 s 的依据**：全量 doctor 四家约 2～4 分钟（手册 §3.4），单家一般远低于此；单次探针调用上限 180～300 s，一家撞上一次挂满还能留出余量做完其余几臂。取 480 而不是贴着 540，是给 D3 的收尾（按组结束约 3～4 s、成员计数的 `ps` 至多 10 s、兜底至多 20 s）与进程启动留空。最坏情形：入选三家都要校准且都挂满，总耗时约 3 × 9 分钟；这在开场那一行播报里说清楚。

### D6 · 配额与上限

- **收窄**：只跑失败项点名的那几侧、那几个组合（D1、D2）；只在全部失败项都能修时才跑（D1）。
- **上限**：每次命令调用至多一轮（D4）；每侧每个组合至多一次 doctor；每次 doctor 至多 `deadline_s` 秒。
- **不做的**：不跨命令记「最近自动校准过」（例如十分钟内同一家不再自动跑）。用户连发同一条命令、每次都卡在同一个修不好但被判为能修的失败上时，会每次各烧一轮。D1 的「拿不准即不能修」是这一条的主防线；跨命令冷却要落盘状态、引入新的过期判据，收益不抵复杂度。作为已知边界写进手册与 BACKLOG。

### D7 · 第三方 claude 路线在会话里挂满（EV-243）撞上时限时怎么转述

不针对 claude 写特判。两种形态：

- 单次调用挂满 180 s、被探针自己的超时杀掉：doctor 照样跑完（`deadline.hit: false`），该段 `notes` 里有「未得出结论」一类原因，重跑预检仍失败 ⇒ 按 D4 第 3 条停下，转述该段 `notes` 与 `rerun`。
- 连续几次挂满、累计撞上总时限：该段 `state: in_progress`，`note` 里那句 EV-243 先例与 `rerun` 原样转给用户。

两种形态都落到「请在终端单独跑」，与今天用户在终端跑能通过的实测一致（记忆 pipeline-known-pitfalls 第 67 条）。

## 五、已知边界（进 BACKLOG EV-251）

- 四家载体的工具时限未实测；某家低于缺省值时须用户调小配置键。
