- 主题：预检失败自动校准（`doc/01_requirements/原始需求.txt` 2026-10-22 需求第 1 条；拟登记 BACKLOG EV-251）

## 〇、要解决的问题

用户 2026-10-22 新需求：「预检没通过（退出码 69）：自动运行 trivium doctor，然后继续进行双审，无需确认。」

现状有三道墙，缺一道都做不成：

1. **skill 侧**：四条命令的预检步骤都写着「失败则原样转述并停止」——`skills-src/partials/review/body.md:73`（三条 `/dual-review-*` 共用）与 `skills-src/commands/run.contract.md:80`（`/dual-run` S0.6）。
2. **预检侧**：失败项只有人读的 `detail`，没有机读字段说「这条 doctor 能不能修、该跑哪一家」。skill 若要自己从文案里猜，就违反「skill 不自行判断」的纪律，也会跟着文案改动静默漂移。
3. **doctor 侧**：没有总时限。各家探针单次调用的超时是 agy / codex / claude 180 s、zcode 300 s（`probes/agy.ts:27`、`probes/codex.ts:58`、`probes/claude.ts:101`、`probes/zcode.ts:73`），一家要调若干次；会话里 Bash 工具上限 600 s（设计 §2 表 206 行）。工具超时杀掉 doctor 时，正在跑的探针子进程（`killTree` 自成进程组）够不到、过继给 init；探针在 `finally` 里删的临时目录——其中 codex、zcode 两家放的是**含真实凭据的副本**（`probes/codex.ts:778`、`probes/zcode.ts:1590`）——也就留在了系统临时目录里。

手册与源码里有两句说法随之过时，需改写：
- 「`doctor` 必须在终端里跑……会击穿 Bash 工具的 600s 超时——届时配额已烧而结论未落盘」（`doc/07_manuals/MANUAL_user.md:193`、`:945`；`doc/02_design/LLD_orchestrator.md:243`；`src/trivium/preflight.ts:9-12` 注释与 `:169-170` **面向用户的报错正文**）。
- 其中「结论未落盘」早已不成立：doctor 每探完一段就 `checkpoint`（`doctor.ts:690-746`，GLM-08 起分段落盘）。丢掉的只会是**撞上超时那一家**的结论。

本主题不改：预检的检查项与判据本身、doctor 各家探针的探测内容、`review` 的任何行为。

## 一、设计决定

### D1 · 哪些失败项归「doctor 能修」（焦点：哪些检查归 doctor 能修）

**判据**：失败说的是「**落盘的探针结论**缺失、过期、或与现场对不上」，而现场本身大概率是好的——doctor 重探一遍就会写入新结论。反过来，**探针已经实测到的否定结论**（读不到、沙箱失守、没登录）与**环境本身坏了**（权限、git、配置未填）都不归 doctor：重探只会再测出同一个否定、白花配额。

拿不准的一律归「不能修」（fail-closed）：错判为「能修」的代价是白花一轮 doctor 配额再停下；错判为「不能修」的代价只是退回今天的行为。

逐项（`runPreflight` 的检查顺序，`preflight.ts:1031-1145`）：

| 检查项（name） | 退出码 | doctor 能修 | 该跑哪一家 |
| :--- | :--- | :--- | :--- |
| Driver 会话声明 / 当轮 Driver | 恒通过 | — | — |
| 模型 slug 合法、档位组合合法（`bad`） | 64 | 不在本主题范围（非 69） | — |
| 档位组合合法（`unavailable`：路线配置或入口读不了，`:525-527`） | 69 | 否（权限 / 配置问题） | — |
| 探针结论存在（`generated_at === null`，`:163-172`） | 69 | 是 | 本轮入选的每一家 |
| 探针结论未过期（全部过期，`:174-183`） | 69 | 是 | 入选且在 `staleCliProbes` 里的那几家 |
| `${cli} 路线探针`（所选路线无有效探针，`:302-306`） | 69 | 是 | 该家，带路线旗标 |
| `${cli} 路线探针新鲜度`（`:308-313`） | 69 | 是 | 该家，带路线旗标 |
| `${label} 可调用`（探针记录的入口不在，`:324-329`） | 69 | 是（入口可能挪了；真卸载了 doctor 会给出「未找到可执行文件」的明确结论，下一轮预检照样失败、停下） | 该家 |
| `${label} 可调用`（取版本失败，`:338-339`） | 69 | 否（CLI 本身跑不起来） | — |
| `${label} 版本与探针一致`（版本漂移，`:340-347`） | 69 | 是（最典型的一类：CLI 自升级） | 该家（入选侧按路线） |
| 只读能力可用（`checkReadonlyCapability`，`:660-698`） | 69 | **按适配器逐条声明**，见下 | 该家 |
| 归档与 git 可用 | 69 | 否 | — |
| 编译测试命令已配置 | 69 | 否（需人确认后写配置，§14.1） | — |
| `${display} 已认证`（探活失败 / 探活内部失败） | 69 | 否（用户已定：认证失败照旧停下） | — |

**只读能力一格**由各适配器 `availability()` 的每个 `ok: false` 分支自己声明——返回值加可选字段 `fix?: 'doctor'`，**缺省即不能修**（`adapters/base.ts:151` 的签名扩一个可选键，旧实现与桩不改也安全）。逐分支初判（实施时逐条核对、在测试里钉住）：

- 「尚未探测，请先运行 trivium doctor --only X」「探针未找到 X 可执行文件」「探针尚未实测 headless 读取能力」 ⇒ `fix: 'doctor'`；
- `readonly_flags` 为空（沙箱 / 白名单失守或未判定）、headless 读不到文件、agy 只读 Agent 未安装、zcode provider 配置定位不到、claude 路线配置或指纹读不了、入口不可执行 ⇒ 不标（不能修）。

**混合失败的处理**：一次预检里只要有**任一**失败项不能修，整体就不自动校准——doctor 修好其余各项，预检照样会卡在那一项上，配额白花。预检有短路（前一项失败后面的不跑），所以第一次预检看不到的失败项可能在重跑时才露出来——这由 D4 的「至多一轮」兜住。

### D2 · 预检输出的机读字段（焦点：机读字段怎么定）

两层，都只在 `--json` 输出里出现，人读输出只多一行提示。

**逐项**：失败项（`ok: false`）带 `recalibrate`：

```json
{ "name": "Codex 版本与探针一致", "ok": false, "detail": "…",
  "recalibrate": { "fixable": true, "targets": [ { "only": "codex", "route_flags": ["--profile-codex", "〈名〉"] } ] } }
{ "name": "Codex 已认证", "ok": false, "detail": "…", "recalibrate": { "fixable": false } }
```

- `only` 是 doctor `--only` 的取值（cliName，由注册表派生，`doctor.ts:82-88`）；`route_flags` 只在失败与具体路线绑定时给（codex / claude 的 `probeFor` 路线：`--profile-<审核者 id> <名>` 或 `--native-<审核者 id>`；doctor 已接受这两个旗标，`cli.ts:195`）。
- 通过项不带这个键；`CheckResult` 内部加可选字段 `recalibrate`，由产出该项的代码置位，**不看文案**（同 EV-123 `warn` 的做法）。

**汇总**（顶层，预检失败时恒在、通过时不出）：

```json
"recalibration": {
  "eligible": true,
  "why": "全部失败项都可由 doctor 重新校准",
  "invocations": [
    { "only": "codex", "args": ["doctor","--only","codex","--profile-codex","〈名〉","--deadline-s","480","--json"],
      "deadline_s": 480, "bash_timeout_ms": 540000 }
  ]
}
```

- `eligible` 为真的充要条件：退出码为 69，且每个失败项都 `fixable: true`，且合并后的调用清单非空。否则 `eligible: false`、`invocations: []`，`why` 说明是哪一条拦下的（「Codex 已认证 不能由 doctor 修复」/「退出码 64 不在自动校准范围」）。
- `invocations` 按（`only`、`route_flags`）去重，按 `ALL_CLI_NAMES` 的顺序排，**同一家两条路线就是两次调用**。skill 只照抄 `args`，不拼、不改、不去重。
- 预检**根本没走到输出**的 69（`loadCtx` 抛出的未初始化等受控错误）没有这个键——skill 按「键缺席 ⇒ 不自动校准」处理（fail-closed，写进 skill 正文）。

### D3 · doctor 的总时限（焦点：时限取多少、到点怎么结束、未探完那一家怎么交代）

**新旗标** `doctor --deadline-s <秒>`：整数，取值 30～540，越界退 64。不给时行为逐字不变。

**到点的处置**——不复用 `shutdownTrackedTrees` 的冻结，原因在 `util/exec.ts:950-963` 写得很清楚：冻结后 `run()` 永不兑现、`finally` 不跑，而探针的 `finally` 正是删凭据副本的地方。改为**协作式中止**：

1. **停止派生**：`exec.ts` 新增进程级、不可撤销的「中止派生」标志。置位后 `run()` 不再 `spawn`，**立即兑现**一个合成结果（`spawned: false`、`code: null`、新增 `aborted: true`），让探针代码沿自己的错误路径走到 `finally`、删掉临时目录。与冻结（`treeShutdown`）互不相干，两者并存。
2. **按组结束在跑的子进程**：对 `liveTrees` 里尚未退出的组，复用 `terminateProcessGroup`（宽限 → SIGKILL → 确认，参数同 worker 处理器 `WORKER_TREE_GRACE_MS` / `WORKER_TREE_KILL_WAIT_MS`）。把 `shutdownTrackedTrees` 拆成「置冻结位」+「按组终止」两段，后一段导出为 `terminateTrackedTrees`，doctor 只调后一段；worker 与前台中断转发的行为逐字不变。被杀的 `run()` 照常兑现（`signal: SIGTERM/SIGKILL`），探针继续向下走、走到 `finally`。
3. **补上进程组的覆盖面**：今天探针里有几处 `run()` 没带 `killTree`（`--version`、`models`、`debug models`、`exec --help`、`node -v`：`probes/agy.ts:56,62`、`probes/codex.ts:89,361,697,821,823`、`probes/claude.ts:673`、`probes/env.ts:37`），它们与 doctor 同组、不在登记里，到点够不到。这些调用都是零配额的短命令，改成 `killTree: true` 的唯一代价是多一个进程组；另加一条源码对账测试：`src/trivium/probes/*.ts` 里每个 `run(` 调用都带 `killTree`（同 `registry-parity` 一类的 grep 对账）。夹具建仓的 `git` 调用（`util/git.ts`）不改：它们有 30 s 超时、到点后被第 1 条拦下不再派生，在跑的那一次自己结束。
4. **在跑的那一家作废、不落盘**：`runDoctor` 在每一段返回后先看中止标志。置位后返回的段一律当作「未探完」：不赋 `probe.cli[x]`、不 `checkpoint`、不进 severity——合成结果与被杀的调用会被探针读成各种否定结论，落盘就是把「被我们打断」写成「能力缺失」。尚未开始的段同样记为未探完。**已探完的段**此前已经 `checkpoint` 过，原样保留；收尾的 `checkpoint(null)` 照常执行（补 `generated_at`）。到点那一刻恰好有一次 `checkpoint` 在写，等它写完再收尾（`patchProbe` 不经 `run()`，不受中止影响）。
5. **收尾兜底**：到点后至多等 `DEADLINE_UNWIND_MS`（拟 20 s）让探针沿 `finally` 退出来。等不到时（探针卡在某个不经 `run()` 的异步上）照样输出、退出，并把本次 doctor 期间 `makeTempDir` 登记过、仍在盘上的目录逐个尝试删除（**只删 mkdtemp 的返回值**，2026-09-20 事故规矩 R1），删不掉的列进输出。为此 `probes/codex.ts:778` 与 `probes/zcode.ts:1590` 两处裸 `fs.mkdtemp` 改走 `makeTempDir`，`makeTempDir` / `tryRemoveTempDir` 维护一份进程级登记（删成功即注销）。

**输出**：`--json` 新增 `deadline` 段（只在给了 `--deadline-s` 时出现）：

```json
"deadline": {
  "limit_s": 480, "hit": true,
  "finished": ["codex"],
  "unfinished": [
    { "only": "claude", "state": "in_progress", "launches": 3,
      "rerun": "trivium doctor --only claude --profile-claude 〈名〉",
      "note": "在时限内没探完，本段已拉起 3 次 CLI，结论未落盘（这几次调用的配额已花）。会话里拉起的厂商 CLI 有过间歇挂满单次探针超时的先例（EV-243），请在终端单独跑上面这条命令。" }
  ],
  "residue": []
}
```

- `launches` 由 `exec.ts` 按树标签计数：`runDoctor` 把每一段包进现成的 `withTreeTag(cliName, …)`（`exec.ts:150`），派生时按标签累加一个计数（新增一个只读的取数函数）。它说的是「拉起过几次 CLI」，不区分其中哪几次真的调了模型——按上界交代配额，文案就这么写。
- `rerun` 是给用户在终端复制的完整命令（含路线旗标、不含 `--deadline-s`）。`note` 的 EV-243 一句**不写 Agent id 或 CLI 名字面量**（`registry-parity` 纪律）：它对哪一家都成立，是「会话里拉起」这件事的先例。
- 人读输出在末尾多一段「本次时限 N 秒，已到点：已探完 …；未探完 …（请在终端单独跑：…）」。

**退出码**：到点（`hit: true`）退新增的 `EXIT.DOCTOR_PARTIAL = 76`（`exit-codes.ts` 登记，与 64 / 69 / 73 / 75 均不冲突），**优先于** blockers 的 69——「没探完」与「探完了有问题」要分得开；已探完各段的 blockers 照样列在输出里。未到点时退出码规则逐字不变（有 blockers 退 69，否则 0）。

### D4 · skill 的自动校准流程（四条命令同一口径）

新增公共片段 `skills-src/partials/preflight/recalibrate.md`，在 `partials/review/body.md` 第 2 步与 `commands/run.contract.md` S0.6 两处以 `{{> preflight/recalibrate}}` 引入，替换「失败则原样转述并停止」那一句。四家载体的渲染产物（`skills/*/SKILL.md`、`skills/dual-critic/entry/*/…`）随构建重生成。正文要点：

1. 预检退 0：照旧。
2. 预检退 69 且 `recalibration.eligible === true`：**不向用户确认**，先发一行文本「预检退 69，以下失败项可由 doctor 重新校准：…；将依次在前台跑 N 次 doctor（每次至多 `deadline_s` 秒），会消耗少量配额」，然后逐条执行 `recalibration.invocations`：
   - 命令为 `TV` 加 `args`（逐个照抄，不改、不增删）；**前台调用**，Bash 工具超时设为该条的 `bash_timeout_ms`；不用后台运行，不拆成发起与等待两步；
   - 每条结束后先发一行播报（家名、退出码、阻断项条数、`deadline.hit` 时点名未探完），再发下一条；
   - 任一条退出码非 0（69 / 76 / 64 / 1，或被工具超时打断）都**继续下一条**——是否真修好由重跑预检判，不由 doctor 的退出码判。
3. 全部跑完后**重跑同一条预检命令一次**（旗标逐字相同）：
   - 通过：照旧往下走（`warnings` 照旧念），并在同一条消息里说明「预检首次退 69，已自动校准后通过」；
   - 仍失败（任何退出码）：**停下**，一并转述三样：第一次预检的失败项、各次 doctor 的结论（退出码、blockers、warnings、`deadline.unfinished` 里的 `rerun` 命令与 `note` 原文）、第二次预检的失败项；有未探完的家时明确请用户在终端跑对应 `rerun`。第二次预检的 `recalibration` 即使 `eligible` 也**不再**自动校准。
4. 退出码不是 69、或 `recalibration` 键缺席、或 `eligible` 为假：照旧原样转述并停止（`why` 一并念出）。

`/dual-run` 只有 S0.6 一次预检，所以一次命令至多一轮自动校准；`/dual-review-*` 同理（第 2 步）。

### D5 · 时限取值：统一取值还是按载体（焦点：四家入口的工具超时上限不一）

**建议统一取值**，由预检在 `invocations` 里给出 `deadline_s = 480`、`bash_timeout_ms = 540000`（= `min(600000, deadline_s×1000 + 60000)`，与 `--wait` 的 `bashTimeoutFor`（`run-protocol.ts:387-389`）同一公式、同一 60 s 余量；实施时把这个函数挪到一个不引入环依赖的位置共用）。理由：

- 注册表与载体配置里**没有**任何一家工具超时上限的实测登记（`skills-src/carriers/*.yaml` 无此键；设计 §2 只登记了 Claude Code 的 120 s / 600 s）。按载体取值就得先登记一份没测过的事实，违反 P7「能力靠探针，不靠记忆」。
- `--wait` 现行就是统一取值、四家同一份 `bash_timeout_ms`，这次沿用同一先例；若某家载体的上限低于 540 s，`--wait` 之外这里会先撞上——那时的形态是工具超时打断 doctor（D3 的到点处置没来得及跑）、子进程过继给 init。这一残余如实记进 BACKLOG，不在本主题里假装解决。
- **480 s 的依据**：全量 doctor 四家约 2～4 分钟（手册 §3.4），单家一般远低于此；单次探针调用上限 180～300 s，一家撞上一次挂满还能留出余量做完其余几臂。取 480 而不是贴着 540，是给 D3 的收尾（宽限约 3.5 s + 至多 20 s 兜底）与进程启动留空。最坏情形：入选三家都要校准且都挂满，总耗时约 3 × 9 分钟；这在开场那一行播报里说清楚。

### D6 · 配额与上限够不够（焦点：doctor 花配额且不再确认）

- **收窄**：只跑失败项点名的那几家、那几条路线（D2）；只在全部失败项都能修时才跑（D1）。
- **上限**：每次命令调用至多一轮（D4）；每家每条路线至多一次 doctor；每次 doctor 至多 `deadline_s` 秒。
- **不做的**：不跨命令记「最近自动校准过」（例如十分钟内同一家不再自动跑）。用户连发同一条命令、每次都卡在同一个修不好但被判为能修的失败上时，会每次各烧一轮。D1 的「拿不准即不能修」是这一条的主防线；跨命令冷却要落盘状态、引入新的过期判据，收益不抵复杂度。作为已知边界写进手册与 BACKLOG。

### D7 · 第三方 claude 路线在会话里挂满（EV-243）撞上时限时怎么转述

不针对 claude 写特判。EV-243 的形态是单次调用挂满 180 s 被探针自己的超时杀掉——那是探针内部的超时，doctor 照样跑完、通常给出「未得出结论」一类 note 或 blocker，重跑预检仍失败，按 D4 第 3 条停下转述，doctor 的 notes 里有原因。若连续几次挂满累计撞上 480 s 总时限，则走 D3：该家记 `unfinished`，`note` 里那句 EV-243 先例与 `rerun` 命令原样转给用户。两种形态都落到「请在终端单独跑」，与今天用户在终端跑能通过的实测一致（记忆 pipeline-known-pitfalls 第 67 条）。
