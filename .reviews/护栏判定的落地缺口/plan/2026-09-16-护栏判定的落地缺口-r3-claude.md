## 2. EV-26：先分类，再处置

### 2.1 四类禁读对象，性质不同

`enumerateDenyPaths()` 的禁读集由四类拼成：

| 类别 | 损害背靠背独立性？ | 本批处置 |
| :--- | :--- | :--- |
| 对端历史审查件与结构化原文（`.reviews/`） | **是** | 判作废（E 的前置，重跑另立） |
| 运行根 `~/.trivium/runs`（对方本轮原始输出） | **是** | 判作废 |
| 编排器状态目录（项目根子树） | 否 | **不判作废**；按 §3 收窄 + 告警级 |
| `sensitive_globs` 命中的凭据文件 | 否 | 安全级告警，另一条处置线 |

**分类信息在 `enumerateDenyPaths` 生成时免费可得，现在只是被 `peerArtifactRead`
一个布尔位塌缩掉了。**

**实证：四次命中全是第三类（误伤）**——r12 两次（codex 措施 b、glm 措施 a）、
r1 一次（glm 全仓检索）、r2 一次（codex `ls -R`）。后两次都是审查员**主动披露**的。
这四个实例共同证明：**要修的是分类处置，不是收窄**（CODEX-06）。

### 2.2 事实更正：项目根子树里没有对端产出

r2 §2.2 写「该子树里真正需要屏蔽的只有对方本轮/历史产出的落点」——**错了**。
`freeze.ts` 的注释自陈：

- 项目根子树：「护栏载体（state.json、lock、bin），审查员**没有读它的正当理由**」
- `~/.trivium/runs/`：「**对方本轮的原始输出就写在这里**」

对端历史产出在 `.reviews/<topic>/<stage>/`，对端本轮输出在运行根。
**项目根那棵子树里一个都没有。**

因此 r2 的 U2（「收过头就是真的漏掉对方产出」）**整条作废**。
真实风险见 §3。

### 2.3 落盘与知情

| 落点 | 改什么 |
| :--- | :--- |
| `guard.ts` | 措施 a 的命中**按类导出**，不再塌缩；`renderGuardWarnings` 按类分流措辞（第三/四类不再说「该侧结论作废」） |
| `review.ts` | `meta.guard` 增 `peer_leak_via_path: { <side>: { hit, category, paths } }`，与既有 `peer_leak_via_command` **同构**（按侧、恒写、`hit:false` 表示「扫过没命中」） |
| `render.ts` | `renderReviewDoc` 增 `peerLeak` 入参；front-matter 记 `peer_leak`；正文头部按类打横幅。**注意现有 `peerDeny` 传的是「路径级 deny 是否生效」，与「是否泄漏」正交，不得混用** |
| **`brief.ts`** | **BRIEF 第 8 段按类分流**——该段现在写着「读取其中任何一个，本次审查即作废」，分类后若不改，就成了「提示语说作废、机器做的是不算」（CODEX-04），且反向制造新盲区：审查员读了第三类会以为自己犯规，实际什么也没发生 |
| `gate.ts` | 作废侧**不进** `findJointRejectedBlockers`（堵反噬漏洞），配套见 §6 |

**知情要求（AGY-04 ≡ CODEX-12）**：r2 写的「要求作废侧那些行的理由带复核依据」
没有可机读判据，会退化成行尾追加「（已复核）」。而且 `gate.ts` **现在并没有**
把裁决表的「来源」列用于跨侧归集（`findJointRejectedBlockers` 按 reviews 的键归集）。

本批改为**两步显式工作**：

1. 先把「来源」列解析进 `rows` 的类型（现在只解析了，没进判定面）；
2. 判据取**结构性**的：要求作废侧的每条意见在裁决表里有对应行，且该行的「落点」列非空
   ——**不检查理由的文字内容**。

若这仍不足以表达「裁决者独立复核过」，就**如实写明这一条只能是人读约束**，
不包装成强约束闸门。宁可承认边界，也不再造第三个假承诺。

## 3. 禁读集：整棵继续禁 + 具名放行

r2 的「收窄」方向被 CODEX-06 指出真实风险：**把该子树从 fail-closed 翻成 fail-open**
——将来任何版本往那里新写一个文件（日志、缓存、轨迹副本），默认就可读，
而没有任何机制会红。这与 `AGENTS.md` 纪律 11（禁止手工枚举禁读矩阵）正面冲突。

**因此方向反过来**：默认整棵继续禁，只开一份**具名放行清单**。

| 落点 | 处置 | 理由 |
| :--- | :--- | :--- |
| `config.yaml` | **放行** | 项目级共享策略，审查员有正当阅读理由 |
| `bin/` 下的 wrapper | **放行** | 无信息价值 |
| `config.local.yaml` | **不放行**（D-5） | **探针结论在这里**（不在 `config.yaml`——init 写盘时显式剥掉 probe 段）。放行则本机绝对路径、各 CLI 入口、provider `base_url` 整份进审查员上下文，而默认 `sensitive_globs` 只挡 `.env`/`.pem`/`.key`/`id_rsa` 形态、挡不住它（CODEX-05）。**更重要的是审查员本就不该需要它**——r12 那次冲突的成因是焦点点名了这个文件，正解是改焦点措辞，不是为一个错误的焦点做制度让步 |
| 状态文件、锁目录、迁移备份 | 继续挡 | 编排器运行态（闸门进度、run_id、会话 id）与迁移备份，无正当阅读理由 |

**机制上按注册表式对账，不留人工白名单**（CODEX-06）：
新增契约测试——「凡代码里写进编排器目录的路径，必须出现在已分类清单中，否则红」。
这让纪律 11 的机制化覆盖这一处。

**登记一条待议**：若将来确实需要让审查员看到探针结论，正解是
**编排器把非敏感字段摘进 BRIEF**，暴露面由代码控制，而不是放开整个文件。

## 6. 共同阻断：排除 + 三态字段（D-4 = 乙）

**问题**（CODEX-02 ≡ GLM-05）：`findJointRejectedBlockers` 的判据是 `critics.size < 2`。
默认双审（N=2）下排除作废侧后**恒剩 1**，函数恒返回空集——
「一检出泄漏，最强的交叉检查当场消失」，而设计 E 允许排除的前提是它**同时重跑补齐侧数**。

**处置**：有效侧 < 2 时落**三态字段**，区分

- 「查过、无共同项」
- 「有效侧不足两家、**该项未做**」
- 「查过、有共同项」

并让它在 `run.json` 与审查文档头部**同时可见**，`renderGuardWarnings` 出一条具名告警
（暂定 `joint_check_degraded`）。**不允许静默空集**——那是三态纪律
（「没测到 ≠ 测出来没有」）在本主题内的第四次复发形态。

**为什么乙成立**：它的隐患是「共同阻断经常失效」，而那取决于排除发生得频不频繁。
四次命中实例**全是第三类误伤**；§2.1 的分类做对之后，排除会变得很少见。
**分类是乙的前提**——若分类被砍掉或推迟，乙不成立，必须回到甲（排除与重跑同批）。

**阈值不变**：N=3 排除一家后仍取 2。阈值 2 的语义是「至少两个互相独立的来源指出同一处」，
与总数无关；三家里的两家仍是两个独立来源（回答 CODEX-02 的追问）。

`gate.ts` 的「双方」措辞按 N 家改写（设计 §6.6 规则 7 同步）。

## 7. `run.v2` 的 `guard` 节点直接收严（D-6）

r2 §6.2 把「是否收严」列为待决，CODEX-08 反对的理由是
「用户机器上别的项目的历史留痕核不了」。**不需要兼容历史版本，这条不成立。**

**本仓库历史留痕已实测**：

```
v2 留痕 28 份
schema 未声明的 guard 键：（无）
```

**零差额**——收严 `additionalProperties: false` 不会打坏任何一份历史归档。

收严比对账测试更强：对账只在测试里查，收严在**每次写盘与读回**都查。
两者都做——收严是硬判据，对账给出更早的失败点与更清楚的报错。

**同批必做**（GLM-07）：`verification_degraded.path` 的枚举扩 `partial`。
不扩则 guard 判出 `partial` 的那侧在 `writeRunMeta` 落盘前被 `validateRunMeta` 拒掉并抛错
——**第一次真实 partial 轮次整份 run.json 写不出来**。
收严之后，这类「忘了同步 schema」会当场炸而不是静默，正是本批要治的病。

## 8. EV-28：三层防线，本批做前两层

| 层 | 做什么 | 能防什么 | 本批 |
| :--- | :--- | :--- | :--- |
| ① 离线用例 | **合成夹具** + 具名盲区清单（照 `known-forms` 的 B-清单式） | **我们自己**重构时改坏提取逻辑 | ✅ |
| ② 运行期覆盖率 | 见下 | **参数改名（工具名不变、tool-trace 族）下一轮可见** | ✅ |
| ③ 探针臂 | `probes/agy.ts` 加 grep 臂，断言该调用能提出路径 | 工具名改名、新增读工具 | ❌ 另排，**给时间表** |

**①的定性写死**：「防我们自己退化的回归用例」，**不声称**能防厂商改名。

**②按 GLM-04 的方案——分母按工具分两档**（三侧里最好的一个）：

- **「必带路径」类**（文件读工具）：提不出路径**即当场红**。这就是改名探测器，近零假阳
- **「可无路径」类**（搜索 / glob / 列目录）：只计数不判——不带目录的搜索是合法形态

**`partial` 的消费方定死**：进 `run.json` + front-matter + 一条告警行，**不改闸门结论**。
不留「按实际覆盖率判定」这种未决措辞。

**三处能力声明收窄**（CODEX-07）：

- 分母本身是厂商事实（读类由工具名白名单认定），**厂商改工具名时分母自己缩小**、
  提取率仍 100%——所以另记「不认识的 tool_name 计数」
- `command-trace` 族（codex）`read_paths` 结构性为空，**第②层对它无信号**，如实写明
- 能力声明改为「**参数改名（工具名不变、tool-trace 族）**下一轮可见」

**键名修复**：`agy-events.ts` 的 `PATH_KEYS` 补 `SearchPath`。
zcode 侧**不改键名**——但结论按证据强度写（CODEX-11）：
`ZCODE_PATH_KEYS` 已含 `path`，M0/M6 探针记录载明其 `input` 含 `file_path`/`path`/`pattern`；
「Grep 只给 pattern」的形态属**设计上有意的缺省**（无路径即无读取事实），
缺失率由第②层计数器兜。**不写成「已解决」**。
