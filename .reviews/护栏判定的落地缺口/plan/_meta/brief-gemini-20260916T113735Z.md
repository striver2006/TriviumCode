## 2. 四条的具体内容

### 2.1 EV-26 · 「该侧结论作废」没有机器实现

**判定是对的。** `checkPeerLeak` 归一绝对路径、目录条目按 `<条目>/` 前缀命中
（那是历史上 GLM-03 修过的）。r12 实测：glm 侧 `read_paths` 26 条，其中含
`.trivium/config.yaml` 与 `.trivium/config.local.yaml`，而 `.trivium` 是它那份
104 条禁读清单里的裸项；把两者喂给生产函数，返回 **`leaked: true`**。

**处置是空的。** `peerArtifactRead` 的全部消费点：

| 落点 | 做了什么 |
| :--- | :--- |
| `review.ts` → `renderGuardWarnings` | 生成一行文字 |
| `meta.ts` | 人读行「⚠️ 读到对方产出」 |
| `report.ts` | 复盘的 `guardFlags` |
| `review.ts` | 落成一个布尔位 |

没有一处影响结论采信、`verdict`、或闸门。「该侧结论作废」这句话写在
`renderGuardWarnings` 返回的字符串里——**它是对人说的话**。

**留痕也是残的。** 措施 b 按侧记（`peer_leak_via_command.<side>.hit` + 命令原文），
措施 a 只有一个**全局 OR** 的布尔位，`peerHits` 一条不进。
于是 r12 里我看得见 codex（措施 b 落了盘）、看不见 glm（措施 a 没落盘），
并据此在裁决件里写下了错误的处置表。

**还有一处**：`renderReviewDoc` 收的 `peerDeny` 参数是 `r.peer_deny_applied`，
即「路径级 deny 有没有启用」，**不是**「有没有泄漏」。审查文档的 front-matter 里
因此没有任何泄漏标记——`side.peerArtifactRead` / `peerHits` / `peerCommandHits`
三个字段在 `verdict.sides[c]` 里躺着，一个都没传进渲染。

### 2.2 EV-28 · 措施 a 对 grep 通道全盲

`adapters/agy-events.ts` 的 `PATH_KEYS` 是

```
['AbsolutePath', 'SearchDirectory', 'DirectoryPath', 'Path', 'File', 'TargetFile']
```

而 `grep_search` 的目录参数叫 **`SearchPath`**（`Query` 是搜索词）。
r12 实测：gemini 的 15 次 `grep_search`（`state` 均为 `DONE`）中，
`extractPath` 取到路径的是 **0 条**，参数值样本是 `…/doc`、`…/src`、`…/test`。

**这条格外要命**，因为 grep 是探针记录里白纸黑字写过的**绕过通道**：

- zcode 侧：「`--disallowed-tools Read(<路径>) …`：模型改用 **Grep** 读到了目标文件」
- claude 侧：「同一批规则（含显式的 Grep 路径规则）下，**Grep 仍从该目录取到了哨兵**」

也就是说，**最可能被用来绕过的那条路，检测面上是空的**。

zcode 侧是否同样丢参数**尚未核实**（本轮它 14 次 `Grep`、`readPaths` 26 条，
未逐条对账）——这是本计划要查的第一件事，见 §5 U1。

### 2.3 EV-29 · 审批后复校把闸门重新关上，两份留痕分叉

`gate --check` 校验通过后按 `run.json` 的 `entry` 分流，B/C/D 一律
`setGateChecked(… 'awaiting_approval')`——**它不看闸门当前是不是已经 `approved`**。

分流本身是有意设计且理由成立（`cli.ts` 注释：「护栏的存续不该取决于执笔者
记不记得走完流程」，防止 Driver 省略 `--await-approval` 让闸门停在 `idle` 被静默旁路）。
问题在缺一个前置判断。

**更实的危害是留痕分叉**：该推进只写 `.trivium/state.json`，不写归档里的 `task.json`。
2026-09-16 实测出现：

```
task.json  : { state: "approved",           since: "09:54:32" }
state.json : { state: "awaiting_approval",  since: "10:42:57" }
```

**同一道闸门，两份留痕给出互相矛盾的答案**，而 `task.json` 才是审批记录的正本
（`approvals[]` 在它里面）。触发路径很常见：审批后按裁决补修复 → 改动涉及裁决件 →
顺手复校一次完整性。撞上之后连提交都做不了（Hook 按 `state.json` 判写锁）。

### 2.4 新条目 · `block_severities` 零消费方

```
src/trivium/types.ts:673      block_severities: Severity[];
src/trivium/config.ts:249     block_severities: ['blocker', 'major'],
```

**声明了一件事，没有任何代码让它成真**。

## 3. 需要你拍板的决策

### D-1（最重要）· 「该侧结论作废」该落地成什么行为？

这是本计划的核心，其余都是技术细节。四个候选：

| 选项 | 行为 | 代价 |
| :--- | :--- | :--- |
| **A · 仅强制知情** | 审查文档头部打作废横幅、front-matter 记 `peer_leak: true` 与命中清单、`run.json` 按侧落盘；裁决仍需逐条，但 `gate --check` 要求裁决件里对该侧有一句明示「本侧结论作废，裁决基于独立复核」 | 作废仍靠人执行，但**漏看变成不可能**。改动面最小 |
| **B · A + 不参与共同阻断** | 在 A 之上，作废侧提的 blocker 不计入 `findJointRejectedBlockers` 的「双方共同」 | 语义正确（作废的结论不该有阻断力），但会**削弱**闸门——一侧作废后，它与另一侧共同提的 blocker 可以被驳回而不报 |
| **C · A + 整轮降级** | 在 A 之上，作废侧按失败侧处置（不产出审查文档，改记 `.failed.json`），整轮进 `degraded` | 干净，但**丢掉已经花了配额的产出**。r12 里 codex 侧八条意见全部有效、我逐条核过并接受了——按 C 它们根本不会落盘 |
| **D · A + 整轮作废** | 该轮直接判失败，要求重跑 | 最严格，也最贵。r12 那轮三侧跑了 898s，重跑一次是实打实的配额 |

**我的建议是 A**，理由：

1. **作废的判断权本就该在裁决者手里**——审查员读了禁读文件，不等于它说的每条都错。
   r12 就是实例：codex 侧被判作废，但它指出的八条我独立复核后**全部成立**。
   C 和 D 会把这些结论一并丢掉。
2. **本轮真正的失败是「我不知道 glm 也命中了」**，不是「我没执行作废」。
   A 直接治这个：命中必落盘、必上横幅、裁决件必须明示。
3. B 的方向是对的，但它**削弱**护栏而不是加强——在没想清楚「作废侧的 blocker
   到底还算不算数」之前，我不想动共同阻断这条线。可以单独列一条待议。

**但这条影响每一轮双审的行为，所以我不自己定。**

### D-2 · `block_severities` 是接线还是删掉？

| 选项 | 说明 |
| :--- | :--- |
| **接线** | 让 `findJointRejectedBlockers` 读它，「共同阻断」的严重度门槛变成可配 |
| **删掉** | 它从来没生效过，删掉比留着一个假承诺诚实；`joint_blocker_policy` 已经能调硬软 |

我**倾向接线**——它的语义清晰且有用（有的项目会想让 major 也阻断），
而删一个已经写进每个项目配置文件的键，迁移成本反而更高。
但接线等于**改变现有行为**（默认值含 `major`，接上之后双方共同的 major 被驳回也会报），
所以要你点头。

### D-3 · EV-29 的修法：加前置判断，还是让两份状态收敛？

| 选项 | 说明 |
| :--- | :--- |
| **窄** | 只加前置判断：闸门已是 `approved` 且 `run_id` 相同时，`--check` 不推进状态 |
| **宽** | 在窄的基础上，让 `--check` 的推进同步写 `task.json`，消掉能分叉的缝 |

我**倾向宽**。窄的改法能解掉我撞上的那个具体场景，但**分叉的可能性还在**——
任何别的路径只写一边，同样的矛盾会再出现一次。不过宽的改法要动
`state.ts` 与 `approval.ts` 的写入边界，风险更高。
