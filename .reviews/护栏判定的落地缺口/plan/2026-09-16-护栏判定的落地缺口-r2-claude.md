# 护栏判定的落地缺口（r2）：先把判据分对类，再谈处置

> **本稿取代 r1。** r1 的三审（`20260916T113735Z`）17 条全部接受、零驳回，
> 项目负责人据此**拒绝**了 r1 并给出三条裁决。r1 与裁决件保留在同目录，不改写。
>
> **r1 错在哪**（三侧独立收敛 + 一条 codex 独家）：
>
> 1. **讨论对象错了**——我用来立论的实例（glm 读了 `.trivium/config.yaml`）
>    根本不属于「读到对方产出」那一类，而我在这个未分类的观测上讨论「作废该有多强」；
> 2. **候选集漏了设计已定的那一项**——§10.1(c) / §12 / AC-04 / AC-25 四处都写着
>    「该侧作废并重跑一次，仍命中标 `failed(peer_leak)`，strict 整次中止」，
>    而我的 A/B/C/D 里没有它，等于把已定口径包装成开放问题；
> 3. **反噬漏洞**——原方案下泄漏侧提的 blocker 仍进 `findJointRejectedBlockers`，
>    等于给一个本应作废的审查员逼停流水线的否决权；
> 4. 两处硬错误：`checkDisposition` 这个函数不存在（是 `checkAdjudication`）、
>    设计 §12 不是闸门状态机（是 §8.4 / §8.6）。

## 2. EV-26：先分类，再处置

### 2.1 根因：四类性质不同的命中被塌缩成一个布尔位

`enumerateDenyPaths()` 的禁读集由四类拼成：

| 类别 | 损害背靠背独立性？ | 应有的处置 |
| :--- | :--- | :--- |
| 对端历史审查件与结构化原文 | **是** | 走 E（设计已定） |
| 运行根 `~/.trivium/runs`（对方本轮原始输出） | **是** | 走 E |
| 编排器状态目录 `.trivium` | 否——读的是自己的护栏配置 | **不判作废**；见 §2.2 收窄 |
| `sensitive_globs` 命中的凭据文件 | 否 | 另一类问题（安全面），单独告警 |

现在四类共用 `peerArtifactRead` 一个布尔位与一句「该侧结论作废」。
**分类信息在 `enumerateDenyPaths` 生成时免费可得，只是被塌缩掉了**（CODEX-02 / GLM-01）。

**实证**：r12 的两次命中（codex 措施 b、glm 措施 a）**都是第三类**，
即两次都是误伤，零次真污染。r1 的整场讨论建立在误伤实例上。

### 2.2 收窄禁读集（AGY-01 ④ 的根因修复）

`.trivium` 现在是**裸目录条目**进禁读集，而 `checkPeerLeak` 对目录条目按
`<条目>/` 前缀命中——于是**任何对该子树的合法查阅都命中**，
包括一次未限定路径的全仓 grep（glm 在 r1 盲区里主动披露过一次）。

该子树里真正需要屏蔽的只有对方本轮/历史产出的落点，
而项目配置、探针结论这些**是审查员本就该能看的**——r12 那次冲突
（焦点要求看配置、禁读集又挡着）正源于此。

**处置**：把该子树从裸目录条目改为**精确到需要屏蔽的那几个落点**，
其余允许读取。同时保留一条兜底：凭据文件仍由 `sensitive_globs` 挡。

### 2.3 落盘与知情（本批的主体）

| 落点 | 改什么 |
| :--- | :--- |
| `guard.ts` | 措施 a 的命中**按 deny 来源分档**导出，不再塌缩；`renderGuardWarnings` 的措辞按分类分流（第三/四类不再说「该侧结论作废」） |
| `review.ts` | `meta.guard` 增 `peer_leak_via_path: { <side>: { hit, category, paths } }`，与既有 `peer_leak_via_command` **同构**（同样按侧、同样恒写、`hit:false` 表示「扫过没命中」） |
| `render.ts` | `renderReviewDoc` 增 `peerLeak` 入参；front-matter 记 `peer_leak`；正文头部按分类打横幅。**注意现有 `peerDeny` 参数传的是 `r.peer_deny_applied`（deny 有没有启用），不是泄漏结论**——两者不能再混用 |
| `gate.ts` | `checkAdjudication` 读 `run.json` 的泄漏标记；对作废侧**按行**要求：裁决表已解析出「来源」列，逐行知道意见来自哪一侧，要求作废侧那些行的理由带复核依据，缺行即失败 |
| `gate.ts` | 作废侧**不进** `findJointRejectedBlockers`——堵掉反噬漏洞（AGY-01 ③） |

**知情要求做成按行的结构性判据，不是正文句子匹配**（GLM-06 ≡ CODEX-04）：
匹配一句话只会退化成「抄模板」，那是本批要修的病的第二次下法。

## 3. EV-28：三层防线，本批做前两层

r1 声称离线对账能「防住厂商改参数名」——**三侧一致指出它不能**，
且那条全称断言在真实轨迹上本就为假（不带目录的搜索是合法形态）。

| 层 | 做什么 | 能防什么 | 本批 |
| :--- | :--- | :--- | :--- |
| ① 离线用例 | **合成夹具** + 具名盲区清单（照 `known-forms` 的 B-清单式） | **我们自己**重构时改坏提取逻辑 | ✅ |
| ② 运行期覆盖率 | 每轮落盘「读类 DONE 调用数 / 其中提不出路径的条数」；`verification.path` 补 `partial` 档 | **厂商改名在下一轮当场可见**，成本是几个计数器 | ✅ |
| ③ 探针臂 | `probes/agy.ts` 加 grep 臂，断言该调用能提出路径 | 参数名属厂商事实，按纪律 1 归探针层 | ❌ 另排 |

**①的定性写死**：它是「防我们自己退化的回归用例」，**不声称**能防厂商改名。

**键名修复**：`agy-events.ts` 的 `PATH_KEYS` 补 `SearchPath`。
**zcode 侧不需要改**——`ZCODE_PATH_KEYS` 已含 `path`，M0/M6 探针报告记载其
`input` 含 `file_path` / `path` / `pattern`（CODEX-06，U1 据此降格为零配额复核）。

## 4. EV-29：窄修，正本认 `task.json`

| 改什么 | 说明 |
| :--- | :--- |
| `--check` 的前置判断 | **直接读 `task.json.approvals[]`**（审批事实的正本），不同时写两份 |
| 「不推进」的条件 | **同 run 的任一终态**（`approved` / `rejected` / `abandoned`），不是只挡 `approved`（GLM-03） |
| `--await-approval` | 终态白名单一并收紧——它是同一缺陷的**第二个入口**，重跑它一样能把已审批闸门打回 |

**不碰写入边界**，因此不涉及 U3 那个未做完的设计。

> 一处事实更正（r1 三审中两侧说法冲突，实测以 codex 为准）：
> `gate --check` **已经**在写 `task.json`（`cli.ts:777` 的 `joint_blocker_rejected`
> 分支置 `disputed`）。所以「同步写」并非全新的写边界——
> 但本批按裁决走窄修，不依赖这一点。

## 5. `block_severities`：删掉 + 防新增对账

**删掉**（D-2）。前提已被推翻：`MANUAL_user.md` 两处与 `LLD_orchestrator.md` 一处
**已明文告诉用户它是死配置**，「用户以为改它有效」不成立；
而接线是对**每个已 init 项目**的默认行为改变（默认值含 `major`）。

**防新增对账**（CODEX-08）：照 `registry-parity` 的手法加一条契约测试——
配置项键集 vs 消费方 grep 集，差额必须逐条落在具名的 `known-dead` 白名单里，
**白名单只许缩短不许变长**。这样第五个、第六个死配置不会再来。

存量（EV-06 `instructionFiles`、EV-15 `readonly_commands`）**另立主题逐条裁**——
EV-15 还顶着设计 §10.1 与 §18.1 #21 两处「把不存在的机制当前提」的论证，
改它要连带改写设计措辞，不是本批能顺带做的。

## 8. 执行顺序（分批落盘，CODEX-09 ≡ GLM-04）

三个已决项不该被未决项按住。建议按此顺序**分两个提交**：

1. **第一批**：`PATH_KEYS` 修复 + EV-29 窄修 + `block_severities` 删除 + 防新增对账
   ——各自闭合、互不重叠、无待决问题
2. **第二批**：分类 + 收窄 + 按侧落盘 + 横幅 + 按行知情 + 不进共同阻断
   ——改动面集中在判定与落盘，U2 的风险在这一批

**本主题不得在计划双审与审批之前动任何业务文件。**
顺序是 `/dual-review-plan` → 逐条裁决 → `/dual-approve` → 实施 → `/dual-review-code` →
裁决 → `/dual-approve` → 提交。四条 skill 的发起权在用户手里。

**审查焦点仍应避开那棵子树**：本主题的被审对象是 `src/trivium/` 下的判定与落盘代码。
