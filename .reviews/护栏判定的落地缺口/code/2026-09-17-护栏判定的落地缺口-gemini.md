**问题**：classifyDenyPath 判定目录条目自身（'.trivium' 或 runRoot）时相对路径为空串，导致目录条目被通通误判为 peer-artifact（作废级）塞进 voidingPaths，完全击穿了「状态目录降为告警级不作废」与「具名放行」的设计。

**依据**：查阅 src/trivium/freeze.ts 第 81-97 行与 src/trivium/guard.ts 第 173-185 行。当 req.deny_paths 包含目录条目 '.trivium' 或 expandHome(cfg.runtime.run_root) 时，path.relative 返回空字符串 ''。在 classifyDenyPath 中，if (triviumRel && ...) 与 if (runRel && ...) 均因空串为 falsy 而跳过分类，最终回落至第 102 行返回 'peer-artifact'。因为 peer-artifact 属 VOIDING_DENY_CATEGORIES，整棵 '.trivium' 和 runRoot 全被判为作废级路径并塞入 voidingPaths。下游 checkPeerLeak 采用前缀匹配，导致审查员只要读取 .trivium/state.json 甚至具名放行的 .trivium/config.yaml，都会匹配 voidingPaths 进而将 peerArtifactRead 判为 true，全案作废。

**建议**：在 classifyDenyPath 中增加对 abs 等于 ctx.triviumDir 或 ctx.runRoot 本身的识别（如 rel === '' 时判为对应分类），且判类应作用在实际命中的叶子读取路径上，同时 checkPeerLeak 必须在比对前过滤具名放行项。

### AGY-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/freeze.ts:88` |
| 类别 | correctness ｜ 层次 code |

**问题**：运行根路径分类取第三段比对侧名，导致位于 runDirBase 顶层的共享运行时材料（request.json、worker.log 等）被全数误判为对端输出，触发错误作废。

**依据**：查阅 src/trivium/freeze.ts 第 88-91 行，运行根判定规则为 seg.length >= 3 && seg[2] === ctx.critic 才判定为 own-run-material。查阅 src/trivium/run-protocol.ts 第 40-45 行及 review.ts 第 536 行，真实运行目录布局为 <runRoot>/<repoId>/<runId>/，其顶层直接存放 request.json、worker.log、worker.pid、status.json。当审查员读取 request.json 时，seg[2] 为 'request.json'，因与 ctx.critic 不等而被误判为 peer-run-output（作废级）。这直接违背了设计 §10.1.1 与 freeze.ts:60 关于「自身 sandbox home、request.json、worker.log 属 ②′ 不判作废」的保证。

**建议**：调整运行根路径判据，不仅比对 seg[2] === ctx.critic，同时将顶层已知的运行时元文件（request.json、worker.log 等）明确归入 own-run-material 或独立非作废类别，仅在第三段明确属于其他入选对端审核者目录时才判定为 peer-run-output。

**问题**：路径核验覆盖率分母排除 grep_search、find_by_name、list_dir，恰恰放过了当初引发 EV-28 的真实退化形态，且 zcode 侧完全未对接该计数。

**依据**：查阅 src/trivium/adapters/agy-events.ts 第 85-88 行及第 213-222 行，AGY_MUST_HAVE_PATH 仅硬编码为 new Set(['view_file'])。但在 agy 工具声明中，grep_search（必须有 SearchPath）、find_by_name（必须有 SearchDirectory）、list_dir（必须有 DirectoryPath）均为必须携带路径参数的只读工具。EV-28 的历史根因正是 15 次 grep_search 因参数名缺失导致提出 0 条路径；若 grep_search 再次发生参数改名退化，因其未在 AGY_MUST_HAVE_PATH 中，total 分母完全不计入，pathVerificationTier 仍会返回 'ok'，使退化探测完全失灵。此外，zcode.ts 根本未采集 path_bearing_reads，导致其在判定中永远恒为 'ok'。

**建议**：将具有必填路径参数的 grep_search、find_by_name、list_dir 纳入覆盖率分母；并在 zcode.ts 适配器中对称采集 path_bearing_reads。

**依据**：查阅 src/trivium/guard.ts 第 223-229 行。在扫非作废类命中时：if (viaPath.leaked || viaCmd.leaked) { notedCategories.push(cat); notedPaths.push(...viaPath.hits); }。当命令文本通道命中非作废路径（例如 cat .env.local，在 codex/command-trace 侧尤为普遍）而路径通道未命中时，viaCmd.leaked 为真，但 notedPaths 仅解构了 viaPath.hits，完全漏掉了 viaCmd.hits。第 289 行构造 typedHits 时，该命中的路径和分类信息全部丢失。

**问题**：jointCheckState 在有效侧仅有单侧结构化结论时，警告文案一律将原因归咎为「排除作废侧」，造成审计诊断信息的归因失实。

**依据**：查阅 src/trivium/gate.ts 第 361-370 行与第 457-461 行。当有效审核者恰好两家且均未被判作废（voidedSides 为空），但其中一家为 parse_fallback 导致 reviews[c] === null 时，effective 计算为 1，jointCheckState 返回 skipped-insufficient-sides。此时 gate.ts 输出的警告信息写死为：「共同阻断这一档未执行：排除作废侧后有效侧只剩 1 家（需要 2 家）」，将「存在解析降级侧（parse_fallback）」与「存在违背独立性而被作废的侧（voided）」混淆。

**建议**：在 jointCheckState 返回结构中明确区分有效侧不足是因为「作废侧排除」还是「存在 parse_fallback 降级侧」，使提示话术与真实场景严格对应。
