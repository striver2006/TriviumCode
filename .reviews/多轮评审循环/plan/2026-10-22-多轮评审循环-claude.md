6. 渲染：front-matter `schema` 写 v2；整份回退侧的 `verdict` 由补 `request-changes` 改为写 **`null`**（v2 起结论要计票，不再伪造）；正文「结论」行 v2 显示「中文档名（英文值）」。

## 三、计票（N2）

新模块 `src/trivium/round-verdict.ts`，全部纯函数：

- `ballotOf(review, voided)`：作废优先 ⇒ `voided`；`null` ⇒ `parse_fallback`；`undefined` ⇒ `missing`；`schema` 不是 v2 ⇒ `legacy_schema`；否则一票。
- `decideOutcome(counts)`：分母 `n` 只收有效票；整数比较 `2k ≥ n`，次序 不通过 → 修改后通过 → 通过 → 兜底修改后通过（D-2）；`n = 0` ⇒ `undetermined`。
- `nextAction(outcome, loop)`：`undetermined` ⇒ `human_review`；通过两档 ⇒ `proceed`；`reject` 且 `round < max_rounds` ⇒ `rerun`，否则 `human_review`。
- **计票只看结构化结论，不看 Driver 的裁决**：裁决决定改什么，结论决定还要不要再审。
- 落点 `review.ts` 收尾（「计票（EV-247）」段，约 :2201）：只对 `meta.review_loop` 存在且 `meta.status === 'success'` 的运行算；
  每侧的选票口径——终判读到对端产物 ⇒ `voided`；`parse_fallback` ⇒ 不计；其余非 `ok`（失败 / 超时）⇒ `failed`；`ok` ⇒ `ballotOf(review)`。
  一行播报 `renderRoundLine`：「第 2/3 轮 · 计票：1 通过 / 0 修改后通过 / 1 不通过（另有 k 侧不计票）→ 不通过 · 下一步：按裁决修改后自动重审」。

## 四、轮次链与上限（N3）

1. **run.v3 补两个可选字段**（不升契约版本）：`review_loop: { round, max_rounds }`（骨架写入）与 `round_verdict: { sides, excluded, counts, outcome, next_action }`（收尾写入）。
   `review_loop` 只在计划与代码阶段、非纯文档跳过轮写；**存在即「本轮按循环规则跑」**，缺席即旧运行 / bug / 跳过轮，闸门完全按旧规则。
2. `review --start --max-rounds <n>`：CLI 入口只校形状与范围（`maxRoundsProblem`，1～10，非纯数字退 64）；阶段适用性与续链一致性在 `prepareRunClaimed` 里、**分配 run_id 之前**判（`review.ts:266 resolveReviewLoop`），拒绝零工件。bug 阶段给了退 64。
3. **续链判定** `deriveReviewLoop(prev, requested)`：上一轮带 `review_loop`、`round_verdict.next_action === 'rerun'`、且**未被人工表态 / 作废**（`closed`）⇒ 续链：`round + 1`、上限沿用链首；
   续链时显式给了**不同**上限 ⇒ 退 64；`round + 1 > max_rounds` ⇒ 退 64（防御：按 `nextAction` 不会出现）。其余情形新起一链：第 1 轮，上限取显式值或缺省 3。
4. **「上一轮」取本阶段最近一次算数的运行**（`review.ts:287 previousRoundFacts`）：run_id 从新到旧，跳过「带 `review_loop`、没有 `round_verdict`、也没被人工表态」的运行——
   失败、超时、取消、作废的那次**不消耗轮次**，重试仍是同一轮，链不被打断、上限不被重置。读不出的 run.json 直接按「没有上一轮」处理（理由：同一份留痕在 `resolveStageDriver` 已判 corrupt 拒跑，走不到这里）。
   `closed` 取 `approval.ts humanDecidedThisRound`（含 approved / rejected / abandoned；task.json 读不出时 fail-closed 判已表态 ⇒ 新链）。
5. `topic resolve` 输出 `max_rounds: { plan, code }`（`topic-args.ts:318 resolveMaxRounds`）：命令 A 收 `--max-rounds-plan` / `--max-rounds-code` 与 `--max-rounds`（同时作用，专属的优先）；
   B / C 只认 `--max-rounds`，写了阶段专属旗标退 64（防「解析成功、随后被丢弃」）；bug 三个都退 64。取值校验与 `--start` 同一个函数。
6. 透出：`--start --json` 恒给 `review_loop`（bug / 跳过轮为 null）；`--wait` / `--status` 在**退出码 0** 时读归档 run.json（`run-protocol.ts readRoundFacts`），给 `review_loop` / `round_verdict` / `next_action` / `round_line`，四键恒在；`gate --check --json` 同。

## 五、闸门去向（N3、N4）

### 5.1 `gate --check` 通过后的分流（`cli.ts:1662`，盖过 entry）

| `next_action` | 闸门去向 | 说明 |
| :--- | :--- | :--- |
| `rerun` | **一律回 idle**（含 B / C） | 中间轮不立人工停点——否则下一轮 `review --start` 的比较-交换会拦下重审 |
| `human_review` | **一律立 `awaiting_approval`**（含 A） | 命令 A 唯一的人工停点；停点话术追加 `HUMAN_REVIEW_REASON` |
| `proceed` | 照旧按 entry：A 回 idle，B / C / D 立停点 | |
| null（无计票） | 照旧按 entry | 旧运行、bug 阶段、骨架之后没跑成 |

「本轮人已表过态就不推进状态」的既有前置不变，排在分流之前。

### 5.2 `--await-approval` 的停点话术

追加 `round_line`；`human_review` 时追加 `HUMAN_REVIEW_REASON`（「通过即按最新一版计划 / 代码继续，拒绝或放弃即停止；要再审一轮，先表态再重新发起」）。

### 5.3 计划阶段每轮必写新一轮完整计划（规则 9 扩展）

`PlanFinalInput.alwaysRequired`（`gate.ts:176`）：本轮 run.json 带 `review_loop` ⇒ 无论有无接受项都要求执笔方的新一轮计划存在；缺了判 `missing_next_plan`（`ids` 为空时文案点名应写的文件名，并要求开头写「本轮无改动」及原因）。逐号引用仍只核接受项。
派生处两个：`loadRoundReviews`（`gate.ts:1477`）与代码阶段复核 `recheckPlanFinal`（`gate.ts:1014`）。不带 `review_loop` 的旧轮次照旧「有接受项才要求」。

## 八、审查重点（用户给定，逐字）

> 重点看三档计票规则与闸门去向是否与需求一致、轮次链续链与失败重试的边界、review.v2 读取侧判据有无遗漏（禁读矩阵与被审对象硬拒）、代码审先改码后校验的次序

执笔方自查时拿不准、请审查员重点核的几处：

1. **`undetermined` 一律 `human_review`，第 1 轮也是**——需求只说「最后一轮仍不通过停下」，没说无有效结论怎么办。执笔方取「没有结论不能当成通过、也不该自动消耗一轮」。
2. **`--allow-single` 下一侧失败**：分母只剩 1，那一侧一票定结论。是否应当另有下限（如有效票 < 入选侧半数即 `human_review`）？本计划未设。
3. **续链的「算数」判据**：跳过的是「带链、无计票、未表态」的运行。作废（终判读到对端产物）的**侧**不影响运行 `status`，整轮照常计票、只把该侧列 `voided`；整轮被作废的运行没有计票，按失败跳过。是否有「有计票、但事后被判漂移 / 篡改」而应当不算数的形态？
4. **读不出的 run.json 直接当「没有上一轮」**：依赖 `resolveStageDriver` 先拒跑。若两者对「读不出」的口径不一致，会静默新起一链、上限重置。
5. **计划阶段 `proceed` 那一轮写的新一轮计划不再送审**：按 D-2「修改后通过 = 无需再审」，它直接成为代码阶段的定稿。
6. **命令 C 最后一轮改码不送审**（D-3）：审批前复核 `verifyRoundForApproval` 只核登记工件、不比对工作树快照，所以先改码不会让审批失败——这正是 D-3 要的，但也意味着最后一轮的改动只有人工审批这一道关。
7. **`isReviewSchemaId` 的覆盖面**：执笔方 grep 过源码里的 `'trivium.review.v1'` 字面，剩余两处见 §九。是否还有**不按字面、而按别的形态**认审查件的读取侧（如 Hook、`checkStageArtifacts`、`report` 的其它分支、按 `verdict` 取值判断的地方）漏改？

## 十、风险与残余

- 全局安装副本是旧构建：提交推送后需重建重装，新 skill 才在本机生效；未重装前用新 skill 调旧编排器，`next_action` 恒为 null，skill 走「照旧」分支，不会卡死。
- 旧运行（无 `review_loop`）的闸门行为逐字不变；新旧混跑同一主题时，新链从第 1 轮起。
- 原始需求文本未单独归档（用户口头给出），以需求说明书 稳需-15 为准。
