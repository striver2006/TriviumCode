6. 渲染：front-matter `schema` 写 v2；整份回退侧的 `verdict` 写 **`null`**（v2 起结论要计票，不再伪造）；正文「结论」行 v2 显示「中文档名（英文值）」。

## 三、计票（N2、D-5）

新模块 `src/trivium/round-verdict.ts`，全部纯函数：

- `ballotOf(review, voided)`：作废优先 ⇒ `voided`；`null` ⇒ `parse_fallback`；`undefined` ⇒ `missing`；`schema` 不是 v2 ⇒ `legacy_schema`；否则一票。
- `decideOutcome(counts, selected)`：分母 `n` 只收有效票；**先判下限（D-5，本版新增）：`2n < selected` ⇒ `undetermined`**（`n = 0` 是它的特例）；
  再按整数比较 `2k ≥ n`，次序 不通过 → 修改后通过 → 通过 → 兜底修改后通过（D-2）。
- `tallyRound(ballots, loop)`：`selected` 取 `ballots` 的键数——收尾处每个入选侧都有一项（有票或不计票原因），即入选侧数。
- `outcomeLabel('undetermined')` 文案由「无有效结论」改为「**有效结论不足**」；`renderRoundLine` 不计票侧非空时写成「（另有 k 侧不计票，由 n/N 侧定论）」。
- `nextAction(outcome, loop)`：`undetermined` ⇒ `human_review`；通过两档 ⇒ `proceed`；`reject` 且 `round < max_rounds` ⇒ `rerun`，否则 `human_review`。
- **计票只看结构化结论，不看 Driver 的裁决**：裁决决定改什么，结论决定还要不要再审。
- 落点 `review.ts` 收尾（「计票（EV-247）」段）：只对 `meta.review_loop` 存在且 `meta.status === 'success'` 的运行算；
  每侧的选票口径——终判读到对端产物 ⇒ `voided`；`parse_fallback` ⇒ 不计；其余非 `ok`（失败 / 超时）⇒ `failed`；`ok` ⇒ `ballotOf(review)`。
- D-5 同步改口径的地方：`HUMAN_REVIEW_REASON`、`skills-src/partials/review/loop.*`、命令 A 契约、`run.v3.json` `round_verdict.outcome` 描述、主设计 8.2.1、需求 稳需-15、BACKLOG EV-247。

## 四、轮次链与上限（N3）

1. **run.v3 补两个可选字段**（不升契约版本）：`review_loop: { round, max_rounds }`（骨架写入）与 `round_verdict: { sides, excluded, counts, outcome, next_action }`（收尾写入）。
   `review_loop` 只在计划与代码阶段、非纯文档跳过轮写；存在即「本轮按循环规则跑」，缺席即旧运行 / bug / 跳过轮，闸门完全按旧规则。
2. `review --start --max-rounds <n>`：CLI 入口只校形状与范围（`maxRoundsProblem`，1～10，非纯数字退 64）；阶段适用性与续链一致性在 `prepareRunClaimed` 里、**分配 run_id 之前**判（`review.ts resolveReviewLoop`），拒绝零工件。bug 阶段给了退 64。
3. **续链判定** `deriveReviewLoop(prev, requested)`：
   - 上一轮带 `review_loop`、`round_verdict.next_action === 'rerun'`、且**未被人工表态 / 作废**（`closed`）⇒ 续链：`round + 1`、上限沿用链首；续链时显式给了不同上限 ⇒ 退 64。
   - **本版新增（代码审 GLM-01）**：上一轮带 `review_loop`、`next_action === 'human_review'`、且未表态 ⇒ **退 64**，文案「上一轮已停在人工审核：用 /dual-approve 审批或作废之后，再决定是否重新起链」。
     原「`round + 1 > max_rounds`」分支按 `nextAction` 的构造不可达，并入这一格（文案共用），保留一行防御。
     理由：「最后一轮仍不通过停下人工审核」原先只靠 `review --start` 对 state.json 的比较-交换把守，而槽位缺失时 `setGateChecked` 放行（跨克隆或本机状态被删）；归档正本里的 `round_verdict` 与审批记录已在手，由它把守。`proceed` 未表态维持新链（不属于轮次链不变量，本机由比较-交换拦）。
   - 其余情形新起一链：第 1 轮，上限取显式值或缺省 3。
4. **「上一轮」取本阶段最近一次算数的运行**（`review.ts previousRoundFacts`）：run_id 从新到旧，跳过两类不消耗轮次的运行——
   - 「带 `review_loop`、没有 `round_verdict`、也没被人工表态」：失败、超时、取消、整轮作废；
   - **本版新增（代码审 GLM-02）**：`skipped: true` 且未表态的纯文档跳过轮。它不写 `review_loop`，原谓词认不出，会被当作上一轮、把链打断、上限重置。
   **读不出的 run.json（本版改，计划审 GLM-02 ≡ 代码审 AGY-01）**：文件在场但 `readRunMeta` 读不出 ⇒ 抛 `EXIT.GATE_BLOCK`，文案点名该 run_id，以 `meta.ts unreadableRunMetaExitAt` 收尾；仍在分配 run_id 之前，零工件。
   原理由「同一份留痕在 `resolveStageDriver` 已判 corrupt」只对比最新可读份更新的坏件成立（`latestRunMeta` 命中第一份可读即返回），夹在失败轮之后的旧坏件会让续链静默新起，是 fail-open 方向。函数注释同步改正。
   `closed` 取 `approval.ts humanDecidedThisRound`（含 approved / rejected / abandoned；task.json 读不出时 fail-closed 判已表态 ⇒ 新链）。
5. `topic resolve` 输出 `max_rounds: { plan, code }`（`topic-args.ts resolveMaxRounds`）：命令 A 收 `--max-rounds-plan` / `--max-rounds-code` 与 `--max-rounds`（同时作用，专属的优先）；
   B / C 只认 `--max-rounds`，写了阶段专属旗标退 64；bug 三个都退 64。取值校验与 `--start` 同一个函数。
6. 透出：`--start --json` 恒给 `review_loop`（bug / 跳过轮为 null）；`--wait` / `--status` 在退出码 0 时读归档 run.json（`run-protocol.ts readRoundFacts`），给 `review_loop` / `round_verdict` / `next_action` / `round_line`，四键恒在；`gate --check --json` 同。
7. **本版新增（计划审 AGY-01）**：`schemas.ts checkAgentIdentities` 补 `round_verdict` 的跨字段约束——`sides` 与 `excluded` 的每个键须是已登记、可当审核者的 Agent id，且在 `critics_selected` 内；同一侧不得同时出现在两处。

## 五、闸门去向（N3、N4）

### 5.1 `gate --check` 通过后的分流（`cli.ts`，盖过 entry）

| `next_action` | 闸门去向 | 说明 |
| :--- | :--- | :--- |
| `rerun` | **一律回 idle**（含 B / C） | 中间轮不立人工停点——否则下一轮 `review --start` 的比较-交换会拦下重审 |
| `human_review` | **一律立 `awaiting_approval`**（含 A） | 命令 A 唯一的人工停点；停点话术追加 `HUMAN_REVIEW_REASON` |
| `proceed` | 照旧按 entry：A 回 idle，B / C / D 立停点 | |
| null（无计票） | 照旧按 entry | 旧运行、bug 阶段、骨架之后没跑成 |

「本轮人已表过态就不推进状态」的既有前置不变，排在分流之前。

### 5.2 `--await-approval` 的停点话术

追加 `round_line`；`human_review` 时追加 `HUMAN_REVIEW_REASON`（「通过即按最新一版计划 / 代码继续，拒绝或放弃即停止；要再审一轮，先表态再重新发起」；D-5 后补一句「有效结论不足时同样停在这里」）。

### 5.3 计划阶段每轮必写新一轮完整计划（规则 9 扩展）

`PlanFinalInput.alwaysRequired`（`gate.ts`）：本轮 run.json 带 `review_loop` ⇒ 无论有无接受项都要求执笔方的新一轮计划存在；缺了判 `missing_next_plan`（`ids` 为空时文案点名应写的文件名，并要求开头写「本轮无改动」及原因）。逐号引用仍只核接受项。
派生处两个：`loadRoundReviews` 与代码阶段复核 `recheckPlanFinal`。不带 `review_loop` 的旧轮次照旧「有接受项才要求」。

## 十、风险与残余

- 全局安装副本是旧构建：提交推送后需重建重装，新 skill 才在本机生效；未重装前用新 skill 调旧编排器，`next_action` 恒为 null，skill 走「照旧」分支，不会卡死。
- 命令 C 放开无约束 `Bash` 后，Bash 侧写入只剩 Hook 的启发式拦截：审查进行中、闸门期的业务写入仍由 Hook 拦，与命令 A 同一护栏面。
- 旧运行（无 `review_loop`）的闸门行为逐字不变；新旧混跑同一主题时，新链从第 1 轮起。
- 原始需求文本未单独归档（用户口头给出），以需求说明书 稳需-15 为准。
