### 2.1 `TraceCapability`：枚举 + 布尔，挂 `CriticAdapter`

```ts
export interface TraceCapability {
  /** 轨迹形态：专用工具带结构化路径，还是 shell 命令 */
  traceShape: 'tool-trace' | 'command-trace';
  /** 被拒的操作是否留痕（false ⇒ 该侧「尝试写」的检测失效） */
  rejectionRecorded: boolean;
}
```

**挂载点**：`CriticAdapter` 上的 `readonly capability: TraceCapability`，**不挂 `CriticResult`**。
r1 §2.3 的理由（它是该侧固有能力，不是单次运行结果；挂结果上允许同一侧两次运行报出不同能力）
之外，r2 的 AGY-04 补了一条决定性的：注册表方案在本步**不可测**——
[critics.ts:128](../../../src/trivium/critics.ts#L128) 在 `criticEnabled=false` 时抛 `EXIT.USAGE`，
而本步不碰 `criticEnabled`，集成测试只能选 gemini/glm，两者恒 `tool-trace`，
桩的 `command-trace` 形态在静态注册表下根本走不到。挂适配器则桩可声明自己的能力。

四家取值：

| Agent | traceShape | rejectionRecorded | 依据 |
| :--- | :--- | :--- | :--- |
| gemini | tool-trace | true | 现状行为等价 |
| glm | tool-trace | true | 现状行为等价 |
| codex | **command-trace** | **false** | M6 P-C1 / P-C2 实测 |
| claude | tool-trace | true | M6 第 3 步 claude 探针实测 |

**`rejectionRecorded` 为什么保留为独立布尔**（沿用 r1 §2.3 的论证，不重新发明）：
它描述的是**沙箱行为**，不是轨迹形态。四个已知样本上它与 `traceShape` 共变，
我拿不出反例——保留它是**按机制归因**而非按数据归因的选择，代价是可能多一个自由度。

**探针对账范围**（r2 GLM-07）：`AgyProbe` / `ZcodeProbe` **没有**对应字段，

### 2.2 `checkEvidence` 的三条口径写死

r1 §2.2 承诺「两条口径写进设计 §11.1」，r2 稿只剩一个函数签名。本稿写死，
并把 `min_project_reads` 的处置从「二选一」落成**确定选择**。

**1. `toolTotal`**：`command-trace` 族计入 `run_command`。

```ts
const toolTotal = cap.traceShape === 'command-trace'
  ? (tc.read ?? 0) + (tc.grep ?? 0) + (tc.glob ?? 0) + (tc.run_command ?? 0)
  : (tc.read ?? 0) + (tc.grep ?? 0) + (tc.glob ?? 0);
```

`ToolCallCounts` 已有 `run_command` 键，是最现成的计数位，不新增字段。

**2. `project_reads`**：从 `command_texts` 提取项目内路径去重计数。四组口径逐一裁定：

| 口径 | 裁定 | 理由 |
| :--- | :--- | :--- |
| 哪些 token 算路径 | 按空白与 shell 元字符切 token；**引号包裹的整体算一个 token**（含空格与中文路径） | 不认引号会把带空格的路径切碎，系统性漏报 |
| 相对路径的 cwd | **与措施 b 同口径**：只认纯回退层级，cwd 不可知时保守不计 | 措施 b 在 [base.ts:533-552](../../../src/trivium/adapters/base.ts#L533-L552) 已定此口径，回填**不得比它宽松**——宽松会让 `project_reads` 虚高，把「读了几个文件」这个证据断言掺水 |
| `HEAD:<path>` 与通配 | `HEAD:<path>` **提取**（EV-01 原文已列为已知形态）；通配 `*` **不展开、不计数** | 通配展开需要文件系统状态，判定层不做 I/O |
| 写命令提到的路径（`echo > f`） | **不计入** `project_reads` | 它是写意图不是读证据；掺进来会让「读了项目文件」这个断言失真 |

**漏报边界如实登记**：变量拼接（`cat $F`）、管道组合、`find -exec` 传递的路径都提不出来。
codex 侧 `project_reads` 因此**系统性偏低**——这是本设计的已知代价，不是缺陷。

**3. `min_project_reads`**：对 `command-trace` 族**单独定阈值**，不沿用结构化轨迹那个数。

取「单独阈值」而非「下限不适用」，理由：后者等于对该族放弃 AC-11 的证据下限，
而提取虽偏低但**不是零**（`read-sentinel.jsonl` 样本里路径就在命令文本中）。
具体阈值在实现时按样本实测定，**并把「该族阈值与两家不同」写进留痕**，
否则事后看到 codex 侧 `project_reads=2` 通过、gemini 侧 `2` 不通过会以为是 bug。

### 2.4 只读失守分档：写事件两档一律判定

**r2 稿在这里写错了逻辑，被判 blocker。** M6 报告 P-C2 断言的是「**被沙箱拒绝的**命令
不产生事件」；P-C1 的样本本身就是 `status:"completed"`、`exit_code:0` 的 `command_execution`——
**成功命令照常留痕**。所以 `rejectionRecorded=false` 的准确语义是「**尝试写**的检测失效」，
不是「轨迹对写事件全盲」。

| rejectionRecorded | readonlyBreach | readonly 档位 |
| :--- | :--- | :--- |
| true | `write_events.length > 0` | ok |
| false | `write_events.length > 0`（**同样成立**） | `write_events` 为空时 `unavailable` |

即：`readonlyBreach` 两档一律由写事件判定——沙箱一旦失守、写命令成功执行，
那是**真阳性**，必须判失守；`unavailable` 只修饰**阴性结论**的可信度：
「没检出写事件」在该侧不足以排除失守。

**连带的归因链必须一并修**（r2 GLM-02 独有的发现）：
[guard.ts:122-123](../../../src/trivium/guard.ts#L122-L123) 的 `fingerprintChangedFiles`
语义是「指纹变化但轨迹无写事件 ⇒ 开发者手改」。对 `readonly` 档位为 `unavailable` 的侧，
这个前提不成立——指纹变化时**不得直接走「开发者手改」分支**，
应标注为**无法归因**并进留痕。否则审查员的失守会被记到开发者头上，方向正好反。
