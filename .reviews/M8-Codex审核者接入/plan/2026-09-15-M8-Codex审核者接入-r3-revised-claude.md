## 1. 逐项处置

### 1.1 §2.2 提取口径重写（AGY-01 ≡ GLM-02，含 GLM-F02/F04 的同一指控）

**先解包子 shell**：codex 的命令形态是 `/bin/zsh -lc '<真实命令>'`。
提取前先剥掉 `/bin/(zsh|bash|sh) -[a-zA-Z]*c` 的外层包裹，对**内层命令**做 token 切分。
不解包则路径一个都提不出——这是本条被判 blocker 的直接原因。

**四组口径改写后**：

| 口径 | 新裁定 | 相对 r3 的变化 |
| :--- | :--- | :--- |
| 引号 | **穿透**：剥掉外层子 shell 包裹后，`'`/`"` 按分隔符处理，与措施 b 的 F-5/F-9 同向 | ← 推翻 r3 的「引号包裹整体算一个 token」 |
| 裸相对路径（`cat src/a.ts`） | **按 projectRoot 归一后计入** | ← 推翻 r3 的「cwd 不可知保守不计」 |
| 逃逸相对路径（`cat ../Other/x.ts`） | 归一后**不在项目根内**，由既有 `isUnder` 过滤自然排除 | 不需要单独规则 |
| `HEAD:<path>` | 提取（不变）；通配 `*` 不展开（不变） | 两侧均确认站得住 |

裸相对计入与 `HEAD:<path>` 按仓库根解析是**同一个假设**（GLM-02 指出的内部不一致就此消解），
也与 `checkEvidence` 对 `read_paths` 既有的 `normalizeAbs` 处理同构。

「只认纯回退层级」这句**从口径里删掉**——它是措施 b 对 F-6 锚定形态的处理，
不是相对路径的总体口径，我引错了适用域。

> **关于 GLM-F04 的「引号整体算 token 站得住」**：该侧在焦点回答里肯定了这条口径，
> 但 AGY-01 用 `read-sentinel.jsonl:4-5` 的真实样本证明它在子 shell 封装下会让提取归零。
> **以 AGY-01 为准**——这是两侧唯一实质分歧，且一侧有样本证据、另一侧无。

§4.2 的用例钉死具体命令形态：`cat src/a.ts`（计入）、`cat ../Other/x.ts`（不计入）、
`/bin/zsh -lc 'head -n 1 src/b.ts'`（解包后计入）各一条。

### 1.2 阈值：给派生机制，不推迟到实现（AGY-03 ≡ GLM-05）

**论据更正**：r3 写「提取虽偏低但不是零（样本里路径就在命令文本中）」——
该样本路径在 `/tmp/codex-probe-*/` 下，按我自己的口径过不了项目内过滤，**它证明不了项目内提取非零**。
真实依据是**设计预期**：BRIEF 给审查员的是绝对路径，codex 模型据此读项目文件，
提取出的就是项目内绝对路径。这个依据写明，不再拿样本充数。

**阈值派生机制**（不推迟）：`command-trace` 族的 `min_project_reads` 由
`TraceCapability` 派生一个折减系数，或在 `CriticRequest` 上显式带该族阈值——
两者择一在实现前定，**不留给实现时拍脑袋**。

**留痕落点补齐**（r3 零落点）：`verification_degraded` 的逐侧对象增第三个键
`evidence_threshold`，记本次该侧实际生效的下限值。
不记的后果是：codex 侧 `project_reads=2` 通过、gemini 侧 `2` 不通过，事后看像 bug。

### 1.4 桩形态三个裁定（GLM-01，GLM-F02 同指）

**(a) 新增注入形态，不做 `baseResult` 全局替换。**
`read:6` 在 `baseResult` 里被 `ok` / `no_project_reads` / `write_breach` / `peer_leak` /
`mutate_file` / `wrong_prefix` 全部模式共享（`stub.ts:132-253` 经 spread 复用）。
全局替换会把既有集成测试与 `doctor --selftest` 的绿路径一并改形，
与 §4.1 刚立的「既有判定结果逐项不变」红线正面冲突。
新增 `command_trace` 注入形态，与 `peer_leak_via_command` 和 `peer_leak` 分列的理由同构——
两条形状要能各自单独触发。

**(b) 「以样本为蓝本」= 借命令形态，不是字面重放。**
r1 裁决的措辞是「蓝本」，r3 我写成了「直接以这两份为数据源」——两者有实质差别。
按字面重放：样本唯一路径在 `/tmp`（项目外，`project_reads=0`）、仅 1 条命令
（`run_command=1 < min_tool_calls=5`），**任何「证据达标」的断言都不可达**。
裁定：**借样本的命令形态**（`/bin/zsh -lc '…'` 封装、路径只在命令文本里），
把路径改写到测试 `projectRoot` 之下，命令条数补足阈值。

**(c) capability 随注入形态变化的机制说明**：`makeStubAdapter` 按构造时 `spec` 定 `capability`。
这与 §2.1「capability 是该侧固有能力」不冲突——**桩适配器就是一个可配置的"侧"**，
每次构造出的是一个不同的侧，不是同一侧两次运行报出不同能力。这句调和写进计划。

### 1.5 写命令判定：裁定判定位（AGY-04 ≡ GLM-03）

GLM-03 的两个反例都成立：命令级分类丢 `grep foo > out.txt` 的真实读取（漏报），
token 级把 `cp a b`、`mv a b`、`tee f`、`sed -i … f` 的目标计成读证据（虚高）。

**裁定：token 级 + 写动词目标位排除**。

1. 输出重定向 `>` / `>>` 右侧紧邻 token 排除；
2. 写动词（`cp` / `mv` / `tee` / `sed -i` / `install`）的**目标位**排除，源位保留；
3. 其余 token 按读取候选处理。

EV-15 的 `readonly_commands` 清单作为读动词白名单的**候选**，但不在本步强绑——
它至今无消费方，本步若采用就给它挣到第一个消费方；若实现时发现覆盖不足，
按上述三条兜底。这一族的误报/漏报边界补进 §2.2 的漏报边界登记，§4.2 各配正负例。

### 1.6 第六处消费方显式裁定（GLM-04）

`command-trace` 侧 `toolTotal` 计入 `run_command` 后非零，`no_trace` 不触发。

同时把「五处」的**论域**写明：指**判定层、受能力化影响**的消费点。

### 1.7 档位定义钉死为能力恒态（GLM-06）
