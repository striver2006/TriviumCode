## 1. 本轮的形状：**我的自查方向对了，方法错了**

**两侧都找到了第四处，而且就在这两个文件里。** GLM-01 把根因说得比我准：

`tool_calls` / `command_texts` 四个**字段名**的消费点，而不是 Agent id。

## 2. 修订内容

### 2.1 §3.1 消费方清单重写（AGY-01 ≡ GLM-01）

原稿列三处，实为**四处**：

| # | 消费方 | 吃什么 | codex 侧现状 |
| :--- | :--- | :--- | :--- |
| ① | `checkEvidence` 的 `toolTotal` | `tool_calls` | 恒 0（见 §2.2） |
| ② | `checkEvidence` 的 `projectReads` | `read_paths` | 恒 0 |
| ③ | `checkPeerLeak` | `read_paths` | 恒空 ⇒ deny 核验失效 |
| ④ | **`judgeSide` 的 consulted 交叉核对** | `read_paths` | **恒空 ⇒ 每轮误报** |
| ⑤ | `judgeSide` 的 `readonlyBreach` | `write_events` | 恒空（P-C2） |

第 ④ 项的后果最刺眼：`consultedUnverified` 会同时触发运行时告警
（`guard.ts:236`）与 front-matter 标记（`render.ts:103`），
而 codex 侧**每一轮**都会命中。这正是 `guard.ts:160-167` 注释点名要防的
「真原因被噪音埋掉」。

**处置**：第 2 步把 consulted 核对纳入泛化面。`command-trace` 族的取值二选一，
在第 2 步的裁决件里定：(a) 从命令文本提取路径回填 `read_paths`，走同一套核对；
(b) 引入「该侧无法核对」第三态，**既不默认放行也不恒报误警**。
**倾向 (a)**——因为 §2.2 的 `project_reads` 无论如何都要做路径提取，
(a) 复用同一份提取结果，(b) 会让同一件事有两套口径。

### 2.2 `checkEvidence` 的口径必须写死（AGY-02 ≡ GLM-02）

GLM-02 指出这口径**M6 已经写过**，在 `types.ts` 的字段注释里：

> `trace_path_structured` ……false 时两者（`project_reads` 统计与禁读核验）都只能走命令文本解析

我在计划里只给 deny 核验设计了命令文本判据，**把 `project_reads` 那一半弄丢了**。
这是 r5 那条教训的第三次复发：**限定/口径必须跟着结论一起搬家**。

**处置**：第 2 步明确两条口径并写进设计 §11.1：

1. **`project_reads`**：从 `command_texts` 提取项目内路径去重计数。
   **提取启发式与漏报边界必须写清**——变量拼接、相对路径、管道组合都提不出来，
   这会让 codex 侧的 `project_reads` **系统性偏低**。
   于是 `min_project_reads` 对该族要么单独定阈值，要么按「下限不适用」处置，
   **不能沿用为两家结构化轨迹定的那个数**。
2. **`toolTotal`**：`command-trace` 族计入 `run_command`。
   这同时回答了 GLM-03——它是 `traceShape` 的第二个消费方。

### 2.3 三个布尔合并为一个枚举 + 一个布尔（AGY-03 ≡ GLM-03）

**焦点一的答案：是过度设计，合并。**

```ts
export interface TraceCapability {
  /** 轨迹形态：专用工具带结构化路径，还是 shell 命令 */
  traceShape: 'tool-trace' | 'command-trace';
  /** 被拒的操作是否留痕（false ⇒ 该侧轨迹核验不可用） */
  rejectionRecorded: boolean;
}
```

`pathStructured` 与 `commandSemantics` 合并进 `traceShape`，消费方有两个
（§2.1 的路径提取、§2.2 的 `toolTotal` 计数）——GLM-03 担心的「无消费方死字段」消解。

**为什么 `rejectionRecorded` 保留为独立布尔，尽管它在已知四家上同样共变**：
它描述的是**沙箱行为**，不是轨迹形态。codex 不记录被拒操作是 P-C2 实测的沙箱特性，
与「读经 shell」没有因果关系——完全可能出现「shell 读 + 记录被拒」的第四家。

> **这是论证，不是实测。** 四个已知样本上它确实共变，我拿不出反例。
> 保留它是**按机制归因**而不是按数据归因的一次选择，代价是可能多一个自由度。
> 写在这里是为了下一轮有人质疑时能看见理由，而不是看见一个既成事实。

**挂载点**（AGY-03 的第二问）：挂在 **`CriticAdapter`** 上（`readonly capability: TraceCapability`），
不挂 `CriticResult`。理由：它是**该侧的固有能力**，不是单次运行的结果；
挂结果上会让每次运行都要重填一遍，且允许同一侧两次运行报出不同能力。

### 2.4 降级留痕钉成契约（AGY-04 ≡ GLM-04）
