## 0. 由来：M8 不是「照着 zcode 再抄一个适配器」

M6 实测推翻了这个预期。**codex 与既有两家的差异不在参数，在能力形状**：

| | agy | zcode | **codex** |
| :--- | :--- | :--- | :--- |
| 读文件 | 专用工具 + 独立路径字段 | 专用工具 + 独立路径字段 | **跑 shell，路径只在命令文本里** |
| `run_command` 出现在轨迹里 | **= 失守**（白名单里就没有它） | 恒为 0（`Bash` 全禁） | **= 正常读取** |
| 被拒的写操作 | 留痕 | 留痕 | **完全不进事件流** |
| 路径级 deny | 不支持 | 不支持 | 不支持 |

第二行是关键：`judgeSide` 现在写死 `readonlyBreach = write_events.length > 0`，
而 `AGY_WRITE_TOOLS` 把 `run_command` 算作写事件。**照搬到 codex 上，它每读一个文件就判一次失守。**

所以 M8 的第一件事不是写适配器，是**让适配层契约能表达「读即命令」这一族**。
这也正是 §24.1 里 `11.1 适配层契约泛化` 一直挂在 M8 名下的原因——
那条登记写的是「⏳ 未并入」，M6 之前没人知道它具体要泛化什么，现在知道了。

**这一条请审查者与用户一并确认**，我不擅自换成更便宜的家族——AC-20 的措辞是
「两个模型家族」，换成同源的两个就是偷偷放宽验收口径。

## 3. 结构性设计：适配层契约怎么泛化（§11.1）

这是本轮的主要设计工作，也是最该被审的部分。

### 3.1 缺口

`CriticResult` 现在这样表达证据：

```ts
read_paths: string[];    // 轨迹里的读取路径
write_events: string[];  // 非空即 readonly_breach
```

三个消费方都假定「路径是结构化拿到的」：
`checkEvidence`（`project_reads` 下限）、`checkPeerLeak`（deny 核验）、
`judgeSide`（`write_events.length > 0` ⇒ 失守）。

codex 三条全不成立。

### 3.2 提议：加一个**能力声明**，而不是在消费方里按 id 分叉

```ts
/** 该侧轨迹能提供什么证据——由探针结论决定，不由 Agent id 决定 */
export interface TraceCapability {
  /** 读取路径是否有结构化字段（codex: false） */
  pathStructured: boolean;
  /** 被拒的操作是否留痕（codex: false ⇒ 轨迹核验对该侧无效） */
  rejectionRecorded: boolean;
  /** run_command 的语义：写类工具，还是这一族的读取手段 */
  commandSemantics: 'write-tool' | 'read-mechanism';
}
```

`CriticResult` 相应增一个字段：

```ts
/** 轨迹里出现过的命令原文（措施 b 的输入；无 run_command 能力的侧为空数组） */
command_texts: string[];
```

**为什么不在 `judgeSide` 里写 `if (critic === 'codex')`**：那是纪律 7 明令禁止的
（Agent id 字面量只许出现在注册表与厂商适配器里），而且 M9 的 claude 又是另一种组合
（`pathStructured: true` + `rejectionRecorded: true`），按 id 分叉会分出三支。
能力声明让消费方**只面对能力**，加第四家时消费方零改动——这正是 FR-31 的承诺。

### 3.3 `readonly_breach` 对 codex 要如实降级，不能假装成立

P-C2 实测：被沙箱拒绝的命令**一条事件都不产生**。所以对 codex：

- `rejectionRecorded: false` ⇒ **轨迹核验这一半失效**，`readonly_breach` 不得由轨迹判定；
- 指纹比对（`tree_hash` + `git status`）**仍然有效**，真写了文件照样发现。

**必须在 `run.json` 与审查文档里留痕**「该侧的只读保障只剩两重」，
而不是让它看起来和另两家一样绿。这是三态纪律在能力面上的同一条：
**「没测到」不等于「测出来没有」。**

### 3.4 措施 b 的判据形态

对每条命令原文做 deny 字面量子串匹配，含 `HEAD:<path>` 等写法变体（EV-01 原文）。

**威胁模型按 §10.1 末段的定调**：目标是「泄漏必检 + 成本抬升」，
**不是**抵御蓄意规避。变量拼接、不带文件名的目录级 `git log -p` 检测不到——
这条边界已登记为 R25，本轮**不扩大承诺**。

## 4. 四步拆分

每步一个「实现 → 双审 → 裁决 → 审批 → 修复 → 提交」闭环。

### 第 1 步 · EV-01 措施 b 落地（J1）

- `CriticResult` 增 `command_texts`；两家既有适配器填空数组（zcode 恒无、agy 有即失守）；
- `adapters/base.ts` 增 `checkPeerLeakViaCommand(commandTexts, denyPaths)`；
- `guard.ts` 的 `judgeSide` 接线，命中与路径命中**同等处置**；
- `run.v2` 的 `guard.peer_leak_via_command` 由「可选 · 未排期」翻为已实现并写入；
- **负例锁死五类形态**（RV-B1 的教训：fail-open 的攻击面穷举不完，
  所以这里只承诺「已知形态必检」，不承诺完备）。

**验收**：故意构造命中命令的桩轨迹 → 该侧作废；两家既有侧行为零变化。

### 第 2 步 · 适配层契约泛化（§3 的设计，J7 的一半）

- `TraceCapability` 落地，三个消费方改为只看能力；
- `judgeSide` 的 `readonlyBreach` 按 `rejectionRecorded` 分档并留痕；
- `stub-agent-kit` 的桩 Agent 增一个「读即命令」形态的变体，
  **让第 2 步的泛化本身有机器判据**，而不是等 codex 接上才知道对不对。

**验收**：既有两家的判定结果逐项不变（回归）；桩的新形态走通。

### 第 3 步 · codex 接入（②③④⑥⑦ 五件 + J8 + J2）

- `adapters/codex.ts`：命令行**一律由探针结论构造**（P7），不抄设计里的示例；
- 探针补 `providers_ok`：对 `config.toml` 的 `model_providers` 逐家族探活，
  不在场的**给可粘贴样例，不代写**（纪律 5，§18.1 #2 已拍板）；
- 隔离按 J2 **双覆盖**（`CODEX_HOME` + `HOME`）——M6 第 4 步三条臂的结论；
- 镜头 `codex` 键、`config.v2` 的 oneOf 分支、`profiles.<档位>.codex`；
- 注册表 `criticEnabled` 翻 true（**放在最后**：翻早了 `realAdapters()` 当场失败）。

**验收**：`doctor --only codex` 有确定结论；`--critics codex,glm` 能选上且预检过。

### 第 4 步 · 真机验收与收口（J3～J6、J9）

- AC-20：`qwen` 与 `deepseek` 各一次真实代码审，核对 `model_effective` 互可区分；
- 沙箱负对照（J5）：写文件必须失败；
- J6：`profile` 请求值入档、生效模型以回读为准——**两者不一致时以回读为准并留痕**；
- 密钥扫描增补（J9）：codex 的 `auth.json` 与 `config.toml` 凭据形态加进扫描器正则
  （**只存正则不存值**，同 M0 对 `ZCODE_API_KEY` 的处理）；
- 回填：§16.1 M8 行状态、§24.1 的 `11.1` 与 `9.3` 两行、AC-20 状态、主设计升次版本。

## 5. 测试计划

沿用 M6 确立的三层，但**第 3 层这次真的要花配额**：

| 层 | 测什么 | 手法 |
| :--- | :--- | :--- |

改回坏实现要当场红。本项目已四次出现「绿测试证明不了任何事」，这一条不省。

### 5.1 一处已知的测试缺口，提前说

第 1 步的五类负例锁的是**已知形态**。`RV-B1` 的教训是 shell 的攻击面穷举不完——
所以这里的承诺是「**已知形态必检**」，不是「不可绕过」。
这个边界要同时写进测试注释与 §10.1 的措施 b 条目，**不能只写在计划里**
（本主题 r1 的教训：免责声明写在别处等于没写；r5 的教训：限定必须跟着结论一起搬家）。

## 6. 请审查者重点看

1. **§3.2 的能力声明是不是过度设计**——三个布尔能不能合并成一个枚举？
   或者反过来：`commandSemantics` 与 `pathStructured` 是否其实是同一件事的两面？
2. **§3.3 的降级留痕够不够**——「只剩两重」写在 `run.json` 与文档 front-matter，
   会不会重蹈 `peer_deny_applied` 的覆辙（字段有了、但没人读、用户看不见）？
3. **第 2 步先泛化再接入，还是先接入再泛化**？我选前者，理由是后者会让
   「泛化对不对」只能靠 codex 一个样本判断；但代价是第 2 步的桩形态可能与真 codex 有出入。
4. **AC-20 的家族选择（§2.3）**——`qwen` + `deepseek` 是否成立，
   以及「换成同源的两个就是偷偷放宽口径」这个判断对不对。

## 8. 一处自查

本计划 §3 的设计**没有经过实测验证**——`TraceCapability` 这三个字段是我从
M6 的实测事实**推导**出来的，不是测出来的。具体说：`pathStructured` 与
`rejectionRecorded` 有 M6 的直接实测支撑（P-C1 / P-C2），
而**「三个消费方只看能力就够了」这句话没有**——它依赖「没有第四种依赖 id 的地方」，
而我只 grep 了 `guard.ts` 与 `adapters/base.ts` 两个文件。

**第 2 步开工前要先把这个 grep 做全**（全仓找按 `critic` / `AgentId` 分叉的消费点），
结果写进第 2 步的裁决件。若发现第四处，§3.2 的方案要重估，**不是顺手加个分支**。
