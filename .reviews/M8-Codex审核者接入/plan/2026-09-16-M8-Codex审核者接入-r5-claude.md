## 2. 开工前实测（本次新做，2026-09-16）

方法与 r4 §2 相同：**先真机、后落笔**。本次花掉的配额是两次 `echo ok` 级最小调用
（合计输入 ≈ 3.8 万 token、输出 31 token）与一次 `doctor --only codex` 重探。

### E-1 ·【阻断】`model_effective` **证明不了家族**，`-p` 与 `-m` 可以各说各话

AC-20 的原文是「两次运行的生效模型均与指定一致且**互可区分**」。
我原本打算就按 `model_effective` 两值不同来判。**这个判据不成立。**

实跑（profile 与模型故意错配）：

```sh
codex exec -p qwen -m deepseek-v4-pro -s read-only --json --skip-git-repo-check -C . -
# → exit=0，模型正常应答
```

回读会话文件首行的 `session_meta`：

```text
model_provider = qwen
base_instructions.provenance.model = deepseek-v4-pro
```

**codex 不校验模型与 provider 的对应关系**：`-m` 的值原样进请求、`-p` 决定走哪家的
endpoint 与凭据，两者矛盾时不报错。于是「两次 `model_effective` 不同」这件事，
既可能是真的跑了两个家族，也可能是**同一个 endpoint 被喂了两个模型名**——
后者下 AC-20 会通过，而它验收的那个能力（多模型家族接入）一点没被证明。

对照组（同一时段，profile 与模型匹配）：

```sh
codex exec -p deepseek -m deepseek-v4-pro …
# → model_provider = deepseek，model = deepseek-v4-pro
```

两次的 `model_provider` 不同，**这才是家族的事实**。

**更要紧的是**：`parseCodexSessionMeta` 已经把 `model_provider` 解析出来了
（`codex-trace.ts:190`，字段叫 `modelProvider`，注释写着「provider 家族——随 `-p` 走」），
但 `buildCodexResult` 只取了 `meta.modelEffective`，**`modelProvider` 在返回对象里没有落点，
整个仓库除解析处外零引用**（`grep -rn modelProvider src/trivium/` 只有 `codex-trace.ts` 自己）。
采了、丢了。

> 这条与第 3 步那个 `2>&1` 缺陷同形：**字段存在 ≠ 有人读它**。
> 上一轮是「注释宣称的行为没有用例断言」，这一轮是「解析出来的事实没有消费方」。
> 区别在于：上一轮是双审替我查出来的，这一轮是真机实测查出来的——
> 而如果我按原计划只比模型名，双审也未必查得出，因为代码本身自洽。

**处置**：`model_provider` 进结果契约与运行元数据，J3 的判据改成
「**`model_provider` 互不相同**，且各自与请求的 profile 家族一致」。详见 §3.1。

### E-2 · `profile` 请求值当前**无写入方**，J6 现在没法验

`run.v2` schema 里有 `profile` 字段，但描述写的是「厂商侧 profile 名。**【待实施 · M11】**」，
与 `effort_requested` / `effort_effective` / `tier_source` 并列——
这是 v1.0.0 定稿时「注 1 分期字段」的安排：四个字段 schema 可选、M7b 不写入、M11 接线。

而 AC-20 的 J6 **直接点名要它**：「Given 指定了厂商 profile，Then 请求值如实入档」。
分期安排把它排到 M11，AC-20 却排在 M8——两处规范对同一个字段给了不同的时点。

**处置**：本步只接这一个字段，另三个仍留 M11；**且接线时改名 `vendor_profile`**——
`profile` 这个名字在本系统里已有第二个含义，D4-2 已裁定不占它。

### E-3 · 家族切换**没有单次覆盖入口**，只能改配置

`agents.codex.profile` 是**配置级**字段（`config.v2` 的 `openai` 分支），
没有对应的命令行旗标。而 `review --start --profile <名称>` 是**档位**（`config.yaml` 的 `profiles`），
与厂商 profile 同名不同物——档位表里只有模型 slug，装不下厂商 profile。

于是 AC-20 要的「分别指定两家族各发起一次审查」，在当前实现下是：
**改一次配置、跑一次、改回来、再跑一次**。

这不算缺陷（M8 的承诺面是「接得上」，不是「切得方便」），但它是 FR-27 的一处
真实可用性欠账，本步要如实登记而不是顺手加旗标。处置见 §3.3 与 D4-3。

### E-4 ·【阻断】**模型目录是逐 profile 一份的，而预检比对的是错的那一份**

本机有五份目录文件（`~/.codex/models-{qwen,deepseek,glm,gpt,cowork}.json`），
由各层配置的 `model_catalog_json` 指定：

| 层 | `model_catalog_json` | 内含 slug |
| :--- | :--- | :--- |
| 基底 `config.toml` | `models-qwen.json` | qwen 五个 + `glm-5.2` + **`deepseek-v4-pro`** + **`deepseek-v4-flash-0731`** + 两个隐藏项，共 10 |
| `deepseek.config.toml`（`-p deepseek` 时叠加） | `models-deepseek.json` | `deepseek-flash`、`deepseek-v4-pro` + 两个隐藏项，共 4 |

而探针把这两层**各取一半**记了下来（`probes/codex.ts`）：

- `probe.models`（预检真正比对的那个列表）来自 `probeCodexModels(bin, null)`
  ——**第二个参数是 `null`**，于是走基底配置，拿到的是 **qwen 的 10 条**；
- `probe.model_catalog_path` 来自 `readCatalogPath(probeProfile)`，探针用的 profile 是 deepseek
  ——记下的是 **`models-deepseek.json`**。

**两个字段来自不同的层，并排躺在同一段里。** 我起初就是被这一对误导，
在本文初稿里写成「目录 10 条、里面没有 `deepseek-flash`」——
那 10 条根本不是 `models-deepseek.json` 的内容。

**而目录不是展示面，是强制面。** 实跑 `-p deepseek -m qwen3.8-max`：

```text
exit=1
turn.failed: The supported API model names are deepseek-flash, deepseek-v4-pro,
             but you passed qwen3.8-max.
```

**provider 端点自己拦**，报错还把该家族的合法名单列了出来——与
`models-deepseek.json` 的可见项逐字一致。

于是 `checkModelAgainstCatalog` 在 codex 侧**两个方向都是错的**：

| 配置 | 预检 | 真跑 | 性质 |
| :--- | :--- | :--- | :--- |
| `profile: deepseek` + `deepseek-flash`（**该 profile 自己的默认模型**） | **拒**（不在 qwen 的 10 条里） | 本可成功 | **误杀** |
| `profile: deepseek` + `deepseek-v4-flash-0731` | **放行**（在 qwen 的 10 条里） | **必败**（不在 deepseek 端点名单里） | **误放** |
| `profile: deepseek` + `deepseek-v4-pro` | 放行 | 成功（E-1 对照组实测） | 恰好两边都在 |

第三行是**巧合**：`deepseek-v4-pro` 同时出现在两份目录里，这也是我第一次试跑
碰巧成功、差点把这个缺陷带过去的原因。

**对本步的直接后果**：第二个家族**只能用 `deepseek-v4-pro`**——
它是唯一既过得了预检、又跑得通端点的 slug。D4-1 因此从「选哪个模型」
变成了「这个缺陷本步修不修」。

> 误放那一行值得单记：它的代价不是跑出错结果，是**跑到一半才失败**。
> 失败点在 `turn.failed`，此时隔离副本已备好、BRIEF 已渲染、进程已拉起。
> 预检存在的全部理由就是把这类失败挡在花钱之前（AC-16「预检失败即中止，失败零工件」），
> 而这一侧的预检现在放的正是它该拦的那一类。

### E-5 · 设计文档的现状断言**已经失实**，而且不是本步造成的

主设计文档头「实现状态基线」现在写着：

## 3. 设计要点

### 3.1 `model_provider` 进契约（E-1 的落点）

三处改动，都很小：

1. `CriticResult` 增 `model_provider: string | null`。
   放结果契约而不是 codex 专属结构：M9 的 claude、M11 的档位都要回答「这次实际走了哪家」，
   而 `tool-trace` 族填 `null` 是**能说明理由的空**（同 `read_paths` 对 codex 的处理）。
2. `buildCodexResult` 把 `meta.modelProvider` 填进去。
3. `run.v2` schema 增同名可选字段，写侧照填。

**判据改写**：AC-20 的「互可区分」在验收脚本与报告里一律按
`(model_provider, model_effective)` **二元组**判，不看单值。
这句话要同时落到 §15.3 的 AC-20 行与验收报告里——
r4 的教训是「限定必须跟着结论一起搬家」，只改一处等于没改。

**为什么不顺手加「模型与 profile 家族一致性校验」到预检**：
判不了。模型目录是**一份合并清单**（本机 10 条里 qwen / glm / deepseek / gpt 四家混在一起），
没有「哪个 slug 属于哪家」的结构化事实；按 slug 前缀猜家族，正是 `config.v2` schema
注释里明写「会随目录命名漂移」而否掉的做法。
**能做的只有事后如实记录**，这也是 E-1 处置定在「入档」而非「拦截」的原因。
该限制登记进 BACKLOG，附本次错配实测的原始回读值。

### 3.2 `vendor_profile` 请求值入档（E-2 的落点，命名见 D4-2）

值取 `codexConfig(ctx).profile`（**请求值**，不是回读值），与 `model_provider`（**回读值**）
并排入档。两者一致是常态，不一致说明 profile 分层文件里的 `model_provider` 被改过——
那正是 AC-20 末句「生效模型仍以回读为准、不采信 profile 意图」要防的形态。

**两个字段是一对，名字要让人看出来**：`vendor_profile`（请求）／`model_provider`（回读）。
配置侧的键仍叫 `agents.codex.profile`，不改——它在 `agents.codex.*` 之下上下文自明，
且 `profile` 正是 codex 自己的词；改的只是留痕里那个平铺记录的字段名。

**不改 `model_effective_source` 的三态语义**：回读到记 `trace`、回读不到记 `unverified`，
`profile` 不参与这个判定。第 3 步为此专门抽了 `buildCodexResult` 并补了变异锁例，
本步不得让请求值从任何路径渗回生效值。

### 3.3 家族切换的操作口径（E-3 的落点）

**用 `config.local.yaml` 覆盖，不改进 Git 的 `config.yaml`**：

- 该文件的头部注释明写「其它字段可覆盖 `config.yaml` 中的任意配置项」，是受支持的用法；
- 它不进 Git，切换与还原不产生仓库 diff，也就不会被误当成本步的业务改动；
- **但 `doctor` 会重写这个文件**（`probe:` 段回填）。切换期间不得跑 `doctor`，
  跑了要立刻复核覆盖键是否还在。这条写进验收步骤，不靠记性。

两次运行的配置差异**逐字进验收报告**（改了哪个键、从什么改成什么、运行 id 是多少）。
AC-20 的可复现性全靠这段记录——运行元数据里只有结果，没有「当时配置长什么样」。

**不加 `--profile-codex` 旗标**：厂商 profile 是 R-6 的落点，
而 R-6 的完整形态（逐审核者模型 + 思考等级 + 三档组合）属 M11。
本步加半截旗标，M11 要么推翻要么带着兼容包袱——这与第 3 步「schema 宁可比示例窄」
是同一条取舍。欠账登记，不抢跑。

### 3.4 沙箱负对照怎么做（J5）

**不复用探针那次**。`doctor --only codex` 的负对照结论（「`-s read-only` 下写入被拒，
`breach.txt` 未创建」）跑在**宿主机 `CODEX_HOME`** 上，而真实审查跑在
`prepareCodexHome()` 产出的**裁剪副本**上。副本改了什么会不会把沙箱放宽——
裁剪白名单里没有 `sandbox_*` 键，**推理上**不会，但 AC-20 要的是负对照，不是推理。

做法：一次性脚本走**与真实审查同一条路径**（`prepareCodexHome` + `invokeCodex`，
直接调生产函数，不另写一份参数构造），prompt 要求在项目内建一个哨兵文件，断言：

1. 哨兵文件不存在；
2. `write_events` 为空——**注意这条是弱证据**：P-C2 已实测被拒的命令不进事件流，
   所以空也可能是「试过但被拒」。真正的阳性证据是第 1 条；
3. 运行前后 `tree_hash` 与 `git status` 不变（指纹那一重）。

**第 2 条为什么还要记**：它验的是第 2 步那条更正后的口径——
「成功执行的写命令照常留痕，所以 `write_events` 非空仍是真阳性」。
负对照下它应为空，若非空则说明写**成功**了，那是比哨兵文件更早的失守信号。

脚本落在 `scripts/` 下并在报告里贴出完整输出。**它不进 `npm test`**：
要真跑 codex、要花配额，混进单测会让 CI 语义崩掉（本项目对「假覆盖」的一贯处置）。

### 3.5 `project_reads` 与折减系数（J4 + T9）

生效下限 = `effectiveMinProjectReads(3, command-trace)` = `ceil(3/2)` = **2**。

`base.ts:259` 的注释自己写着「依据是设计预期，不是实测……系数值**待第 3 步真实 codex 轨迹回标**」。
第 3 步没跑真审查，这笔回标顺延到本步。

回标的诚实口径：**两次运行是 n=2**。
若两次的真实 `project_reads` 都远高于 2（比如 ≥ 6），那说明折减过度、可以调回；
若落在 2～3，现值合理；若低于 2，说明提取口径漏得比预期多。
**但无论哪种，n=2 都不足以标定一个阈值**——所以 T9 允许的结论包含
「样本不足以回标，保留现值并把两次读数记进注释」。
这条是刻意写宽的：`base.ts` 那段注释的自我更正（「那是编的」）就是拿 n=1 当依据的后果。

### D4-1 · E-4 的模型目录缺陷，本步修还是记 —— 【已裁定：C】

模型选哪个已经没得选了：`deepseek-v4-pro` 是唯一既过预检又跑得通端点的 slug（E-4 表第三行）。
要定的是**缺陷怎么处置**。

| 选项 | 做什么 | 代价 | 风险 |
| :--- | :--- | :--- | :--- |
| **A 修** | 探针改为逐 profile 采目录（`probeCodexModels(bin, readCatalogPath(name))` 按 profile 存一份），预检按 `agents.codex.profile` 取对应那份比对 | 探针结构改动（`CodexProbe.models` 由一个列表变成逐 profile 的 map），牵动 `config.local.yaml` 形状与既有用例 | 本步范围明显变大；改动落在**所有侧共用**的 `checkModelAgainstCatalog` 上 |

**提议 C**。理由：A 的正确性最好但它把一个**通用机制**的重构塞进真机验收步，
与本步「产出是事实、不是代码」的定位冲突；B 的问题是 AC-20 的措辞里就有

验收条自己要求预检在这一面上是可信的，拿一个误放的预检去过它，属于自证。

通用判据留在预检单点。它拦的是「你配的模型这个家族根本不供」，
与现有那条「profile 不存在 / 没凭据」是同一族拦截。

**但 C 有个诚实的缺口要说清**：它只对 codex 侧成立，
`checkModelAgainstCatalog` 的通用缺陷（比对的列表可能不是生效的那份）还在，
只是 codex 侧被前面那道拦截兜住了。这笔账要如实登记，不能因为「这一侧不疼了」就当它没了。

### D4-2 · `profile` 字段：接线时点 **＋ 字段叫什么** —— 【已裁定：接 + 改名 `vendor_profile`】

> 本条经项目负责人指出后重写。原稿只把它当「AC-20 要它 vs 分期表排它到 M11」的**时点冲突**，
> 漏了更要紧的一层：**「profile」这个词在本系统里已经有两个意思**，
> 而本步正要给它在留痕契约里钉一个。时点让步是一次性的，名字钉下去是长期的。

#### 第一问（时点）：接，理由不变

AC-20 的 J6 直接点名要它、排在 M8；分期表（§6.7.1 表末行）把它与
`effort_requested` / `effort_effective` / `tier_source` 打包排到 M11。两者必有一方让步，
而让 AC-20 空着比让分期表松一格代价大。**只接这一个，另三个不动。**

#### 第二问（命名）：这才是真问题

「profile」在本系统里指两件事，而且**已经在同一个文件里同时出现**：

| 含义 | 落点 | 取值样例 |
| :--- | :--- | :--- |
| **档位**（本项目自己的概念：一张逐阶段逐 Agent 的模型表） | `config.v2` 的 `profiles` / `active_profile`；CLI `review --profile <名称>` | `default` / `flash` |
| **厂商 profile**（codex 的 `-p`，即 `$CODEX_HOME/<name>.config.toml` 分层） | `config.v2` 的 `agents.codex.profile`；本步要接的 `run.v2` 字段 | `qwen` / `deepseek` |

`config.v2.json` 里 `profiles`、`active_profile`、`profile` **三个键并存、前两个是档位、第三个是厂商**。
这不是本步造成的，是已发生的事实（E-3 记了它的 CLI 那一半，但当时我当成可用性欠账，不是命名缺陷）。

**一个为本条辩护的事实**：`run.v2` **自己的**词汇表里，档位叫 `tier`——
已有的 `tier_source`、以及 AC-23 规划的 `--tier-<id>` 旗标都用这个词。
所以在 `run.v2` 内部，`profile` 归厂商**不当场制造歧义**。

**但跨文件读者要吃两次亏**：`run.json` 里 `critics.codex.profile = "deepseek"`
与 `config.yaml` 里 `active_profile: default` 是两回事；而用户敲 `--profile` 换的那个东西，
**恰恰不是** `run.json` 里叫 `profile` 的那个。

#### 决定性事实：改名的窗口现在是免费的，写下去就不是了

实测扫了 **54 份历史 `run.json`（`~/.trivium/runs/**` + 归档 `_meta/`），
`"profile"` 命中 0 份**——与 §6.7.1 的「schema 已留位而写侧尚未接线，
落盘的 run.json 里恒不出现」一致。

**没有任何历史留痕带着这个名字**，所以现在改名的兼容成本是零。
本步一旦按现名写进去，它就成了要双读兼容的历史契约（本项目对历史工件的立场是
「按写入时的规范解读」，不改旧留痕）。

#### 提议：接，但改名 `vendor_profile`

| | 方案 | 代价 |
| :--- | :--- | :--- |
| A | 按现名 `profile` 接 | 零改动，但把跨文件同名不同义**固化进留痕契约** |
| **B** | 改名 `vendor_profile` 后接，`profile` 这个名字**留空不占** | 改 schema 一处 + 设计 §6.7.1 表一行；零兼容成本 |
| C | 不接，留到 M11 连命名一起设计 | J6 空着，AC-20 不完整 |

**选 B**，三条理由：

1. **零成本窗口只有现在**；
2. **E-1 让这个字段马上会有个邻居**——`model_provider`（**回读值**）。
   `vendor_profile`（请求值）+ `model_provider`（回读值）并排，一眼看出是一对，
   而这一对的关系正是 AC-20 末句要验的（「请求值如实入档，生效仍以回读为准」）；
   叫 `profile` + `model_provider`，它俩看起来毫无关系；
3. **不占 `profile` 这个名字，M11 就仍有自由**：档位在 CLI 上现在就叫 `--profile`，
   M11 收口时若想让留痕与 CLI 对齐，`profile` 得是空的才行。

**不改 `agents.codex.profile`**（配置侧那个）：它在 `agents.codex.*` 之下，
上下文自明，且 `profile` 正是 codex 自己的词；而 `run.json.critics.<id>.*` 是一张平铺记录，
没有这层上下文。**改名只改缺上下文的那一处，不做全局改词**——
后者要动已生效的配置契约与迁移，代价与收益不成比例。
