## 2. 逐条处置

### 2.1 GLM-01 + AGY-02 —— 扩实现，不是补一条盲区

**这一条的处置方向本身要说清楚。** GLM 给了两条路：(1) 扩实现把锚定形态收进来；
(2) 作为 B-5 写进盲区表配负断言。

**选 (1)。** 理由不是「能做就做」，而是**威胁模型不允许选 (2)**：
§10.1 末段的定调是「防**非对抗穿透**」，而 `cat ../<rel>` 是 agent 在子目录工作时
**最自然**的写法——它不是规避，是日常。把它记成盲区，等于把承诺面缩到实现的形状上，
方向反了。

> B-1～B-4 能当盲区，是因为它们各自需要一个**刻意**动作（拆开拼接、用 glob、编码）。
> `../` 不需要。这条线就是「非对抗 / 对抗」的分界，也是我当初该用来划盲区的判据。

**做法**（按 GLM 的建议 (1)）：`boundaryOk` 左边界遇到 `/` 或 `.` 时不直接判假，
而是回扫包含命中位置的**整个路径 token**，`normalizeAbs` 归一后判断它是否等于 deny 条目
或落在其下。

**两条既有误报防线必须保住**（GLM 在意见里点名了，我核过它们确实靠左边界排除 `/`）：
- `cat /Users/other/repo/<rel>`（他库同名文件）——归一后不在 projectRoot 内，仍判否；
- `~/.trivium/…` 命中项目内 `.trivium` 条目——归一后是 HOME 下的路径，不等于项目内条目。

**AGY-02 并进这里**：归一走同一条路径后，`/private` 的正反两向自然一致，
不需要再单独补前缀拼写。

**新增用例**：`../`、`$VAR/`、内嵌 `..` 三组正断言 + 上面两条误报负断言。

### 2.2 AGY-03 ≡ GLM-02 —— HOME 下的 deny 条目补 `~` / `$HOME`

**严重度按 EV-01 的原文算要更高**：BACKLOG EV-01 写着措施 b 是
「**通道②与③在检测侧的唯一覆盖**」。通道③就是运行目录 `~/.trivium/runs/`——
对端**本轮**产出实时写在那里。`~` 写法漏检，等于通道③在命令侧根本没接上。

**落点**：`spellingsOf` 对位于 `os.homedir()` 之下的条目追加 `~<后缀>` 与 `$HOME<后缀>` 两种拼写。

### 2.3 AGY-01 ≡ GLM-04 —— `.mutbak` 混入

属实。两份备份是我变异脚本 `copyFileSync(m.file, bak)` 留下的，
`restore` 只还原不删除，于是留在工作树里、被 `git diff` 扫进送审补丁。

**GLM-04 指出的那一半更要紧**：`base.ts.mutbak` 存的是**修 `/private` 归一之前**的
缺陷版 `spellingsOf`。真进了仓，读者会看到两份实现、其中一份是已知错的。

**落点三处**，不只是删文件：
1. 删除两份 `.mutbak`；
2. `.gitignore` 加 `*.mutbak`；
3. **变异脚本改为仓外落盘**（备份写进 scratchpad，不在工作树里落）——
   前两条治的是这一次，第三条治的是下一次。

### 2.4 AGY-04 + AGY-05 —— 边界字符集

- `{` / `}` 进 `CMD_BOUNDARY`（brace expansion）；
- `@` 一并加（`curl -d @<file>` 一类）；
- 右边界豁免从 `after !== nodePath.sep` 改为 `after !== '/' && after !== nodePath.sep`。

AGY-05 的 Windows 场景**不是现行缺陷**（本项目只跑 macOS，glm 也按越界处理）。
收它是因为改动是一个字符且零风险：**git 对象语法与 shell 路径分隔符恒为 `/`**，
与宿主 `sep` 无关——这条独立于 Windows 也成立。

### 2.5 GLM-05 —— 我的注释宣称了不存在的保障

**本轮最该记的一条，且它是本项目的老毛病**。

我在 `base.ts` 文档块写的是：

> 改清单必须同时改用例，否则 `known-forms` 那条守卫会红。

而 `known-forms` 用例里的 `forms` 是**测试文件内的本地字面量**——它既不读 `base.ts`
的文档块，也不读设计 §10.1。**文档里的清单长出 F-6，它什么都不会红。**
它防的是「实现退化」，不防「清单漂移」，而我写的是后者。

> **这与设计 v1.3.6 记过的那条同形**：「注释宣称了扫 `enum / const`、实现只有 `enum`
> ——**注释宣称了不存在的覆盖，比单纯漏做更糟**」。
> 那次的教训我当时写进了变更记录，这次自己又犯一遍，而且犯在**同一个动作**上：
> 写下保证时没去核实保证是否存在。

**落点**：仿 `registry-parity` 的 grep 级对账做成真守卫——解析 `base.ts` 文档块里
F 表与 B 表的行标识，与 `peer-leak-command.test.ts` 的 `[F-n]` / `[B-n]` 用例名
**双向相等**（少一个多一个都红）。做不成就把那句话删掉，**不能留着**。

GLM 提的 zcode 侧同族问题（「若哪天放开 `Bash` 要跟着改」也是纯注释约定）一并处理：
改为由探针结论派生的断言——`probe.cli.zcode.readonly_flags` 仍含 `Bash` 禁用时才允许恒空。

### 2.6 GLM-03 —— B-2 一窄一宽，通道②「已收口」过头

实测确认两头都不准：

- **窄**：B-2 写「目录级 git 读取检测不到」，但 deny **目录条目自身**
  （`.trivium`、run root）经 F-4 是命中的（`git log -p -- .trivium` 实测命中）。
  真正残留的是「deny **文件**条目的**祖先目录**」。
- **宽**：残留盲区比 B-2 的例子宽得多——裸 `git log -p`（无 pathspec）与根递归
  `grep -rn . ` 都是「不指名 deny 路径的内容转储」，两者都在 `readonly_commands` 白名单内、
  且 `.reviews/` 进 Git，**HEAD 历史里就有对端产物**。

**落点**：
1. B-2 泛化为「**未指名 deny 路径的内容转储**：`git log -p`（含无 pathspec 与祖先目录形态）、
   根递归 `grep`/`rg`、`cat` 通配」，并注明「deny 目录条目自身已被 F-4 覆盖」；
2. R25 的措辞同步（它现在限定「不带对方文件名的目录级 `git log -p`」，同样偏窄）；
3. §10.1 通道表②的「**已收口**」改为「**F-3 字面形态已收口**」——
   GLM 说得对，速读者会得出通道②已封死的结论，而那正是我在 §17.2 的 AC 注记里
   自己警告过的误读。

**一处不在本轮决定的**：是否把裸 `git log -p` / 根递归 `grep` 挡在 `readonly_commands`
白名单外。那是 §10.1 自己指出的旋钮，代价是 bug 阶段排查能力受损，
属**取舍**而非缺陷修复，**登记待议、本轮不动**——本轮只把承诺面的话说全。

### 2.7 GLM-06 —— 跨侧合并字段

两条都属实：
1. `commands` 用 `flatMap` 合并两侧，**没有归因**；
2. 更要紧的是 `judgeRun` 会跳过 timeout/failed 侧，那一侧的 `command_texts`
   **从未被扫描**——此时 `hit:false` 的含义是「没扫」，
   而我自己在 `types.ts` 与 schema 里写的三态是「`hit:false` = 扫过、没命中」。
   **我用一个字段表达了两件事，正是这轮我自己在反对的塌缩。**

**落点**：改为 `Partial<Record<CriticId, { hit: boolean; commands: string[] }>>`，
与 `run.v2` 把双侧字段改逐审核者 map 的既定原则对齐（M8 马上要引入第三家，
现在不改，第三家来了要再改一次）。schema 与 `types.ts` 的三态注释同步。

### 2.8 AGY-06 —— F-5 改名

`cat \.reviews/…` 实测漏检，而 F-5 叫「引号/**转义**包裹」——名字承诺了没做的事。

**落点**：F-5 改为「**引号/命令替换包裹（双引号、单引号、反引号）**」，
反斜杠转义**显式归入 B-4**，三处（`base.ts` 文档块、设计 §10.1、用例名）同步。

## 4. 一条要带走的

这轮 12 条里，**有 9 条指向同一个动作缺陷：我把「我以为的」当成了「测过的」。**

- F-1～F-5 的闭集：我按想象划，没跑过 `../` 这种最常见的写法；
- `/private` 归一：上一轮刚被故障注入逼出来一次单向问题，我修了正向、**没想到反向**；
- `~` 写法：EV-01 白纸黑字写着措施 b 是通道③的唯一覆盖，我却没试过 `~/.trivium/runs`；
- `known-forms` 守卫：我写下「它会红」的时候，**没有去验证它会不会红**。

上一轮我记的教训是「盲区写成断言才会红在错误认知上」——这轮证明那句话只对了一半：
**断言只能红在你想到要写的地方。** `../` 我根本没想到，所以没有断言，所以不红。

所以补一条可执行的：**划闭集之前，先把「这一族里最常见的三种写法」逐个跑一遍**，
而不是先写清单再挑例子去填。前者是测量，后者是自我确认——而本项目已经在后者上
栽了太多次。

> 另记一处流程观察：本轮 glm 侧产出带了一条 guard 告警
> 「evidence 引用但未列入 consulted」（`zcode.ts`、`peer-leak-command.test.ts`）。
> 那是审查员自身的结构问题、不影响意见质量，**但它说明 `consulted` 交叉核对是活的**
> ——而修订计划 §2.1 刚把这条判据列为 codex 侧必须泛化的第四处消费方。
> 一个反向的佐证：它在两家结构化轨迹上确实在工作。
