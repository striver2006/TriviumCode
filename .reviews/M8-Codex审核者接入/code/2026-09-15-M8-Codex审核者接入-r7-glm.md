### GLM-02 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/adapters/base.ts:379-401` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：焦点一问「分段正则对嵌套引号内的分隔符是否安全」的答案：只对**含空格**的引号段安全。不含空格的引号段在 dequoted 阶段被剥掉引号、内容原样保留（` ${inner} `），其内部的 `;` `|` `&&` `(` `)` 随后成为**活分隔符**把命令错切。可复现反例 `grep '};' src/a.ts`（搜行尾 `};` 是代码审查的自然动作）：引号对 inner=`};` 无空白 → 保留 → 按 `;` 切段得 [`grep  }`, `  src/a.ts`] → 第二段唯一 token `src/a.ts` 落在动词位被 skip.add(0) 无条件跳过 → 提取结果为空，真实读取整条丢失。同族：`rg 'foo|' f.ts`、`$(< a.ts)`（`(` 切段 + `<` 切 token 后 a.ts 独占一段成动词）。这不是本轮引入（r6 的全局引号替换同样漏），但本轮重写正是收口时机，且文档块宣称引号穿透已与措施 b「同向」——实际 F-5 的穿透不产生这种错切。

**依据**：base.ts:390-392（replace 无空格分支原样保留 inner）、base.ts:395（split(/\|\||&&|[|;()]/)）、base.ts:327-329（动词位无条件 skip）；对 `grep '};' src/a.ts` 逐字符走查：输出为空数组；对照 guard-capability.test.ts 的 r6 反例锁例（`cat "my notes/a.ts"` 含空格分支）证实含空格分支安全、无空格分支无任何用例。

**建议**：无空格分支若 inner 含段分隔符（`;&|()`）也整段丢弃——与含空格同判「宁可漏报」，一并防住假分段与路径落动词位两种后果；补 `grep '};' src/a.ts` 的负断言锁住。
