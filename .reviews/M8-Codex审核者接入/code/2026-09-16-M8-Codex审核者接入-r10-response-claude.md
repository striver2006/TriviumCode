## 1. GLM-01：我改了解释、没改规定

这条值得单记，因为它的成因不是疏忽，是**顺序**。

时间线是这样的：

1. 按 r6 审查建议（CODEX-01）写 AC-20 的正对照判据 → 落进 **PRD 第 20 条**与**设计 §15.3**；
2. 去做沙箱对照实验 → **实测把那条建议打穿了**（`-s read-only` 下整个文件系统只读，
   「允许写的路径 B」根本不存在）；
3. 换成更好的正对照（写命令进轨迹 + 输出显示被拒），
   并更正了 **§3.6**、**M6 报告 P-C2**、**v1.3.11 台账**、**脚本**；
4. **没有回到第 1 步落的那两处。**

第 3 步那四处是**解释性**的（说明为什么这么判），第 1 步那两处是**规定性**的（验收执行者照着跑）。
我更新了前者、漏了后者——而两者冲突时，照字面执行的人拿到的是**恒不可满足**的判据。

这与本项目反复记的「同一份唯一实现依据存两个答案」（EV-14）同形，
但这次直接长在**验收条款**上，比长在散文里严重一档。

**据此补一条方法教训**（见 §4）。

## 2. CODEX-01：我把「没测到」又一次做成了「测出来没有」

三种情形合流成同一个 `[]`，消费方把它读成「确认没有目录」。而这正是**三态纪律**在本项目里被写过无数遍的那一条：
**「没测到」不等于「测出来没有」**。

更难看的是两处：

- `why` 的文案替那个未知**编了一个具体原因**（「该机可能未配置 `model_catalog_json`」）——
  数据支撑不了它，用户会去查一个可能并不存在的问题；
- **我的用例把这一格断言成了「确认没有」**（`test/unit/codex-adapter.test.ts` 那条
  「表在而本 profile 渲染不出目录 → 空清单（无法校验）」），于是守卫不但没守住，
  还把错误语义**锁死**了。

## 4. 本轮的方法教训

r5 记的是「提了问题不等于看过答案」，r6 记的是「一组断言要先验它们共用的前提」。本轮再加一条：

> **当实测推翻了一条你已经写进规范的判据时，先列出这条判据的全部落点，
> 再逐个改——而且要按「规定性 / 解释性」分开列。**
> 解释性文字（为什么这么判）改起来顺手，因为它就在你刚写更正的那一段附近；
> 规定性条款（照着跑的验收条）往往在另一份文档的另一章，**离你当时的注意力最远，
> 而它才是别人真正会照着执行的那一份**。
> 判据的落点清单，不能靠「我记得改过哪几处」。
