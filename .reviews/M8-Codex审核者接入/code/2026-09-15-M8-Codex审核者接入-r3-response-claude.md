## 2. 逐条处置

### 2.1 AGY-01 + GLM-04 —— `~` 的三种形态要分清

**这一条最该记，因为它是我自己在焦点里写错的。**

本轮焦点第二问，我写的是：

> `expandTilde` 只处理 `~/`、**`~user/` 归入保守命中**，这个边界对不对

**而 `~user/` 根本不归保守命中**——r2 我把 `~` 从 `UNRESOLVABLE` 移出去的那一刻，
`~user/` 就既不触发保守分支、又展开不了、又过不了 `prefixIsOnlyDotHops`，
于是**静默判否**。我拿一个不存在的行为去问审查员「这个边界对不对」。

> 这是**第四次**同形：r1 的 `known-forms` 守卫、r1 的 `readonly_commands` 旋钮、
> r2 应答件的误报防线、**本轮的焦点文本**。
> 前三次写在注释/设计/应答里，这次写进了**送审的焦点**——
> 也就是说我用它污染了审查员的前提。幸好 AGY 去读了代码而不是信我。

**三种形态分开处置**：

| 形态 | 处置 | 理由 |
| :--- | :--- | :--- |
| `~` / `~/…` | **精确展开**后走归一 | `os.homedir()` 是静态已知事实 |
| `~user/…`（他人家目录） | **保守命中** | 解析不了 `user` 指向谁；而通道③是 F-7 的唯一覆盖，宁可误报 |
| `~<自己登录名>/…` | 由上一行覆盖 | GLM-04 建议另派生一条拼写，但**保守命中已经把它包住**，不必再加第二条路径 |

**落点**：`expandTilde` 对「`~` 开头但非 `~` / `~/`」返回一个哨兵，
`hitsAt` 见哨兵即判命中；补 `~user/` 与 `~<登录名>/` 两条正断言。

**引号切分（`"$HOME"/…`）不在本条解决**——见 §2.4 的 B-6。

### 2.2 AGY-03 ≡ GLM-02 —— F-6 锚定只认 `/`

`before === '.'` 当初是为了让 `./<rel>` 走 F-6。但 GLM-02 指出关键事实：

> **现有全部 F-6 真阳性的 deny 拼写前都是 `/`**，`.` 分支没有可失去的真阳性。

核实属实——`./<rel>` 的匹配点在 `.` 之后的 `/` 后面（`./` 是两个字符），
所以 `./<rel>` 走的本来就是 `/` 分支。`.` 分支纯粹是多余的，而它引入了误报。

**落点**：F-6 入口改为只认 `before === '/'`；补 `cat ..env`、`cat n/...env` 两条负断言。

### 2.4 GLM-03 —— 注释的全称断言不成立，登记 B-5

我在 `prefixIsOnlyDotHops` 的注释里写：

> `../OtherProject/<rel>` 中间夹了实体目录段，它从**任何**树内 cwd 都到不了本项目的 deny 条目

**实测证伪**：cwd 在 `src/trivium`（两层）时，`cat ../../../proj/.env` 归一后正是 `<root>/.env`。

**处置按 GLM 的建议 (1)**：注释改准，并把这族**登记为 B-5**（与 B-1～B-4 并列，
`known-forms-parity` 随之纳管）。

对整个 token 归一再判，等于把「cwd = 项目根」换成另一组同样无据的假设——
一层 `../proj/<rel>` 侥幸命中、三层不命中，这种「深度决定检出」的行为比明确的盲区更坏。
