### 2.1 AGY-01 ≡ GLM-03 —— 逃树兜底收窄，注释重写

**先认一处更难看的**：那段注释写的是

> 只要归一后**仍在项目树内**、或者它逐字包含 deny 的项目相对拼写，就算命中。

而代码是 `!asIfFromRoot.startsWith(root) ? true : false`——**跑出树才命中**。
注释与实现**完全相反**。这是本主题第三次「注释宣称了代码没做的事」
（r1 GLM-05 的 `known-forms`、r1 我自己的 `readonly_commands` 旋钮、本条）。

**收窄按 GLM-03 的建议 (1)**（与 AGY-01 的建议实质相同，GLM 的表述更精确）：
逃树兜底加前置条件——deny 拼写必须是 token 的**路径尾段**，
且拼写之前的段**仅由 `..` / `.` 组成**。

| token | 收窄后 | 说明 |
| :--- | :--- | :--- |
| `../<rel>` | 命中 | 纯回退层级，子目录 cwd 的自然写法 |
| `sub/../../<rel>` | 命中 | 同上 |
| `../OtherProject/<rel>` | **判否** | 中间有实体目录段 |
| `../.env` | **判否** | 同上（`.env` 前无 `..` 之外的段，但归一后是**上级目录的** `.env`，不是项目内那个——见下） |

> **`../.env` 这一条我要说清楚**，因为它看着像反例：deny 条目是 `<root>/.env`，
> 而 `../.env` 从项目根归一是 `<parent>/.env`。按新规则它的前置段只有 `..`，
> 会落进「纯回退层级」……**但它的层级数超过了到项目根的距离**。
> 所以判据不能只看「段是否全为 `..`」，还要看**回退后是否仍能落在 deny 上**：
> 从某个子目录出发时 `../<rel>` 才等于 deny，而 `../.env` 需要 cwd 在项目根的子目录、
> 且 `<rel>` 恰好是 `.env`——那正是 `cat ../.env` 在 `sub/` 下的真实语义，**应当命中**。
> 真正该判否的是**中间夹了实体目录段**的那类。
> **本条的实现与用例以「前置段仅由 `..`/`.` 组成」为准**，`../.env` 保留命中——
> 它与 `../OtherProject/.env` 的区别就是那个实体段。

**新增用例**：三条误报负断言 + `sub/../../<rel>` 正断言。

**焦点四我站 glm 这边，并说明为什么驳回 gemini 的归组建议**（AGY-05 其余部分已接受）：

gemini 说「按正交维度归组（路径派生层 / shell 包裹层 / git 对象层）」。
这个分类本身是对的，但**它解决不了它要解决的问题**：形态会不会无限增长，
取决于 shell 语法的组合面，与编号是扁平还是分层无关。分层后同样会出现
「路径派生层第 7 种」。而分层的代价是实打实的——**对账正则要跟着分层改**，
而那正是 AGY-05 自己担心的脆弱点。

真正让「12 行」不成为负担的是 **glm 指出的那件事**：三处三种角色
（设计 = 对外承诺面、docblock = 对内、用例名 = 可执行断言）+ 机器对账，
使「改一处漏两处」必红。行数增长不产生连锁修改，**这才是纪律 12 要的形态**。

glm 另指出真正的风险是「**同 id 内的语义漂移**」——比如有人把 F-4 的范围悄悄改宽，
编号没动，对账不红。这条我认，**登记 EV-17**，不在本轮解决
（要判它得比较语义而非编号，与 EV-14 同族）。
