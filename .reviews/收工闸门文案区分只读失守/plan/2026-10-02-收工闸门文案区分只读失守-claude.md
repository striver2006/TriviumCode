## 0. 范围与不做

**做**：`hooks.ts` 里收工 Hook（`hookStop`）的拦截文案、阻断上限放行文案，提交 Hook（`hookPreCommit`）的闸门段文案，在「该闸门这一轮的运行留痕记录了只读失守」时换成说出真因与出口的另一套；其余情形逐字不变。设计 Hook 职责表两行按实补一句；BACKLOG EV-98 改部分结案。

**不做**（决策一）：

- 不改任何判据：写判据（`unwrapSubshell` / `classifyWriteCommands`，EV-98 判据部分）、`readonly_breach` 的判定、`checkAdjudication` 的失败码与顺序一概不动；
- 不改闸门状态机：`gate --check` 只在全部通过时把状态推离 `review_done_awaiting_disposition`，失守时停在原地，**两处 Hook 照旧拦**，退出码、`decision: block`、阻断计数一概不变——变的只有给人看的文字；
- 不给 `GateEntry` 加字段，不改 `gate --check` / `--await-approval` / `approve` 自己的输出；
- 不区分 `missing_review_json`（决策三，实际表现见 §1.4）；
- 不改会话开始 Hook（`hookSessionStart`）的待办注入句（见 §1.5，D2 待议）。

## 1. 现状（`364ef0f`，已核）

### 1.1 两处 Hook 只看闸门状态

- `hookPreCommit`（`hooks.ts:1265`）：`listOpenGates` 后按 `state === 'review_done_awaiting_disposition'` 过滤（:1278，**不按会话过滤**，AGY-05），非空即退 2，文案三行（:1284～1286）：
  「以下阶段的审查意见尚未逐条裁决，提交被拦下：〈列表〉」「请先补齐裁决件并通过 `trivium gate --stage <阶段> --check`。」「如需关闭该拦截，可在 .trivium/config.yaml 设 gate.block_commit: false。」
  该段先于留痕完整性段（`checkArchiveIntegrity`，:1299）返回。
- `hookStop`（`hooks.ts:1424`）：同一状态过滤，再按会话过滤（:1429～1435）；取 `pending[0]` 记阻断计数（:1438～1443）。超限时退 0 并带 `systemMessage`（:1447～1451）：「已连续 N 次阻断收工仍未完成裁决，本次放行以避免死循环。」「〈主题/阶段〉 的裁决仍未齐备，请手工处理。」；未超限时退 2，`reason`（:1459～1463）「还有未逐条裁决的审查意见：〈列表〉。」+「请读完两份审查文档全文，按 trivium.disposition.v1 写出裁决件……再运行 `trivium gate --stage 〈pending[0] 的阶段〉 --check`。」，`stderr` 为第一句（:1465）。

### 1.2 只读失守时闸门停在原地

- `review.ts:1858` / :1872：运行 `status === 'success'` 就置 `review_done_awaiting_disposition`，**不看** `guard.readonly_breach`——失守轮也是 success。
- `gate.ts:347`：`readonlyBreach.hit` 时推 failure `readonly_breach`，处置文案（:368～376）要求先核 `snapshot.drift` 与工作区、说明 drift=false 不足以判误报、列调用记录（至多 8 条）。
- `cli.ts:1538～1574`（entry A 与无 entry）：`result.ok` 才放行回 `idle`；entry B/C/D 那一支（:1510 起）同样以 `result.ok` 为前提推到 `awaiting_approval`。失守 ⇒ `ok: false` ⇒ 状态停在原地 ⇒ 两处 Hook 继续按「未裁决」拦。
- 出口只有两条：`abandon`（状态离开开放集，两处 Hook 都放行）或重跑（新一轮置 `running` 再置 `review_done_awaiting_disposition`，`run_id` 换新，新一轮干净则 `--check` 可过）。EV-79 代码双审 r2 走的是前者。

### 1.3 早退：裁决件缺失时 `gate --check` 看不到失守那一条

`checkAdjudication` 找不到本轮裁决件即以 `missing_disposition` **早退**（`gate.ts:215`），走不到 :347。`fault-injection.test.ts:450` 与 `mcp-detect.test.ts:50` 的注释已记下这个顺序。所以「先运行 `gate --check` 看调用记录」**只在裁决件已落盘时成立**——决策二的出口句若照写，Driver 在还没写裁决件时照做会只看到缺件那一条。本计划因此让 Hook **自己**列出调用记录（§2.3），`gate --check` 只作为处置判据的权威出处引用。

### 1.4 `missing_review_json` 在两处 Hook 的实际表现（决策三要求写明）

`_meta/review-<侧>-<run_id>.json` 丢失时：`gate --check` 报 failure `missing_review_json` ⇒ 闸门同样停在 `review_done_awaiting_disposition` ⇒
- 收工 Hook 报「还有未逐条裁决的审查意见」——同样说偏，但它给的出口（读审查文档、写裁决件、跑 `gate --check`）照做**会**看到 `missing_review_json` 那一条及其恢复指引（不早退，它在 :393 起、裁决件定位之后——裁决件尚未落盘时同样被 :215 的早退挡住，但按收工 Hook 的指引先写裁决件再跑就看得到）；
- 提交 Hook 在闸门段就返回，**走不到**留痕完整性段（`checkArchiveIntegrity` 对登记过的 `review-*.json` 会报「已丢失」并给 restore 出口）。即「另有提交 Hook 的留痕完整性段管」只在闸门已离开这一格之后成立。
不纳入本题：它的真实出口（在终端 restore）由 `gate --check` 给出，Driver 按现文案走得到；且触发它需要工具之外的删改。仅如实记在此处，不改代码。

### 1.5 第三处同类句：会话开始 Hook

`hookSessionStart` 注入待办时对同一状态写「审查已落盘但裁决未齐备」（`hooks.ts:1611`）。它是给新会话的提示、不拦截，误导程度低于两处拦截 Hook；决策一只点了两处，本计划不改，列 D2 交双审判断要不要顺手改或登记。

### 1.6 读取入口

- `meta.ts:479` `latestRunMeta`：按 run_id 倒序扫，**读不出的每一份都 `warn` 到 stderr**（:500）。
- `meta.ts:605` `readRunMeta(layout, stage, runId)`：读指定一份，任何失败返回 null，**不输出任何东西**。
- `GateEntry.run_id`（`state.ts:52`）就是置这一格的那次运行的 run_id（`review.ts:1873` 传 `runId`）。

## 2. 方案

### 2.1 区分方式：按闸门项的 run_id 直读那一份（对决策二的一处收窄，请双审核）

对每个待裁决闸门项 `g`：`g.run_id` 非 null 时 `readRunMeta({archiveRoot: ctx.archiveRoot, topic: g.topic}, g.stage, g.run_id)`，读得出且 `guard.readonly_breach === true` ⇒ 判该项为「本轮失守」；其余一切（`run_id` 为 null、文件不在、读不出、不合契约、`readonly_breach` 为 false）⇒ 判「未见失守」，走原文案。

为什么不照决策二写 `latestRunMeta`：
1. **逐字不变会被打破**：`latestRunMeta` 遇读不出的留痕会 `warn` 到 stderr，Hook 的 stderr 就多出一行——「读不出时文案与改前逐字相同」当场不成立。`readRunMeta` 静默返回 null。
2. **「是不是这一轮」天然成立**：闸门项的 `run_id` 就是这一格的那次运行；`latestRunMeta` 拿到的「最新可读」那份还要再与 `g.run_id` 比一次才知道是不是这一轮（最新那份坏了时它会退到上一轮）。直读把「留痕不是这一轮」这一格消掉了，而不是靠一次比较兜住。
3. 来源仍是同一份运行留痕（`run.json` 的 `guard.readonly_breach`），与决策二的事实来源一致，只换了读取入口。

**这条读取只影响文字，不影响判定**：退出码、是否拦、阻断计数全部在读取之前就已确定，读取结果只选文案。所以它不需要 `resolveRoundDriver` 那套 realpath / 软链守卫——伪造一份失守留痕的最坏后果是 Hook 把「未裁决」说成「失守」，拦截照旧（§4 R1）。

实现为 `hooks.ts` 内一个私有 `async function roundBreach(ctx, g): Promise<string[] | null>`：失守时返回调用记录（`guard.breached_files ?? []`），否则 null。不吞异常之外的东西——`readRunMeta` 本身不抛。

### 2.2 文案组织：按「未见失守 N / 失守 B」两组拼

两处 Hook 都把 `pending` 拆成 N 与 B（保持原顺序）：
- **B 为空** ⇒ 走原代码路径，**逐字不变**（含 `stderr`、`reason`、`systemMessage`、阻断上限那句）；
- **B 非空、N 为空** ⇒ 只出失守段；
- **B、N 都非空** ⇒ 先出原文案（列表只列 N、指引里的阶段取 N 的第一项），再接失守段。

阻断上限分支按 `pending[0]`（与计数对象同一项）判：它在 B 里 ⇒ 用失守版两句；否则原句逐字不变。

### 2.3 失守段的文字（送计划双审定稿）

共用一个私有函数 `breachGuidance(items: {g, records}[]): string[]` 生成逐项的若干行，两处 Hook 与阻断上限分支只写各自的首句。

**收工 Hook 拦截（`reason`）**，B 只有一项 `t/code`、调用记录两条时的样例：

```
本轮审查记录到只读失守：t/code。这道闸门靠补裁决件解不开——gate --check 对只读失守一律判失败，裁决件写得再齐也不放行，不要再为解闸门去补裁决件。
  · t/code（run 20261002T000000Z）调用记录（非文件路径）：write_to_file(…/src/injected.ts)、MCP:mcp__node_repl__js(c1 …)
处置：先核对该轮 run 元数据的 snapshot.drift 与工作区是否确有改动——确有则清理后重跑审查；drift 为 false 只排除「未被 .gitignore 忽略的文件被改」，不足以判误报，还须核调用记录本身是否真的写入、目标是否存在、是否被 ignore（与 gate --check 的 readonly_breach 一条同一判据；裁决件尚未落盘时 gate --check 会先报缺件、看不到那一条）。
核实为误报时，由用户决定：用 /dual-abandon --topic t --stage code 作废这一轮（保留工件、只解闸门），或重跑该阶段审查。
```

`stderr` 为首句（与原来「`stderr` 为首句」同构）。

**收工 Hook 阻断上限放行（`systemMessage` 与 `stderr`）**：

```
已连续 N 次阻断收工，本次放行以避免死循环。
  t/code 本轮记录到只读失守，补裁决件解不开这道闸门；请手工处理：核对 snapshot.drift 与工作区，确有改动则清理后重跑审查，核实为误报则由用户决定用 /dual-abandon --topic t --stage code 作废这一轮，或重跑审查。
```

**提交 Hook（`stderr`）**：

```
以下阶段的审查记录到只读失守，提交被拦下：t/code
  这道闸门靠补裁决件解不开——gate --check 对只读失守一律判失败，裁决件写得再齐也不放行。
  · t/code（run …）调用记录（非文件路径）：…
  处置：（同收工 Hook 的处置两句）
  如需关闭该拦截，可在 .trivium/config.yaml 设 gate.block_commit: false。
```

N 非空时原三行在前、失守段在后，「如需关闭」那行只出一次（放最后）。

细节：
- 调用记录每项至多 8 条、超出加「…」，与 `gate.ts:375` 同口径；记录为空时写「（run 元数据未记录）」，同口径。
- 出口写法用 `/dual-abandon`：会跑到这两个 Hook 的只有带 Hook 的载体，它们的调用写法今天都是 `/名字`——与 `checkArchiveIntegrity` 收尾（`hooks.ts:1409` 的注释）同一前提，同一处注释引用。
- 「由用户决定」：abandon 与重跑都由用户发起（审批、作废的发起权在用户），文案不让 Driver 自行执行。
- 主题名、阶段名、run_id 原样嵌入，不加引号（与原文案一致）。

### 2.4 文档

- 设计 §8.5 Hook 职责表：`hook-pre-commit` 行与 `hook-stop` 行各补一句（保持单行）：「该轮运行留痕记录了只读失守（`guard.readonly_breach`，按闸门项的 `run_id` 直读）时改说真因、列调用记录并给出 abandon / 重跑出口，拦截行为不变；读不出或未失守时文案不变（EV-98 文案部分）」。设计版本升一个小号，变更记录加一行。
- BACKLOG EV-98：状态改为「部分结案（文案部分）」，写明本主题、run 与落点；判据部分（解释器内联脚本误报）仍 todo、触发条件不变（再次失守）。排序快照里「EV-98 文案」那一行按实处理。
- 不新登条目（决策四），除非双审核出（§1.5 的 D2 由双审决定是否登记）。

## 4. 风险

- **R1 伪造失守留痕**：有人在 `_meta` 放一份 `readonly_breach: true` 的 run.json、run_id 与闸门项相同 ⇒ Hook 把「未裁决」说成「失守」。拦截不变，后果是文案误导；而 `_meta/` 是编排器独占面（写入本就被 Hook 拦），提交锚也会拦改动。不加守卫。
- **R2 失守段过长**：调用记录多时一屏装不下。至多 8 条/项，与 `gate --check` 同口径。
- **R3 文案承诺失真**：「裁决件写得再齐也不放行」依赖 `checkAdjudication` 对 `readonly_breach` 无条件推 failure（`gate.ts:347`）。若将来有人加「豁免失守」的出口，此句要同改——在两处各留一行注释指向 `gate.ts` 那一条。
