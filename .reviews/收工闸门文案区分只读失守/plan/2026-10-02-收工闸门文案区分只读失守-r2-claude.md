### 1.2 只读失守时闸门停在原地

- `review.ts:1858` / :1872：运行 `status === 'success'` 就置 `review_done_awaiting_disposition`，**不看** `guard.readonly_breach`——失守轮也是 success。

### 1.3 早退：裁决件缺失时 `gate --check` 看不到失守那一条

`checkAdjudication` 找不到本轮裁决件即以 `missing_disposition` **早退**（`gate.ts:215`），走不到 :347。`fault-injection.test.ts:450` 与 `mcp-detect.test.ts:50` 的注释已记下这个顺序。所以「先运行 `gate --check` 看调用记录」**只在裁决件已落盘时成立**。本计划因此让 Hook **自己**列出调用记录与快照漂移的实际取值（§2.3），`gate --check` 只作为处置判据的权威出处引用。

### 1.4 `missing_review_json` 在两处 Hook 的实际表现（决策三要求写明）

`_meta/review-<侧>-<run_id>.json` 丢失时：`gate --check` 报 failure `missing_review_json` ⇒ 闸门同样停在 `review_done_awaiting_disposition` ⇒

- 收工 Hook 报「还有未逐条裁决的审查意见」——同样说偏，但它给的出口（读审查文档、写裁决件、跑 `gate --check`）照做**会**看到 `missing_review_json` 那一条及其恢复指引（它在 :393 起、裁决件定位之后——裁决件尚未落盘时同样被 :215 的早退挡住，但按收工 Hook 的指引先写裁决件再跑就看得到）；

不纳入本题：它的真实出口（在终端 restore）由 `gate --check` 给出，Driver 按现文案走得到；且触发它需要工具之外的删改。仅如实记在此处，不改代码。

### 1.6 读取入口

- `meta.ts:479` `latestRunMeta`：按 run_id 倒序扫，**读不出的每一份都 `warn` 到 stderr**（:500，`util/log.ts` 直写 `process.stderr`，不经 Hook 返回体）。

## 2. 方案

### 2.1 区分方式：按闸门项的 run_id 直读那一份（对决策二的一处收窄，计划双审三侧均认可）

对每个待裁决闸门项 `g`：`g.run_id` 非 null 时 `readRunMeta({archiveRoot: ctx.archiveRoot, topic: g.topic}, g.stage, g.run_id)`，读得出且 `guard.readonly_breach === true` ⇒ 判该项为「本轮失守」；其余一切（`run_id` 为 null、文件不在、读不出、不合契约、`readonly_breach` 为 false）⇒ 判「未见失守」，走原文案。

为什么不照决策二写 `latestRunMeta`：

1. **逐字不变会被打破**：`latestRunMeta` 遇读不出的留痕会 `warn` 到进程 stderr，Hook 的输出就多出一行——「读不出时文案与改前逐字相同」当场不成立。`readRunMeta` 静默返回 null。
2. **「是不是这一轮」天然成立**：闸门项的 `run_id` 就是这一格的那次运行；`latestRunMeta` 拿到的「最新可读」那份还要再与 `g.run_id` 比一次才知道是不是这一轮。
3. 来源仍是同一份运行留痕（`run.json` 的 `guard.readonly_breach`），与决策二的事实来源一致，只换了读取入口。

**这条读取只影响文字，不影响判定**：退出码、是否拦、阻断计数全部在读取之前就已确定，读取结果只选文案。所以它不需要 `resolveRoundDriver` 那套 realpath / 软链守卫——伪造一份失守留痕的最坏后果是 Hook 把「未裁决」说成「失守」，拦截照旧（§4 R1）。

**与 `gate --check` 轮次来源不同源的一格**（CODEX-07）：闸门项 `run_id = R2` 的 run.json 读不出、而更旧的 R1 可读且记着失守时，`gate --check` 不带 `--run-id` 走 `latestRunMeta` 退回 R1 报 `readonly_breach`，Hook 却按「未见失守」出原文案。这一格本身是「留痕坏了」（EV-148 的状态），只来自工具之外的改动；Hook 若改去扫更旧的留痕，就要重新引入 `latestRunMeta` 的 stderr 告警并把上一轮的失守说成这一轮的。**不改，登记为已知边界**（§4 R4），并用 U14 锁住现行为（原文案、无额外输出）。

实现为 `hooks.ts` 内一个私有 `async function roundBreach(ctx, g)`：失守时返回 `{ g, meta }`（后续取 `breached_files`、`snapshot.drift`、`driver`），否则 null。`readRunMeta` 本身不抛。

### 2.2 文案组织：按「未见失守 N / 失守 B」两组拼

两处 Hook 都把 `pending` 拆成 N 与 B（保持原顺序）。**B 为空 ⇒ 走原代码路径，逐字不变**（含 `stderr`、`reason`、`systemMessage`、阻断上限那句）。B 非空时：

**收工拦截（`reason` / `stderr`）**：

- N 为空：失守首句 + 逐项段 + 共用处置段。`stderr` = 失守首句。
- N 非空（混合）：原文案两句（列表只列 N；指引末尾的阶段取 N 的第一项，并在句末补「（只针对上列阶段；下列只读失守的阶段另行处置，它们的 gate --check 不会通过）」——CODEX-03），再接「另有阶段本轮审查记录到只读失守：…」开头的失守段。`stderr` = 原首句（列 N）+ 换行 + 失守首句，两个真因都在（AGY-02 ≡ GLM-04）。

**阻断上限放行（`systemMessage` / `stderr`）**（CODEX-02）：B 非空时一律出新版，**N 与 B 都点名**——

```text
已连续 N 次阻断收工，本次放行以避免死循环。
  〈N 列表〉 的裁决仍未齐备，请手工处理。           ← 只在 N 非空时出现
  〈B 列表〉 本轮记录到只读失守，补裁决件解不开这道闸门，请手工处理：
  〈逐项段，缩进两格〉
  〈共用处置段，缩进两格〉
```

计数对象仍是 `pending[0]`（不变）；不论它在 N 还是 B，B 非空就出新版。B 为空时原两句逐字不变。

**提交 Hook（`stderr`）**（GLM-03 定行序）：「如需关闭该拦截……」**恒为最后一行、只出一次**。

- N 非空：原文案前两行（列表只列 N）；
- 失守段：首句「以下阶段的审查记录到只读失守，提交被拦下：〈B 列表〉」+ 解不开那句 + 逐项段 + 共用处置段，统一缩进两格（首句除外，与原文案同构——AGY-04）；
- 最后一行：关闭方式。

### 2.3 失守段的文字（逐项段 + 共用处置段）

共用私有函数 `breachLines(items, indent)` 生成，两处 Hook 与阻断上限分支只写各自的首句（AGY-04：带缩进参数）。

**逐项段**（每个失守项各一组，AGY-01）：

```text
· t/code（run 20261002T000000Z）
  调用记录（非文件路径）：write_to_file(…/src/injected.ts)、MCP:mcp__node_repl__js(c1 …)
  快照漂移：未检出（snapshot.drift.changed 为 false——这不足以判定误报，见下方处置）
  核实为误报时，由用户决定：用 /dual-abandon --topic t --stage code 作废这一轮（保留工件、只解闸门），或重跑该阶段审查。
```

- 调用记录至多 8 条、超出加「…」，为空写「（run 元数据未记录）」，与 `gate.ts:375` 同口径。
- 快照漂移按 Hook 已读到的那份 run.json 直接写实际取值（CODEX-08），三种形态：`changed: false` ⇒ 上面那句；`changed: true` 且有文件 ⇒「检出 K 个文件改动：a、b…」（至多 8 个）；`changed: true`、文件为空且有 `unknown_reason` ⇒「比对未完成（〈unknown_reason〉），按有改动对待」。
- 作废命令按该轮 run.json 的 `driver` 用 `entryCommandOf(meta.driver, 'dual-abandon')` 生成（CODEX-04），不写死 `/`；主题、阶段逐项各给一条（AGY-01）。
- 「由用户决定」：abandon 与重跑都由用户发起，文案不让 Driver 自行执行。

**共用处置段**（所有失守项共用一次）：

```text
〈READONLY_BREACH_TRIAGE 原文〉
（与 gate --check 的 readonly_breach 一条同一判据；裁决件尚未落盘时 gate --check 会先报缺件、看不到那一条。）
```

`READONLY_BREACH_TRIAGE` 是从 `gate.ts:369～372` 抽出的导出常量（CODEX-01）：「处置：先核对 run 元数据的 snapshot.drift 与工作区是否确有改动——确有则清理后重跑审查。drift 为 false 只排除了……确认后再按 BACKLOG EV-75 登记重跑。」`gate.ts` 的 failure message 改为由它拼接，**拼出的字节与改前相同**（§3.1 U15 以字面常量锁住）；两处 Hook 引用同一常量，判据句只有一份来源，改一处即两处生效。

**失守首句**（两种前缀）：

- 单独：「本轮审查记录到只读失守：〈B 列表〉。这道闸门靠补裁决件解不开——gate --check 对只读失守一律判失败，裁决件写得再齐也不放行，不要再为解闸门去补裁决件。」
- 混合：「另有阶段本轮审查记录到只读失守：〈B 列表〉。」+ 同一后半句。

## 4. 风险

- **R1 伪造失守留痕**：有人在 `_meta` 放一份 `readonly_breach: true` 的 run.json、run_id 与闸门项相同 ⇒ Hook 把「未裁决」说成「失守」。拦截不变，后果是文案误导；而 `_meta/` 是编排器独占面（写入本就被 Hook 拦），提交锚也会拦改动。不加守卫。
- **R2 失守段过长**：调用记录多时一屏装不下。至多 8 条/项，与 `gate --check` 同口径。
- **R3 文案承诺失真**：「裁决件写得再齐也不放行」依赖 `checkAdjudication` 对 `readonly_breach` 无条件推 failure（`gate.ts:347`）。处置判据句已抽成单一常量（不再有第二份）；「一律判失败」这半句仍是对 `gate.ts` 行为的陈述，在常量旁与 Hook 首句旁各留一行注释互指，并由 §3.2 集成用例（齐裁决件仍失败 + Hook 说失守）端到端锁住——将来有人加豁免出口，该用例会先红。
- **R4 轮次来源不同源**（CODEX-07）：闸门项那一轮读不出而更旧一轮记着失守时，Hook 出原文案、`gate --check` 报失守。不改（理由见 §2.1），U14 锁现行为，EV-98 结案说明里记一句。

## 7. 实施期更正（S5 编码时追加，计划双审之后）

**「或重跑该阶段审查」不是独立出口。** r1 / r2 §1.2 与 §2.3 把出口写成「作废这一轮，或重跑审查」两条并列（沿用决策二的原话），三侧审查也都没有指出。编码写集成用例时核实：闸门停在 `review_done_awaiting_disposition` 时，`review --start` 在落盘之前做比较-交换（`review.ts:985～1001`，期望状态集不含待裁决），判负即以「上一轮……的审查意见尚未裁决，不能直接重跑」退 2；`gate-loop.test.ts:641` 已锁这一行为。而失守轮的 `gate --check` 必败，闸门离不开这一格——**唯一出口是作废这一轮**，重跑（不论是确有改动清理之后，还是核实为误报之后）都要先作废。

落点：§2.3 逐项段末行改为「出口：由用户决定用 〈作废命令〉 --topic … --stage … 作废这一轮（保留工件、只解闸门）。」；共用处置段末尾加一行「不论确有改动要清理后重跑，还是核实为误报想重跑，都须先作废这一轮：闸门停在待裁决时 review --start 拒绝重跑，而这一轮的 gate --check 不会通过。」；U2 加断言（含该行、不含「或重跑该阶段审查」）；§3.2 集成用例在失守格里实跑一次「不作废直接重跑 ⇒ 退 2」再作废、重跑成功。

同族的另两处说法本题不改，只记入 EV-98 结案说明：`gate.ts` 处置句里「确有则清理后重跑审查」（决策一不改 gate 输出，它在 Hook 里有上面那行补足）；`review.ts:997` 重跑拒绝文案给的第一条路「补齐裁决件并通过 gate --check 后再来」对失守轮同样走不通。
