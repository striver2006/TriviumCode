## 总判断

三条的定位与方向大体站得住（EV-24 的判据放下发层、EV-18 删第二跳，我都同意），但计划的事实基线有一处失实、EV-20 的落点有六处会返工。最危险的一条：§7 断言「agy/zcode 运行目录里没有凭据副本」不成立——`prepareZcodeHome` 把整份含凭据的 `~/.zcode/cli/config.json` 拷进 `<runDir>/home/`，`retention.ts` 文件头自己就写着「每次运行还各留两份 zcode 凭据副本」。按现计划做完，EV-20 的威胁只补了一半，而且 D-2 的后验扫描范围（`codexhome/` 内、`sessions/` 外）恰好避开了 2026-09-16 那次真实泄露的留痕通道（编排器自己写的 `stdout.jsonl`）。其次三处是机制性的：哨兵幂等判据与 `runner.ts` 的重叠使用同一 `out_dir` 冲突，重试那一次的副本抹不掉；兜底清扫挂在 `pruneRunDirs` 上，被 `run_dir_days: 0` 整体短路（而计划明说抹除不该有关档）；「worker 已死」的前提里 `status.json` 读不到会被折叠成「可抹」，对不可逆操作是 fail-open，正是本项目 EV-26 ④ 刚复过的三态纪律。EV-24 侧一条同源缺口：`--reject=true` 走 `=` 分支存字符串、`=== true` 判假，静默把拒绝变通过，加了 BOOLEAN_FLAGS 也管不住。

**结论**：`request-changes`

### CODEX-05 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.1 表格「清扫兜底」行的判据「终态或 worker 已死」；§6 自查表 U2；§8.3` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：对 U2 我的答复是：需要比整删更强的判据，而且缺口不在「进程判活」上，在「读不到 status」上。现有结构里 `status.json` 缺失/撕裂与「worker 已死」是同一个出口（都落到 TTL 判据），对整删无害（新鲜目录 mtime 未到期就不会删），对抹除则是把**证据不存在**当成**证据成立**——一次正在跑、状态文件尚未落盘的审查会在中途被抹掉凭据而失败。这正是本项目三态纪律反复复发的形状。

**依据**：`src/trivium/status.ts:95-103`：`readStatus` 对「文件不存在」与「JSON 撕裂/损坏」**都返回 null**，注释自己写明「撕裂读或损坏：由 `interpretStatus` 归入本次轮询无效」——即上游本来的口径是三态。`src/trivium/retention.ts:53-68`：`if (status) { … 判活 … }` 为假时直接落到 TTL 那一支。而「status.json 还不存在但运行是活的」不是假想：`src/trivium/run-protocol.ts:679-695` 专门为此写了 `readHandoffIdentity`，注释逐字「status.json 读不到（刚派生还没落盘、或运行目录被清了）」；`run-protocol.ts:739-741` 也承认 `patchStatus` 可能静默不写。

**建议**：抹除前提写成两条合取式，且 null 一律跳过：status 读得到 **且** `isTerminal(phase)`；或 status 读得到 **且** 有 `worker_pid` **且** `processAlive` 明确返回「不是同一进程」（pid 复用按纪律 6 用 `lstart` 比对）。把「status 读不到」单列为第三种结论，记进清扫输出（跳过多少、为什么），并给 `test/unit/retention.test.ts` 加一条「无 status.json 的目录不被抹」的用例——计划 §4.2 现在只有「不实现 `scrubRunDir` 的侧如实跳过」这一类，没有这一条。

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.2 表格第一行（`BOOLEAN_FLAGS` 永不吞下一个 token）与 §4.2「对账测试（新）」` |

**问题**：`BOOLEAN_FLAGS` 只治「吞下一个 token」这一半，漏了「`=` 传值」那一半：`--reject=true` / `--json=0` / `--allow-single=1` 走的是 parseArgs 的等号分支，存进 Map 的是字符串，而所有消费点判 `=== true`。于是 `trivium approve --topic X --stage plan --reject=true` **静默按通过处理**——与 EV-24 要修的是同一个后果（拒绝变通过），却不在计划的判据覆盖面内，改完仍是第三种结局。

**建议**：`BOOLEAN_FLAGS` 同时用作「不接受 `=` 取值」的判据：等号分支里若 `name ∈ BOOLEAN_FLAGS` 且值不是 `true`/`false` 的字面（或直接一律拒绝），退 64 并给写法。§4.2 的对账用例请把「`--<bool>=<值>` 也红」并进去（一条命令两种形态都扫），否则下次新增布尔旗标仍只补一半。

### CODEX-08 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.3 表末两行（测试与 skill 指引）+ §4.2 对账测试「四条 skill 不再含字面双引号字样」` |
| 类别 | contract ｜ 层次 plan |
