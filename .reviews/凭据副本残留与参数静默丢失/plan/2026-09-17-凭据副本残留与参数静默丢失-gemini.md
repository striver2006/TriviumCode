## 总判断

核心取舍合理，但存在两处关键安全与生命周期缺口：
1. 凭据残留漏算了 zcode 侧：zcode 在指定模型时同样会向运行目录复制含鉴权凭据的 config.json，计划排除 zcode 会留下 30 天未抹除漏洞；
2. 抹除挂载点遗漏了 waitRun 的 worker_lost 路径，导致强杀/崩溃后同会话重跑期间凭据持续残留；
3. Skill 指引建议在含单引号时改用双引号加转义，存在严重变量展开与注入风险，应改为 POSIX 单引号转义模式；
4. 并发清扫需加固 starting 保护以防竞态，既有两条集成测试也需同步更新。请修订后再推进实施。

**结论**：`request-changes`

### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.1 & §7` |
| 类别 | security ｜ 层次 plan |
| 置信度 | high |

**问题**：方案假设「运行目录下仅 codex 有凭据副本」与代码事实不符：zcode 在指定模型（config_copy 路由）时同样会在运行目录下复制含凭据的 config.json，若不接入抹除契约将遗漏整整一族的凭据残留。

**依据**：被审计划 §2.1 与 §7 明确写道：「不给 agy / zcode 加 scrubRunDir：它们的凭据走各自 CLI 登录态，运行目录里没有副本（若审查者知道反例，请指出）」。查阅 src/trivium/adapters/zcode.ts:153-180 的 prepareZcodeHome，当指定模型（非默认）时，适配器会将宿主机 ~/.zcode/cli/config.json 完整拷贝至 path.join(runDir, 'home', '.zcode/cli/config.json')，且代码注释 177 行白纸黑字写明「// 配置副本含凭据，权限收紧」；在 retention.ts:4-6 的注释中也明确记录「每次运行还各留两份 zcode 凭据副本」。然而 zcode.ts:307 跑完后从未清理此目录，如果仅 codex 实现 scrubRunDir，zcode 的凭据副本将继续在运行目录下残留 30 天。

**建议**：CriticAdapter.scrubRunDir? 契约应当同时由 zcodeAdapter 实现（清理其 runDir/home 下的配置副本），或在 zcodeAdapter.run() 的 finally 与清扫路径中一并纳入，并在 §7 中更正该前提断言。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.1 & §8 #1` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：凭据抹除挂载点存在第五种常见结局遗漏：worker 崩溃或强杀后由 waitRun 判定 worker_lost 结案时，未就地触发该运行目录的抹除。

**依据**：被审计划 §2.1 与 §8 #1 规划了三处挂载：适配器 finally、--cancel、会话启动清扫（pruneRunDirs）。查阅 src/trivium/run-protocol.ts:580-598 的 waitRun 实现：当工作进程崩溃、被系统 OOM killer 终止或异常退出时，正在等待的客户端会通过 status.ts 的 interpretStatus 判定为 reading.kind === 'worker_lost'；waitRun 随即 patchStatus 将 phase 置为 failed 并释放闸门，但此处并未调用抹除逻辑。此时用户并未退出会话（不会触发 hook-session-start），也不会执行 --cancel（因为进程已死），导致崩溃/强杀后的凭据在同会话后续工作中一直残留。

**建议**：在 run-protocol.ts:580 的 waitRun 的 reading.kind === 'worker_lost' 处理分支中，在确认 worker 已死并置 failed 之后，追加对该 runDir 逐侧调用适配器 scrubRunDir 的逻辑。

### AGY-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.3 & §8 #5` |
| 类别 | security ｜ 层次 plan |
| 置信度 | high |

**问题**：Skill 指引要求正文含单引号时换用双引号并手动转义 shell 元字符，极易引发 shell 变量展开、命令代换或反斜杠失真，危及安全性与 FR-20 逐字承诺。

**依据**：被审计划 §2.3 与 §8 #5 指引四条 review skill 的第 2 步：「单引号包住；正文含单引号时改用双引号并转义 $、反引号、\\、\"」。在实际生产中，Claude Code 的 Bash 工具是起子 shell 执行命令字符串，如果正文含单引号而让 LLM 改用双引号并自行转义特殊字符，极易发生遗漏：例如焦点中包含变量 `$ARGUMENTS`、代码测试反引号（如 `cat file`）或正则表达式字面量（如 `\\s+`），双引号下的未转义字符会被 shell 发生环境展开、命令替换注入或反斜杠折叠，直接破坏 FR-20 逐字承诺甚至引发命令执行风险（EV-18 本身就是因焦点含各类字符类引发）。Unix shell 中传递任意自由文本的标准安全解法是单引号包裹，并将其中的单引号替换为 `'\\''`，其余一切元字符在单引号中均为字面量。

**建议**：修改 skill 指引文案，禁止建议换用双引号；统一规定使用 POSIX shell 单引号包裹正文，单引号内的 `'` 一律转义为 `'\\''`，其他字符（包括 $、`、\\、\"）在单引号内完全保持字面量，无需且严禁额外转义，并提供照抄格式。

### AGY-04 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.1 & §6 U2 & §8 #3` |
| 类别 | concurrency ｜ 层次 plan |
| 置信度 | high |

**问题**：清扫未到期目录凭据时，若判据仅为「worker 已死」，在并发会话刚拉起（phase === 'starting'，worker_pid 尚为 null）时会发生误杀竞争。

**依据**：被审计划 §2.1 与 §6 U2 / §8 #3 提出在 pruneRunDirs 中对「终态或 worker 已死」但尚未到期的运行目录调用抹除。查阅 src/trivium/status.ts:78，newStatus 刚创建时 phase 为 'starting' 且 worker_pid: null。查阅 src/trivium/retention.ts:57-64，现有整删逻辑只在 now - lastActive > ttlMs（30天）时才删，因而 starting 窗口不会被删；但若对未到期目录新增抹除分支，若仅以 !isTerminal && !workerAlive 为判据，当另一进程刚创建 runDir 但尚未回填 worker_pid 时，会被判为「worker 不在」而将其刚准备好的 config.toml 提前抹除，导致新运行在拉起瞬间崩溃。

**建议**：明确回答 U2：不可逆抹除必须采用比整删更严的判据——仅当 isTerminal(status.phase) 为 true，或者 status.phase !== 'starting' 且 heartbeat 已超出 heartbeat_stale 且 processAlive 确认进程不存在时，方可执行未到期抹除；对于 status 不存在、损坏或刚处于 starting 的目录严格跳过。

### AGY-06 · 吹毛求疵（nit）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §2.1 & §8 #2` |
| 类别 | maintainability ｜ 层次 plan |
| 置信度 | high |

**问题**：抹除失败的警告若仅停留在适配器进程的 console.warn，会沉淀在后台 worker 日志中，无法及时被等待中的用户和 Driver 察觉。

**依据**：被审计划 §2.1 与 §8 #2 提到「抹除失败：warn + 哨兵记 ok: false，不改变该侧审查结果」。查阅 src/trivium/run-protocol.ts:402-461，worker 是独立后台派生进程（workerMain），其 console warn/error 输出被重定向至 workerLogPath(runDir)。如果 codex.ts 的 scrub 失败仅在适配器内部 warn，前台等待的 Claude Code 进程只能拿到 status.json，无法看到 worker.log 内的警告，导致「抹除失败」对操作者实际上处于隐默状态。

**建议**：抹除失败的警告应作为结构化信息收进 CriticResult.warnings（或通过 executeRun.warnings 汇入 status.message），确保在 review --wait 的进度输出以及 run.json 元数据中对用户显式可见。

**问题**：cli.ts 中的 BOOLEAN_FLAGS 若不处理带等号传值（如 --flag=true），会导致带等号的显式布尔值无法正确匹配 === true 判定。

**建议**：在 parseArgs 识别 BOOLEAN_FLAGS 时，对 a.slice(2, eq) 命中的情况同步进行布尔值解析转换，参考 topic-args.ts 的处理口径。
