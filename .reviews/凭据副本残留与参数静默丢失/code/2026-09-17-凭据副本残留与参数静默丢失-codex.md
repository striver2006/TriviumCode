### CODEX-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/run-protocol.ts 的 waitRun worker_lost 分支（约 581-607 行）；src/trivium/status.ts 的 interpretStatus（188-195 行）` |
| 类别 | concurrency ｜ 层次 code |
| 置信度 | medium |

**问题**：挂载点②在「进程活着但心跳过期」的 worker_lost（reason='heartbeat_stale'，status.ts 注释明说 worker 仍存活）下也会执行 scrubRunDir——对一份可能还活着的运行做不可逆的载体删除与自有目录扫描。worker_lost 分支不复核进程存活就抹；原先该分支只做状态与闸门回收（可逆），本版把不可逆动作挂上去了。若 worker 其实活着（磁盘抖动、事件循环被同步段堵住超过 heartbeat_stale_s=120s），codex/zcode 子进程还在跑，config 副本被中途删掉，症状会变成该侧以莫名的鉴权/配置错误失败，与真实原因对不上号。

**依据**：src/trivium/status.ts:194-195「进程活着但心跳过期 → 也算失联」；src/trivium/run-protocol.ts:582-600 worker_lost 分支直接 patch failed + releaseRunningGate + scrubRunDir(runDir, wiredAdapter)，对 reason==='heartbeat_stale' 与 'pid_gone' 不加区分；retention.ts 的④路径则显式核对了 processAlive/sameProcess 后才判 eligible——同一动作两个挂载点严紧不一。

**建议**：②在动手抹除前按④的口径复核一次（status.worker_pid 现势 processAlive 不活才抹；heartbeat_stale 且进程仍在则只记待办、留给④），或至少只在 reason!=='heartbeat_stale' 时抹。方向：不可逆动作的准入判据应与 retention 的严判据同源。

### CODEX-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/scrub.ts 的 SCAN_SIZE_CAP 段（scanAndRemoveSecrets 与 redactLogs 对超限文件的处置）` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | medium |

**问题**：超过 8MB 的文件在扫描侧记 warning、在日志侧记 error，两者都并进 out.errors → ok:false。后果有两个：(a) codex 侧 stdout.jsonl 是 900s 级别审查的完整事件流，超时/大仓库轮次超过 8MB 完全现实——这样的运行目录哨兵永远 ok:false，④每轮会话启动重扫再失败，hooks 每次都渲染「凭据副本抹除失败……副本仍在盘上」，而载体其实早已删净：待办区被一条持续 30 天的误导性告警占住（正好违反本版自己声明的「失败必须看得见」——看得见的是假失败）；(b) 真正的问题被这个假信号盖住：超限的 stdout.jsonl/trace.json 从未被脱敏，明文 token 若在其中会一路躺到 TTL 整删，EV-32 只登记了 sessions/，没登记这条。

**依据**：src/trivium/scrub.ts：redactLogs 里「${rel} 超过扫描上限（…），未脱敏」push 进 errors；scanAndRemoveSecrets 的「跳过超大文件」warnings 经 scrubSideDir 的 out.errors.push(...r.warnings) 同样并入；scrubSideDir 的 out.ok = out.errors.length === 0；retention.ts 把 !o.ok 一律计入 scrubFailed；hooks.ts:1070-1075 渲染「副本仍在盘上，下次会话启动会重试」。

**建议**：把「载体没抹掉」与「日志没脱敏/没扫到」分成两档严重度：前者才配「副本仍在盘上」与人读失败，后者降为独立告警（并可考虑对超限日志分块流式脱敏，或至少整文件删除兜底——它不是回读来源）。否则④的重试语义与 hooks 文案都在说一件没发生的事。

### CODEX-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/secrets.ts 的 private-key-block 规则 × redactSecrets 的替换路径` |
| 类别 | security ｜ 层次 code |
| 置信度 | high |

**问题**：「就地脱敏只换值、留键名与结构」对 PEM 私钥这一族不成立：private-key-block 的匹配只是 BEGIN 标记行，redactSecrets 把标记替换成首尾预览后，其后整段 base64 私钥正文一字不动地留在 stdout.jsonl / trace.json 里，且哨兵记 ok:true、redacted 计数为正——留痕宣称「已脱敏」，实际密钥主体完好。规则集中没有任何一条命中裸 base64 密钥正文行（其它规则都要求前缀形态或键名）。

**依据**：src/trivium/secrets.ts：RULES 里 private-key-block 的 re 只匹配 -----BEGIN … PRIVATE KEY-----；redactSecrets 对无 secretGroup 的规则做 redact(whole)——whole 即标记本身；scanSecrets 同形。归档侧命中即拒所以无害，运行目录侧走的是 redact 路径，正是本补丁新开的口子。

**建议**：要么给 private-key-block 增加「连正文一起处理」的脱敏形态（如从 BEGIN 到 END 整段替换占位），要么对命中该规则的日志文件改「脱敏」为「整删」（它同属排障依据的话，如实记 EV-32 同族的登记项）。至少不得让 ok:true 为「私钥已被抹」背书。
