### GLM-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/secrets.ts:77-79` |
| 类别 | security ｜ 层次 code |
| 置信度 | medium |

**问题**：PEM 材料判据 `PEM_BODY = [A-Za-z0-9+/]{40}` 的字符类包含整个十六进制字母表：git SHA-1 恰为 40 个连续 hex、SHA-256 为 64 个，而本项目的审查留痕里哈希随处可见（任务书与 front-matter 的 content_hash/snapshot_hash、证据里的提交号）。审查文档只要引用一句 PEM 标记行（r2 事故的原始形态：审查员摘录 secrets.ts 的标记常量）且其后 400 字符内出现任一 40+ 连续 hex 或纯字母数字串，`private-key-block` 照样命中、assertNoSecrets 拒绝整份文档落盘——三侧配额再烧一轮。修复的论断「讨论性引用必然不带（材料）」对「谈论标记 + 顺手引一个哈希」的普通评审写作不成立。检出面代价几乎为零：真 base64 密钥材料连续 40+ 字符全部落在 [0-9a-fA-F] 的概率约 4^-40。

**依据**：src/trivium/secrets.ts:74-93（PEM_LABEL/PEM_BODY/PEM_DETECT 构造及「真私钥必带它，讨论性引用必然不带」的论断）、:325-341（assertNoSecrets 以 full 模式扫审查文档）；test/unit/secrets.test.ts「PEM：只有标记行不命中」用例只覆盖标记后无任何长串的形态，无「标记后跟哈希」的边界用例；被审补丁 v1.3.15 台账第十条记载的 r2 实撞即「引用一句标记行」。

**建议**：给材料段加负向条件：40+ 连续 base64 的窗口内要求至少一个 [g-zG-Z+/] 字符（即排除纯 hex 串），或对材料段紧邻 sha256:/sha1:/commit 上下文的情形降档；补两条边界用例（标记+40 hex 不命中、标记+真 base64 仍命中）。不建议单纯抬高长度下限——45+ 只挡住 SHA-1、挡不住 64 位的 SHA-256。

### GLM-02 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/run-protocol.ts:604-615` |
| 类别 | concurrency ｜ 层次 code |
| 置信度 | high |

**问题**：worker_lost 分支的存活复核只读 status.json 的 worker_pid：meta0 为 null（status 缺失或损坏）时 pid0=null → stillAlive=false → 直接抹。而 interpretStatus 的情形 A 在「无 status 且无 fallbackPid」时是**假定失联**（status.ts:172-175 明写「连 pid 都不知道：只能判失联」），没有任何存活证据；④ 清扫对同状态判 unknown 跳过（retention.ts:96-99）。作用域内现成的 fallbackPid（worker.pid 文件，interpretStatus 自己用的同一来源，run-protocol.ts:542-547）未被复用。结果：status.json 与 worker.pid 同时读不到而 worker 实际在跑（两个独立文件故障叠加）时，② 会在其运行中整删凭据副本——正是 CODEX-01 要防的「副本在用却被抹、该侧莫名鉴权失败」。可达性极窄，但这是不可逆动作准入判据上仅存的不同源点，注释里「与 ④ 清扫同源」的说法在这一档不成立。

**依据**：src/trivium/run-protocol.ts:592-615（meta0 现读、pid0 取自 meta0、stillAlive 计算）、:542-547（fallbackPid 仅循环前读一次）；src/trivium/status.ts:166-179（情形 A 的无证据失联判定）；src/trivium/retention.ts:94-103（④ 对 status 读不到一律 unknown 跳过）。

**建议**：pid0 为 null 时退回 fallbackPid 复核；两者都拿不到时不做不可逆抹除，报错附一句与 ④ 同款的「留给会话启动清扫/人工检查」，让「未知」在两处都归入不抹档。
