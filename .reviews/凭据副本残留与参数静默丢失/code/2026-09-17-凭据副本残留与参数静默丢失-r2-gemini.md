## 总判断

最危险的一条：waitRun 在 heartbeat_stale 下将状态标记为 failed 并承诺将活进程留给清扫，但 retention 清扫仅对非终态检查 processAlive，导致启动清扫会直接抹除仍存活工作进程的凭据副本。
此外，超大日志跳过仅记告警却返回 ok:true 并落盘哨兵，导致凭据残留且被永久阻断清扫重试；zcode 载体删除前的 exists 检查存在权限异常下的静默放行漏洞；正则对账与 JSON 键名匹配存在遗漏形态。补丁只扫新增行设计站得住脚，但上述并发与安全状态漏洞需修订。

**结论**：`request-changes`

### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/retention.ts:76` |
| 类别 | concurrency ｜ 层次 code |
| 置信度 | high |

**问题**：worker_lost 复核存活的判据与会话启动清扫未真正同源。waitRun 在 heartbeat_stale 判定 worker_lost 时将状态落盘为 phase='failed'（isTerminal 成立），复核进程仍存活则跳过抹除并提示留给清扫；然而 retention.ts 的 pruneRunDirs 仅在 !isTerminal 时才调用 processAlive，导致对已置 failed 的目录跳过存活检查直接抹除，从而将正在运行或暂停的子进程凭据副本提前抹除。此外 run-protocol.ts:605 仅从 meta0 取 pid，缺少 fallbackPid 回落。

**依据**：核对 src/trivium/run-protocol.ts:582-615 与 src/trivium/retention.ts:76-103、src/trivium/status.ts:136-137 及 test/integration/gate-loop.test.ts:635-671。

**建议**：在 retention.ts 中只要 status.worker_pid 存在，即使 phase 为终态（特别是 failed）也必须复核 processAlive，存活则跳过抹除；同时在 run-protocol.ts:605 增加对 fallbackPid 的回落检查。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/scrub.ts:240` |
| 类别 | security ｜ 层次 code |
| 置信度 | high |

**问题**：超大日志跳过仅记告警导致凭据残留却报 ok，且哨兵 ok:true 导致后续清扫彻底放弃重试。redactLogs 遇到超过 32MB 的日志文件时仅向 warnings 推送跳过信息，未脱敏日志留在盘上，但整个 scrubSideDir 仍返回 ok:true 并写入哨兵。这导致 retention.ts 认为 already-scrubbed 而永久跳过，敏感凭据无法被后续会话清理。同理 scanAndRemoveSecrets 中 readdir/readFile 失败仅记 warning 也存在相同残留隐患。

**依据**：核对 src/trivium/scrub.ts:166-169、src/trivium/scrub.ts:193-195、src/trivium/scrub.ts:239-247、src/trivium/scrub.ts:267-269 及 src/trivium/retention.ts:106。

**建议**：对编排器日志等关键目标跳过脱敏时不得判定 ok:true，或在哨兵中记录未完成状态，使后续清扫流程保持重试能力。

**问题**：scrubZcodeHome 中使用 if (await exists(carrier)) 门禁，当遭遇权限限制或损坏软链导致 fs.access 抛错时，exists() 返回 false，使得 fs.rm 不被执行且未向 errors 记录错误，导致载体未删除却报告 ok:true。
