### 1.1 EV-239：闸门对命令通道命中不看类别

作废判定在代码里有三个派生点，**只有闸门那一处不看类别**：

| 派生点 | 位置 | 口径 |
| :--- | :--- | :--- |
| 守卫侧级判定 | `guard.ts:396-427`（逐条命令分档）、`:480-487`（`peerArtifactRead` / `peerCommandHits`） | 只有作废类（`peer-artifact` / `peer-run-output`）命中才计入；告警档进 `notedCategories` |
| run.json 共同阻断运行期三态 | `review.ts:127` `jointCheckRunState`，读守卫的侧级判定 | 同上 |

### 1.2 EV-238：agy 探活超时被报成「请先交互登录」

- `adapters/agy.ts:240-272` `authProbe`：用请求组合的模型发「只回复 OK」，外层超时 120 s（`:260`），内层 `--print-timeout` 取外层减 20 s（`:118-119`）。

## 2. 做法

### 2.1 EV-239：一个作废谓词，守卫与闸门同一次调用

在 `freeze.ts` 的 `isVoidingCategory`（`:166`）旁新增三个导出（AGY-02）：

```ts
/** 一组类别里有没有作废类（守卫逐条命令分档用：那里手上是裸类别数组） */
export function categoriesVoid(cats: readonly DenyCategory[]): boolean;

/** 一组带类命中里有没有作废类 */
export function hitsVoid(hits: readonly { category: DenyCategory }[]): boolean; // = categoriesVoid(hits.map(h => h.category))

/**
 * 一侧的两条泄漏通道记录是否判该侧作废——形状与 run.json `guard.peer_leak_via_path/command` 的单侧值相同。
 * 路径通道：只看 hits，缺 hits 按无作废（旧口径）。
 * 命令通道：有 hits 按 hitsVoid(hits)；缺 hits 的旧记录退回 hit === true（旧口径）。
 */
export function leakRecordVoids(rec: {
  path?: { hits?: readonly { category: DenyCategory }[] };
  command?: { hit: boolean; hits?: readonly { category: DenyCategory }[] };
}): boolean;
```

- **守卫**：`guard.ts:416` 逐条命令的 `typed.some((c) => isVoidingCategory(c))` 改调 `categoriesVoid(typed)`；侧级 `peerArtifactRead`（`:485`）改为
  `leakRecordVoids({ path: { hits: typedHits }, command: { hit: cmdTypedHits.length > 0, hits: cmdTypedHits } })`。与现行 `peerHits.length > 0 || cmdVoiding.hits.length > 0` 等价（`peerHits` 是 `typedHits` 的作废子集，`cmdVoiding.hits` 非空当且仅当 `typedCommandHits` 含作废类），不改行为。
- **闸门**：`gate.ts:1430-1437` 的循环体改为 `leakRecordVoids({ path: viaPath 记录, command: viaCmd 记录 })`，删掉过时注释，写明这次漂移的来历（`f2bc7635` 写注释、`333e5a29` 加带类 `hits`、闸门没跟上）。
- 于是守卫的侧级判定与闸门的作废派生是**同一个函数**，前者喂内存里的命中，后者喂落盘的同形记录。
- **EV-225**（M12 批次 3）的重跑触发将调 `leakRecordVoids`，本批不接，只在注释里点名。
- `review.ts` 的 `peerLeakOf`（`:154`）是渲染层选「最重类别」，不是作废判定，本批不动。

### 2.2 旧记录与旧轮次（用户 D-5）

- 没有 `hits` 的命令通道旧记录照旧按 `hit` 作废，不追溯改判。
- 有 `hits` 的已归档轮次，若重新跑 `gate --check`，按新逻辑派生：之前被误判作废的一侧恢复有效，共同阻断会真的执行，理论上可能新报「两家同提 blocker 被驳回」。已审批的阶段不会再被闸门复查，所以统一按新逻辑、不加版本开关。写进主设计变更说明。

### 2.3 EV-238：失败分三档文案，判定不变

把失败文案抽成纯函数 `describeAgyAuthFailure(out, model)`（放 `adapters/agy.ts`，导出供单测），`authProbe` 只在 `!ok` 时调它。三档按优先级判：

1. **认证档**：stdout 或 stderr 匹配 `/please sign in/i`。文案：「探活失败：agy 提示未登录（模型 X，Ns）。请交互运行一次 `agy` 完成登录后重试」+ stderr 摘要。**优先于超时档**：出现未登录特征时，不论是否超时都报未登录。
   - 特征只用仓库里已存的原始样本（`REPORT_2026-09-24_m10b_driver_entry_probe.md:45`，空 HOME 下 `agy models` 的原话 `Please sign in to view available models…`）。**不凭猜测扩词**（AGY-01 建议①只部分采纳）：解析厂商 CLI 输出的样本必须取原始输出（已知坑），`auth`、`login` 一类宽词还会命中正常 stderr；未识别特征的未登录由下面两档的登录指引兜住。
2. **超时档**：`timedOut || printTimeoutWarned`（GLM-02，与上位计划一致）。再按**有无交互证据**分两层（AGY-01）：
   - **有交互证据**——`printTimeoutWarned`、`parsed.status === 'SUCCESS'`、`parsed.conversationId` 非空，任一成立：「探活超时（Ns，模型 X）：agy 已开始应答但没答完，多半是模型侧响应慢，可稍后重试，不必重新登录」+（`printTimeoutWarned` 时）「agy 自报 print timeout」+ stderr 摘要。Z1 落这一层。
   - **无交互证据**——以上都不成立：「探活超时（Ns，模型 X），且没有收到任何应答：可能是在等交互登录，请交互运行一次 `agy` 确认；已登录的话，也可能是网络或服务端无响应」+ stderr 摘要。
3. **其他档**：以上都不是（status 非 SUCCESS、未超时、无 print timeout、无未登录特征）。文案：「探活失败（status=…，模型 X，Ns）：原因未识别。若近期未登录过，请交互运行一次 `agy`；否则请看 stderr 摘要」+ stderr 摘要。

- 三档都点名探活所用的模型（与 `:257` 同一条取值链：`combination?.model ?? 探针模型首项`，都没有时写「缺省」）与耗时。
- **未识别特征的未登录落在哪里**（GLM-01）：快速失败的落其他档；挂起到外层超时的落超时档「无交互证据」一层。两处文案都给登录指引，后者以它打头。
- **不做**：不因打印超时而改动 `ok` 的判定（GLM-03）；不改 120 s 外层超时；不自动重试。**现状角落如实记**：内层 print timeout 触发、agy 在外层超时前带部分输出退出且 status 仍为 SUCCESS 时，`ok` 为真、探活判通过——status=SUCCESS 说明服务端已开始回应，本批接受这一现状，不写进主设计作为「部分输出不算已认证」的承诺。
- 不取新样本：本命令约定 Driver 不得自行调用 agy。若用户愿意在终端零配额跑一次空 HOME 的 `agy -p`，原话可补成夹具，另记。
