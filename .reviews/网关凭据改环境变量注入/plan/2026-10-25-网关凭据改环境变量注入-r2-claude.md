## 一、改法

### 1.1 唯一的注入函数（`claude-route.ts`）

新增并导出：

```ts
/**
 * claude 子进程的环境补丁（EV-256）：先清、后注，次序固定。
 * 先展开 route.env（claudeRouteEnv 的清除补丁：父进程 ANTHROPIC_* 等置 undefined），
 * 再展开 route.settingsEnv（extractSettingsEnv 提取出的网关键）——同名键网关值胜出；
 * 父进程里有、settings.json 里没有的键仍被清除。未开 settings_env_source 或 env 段为空时
 * settingsEnv 是 {}，结果与 route.env 逐键相同。
 */
export function claudeInvocationEnv(route: Pick<ClaudeRoute, 'env' | 'settingsEnv'>): Record<string, string | undefined> {
  return { ...route.env, ...route.settingsEnv };
}
```

选「调用时组合」而不是把网关键直接并进 `route.env`：`route.env` 还被 `--version` / `--help` / 预检版本核对用（0.1 末段），并进去会让这些本不带网关的调用也带上凭据——扩大暴露面、也破坏「零变化」。两条执行出口各调一次本函数，它是网关键进入子进程的**唯一**入口。

### 1.2 两条执行出口改走它

- `invokeClaude`（`adapters/claude.ts:578-586`）：`env: opts.route?.env` → `env: opts.route ? claudeInvocationEnv(opts.route) : undefined`（无 route 时保持现状：不给补丁）；argv 改为 `buildClaudeArgs(opts)`，不再传 `settingsEnv`。
- 探针 `routeInvocation`（`probes/claude.ts:90`）：`env: ctx?.route.env ?? claudeRouteEnv(null)` → `env: ctx ? claudeInvocationEnv(ctx.route) : claudeRouteEnv(null)`。`execArgv` 与 verbose 阴性对照都从这里取 env，所以探针侧只改这一处。

### 1.3 argv 构造器去掉网关通道（让「某一臂仍内联」在结构上写不出来）

- 删 `mergeSettingsEnv`（`adapters/claude.ts:103-131`）与 `ClaudeInvokeOptions.settingsEnv`（`:86-91`）；`buildClaudeArgs` 的 `Pick` 去掉 `'settingsEnv'`，`--settings` 的值恢复为 `opts.settingsJson` 原样（即 1.2.0 之前的配方）。
- `probeArgs` 删 `settingsEnv` 入参（`probes/claude.ts:156-157`、`:194`），`--settings` 取 `opts.settings` 原样。
- `projectMemoryArmArgs(prompt)`、`verboseNegativeControlArgs()` 去掉 `settingsEnv` 形参；`execProbe`（`:773-774`）、记忆两臂（`:1698`）、阴性对照（`:884`）三处调用点相应删实参。
- 删掉之后，`src/` 里没有任何把网关键写进 argv 的代码路径；`tsc` 会拦住给这几个函数再传 `settingsEnv` 的写法。`probes/claude.ts:73` 的 `mergeSettingsEnv` import 随之删除（`scrubGatewayEnv` 保留）。

`permissions.deny` 等非凭据载荷的 `--settings` 内联不变：审查调用与目录臂照旧传 `settingsJson`，探针的路径 deny 臂照旧传 `settings`。

### 1.4 文案与注释同步

- `doctor.ts:1202` 的注记：`网关 env 经 --settings 内联注入（N 键，值不落留痕）…` → `网关 env 经子进程环境变量注入（N 键；不进命令行，值不落留痕）：受限模式在第三方网关下保住鉴权`。
- `ClaudeRoute.settingsEnv` 的注释（`claude-route.ts:21-27`）、`resolveClaudeRoute` 段注释（`:119-122`）、`types.ts:1097` 的配置项注释、`probeArgs` / `buildClaudeArgs` 里「网关 env 与 deny 规则合并进同一份载荷」两行注释、`verboseNegativeControlArgs` 的 1.2.2 注释，改成新通道并点名 EV-256。

### 1.5 一处语义变化要如实登记：profile 路线 + 网关同开

`settings_env_source` 不看路线，profile 路线也会读 settings.json。修复前网关键在 `--settings` 里，由 claude 进程启动后套用；修复后在子进程环境里，而 profile 路线的子进程是包装器（`cld --profile X`），包装器 source profile 文件的 `export ANTHROPIC_*` 会**覆盖**同名注入值——同名键的胜出方从「网关」变成「profile」。

**部分同名的混配形态（GLM-03）**：profile 文件只 export 网关键集的一个子集时（例如只有 `ANTHROPIC_AUTH_TOKEN`、没有 `ANTHROPIC_BASE_URL`），未被覆盖的键仍取网关值，子进程会拿到「网关端点 + profile 令牌」一类混配的鉴权面，典型失败是 401 且没有先验线索可归因。包装器行为属外部实现，这一段是结构推理、**未实测**。

处置：**不改代码，只登记**。理由：该开关为 Windows 上 CC Switch 的 native 路线而设（部署手册 §1a），profile 路线自带鉴权，两者同开没有已知使用者；修复后「显式选的 profile 胜出」也更符合 profile 的语义。登记进主设计变更记录与部署手册 §1a 的网关段，写全两种形态（同名键 profile 胜出；部分同名时端点与令牌混配可致 401）与排障第一步（先关 `settings_env_source`，或改用键完整的 profile），不加用例（无真实形态可验，不臆造）。
