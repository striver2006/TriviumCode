### CODEX-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3 D6、§4 R3` |
| 类别 | performance ｜ 层次 plan |
| 置信度 | medium |

**问题**：D6 断言「均在 Bash 缺省 120 s 工具超时之内」，但只核算了首检判不了（约 20 s）与宽限期满判不了不升级（约 40 s）两条路。改后新拉长的恰是 escalate 路：宽限期满判「同一进程」→ SIGKILL → 新增的 killWaitMs=ORPHAN_KILL_CONFIRM_MS 等待（`waitGone` 的轮询与期满最后一次各是一次 ≤10 s 的 `ps`，即本段最坏 +20 s，今天这段是 `killWaitMs: 0` 不等的）→ `t.escalated` 仍先跑 `terminateRecordedCliGroups`（每个 CLI 组一次判定 `judgeCliGroup` 即一次 `ps -p … lstart=` ≤10 s，组长不在时还串一次 `ps -axo` ≤10 s；2 s 宽限与 1 s killWait 的每轮 `isGone` 在 ps 超时下各再摊 ≤10 s，收尾后另有 `processGroupMemberCount`）。这些格在「ps 间歇超时」的混合形态下叠乘，最坏总账接近乃至可能越过 120 s——而 D3.4 第三形态（SIGKILL 后仍是同一进程 ⇒ 69）正是这条最贵路上抛出的。最坏耗时没入账，编码阶段若实测打脸就是返工。

**依据**：读 `src/trivium/util/exec.ts`：`/bin/ps -p 〈pid〉 -o lstart=` 与 `ps -axo` 的 timeoutMs 均为 10_000（:542-:543、:672）；`terminateProcessGroup` 的 `waitGone` 每轮与期满最后一次各调一次 `isGone`（:765-:783），故 5 s 的等待窗在 ps 超时下实际 ≤20 s。读 `src/trivium/run-protocol.ts` :817-:838：`terminateRecordedCliGroups` 的 `isGone` 经 `judgeCliGroup` 每次判定取 `ps -p`、组长不在时再取 `ps -axo`（`src/trivium/status.ts` 的 `judgeCliGroup` 实现确认两路串行）；worker 的 CLI 宽限链常量 WORKER_TREE_GRACE_MS=2000 / WORKER_TREE_KILL_WAIT_MS=1000（:55-:59）。计划 D6 只给了 20 s 与 40 s 两个数，未列 escalate+CLI 链的组合账。

**建议**：在 D6 把 escalate 路的分格账补全（首检、宽限、SIGKILL 确认、CLI 链各段的最坏 ps 超时叠加），并在 §5.2 探针/跨进程矩阵里点名加一格「SIGKILL 之后确认窗内 ps 超时」与含 CLI 记录的超时格，实测读数进报告；若逼近 120 s，R3 里给出结论口径（例如提示调用方加大超时或说明 69 的播报仍会部分落盘）。

### CODEX-02 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3 D3 第 3 点、§4 残余清单` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：「SIGKILL 被扣下时不按记录结束 CLI——worker 若还活着，它的 SIGTERM 处理器正在做这件事」这句论据对它要论证的那格不成立：能走到「宽限期满仍判不了、扣下 SIGKILL」的 worker，恰恰是收到 SIGTERM 后没在 5 s 内退出的形态——处理器要么没装/被忽略（探针 G2 构造即「忽略 SIGTERM」），要么事件循环被堵住跑不到（`cancelLostWorker` 文档块 :1600 自己写明「事件循环被堵住时处理器跑不到」）。该格的真实后果是：审查员 CLI 进程组既没被 worker 转发终止、也没被按记录结束，继续白跑到重试或手工出路为止；而 §4 的 R1/R2 都没登记这个泄漏面。决策本身（不越过判不了的进程）守用户决策、站得住，但论据失实会在代码双审被抓，残余没登记会让「如实保留清单」少一项。

**依据**：读 `src/trivium/run-protocol.ts` :1600-:1610（cancelLostWorker 文档块：处理器在事件循环堵住时跑不到）、:808-:816（terminateRecordedCliGroups 文档块：升级到 SIGKILL 时处理器跑不到、才由按记录结束兜底——反过来说明「处理器正在做」在 escalate 前夜不成立）；探针 §2 G2 格的构造就是「忽略 SIGTERM」。计划 D1 第 3 步使 escalate 不发生（`t.escalated` 为假），D3 第 3 点据此跳过 `terminateRecordedCliGroups`。

**建议**：把这句论据改成诚实形态（「宁可让 CLI 多活一轮，等重试时身份可判再收拾」），并在 §4 增补一条残余：扣下 SIGKILL 的格中厂商 CLI 不被动、重试语义段里说明它们由下一次成功升级或手工出路收掉；正文（D3.4 第二种形态的话术）要不要向用户提示 CLI 仍在跑，也一并定调。
