## 3. 修法

### D1 `terminateProcessGroup` 认得「判不了」（`util/exec.ts` :718～:783）

- `TerminateOptions.isGone` 的类型放宽为 `() => boolean | 'unverifiable' | Promise<boolean | 'unverifiable'>`。文档块写明：返回 `'unverifiable'` 表示「这一次判不了它是否已退出」——只有按 pid + 启动时刻判的调用方会给；按句柄判的调用方与 `terminateRecordedCliGroups` 只给布尔，**行为逐字不变**（`'unverifiable'` 从不出现，下列每一条在布尔输入下都退化为原逻辑）。
- 新增可选 `onTerm?: () => void`：**发 SIGTERM 之前**回调一次（与既有 `onEscalate` 对称）。
- 返回值加可选字段 `unverifiable?: true`：只在 `gone: false` 且**最后一次判定**为 `'unverifiable'` 时出现。返回类型具名为 `TerminateResult`（`CancelOptions.terminateWorker` 的签名随之改引用它，字段是加法，既有注入不受影响）。
- 流程（`last` = 最近一次判定）：
  1. 首检：`gone` ⇒ 返回已退出（原 :775）；**`unverifiable` ⇒ 一个信号都不发，返回 `{ gone: false, escalated: false, signals: [], unverifiable: true }`**；
  2. `onTerm?.()`、发 SIGTERM；`waitGone(graceMs)`：`unverifiable` **不算已退出**，继续轮询；期满再判最后一次；
  3. 已退出 ⇒ 返回；**期满最后一次仍 `unverifiable` ⇒ 不升级 SIGKILL**，返回 `{ gone: false, escalated: false, signals: ['SIGTERM'], unverifiable: true }`（不向身份判不了的进程发 SIGKILL，用户决策）；
  4. 期满最后一次判「未退出」（仍是同一进程）⇒ `onEscalate`、发 SIGKILL；`killWaitMs <= 0` 只判一次，否则 `waitGone(killWaitMs)`；未确认时按 `last` 带上 `unverifiable`。
- 期中出现 `unverifiable` 而之后恢复（`ps` 好转）不影响：只看每一步的最后一次判定。

### D2 `workerGoneForCancel` 改由三态判（run-protocol.ts :753～:767）

```ts
export async function workerGoneForCancel(pid: number, rec: RecordedStart): Promise<boolean | 'unverifiable'> {
  const p = await processMatchesRecord(pid, rec);
  if (p.identity === 'unverifiable') return 'unverifiable';
  return !p.alive || !p.sameProcess;
}
```

`same` ⇒ false、`different`（不在，或取到了且不符 = pid 已被复用）⇒ true，与改前逐字相同；只把 `unverifiable` 从「true」分出来。文档块删去「有意不读 identity」与 EV-176 指向，改写为三态语义与 D1 的配合。既有断言（`start-canonical.test.ts` U8、`run-protocol.test.ts` :695～:697）只覆盖 `same` / `different`，不变。

### D3 `cancelRun` 主路径（run-protocol.ts :1799～:1828）

1. :1808 的 `step('向工作进程组 N 发送 SIGTERM')` 挪进 `onTerm`：**只在确实要发 SIGTERM 时播报**（零信号格不再失实）。`onEscalate` 的 warn 不变。
2. `killWaitMs: 0` 改为 `killWaitMs: ORPHAN_KILL_CONFIRM_MS`（与 `cancelLostWorker`、`settleOrphanedStart` 同口径；撤回 EV-150 的「SIGKILL 之后刻意不等」，用户决策），:1812 的注释随之改。
3. `t.escalated` ⇒ 按记录结束 CLI **照做**（位置不动，在未确认判定之前）：升级 SIGKILL 意味着 worker 的处理器跑不到，CLI 只能按记录结束；与 `cancelLostWorker` 的「没确认退出也照做」（EV-146 D4）同口径。SIGKILL 被扣下（D1 第 3 步）时**不**按记录结束 CLI——worker 若还活着，它的 SIGTERM 处理器正在做这件事；判不了时不越过它。

   - 发过信号、最后一次判不了：「已向工作进程组 N 发送 〈信号序列〉，〈宽限 5 s 期满时 / SIGKILL 之后 5 s 内〉仍取不到它的启动时刻、判不了它是否已退出〈；不升级 SIGKILL（不向身份判不了的进程发）〉：本次不收尾——status.json、主题锁、闸门、归档与凭据副本都没动〈；按记录结束的审查员 CLI 见上方输出〉。请稍后重试 …… 手工出路……」；

5. `t.gone` 为真 ⇒ 其后一切照旧（:1842 起逐字不动）。「已不存在」格（:1823～:1828）不动。

**重试语义**（给正文与文档用）：抛 69 之后 status.json 仍为 running、锁与闸门都在。再跑 `--cancel`：工作进程已退出 ⇒ 入口判「已不存在」⇒ c 格收尾为 cancelled（与今天手工结束之后再 `--cancel` 同路）；仍在且 `ps` 恢复 ⇒ 再走一遍 SIGTERM → SIGKILL；仍取不到 ⇒ 入口 69（EV-175）。工作进程若在两次 `--cancel` 之间自己退出，它持有的运行锁变成遗留锁（持有者 pid 不在）——下一次 `--start` 按 `pid_gone` 回收，与 worker 被强杀后的既有路径相同；闸门停在 running 直到那一次 `--cancel`，与今天「worker 被强杀后、`--cancel` 之前」同形。

### D6 `--cancel` 耗时

## 7. 风险

- **把「判不了」判成「已退出」的代价**（改前）：活锁被释放、同主题可双跑、凭据与归档漏收（探针 Z1 / G1 / G2 / G3 / K1）。

- **`terminateProcessGroup` 是共享函数**：D1 只在 `isGone` 返回 `'unverifiable'` 时改变行为，四个布尔调用方逐字不变——T6 回归与既有 `orphan-worker` / `cli-group-record` / `shutdownTrackedTrees` 用例守住；变异 M1～M4 只动三态分支。
