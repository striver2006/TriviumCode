1. **run 契约版本**。上位计划 §3.2「留痕」一行写「run.v2 原地扩一个可选的 `attempts` 数组」。**现行写形是 `trivium.run.v3`**（`meta.ts:425` 写 `schema: 'trivium.run.v3'`；v1 / v2 只按历史契约读，`meta.ts:528-529`、`schemas.ts:245`）。新运行只会写 v3，带 `attempts` 的记录不可能是 v2。所以 `attempts` 加在 **`run.v3.json` 的 `$defs.critic`**（逐侧节点，`additionalProperties: true`），`run.v2.json` 不动——与「原地扩可选字段、不升契约版本」的原意一致，只是落在当前写形上。

## 1. 问题与现状

### 1.1 承诺与实现脱节

- 设计 12.1 与 PRD AC-25 原先承诺「该侧作废重跑一次（BRIEF 追加更醒目的禁读提示），二次命中 `failed(peer_leak)`；strict 中止」，从未实现。v1.3.129 / v1.4.19 起移出 AC-25、另立 EV-225；v1.3.130 / v1.4.20 把现行行为定稿为「不自动重跑、strict 下不因作废整次中止」。
- 现行行为（源码核实）：
  - `runner.ts:102-195` `runOneSide` 只认瞬时故障重试；作废判定根本不在 runner 里。
  - 作废判定在两侧都跑完之后：`review.ts:1562` `judgeRun` → `guard.ts:653` → 逐侧 `judgeSide`（`guard.ts:228`），侧级作废位 `peerArtifactRead` 由 `leakRecordVoids` 给出（`guard.ts:492`）。
  - 作废侧照常落盘、意见仍须逐条裁决；`decideMode`（`runner.ts:316`）只看失败 / 超时，作废不进它的判据，所以 strict 下照样 `success`、退 0。
  - 闸门 `gate.ts:1443-1450` 用 `leakRecordVoids` 从 run.json 的 `guard.peer_leak_via_path` / `peer_leak_via_command` 派生 `voidedSides`，只把作废侧排出共同阻断。
  - 全仓没有写 `failed(peer_leak)` 的地方（`parse.ts:190` 的 `peer_leak` 只是 front-matter 键名清单）。
- 钉住现行行为的用例：`test/integration/fault-injection.test.ts` 的「AC-25 三审」**8 格**（`:906-1100`：归档通道 3 格、运行根通道 3 格、两侧作废 1 格、Driver 轮换 1 格，经 `assertStrictRunUnaffected` 断言 strict 下退 0、`success`、`review_mode: full`、各侧 `status: ok`），以及两侧分档组里三格作废类用例（`:553`、`:637`、`:663`，断言 `peer_artifact_read: true`）。

### 1.2 为什么不能「两侧跑完再整轮重跑那一侧」

用户 D-7 定的是「单侧重拉期间另一侧不受影响」。若沿用「两侧都跑完 → judgeRun → 再拉作废侧」，没泄漏的那一侧要白等作废侧的第二次，且第二次的漂移复算、落盘时机都要另起一套。所以作废判定要**挪到该侧刚跑完的那一刻**、在该侧自己的 promise 里决定重跑，另一侧的 promise 完全不感知。

## 3. 做法

### 3.1 守卫：抽出单侧泄漏判定，与 `judgeRun` 共用同一套入参装配（`guard.ts`）

- 新增导出 `makeSideLeakJudge(input)`（async，一次性算好 `projectRoots` 的 realpath 别名），返回同步函数 `(critic, result) => SideLeakVerdict | null`：
  - 内部**直接调 `judgeSide`**（`review` 传 `null`、`degraded` 传 `[]`），取它的 `peerArtifactRead`、`typedHits`、`typedCommandHits`。泄漏判定只读 `result.read_paths` / `search_hit_paths` / `command_texts` 与 `req.deny_paths`（`guard.ts:338-342`、`:396`），不依赖解析结果，所以「先判泄漏、后解析」与 `judgeRun` 对同一份结果给出同一结论。
  - `status` 为 `failed` / `timeout` 时返回 `null`，与 `judgeRun` 跳过失败侧（`guard.ts:710`）同口径。
- `judgeRun` 里给 `judgeSide` 拼 opts 的那段（`guard.ts:686-731`：`projectRoots`、`triviumDir`、`runRoot`、`capability`）抽成一个内部函数，`makeSideLeakJudge` 与 `judgeRun` 都调它——**入参装配只有一份**，不会出现「重跑判据按 A 根算、终判按 B 根算」。
- 返回值形状：`{ voided: boolean; path: { hit, hits }; command: { hit, commands, hits } }`，后两者与 run.json `guard.peer_leak_via_path` / `peer_leak_via_command` 的单侧值**同形**（`hit` 取「扫到了东西」，与 `review.ts:1843`、`:1879` 同口径）。`voided` 就是 `judgeSide` 的 `peerArtifactRead`，即 `leakRecordVoids` 的结果——**守卫重跑判据、守卫终判、闸门三处读的是同一个谓词**。

### 3.2 runner：该侧跑完立刻判，作废则在该侧 promise 内重拉一次（`runner.ts`）

`RunnerInput` 加三个可选钩子（同步路径与 worker 路径都由 `executeRun` 传入）：

- `judgeLeak?(critic, result): SideLeakVerdict | null` —— §3.1 的单侧判定；
- `stashVoided?(critic, attemptNo): Promise<string | null>` —— 把这次的原始输出移出该侧目录（§3.4），返回新位置（运行目录相对），失败返回 null；
- `voidRerunBanner?(critic, verdict): string` —— 生成 §3.3 的点名段。

`runOneSide` 的改动：

1. **瞬时重试改用独立计数** `transientUsed`：原判据 `attempts > maxTransientRetries`（`runner.ts:168`）改成 `transientUsed >= maxTransientRetries`，重试时 `transientUsed++`。没有作废重跑时 `transientUsed === attempts - 1`，与原判据逐值等价；有作废重跑时，瞬时重试额度在整侧内共用、不因重跑而重置。
2. 每次尝试记一条内存记录 `{ n, started_at, duration_s, status, fail_reason }`（`status`、`fail_reason` 取适配器结果，见 §3.6 的分层）。
3. 结果为 `ok` 时调 `judgeLeak`：
   - 判定为 `null` 或 `voided: false` → 照原样收口返回（该条记录补 `voided: false` 与两通道明细）。
   - `voided: true` 且本侧作废重跑次数为 0 → 该条记录补 `voided: true` 与明细；`stashVoided` 挪走输出、记 `output_dir`；`emitProgress` 报 `{ state: 'running', attempt, note: '上一次尝试读到对端产物，作废重跑中', voidRerun: true }`；`req = { ...req, brief_text: banner + '\n\n---\n\n' + req.brief_text }`；`continue`。请求里的 `timeout_s` 不变——适配器每次 `run` 都按它重新计时，**重跑天然拿到完整单侧超时**。
   - `voided: true` 且已重跑过 1 次 → 该条记录同上；把**侧级结果**改成 `status: 'failed'`、`fail_reason: 'peer_leak：重跑后仍读到对端产物（N 处）'`，**不进瞬时重试判定**，直接收口返回。
   - `judgeLeak` 抛异常 → `warn` 一条、按「未判出作废」收口，不重跑；终判仍由 `judgeRun` 做（§3.6），该侧若确实作废就落回现行的「作废但 ok」处置。这是唯一能让旧处置出现在新运行里的出口，选它而不选「判失败」是因为判定器异常属编程错误，不该把一次真实审查判成失败；告警会进 run 的 warnings。
4. `RunnerOutput` 加 `attemptLog: Partial<Record<CriticId, AttemptRecord[]>>`；`runBothSides` 不改并行结构（`Promise.allSettled` 照旧），重拉完全发生在该侧自己的 `runOneSide` 里，**另一侧的 promise 不读、不等、不改任何共享状态**（唯一共享的是 `status.json` 的逐侧补丁，`patchStatus` 按运行目录串行、各改各的键）。
5. 常量 `MAX_VOID_RERUNS = 1` 导出，供测试与文案引用。
6. **重跑之后的终态进展事件显式带 note**（计划双审 AGY-02）：worker 回写只在 `p.note !== undefined` 时改 note（`run-protocol.ts:1198`），而现行成功收口的事件（`runner.ts:165`）不带 note。发生过作废重跑的一侧，成功收口时传 `note: null`，失败 / 超时收口照旧传 `fail_reason`——`status.json` 不会残留「作废重跑中」。`void_rerun` 标记不随之清掉（§3.5）。

### 3.3 重跑侧 BRIEF 的点名段（`brief.ts`）

新增 `renderVoidRerunBanner(verdict, ctx)`，导出段首标题常量 `VOID_RERUN_BANNER_HEADING`。段落**插在原任务书之前**，原任务书逐字不变（拼接方式见 §3.2 第 3 步）；瞬时重试的提示仍追加在末尾（`runner.ts:184`），两者不冲突。

内容：

- 一句说明：上一次的工具轨迹里出现了对另一位审查员产出的读取，那次结论已作废、不会交给 Driver；这是同一份任务书的重跑，**只有这一次**，再碰到下列任何一项本侧直接判失败。
- 「上一次碰到的」逐条列，每条是**位置 + 类别标签**（复用 `DENY_CATEGORY_LABEL`），命令通道的条目前面加「经命令 `〈程序名〉`」；两条通道合并按位置去重，最多 10 条、其余写「另有 N 条」。
- 重申：这些位置与第 8 段 8.1 同属禁读；上一次尝试的原始输出已移出你的运行目录，同样禁读；不要为了「核对」再打开任何一项。

**点名内容本身不成为新的泄漏面**——这是焦点里点名要看的，具体约束三条：

1. **不回显命令参数。** 命令通道的命中只取两样：它碰到的那个路径（`typedCommandHits[].path`，再经下一条收敛），与命令首个词的末段作程序名（字符集 `[A-Za-z0-9._-]`、至多 32 字符，不合就省略）。命令的其余文本一个字都不进点名段。理由见 §0 第 2 条。
2. **位置收敛到禁读条目或侧目录层级。** 落在运行根下的命中，只显示到 `〈运行根〉/〈项目槽〉/〈runId〉/〈第三段〉/` 这一层（第三段是侧名时写成「运行目录里 X 侧的本轮输出」，是 `voided` 时写成「运行目录里被作废的上一次输出」）；落在项目内的命中，显示 `req.deny_paths` 里罩住它的那个条目（命中本身就是条目时即它自己）。于是点名段里出现的每一个位置，都已经以「条目」或「条目所在目录」的形态出现在原任务书第 8 段里——**点名段不引入任何原任务书没有的信息**，只是告诉它「你碰的是其中这几个」。
3. 位置字符串过一遍 `redactSecrets`（路径里理论上可以带凭据形态的片段），超长截断到 200 字符。

### 3.4 首次原始输出的去处：运行目录里、但不在该侧子树里（`review.ts` + `run-files.ts`）

- 挪到 `〈运行目录〉/voided/〈侧〉/attempt-〈n〉/`：**先递归创建父目录 `voided/〈侧〉/`**（计划双审 AGY-01：`rename` 的目标父目录首次必然不存在），再把 `〈运行目录〉/〈侧〉/out` 整个改名过去。常量 `VOIDED_ATTEMPTS_DIR = 'voided'` 放 `run-files.ts`，与 `RUN_DIR_FILES` 并列但**刻意不进 `RUN_DIR_FILE_NAMES`**，注释写明理由（它是对端也是本侧都不得读的被污染输出，进了清单就会被判成己方材料）。
- 挪动钩子写在 `review.ts`（`out_dir` 的拼接点 `review.ts:1141` 也在这里），目录名只经常量拼接，不写字面量——`run-files-parity` 对账测试只扫 `run-protocol.ts` / `status.ts` 的字面量拼接（`test/unit/run-files-parity.test.ts:38-41`），这里既不绕开它也不撞上它（计划双审 AGY-03）。
- **为什么不能留在 `〈侧〉/` 子树里**：`classifyDenyPath`（`freeze.ts:129-134`）对 `〈槽〉/〈runId〉/〈自己〉/…` 判 `own-run-material`，整个不算命中。首次输出是被污染的结论，若留在己方子树，重跑侧读一眼自己上一次的 `result.json` 就能把对端内容间接带回来，而且守卫看不见。挪到 `voided/` 之后第三段是 `voided`，不等于任何侧名、也不是运行目录层文件，按现行规则落 `peer-run-output`——**重跑侧去读它会被判作废**，正是我们要的；对端读它本来就是作废。
- 需要的两条护栏：`VOIDED_ATTEMPTS_DIR` 不得与任何已登记 Agent id 同名、不得进 `RUN_DIR_FILE_NAMES`（加单测；否则它会被判成己方材料）。
- **挪之前该次尝试的凭据抹除已经做完**：`runOneSide` 的顺序是 `adapter.run` → `scrubSideDir(force)`（`runner.ts:149`）→ 判泄漏 → 挪输出。载体（`codexhome/`、`home/`）在侧目录根，不在 `out/` 里，不随之挪走。
- 会话启动清扫（`scrubRunDir`，`scrub.ts:444`）现在只按侧名认子目录。补一段：对 `voided/〈侧〉/attempt-*/` 下的 `ORCHESTRATOR_LOG_FILES` 也跑一遍 `redactLogs`（只脱敏、不删），覆盖「首次尝试那次抹除失败」的情形。结果并进运行目录层的上报（`RunDirLayerScrub`），不新增哨兵。
- **改名失败的兜底**（计划双审 GLM-03）：`warn` 一条、`output_dir` 记 null；再对编排器自己算出的 `〈运行目录〉/〈侧〉/out` **这一个路径**尽力整删一次（只删这一个由 `out_dir` 派生的路径，不接受任何外部输入）；删也失败则再告警「首次输出可能残留在己方子树、守卫看不见」并进 run 的 warnings。无论哪种都**照样重跑**——不因挪不动就放弃重跑，那会让作废侧以污染结论收场。前提写实：三家适配器写进 `out/` 的都是固定文件名（`stdout.jsonl` / `stdout.json`、`trace.json`、`rollout.jsonl`，与 `scrub.ts:76` 的 `ORCHESTRATOR_LOG_FILES` 一致），桩是 `stub-stdout.json` / `stub-trace.json` / `result.json`，删不掉时重跑的同名输出也会覆盖它们，残留面只剩「删不掉又不同名」的文件。
- 归档只放最终那次的审查件：`executeRun` 只渲染 `results` 里的最终结果，现状即如此；首次输出不进 `_meta/`，只在运行目录，随运行目录的保留期一起删。

### 3.5 等待预算与进度（`status.ts`、`run-protocol.ts`、`cli.ts`、skill）

- `SideProgress` 加 `voidRerun?: true`；worker 的回写（`run-protocol.ts:1191-1200`）把它写成 `SideStatus.void_rerun = true`，**此后不再清掉**（该侧这一轮确实重跑过，预算要一直算进去）。缺席 = 没重跑或旧版写的。
- `budgetFor(cfg, stage, waitTimeoutS?, status?)` 加可选第四参：任一侧 `void_rerun` 为真时，`maxWaits += ceil(stageTimeoutS / waitTimeoutS)`。**只加一份**：各侧并行，最坏路径是单侧链条「1 次 + 瞬时重试 + 1 次作废重跑」，基础值已含前两段（`computeMaxWaits`，`status.ts:723`），作废重跑最多再长一个单侧超时；两侧同时重跑也只是这一段重叠，不叠加。
- `waitRun` 现在只在循环前算一次预算（`run-protocol.ts:1347`）。改成**每次返回前**按刚读到的 status 现算（终态与窗口用尽两个出口都改），`statusRun`（`run-protocol.ts:1549`）同样传 status。`--wait --json` 的 `max_waits` 因此会在决定重跑后变大。
- 进度文案：`renderProgress` 该侧行沿用 `note`（「上一次尝试读到对端产物，作废重跑中」）；`renderProgressBrief` 在该侧状态后加「（作废重跑）」。`--start` 返回的 `max_waits` 仍是初值。
- skill 文案（`skills-src/partials/review/body.md:171`）：「循环次数上限为返回的 `max_waits`」改为「以**最近一次** `--wait` 返回的 `max_waits` 为准（某侧作废重跑时编排器会追加一个单侧超时的份额；`--start` 给的是初值）」，并在「状态有变化时补一句」的列举里加「某侧进入作废重跑」。重新渲染各载体入口。

### 3.6 收尾、run.json 与闸门（`review.ts`、`types.ts`、`run.v3.json`、`gate.ts` 不改代码）

- `executeRun` 把 §3.1 的判定器与 §3.4 的挪动钩子、§3.3 的点名段生成器传给 `runBothSides`。
- **终判照旧由 `judgeRun` 对最终结果做**，写进 `guard.peer_leak_via_*`、`peer_artifact_read`、`joint_check`；闸门的 `voidedSides` 照旧读 `guard.peer_leak_via_*`。所以「闸门的作废侧只看最终尝试」**不需要改闸门代码**——它读的字段本来就只写最终尝试。为防将来有人让闸门去读 `attempts`，加一条闸门单测钉住：`attempts[0]` 作废、最终尝试干净时 `voidedSides` 为空。
- 二次命中的那一侧在 runner 里已是 `failed`，于是：`judgeRun` 跳过它（`guard.peer_leak_via_*` 无该侧的键，语义「没判过」——它确实不作为一侧结论参与本轮）；`decideMode` 把它记失败侧（strict → `abort`、退 75；`--allow-single` → `partial` + `degraded_reason`）；渲染循环走失败分支写 `_meta/review-〈侧〉-〈run〉.failed.json`（`review.ts:1669-1677`），不产审查文档。现有失败侧规则一条不改。
- 共同阻断与三态：`jointCheckRunState`（`review.ts:127`）的有效侧 = 判过且未作废且有结构化结论。重跑后干净的一侧重新计入有效侧；二次命中判失败的一侧不计入（与超时侧同处置）。闸门 `jointCheckState` 用同一分母，`reason` 在新运行里不会再出现 `voided`（作废侧要么重跑干净、要么失败），失败侧走现有的「有效侧不足」文案。
- **终判与重跑判据一致性自检**：重跑过的一侧，若 `judgeRun` 对它最终尝试的 `peerArtifactRead` 与 runner 记的最后一条 `voided` 不等（同一函数、同一输入，理论上不可达），记一条 warning 进 run 的 warnings，以终判为准。
- **run.json 逐侧 `attempts`**（`CriticRunMeta.attempts?`，`run.v3.json` `$defs.critic.properties.attempts`）：
  - **只在该侧发生过作废重跑时写**，内容是该侧这一轮的全部尝试（含瞬时重试）；没发生过就不写。理由：不泄漏时 run.json 逐字不变（回归的最强形态）；字段缺席的两种来源——旧记录、这一侧没有作废过——对读者处置相同（只有一次有效尝试），不需要分开。
  - 每条：`n`（≥1）、`started_at`、`duration_s`、`status`、`voided`、`peer_leak_via_path?` / `peer_leak_via_command?`（与 `guard` 单侧值同形，只在判过时写）、`output_dir?`（运行目录相对，只在挪过的那次写；挪失败为 `null`）、`fail_reason`。
  - **分层记法写死**（计划双审 GLM-04）：条目的 `status` 与 `fail_reason` **恒记适配器层结果**（`ok` / `failed` / `timeout`；二次命中那一条是 `status: ok`、`fail_reason` 为适配器给的值，通常 null），`voided` 记这一条的泄漏判定（`status` 非 `ok` 时为 `null`，表示没判）。**改判只发生在侧级**：`critics.〈侧〉.status: failed`、`fail_reason` 以 `peer_leak` 起头。于是「这一次跑成了但读了对端」与「这一侧因此判失败」分在两层，对账时各看各的。
  - schema：条目 `additionalProperties: false`，`voided` 与两通道明细的一致性（`voided === leakRecordVoids({path, command})`）由单测核，不进 schema。
  - 二次命中侧的 `duration_s` 等逐侧字段照旧取最终尝试。
- `_meta/brief-〈侧〉-〈run〉.rerun.md`：重跑时追加的点名段原文落盘并进保护集，与现有的 `.retry.md`（`review.ts:1655-1665`）同一做法——审计材料要与实际送审一致。
- `report.ts` 的 guard 旗标与 `meta.ts` 的运行摘要各加一项「作废重跑」（任一侧有 `attempts` 即亮），否则一轮「首次泄漏、重跑干净」的运行在报告里看不出发生过泄漏（`peer_artifact_read` 按最终尝试为假）。
- 守卫告警（`renderGuardWarnings` 或 `executeRun` 的 warnings 汇总处）加两句：「X 侧首次尝试读到对端产物，已作废并重跑一次（重跑干净）」与「X 侧重跑后仍读到对端产物，判失败（peer_leak）」。

### 3.7 旧记录与向后兼容

- 读：`attempts` 是 v3 逐侧节点上的可选键；`$defs.critic` 本就 `additionalProperties: true`，旧构建读到带 `attempts` 的新记录也不会被拒。新构建读没有 `attempts` 的旧记录：闸门、`status`、`report` 都不读 `attempts`（report 只判有无），行为不变。
