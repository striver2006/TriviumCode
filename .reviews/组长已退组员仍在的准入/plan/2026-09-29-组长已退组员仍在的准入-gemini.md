**问题**：judgeCliGroup 在 processStartTime 取不到（now === null）且 leader 恰好退出时，依然无条件 return 'gone'，绕过了成员计数判定与 out.membersLeft 的赋值。若组长在启动时刻获取期间退出而组员仍在，准入将直接误判 gone 放行并抹除凭据。

**依据**：查阅 src/trivium/status.ts:300-309 与 plan §1.2 源码：当 processStartTime 返回 null 时，现有代码在 catch 块中若 err.code !== 'EPERM' 则执行 `return 'gone'`。计划稿完全照搬了这几行，未将其纳入孤儿组与非僵尸成员数判定逻辑。

**建议**：在 now === null 的重试存活分支中，如果 kill(pgid, 0) 确认组长不在，应当统一转入与 !alive 相同的成员计数逻辑（判断 memberCountOf），而非直接 return 'gone'。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `plan §3.2 / test/integration/gate-loop.test.ts` |
| 类别 | test-gap ｜ 层次 plan |
| 置信度 | high |

**问题**：集成测试 K5/K6 夹具设计缺陷：若在 worker 活着时直接 killLeaderOnly 杀掉桩 CLI 组长，worker 的 child.once('exit') 会立即响应并触发 syncCliRecords 将 status.json 中该侧的 cli 记录刷为 null。导致后续 scrub、--wait 或 --cancel 根本读不到该侧 CLI 进程组记录，用例无法验证孤儿组阻挡与清理行为。

**依据**：查阅 src/trivium/util/exec.ts:215-220：run(..., { killTree: true }) 会在 child.once('exit') 时从 liveTrees 删除条目并触发 notifyTrees()。查阅 src/trivium/run-protocol.ts:963-966：worker 的 watchTrackedTrees 监听到变化后立即调用 patchStatus 刷入 syncCliRecords，将已退出进程对应的 sides[side].cli 置为 null。而 test/integration/gate-loop.test.ts 中现有的 K1-K4 均显式先执行 await killWorker() 阻断 worker 事件循环。plan §3.2 的 K5 却提出在 worker 存活（「心跳仍新鲜」）时直接调用 killLeaderOnly。

**建议**：修订 K5 与 K6 的执行序列，明确在调用 killLeaderOnly 前必须先终结 worker（如 killWorker）或堵住 worker 事件循环（如 blockAfterMs），确保 status.json 中保留带有启动时刻的 CLI 组记录，使测试现场真实稳定。

**问题**：测试计划中关于 Hz 格（组员全僵尸——视同 gone）的构造方案为「对残留成员逐一 SIGKILL，确认 groupMemberCount === 0」。残留进程在父进程退出后由 init 回收，SIGKILL 后立即彻底消失，这只测试了「组内进程数为 0」，未真正构造并验证 STAT 包含 Z 前缀时 processGroupMemberCount 的排除逻辑。

**依据**：查阅 src/trivium/util/exec.ts:635-644（processGroupMemberCount）与 test/helpers/proc.ts:24-29（groupMemberCount）：前者显式过滤 !m[2]!.startsWith('Z')，后者未过滤。当组内仅有僵尸进程时，processGroupMemberCount 应返回 0，而如果只是通过 SIGKILL 杀死子进程并等其被 init 回收，实际得到的是进程完全不存在（0 进程），而非僵尸态。

**建议**：通过注入 memberCountOf 或对 processGroupMemberCount 单独提供单元测试（包含模拟含 'Z' 状态的 ps 输出）来确定性测试僵尸过滤分支，避免用无进程场景假冒僵尸测试。
