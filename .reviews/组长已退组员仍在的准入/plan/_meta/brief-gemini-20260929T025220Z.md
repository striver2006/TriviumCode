## 1. 判据设计

### 1.1 `CliGroupVerdict` 新增两个值（`status.ts:281`）

```ts
export type CliGroupVerdict = 'alive' | 'gone' | 'reused' | 'unverifiable' | 'orphaned' | 'orphan_unverifiable';
```

- `orphaned`：组长不在（`kill(pgid, 0)` 为 ESRCH），且 `processGroupMemberCount(pgid)`（`util/exec.ts:635-644`，按
  `ps -axo pgid=,stat=` 排除僵尸）> 0。**新的阻挡态**：五处准入都挡；`--cancel` 仍尝试按组结束（§1.3）。
- `orphan_unverifiable`：组长不在，且成员计数取不到（`ps` 非零退出，`processGroupMemberCount` 返回 `null`）。**判不了**，
  比照既有 `unverifiable`（组长在、启动时刻未记下）同一档处置：阻挡、不发信号。

**为什么是两个新值而不是一个**（D1）：`gone`（成员数=0，视同已结束）、`orphaned`（成员数>0，阻挡且 `--cancel` 可处理）、
`orphan_unverifiable`（成员数取不到，阻挡但 `--cancel` 不处理）是三种行为互不相同的结果，与既有 `CliGroupVerdict` 「每个
值对应一种消费方处置」的既有风格一致（`reused` 与 `unverifiable` 早已是这种细分）。合并成一个值会让 `cliGroupsConfirmedGone`
与 `terminateRecordedCliGroups` 各自再判一次「是哪种子情形」，判据就不再单一来源。

### 1.2 `judgeCliGroup` 改动（`status.ts:290-311`）

```ts
export async function judgeCliGroup(
  r: CliGroupRecord,
  o: { memberCountOf?: (pgid: number) => Promise<number | null>; out?: { membersLeft?: number | null } } = {},
): Promise<CliGroupVerdict> {
  let alive: boolean;
  try {
    process.kill(r.pgid, 0);
    alive = true;
  } catch (e) {
    alive = (e as NodeJS.ErrnoException).code === 'EPERM';
  }
  if (!alive) {
    const n = await (o.memberCountOf ?? processGroupMemberCount)(r.pgid);
    if (o.out) o.out.membersLeft = n;
    if (n === null) return 'orphan_unverifiable';
    return n > 0 ? 'orphaned' : 'gone';
  }
  if (r.started_at === null) return 'unverifiable';
  const now = await processStartTime(r.pgid, { canonical: true });
  if (now === null) {
    try {
      process.kill(r.pgid, 0);
    } catch (e) {
      if ((e as NodeJS.ErrnoException).code !== 'EPERM') return 'gone';
    }
    return 'unverifiable';
  }
  return now === r.started_at ? 'alive' : 'reused';
}
```

**为什么用可选 `out` 出参而不是改返回类型**（D2）：`cliGroupsConfirmedGone` 的阻挡文案要带精确成员数（用户决策「成因带
侧、组号与成员数」），若不传出这个数字，`cliGroupsConfirmedGone` 就得对 `orphaned` 的记录再调一次 `processGroupMemberCount`
——多一次 `ps` 之外，两次调用之间有极短的 TOCTOU 窗口（成员数可能已经降到 0），文案会与刚判定的事实不一致。`out` 参数与
`processMatchesRecord`（`util/exec.ts:604-628`）的 `canonicalStartTimeOf` 依赖注入是同一种既有写法：可选、零侵入、缺省
不影响任何既有调用方（含 `terminateRecordedCliGroups` 的 `judge?: (r) => Promise<CliGroupVerdict>` 覆盖类型——少一个可选
参数的函数可以赋给多一个可选参数的函数类型，`judgeCliGroup` 依旧满足这个既有类型，测试里的 `judge` 覆盖签名不用改）。
`memberCountOf` 依赖注入让「ps 失败」这一路径可以在单元测试里零配额、确定性地构造（不依赖真的让 `ps` 崩溃）。

「代价是组长不在时多一次 `ps`（会话启动清扫路径也要付）」——这正是 BACKLOG EV-165 候选描述里已经预告的成本，本稿只把它
兑现为 `judgeCliGroup` 内部这一次 `processGroupMemberCount`，不再叠加第二次。
