### 1.2 `judgeCliGroup` 改动（`status.ts:290-311`）——**r2 改写**

**r1 的疏漏**（AGY-01 阻断 ≡ CODEX-05 次要，两条是同一处代码的两个观察角度，合并处理）：r1 §1.2 的代码把既有
`now === null` 分支原样照搬为直接 `return 'gone'`，只在最外层 `!alive` 分支接了成员计数——但 `now === null` 分支恰恰
是「组长（按 `started_at` 判）曾经活着，这一刻 `ps` 取不到规范化启动时刻，复检 `kill(pgid,0)` 发现它已经不在」，这与
最外层 `!alive` 分支是**同一个事实**（组长确认不在），必须走同一条成员计数路径，而不是分别处理成两种结果。

```ts
export async function judgeCliGroup(
  r: CliGroupRecord,
  o: { memberCountOf?: (pgid: number) => Promise<number | null>; out?: { membersLeft?: number | null } } = {},
): Promise<CliGroupVerdict> {
  const memberCountOf = o.memberCountOf ?? processGroupMemberCount;
  /** 组长确认不在（无论走哪条路径发现的）：按成员数判 gone / orphaned / orphan_unverifiable，不猜、只数 */
  const leaderGone = async (): Promise<CliGroupVerdict> => {
    const n = await memberCountOf(r.pgid);
    if (o.out) o.out.membersLeft = n;
    if (n === null) return 'orphan_unverifiable';
    return n > 0 ? 'orphaned' : 'gone';
  };
  let alive: boolean;
  try {
    process.kill(r.pgid, 0);
    alive = true;
  } catch (e) {
    alive = (e as NodeJS.ErrnoException).code === 'EPERM';
  }
  if (!alive) return leaderGone();
  if (r.started_at === null) return 'unverifiable';
  const now = await processStartTime(r.pgid, { canonical: true });
  if (now === null) {
    // ps 这一刻没取到：可能是进程恰好退出，也可能是 ps 本身瞬时失败——复检才知道是哪一种
    try {
      process.kill(r.pgid, 0);
    } catch (e) {
      if ((e as NodeJS.ErrnoException).code !== 'EPERM') return leaderGone();
    }
    return 'unverifiable';
  }
  return now === r.started_at ? 'alive' : 'reused';
}
```

**效果**：`processStartTime` 瞬时失败、复检发现组长确实已退出时，不再无条件判 `gone`，而是像 `!alive` 分支一样去数
一次成员——这同时回应了 r1 CODEX-05（「组长在而无法确认启动时刻」与「组长确认不在」两件事此前被合并处理，现在按事实
分开：前者仍是既有 `unverifiable`，后者与 `!alive` 分支同源）。`leaderGone` 只在这两处被调用，两个来源共用一次
`memberCountOf`，判据仍然单一。

D2（`out` 出参 + `memberCountOf` 依赖注入）论证同 r1，三侧均认可。

### 3.2 集成（`test/integration/gate-loop.test.ts`，EV-157 K 系列之后新增 K5／K6，真实 bundle）——**r2 改写前提**

**r1 的前提缺陷**（CODEX-01 重要 ≡ CODEX-02 重要 ≡ AGY-02 重要 ≡ GLM-03 次要，四条并为一处修正）：`run()` 的
`killTree` 派生逻辑（`util/exec.ts:211-220`）在 worker **存活**期间，一旦它跟踪的**直接子进程**（`hang_cli` 桩里的
`sh`，即组长）触发 Node 的 `'exit'` 事件，就会 `liveTrees.delete(pid)` + `notifyTrees()`，worker 的唯一观察者
（`run-protocol.ts:963` 起）随即把该侧 `status.json` 的 `cli` 字段写成 `null`（`syncCliRecords`，`status.ts:234-240`
对没有对应活跟踪条目的侧置 null）。这个机制**只认自己派生的那个直接子进程是否退出，对它的孙辈毫无感知**——所以如果
worker 还活着，`killLeaderOnly` 杀掉 `sh` 的那一刻，无论 `sleep` 是否还在跑，worker 都会把记录清成 `null`，**根本不会
留下「组长已退、组员仍在」的记录**给 `judgeCliGroup` 去判。r1 §3.2 的 K5/K6 在这个前提下无法构造出目标场景。

**这同时说明**（呼应 CODEX-01 的深层观察，§4 详述）：本轮新增的 `orphaned` / `orphan_unverifiable` 判据只对**worker
已经不在场、来不及处理 CLI 退出事件**的场景生效——而这恰好是全部五处准入的共同前提（`scrubAdmission` 先判
`workerConfirmedGone`，worker 活着时五处都不会碰 CLI 那一半，见 §2.5「不改的地方」），与 EV-165 描述的「凭据准入……
判已结束、放行」场景完全对应：那个场景本身就只发生在 worker 已死之后。

**修订后的构造前提**（GLM-03 给出的精确表述）：先用既有 `killWorker`（`gate-loop.test.ts:2599` 起，按组 SIGKILL
worker、等它确认不在，worker 不再是任何进程的观察者）结束 worker，**再**用 `killLeaderOnly` 杀掉一侧的组长——此时没
有观察者会响应组长的 `exit` 事件，记录原样留在 status.json 上，组员则继续存活，这才是真正的「组长已退、组员仍在」
持久态。

```ts
async function killLeaderOnly(pgid: number): Promise<void> {
  try { process.kill(pgid, 'SIGKILL'); } catch { /* 已不在 */ }
  for (let i = 0; i < 100 && !pidGone(pgid); i++) await new Promise((r) => setTimeout(r, 50));
  assert.ok(pidGone(pgid), `组长 ${pgid} 应已不在（用例前提）`);
}
```

## 4. 风险与如实保留

- **worker 存活期间的自身子进程退出盲区**（CODEX-01 的深层部分，本轮不修、登记新 BACKLOG）：`run()` 的 `killTree`
  跟踪面（`liveTrees`）只认自己派生的**直接子进程**是否退出（`util/exec.ts:211-220`），对该子进程的孙辈毫无感知。
  只要 worker 还活着，CLI 组长一退出，worker 就会把该侧记录清成 `null`（`syncCliRecords`），此后即使孙辈仍在跑，
  `cliRecordsOf` 也读不到任何记录（视为「没有 CLI」），无法被 `judgeCliGroup` 判定为 `orphaned`。**这不会导致凭据被
  误抹**——五处准入都先判 `workerConfirmedGone`，worker 活着时压根不会碰 CLI 那一半（§2.5）——但意味着：如果 worker
  之后也死了（记录已经是 `null`），孙辈会成为「记录里从未存在过」的进程，之后的清扫、到期整删都不会再意识到它们的
  存在，也不会被本轮的新判据挡住。这是 EV-154 原始设计的既有边界（`liveTrees` 的跟踪面从一开始就只到直接子进程），
  不是 EV-165 引入或能够独自修复的——修它要改 `liveTrees` 的跟踪粒度（例如按进程组而非单个 pid 跟踪），改动面超出
  「只改 `judgeCliGroup` 与 `cliGroupsConfirmedGone`」的范围，登记为新 BACKLOG 条目（拟编号由实施时的 BACKLOG 当前
  最大编号顺延，见 §6），暂缓、不并入本轮。
- **`processGroupMemberCount` 自身的僵尸排除逻辑目前没有专门测试**（AGY-05 提及，EV-154 遗留、非本轮引入）：本轮
  Hz 格测试用依赖注入覆盖了「成员数为 0」这个契约点在 `judgeCliGroup` 里的处理，但没有验证 `processGroupMemberCount`
  本身对 `ps` 输出里 `Z` 前缀的过滤逻辑——macOS 上真实僵尸态的构造窗口短且不确定（受 launchd 回收孤儿进程的速度影
  响）。登记为新 BACKLOG 条目，暂缓、不并入本轮。
- **`orphaned` 来源触发「组长已退出，组里还有 N 个成员」告警在实践中不可达**（§2.3）：只有 `alive` 来源经历「组长在
  终止过程中退出、成员忽略信号」这一特定时序才会触发；`orphaned` 来源要么升级到 `gone`（不触发任何告警），要么停在
  「未能确认退出」（既有告警）。如实保留，不特别处理。
- **判定与发信号之间的窗口**：同 r1，`isGone` 复核之后、`kill(-pgid)` 之前组员恰好全部退出且组号被复用为别的
  组——概率与既有 `reused` 判据窗口同量级，本轮不新增处理。
- **`orphan_unverifiable` 不去猜**：同 r1。`now===null` 复检路径接入 `leaderGone` 后，一次瞬时 `ps` 失败仍会把该侧
  暂时挡住（下次清扫重判），比 r1 的写法（该分支完全没有走到成员计数、直接判 `gone`）更保守、更安全，但没有改变
  「不重试」的既有立场——重试会把「判不了」偷换成「多试一次直到判得了」，不是本轮范围。
- **僵尸判定依赖 `ps` 的 `STAT` 列**：同 r1，与既有 `processGroupMemberCount` 同一份判据，不新增。
- **不影响 worker 自身的 SIGTERM 处理器**（`shutdownTrackedTrees`，EV-152 范围）：同 r1。
- **真实厂商 CLI 未实测**（用户决策，不花配额）：同 r1。
- **超范围、暂缓**：EV-163、EV-161、EV-162、EV-166、EV-167、EV-159 第二形态——均不并入，维持 BACKLOG 现状；新增两条
  暂缓（本节前两条）。
