## 1. 现状核实

### 1.1 为什么要在预检就说

EV-122 的收尾播报（`model_unenforced`）按构造只能在该侧**跑完之后**出现：触发条件含「回读到了生效模型」。
而副本源在不在，预检期就知道。EV-112 E2 那一轮就是这样白跑了一整轮：16m42s、27 次工具调用、单侧真实配额，结论来自一个不是 GLM 的模型。

## 2. 范围

**做**：
1. zcode 适配器导出副本源路径的**唯一出处**，C1、C2 与新检查共用（§3.1）；
2. 预检新增检查 `checkZcodeOverrideSource`：glm 入选且副本源不在 ⇒ 一条 `ok: true` 的警告（§3.2）；
3. `CheckResult` 加 `warn?: true`；`PreflightResult` 与 `--json` 输出加 `warnings` 汇总；人读输出对警告项用 `⚠` 而非 `✓`；C5 那条一并标上（§3.3）；
4. 四条 skill 的预检步骤补转述约定（§3.4）；
5. 用例、变异、设计文档（含补 C8）、RUNBOOK、BACKLOG 同步（§4、§5）。

**不做**：
- 不拒跑：副本源缺失时判 glm 侧不可用是 EV-122 的候选 ②，用户未选；
- 不在预检预判「限定失败」（`qualify_failed`）：预检的 `checkModelSlugs` 已按探针目录校验模型名，目录与副本源异源是 EV-93 的既有问题，不在本题；
- 不在 `review --start` 再报一次（D2 的 (c)）；
- 不改 `doctor`：doctor 探的是 CLI 能力，副本源在不在是每一轮运行前的事实；
- 不扩到 codex / agy / claude：它们没有「副本源」这一概念，同类缺口归 EV-91。

## 3. 改动

### 3.1 副本源路径的唯一出处（决策 D1）

- **(a) zcode 适配器导出 `zcodeOverrideSourcePath(): string`（推荐）**：返回 `path.join(os.homedir(), '.zcode/cli/config.json')`，C1 的缺省值、C2 的指纹、新检查三处都调它。
  预检从适配器导入它，与 `checkZcodeRuntimeSelection` 读 zcode 探针结论同形：厂商知识留在适配器，预检只消费。
- (b) 给 `CriticAdapter` 加可选钩子 `preflightAdvisories(ctx)`，由各适配器自报预检提示。**不取**：通用化只有一个调用方，接口面扩大换不来什么；EV-91 通用化时若别家也要，再把 (a) 提升为钩子，届时改动是局部的。
- (c) 预检里再写一遍路径字面。**不取**：第三份字面，C1、C2 已经是两份，这正是「改一漏二」的形状。

### 3.2 新检查（决策 D3：措辞）

`checkZcodeOverrideSource(cfg, selected): Promise<CheckResult | null>`：按入选侧经注册表取 CLI 名（同 C5，不写 `'glm'` 字面），只对 zcode 那一侧查 `zcodeOverrideSourcePath()` 是否存在；存在或未入选 ⇒ `null`（不出项）。
不在时：

```
name:   'ZCode 模型覆盖副本源'
ok:     true
warn:   true
detail: ⚠️ 副本源 ~/.zcode/cli/config.json 不在：若发起时仍不在，本轮 glm 侧不会做模型覆盖，
        CLI 跑的是它自己选的模型（EV-112 E2 实测为个人配置的默认模型），FR-06 / NFR-06 在该侧不成立；
        跑完 guard 会给「本次没有做模型覆盖」告警。要按请求的模型跑，先把副本源放回原处再发起。
```

- 路径**恒以 `~/` 形式展示**，不展示绝对路径：预检输出常被抄进 evidence 目录，不必带出用户名；
- 「若发起时仍不在」：预检与拉起之间文件可能被放回，预检只能说「若」，实际是否覆盖由收尾那条说；
- 位置：紧跟 C5 之后（④″），同样只在前面各项都通过时才跑；它不花配额，放在探活之前。

### 3.3 警告这一级（决策 D2：转述通道）

- **(a) 结构化标记 + JSON 汇总 + skill 约定（推荐）**：`CheckResult` 加 `warn?: true`；`PreflightResult` 加 `warnings: { name: string; detail: string }[]`（由 `checks` 过滤 `warn` 得出，不另存一份）；
  `--json` 输出同名字段；人读输出对 `warn` 项打 `⚠` 而非 `✓`，末行「✓ 预检通过」后追加「（含 N 条警告）」。`ok` 与退出码**不受影响**。C5 那条同时标 `warn: true`。
- (b) 让 Driver 扫 `detail` 的 `⚠️` 前缀。**不取**：按文案匹配判语义，EV-122 计划轮 CODEX-02 刚否掉这种做法。
- (c) 在 `review --start` 的返回里再带一份。**不取**：多一条路径、多一份判定；`--start` 紧接在预检之后，两者之间的时间差不足以抵消两处判定分叉的风险。收尾的 `model_unenforced` 已经兜住「预检后文件被挪走」这一格。

### 3.4 skill 的转述约定

四处原句「失败则**原样转述**错误并停止」之后补一句（dual-run 的 S0 同义改写）：

> 通过时若 `warnings` 非空，把每一条的 `detail` 原样念给用户，**然后继续**，不停下来等确认——警告不阻断，要不要处理由用户决定。

## 4. 验证

### 4.1 用例

- **`zcodeOverrideSourcePath`**：HOME 钉到临时目录 ⇒ 返回 `<临时 HOME>/.zcode/cli/config.json`；`prepareZcodeHome` 不传 `srcConfig` 时用的就是它（临时 HOME 下不放文件 ⇒ `cause: 'source_missing'`）。
- **`checkZcodeOverrideSource`**：glm 入选且文件不在 ⇒ 出项，`ok: true`、`warn: true`、`detail` 以 `⚠️` 开头、含 `~/.zcode/cli/config.json` 且**不含**临时 HOME 的绝对路径；文件在 ⇒ `null`；glm 未入选 ⇒ `null`（文件不在也不出）。
- **`runPreflight` 汇总**：用现有预检用例的夹具，让 C5 与新检查各出一条 ⇒ `warnings` 恰两条、`ok: true`、`exitCode` 为 0；两条都不出 ⇒ `warnings` 为空数组（恒写，不缺席）。
- **人读输出**：`warn` 项行首是 `⚠`，末行含「含 2 条警告」；无警告时末行与今天逐字相同。
- **skill 文本**：四个 `SKILL.md` 的预检段都含 `warnings` 转述句（仿 `topic-args.test.ts` 读 `SKILL.md` 的先例）。

### 4.2 变异

规格与输出进 `doc/05_testing/evidence/ev123-mutation-<日期>/`，另写一份 `00-readout.md`（写明「工作树干净」的口径，EV-122 代码双审 GLM-F03 ③）：
- P1 新检查恒返回 `null` ⇒「文件不在 ⇒ 出项」红；
- P2 不查入选侧（glm 未入选也出）⇒「未入选 ⇒ null」红；
- P3 `detail` 用绝对路径 ⇒「不含绝对路径」红；
- P4 `warnings` 不过滤 `warn`（全部 `checks` 进去）⇒ 汇总条数红；
- P5 C5 那条不标 `warn` ⇒ 汇总「恰两条」红；
- P6 `prepareZcodeHome` 的缺省值不走 `zcodeOverrideSourcePath` 而另写一个路径 ⇒ 共用出处那格红；
- P7 删掉某一个 `SKILL.md` 的转述句 ⇒ skill 文本用例红。

### 4.3 验收（零配额，不挪用户文件）

- **E1 正向**（本机，副本源在）：`npm run install:local` 之后跑 `trivium preflight --stage plan --json`，断言 `warnings` 为空、不出新检查项。
- **E2 反向**（不挪用户文件）：evidence 目录里的只读脚本从构建产物导入 `checkZcodeOverrideSource`，把 `HOME` 钉到一个 mkdtemp 空目录后调用，断言出项与措辞；再调 `renderPreflight` 断言 `⚠` 行与末行。
  **不在真实 HOME 上挪 `~/.zcode/cli/config.json`**：挪文件换来的只是「`os.homedir()` 确实被读了」，而这一点 E1 与用例已经覆盖。
- `npm run typecheck && npm run build && npm test` 全绿；`trivium doctor --selftest` 全绿。
