## 认为正确的部分

- D1 (a′) 站得住，且与既有逐侧可选钩子同形：`authProbe?` / `normalizeModelForCatalog?` / `catalogModelsFor?` 三个可选成员的口径就是「这条知识属于那一侧，不住在 preflight 里」（base.ts:103/127/132），新成员落在同一处、由 zcodeAdapter 实现一处出口，判侧由「入选侧的适配器有没有这个成员」承担，不写 Agent id / CLI 名字面量，也确实不需要 parity 豁免。把 zcode.ts:897 与 :974 两处路径字面合并为一个出口，方向与范围都对。一处事实小错不影响结论：C12 把 `availability` 记作可选，实际它是必填成员（base.ts:96），四个钩子是「一必填 + 三可选」。
- 措辞我逐句核过，r2 已无明显越界断言：zcode 拉起路径上没有命令行模型旗标（zcode.ts 全文没有 `--model` 一类参数），所以「不做模型覆盖 ⇒ 跑的是 CLI 自己选的模型」是构造性事实；「不一定是请求的那个」与「回读不到生效模型时它不出声」两处 hedging 与 `decideModelUnenforced` 的四条件（zcode.ts:159：没做覆盖、请求非空、回读到生效模型、modelId 段不同）一致；引用的那句「本次没有做模型覆盖」在 guard.ts:892 与 RUNBOOK 都有原文，用户按这句话找得到东西。「要按请求的模型跑，先把副本源放回原处再发起」是必要条件式建议，不构成「放回就一定生效」的断言。
- 兜底分层（预检 / `--start` / 收尾 guard）与「不拒跑、不在拉起前阻断」的取向自洽，与 EV-122 的 `model_unenforced` 不打架；「预检选侧 ≠ 当轮选侧」用条件句加插值处理掉之后，我没有再找到把条件写成断言的句子。把 `warn` 做成结构化字段而不是继续让 Driver 扫 `⚠️` 前缀，也是这条主题该走的方向。
- 零配额方向正确：E1 补 `--skip-auth-check` 后只跳过 ⑧ 探活（preflight.ts:686-700），不影响 ④″ 的出项；`doctor --selftest` 走桩；「不在真实 HOME 上挪副本源」的判断成立——世界 A/B 与 E3 已覆盖 `os.homedir()` 这条链（POSIX 下 `os.homedir()` 读 `HOME`，E3 的机制可行），而挪真实文件换来的信息确实只多一点点。
- 变异与用例大体能咬住新增三处：P1–P6、P8 分别咬住新检查的判据、`selected` 过滤、路径展示、`warnings` 过滤、C5/探活的 `warn` 标记、`prepareZcodeHome` 的缺省值来源（P6 现在真咬得住：世界 B 会在缺省值被改成 `.bak` 时红，r1 那个「P6 杀不死」已被修掉）与预检 JSON 映射。E2「从构建产物导入」的先例真实存在（doc/05_testing/evidence/ev122-acceptance-20260925/e1-check.mjs 从 `dist/test/src/trivium/...` 导入 `prepareZcodeHome`/`renderGuardWarnings`），E1/E3 的分工（本机正向 / 临时 HOME 反向）也合理。
