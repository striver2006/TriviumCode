### CODEX-03 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/probes/zcode.ts:67-68（对照 src/trivium/adapters/zcode.ts:865-875）` |
| 类别 | maintainability ｜ 层次 code |
| 置信度 | medium |

**问题**：zcodeOverrideSourcePath() 的 docblock 与设计变更记录都把这件事叙述成「副本源路径的唯一出处」，但同一份文件在探针模块里还有第四处拼写：ZCODE_CLI_DIR / ZCODE_CLI_CONFIG，而它正是 doctor 三条模型覆盖臂的副本源（三处都以 opts.cliConfigPath ?? ZCODE_CLI_CONFIG 起手）。更要紧的是取值时点不同：它是模块加载时算一次的常量，而新函数是每次调用现取 os.homedir()（「不缓存」正是它 docblock 写下的理由）。于是本题新依赖的「钉 HOME 造两个世界」用例技法对探针那一路无效：进程内改 HOME 之后，测试里 import 过的 probes 仍指向 import 时的家目录，也就是开发机真实的 ~/.zcode/cli/config.json（含凭据）；只有进程级钉 HOME（集成用例那种 subprocess）才一致。今天新用例只碰适配器一侧的调用时路径，所以没有现红，但「唯一出处」这个记忆点与残留的第四处相加，会让下一个换副本源位置的人漏改探针侧。设计/注释的括号里列的是「三处共用」，措辞本身没算错，问题在总括语与残留实现不一致。

**依据**：src/trivium/probes/zcode.ts:60-68（两个模块级常量）、:250-265（probeZcodeModels 的 homeDir 三元）、:554 与 :886 与 :1195-1210（三条覆盖臂的副本源与 note 文案）；src/trivium/adapters/zcode.ts:865-875（新函数的 docblock 与三处调用点）；test/unit/model-override-source.test.ts:1-45（docblock 把钉 HOME 写成这一片的技法）；实证：node -e 在 Node v25.2.1 下改 process.env.HOME 后 os.homedir() 立刻跟随（不缓存、读 $HOME），而模块级常量不会重建。

**建议**：把探针那三处的缺省源指向同一个出处（或让 ZCODE_CLI_DIR/ZCODE_CLI_CONFIG 改成调用时求值，注意它同时服务 log / rollout / models 三格）；退一步至少在新函数 docblock 里点明「探针的 ZCODE_CLI_CONFIG 未并入」，让「唯一出处」不至于被读成全局。
