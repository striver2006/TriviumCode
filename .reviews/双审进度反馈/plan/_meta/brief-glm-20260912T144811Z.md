# 计划：让双审等待期间的进度及时反馈给用户

## 一、目标与范围

### 目标

双审跑起来之后，用户在 plan 阶段最长要等 1500s、code 阶段最长要等 2700s（两侧并行，
各自还有一次重试预算）。这段时间里用户看到的只有 Driver 反复调用同一个 Bash 工具，
不知道跑到哪了、还要多久、有没有卡死。本次要让用户在等待期间按**稳定节奏**收到
可读的进度，且每条进度都能回答三个问题：**跑到哪了 / 还要多久 / 两侧各自什么状态**。

### 范围内

1. `--wait` 的 JSON 输出增加**成品短句**与结构化进度字段，让 Driver 不必自己组织语言。
2. `renderProgress` 补上「期待值」维度：阶段预算、已用占比、第几次等待 / 共几次。
3. 反馈粒度：`wait_timeout_s` 从 540s 降到 180s。
4. 三个 review skill（plan / code / bug）的等待循环指令，新增**播报义务**；
   `dual-run` 的 S2 / S6 声明该义务随委托一并继承。
5. 文档同步：设计文档、PRD、RUNBOOK、QUICKSTART。

### 明确不做

- **不做真流式**。Bash 工具在命令退出前不回传 stdout，wait 窗口内 Driver 物理上
  说不了话。这是架构硬约束，不是本次能绕过的；反馈粒度的下限恒等于 `wait_timeout_s`。
- **不引入宿主专属推送工具**（PushNotification / SendUserFile 之类）。skill 要对宿主
  保持解耦，只依赖「Driver 能发文本消息」这一最小假设。
- **不碰审查本身**的并行、超时、重试、指纹、漂移判定。本次只动「怎么把已有的进度说出去」。
- **不新增配置项**。见不可逆决策 D1。

### 缺口

**缺口 1 · 指令层没有播报义务。** 三个 skill 的第 3 步（[dual-review-plan/SKILL.md](skills/dual-review-plan/SKILL.md)、
[dual-review-code/SKILL.md:114](skills/dual-review-code/SKILL.md#L114)、
[dual-review-bug/SKILL.md:112](skills/dual-review-bug/SKILL.md#L112)）对退出码 73 的说明
是同一句：

> 退出码含义：`73` 仍在运行（**打印进度后继续等**）；`0` 两份审查文档与元数据已落盘

「打印」在 Driver 的语境里就是**工具输出**——它本来就打印了，义务在字面上已经满足，
于是 Driver 直接发下一次 `--wait`。而工具输出在折叠视图下用户看不到。这一句是整个
需求的根因：它描述的是 CLI 的行为，不是 Driver 对用户的义务。

**缺口 2 · 粒度是 9 分钟。** `wait_timeout_s: 540`（[.trivium/config.yaml](.trivium/config.yaml)）。
即使 Driver 每次都转述，code 阶段 2700s 预算下最坏也只有 5 次反馈，间隔 9 分钟。
9 分钟没有任何信号，与「没有反馈」在体感上没有区别。

**缺口 3 · 进度没有期待值。** 现有 `progress` 回答了「跑了多久」，没回答「还要多久」。
用户看到「已用时 612s」无从判断是正常还是快卡死了——它缺少分母（阶段预算）与
序号（第几次 / 共几次）。

**缺口 4 · 开场是静默的。** `--start` 立即返回，Driver 随即进入第一次 `--wait`。
从启动到第一条进度之间有一整个窗口的静默，而这恰是用户最想知道「启动成功了吗」的时刻。

## 三、方案

### 步骤 1｜`--wait --json` 增加成品短句与结构化字段

在 [cli.ts:231](src/trivium/cli.ts#L231) 的 JSON 输出里，保留 `progress` 原样，新增：

```jsonc
{
  "progress_brief": "code 审查中 ｜ 已用 10m12s / 预算 45m（23%）｜ gemini 已完成 · glm 审查中",
  "elapsed_s": 612,
  "budget_s": 2700,
  "pct": 23,
  "waits_done": 2,
  "max_waits": 32,
  "sides": { "gemini": { "state": "ok", "elapsed_s": 340 },
             "glm": { "state": "running", "attempt": 1, "elapsed_s": 612 } }
}
```

`progress_brief` 是**给 Driver 原样念的一行**，长度控制在 60 字以内。给成品而不是给
原料，是为了压掉转述时的自由发挥——让 Driver 组织语言，每次说法都会不一样，用户
反而更难从中看出「和上次比变了什么」。

`waits_done` 由 `waitRun` 用 `⌈elapsed / waitTimeoutS⌉` 推算，不落盘、不加状态。
status.json 的 schema 因此**不动**。

### 步骤 2｜`renderProgress` 补期待值

给 `renderProgress(s, now)` 加第三个可选参数：

```ts
export interface ProgressBudget {
  stageTimeoutS: number;   // 本阶段单侧超时
  waitTimeoutS: number;    // 每次 --wait 的窗口
  maxWaits: number;        // 循环上限
}
export function renderProgress(s: RunStatus, now?: number, budget?: ProgressBudget): string
export function renderProgressBrief(s: RunStatus, now?: number, budget?: ProgressBudget): string
```

参数**可选**：不传就退回现有输出，既有调用方（`statusRun`、`trivium status`）不受影响。
传了则多两行：

```
运行 r-20260912-… ｜ 主题 双审进度反馈 ｜ 阶段 code ｜ 阶段状态 审查中
已用 10m12s / 预算 45m（23%）｜ 第 2/32 次等待 ｜ 最近心跳 3s 前
  gemini: 已完成 ｜ gemini-3.8-flash-high ｜ 340s
  glm: 审查中 ｜ GLM-5.3-Flash ｜ 第 1 次尝试 ｜ 612s
```

两处可读性修整，一并做掉：

- `SideStatus.state` 译成中文：`pending`→待启动、`running`→审查中、`ok`→已完成、
  `failed`→失败、`timeout`→超时、`parse_fallback`→解析回退。`RunPhase` 同理。
  译表集中一处导出，避免散落。
- 秒数超过 60 时渲染成 `10m12s`，`612s` 读起来要换算。

`renderProgressBrief` 产出步骤 1 那一行，供 `progress_brief` 字段使用。

### 步骤 3｜把反馈粒度从 9 分钟压到 3 分钟

`wait_timeout_s`：`540` → `180`。改两处，保持一致：
- 项目配置 [.trivium/config.yaml](.trivium/config.yaml)
- `trivium init` 写出的默认配置（[init.ts](src/trivium/init.ts)）

`computeMaxWaits` 随之自适应：code 阶段 `2700×2÷180+2 = 32` 次，plan 阶段
`1500×2÷180+2 = 19` 次。上限变大不影响正确性——它本就是按总预算推的。

顺带把 `bashTimeoutMs` 从硬编码改成 `Math.min(600_000, waitTimeoutS * 1000 + 60_000)`。
窗口 180s 时工具超时 240s：仍有 60s 余量覆盖进程启动与收尾，而 `--wait` 真卡死时
4 分钟就能发现，不必干等 10 分钟。窗口若被调回 540s，该式仍得 600_000，行为不变。

### 步骤 4｜skill 指令层落地播报义务（本次的核心）

三个 review skill 的第 3 步，把那句「打印进度后继续等」换成一段明确的义务。统一措辞：

> **每次 `--wait` 返回后，先向用户发一条文本消息，再发下一次 `--wait`。**
> 这条消息是**给用户看的**，不是工具输出——工具输出在折叠视图下用户看不到，
> 只打印不等于反馈。内容用返回里的 `progress_brief`，原样念一行即可，不要改写、
> 不要合并、不要「等下一次一起说」。退出码 `73` 和 `0` 都要说。
>
> 若两侧状态较上次有变化（`running`→`ok`、`attempt` 增加、出现 `note`），
> 在那一行后面补一句说明变化。**状态不变时不要补**——每次都写只会淹掉真正的变化。

`--start` 之后补一条开场播报（补上缺口 4）：

> `--start` 返回后**立刻**向用户播报一条：主题、阶段、两侧模型、预算时长、
> 汇报节奏（约每 `wait_timeout_s` 一次）、`run_id`。并告诉他：想自己看进度可以
> 随时 `/dual-status`，想中止用 `.trivium/bin/trivium review --cancel <run_id>`。

收尾（退出码 `0`）时播报总耗时与两份文档路径，再进第 4 步读全文。

[dual-run/SKILL.md](skills/dual-run/SKILL.md) 的 S2 / S6 各补一句：委托 `/dual-review-*`
第 3 步执行时，**播报义务一并继承**——S2/S6 是交接处，这类义务最容易在交接时掉。

## 五、被放弃的方案

**A · 让 worker 直接写一个「用户可读进度文件」，由 Driver 隔一段时间读。**
放弃：Driver 只有在工具返回时才能说话，读文件同样要发一次工具调用。它没有绕开
Bash 不流式的约束，只是把 `--wait` 换成 `cat`，还多一份要维护的产物。

**B · 把 `--wait` 改成每 N 秒就返回一次，N 做成新配置。**
放弃：这就是 `wait_timeout_s` 本身。见 D1。

**C · 用宿主的推送能力（PushNotification 等）在窗口内推进度。**
放弃：把 skill 绑死在特定宿主上。TriviumCode 的 skill 目前只假设「Driver 能发文本」，
这个最小假设值得守住。且窗口内 Driver 未被唤醒，推送也得有人去触发。

**D · 只改 skill 文档，不动代码（最小改动）。**
放弃：它能修掉缺口 1，但留下缺口 2（9 分钟粒度）和缺口 3（没有分母）。
用户 9 分钟收到一句「已用时 612s」，依然不知道该不该慌。四个缺口是一件事的四个面。

**E · 把 `wait_timeout_s` 降到 60s，做到分钟级反馈。**
放弃：code 阶段会到 92 次 wait，往返成本与上下文占用都不划算（见风险 R1），
而 3 分钟一次已经足够消解「不知道死没死」的焦虑。180s 是成本与体感的折中。

## 八、风险与未决问题

**R1 · 往返成本上升。** 窗口 540→180 后，code 阶段最坏 32 次 wait（原 11 次）。
每次约 300~500 token（JSON 输出 + 一句转述），最坏新增约 10k token 上下文占用。
判断：可接受——但这是本次唯一有量化代价的改动，请审查员重点核这个折中。
若认为过重，退路是 300s（约 5 分钟一次，code 阶段 20 次）。

**R2 · 指令层没有强制力。** D2 已说明 CLI 管不到 Driver 说不说话。Hook 也不行——
`hook-stop` 只在收工时触发，管不到等待期。实际效果依赖 Driver 守指令，
和现有的「逐条裁决」义务是同一种约束强度。如实记录，不假装它是强制。

**R3 · 播报可能变成噪音。** 32 条内容雷同的进度同样会被略过。步骤 4 里「状态不变时
不要补说明」是针对这点的，但一行摘要本身仍每次都发。未决：是否在状态完全无变化时
只发更短的一行（如「glm 审查中 · 已用 12m / 45m」）。倾向于是，但先按统一格式实现，
留待审查员判断是否值得增加这层分支。

**R4 · 既有项目不会自动获得新粒度。** `config.yaml` 进 Git 且由用户持有，不能代改。
只能在 RUNBOOK 写明。这是配置所有权的必然结果，不做静默迁移。

## 5. 审查要点与你这一侧的镜头

被审对象是一份**还没实施的计划**。这决定了审查的重心与代码审完全不同：

- **现在指出比事后返工便宜几个量级。** 计划阶段最值得找的是「做了会发现方向不对」
  的问题，而不是措辞与格式。
- **不可逆决策优先。** 数据模型、对外契约、迁移与回滚路径、第三方依赖的引入——
  这些一旦落地就很难改。先审它们，再审其余。
- **计划没写的部分也是问题。** 需求里有、计划里没有的，属于遗漏；
  计划里含糊其辞（「适当处理」「必要时优化」）的，属于未决策。两者都要指出。
- **不要替 Driver 重写计划。** 指出「§3 没有覆盖并发回滚」即可，
  不要给出整段替代方案——那会让裁决变成二选一而不是逐条判断。

判断一条意见该不该提，用这个标准：**如果按现在的计划做完，这个问题会不会变成返工？**
会，就提；不会，且只是风格偏好，就不提（但可以写进 `agreed` 或 `not_covered`）。
