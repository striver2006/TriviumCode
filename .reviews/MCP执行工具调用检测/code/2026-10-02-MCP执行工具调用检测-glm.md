### GLM-01 · 次要（minor）

| 项 | 内容 |

| 位置 | `src/trivium/adapters/zcode-trace.ts:425-461（summarizeZcodeMcp 的 logOnly 与 byTool；rollout 侧 id 缺省空串见 parseZcodeRollout 356-361）` |

**问题**：合并计数的并集假设有一个未考虑的破口：logOnly 收「日志有 id 而 rolloutIds 里没有」的调用，byTool 取 max(ro.length + logOnly, logCounts)。若 rollout 的同名 MCP 条目本身缺 id（parseZcodeRollout 对缺失 id 记空串、不进 rolloutIds），而日志侧带着这批调用的 id，则同一次调用既算进 ro.length 又算进 logOnly——byTool 翻倍、tool_calls.mcp 与 trace.json 的 mcpCalls.total/byTool 虚高，且执行型那档会多产出一条「会话日志另记 k 次，参数不可得」的写事件（留痕声称发生了并不存在的额外调用）。注释只考虑了「日志缺 id」的兜底方向，没考虑「rollout 缺 id + 日志带 id」的重叠方向。触发前提是厂商 rollout 格式变化（五次真实运行 172 次调用 id 一一对应，未观测到缺 id），且该侧已因真实调用判失守，判定与闸门不受影响，错的是计数与留痕条数——而这个字段的全部用途就是如实计数。

**依据**：实读 src/trivium/adapters/zcode-trace.ts（425-474 行：rolloutIds 只收真值 id、logOnly 按「不在 rolloutIds」累加、byTool 与 extra 的计算式）；实读 doc/05_testing/evidence/mcp-exec-detect-20261002/history-scan-output.json 的 idCheck（五轮 onlyInRollout/onlyInLog 均 0，即缺 id 形态未出现）；U5/U6/U7/U12 覆盖了 rollout 没读到、rollout 丢行、日志缺 id、两边各丢调用的形态，唯独没有 rollout 条目缺 id 而日志带 id 的用例。

**建议**：对「该名字在 rollout 里存在无 id 条目」的分支退回按名取大（byTool 取 max(ro.length, logCounts)，跳过该名字的 logOnly 累加），与注释宣称的兜底口径对齐；并补一条 U 用例钉住这个形态（构造 rollout 条目无 id + 日志带同批 id，断言 total 不翻倍、execEvents 无「另记」条目）。
