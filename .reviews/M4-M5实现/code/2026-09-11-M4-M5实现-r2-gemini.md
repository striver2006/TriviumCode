### AGY-01 · 阻断（blocker）

| 项 | 内容 |

| 位置 | `src/trivium/run-protocol.ts:360` |
| 类别 | concurrency ｜ 层次 code |

**问题**：工作进程异常退出或失联（worker_lost）时未将 state.json 闸门状态重置为 idle，导致 Driver 业务写锁永久锁死。

**依据**：在 src/trivium/review.ts:425 的 prepareRun 中，编排器将 state.json 的闸门状态置为 running。派生 worker 后，若 src/trivium/run-protocol.ts:360 的 workerMain 在 rebuildContext 或 executeRun 抛出异常，catch (e) 仅更新了 status.json 为 failed 并释放锁，却未调用 setGate 将状态重置为 idle；同样，在 src/trivium/run-protocol.ts:427 的 waitRun 中，检测到 worker_lost 时也只更新了 status.json 并抛错，未重置闸门。由于 src/trivium/hooks.ts:109 的 hookPreWrite 与 src/trivium/state.ts:137 的 OPEN_STATES 包含 running，且 shouldLockWrites 只要状态为 running 且在 TTL 内就会判定加锁，导致哪怕工作进程已死亡，后续同会话的任何业务文件写入都将被持续阻断（报错「双审进行中」），破坏流水线可用性。

**建议**：在 workerMain 的异常捕获块以及 waitRun 判定 worker_lost 的分支中，补充将 state.json 中该主题/阶段的闸门状态重置为 idle 的逻辑（对齐 cancelRun 与 review.ts:677 的失败处理）。

### AGY-02 · 阻断（blocker）

| 项 | 内容 |

| 位置 | `src/trivium/cli.ts:510` |
| 类别 | security ｜ 层次 code |
| 置信度 | high |

**问题**：trivium gate --await-approval 缺少前置状态与裁决完整性校验，可被直接调用完全绕过裁决与工件核验。

**依据**：在 src/trivium/cli.ts:510-527 的 cmdGate 中，当传入 --await-approval 参数时，代码未检查当前闸门状态是否经过裁决，也未调用 checkAdjudication 或 checkStageArtifacts，而是直接调用 setGate 将状态覆写为 awaiting_approval。这覆盖了刚双审完成时的 review_done_awaiting_disposition 状态。一旦覆写，src/trivium/hooks.ts:197 的 hookPreCommit 和 hookStop 便无法再感知「审查已落盘但裁决未完成」，进而允许直接执行 /dual-approve。因为 approval.ts:34 只校验 state === 'awaiting_approval'，且 hookPreCommit 随后调用的 checkArchiveIntegrity 仅校验 run.json.artifacts 中已有工件（裁决件不在此清单内），导致执笔者无需编写任何裁决件即可完成审批并成功 commit，使逐条裁决硬约束彻底被绕过。

**建议**：在 cmdGate 处理 --await-approval 时增加前置校验：必须要求该阶段本轮已通过 checkAdjudication（或要求状态必须是由合法的裁决校验放行流转而来，且裁决件与工件齐备），禁止在未经校验时随意跃迁至 awaiting_approval。

### AGY-03 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/code-stage.ts:31` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：filesInDiff 对 git diff --no-index 产物的解析未过滤 /dev/null，导致未跟踪文件引入 /dev/null 污染变更文件列表并破坏纯文档变更跳过机制。

**依据**：在 src/trivium/util/git.ts:133 中，未跟踪文件是通过 git diff --no-index --find-renames /dev/null f 生成补丁的，其 diff 头输出格式包含 diff --git a//dev/null b/f（或 diff --git a/dev/null b/f）。而在 src/trivium/code-stage.ts:31-41 的 filesInDiff 中，正则 ^diff --git a\/(.+?) b\/(.+)$ 会提取出 m[1] 为 /dev/null（或 dev/null）并存入 files 集合。代码注释声称 /dev/null 只出现在 ---/+++ 行并不成立。结果导致：①在 src/trivium/code-stage.ts:133 的 classifyDiff 中，新增未跟踪文档（如 docs/foo.md）时，files 中混入的 dev/null 无法匹配任何 skip_globs，导致被误判为存在非文档路径并归类为 business，使 FR-23 的纯文档跳过逻辑完全失效；②补丁头部 buildDiffHeader 会将 /dev/null 记录为项目变更文件；③brief 与 drift 也会将 /dev/null 当作项目文件传递给模型与快照核对。

**建议**：在 filesInDiff 中解析 m[1] 和 m[2] 时，显式过滤掉值为 /dev/null、dev/null 等空源伪路径，防止非项目真实路径混入文件清单。

**问题**：hookPreCommit 错误复用了 approval_lock_scope 会话过滤条件，导致非会话或新会话中的提交操作直接绕过未裁决拦截。

**依据**：在 src/trivium/hooks.ts:196-203 中，hookPreCommit 对未裁决闸门进行了会话过滤：(ctx.config.gate.approval_lock_scope === 'global' || (g.session_id !== null && g.session_id === (input.session_id ?? null)))。依据设计 §8.5 与 PRD，会话级作用域是针对业务代码写入锁（hook-pre-write）设计的，以防锁死其它无关编辑；而 git commit 是版本提交操作，设计要求只要存在未裁决阶段就应当阻断提交。当前的实现会导致：若 review 是通过独立终端/CLI 启动的（g.session_id 为 null），或者开发者在 Claude Code 中重新开启了新会话，hookPreCommit 会判定会话不匹配而直接放行 git commit，造成未裁决代码被提前提交。

**建议**：审查 hookPreCommit 的作用域策略，针对存在未完成裁决的阶段，只要开启了 block_commit: true，提交拦截应面向整个仓库生效，不应因 session_id 不匹配或为 null 而放行。
