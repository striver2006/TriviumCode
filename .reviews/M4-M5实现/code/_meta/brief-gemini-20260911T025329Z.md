+## 一、四份 JSON Schema
+
+机读契约的唯一真理来源在 `skills/dual-critic/schema/`，由 `parse` / `gate` / `meta`
+共用，ajv（draft 2020-12）强校验。
+
+| Schema | 文件 | 生产者 | 消费者 |
+| :--- | :--- | :--- | :--- |
+| `trivium.review.v1` | `review.v1.json` | 两侧审查员（最终回答即该 JSON） | `parse` → `render` → `gate` |
+| `trivium.disposition.v1` | `disposition.v1.json` | Driver（裁决件 front-matter + 表格） | `gate --check` |
+| `trivium.run.v1` | `run.v1.json` | 编排器 | `gate`、`report`、人工审计 |
+| `trivium.config.v1` | `config.v1.json` | 人（`.trivium/config.yaml`） | `config` 四级合并后校验 |
+
+### `trivium.review.v1` 的硬约束
+
+- **意见编号前缀固定**：Antigravity 为 `AGY-`、ZCode 为 `GLM-`，两侧不冲突；
+  pattern 为 `^(AGY|GLM)-(r[0-9]+-)?[0-9]{2,}$`（序号至少两位，重跑追加轮次如 `AGY-r2-01`）。
+  裁决件解析器据此过滤数据行，所以编号不合规的意见会在闸门处被视为不存在。
+- **每条意见七个字段必填**：`id` / `severity` / `location` / `problem` / `evidence` /
+  `suggestion` / `confidence`，另需 `layer` 与 `kind`。
+- **每条意见必须是可单独接受或驳回的最小单元**——这是「逐条裁决」得以成立的前提。
+- `findings: []` **是合法的**（表示没发现问题），但 `summary` 与 `not_covered` 必须说明检查了什么。
+- `consulted` 必填，用于与工具轨迹交叉核对（§11.4）。
+
+### 解析失败的降级：`parse_fallback`
+
+两侧输出不符合 schema 时**不丢弃**：原文照常落盘，该侧标 `parse_fallback: true`，
+其意见按 `<前缀>-F<序号>` 虚拟编号参与裁决校验，但**不参与阻断判定**（§6.6 规则 8）。
+
+`gate` 会用**当前**解析器重试一次历史 `parse_fallback` 原文——解析器修好之后，
+旧的运行不该继续背着一个已经不存在的缺陷。

## 5. 审查要点与你这一侧的镜头

被审对象是**一段补丁**（`_meta/changes.diff`），不是一份文档。据此调整读法：

- **先读补丁，再读被改文件的完整上下文。** 补丁只给了变更行，
  而绝大多数真问题出在「这一行在它所处的完整函数/调用链里是否成立」。
  只看 diff 上下文几行就下结论的审查，会漏掉几乎所有竞态与契约漂移。
- **顺着调用链向上下游各走一层。** 改了签名，谁在调？改了返回形状，谁在解？
  改了错误处理，谁依赖那个异常？这些文件不在补丁里，但必须读。
- **补丁头部记了 `base` 与 `head`。** 你看到的是相对那个基线的变更；
  若正文与基线看起来不一致，如实写进 `not_covered`，不要自行推测。
- **实现偏离已批准的计划，本身不一定是错误**，但必须是显式的。
  发现偏离就指出，让 Driver 去裁决是「计划错了」还是「实现跑偏了」。
- **不要给出大段可粘贴的补丁。** 指出位置与方向即可。

判断标准：**这个问题会让线上出错、让后来的人误解、还是让下一次改动变难？**
三者之一即值得提；纯风格偏好不提。

**你这一侧的镜头：**

- 实现是否偏离已批准的计划：偏离本身不一定错，但必须是显式的
- 对外契约漂移：签名、返回形状、错误码、事件格式
- 无必要的复杂度：能用更少的抽象达成同样效果吗
- 跨文件调用链断裂：改了这里，链路上游/下游还成立吗
