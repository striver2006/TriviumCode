### AGY-01 · 重要（major）

| 项 | 内容 |

| 位置 | `plan §2.5` |
| 类别 | correctness ｜ 层次 plan |

**问题**：计划称同步路径在 runReviewLocked 中把 detail 串并进 ReviewOutcome.warnings「人读模式随既有的 warn 循环打印」，但 runReviewLocked 本身没有 warn 循环，既有 warn 循环位于 executeRun 内部且 cli.ts 在非 JSON 模式下不打印 ReviewOutcome.warnings，导致同步终端执行时剔除告警会被静默丢失。

**依据**：查阅 src/trivium/review.ts:1847-1851 与 :1800-1803，runReviewLocked 仅调用 rc = await prepareRun(opts) 后直接 return await executeRun(rc)，人读终端的 warn 循环位于 executeRun 内部（:1800-1803）。查阅 src/trivium/cli.ts:704-714，非 JSON 模式下 cli.ts 仅返回 out.exitCode、完全不处理 out.warnings。若按计划在 runReviewLocked 中在 executeRun 返回后再并入 warnings，executeRun 内部的 warn 打印早已完成，终端用户将完全看不到剔除告警。

**建议**：将 rc.mustReadPruned 的并入与打印时机明确放在 executeRun 内部（与既有的 renderGuardWarnings 告警一同处理），或在 executeRun 的入参 rc 中消费它，确保在 executeRun 内部的 warn 循环中统一打印，并在返回的 ReviewOutcome.warnings 中保留。

**问题**：findDenyConflicts 的伪代码在 under 方向直接调用 isOrchestratorReadable(entry) 与 classifyDenyPath(entry)，若 entry 为带 ~/ 前缀的写法，这两个辅助函数内部未调用 expandHome，会导致放行判断与分类失败。

**依据**：查阅 src/trivium/freeze.ts:95 与 :173，classifyDenyPath 与 isOrchestratorReadable 内部均直接以 normalizeAbs(hitPath, ctx.projectRoot) 计算，没有对 hitPath 做 expandHome。若 findDenyConflicts 直接向它们传递原始 entry（如 ~/.trivium/config.yaml 或 ~/.trivium/runs/...），路径会被拼在 projectRoot 之下，导致 isOrchestratorReadable 判负或 classifyDenyPath 误判为 peer-artifact。

**建议**：在 findDenyConflicts 的第 2 步中，明确将第 1 步已经完成 expandHome 与 normalizeAbs 的 entryAbs 传递给 isOrchestratorReadable(entryAbs, ctx) 与 classifyDenyPath(entryAbs, ctx)。
