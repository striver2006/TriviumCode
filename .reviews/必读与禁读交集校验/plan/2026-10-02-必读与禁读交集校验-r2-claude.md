### 1.4 `--context` 的解析

`cli.ts:633` 与 `topic-args.ts:621-624` 都只是按逗号切、trim、去空，**不做任何过滤**。MANUAL 配置表 `sensitive_globs` 一格（`MANUAL_user.md:449`）说的「主题参数解析时剔除」，代码里找不到对应的剔除——`sensitive_globs` 在 resolve 里只用于算补丁（`diffAgainst` 的排除参数），与 `--context` 无关。USAGE（`cli.ts:215`）写「并入必读清单」。

**顺带核出（不在本主题修）**：`buildMustReadList` 的存在性检查用 `path.join(projectRoot, c)`，绝对路径 `c` 会被拼成 `projectRoot + c`、判不存在、**静默丢掉**；`~/…` 不展开，同样丢掉。`../x` 这类越出项目根的写法若存在则原样进第 4 段。

### 1.6 必读不被核验

`consulted` 与 `min_project_reads` 只核「读了多少」，不核「必读清单读没读」——BACKLOG EV-02 原话「审查员无论读不读都会被判违规」说过头了：不读不罚；真实后果是**照必读去读的那一侧被判作废**（作废类），或平白多一条告警（只记一笔类）。

## 2. 设计

### 2.1 纯函数：交集判定（`brief.ts`，新增导出）

```ts
export type DenyConflictDirection = 'under' | 'contains';
export interface DenyConflict {
  entry: string;          // 第 4 段条目，原样（报错与告警按用户写法点名）
  denyEntry: string;      // 撞上的禁读条目，原样
  category: DenyCategory; // 命中点的类别
  direction: DenyConflictDirection;
}
export function findDenyConflicts(entry: string, denyPaths: readonly string[], ctx: DenyContext): DenyConflict[]
```

判定（逐条禁读条目 `d`）：

1. 两侧归一：`entryAbs = normalizeAbs(expandHome(entry), projectRoot)`，`dAbs = normalizeAbs(d, projectRoot)`——与 `classifyDenyPath` / `checkPeerLeak` 同一口径（`path.resolve` 吃掉 `./`、`..`、绝对路径，抹 `/private`），**不 realpath**（理由见 §4 ①）；
2. `under`：`isUnder(entryAbs, dAbs)`（含相等）。命中点是**条目本身**，**两个辅助函数一律传 `entryAbs`**，不传原始写法（r2：AGY-03——它们只做 `normalizeAbs`、不展开 `~`；`normalizeAbs` 对绝对路径幂等）：
   - `isOrchestratorReadable(entryAbs)` 为真 ⇒ 跳过（具名放行，决策二）；
   - `category = classifyDenyPath(entryAbs)`；`own-run-material` ⇒ 跳过（决策二）；
3. `contains`：`dAbs !== entryAbs && isUnder(dAbs, entryAbs)`。命中点是**那条禁读条目**：
   - `isOrchestratorReadable(d)` 为真 ⇒ 跳过（r2：GLM-02——宽 `sensitive_globs` 能让 `.trivium/config.yaml` 成为独立禁读条目；第 8 段渲染与机器侧都滤掉它，这里同口径）；
   - `category = classifyDenyPath(d)`；`own-run-material` ⇒ 跳过（防御性；当前禁读条目里只有运行根整棵，判 `peer-run-output`）。

「命中点」取法与 §10.1.1「分档的粒度是命中，不是禁读条目」一致：条目落在整棵运行根之下时，按条目自己的位置判它是己方还是对端。

`DenyContext`（`{ projectRoot, triviumDir, runRoot, critic, sensitiveGlobs }`）抽成 `brief.ts` 里的一个工厂 `denyContextFor(cfg, projectRoot, critic)`，第 8 段渲染（`brief.ts:309-315`）改用它——两处同一份上下文，不再各拼一份。

### 2.2 第 4 段条目带来源

`buildMustReadList` 改为返回 `{ path: string; source: MustReadSource }[]`（唯一调用点 `review.ts:772`；`test/` 无直接调用）。排序、去重、存在性判定、`context_max_docs` 上限**一律不变**——只是给每条记上来源。

export type MustReadSource = 'convention' | 'keyword' | 'context' | 'suggested' | 'own-history';

`Record` 穷尽由编译期守；`context` 一格不会出现在告警里（命中即拒跑），留着是为了穷尽。

### 2.3 `prepareRun` 改为三段（`review.ts:778-873`）

1. **冻结段**：逐侧 `freeze()`，只算快照（循环体其余部分挪到第 3 段）；
2. **`--context` 校验段**（新增）：逐侧对 `opts.contextPaths` 的**每一条原始写法**跑 `findDenyConflicts`。有任一命中 ⇒ `throw usageError(...)`（退 64）。此刻尚未置闸门、未写任何文件，零工件由既有结构保证；`startRun` 放锁后原样抛。
   - 判的是**原始写法**而不是 `buildMustReadList` 的产物：后者会静默丢掉绝对路径与 `~`（§1.4）、会按字符串把 `--context CLAUDE.md` 并进公约条目——用户写了它就是要审查员读，丢不丢、并不并都不改变「这个请求自相矛盾」；也不看存在性（指向一个尚不存在的对端审查件路径，同样是写错了）；
3. **渲染段**：逐侧
   - 第 4 段三张清单各过一遍 `findDenyConflicts`，命中的从**该侧**剔除（`mustRead` 里来源为 `context` 的条目此时必不命中——第 2 段已拦；剔除逻辑不按来源分支，统一处理）；`ownHistory` 同样过（§1.5 末行）；
   - 剔除记录攒进 `pruned: Array<{ critic, source, entry, conflicts }>`（r2：AGY-04，带 `source`）；
   - 其余照旧：`routeModel` → `renderBrief`（传该侧剔除后的三张清单）→ 暂存。
4. 循环后把 `pruned` 按条目聚合成 `mustReadPruned: PreflightWarning[]`（§2.5），挂到返回的 `RunContext` 上。

次序上的一个变化：原先第二侧 `routeModel` 的 69 可能先于本主题的 64 抛出，现在 64 在前。两者都在零工件区，退出码按「先报能自己改的那个」排，不影响别的不变式。

### 2.4 拒跑文案（64）

```
--context 里有路径落在本轮的禁读集里：任务书会一面把它列进必读，一面说读了会作废（或被记告警）。
  「.reviews/T/plan/2026-10-01-T-gemini.md」
    落在禁读条目「.reviews/T/plan/2026-10-01-T-gemini.md」之中 · 对端审查件（读了该侧作废）· 涉及 codex、glm 侧
  「.」
    含禁读条目「.env.example」· 凭据类文件（读了记一条告警）· 涉及 codex、gemini、glm 侧
    含禁读条目「.trivium」· 编排器状态目录（读了记一条告警）· 涉及 codex、gemini、glm 侧
    …另有 N 条
  出口：从 --context 里去掉这些路径，或改指它们之外的具体文件后重跑。本次没有写任何工件。
```

- 按 `--context` 条目分组；组内按（禁读条目, 类别, 方向）聚合出侧列表——同一路径对不同侧可能类别不同（对端审查件只对非所有者侧是禁读；运行目录下某侧子树对该侧是己方材料），逐组照实写；
- 每个 `--context` 条目最多列 10 行，其余写「…另有 N 条」（写 `.` 时禁读集可能上百条）；
- 类别人读标签集中成一张 `Record<DenyCategory, string>` 表（`own-run-material` 也给一格，编译期穷尽；它不会出现在文案里）。

### 2.5 剔除告警

形状：`PreflightWarning`（`{ name, detail }`），按条目聚合一条。

- `name: '必读清单剔除'`；
- `detail`（r2：AGY-02，按是否覆盖全部入选侧分支）：
  - 部分侧：`⚠️ 任务书第 4 段的「X」（来源：建议核实）落在 codex、glm 侧的禁读集里（对端审查件，读了该侧作废；禁读条目「Y」），已从这几侧任务书的第 4 段剔除，gemini 侧照常列出。来源是编排器自动生成的，无需处理；若确实需要审查员看到其中内容，请把它写进被审对象本身。`
  - 全部入选侧：`…落在各侧的禁读集里（…），已从各侧任务书的第 4 段剔除。来源是…`
  - 同一条目在不同侧类别不同时，括号里逐类列出（类别 + 侧）。

三个出口（r2：CODEX-01、AGY-01）：

1. **run.json 留痕**：`prepareRun` 构造骨架（`review.ts:984` 起）时把各条 `detail` 写进 `meta.gate.warnings`——既有字段、零 schema 变更，`gate --check` 回灌为 `run_warning`（只告警、不阻断，`gate.ts:187-200`）。`_meta/brief-*.md` 落盘的是剔除后的版本，这一笔让事后对账者知道少过什么。纯文档跳过轮不写（没有审查员会被拉起，与 `--start` 的「不计算」同口径）；
2. **`--start`**：`warnings = [...collectWarnings([...]), ...rc.mustReadPruned]`（追加在后，既有两项顺序不变）；纯文档跳过分支仍为 `[]`；
3. **同步路径**：由 `executeRun` 消费 `rc.mustReadPruned`——在汇总 `warnings`（`review.ts:1276` 一带）时把 `detail` 串排在 guard 告警之前并入，于是既有的 `warn` 循环（`:1800-1803`）在人读模式下打出来，`ReviewOutcome.warnings` 带给 `--json`。`runReviewLocked` 不改。工作进程从交接文件重建上下文时该字段给 `[]`——任务书已在 `--start` 时渲染进交接文件、告警已随 `--start` 返回，`--wait` 终态里不重复；`executeRun` 的纯文档跳过分支在汇总之前返回，不受影响。

第 4 段**不**加任何解释（决策四）。若剔除后某张清单为空，沿用既有的空清单兜底句（如「被审文档中未出现路径式引用」）——这句在剔除场景下措辞不精确，接受（§4 ③）。

## 4. 风险与边界

1. **不 realpath**：与 `checkPeerLeak`、`classifyDenyPath` 同口径（词法 + 抹 `/private`）。`--context` 经软链指进禁读区时校验认不出——而机器判定同样按词法认，审查员照必读的那个写法去读也不会被判命中，两段的矛盾就不存在；口径一致比单边更严重要；
2. **大小写不敏感的文件系统**：同上，沿用既有口径；
3. 剔除后某张清单为空时，兜底句（如「编排器未能定位到项目公约与需求设计文档」）措辞不精确；决策四定了第 4 段不解释，接受；
4. 禁读集在冻结时算定；冻结之后才出现的对端文件不在两段任何一段里，由既有机器判定兜，不属本主题；
5. `--context` 写成通配符不展开（现状如此），按字面路径判；
6. 拒跑点前移改变了与 `routeModel` 69 的先后（§2.3 末段）。

## 5. 暂缓（新登 BACKLOG）

- **EV-185**：`--context` 绝对路径与 `~/…` 写法在 `buildMustReadList` 里被静默丢掉（`path.join` 拼接后判不存在）。修它会改变第 4 段对这类写法的内容（以及越出项目根的路径该不该列），是另一项行为变更；本主题的校验按原始写法判，不依赖它；
- **EV-186**：`listOwnHistory` 写死收 `-(revised|response)-claude.md`：非 `claude` 当轮 Driver 时，Driver 自己的裁决件不进「己方历史」，而 `claude` 的旧裁决件会进、且它在禁读集里。本主题的剔除兜住了「同时出现在两段」那一半，「该进的没进」不在本主题。
