## 3. 三处设计与本机现实的冲突（本轮必须钉死）

这一节是 M6 存在的理由的直接证据：演进设计那张表在本机**对不上三处**。

### 3.1 冲突 A ·【最重要】`[profiles.*]` 段在本机零证据

演进设计 §3.1 把 `codex -p <name>` / `--profile` 当作模型路由主方案写入，
标注「项目负责人指定（最终运行形态 `codex -p <配置>`）+ 官方文档 · 中高」。

**本机实测：`~/.codex/` 下五份 toml（`config.toml` 与 `qwen` / `deepseek` /
`glm` / `gpt` 四份预置副本）里，一个 `[profiles.*]` 段都没有。**
项目负责人实际使用的是「**替换 `config.toml` 整个文件**」的切换模式，
配套四份模型目录 `models-*.json`。

这条冲突的严重性在于它**没有安全退路**：

- 「换文件」这条路对编排器是**禁区**——纪律 9「不动用户全局配置」；
- 若 `--profile` 实际不被接受，codex 侧的逐审核者模型路由就只剩
  `CODEX_HOME` 独立副本一条路（演进设计 §7.1 的 `isolation` 探针项），
  而那条路的可用性同样未经实测；
- 两条都不成立时，M8 的「逐审核者模型 + 三档思考等级」对 codex 侧**无法实现**，
  需求 R-3 / R-4 要按侧降级——这是设计级后果，不是实现细节。

因此 `profile_flag` 与 `isolation` 两项从「必测清单里的一项」**升为本轮的头号产出**。

### 3.2 冲突 B · 模型目录路径名对不上

## 4. 一道结构性准入条件：探针段是闭合形状

### 4.1 缺口

`ProbeSection`（[types.ts:159](../../../src/trivium/types.ts#L159)）只有
`agy` / `zcode` 两个**固定键**——即 BACKLOG **EV-05①**。连带两处同形：

- `DoctorOptions.only` 是手写三值 `'agy' | 'zcode' | 'env'`（[doctor.ts:29](../../../src/trivium/doctor.ts#L29)）；
- `checkpoint` 的 `probedSections` 是 `Set<'env' | 'agy' | 'zcode'>`。

三处都是**手工枚举 Agent/厂商身份**，与纪律 7 / 10 直接相抵。

### 4.2 为什么它是准入条件而不是「顺带做」

判据 J1 要求 `doctor --only codex` 有**确定结论**。结论落不进 `probe` 段，
就只能进一份 Markdown：`preflight` 读不到、`probeIsFresh` 管不着、
TTL 过期无从发现、M8 接入时还要再探一遍。那不叫「确定结论」。

所以 EV-05① 从「登记不修」**改判为 M6 第 1 步**。这是对已登记欠账的范围变更，
在此显式声明而不是悄悄带过。

### 4.3 一个必须先决定的键名歧义

`ProbeSection` 现有两键是 `agy` 与 `zcode`。对照注册表：

| Agent id | vendor | cliName | 现 probe 键 |
| :--- | :--- | :--- | :--- |
| gemini | `antigravity` | `agy` | `agy` ← **cliName** |
| glm | `zcode` | `zcode` | `zcode` ← **两者同名，看不出是哪个** |
| claude | `anthropic` | `claude` | — |
| codex | `openai` | `codex` | — |

**两家恰好让这个歧义不可见**：`agy` 取的是 cliName，而 `zcode` 的 vendor 与 cliName
碰巧同名。加第三家立刻分叉——`probe.claude` 是 cliName，vendor 却是 `anthropic`。

这与 EV-03 记的 `vendor === 'antigravity' ? 'agy' : 'zcode'` 是同一族形态：
**两值时恰好穷尽/恰好同名，放开就分叉。**

**拟定处置**：注册表新增显式字段 `probeKey`，登记而非从 vendor 或 cliName 推算。
理由与 `cliName` 当初「登记而不是从 vendor 三目算」的注释**逐字同构**——
推算出来的键在两值下恰好正确，第三家进来就悄悄错位，而错位的症状是
探针结论写到一个没人读的键上，**不报错**。
现有两家的 `probeKey` 分别登记为 `agy` / `zcode`，与盘上已有结论**逐字兼容**，
不产生迁移。

### 4.4 探针结论的形状

`AgyProbe` 与 `ZcodeProbe` 差异很大（`bin` vs `entry`、`json_schema_ok` /
`pty_required` vs `readonly_flags` / `response_field` / `model_override`），
但有一组**共有事实**：`version`、`models`、`path_deny`、`scratch_paths`、`isolation`。

拟定：抽 `CommonProbe` 承载共有事实，各家特有字段以交叉类型扩展；
`ProbeSection` 的各家键改为 `Partial<Record<ProbeKey, …>>`。
**`Partial` 是刻意的**——「这家还没探过」与「探过且结论为否」必须可区分，
这正是 M7b 第 6 步 `checkModelSlugs` 引入「无法校验」第三态时确立的口径。

## 6. 测试计划

探针的测试形态与前六步不同，需要单独说明，因为**常规手法在这里会失效**。

### 6.1 探针函数不能在 CI 里真跑

真实调用要凭据、要网络、要烧配额。所以分两层：

| 层 | 测什么 | 手法 |
| :--- | :--- | :--- |
| 单测 | **解析逻辑**：给定一段录制的 CLI 输出，判定结论对不对 | 录制真实输出存为 fixture，覆盖成功/失败/畸形三态 |
| 集成 | **段落落盘与合并**：`--only <x>` 只写该段、不擦别段 | 现有 `patchProbe` 测试的模式，纯文件系统 |
| 人工 | **真实调用本身** | `doctor` 实跑，结论进报告，不进 CI |

### 6.2 fixture 必须是录制的真输出，不是我编的

这条要写死。手编的 fixture 只能证明「解析器能解析我以为的格式」，
而探针存在的全部理由是「我以为的格式可能不对」。
每份 fixture 落盘时附注录制时间、CLI 版本、原始命令行。

### 6.3 变异验证

第 1 步的三条验收逐条做变异：`probeKey` 改回从 vendor 推算 → 假 Agent 的
键错位断言必须红；`Partial` 改回必填 → 「未探过」与「探过为否」的区分断言必须红；
`--only` 改回手写枚举 → 注册表跟随断言必须红。

第 2～4 步的变异面是解析器：把录制 fixture 里的关键字段改坏，
对应判定必须从 true 翻成 false 或 null，**不能静默沿用默认值**。
