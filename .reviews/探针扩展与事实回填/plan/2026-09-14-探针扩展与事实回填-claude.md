# 探针扩展与事实回填（M6）实施计划

## 0. 本计划的由来

M6 是演进设计 §14 实施路线的第一环，遵循 16.2 纪律 1「先探路后编码」。
它与 M7a / M7b 的关系是**并行而非串行**（演进设计 §14 依赖关系原文：
「M7a/M7b 独立于 M6 结论」），所以 M7b 六步先行合入并不构成对 M6 的欠账。

M6 要把 codex 与 claude 两家的能力，从**联网调研得到的文档推定**，
变成**本机实测得到的事实**。演进设计 §3.1 / §3.2 的每一条都带置信度标注，
且全文反复声明「一律以 M6 探针为准」——这份计划就是去兑现那句话。

**它不是新增功能。** M6 一行审查链路的代码都不改，产出物是三样：
探针实现、落盘的探针结论、以及回填进主设计 3.6 / 3.7 的事实表。

## 3. 三处设计与本机现实的冲突（本轮必须钉死）

这一节是 M6 存在的理由的直接证据：演进设计那张表在本机**对不上三处**。

### 3.1 冲突 A ·【最重要】`[profiles.*]` 段在本机零证据

演进设计 §3.1 把 `codex -p <name>` / `--profile` 当作模型路由主方案写入，
标注「项目负责人指定（最终运行形态 `codex -p <配置>`）+ 官方文档 · 中高」。

**本机实测：`~/.codex/` 下五份 toml（`config.toml` 与 `qwen` / `deepseek` /
`glm` / `gpt` 四份预置副本）里，一个 `[profiles.*]` 段都没有。**
项目负责人实际使用的是「**替换 `config.toml` 整个文件**」的切换模式，
配套四份模型目录 `models-*.json`。

这条冲突的严重性在于它**没有安全退路**：

- 「换文件」这条路对编排器是**禁区**——纪律 9「不动用户全局配置」；
- 若 `--profile` 实际不被接受，codex 侧的逐审核者模型路由就只剩
  `CODEX_HOME` 独立副本一条路（演进设计 §7.1 的 `isolation` 探针项），
  而那条路的可用性同样未经实测；
- 两条都不成立时，M8 的「逐审核者模型 + 三档思考等级」对 codex 侧**无法实现**，
  需求 R-3 / R-4 要按侧降级——这是设计级后果，不是实现细节。

因此 `profile_flag` 与 `isolation` 两项从「必测清单里的一项」**升为本轮的头号产出**。

### 3.2 冲突 B · 模型目录路径名对不上

| | 演进设计 §3.1 | 本机实际 |
| :--- | :--- | :--- |
| catalog 路径 | `~/.codex/model-catalog.local.json` | `~/.codex/models-qwen.json`（随 provider 一份） |

`model_catalog` 探针若按设计写死路径，会对一个**配置正确**的本机判出假阴性。
按原则 P7，实现一律读 `config.toml` 的 `model_catalog_json` 键，不写死路径。

### 3.3 冲突 C · 默认模型档与设计表不一致

本机 `config.toml` 当前 `model = "qwen3.6-flash"`、`model_reasoning_effort = "low"`，
而演进设计表里没有 3.6 这一档。

不过 `models-qwen.json` 的目录里 `qwen3.8-flash` / `qwen3.8-max` **都在**，
`models-deepseek.json` 里 `deepseek-flash` / `deepseek-v4-pro` **都在**——
四个 slug 与设计表一致，可全部实测。`deepseek.config.toml` 里
`model_reasoning_effort = "medium"` 是现成素材：设计称 DeepSeek 会把
`medium` 归并为 `high`，本轮直接验证这条归并映射是否真实发生。
那条映射是 `run.v2` 的 `effort_effective` 字段**存在的唯一理由**，
证伪了就要回头处理该字段的去留。

## 4. 一道结构性准入条件：探针段是闭合形状

### 4.1 缺口

`ProbeSection`（[types.ts:159](../../../src/trivium/types.ts#L159)）只有
`agy` / `zcode` 两个**固定键**——即 BACKLOG **EV-05①**。连带两处同形：

- `DoctorOptions.only` 是手写三值 `'agy' | 'zcode' | 'env'`（[doctor.ts:29](../../../src/trivium/doctor.ts#L29)）；
- `checkpoint` 的 `probedSections` 是 `Set<'env' | 'agy' | 'zcode'>`。

三处都是**手工枚举 Agent/厂商身份**，与纪律 7 / 10 直接相抵。

### 4.2 为什么它是准入条件而不是「顺带做」

判据 J1 要求 `doctor --only codex` 有**确定结论**。结论落不进 `probe` 段，
就只能进一份 Markdown：`preflight` 读不到、`probeIsFresh` 管不着、
TTL 过期无从发现、M8 接入时还要再探一遍。那不叫「确定结论」。

所以 EV-05① 从「登记不修」**改判为 M6 第 1 步**。这是对已登记欠账的范围变更，
在此显式声明而不是悄悄带过。

### 4.3 一个必须先决定的键名歧义

`ProbeSection` 现有两键是 `agy` 与 `zcode`。对照注册表：

| Agent id | vendor | cliName | 现 probe 键 |
| :--- | :--- | :--- | :--- |
| gemini | `antigravity` | `agy` | `agy` ← **cliName** |
| glm | `zcode` | `zcode` | `zcode` ← **两者同名，看不出是哪个** |
| claude | `anthropic` | `claude` | — |
| codex | `openai` | `codex` | — |

**两家恰好让这个歧义不可见**：`agy` 取的是 cliName，而 `zcode` 的 vendor 与 cliName
碰巧同名。加第三家立刻分叉——`probe.claude` 是 cliName，vendor 却是 `anthropic`。

这与 EV-03 记的 `vendor === 'antigravity' ? 'agy' : 'zcode'` 是同一族形态：
**两值时恰好穷尽/恰好同名，放开就分叉。**

**拟定处置**：注册表新增显式字段 `probeKey`，登记而非从 vendor 或 cliName 推算。
理由与 `cliName` 当初「登记而不是从 vendor 三目算」的注释**逐字同构**——
推算出来的键在两值下恰好正确，第三家进来就悄悄错位，而错位的症状是
探针结论写到一个没人读的键上，**不报错**。
现有两家的 `probeKey` 分别登记为 `agy` / `zcode`，与盘上已有结论**逐字兼容**，
不产生迁移。

### 4.4 探针结论的形状

`AgyProbe` 与 `ZcodeProbe` 差异很大（`bin` vs `entry`、`json_schema_ok` /
`pty_required` vs `readonly_flags` / `response_field` / `model_override`），
但有一组**共有事实**：`version`、`models`、`path_deny`、`scratch_paths`、`isolation`。

拟定：抽 `CommonProbe` 承载共有事实，各家特有字段以交叉类型扩展；
`ProbeSection` 的各家键改为 `Partial<Record<ProbeKey, …>>`。
**`Partial` 是刻意的**——「这家还没探过」与「探过且结论为否」必须可区分，
这正是 M7b 第 6 步 `checkModelSlugs` 引入「无法校验」第三态时确立的口径。

## 5. 四步拆分

每步一个完整周期：实现 → 代码双审 → 逐条裁决 → 人工审批 → 按接受项改 → 提交。

### 第 1 步 · 探针段按注册表打开

**改动面**：`agents/registry.ts`（加 `probeKey`）、`types.ts`（`ProbeSection` 泛化 +
`CommonProbe` 抽取）、`doctor.ts`（`--only` 取值由注册表派生、`checkpoint` 去枚举）、
`config.ts`（`defaultProbe` 随注册表生成）、`preflight.ts` 读侧跟随、
`registry-parity` 盯防点增补。

**验收**：①`doctor --only codex` 不再退 64 而是给出「已登记未实现」的确定答复；
②往注册表加一个假 Agent，`--only <它>` 与 `defaultProbe` 自动跟随、无需改 doctor；
③盘上已有的 agy / zcode 结论**逐字不变**（迁移零影响，用前后 YAML 比对断言）。

**这一步不碰任何真实 CLI，不烧配额。**

### 第 2 步 · codex 探针全清单

清单（演进设计 §3.1 原文，一项不减）：
`bin/version`、`exec_headless_read_ok`、`json_events`、`trace_source`、
`readonly_flags`、`model_override`、`effort_flag`、`model_catalog`、
**`profile_flag`**、`profiles`、`models`、`providers_ok`、`path_deny`、
`scratch_paths`、`isolation`、`auth`。

**优先级**：`profile_flag` 与 `isolation` 先做（§3.1 的头号冲突），
因为它们的结论决定后面几项怎么探——若 `--profile` 不被接受，
`model_override` 与 `effort_flag` 的实测手法要整体改走 `CODEX_HOME` 副本。

**必配的负对照**（缺了就是自证）：
- `readonly_flags`：`--sandbox read-only` 下**写文件必须失败**；
- `path_deny`：被 deny 的文件**必须读不到**，且轨迹里无该读取事件。

**模型与配额**：探能力不探质量，一律用 `qwen3.8-flash` + 最低 effort 档。
DeepSeek 侧只跑 `effort_flag` 的归并验证（`medium` → 回读实际值）与
`providers_ok` 探活，用 `deepseek-flash`。
每段探完即落盘（复用 `checkpoint` 机制），中断不浪费已烧配额。

### 第 3 步 · claude headless 探针全清单

清单（演进设计 §3.2 原文）：
`bin/version`、`headless_read_ok`、`stream_trace`、`readonly_flags`、
`model_flag`、`json_schema_ok`、`session_id_source`、`scratch_paths`、
`path_deny`（预期 false，配负对照）、**headless 在项目目录的信任行为**、`auth`。

「信任行为」单列的理由（设计原文）：若首跑需要人工信任，
则该侧**对新克隆仓库不可用**，必须如实标记，不能靠「我这台机器上是好的」糊过去。

### 第 4 步 · 入口承载面 + zcode 复测 + 收口

- **Driver 入口承载面探针**：codex 的 prompts 参数、zcode 的 skills 目录优先级与
  Hook 形态、antigravity 的 driver agent 定义——对应待拍板项第 3 条（J3）。
- **zcode `effort_flag` 复测**：0.16.5 记录为「无 effort 旗标」，本轮复测一次。
- **回填 J2 / J4**：主设计 3.6 / 3.7 事实表、坑清单报告、演进设计 §3.1/§3.2
  的置信度标注按实测升级或**下调**。

**下调也要写。** 实测证伪的条目必须留下「原推定 → 实测结论」的对照，
而不是把原文悄悄改掉——否则下一个人无从判断哪些结论有实测支撑。

## 6. 测试计划

探针的测试形态与前六步不同，需要单独说明，因为**常规手法在这里会失效**。

### 6.1 探针函数不能在 CI 里真跑

真实调用要凭据、要网络、要烧配额。所以分两层：

| 层 | 测什么 | 手法 |
| :--- | :--- | :--- |
| 单测 | **解析逻辑**：给定一段录制的 CLI 输出，判定结论对不对 | 录制真实输出存为 fixture，覆盖成功/失败/畸形三态 |
| 集成 | **段落落盘与合并**：`--only <x>` 只写该段、不擦别段 | 现有 `patchProbe` 测试的模式，纯文件系统 |
| 人工 | **真实调用本身** | `doctor` 实跑，结论进报告，不进 CI |

### 6.2 fixture 必须是录制的真输出，不是我编的

这条要写死。手编的 fixture 只能证明「解析器能解析我以为的格式」，
而探针存在的全部理由是「我以为的格式可能不对」。
每份 fixture 落盘时附注录制时间、CLI 版本、原始命令行。

### 6.3 变异验证

第 1 步的三条验收逐条做变异：`probeKey` 改回从 vendor 推算 → 假 Agent 的
键错位断言必须红；`Partial` 改回必填 → 「未探过」与「探过为否」的区分断言必须红；
`--only` 改回手写枚举 → 注册表跟随断言必须红。

第 2～4 步的变异面是解析器：把录制 fixture 里的关键字段改坏，
对应判定必须从 true 翻成 false 或 null，**不能静默沿用默认值**。

## 7. 分步与回滚

四步各自独立提交。前一步不合入不影响后一步的设计，但影响实施顺序：
第 2～4 步都要往 `probe` 段写结论，**必须等第 1 步合入**。

回滚粒度：任一步单独 revert 不破坏其余。第 1 步含类型改动，
revert 后盘上若已有 `probe.codex` 段会成为「多余键」——
`config.v2.json` 的 `probe` 段是 `additionalProperties: true`，**不会校验失败**，
只是没人读。这条已实测核正（M7b 第 6 步 GLM-05），此处复用该结论。

本计划 §2.2 记录了一条**我在起草期自己犯并纠正的前提错误**（把 `config.yaml`
没有 probe 段读成「探针从未落盘」）。保留它而不是改干净，
是因为下游的成本估算依赖这条事实：若按错误前提写，第 1 步会被估成
「还要把落盘链路从零建起」，范围凭空大一圈。

同一形状的风险在本计划里还有一处未消解：§3 的三条冲突都来自我**今天读配置文件**
得到的观察，而不是来自运行 codex 本身。`[profiles.*]` 段不存在是文件事实，可靠；
但「所以 `--profile` 不可用」是我的**推断**——codex 完全可能接受一个
指向缺失 profile 的旗标并回落默认值，也可能 profile 支持从别处加载。
第 2 步的头一件事就是把这个推断送去实测，**在实测之前它不得被当作结论引用**。
