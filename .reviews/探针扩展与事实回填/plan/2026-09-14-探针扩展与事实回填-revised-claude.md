### 0.1 本轮最重的一条：我的核心论证方向反了

**GLM-01（重要）** 指出计划 §3.1「冲突 A」——那是我给 M6 排优先级的**头号依据**——
建立在对 `-p` 机制的错误模型上。裁决前我亲验了两条一手证据：

```
-p, --profile <CONFIG_PROFILE_V2>
        Layer $CODEX_HOME/<name>.config.toml on top of the base user config
```

```
# DeepSeek 官方配置 —— 自包含，供 `codex -p deepseek` 使用
```

**GLM-01 成立，而且比它陈述的更准。** 参数类型名直接叫 `CONFIG_PROFILE_V2`——
盘上那四份 `<name>.config.toml` **就是 profile 本身**，不是绕过 profile 的替代品。
于是我写进计划的三句话逐句作废：

| 我写的 | 实际 |
| :--- | :--- |
| 「用户实际用的是换文件模式」 | 那**就是** profile 机制（V2 形态） |
| 「`[profiles.*]` 零证据 → `--profile` 可能不可用」 | 零命中是 V2 机制下的**预期**，与可用性无关 |
| 「换文件对编排器是禁区（纪律 9）」 | `-p` 只做**分层叠加**，不写 `config.toml`，完全可用 |

我读那四份文件时只 grep 了非敏感键名，**跳过了注释行**——而答案就写在每份文件的第一行。

### 0.2 这条错误的形状：标注了不确定性，然后照用不误

计划 §10 的自查里我写过：

> 「`[profiles.*]` 段不存在是文件事实，可靠；但『所以 `--profile` 不可用』是我的**推断**
> ……在实测之前它不得被当作结论引用。」

**然后我在 §3.1 里把它当结论引用了**——写下「没有安全退路」「设计级后果」
「R-3/R-4 按侧降级」，并据此把 `profile_flag` 提为头号产出。

这与记忆里那条 `assertion-scope-creep` 同族，但形状更隐蔽：上一次是**悄悄**扩大适用范围，
这一次我**明确写下了免责声明，下游文字却完全不受它约束**。
标注不确定性不等于处理了不确定性——**免责声明写在别处，就等于没写**。
本次修订把处置写死：§3.1 改为陈述机制差异本身，任何严重性判断一律不出现在实测之前。

### 0.3 一条真正的连锁缺陷（GLM-01 后半）

按设计原文，第 2 步的 `profiles` 探针项定义是「`config.toml` 的 `[profiles.*]` 名单回读，
供 preflight 校验」。按 V2 机制，**该名单恒为空**。而 M8 的未知 profile 预检拦截
（演进设计 §7.1 要点 4）是「名单为空即跳过」——于是那道拦截会**静默失效**。

这正是本项目反复反对的「两值下恰好正确」形态，而我差点把它当既定探针项抄进计划。
这条比冲突 A 的严重性判断更值得留，因为它是一处**会真的漏掉东西**的缺口。

## 1. 逐条裁决

### GLM-01 · 重要 —— 接受

**裁决**：接受，且按其建议**整段重写**冲突 A。

**为什么不是部分接受**：我原本考虑保留「机制与设计描述不符」这半句、只删严重性叙事。
但那样仍然把「不符」写成了一个待解决的问题，而实际上**不符的是设计文档，不是本机环境**——
演进设计 §3.1 描述的 `[profiles.<name>]` 段是 Codex 的 V1 profile 形态，
0.154.0 已换成 V2 文件分层。这是一处**文档过期**，该修的是文档。

**落点**：

1. §3.1 改写为「冲突 A · `--profile` 的机制形态与设计描述不符（V1 段式 vs V2 文件分层）」，
   **删除全部严重性判断**（「没有安全退路」「设计级后果」「R-3/R-4 按侧降级」）。
   退路清单如实列三条：`-c key=value`（dotted path，TOML 解析，`--help` 明载）、
   `-p <name>`（文件分层，本机在用）、`CODEX_HOME` 副本（兜底）。
2. 第 2 步探针清单**增** `config_override` 项：实测 `-c` 的 dotted path 覆盖、
   provider 覆盖、以及与 `-m` / `-p` 的叠加优先级。
3. 第 2 步的 `profiles` 项**改写定义**：由「`[profiles.*]` 名单回读」改为
   「枚举 `$CODEX_HOME/*.config.toml`，或实测 `-p` 的实际读取来源」——
   并在计划里写明**改写理由是 M8 预检拦截会因空名单静默失效**，
   否则下一个人会把它改回去。
4. 演进设计 §3.1 第 102 行与 §7.1 的 `profiles` 探针定义、
   「CODEX_HOME 副本须整份携带 profiles 段」注释，一并列入第 4 步回填清单。

**保留 GLM 自己提的警告**：`--help` 也可能说谎（zcode `--max-turns` 先例，
`probes/zcode.ts:61-66`）。所以上述全部按「文件级/帮助文本级证据」记，
最终结论仍以第 2 步实测为准——这一次不再把帮助文本当成实测。

## 4. 一条要带走的教训

本轮 12 条零驳回，而我在 §8 主动请审查者检查的四个焦点，**四个都判我这边错**。
这不是「审查员太严」，是一个可复现的方法缺陷：

> **我怀疑对了地方，但每一处都选了错的那一边。**

三条具体成因，都指向同一件事——**取证不完整就停手**：

1. 读那四份 toml 时 grep 了键名、**跳过注释行**，而答案在第一行（GLM-01）；
2. 引用演进设计时取了支持我判断的那段、**没读相邻的对策行**（AGY-02）；
3. 列改动面时读了要改的文件、**没有反向 grep 谁在消费 `cfg.probe.*`**（AGY-03）。

而 §10 的自查之所以没接住，是因为它**只标注了不确定性，没有约束下游文字**。
处置写进第 1 步的实施纪律：**凡标注为「推断」的结论，在实测前不得被任何严重性判断引用；
若下游确实需要它，就先去取证，取不到就把下游那段删掉。**

这条与记忆里的 `assertion-scope-creep` 同族，形状是它的一个变体：
上一次是悄悄扩大适用范围，这一次是**明写了免责声明却照用不误**。
