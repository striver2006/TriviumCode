## 总判断

最危险问题是 probeClaudePathDeny 将未证实状态（既未泄漏也未记入 denials）错误塌缩为 supported: false，文案自称「无从证实」字段却落确定否定，会误导 M9 降级第 ③ 道屏蔽（AGY-01）；
其次若读探针偶发超时导致 read.init 为空，readonly_flags 留空会被 claudeSeverity 误判为阻断级「只读保障不成立」假失守（AGY-02）；
此外 claudeArgs 硬编码了探针专用预算与模型且包含未用参数 cwd，与 P7 纪律冲突（AGY-03）；trace_path_structured 绝对路径子串匹配在软链与相对路径下易假阴性（AGY-04）；
trust_prompt_required 三元表达式永不为 true 使声称的守卫链路失真（AGY-05）；报告对 EV-01 归因将常规读与 git 通道混淆，且将 Agy/ZCode 既有需求误称为「只来自 codex」（AGY-06）。
针对焦点二：denied_tool_in_trace 现行提示词过软易引出纯文本推脱，提示词适度加强配合现有三态兜底更为稳妥。

**结论**：`request-changes`

### AGY-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/probes/claude.ts:789` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：probeClaudePathDeny 将未证实状态（哨兵未泄漏且未记录 denials）直接判定为 supported: false，文案自认「无从证实」而字段却落确定否定，会导致 M9 误将可用的路径级 deny 降级。

**依据**：在 src/trivium/probes/claude.ts:788-795 中，当 leaked === false && recorded === false 时（例如模型未发起读取工具调用），函数返回 supported: false，而 method 明确注明「哨兵未出现，但该次尝试也没记入 permission_denials——挡没挡住无从证实」。在 src/trivium/types.ts:251 中 PathDenyProbe.supported 定义为 boolean | null，null 正是未得出结论态。此处与上一轮 denied_tool_in_trace 的塌缩错误完全同形；若模型偶然未调用 Read，落盘的 supported: false 会导致 M9 的第 ③ 道屏蔽（设计 §10.1）退化为事后核验，误杀本侧的核心隔离优势。

**建议**：仅在 leaked === true（哨兵泄漏）时返回 supported: false；在 !leaked && !recorded 时返回 supported: null，与三态契约及 method 文案对齐。

### AGY-02 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/probes/claude.ts:874` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | high |

**问题**：probeClaude 未在 read.init 为空（如读探针超时或网络报错）时妥善处置 readonly_flags，导致 claudeSeverity 将偶发读超时误判为阻断级「只读保障不成立」。

**依据**：在 src/trivium/probes/claude.ts:874-891 中，probe.readonly_flags 仅在 if (read.init) 成立且无 MCP 工具时才被填充；若 read 探针发生网络超时或在输出 init 事件前报错退出，read.init 为 null，readonly_flags 保持空数组 []，同时 breach.txt 负对照也未产生 breach。此时在 src/trivium/doctor.ts:164-173 中，claudeSeverity 优先判断 probe.readonly_flags.length === 0，直接抛出阻断级 blocker（「claude 只读保障不成立：工具面混入了写工具，或负对照下文件仍被创建」），完全盖过了 line 178 本应给出的 note（「⚠️ 读文件探针未得出结论……」）。这使偶发读超时被误报为严重安全失守。

**建议**：在 probeClaude 中，当未观察到 read.init 时明确记录工具面状态未测（或避免让未探状态伪装成失守），并在 claudeSeverity 中仅在确认负对照 breach 或明确检出 MCP 工具混入时才报只读失守 blocker。

### AGY-03 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/probes/claude.ts:585` |
| 类别 | contract ｜ 层次 code |

**问题**：claudeArgs 宣称为「唯一构造处」，但硬编码了探针专属参数（预算 $0.20、Haiku 默认模型、固定工具列表），包含死参数 cwd，且与 P7 纪律由适配器读取 readonly_flags 的设计相抵触。

**依据**：在 src/trivium/probes/claude.ts:585-610 中，claudeArgs 将 --max-budget-usd 硬编码为 PROBE_BUDGET_USD（0.20 美元），这满足最小探针需要，但 M9 作为独立审查员执行全量任务时必然因预算过低熔断；其入参声明了 cwd: string 但在函数体内从未被读取；且 src/trivium/types.ts:358 明确标注 ClaudeProbe.readonly_flags 的消费方是「M9 适配器构造命令行（P7）」，若 M9 必须复用 claudeArgs，则 P7 适配层只读探针结论的纪律被硬编码架空。

**建议**：剥离探针专用硬编码，将 claudeArgs 定位为参数拼装纯函数，支持传入可选预算、模型与额外参数，移除未引用的 cwd，明确探针与未来 M9 适配层在参数拼装上的职责边界。

**问题**：trace_path_structured 采用绝对路径精确子串匹配，在 macOS 临时目录软链及模型相对路径调用下存在假阴性风险。

**依据**：在 src/trivium/probes/claude.ts:860-862 中，判定为 v.includes(fx.openFile)。在 macOS 上 src/trivium/util/fsx.ts:118 的 makeTempDir 返回 /var/folders/...，而系统真实路径为 /private/var/folders/...；且 Claude Code 在执行项目内文件读取时常使用相对路径 README.md。此时模型即使在 tool_use.input.file_path 中传入了结构化相对路径或 realpath，v.includes(fx.openFile) 均会判为 false，导致 trace_path_structured 误报为 false，并在 M9 中引起不必要的文本回退。与 test/unit/claude-events.test.ts:1168 中以 includes('sentinel.txt') 判定的口径脱节。

**建议**：判据改为检查入参是否包含目标文件名 path.basename(fx.openFile) 或将其归一化后比对，避免软链前缀或相对路径导致假阴性。
