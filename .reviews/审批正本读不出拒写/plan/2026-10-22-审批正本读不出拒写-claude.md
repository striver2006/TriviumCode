# 审批正本读不出拒写 · 实施计划（原稿）

- 主题：审批正本读不出拒写（BACKLOG EV-248）
- 执笔：claude（Driver）
- 日期：2026-10-22

## 〇、要解决的问题

审批正本是主题根下的 `task.json`（`src/trivium/meta.ts:268` 的 `taskPath`），进 Git，`approvals[]` 是「谁在何时表过态」的唯一持久记录。

现状（行号取自 `e34c23d0`）：

1. **两个写入口用宽松读。**`updateTaskAsync`（`meta.ts:348-364`，`updateTask` 只是它的同步外壳，`meta.ts:328-334`）在锁内调 `readTask`（`meta.ts:316`），后者对 `unreadable` 一样回落 `emptyTask`。随后照常 `mutate` 并原子写回——读不出的正本被**整份覆盖**成只含本次改动的新正本，`approvals` / `runs` / `drivers` / `disputes` 全部清空。
2. **`gate --check` 先写后判。**`cli.ts:1614-1641` 每次校验都先经 `updateTask` 写 `joint_checks`（共同阻断三态，`result.jointCheck` 存在即写）、命中 `joint_blocker_rejected` 时再写 `disputed`；而「本轮是否已表态」的判定 `humanDecision` 在其后（`cli.ts:1680`）。于是正本写坏后跑一次 `--check`：坏件先被覆盖，`humanDecision` 读到的是刚写下的新正本（`state: 'ok'`、`approvals: []`），判成 `undecided`，闸门照常推进（B/C/D 立 `awaiting_approval`、A 回 `idle`）。`cli.ts:1682` 那条 `TASK_UNREADABLE_HOLD` 分支在有共同阻断三态的轮次上**实际不可达**。
3. 同样经这两个入口写正本的调用方共 8 处（全仓 grep `updateTask\b` / `updateTaskAsync` / `registerRun(` 所得，无别处直接写 `taskPath`）：

| # | 调用方 | 位置 | 写正本之前已做的落盘 |
| :-- | :-- | :-- | :-- |
| C1 | `gate --check` 共同阻断三态 | `cli.ts:1621` | 无（但在已表态判定之前） |
| C2 | `gate --check` 争议标记 | `cli.ts:1637` | C1 |
| C3 | 审批 / 拒绝 / 放弃 `recordApproval` | `approval.ts:253` | **`setGateChecked` 已把闸门改成 approved / rejected / abandoned**（`approval.ts:233`） |
| C4 | `topic claim` | `cli.ts:1034` | 无 |
| C5 | `verify` 登记 `registerVerifyRun` | `verify.ts:335` | 验证记录 `-verify.md`、`verify/_meta/verify-〈id〉.json`、`verify/_meta/run-〈id〉.json`；命令已执行完 |
| C6 | `review` 准备阶段 `registerRun` + 任务目标 | `review.ts:1441` / `review.ts:1455` | 闸门置 running、brief / 补丁、run.json 骨架、运行目录 |
| C7 | 纯文档跳过收尾 `registerRun` | `review.ts:1518` | run.json 已写成 success |
| C8 | worker 收尾 `registerRun`、事后收尾 `unfinishedTaskEntryStep` | `review.ts:2297` / `meta.ts:1019` | run.json 终态 |

只把写入口改成「读不出就抛错」不够：C3 会留下「闸门已放行、正本没有审批记录」的半截态，C5 / C6 / C7 会留下「run.json 在、正本未登记」的半截态。所以每个调用方都要定「在哪里先判、判不过退什么、来不及先判时怎么收」。

## 一、目标与非目标

**目标**

- G1 两个写入口改用严格读：`unreadable` 拒写并抛受控错误，点名 task.json 绝对路径与读不出原因，给出从 Git 找回的出口；`missing` 照旧按新主题从 `emptyTask` 起写。
- G2 每个调用方在**第一次落盘之前**先判正本可读，判不过零写入退出；来不及先判（判后写前被搅坏的竞态）的，明确收尾方式。
- G3 `gate --check` 在正本读不出时不写任何东西、不推进闸门。
- G4 读不出的出口与既有的两处（`previousRoundFacts`、`TASK_UNREADABLE_HOLD`）统一成同一段文案、同一个退出码。
- G5 单测与集成用例覆盖每个调用方的读不出形态，新主题首次写入不受影响；变异验证。

**非目标**

- 不改读侧的宽松调用方（`report`、`status`、`driver-claim.ts:134` 第 2 级声明判读等）：它们只读不写，读不出当空是它们既有的、各自有理由的口径。
- 不做自动修复或自动从 Git 恢复：恢复是人的决定，编排器只给出口。
- 不处理「worker 跑到一半正本被搅坏」的竞态以外的新形态（见 §八 残余）。

## 二、统一的拒写错误与出口文案（`meta.ts`）

新增：

```ts
/** 审批正本读不出时的共用出口段：点名路径与原因，给 Git 找回的办法（写入口拒写、续链判定、校验 / 停点保守处理共用） */
export function taskUnreadableExit(l: ArchiveLayout, error: string | undefined): string
/** 写入口拒写抛的受控错误，退出码 GATE_BLOCK（2） */
export function taskUnreadableError(l: ArchiveLayout, error: string | undefined, what: string): TriviumError
```

- 出口段内容：`审批正本 〈绝对路径〉 读不出（〈原因首行〉）。` + `读不出时写回会把它整份覆盖成空正本，审批记录（approvals）随之丢失，所以本次不写。` + 找回办法三行：`git log --oneline -- 〈路径〉` 看历史、`git diff -- 〈路径〉` 看当前改动、`git restore --source=HEAD -- 〈路径〉` 恢复到最近一次提交（未提交过的改动会丢，先看 diff）。路径取绝对路径（与 `unreadableRunMetaExitAt` 同样按布局拼出）。
- `what` 是调用方的一句「本次没做成什么」（如「未记录审批，闸门保持不变」），放在出口段之前，让每个调用方的文案说清自己的那一半。
- **退出码取 2（`GATE_BLOCK`）**：与既有的两处读不出出口同口径——`previousRoundFacts` 读不出正本退 2（`review.ts:310-317`）、`topic claim` 留痕读不出退 2（`cli.ts:1009`）。不取 69（ENV）：那是 CLI / 认证 / 归档根不可写一类环境问题，这里是归档内容坏了。
- `updateTaskAsync` 锁内改为 `readTaskStrict`：`unreadable` ⇒ `throw taskUnreadableError(l, error, '本次未写入')`，**不调 `mutate`**（回调里可能有 I/O 与判定，读不出时不该跑）；`missing` ⇒ `emptyTask` 照旧；`ok` ⇒ 照旧。
- 既有两处改用 `taskUnreadableExit`：
  - `previousRoundFacts`（`review.ts:310-317`）：保留首句「无法判定轮次链……不按各轮都已表态新起一链」，后半换成共用出口段。
  - `TASK_UNREADABLE_HOLD`（`approval.ts:142`）：由常量改为 `taskUnreadableHold(layout, error)` 函数，首句「按已表态保守处理：闸门状态保持不变」保留，后半换成共用出口段；`humanDecision` 的返回带上 `error`（新增可选返回形态或另给 `humanDecisionDetailed`，以不改既有调用方签名为准）。

### 三.1 `gate --check`（C1 / C2，G3）

`cli.ts` 的 `--check` 段改为：

1. `checkAdjudication` 照旧（只读）。
2. 新增：`const taskRead = await readTaskStrict(ref.layout)`。
3. `taskRead.state === 'unreadable'` 时：
   - `result.failures` 追加一条 `{ code: 'task_unreadable', message: taskUnreadableExit(...) 的首两句 }`，`result.ok` 置 false（`GateFailureCode` 联合补 `task_unreadable`）；
   - JSON 照常输出（`ok: false`，轮次事实照给，方便播报），人读模式经 `renderGateResult` 打出；
   - `warn(taskUnreadableHold(...))` 打一次完整出口段；
   - **直接 `return EXIT.GATE_BLOCK`**，不进入下面的写、已表态判定、闸门迁移与阻断计数归零。
4. 可读（`ok` / `missing`）时其余逻辑不变；`missing` 仍会由写入口新建正本（既有行为）。
5. 原 `cli.ts:1682` 的 `decision === 'unreadable'` 分支保留（判后写前被搅坏、写入又恰好成功之外的路径已无法到达这里，但留着成本为零）——**改为**：在第 3 步之后它只在竞态下可达，文案同样换成 `taskUnreadableHold`。

为什么校验通过也退 2：`--check` 的契约包含「每次都落共同阻断三态」（`cli.ts:1605-1613` 注释），这一笔落不了，本轮的校验就没有完成；退 0 会让命令 A 按 `next_action` 往下走（S4.5 认领、S5 编码），而闸门停在 `review_done_awaiting_disposition`，Hook 照拦——正是「闸门与正本不一致」的半截态。

### 三.2 审批 / 拒绝 / 放弃（C3）

- `cmdApproval`：在 `stages` 算出之后、approved 的复核循环之前，`readTaskStrict(主题布局)`；`unreadable` ⇒ `throw taskUnreadableError(..., '未记录审批，闸门保持不变')`。拒绝与放弃同样先判（它们同样写正本）。
- `recordApproval`：在 `setGateChecked` 之前再判一次（函数自身的前置条件，不依赖调用方）。
- **补偿**：`setGateChecked` 已应用、随后的 `updateTask` 抛 `taskUnreadableError`（两次判之间正本被搅坏）时，用 `setGateChecked({ state: 原 gate.state, expect: { state: [i.decision], runId: gate.run_id } })` 比较-交换回原状态，再把原错误上抛。补偿只回退本次刚写下的那一笔：期望状态与 run_id 都对得上才改，否则说明闸门已被别人接管，不动它，并在错误文案末尾追加一句「闸门当前状态已不是本次写下的 〈决定〉，未回退，请 `trivium status` 核对」。补偿本身失败（锁 / 写盘异常）同样追加一句如实报告，不吞原错误。阻断计数归零（`resetStopBlockCount`）在 `updateTask` 之后，抛错时不执行，无需回退。
- 退出码 2；拒绝 / 放弃也是 2（同一个错误）。

### 三.3 `topic claim`（C4）

无前置落盘，`updateTaskAsync` 锁内判即是唯一判定点，抛错原样上抛，退 2。`resolveStageDriver` 第 2 级的宽松读不改（只读，见非目标）。skill 的 S0.8 / S4.5 目前只写了退 0 / 退 64 的处置，补一句「退 2（审批正本读不出）同样原样转述并停止，恢复由用户在终端做」。

### 三.4 `verify`（C5）

- `cmdVerify` 在确认主题存在之后、`allocateRunId` 之前判一次；`unreadable` ⇒ 抛 `taskUnreadableError(..., '未执行任何编译测试命令，未写验证记录')`，退 2。
- 竞态（命令跑完、`registerVerifyRun` 时正本才坏）：验证记录与 verify 的两份 `_meta` 已落盘，不删（它们是真实执行的记录，FR-21 保留工件）。`runVerify` 捕获 `registerVerifyRun` 的 `taskUnreadableError`，把「本次验证结论 + 未登记进正本」写进错误文案后以 2 退出：退 2 盖过 0 / 1，因为验证记录没进留痕护栏（GLM-r2-08 的初衷），这一轮不能当收口；文案里写明本次命令结论是通过还是失败，**不得**因退 2 而把失败说成别的、也不得把通过说成已收口。

### 三.5 `review` 准备与纯文档跳过（C6 / C7）

`prepareRunClaimed` 在 `resolveReviewLoop`（`review.ts:966`）之后、`allocateRunId`（`review.ts:968`）之前判一次：

- 位置理由：`resolveRerunIndex` / `resolveReviewLoop` 都只读；`allocateRunId` 起开始占运行目录。排在 `resolveReviewLoop` 之后，是让「有前序轮次」的场景照旧先由 `previousRoundFacts` 报轮次链语境的那句（集成 L10 的断言不变），没有前序轮次的场景（新阶段的第一轮，`previousRoundFacts` 在 `ids.length === 0` 时根本不读正本）由这里兜住。
- 覆盖 C6 的两笔写与 C7：纯文档跳过的 `skipVerdict` 在 `prepareRunClaimed` 里算出，跳过收尾在 `executeRun` 里，二者都在这次判之后。
- 零工件：抛错时运行目录由外层 `prepareRun` 删除（EV-218 既有）；闸门尚未置 running。

### 三.6 事后收尾（C8）

不加先判：worker 收尾时正本已在开跑前判过可读，坏在运行中属于竞态。写入口抛错后：`executeRun` 收尾的 `registerRun` 抛出 ⇒ worker 异常分支打出 `taskUnreadableError` 的文案、`finalizeFailedRunMeta` 按「仍为 running 才写」不改已是终态的 run.json、同步正本那一步报未改、`finally` 回收闸门。留下的形态是「run.json 终态、正本坏件原样」，提交时 `hook-pre-commit` 的锚 ② 已按「主题元数据不可读」拦（`hooks.ts:1496-1499`），不会被静默带进 Git。这一格只补用例确认文案里有 task.json 路径，不改代码。
