**问题**：`reorderRequestedFirst` 用原样键查表 `providers[providerKey]`，而 `providerKey` 来自 `qualifyAgainstCliConfig`→`legacyProviderMembers`，那里的键是 `key.trim()` 的规整形态（与导入器 `let u=a.trim()` 同规则）。副本源里 provider 键带首尾空白时：限定通过（`qualified` 非空，写进副本的 `model.main` 用规整键，与导入器一致、覆盖照旧生效），置首却查不到，返回 `applied:false` + 「副本源里没有 provider …」——这句话与事实相反，而按计划 §4 该次读数不落 (F1)/(F3)，实验会把它读成「置首未生效」并去查不存在的形态问题。

**依据**：在产物上只读实测（dist 版模块）：`reorderRequestedFirst({provider:{' bp ':{models:{A:{},B:{}}}}}, 'bp','B')` ⇒ `{"variant":"requested-first","applied":false,"reason":"副本源里没有 provider bp"}`，同一份配置的 `legacyProviderMembers` 会把它规整成 `bp`（故 qualify 通过、`model.main` 写得进）；读 src/trivium/probes/zcode.ts:775-800 与 src/trivium/adapters/zcode.ts:568-586（`const k = key.trim()`）；对照包内 `NHa`（legacy 导入）`for(let[a,l] of Object.entries(t.provider??{})){let u=a.trim(); …}` 亦证两条实现都规整 provider 键。成员侧无此问题（比较时已 trim，实测「id 带空白」用例通过）。

**建议**：定位 provider 时改用规整比较（扫描 `Object.keys(providers)` 取 trim 后相等者，或让 `qualifyAgainstCliConfig` 回传匹配到的原始键），使「找不到 provider」这句只在真找不到时出现；顺带在注释里点明「键查表与导入器同规则」也覆盖 provider 段。
