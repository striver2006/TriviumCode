## 2. 聚合规格（拟并入主设计 13.2，纪律 6b）

> 以下是并入 13.2 的条文草案，§6 拍板后按结果定稿。凡标「【D-n】」处随拍板改写。

### 2.1 总则

- **论域**：聚合只读报告已经读出的东西——时间线轮次（`rounds`）与未进时间线的运行（`unlistedRuns`），数据源仍只有 `.reviews/`（P4）。
- **两个维度正交**（R23）：Driver 维度按 run.json 的 `driver`（发起方）分组；审核者维度按意见的提出方（产出方）分组。同一个 Agent id 可以同时出现在两张表里，各计各的，不互相抵扣。
- **读不到就说读不到**：凡分子或分母取不到，格子写「—」，不补 0。

### 2.2 按 Driver 聚合

- **分组键**：时间线轮次按该轮 run.json 的 `driver`；未进时间线的运行按它自己 run.json 的 `driver`。
- **读不到 Driver 的轮次单独成组**（组名「读不到 Driver」），排在最后，**不归给缺省 Driver、也不归给该阶段的认领声明**——声明说明的是「谁声明要写」，不是「那一轮是谁发起的」。该组逐轮列原因：「找不到对应的 run.json」或「run.json 读不出（〈成因〉）」。该组只给轮次数与原因，意见数、裁决、采纳率一律「—」：读不到 Driver 就不知道该找谁的裁决件，按任何后缀去试都是猜。
- **run.v1 迁移轮次【D-3】**：推荐归 claude 并在该行注明「其中 N 轮为 run.v1 迁移，Driver 按 v1 惯例记为 claude」。
- **行**：每个（Driver, 阶段）一行，再给每个 Driver 一行「合计」；Driver 按注册表顺序，阶段按 plan / code / bug【D-2】。
- **列与口径**：

  | 列 | 口径 |
  | :--- | :--- |
  | 轮次 | 该组时间线轮次数（含状态非 success 但产出了审查文档的轮次） |
  | 已裁决 / 未裁决 | 有无本轮裁决件（按该轮 Driver 后缀定位）；未裁决轮次的意见计入意见数，**不进**采纳率分子分母 |
  | 意见数 | 该组各轮各侧合格意见之和（`findings`，不跨侧去重）；逐条降级的另记「另 N 条逐条降级」；结论读不到的侧（失败、超时、整份回退）不贡献，不记 0 |
  | 接受 / 驳回 / 暂缓 | 该组已裁决轮次裁决表的行数之和 |
  | 采纳率 | 接受 ÷（接受 + 驳回 + 暂缓）；分母为 0 写「—」；整份回退编号的处理【D-1】 |
  | 未进时间线的运行 | 该 Driver 发起、没产出审查文档的运行数（取消、异常、全侧失败等，不占轮次号，原因见时间线下方那张表） |

- **不变式**：各 Driver 组（不含「读不到 Driver」组）的接受 / 驳回 / 暂缓之和 = 第二节全主题采纳率的分子与分母（读不到 Driver 的轮次本来就读不出裁决件，两边都不含它）。

### 2.3 按审核者聚合

- **归属**：一条意见按**提出它的审核者**计——合格意见与严重度按 review json 所属的侧；裁决行按该行的来源（「来源」列，缺省按编号前缀）；回退编号 `〈前缀〉-F〈n〉` 按前缀归到那一侧。来源判不出的裁决行单列一行「来源不明」，不猜。
- **重复意见不去重**：两侧对同一处各提一条，各计一条、各自的裁决各计一次——裁决表本来就逐条裁决，跨侧「是否同一条」需要语义判断，报告不做；重合程度看第六节的配对指标。
- **表 A · 意见与裁决**（每个出现过的审核者一行，全阶段合并【D-2】）：入选轮次、产出结论轮次、合格意见数、blocker / major / minor / nit、逐条降级数、接受 / 驳回 / 暂缓、其中整份回退编号数（及其裁决）【D-1】。
- **表 B · 运行与模型**：失败次数（状态 `timeout` / `failed`）、整份回退次数（状态 `parse_fallback`）、逐条降级轮次数（`findings_degraded` 非空）、未进时间线运行中的失败次数（单列，不并进前一格）、用过的生效模型（逐值计次，读不到写「**未回读到** ×N」）、思考等级请求值与生效值（逐值计次，写法同 §2.4，缺席记「— ×N」，与 null 的写法分开计次）。
- **入选轮次**：该侧在本轮 `critics_selected` 里，或本轮 run.json 有它的条目；读不到 Driver 的轮次没有 run.json，不计入任何审核者。

### 2.4 第四节新增思考等级两列

列序：阶段/轮、侧、请求模型、实际生效模型、**思考等级请求**、**思考等级生效**、证据。

| 留痕形态 | 请求列 | 生效列 |
| :--- | :--- | :--- |
| 字段缺席（第 6 步之前的旧留痕） | 「—」【D-4】 | 「—」 |
| `effort_requested: null` | 「（未请求）」 | — |
| `effort_effective: null` + `source: unverified` | — | 「**未回读到**」 |
| `effort_effective: null` + `source: null` | — | 「（无此概念）」 |
| `effort_effective: null` + `source` 缺席 | — | 「**未回读到**」（写侧恒写两格，此形态只可能来自手改，按读不到处理） |
| 有值 | 原值 | 原值；与请求值都为字符串且不等时加 ⚠️ |

- **生效列只读 `effort_effective` 与 `effort_effective_source`**，任何分支都不读请求值，也不读旧名 `effort`（AC-13、AC-23）。
- 节末注一句：「— 表示该轮留痕早于思考等级字段（缺席）；括号与加粗写法表示留痕里明确记了空值，两者不是一回事」。

### 2.5 JSON 输出【D-5】

`report --json` 原样输出 `TopicReport`（`cli.ts:1898`）。推荐同步带：`aggregates: { byDriver, unknownDriver, byCritic }`；逐侧加 `effortRequested` / `effortEffective` / `effortEffectiveSource`（及旧名 `effortLegacy`），**缺席时不写键**、null 写 null，三态在 JSON 里同样可区分。只增不改，既有键不动。

## 3. 实现

### 3.1 `meta.ts`（附加字段，不改判定）

`RunMetaReadResult` 成功分支加 `sourceSchema: 'trivium.run.v1' | 'trivium.run.v2'`，在 `readRunMetaDetailed` 两个成功出口各填一值。`readRunMeta` 与其余调用方不受影响（只增字段）。用途：报告据此标出 v1 迁移轮次【D-3】。

### 3.2 `report.ts` 轮次枚举与裁决件按当轮 Driver【D-6】

- `enumerateRounds` 改为先读该阶段全部可读 run.json，按 `rerun_index` 取该号最后一份（与现行「后写覆盖」同序）。轮次由**审查文档**（无 kind 的文件）定义：
  - 第 n 轮**有**可读 run.json：后缀 ≠ 那份 run.json 的 `driver` 的文件是审查文档；
  - 第 n 轮**没有**可读 run.json：后缀不属于「本阶段任一可读 run.json 记过的 driver ∪ 缺省 Driver」的文件才是审查文档——这只用于**枚举**，该轮 Driver 记为读不到。这样 codex 当 Driver 时写下的下一轮计划 `…-r3-codex.md`（r3 还没送审、没有 run.json）不会被当成审查文档，不造幽灵轮次（§1.2 ③）。
- `buildRound` 调 `loadDisposition` 时传 `meta.driver`。
- 不改：`collectUnlistedRuns` 的选取口径、时间线列、未进时间线表的说明文字。

### 3.3 `report.ts` 数据补充

- `RoundReport`：加 `driverSource: 'run.v2' | 'run.v1' | null`、`driverUnknownReason: string | null`；`sides[]` 加逐侧 `severity`、`effortRequested?` / `effortEffective?` / `effortEffectiveSource?` / `effortLegacy?`（可选键 = 缺席，照抄 run.json 的在场性）；加 `disposalsBySource`（键为审核者 id 或 `unknown`，值为接受 / 驳回 / 暂缓计数）与 `fallbackDisposalsBySource`。
- `UnlistedRun`：加 `driver`、`sideStatuses`（逐侧状态）。
- `TopicReport`：加 `aggregates`。

### 3.4 纯函数（导出，单测直接打）

`aggregateByDriver(rounds, unlistedRuns)`、`aggregateByCritic(rounds, unlistedRuns)`、`renderEffortRequested(side)` / `renderEffortEffective(side)`。`renderEffortEffective` 的入参类型**不含**请求值字段（只收 `effortEffective` 与 `effortEffectiveSource`），让「拿请求值顶替」在类型上写不出来——照第 6 步 `effortReadback` 的做法。

### 3.5 渲染

第二节末尾追加「### 按 Driver 聚合」「### 按审核者聚合」两个小节（**不新增一级节、不改既有节号**，免得改动「三、」以后所有引用）；第四节按 §2.4 加两列。

## 7. 不做与残余风险

- **不做**：审核者 × Driver 的二维矩阵；第四节加档位（`tier` / `tier_source`）列；读不到 Driver 的轮次按后缀试探裁决件；跨侧重复意见的语义去重。
- **R1**：没有可读 run.json 的轮次号按「本阶段出现过的 driver ∪ 缺省 Driver」排除文件来**枚举**（§3.2）。两个方向都有残余：①那一轮的 Driver 是本阶段从没出现过的一家（例如唯一一份 run.json 恰好读不出）⇒ 其原稿会被当成审查文档，多出一个「读不到 Driver」轮次；②那一轮里某审核者恰好在本阶段别的轮次当过 Driver ⇒ 它的审查文档被排除，若它是该轮唯一产出方，这一轮从时间线消失（run.json 读不出时 `collectUnlistedRuns` 已把它记进主题 notes，不至于无声）。两者的影响都只在「读不到 Driver」组内，不污染任何已知 Driver 的读数。请审查员核这个取舍。
- **R2**：审核者的意见数（review json）与其裁决行数（裁决表）来源不同、可以不等；规格写明不强求相等，但读者可能误读，表下加一句说明。
- **R3**：`meta.ts` 的附加字段会被所有 `readRunMetaDetailed` 调用方看到；只增不改，调用方都只解构 `meta` / `cause`，全量会兜住。
