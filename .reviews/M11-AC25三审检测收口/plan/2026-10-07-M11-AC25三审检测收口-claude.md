## 0. 结论速览

1. **严格策略下作废侧的整体处置（任务三）已核实：不整次中止。** 泄漏判定与中止判定是两条互不读取的路径——`decideMode`（`runner.ts:316-376`）只按各侧 `ok/parse_fallback` 与 `failed/timeout/缺席` 分，泄漏侧的 `status` 仍是 `ok`；终态分支（`review.ts:2046-2057`）只认 `subject_drift`、`driftAction === 'fail'`、`mode.abort` 三种失败。于是 `failure_policy: strict` 下一侧被判作废，运行照常 `success`、退出 0、`review_mode: full`。**与 10.1.1、12.1 不冲突**（理由见 §1.4），不列待拍板；本步用用例钉住现行行为，据实定稿那一句。
2. **任务书的一处前提要修正：运行根通道的桩在三审下不可用。** `peer_leak` 按 `req.deny_paths` 子串取目标，确实天然支持三侧；但「读运行根内对端本轮输出」走的是另一个形态 `run_material_leak`，它的对端取 `CRITICS.find((c) => c !== critic)`（`stub.ts:575`），而 `CRITICS` 是注册表全部启用的审核者，顺序为 claude、codex、gemini、glm。后果有二：三审下每侧只能指向**一家**对端，且可能是**未入选**的那一家；既有两侧用例（`fault-injection.test.ts:642`，gemini 读「对端」）自 M9 第 4 步启用 claude 起，读的其实是**未入选的 claude 侧目录**——它照样判作废（第三段不是己方、不是运行时文件，`freeze.ts:123-126`），所以一直是绿的，但测的不是「读到真正参审的对端」。**本步给桩加一个显式指定对端的写法**（§2.2），这是本步唯一一处 `src/` 下的非注释改动，属测试支撑代码、只在设了桩环境变量时生效，偏离了上位计划 §4.3「只加测试与文档」的字面，在此显式登记。
3. **种历史审查件会把本轮抬成第 2 轮。** `resolveRerunIndex`（`archive.ts:66-84`）取非 Driver 产出的最大轮次加 1，种下的对端历史审查件是第 1 轮，本轮审查件因此落成 `-r2-〈侧〉.md`、裁决件须写 `-r2-revised-claude.md`。这正是「同主题重跑」的真实形态，用例按 `run.json.rerun_index` 取名，不写死。
4. 改动面：两份测试文件扩写、桩一处、`scratch-guard` 豁免表删一行、四处 `src/` 注释改准（不改行为）、主设计 / PRD / BACKLOG / 测试报告收口。LLD 不涉及（§2.6）。

### 1.3 桩的两个伪造读取形态（`adapters/stub.ts`）

- `peer_leak`（`:516-557`）：`note` 为子串筛选，从 `req.deny_paths` 取目标，筛空即判该侧失败（不静默放过）。目标即编排器下发的禁读清单本身，**三侧天然可用**。
- `run_material_leak`（`:559-584`）：`note: 'own'` 读己方 `out/result.json` 与运行目录的 `request.json`；`note: 'peer'` 读 `CRITICS.find((c) => c !== critic)` 那一家的 `out/result.json`。问题见 §0 第 2 条。

### 1.4 严格策略下的整体处置（任务三的核实）

**读到的事实**：

1. `effectivePolicy`（`review.ts:1612-1613`）只喂给 `decideMode`；
2. `decideMode`（`runner.ts:332-366`）的 `okSides` 是 `status ∈ {ok, parse_fallback}`，泄漏判定不改 `status`；`abort` 只在「有失败侧且策略为 strict」或「入选侧全军覆没」时为真；
3. 终态（`review.ts:2046-2057`）：`subject_drift` / `driftAction === 'fail'` ⇒ `failed` 退 1；`mode.abort` ⇒ `failed` 退 75；否则 `success`；
4. 全仓没有 `failed(peer_leak)` 这个状态的写入点（`grep "peer_leak'"` 只见 `parse.ts` 的回显字段表与桩的模式名）。

**结论**：strict 下作废侧**不触发整次中止**；作废侧照常落盘、须逐条裁决；运行状态与退出码不变；降级策略同理（两条路径互不读取）。

**是否与 10.1.1 或 12.1 冲突——不冲突**：

- 10.1.1 对第①②类只规定「判该侧作废」，没有对整次运行的处置。
- 12.1「N 审中部分审核者失败，`failure_policy: strict`」行（:3031）的触发条件是**失败**；作废侧不是失败侧。
- v1.3.129 之前的原文是「作废并重跑一次……**仍命中**则 `failed(peer_leak)`，strict 下整次中止」——strict 中止挂在**二次命中后的 `failed(peer_leak)`** 上，而二次命中以重跑为前提。重跑已移出 AC-25、另立 EV-225，于是「二次命中」这条路径今天不存在，strict 中止也就无从触发。现行行为 = 原设计去掉重跑那一段，不是另一套语义。二次命中后 strict 与 `--allow-partial` 各怎么走，EV-225 已列为「做之前要先定」的事项。

因此不停下来列待拍板。**若审查员判为冲突，本步不改判据，交用户拍板。**

**为什么 FI-1～3 把审查件正文与结构化意见合在一次注入里**：桩一侧一次只能处于一个模式；两类同属第①类，命中逐条带路径与类别，「逐元素相等 + 每条带作废类」已能逐格证明每一条都被单独判出（任一条从禁读集消失，路径集即不等；任一条分类错，类别断言即红）。运行根是第②类、走另一个模式，所以单独成格。

**为什么集成层只做一格 Driver 轮换（FI-8）**：禁读集对 Driver 的依赖全部在 `enumerateDenyPaths(…, driver)` 里，§2.1 的矩阵逐格穷举了四种 Driver；`review.ts → freeze()` 透传 driver 这一段由 `deny-matrix.test.ts` 的源码扫描用例与 `driver-wiring.test.ts` 守着。FI-8 补的是「非缺省 Driver + claude 当审核者」在真实 CLI 链路上走一遍。
