## 1. 现状核实（`50110fc`）

### 1.1 闸门的三个调用点都经 `checkAdjudication`（现状一、二）

- `gate --check`：`cli.ts:1375`，`rerunIndex` 取最新一次运行的 `rerun_index`（`cli.ts:1186`），Driver 取该轮 `run.json.driver`（`cli.ts:1177`）。
- `gate --await-approval`：`cli.ts:1268` 调 `verifyRoundForApproval`（`gate.ts:1184`），后者在 `gate.ts:1220` 调 `checkAdjudication`。
- `approve`（通过）：`cli.ts:1663` 同样调 `verifyRoundForApproval`。

三处的输入都由 `loadRoundReviews`（`gate.ts:877`）从 `run.json` 派生。Hook（`hook-stop` / `hook-pre-commit`）不直接调 `checkAdjudication`，它们看闸门状态；`--check` 不通过时闸门状态不前进，收工闸门随之继续拦——新失败项自动进入这条链，不必改 Hook。

所以规则落在 `checkAdjudication`、输入由 `loadRoundReviews` 派生，命令 A 与 B 的三个调用点（含审批前复核）同时生效（决策二）。

### 1.2 轮次与被审对象（现状三、四）

- `resolveRerunIndex`（`archive.ts:66`）只看**非当轮 Driver** 的工件取最大轮次 +1；Driver 的原稿与新一轮计划不影响轮次。第 1 轮 `rerun_index = 1`、裁决件无 `-r` 段；Driver 随后写 `…-r2-<Driver>.md`；第 2 轮计划双审 `locateSubject` 取到 r2 当被审对象，`rerun_index = 2`，裁决件 `…-r2-revised-<Driver>.md`；此时若有接受项，新一轮计划应为 r3。
- `run.json` **没有记被审对象的路径或轮次**：plan 阶段只记 `snapshot.subject_sha256`（`meta.ts:345`），路径只出现在任务书第 3 段与运行期请求里。被审对象可以是 `--plan-file` 显式指定的归档外文件（`topic.ts` 的 `locateSubject` 显式分支），这时它没有轮次。
- 被审对象的轮次可能大于 `rerun_index`：Driver 在第 1 轮送审前就写了 r2，`locateSubject` 取 r2，而 `rerun_index` 仍是 1。

### 1.3 计划定稿的取法（现状五）

`resolvePlanFinal`（`review.ts:267`）经 `locateSubject` 取计划阶段执笔方后缀、非裁决件、剔除审查件（`isReviewArtifact`）之后**轮次最大**的一份。

### 1.4 编号的形态（现状七）

- 审查员编号按 `review.v1.json` 的 `^[A-Z][A-Z0-9]*-(r[0-9]+-)?[0-9]{2,}$`，每一轮都从 01 起编——**同名编号跨轮重复是常态**。
- 整份回退侧的虚拟编号 `<前缀>-F<n>` 由编排器写进 `_meta/review-<侧>-<run_id>.fallback-items.md`，同一轮内稳定，`gate` 按它逐条对账（§6.6 规则 8）；逐条降级的意见按原编号裁决。
- 裁决行的 `disposal` 已归一为 接受 / 驳回 / 暂缓（`normalizeDisposal`）。

### 1.5 历史归档实扫（决策六）

用只读脚本对 `.reviews/` 下全部 92 个主题的计划阶段每一轮（读 `run.json` 的 driver 与 `rerun_index`，按 `subject_sha256` 认被审对象，解析该轮裁决件）按本稿规则模拟一遍。结论：

- **约 20 个主题的最新一轮会转红**：大约 2026-09-26 之前，有接受项却没有新一轮计划是常见做法，例如 M9 系列各步、「双审进度反馈」「凭据副本残留与参数静默丢失」「配置v2与动态多审」「护栏判定范围收窄」。
- **多轮主题的早期轮次**若按「最大轮次那份计划」核对，几乎全部报缺编号——最大轮次的计划引用的是最后一轮的编号（如 M10b、M8、EV-79）。
- 近期主题（2026-09-26 起）的最新一轮几乎都通过；例外是「两个空配置项收口」：r2 没有引用被接受的虚拟编号 `GLM-F02`。

所以「一律校验」会让大批历史主题的复核转红，违背决策六的原则；本稿取「只对新运行生效」（§2.6）。同时这份读数也是 §2.4 选「紧随本轮的那一份」而不是「最大轮次那份」的依据。

### 1.6 流程说明的结构（决策五）

## 2. 设计

### 2.1 规则（决策一）

计划阶段某一轮（下称本轮）的裁决件里只要有一行裁决为「接受」，就必须存在一份**执笔方的新一轮计划**：

- 在 `plan/` 根目录，文件名可解析，主题等于本主题，角色后缀等于当轮 Driver，没有 `-revised` / `-response` 中缀；
- 不是审查件（`isReviewArtifact` 为假——与 `locateSubject` 同一道剔除，防换过 Driver 的主题里别家当 Driver 时留下的审查件冒充）；
- 轮次 **大于 基准轮次**，基准轮次 = max(本轮 `rerun_index`, 本轮被审对象的轮次)；被审对象在归档外、没有轮次时只取 `rerun_index`。

全部驳回、全部暂缓、零意见（空表）时不要求，上一轮计划即为定稿。

### 2.2 落点（决策二）

- `gate.ts` 新增导出的 `checkNextPlan(…)`，由 `checkAdjudication` 在既有各项之后调用；只在 `stage === 'plan'` 时执行。
- `GateCheckInput` 新增 **必填、可为 null** 的 `planFinal: { subjectRerunIndex: number | null } | null`——沿用 `reviewDocs` 的写法与理由：做成可选参数，漏传就静默不校验（文件内 `voidedSides` / `reviewDocs` 两段注释记着同一教训）。null 表示本轮不适用（非计划阶段，或旧运行没有标记）。
- `loadRoundReviews` 新增返回 `planFinal`：计划阶段且 `run.json` 带标记时给出 `{ subjectRerunIndex }`，否则 null。三个调用点照现有写法透传（`cli.ts` 的 `--check`、`verifyRoundForApproval`）；由于字段必填，`tsc` 会逼出每一处。

### 2.3 校验强度与编号判据（决策三）

- **核对哪些编号**：本轮裁决件中裁决为「接受」的全部行的编号——合格意见、逐条降级意见、整份回退的虚拟编号 `<前缀>-F<n>` **一律要求**。虚拟编号同一轮内稳定（编排器落盘、闸门按它对账），裁决件本来就用它指代那条意见；豁免它等于让整份回退一侧的接受项整批不受约束（§1.5 的「两个空配置项收口」正是这一格）。
- **在哪里算数**：新一轮计划的**全文**。不限定在「改动清单」一节：本仓没有固定的节标题约定（历次 r2 的标题写法各不相同），按节解析要再造一个约定和一套解析，且对「编号写在别处」误判；流程说明仍要求开头列改动清单（§2.8），闸门只核字面存在。
- **字面判据**：编号作为整词出现——前一个字符不是 `[A-Za-z0-9_]`、后一个字符不是 `[A-Za-z0-9_]`。这样 `GLM-01` 不会被 `GLM-010`、`XGLM-01` 冒充；`GLM-01：`、`（GLM-01）`、`GLM-01-②` 都算数。区分大小写，不做全半角归一（编号本身是 ASCII）。
- **边界（写进设计）**：
  1. 只核字面，不判合入内容是否正确，也不判编号出现的语境（写「GLM-03 不改」同样算出现）；
  2. 编号每轮从 01 重编，字面判据分不出新一轮计划里的 `GLM-01` 指的是哪一轮的 `GLM-01`——第 2 轮之后，照抄上一轮改动清单可能让同名编号「顺带」过关；
  3. 闸门拿到的接受集合来自裁决件，裁决件本身被改动（如把接受改成驳回）由既有的裁决件校验与提交锚负责，不在本条。

### 2.4 核对的是哪一份（决策一、三）

候选 = §2.1 条件下轮次大于基准的全部执笔方计划。**核对其中轮次最小的一份**（同轮次多份按文件名降序取第一份，与 `locateSubject` 排序一致），即「紧随本轮的新一轮计划」：

- 正常流程里它就是唯一的候选，也是代码阶段 `resolvePlanFinal` 会列的那份；
- 多轮主题里，第 k 轮的接受项合进 r(k+1)，r(k+1) 又是第 k+1 轮的被审对象——逐轮各核紧随其后的一份，链条每一环都有判据；按「最大轮次」核对会让用 `--run-id` 回看早期轮次时无故转红（§1.5 第二条）。
- 候选里还有更高轮次时（例如 Driver 写了 r2 又写了 r3、r3 没再送审，或回看的是早期轮次），出告警 `next_plan_not_final`：点名代码阶段会读的是更高那份、本轮核对的是哪份，请确认更高那份同样合入了本轮接受项。告警不阻断——回看早期轮次时这句话就是事实，不该转红。

### 2.5 失败码、文案与顺序（决策四）

新增两个失败码，加在 `GateFailureCode` 末尾：

| 失败码 | 触发 | 文案要点 |
| :--- | :--- | :--- |
| `missing_next_plan` | 有接受项，候选为空 | 本轮有 N 条接受（列编号），必须写一份新一轮计划合入它们；应为 `<今日>-<主题>-r<基准+1>-<Driver>.md`（用 `buildArtifactName` 生成，日期取本地今日）；开头列「相对上一轮的改动」并逐条引用编号；全部驳回 / 暂缓时不要求 |
| `next_plan_missing_ids` | 候选存在，但有接受编号没有逐字出现 | 点名核对的文件名，`ids` 给缺的编号（排序）；说明判据是整词逐字出现、只核字面 |

候选文件读不出（权限、非 UTF-8 等）按 `next_plan_missing_ids` 报、`ids` 给全部接受编号，文案注明「读不出」。

**顺序**：排在全部既有失败项之后。既有各项都是裁决件自身的问题（缺裁决、多余编号、缺落点…），先修裁决件、接受集合才定得下来；新一轮计划依赖它。两项照常一次全报（不因前面有失败而跳过本项），与闸门「让 Driver 一次照着补完」的口径一致。

新增两个告警码：`next_plan_unchecked`（§2.6）、`next_plan_not_final`（§2.4）。

### 2.6 只对新运行生效（决策六）

- `run.v2` 新增**可选**顶层字段 `plan_final_check: { subject_rerun_index: integer ≥ 1 | null }`，`additionalProperties: false`。只在计划阶段、由本题之后的编排器在 `newRunMeta` 骨架里写入；代码与 bug 阶段不写。
- 写入值：`prepareRun` 在计划阶段定位到被审对象后算一次——被审对象位于本主题 `plan/` 根、文件名可解析、主题与角色（当轮 Driver）匹配、无中缀时取其轮次，否则（归档外的 `--plan-file`、名字不合规）记 null。纯函数 `planSubjectRerunIndex(layout, subjectPath, driver)` 放在 `review.ts`，单测直接调。
- 闸门：`planFinal` 为 null（旧运行没有标记、或运行元数据读不出）而本轮有接受项时，不判失败，出告警 `next_plan_unchecked`：「本轮运行早于 EV-214（运行元数据没有 plan_final_check），未校验新一轮计划」。运行元数据读不出的那一格本来就由 `missingSides`（`--check`）与审批前复核的硬拒兜底。
- 选它而不是「一律校验」：§1.5 的读数。选它而不是按 `started_at` 设一个日期切分点：日期切分把「什么时候装的新版」与「什么时候跑的」绑在一起，旧版跑出的运行在升级后复核会按新规则判；标记写在运行元数据里，「这一轮按什么规则跑的」由这一轮自己作证，与 `driver_enabled` / `driver_guard_level`「缺失即无从得知」同一口径。
- 本题自己的计划阶段由当前安装的旧版编排器跑，不带标记，闸门不会对本题执行新规则；本题照样手写 r2（习惯不变）。用户重装之后的新运行才生效——与 EV-210 一样，结案要等重装复核。

### 2.7 与既有判定的关系

- 不改 `resolveRerunIndex`、`locateSubject`、`resolvePlanFinal`。
- 不改 `checkStageArtifacts`（`gate --check-artifacts` 的最低工件集）：那是「本轮该有的审查与裁决件」，新一轮计划是下一轮的原稿，放进最低工件集会让「全部驳回」的轮次也被要求。
- `jointCheck`、`disputed` 等返回值与持久面不变。

### 2.8 流程说明（决策五）

- 新增片段 `skills-src/partials/review/next-plan.plan.md`（有内容）与 `next-plan.code.md`、`next-plan.bug.md`（空变体）。`body.md` 第 5 步列表之后加 `{{> review/next-plan@STAGE}}`；`run.contract.md` 的 S3 之后嵌入 `{{> review/next-plan.plan}}`——渲染器按「相对路径去掉 `.md`」建片段表、`{{> 名}}` 直接按名查表（`entry-render.ts:154`、`:223`），带点的键可用，两处共用一份正文。
- 片段正文（措辞以落盘为准）：裁决件里有「接受」时，**同时**写一份新一轮计划 `…-r<N>-<当轮 Driver>.md`（N 比本轮被审对象的轮次大 1，第 1 轮即 r2），开头列「相对上一轮的改动」，逐条引用被接受意见的编号（含 `<前缀>-F<n>`）；它就是代码阶段送审的计划定稿。全部驳回或暂缓时不写。闸门只核这份文件存在、编号整词逐字出现，不核合得对不对。
- 改完跑 `node scripts/build.mjs` 重新生成 `skills/dual-critic/entry/*` 各载体；`.reviews/README.md` 的 `plan/` 一行补「④有接受项时的新一轮计划 `…-r<N>-<Driver>.md`」。

### 2.9 自检

`selftest.ts` 计划阶段那一格在写裁决件之后补写 `…-r2-claude.md`（引用示例接受编号），保持 `--check` 通过；「重跑抬升」那一格的判据从 `includes('-r2-')` 收紧为「存在 `-r2-` 且后缀是审核者的文件」，不被 Driver 的 r2 计划冒充。自检项数不变（14）。
