### GLM-01 · 重要（major）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `计划 §2.1（基准轮次），与 §2.5、§2.8 联动` |
| 类别 | correctness ｜ 层次 plan |
| 置信度 | high |

**问题**：基准轮次 = max(本轮 rerun_index, 被审对象轮次) 在「本轮被审对象未被修订」的合法流里判错。rerun_index 只数非 Driver 工件（archive.ts 的 resolveRerunIndex 跳过当轮 Driver 的原稿与裁决件），被审对象轮次由 Driver 计划的最大轮次决定（topic.ts 的 locateSubject）：上一轮全部驳回/暂缓后原稿未修订、再次发起计划双审时，rerun_index 抬到 2 而被审对象仍是 r1；本轮有接受项时基准 = 2，闸门要求写 r3，而 §2.8 流程说明让 Driver 写的是「被审对象轮次 + 1」即 r2，§2.5 的应写文件名同样给 r3——同一份计划内部自相矛盾，照指引写的 r2 过不了闸。「旧运行有接受项未修订、升级编排器后重跑计划双审补审」这一 §2.6 自己设想的收口路径正是这个形状。任务目标决策一原文是「轮次高于本轮被审对象」，把 rerun_index 并进 max 偏离了已确认的决策。

**依据**：读过 src/trivium/archive.ts（resolveRerunIndex 只数审核者工件取 max+1）、src/trivium/topic.ts（locateSubject 按 Driver 后缀、kind 为 null 取轮次最大者作被审对象）、被审计划 §1.2（只提了被审对象轮次大于 rerun_index 一个方向）、§2.1、§2.5、§2.8，以及 §3.1 的 U7/U8 与 §4 的 M2：U7、U8 两个方向都是被审对象轮次 ≥ rerun_index，没有任何用例覆盖 rerun_index > 被审对象轮次，M2（只取 rerunIndex）的变异也区分不了 max() 与「只取被审对象轮次」两种实现。

**建议**：基准只取被审对象轮次（被审对象在归档内时），归档外无轮次时才退回 rerun_index——被审对象轮次单独就能覆盖 U8（送审前预写 r2）那一向，max 里并进 rerun_index 没有它能 cover 而被审对象轮次 cover 不了的场景。§3.1 补一格「rerun_index=2、被审对象轮次=1、有接受 ⇒ 要求 r2 而非 r3」，集成侧（§3.2）补同形状一格；M2 改成能区分两种基准取法的变异。§2.5 的应写文件名公式随之对齐。
