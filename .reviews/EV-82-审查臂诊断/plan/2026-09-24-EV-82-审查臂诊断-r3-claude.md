## 3. 第 4、5 步：派发与判读

派发：`--critics glm --model-glm GLM-5.3-Flash`，被审对象即原稿。读 run.json glm 段
`status`、`cli_version`、`model_requested`、`model_effective`（拆 provider 段与 modelId 段）、`model_route`、`model_override_applied`、`snapshot.git_head` / `snapshot.dirty`，
并读该侧运行目录的 `out/rollout.jsonl`。

**run.json 的 `model_effective` 只取首个非空记录**：`zcode-trace.ts` 的两处解析（日志的 `context.model`、rollout 顶层 `model`）都是「首个即定值」，
`response.modelId` 全程不读。单凭它，只能证明**首条**模型请求以哪个模型发出。

**判读次序**（按序，命中即停）：

1. 先读 `status`：不是 `ok` 或 `parse_fallback`，一律归 (E)。失败出口先于 `decideModelOverride`，
   `model_route` 与 `model_override_applied` 两个字段在失败侧本来就不落盘，此时字段缺席**不代表**「限定没建起来」。
2. `model_route: global`，或 `model_route` / `model_override_applied` 缺席 ⇒ (A)。
3. 看 provider 段形态 ⇒ 再看 modelId 段 ⇒ 最后看布尔值，对号入 (B)(C)(D)。
4. 判任一格之前，逐条核 `out/rollout.jsonl`：每条记录的顶层 `model` 一致，且 `response.modelId`（如在）与之一致。
   与 run.json 不一致时降为 (E)，照实登记形态。
5. 以上都不中的形态，一律归 (E)，照实登记。

| 格 | 观测形态 | 读出什么 | 接下来 |
| :-- | :--- | :--- | :--- |
| (A) | `status` 正常；`model_route: global`，或该字段缺席 | 限定没建起来 | 成因见该侧 `trace.json` 的 `modelSelection.reason`（run.json 没有这个字段）；登记环境原因，按证据不足报告 |
| (B) | provider 段 ≠ 副本源 legacy 键（UUID 是已见形态之一），或 `model_effective` 没有 provider 段 | 疑似隔离失效（没有 provider 段时，也可能只是轨迹没记 `providerId`） | 定位 `omitPersonalProviderConfig` 与目录键清除，进修复排查 |
| (C) | provider 段 = 副本源 legacy 键（本机为 `bigmodel-coding-plan`），modelId 段 = `GLM-5.3-Flash`，`true`，rollout 逐条一致 | 当前代码在当前环境生效 | 进构建标识改动，再做 T2 |
| (D) | provider 段 = 副本源 legacy 键，modelId 段 = 该 provider 首位（本机为 `GLM-5.3`），`false` | 选择回落首位：H3 候选，也不排除 H2 | 同形第二臂零配额区分；指向 H3 则停下向用户报告 |
| (E) | `status` 异常；`model_effective` 为 `null`；rollout 与 run.json 不一致；或以上都不中 | 证据不足 | 照实登记，报告后再定 |

**注**：

- 「Flash + `false`」与「首位 + `true`」两种交叉形态不会出现：`decideModelOverride` 按 modelId 尾段比对得出布尔值。
  provider 段不同而尾段相同时会得出 `true`，所以判读次序把 provider 段放在布尔值之前。
- **(D) 的「隔离成立」一腿有前提**：个人配置的 provider 键 ≠ 副本源 legacy 键。个人配置的键形态按凭据纪律未读；
  UUID 形态来自设计 v1.3.32 记录的一次回读快照（r5 §1.4④ 引），而 EV-87 记有 2026-09-21 17:56 个人配置被重写（嫌疑在桌面端）。
  这条前提的机制支撑待补，补法交给 EV-82 小主题计划（§6）。
