> 起点 `7b643b0`；命令 A；Driver claude。任务目标原文较长，审查员任务书末尾有「附录：任务目标原文」；

## 1. 现状（已核，行号取 `7b643b0` 源码）

1. `review.ts` 的 `resolveTaskGoal`（约 418～453 行）三级取值：显式 `--goal` → 任务文件 `goal` → 本主题计划文档。
   计划阶段不走第三级。第三级 `locateSubject(planRef, null, projectRoot, opts.driver ?? DEFAULT_DRIVER)`
   传的是**本轮**（代码 / bug 阶段）的 Driver，整段 try/catch，找不到静默返回 null。
2. `locateSubject`（`topic.ts` 约 76 行）取该后缀、无中缀、非审查件、轮次最大的一份：有 r2 取 r2，不是原稿。
   设计 §9.4 第 4 条写「同主题 plan 原稿的首个标题/首段」，与实现不符；MANUAL 306 行同。
3. `resolvePlanFinal`（约 284～316 行）先 `resolveStageDriver(layout, 'plan')` 判**计划阶段**执笔方
   （留痕读不出 ⇒ `corrupt`，不列、返回一条「必读清单未列计划定稿」告警），再用同一个 `locateSubject` 取件，
   返回项目相对路径。`prepareRun` 里它只在代码阶段调用（约 953 行），排在 `resolveTaskGoal`（约 967 行）之前；bug 阶段不调。
4. 第三级只在两级都没有目标时走到。命令 A 的 S2 把目标写进任务文件，所以多见于命令 B、C、D 单独发起、从未带过 `--goal` 的主题。

   `RECONCILE` 里 `locateSubject` 期望 3 处。
6. 缺陷形态：计划阶段 codex 执笔、代码阶段 claude 执笔 ⇒ 第三级按 `-claude.md` 找，计划目录里只有 `-codex.md` ⇒ 抛 65 被吞、目标为空；

## 2. 决策（用户已确认，逐条复述）

- **D1** 第三级改为复用 `resolvePlanFinal` 的取件，全仓只留一处「哪份是计划定稿」的判定；`resolveTaskGoal` 里那次
  `locateSubject` 调用删去（护栏表同步：该函数调用点 3 降 2）。「怎么取计划定稿」作为 `resolveTaskGoal` 的**必填参数**传入、
  **用到才调用**：代码阶段传 `prepareRun` 已算好的结果、不判第二次；bug 阶段在第三级真正走到时才现算一次。
  不做成可选参数——漏传会静默退回旧取法。
- **D2** 计划阶段留痕读不出时第三级返回 null、不拒跑，bug 阶段不补告警（要同时满足 bug 阶段、两级无目标、计划留痕读不出才走到；
  留痕读不出本身已被计划阶段各入口与提交时的留痕核对拒绝）。丢弃那条结果处写注释说明理由，并有用例钉住「不取、不拒跑、不报错」。
  代码阶段「必读清单未列计划定稿」告警不变。
- **D3** 取件口径保持「轮次最大的一份」（计划定稿）；设计 §9.4 改成与实现一致，不改回只取原稿；执笔方相同的既有主题取到的目标逐字不变。
- **D4** 只改第三级；前两级、`clampGoal` 截断（EV-213）、bug 阶段是否必读计划定稿（EV-211）不在本题。
- **D5** 历史主题不追溯：已冻结的任务书与任务文件不动。
- **D6** 文档：EV-212 结案；设计 §9.4 第 4 条改写、版本记录加一行；LLD 与 MANUAL 凡写到第三级处同步；新发现另登；
  测试报告登记进 `doc/05_testing/README.md`。
- **D7** 测试零配额（桩适配器），覆盖：计划 codex / 代码 claude、无 `--goal` 且任务文件无目标 ⇒ 代码阶段第 4 段取到 codex 那份定稿的标题；
  bug 阶段同；计划与代码同为非缺省执笔方照旧取到；缺省执笔方主题任务书逐字不变；计划留痕读不出时不取、不拒跑；别家后缀不被误取。
- **D8** 验证零配额：单测；变异先逐条带超时预跑再跑装置；全量两次（串行）、doctor 自检；前后数系统临时目录 `trivium-` 新建条目，
  除 `trivium-index` 外为 0。

## 3. 改动设计

### 3.1 `resolveTaskGoal` 的新签名（`review.ts`）

```ts
/** `resolvePlanFinal` 的结果（项目相对路径 + 至多一条告警） */
export type PlanFinal = Awaited<ReturnType<typeof resolvePlanFinal>>;

export async function resolveTaskGoal(
  opts: Pick<ReviewOptions, 'taskGoal' | 'stage'>,
  ref: { topic: string; layout: ArchiveLayout },
  projectRoot: string,
  planFinal: () => Promise<PlanFinal>,   // 必填；只在第三级真正走到时调用，至多一次
): Promise<string | null>
```

- `opts` 的 `Pick` 去掉 `driver` 与 `subjectFile`：第三级不再按本轮 Driver 找件，`subjectFile` 原本只出现在注释里。
  留着它们会让人以为第三级仍受本轮 Driver 影响。
- 第三级：

```ts
if (opts.stage === 'plan') return null;   // 不变：同义反复
try {
  const final = await planFinal();
  /*
   * final.path 为 null 有两种：本主题没有计划阶段（无告警，正常），或计划阶段留痕读不出（带告警）。
   * 后者的告警在这里**有意丢弃**（D2）：代码阶段 prepareRun 已把同一份结果的告警送进三个出口，这里再报是重复；
   * bug 阶段要同时满足「bug 阶段、两级都没有目标、计划留痕读不出」才走到，而留痕读不出本身已被计划阶段各入口
   * 与提交时的留痕核对拒绝，不另起告警、不拒跑——自动推导的目标取不到，与「没有计划阶段」同样处理为不渲染。
   */
  if (!final.path) return null;
  return goalFromPlanDoc(await fs.readFile(path.resolve(projectRoot, final.path), 'utf8'));
} catch {
  // 读件失败（竞态删除等）或 bug 阶段现算时的意外抛出：与旧口径一致静默跳过，自动推导不拦整轮审查
  return null;
}
```

- `path.resolve(projectRoot, final.path)`：`resolvePlanFinal` 给的是项目相对路径，必须按同一个 `projectRoot` 还原，
  不能按进程 cwd 读。
- try 包住 `planFinal()` 本身：bug 阶段是新增的一次 `resolvePlanFinal` 调用，它内部 `resolveStageDriver` 读留痕若意外抛出，
  旧代码这条路径不会抛（旧第三级全在 try 里）；包住才保持「bug 阶段第三级不新增拒跑面」。代码阶段传的是已算好的结果，不会抛。

### 3.2 `prepareRun` 的调用（`review.ts` 约 967 行）

```ts
// 代码阶段复用上面已算好的计划定稿，不判第二次；bug 阶段第三级真正走到时才现算（D1）；计划阶段不走第三级、不会调用
const taskGoal = await resolveTaskGoal(opts, ref, ctx.projectRoot,
  stage === 'code' ? async () => planFinal : () => resolvePlanFinal(ref, ctx.projectRoot));
```

次序不变（`resolvePlanFinal` 仍在前）。bug 阶段现算的那次结果只用来取目标，**不**进必读清单、**不**出告警（EV-211 未定）。

### 3.5 边界（如实写明，不在本题改）

- **⑴ 跨禁读集**：计划 codex、代码 claude、入选 codex / gemini / glm 时，codex 那份定稿对 gemini、glm 是禁读（`indeterminate`），
  必读清单会从这两侧剔除；但第 4 段的任务目标行是各侧共用的一行，会照样带上它的**首个标题/首段**。我认为可接受：
  ① 取的是计划执笔方（Driver 角色）的标题，不是任何审查员的意见；② 执笔方相同的主题今天就把 r2 标题给每一侧；
  ③ 只有一行、过 `clampGoal` ≤200 字。D7 第一格要求的正是这个行为。若审查员认为这一行也应按侧剔除，请给出理由，我按裁决处理。
- **⑵ 首段可能不是标题**：`goalFromPlanDoc` 取首个非空行，r2 若不以标题开头而以「相对上一轮的改动」段开头，目标会是那句话。
  既有行为，执笔方相同的主题今天同样如此；不在本题改。
- **⑶ bug 阶段现算的是计划阶段的定稿**，不看 bug 阶段 Driver；bug 阶段 Driver 与计划执笔方不同时也取得到——这正是本题要的。
- **⑷ 代码阶段 `planFinal.path` 撞禁读被剔除时**，目标仍取它的标题（同 ⑴；必读剔除是按侧的、目标解析在剔除之前且与侧无关）。
