### 3.1 成因 A：Hook 把 **Driver 自己的产出**判成审查件（6 条）——**本步最重的一格**

`hooks.ts:92` 的 `hasCriticRoleSuffix` 与 `hooks.ts:474` 的 `ROLE_SUFFIX_ANYWHERE`
都由 `CRITICS.join('|')` 生成正则。`CRITICS` 是 `criticEnabled` 派生集合
（`types.ts:106`），翻开关后它含 `claude`，于是 **`*-claude.md` 进入「审查员角色后缀」集**。

后果不是测试红，是**流水线锁死**。实测第 1 条的断言消息逐字是：

```
AssertionError: 归档内的写入不受闸门写锁约束
2 !== 0
```

——归档内写 `-claude.md` 退 **2**（被 `isForgedRoleFile` 判成伪造件），
而它正是 Driver 写裁决件的路径。**翻开关 = Driver 交不了卷。**

仓库根 `CLAUDE.md` 逐字写着「你的产出后缀是 `-claude`」，而同一份文件
也写着 Hook 会拦审查员后缀——两句话在翻开关的那一刻开始互相矛盾。

**处置（= 原计划 B-2，本步照做）**：两处派生改为
**`ALL_AGENT_IDS` 去掉当轮 Driver**（M9 取 `DEFAULT_DRIVER`，M10 改按会话 Driver）。
今天行为逐字不变（当前 `CRITICS` 恰等于全集减 claude），翻开关后不误锁 Driver 原稿。

**revised §2.3 的三条连带，逐条落**：

1. **`hasCriticRoleSuffix` 有两个消费者，判据含义不同**：`isForgedRoleFile`
   （形态 + 位置、当轮语境）与 `immutableChangeReason`（纯 basename、**跨时间**）。
   「减当轮 Driver」对前者成立；对后者是把**跨时间**的保护面绑到一个**当轮**的值上。
   **本步不重构提交锚判据**（那是安全关键面重写，触发时点是 M10 换 Driver），
   但要在代码里写明这层不对称，并登记 BACKLOG 挂 M10。
2. **如实承认边界**：纯词法后缀检查区分不了「Driver 自身原稿」与「同名历史审查件」。
   M9 不假装能分，写下来。
3. **补一条不等式用例**：识别集（`naming` 用 `suffixAlternation()` 全量后缀）
   ⊇ 保护集（全量减 Driver）。今天恒成立，改错了当场红。

**第 4～6 条用例的断言理由要改写**（结论不变）：`hooks.test.ts:53-54` 现在写的是
「`-claude.md` 不是审核者角色」，改成「`-claude.md` 是当轮 Driver 自己的产出」。
——注释里任何「X 会/不会 Y」的行为断言，落笔时必须指得出断言它的那一行用例。

### 3.2 成因 B：夹具用 `CRITICS[0]` 取「任一审核者」，而它翻开关后变成 Driver（9 条）

注册表 `AGENTS` 的顺序是 `claude, codex, gemini, glm`（`registry.ts:126-`），

- **10 / 13 / 16**：断言报错文案里含 `CRITICS[0]`，而 `legalList` 正是**排除 Driver**的

/** 本轮可真正入选的审核者（= 启用集合减缺省 Driver）。用例不得再用 CRITICS[0]。 */

## 5. 本步新挖出的两处缺口，请裁定是否纳入范围

### 5.1 `override_reason` 恒缺：AC-18 在 claude 侧只剩一句渲染文案

AC-18（PRD `:394-395`）逐字要求：

> Given 用户显式覆盖审查模型，Then 覆盖后的模型在**归档或本次运行的可观测信息中可见**（NFR-05）。

`isHeterogeneous`（`adapters/base.ts:1670`）对 Claude 系模型返回 `false`，
于是 claude 一旦入选，`run.json` 的 `critics.claude.heterogeneous` 恒为 `false`。
`run.v2.json` 对该字段的 description 逐字写着「**false 时必须有 `override_reason`**（AC-18）」。

**而 `override_reason` 没有任何写入方**：全仓 grep 只有三处，全在 `render.ts`
（`:99` 类型声明、`:192` front-matter 条件写入、`:314` 人读面 flag），
`review.ts:1144` 与 `:1341` 两个 `heterogeneous` 写点**都不传它**。
也就是说翻开关后第一次真跑 claude，`run.json` 会落一个
「`heterogeneous: false` 且 `override_reason` 缺席」的组合——**正是 schema 说不该出现的那个**。

**两件事要分开看**：

- **(a) description 里的「必须」没有机器判据**。`run.v2.json` 该处只有 `description`，
  没有 `if/then`。所以这条「必须」今天是**一句散文**，落一个自相矛盾的 run.json
  不会被 ajv 拦下。
- **(b) 值从哪来**。claude 入选是用户显式 `--critics claude` 的结果，
  那本身就是「显式覆盖」，理由可以是机器生成的一句话
  （如「用户显式选择 claude 为审核者，与主脑同源」）。

**处置请裁定**：①本步只做 (b)（补写入方），(a) 登记 BACKLOG；
②(a)(b) 同批做；③两条都推到第 6 步（真跑之前不动）。
我倾向 ①——(a) 是 schema 升版，牵动 `run.v2` 的既有落盘件，
而本步已经动了六件，再叠一次数据契约变更会让代码双审的面过宽。

### 5.2 `默认 profile 两侧互不相同且均为非 Claude 系（AC-18）` 的口径要重新界定

`test/unit/adapter-base.test.ts:168-179` 的这条用例遍历 gemini / glm 两侧断言
`isHeterogeneous === true`。**加了 `profiles.*.claude` 之后它不会红**
（用例只取 gemini / glm 两个键，实测 19 条红里没有它）。

但它的**名字**会开始说谎：叫「默认 profile 两侧均为非 Claude 系」，
而默认 profile 从此有三个键、其中一个恒为 Claude 系。
AC-18 的原文是「未显式覆盖时**两边所用模型**均与主脑不同源」——
锚点是「本次实际跑的两侧」，不是「profile 表里有哪些键」。
而 `DEFAULT_CRITICS` 仍是 gemini / glm（`defaultSelected` 不翻），所以 **AC-18 仍然成立**。

**处置**：改用例名与注释，把断言锚定到 `DEFAULT_CRITICS` 而不是硬写的两个 id，
这样「有人把 claude 设成 `defaultSelected`」的那天它会当场红。**这是加强，不是放宽。**
