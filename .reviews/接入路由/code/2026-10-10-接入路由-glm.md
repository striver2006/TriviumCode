**问题**：codexRouteEnv 的清理面是九个固定变量名（OPENAI_* 与 CODEX_*），与同函数族已解析出的各 provider env_key 集合没有打通：除所选 provider 的键被保留外，配置里其它 provider 声明的自定义 env_key（名字不在九个固定项里）会随 process.env 原样继承进 codex 审查子进程。codex 审查员是 readonly-shell，可执行 printenv 一类只读命令，被审代码中的提示注入有机会让这些与本次审查无关的凭据进入命令输出、进而落入归档的 trace 留痕。函数注释宣称「仅保留所选provider明确引用的认证变量」，与实现（只清九个固定名）不符。属本批收紧未竟，不是回归（此前为全量继承）。

### GLM-02 · 次要（minor）

| 项 | 内容 |
| :--- | :--- |
| 位置 | `src/trivium/adapters/claude-route.ts:86-101` |
| 类别 | correctness ｜ 层次 code |
| 置信度 | medium |

**问题**：路线指纹含 version 分量，读取侧 claudeProbeForRoute 重算指纹时 version 取根快照 cfg.probe.cli.claude.version，即最后一次 doctor 探测的那条路线的版本；而路线条目写入时（doctor.ts）用的是当条路线自己刚探出的版本。两条路线底层 CLI 版本不同时（如 profile_bin 指向钉住旧版的包装器），为路线 B 重跑 doctor 会把根版本换成 B 的，路线 A 的存量条目指纹从此对不上、被无声判为失效（availability 报「尚未探测」），且该死条目不被清理；用户按文案重跑 doctor（不带路线旗标）也恢复不了 A。失效方向是 fail-closed，但失效无据、修复指引也走不通。

**依据**：src/trivium/adapters/claude-route.ts:86-89（version 缺省取 probe?.version，probe 为根条目）与 :100（读取侧比对）；src/trivium/doctor.ts:797-802（写入时把 cfg.probe.cli.claude 置为当轮 snapshot 后计算指纹，routes 展开保留旧条目）；test/integration/claude-profile.test.ts:40-46 只覆盖 wrapper 与配置内容轮换，无跨路线版本漂移用例。

**建议**：路线条目里记录写入时的 version（或比对时用 entry.probe.version 重算指纹），使各路线指纹互不牵连；补一条「为 B 路线重跑 doctor 不得作废 A 路线条目」的用例。
