## 1. 现状核对（e00a1e2）

1. **`workTreeHash`**：`makeTempDir('trivium-index')`（`os.tmpdir()` 下 `trivium-index-XXXXXX`）在 try 之前；try 里 `read-tree HEAD` → `add -A -- .` → `write-tree`，`GIT_INDEX_FILE` 指向目录里的 `index`；finally `fs.rm(tmpDir, { recursive: true, force: true })`（`git.ts:121`）。finally 抛出时 JS 用 finally 的异常顶替 try 的返回值或异常——现状描述的两种坏法都成立。TriviumCode 往目录里写的只有 git 经 `GIT_INDEX_FILE` 写的索引文件：`index`，以及 git 写索引时的 `index.lock`（正常结束会改名掉，被超时杀掉时可能留下——只有工作树摘要那条传 `timeoutMs`、会按进程组杀）。没有文件内容、没有凭据。用户仓库里配置的 clean 过滤器之类第三方进程也能往这个目录写东西（§2.6 的摆锁法就是这么做的），所以措辞不断言目录全貌。
2. **八处调用方**与任务目标「现状二」逐处一致：`freeze.ts:442`、`review.ts:1233`、`worktree-summary.ts:171`、`build-stamp.ts:64`、`probes/fixture.ts:109` 与 `:157`、`probes/agy.ts:242`、`probes/zcode.ts:336`。`review.ts:1233` 在 `executeRun` 里、没有局部 try：worker 路径落进 `run-protocol.ts:1054` 的 catch（`工作进程异常：…`，`finalizeFailedRunMeta` 把 run.json 收尾为 failed、`status.json` 写 failed）；同步路径落进 `review.ts:1950` 的 catch（`sync_exception`）。
3. **selftest 建夹具失败那一处走不到**（现状三的前半句与代码不符）：`runSelftest`（`selftest.ts:198-208`）写的是 `let root = ''; try { root = await buildFixture(); } catch { if (root) await fs.rm(root, …) … }`——`buildFixture` 抛出时赋值不发生，`root` 恒为 `''`，`:202` 的删除**永远不执行**。真实的缺口是另一形：`buildFixture`（`:88-162`）在 `mkdtemp` 之后任一步抛出，已建的临时目录随异常遗留、无人清理，`fixtureRoot` 也报成 `''`。另：`buildFixture` 里能抛的只有文件系统操作（`initFixtureRepo` 用 `run()`，git 非零退出不抛、二进制不存在也只是把 `[spawn error]` 拼进 stderr），实践中只在磁盘满、I/O 错误一类情形下发生。`:387` 那处（`finish` 里）与现状描述一致：自检全部通过、`keepFixture` 未置时删夹具根，删不掉就从 `finish` 抛出。`finish` 在 try 末尾以 `return finish(…)` 返回、**没有 `await`**，返回的 Promise 被拒绝时不会落进同一个 try 的 catch，而是直接穿出 `runSelftest` 与 `selftestCommand`，CLI 顶层报内部错误——已逐条跑过的十四步结论连同「未覆盖」声明一起丢掉。
4. **selftest 的运行目录**：夹具配置把 `run_root` 设为 `${root}-runs`（夹具根的兄弟目录），`finish` 只删夹具根、从不删它（§5 观察 2）。自检的归档根是夹具里的 `.reviews/`：审查文档、裁决件与 `_meta/` 在夹具根内，运行目录（`worker.log`、交接文件）在 `-runs` 里。
5. **retention 到期整删**（`retention.ts:229-240`）：在 `for (const name of entries)` 循环里，`cliGroupsConfirmedGone` 通过后 `fs.rm(dir, { recursive: true, force: true })`，抛出即穿出 `pruneRunDirs`；`hooks.ts:1671-1686` 的 catch 只记 `retentionError`，待办一行「运行目录清扫本身失败：…——过期目录与凭据副本本次都没处理」。循环里排在它后面的目录既不整删、也不抹凭据；只要它还在，每次会话启动都在同一处中止。被 CLI 记录挡下的到期目录已有一条现成的「落回未到期那条路」（`out.kept++` 后走 `admitScrub` / `applyScrub`）。到期判据取 `max(目录 mtime, status 心跳)`（`:218-223`），遍历按 `readdir` 原序、不排序。
6. **`tryRemoveTempDir`**（`util/fsx.ts:153-166`）：`fs.rm(dir, { recursive: true, force: true, maxRetries: 3 })`，失败返回 `{ code, remaining }`、不抛；`copies` 传空数组时不做现场查。`maxRetries` 只对 EBUSY / EMFILE / ENFILE / ENOTEMPTY / EPERM 重试，EACCES 不重试（EV-199 报告已记）。
7. **清零守卫 W3**（`test/unit/probe-fixture-cleanup.test.ts:583-597`）：论域只有 `src/trivium/probes`、`src/trivium/adapters`，`countRecursiveRm` 按括号配平截取实参、认 `rm` / `rmdir` / `rmSync` 任意接收者与速记 `recursive`。`e00a1e2` 上两目录之外的递归删除恰好八处：`util/git.ts:121`、`selftest.ts:202`、`:387`、`retention.ts:237`、`lock.ts:522`、`install.ts:243`、`:477`、`:491`；外加 `util/fsx.ts:155`（`tryRemoveTempDir` 本体，带 `maxRetries`）。
8. **注入点**：`os.tmpdir()` 在 POSIX 上每次读 `TMPDIR`，`os.homedir()` 读 `HOME`；`run()` 的 `env` 叠加在 `process.env` 之上、子进程继承。git 在 `add` 时对内容有变或 stat 信息不匹配的文件跑 clean 过滤器，过滤器子进程继承 git 的环境——包括 `workTreeHash` 设的 `GIT_INDEX_FILE`。临时索引由 `read-tree HEAD` 填充、没有 stat 信息，于是 `add -A` 对每个匹配文件都跑过滤器。scratchpad 实测（git 2.54.0）：过滤器在 `dirname "$GIT_INDEX_FILE"` 里建只读子目录、放一个文件，`write-tree` 的结果与不挂过滤器时逐字相同。这给了一个**不改生产代码**的摆锁法（§2.6）。
9. **`--start` 里的 `workTreeHash` 次数等于入选侧数**（计划双审 AGY-01）：`review.ts:810` 对每个入选侧各调一次 `freeze`，每次都在 `freeze.ts:442` 算一遍；worker 里只有漂移复算（`review.ts:1233`）一次。worker 由 `spawnDetached` 以 `〈node〉 〈bundle〉 review --worker 〈run_id〉` 派生（`run-protocol.ts:433-436`），环境与 `--start` 相同、没有专属变量——能区分两者的是进程命令行。

## 2. 设计

### 2.1 `workTreeHash`（`util/git.ts`）

```ts
import { warn } from './log.js';
import { makeTempDir, matchesAnyGlob, tildeHome, tryRemoveTempDir } from './fsx.js';

/** 同一进程只提示一次（决策二）：送审、漂移复算、探针一轮里会调好几次，同一个成因不必刷屏 */
let indexResidueNoticed = false;

/** 临时索引目录删不掉时的提示正文（导出供单测逐字比对） */
export function indexResidueText(dir: string, code: string): string {
  return `工作树哈希的临时目录删除失败（${code}）：${tildeHome(dir)} 仍在——` +
    'TriviumCode 只往里写了 git 临时索引、没有凭据，请手工删除（本进程之后的同类失败不再提示）';
}

export async function workTreeHash(cwd: string, opts: GitCallOptions = {}): Promise<string> {
  const tmpDir = await makeTempDir('trivium-index');
  const idx = path.join(tmpDir, 'index');
  try {
    … // 原样
  } finally {
    // 删不掉不抛（EV-204）：哈希已算出就照常返回，git 某一步失败就让那个原始错误出去，不被删除失败顶替
    const left = await tryRemoveTempDir(tmpDir, []);
    if (left && !indexResidueNoticed) {
      indexResidueNoticed = true;
      warn(indexResidueText(tmpDir, left.code));
    }
  }
}
```

- 经 `util/log.ts` 的 `warn`（`⚠️  ` 前缀、写 stderr）：`--json` 模式下 stdout 只有一个 JSON 文档的铁律不受影响。
- **措辞相对决策二原话有改动，收尾时向用户说明**：原话「其中只有一份 git 临时索引、没有凭据，请手工删除」→「TriviumCode 只往里写了 git 临时索引、没有凭据，请手工删除」。理由：①被超时按进程组杀掉时 `index.lock` 也会留下（§1.1），「一份」说少了；②目录全貌不归本程序管，用户仓库的 clean 过滤器之类也能往里写（计划双审 CODEX-04），主语收到本程序，安全关键的「没有凭据」只对本程序写入的东西负责。句末补「本进程之后的同类失败不再提示」，让读的人知道后面没提示不等于后面都删成功了。
- 「同一进程只打一次」是模块级标志，不可撤销、不导出重置口（计划双审 AGY-03 驳回）：进程内用例（G1～G3b）不断言 stderr，标志被置真只少打一行；「只打一次」只在 G4 的子进程里断言。
- 调用方看到的形态：送审 `--start` 与同步 `review` 的提示进终端 stderr；**worker 路径（漂移复算）的 stderr 落 `worker.log`**（`run-protocol.ts:430`），没有人读——决策二定了不新开通道，写进 §4 残余。doctor 的两个夹具工厂与两侧 scratch_paths 比对同样只打 stderr，不进 notes（`workTreeHash` 没有 notes 通道，决策二）。

### 2.2 selftest（`selftest.ts`）

1. **先让建夹具失败那一处走得到**：`buildFixture(made: { dir: string | null }, init = initFixtureRepo)`，`mkdtemp` 一返回就 `made.dir = raw`（用对象持有，不用回调里赋值的 `let`——TypeScript 在 catch 里会把后者收窄成 null，坑清单已记）。删除只认 `mkdtemp` 的返回值 `made.dir`（2026-09-20 事故后的 R1），不认 `realpath` 之后的 `root`。
2. **catch（建夹具失败）**：`made.dir` 非空就 `tryRemoveTempDir(made.dir, [])`；失败步骤仍是那一条「创建夹具仓库」、`detail` 仍是 `buildFixture` 抛出的原始消息（决策三）；删不掉时结果带 `cleanupResidue`、`fixtureRoot` 报 `made.dir`，删掉了 `fixtureRoot` 仍报 `''`（与现状同）。
3. **`finish`**：`!keep` 时 `tryRemoveTempDir(root, [])`，删不掉就带 `cleanupResidue`、`ok` 与 `steps` 原样（决策三：结论不因删不掉而改变，不新增失败步骤）。`kept` 仍为 false（我们没有打算保留它）。
4. **结果形状**：`SelftestResult` 加 `cleanupResidue: string | null`。措辞（主语同 §2.1 收到本程序，计划双审 CODEX-04）：

   ```text
   自检夹具目录删除失败（〈错误码〉）：〈~ 归一的路径〉 仍在——自检只往里写了夹具文件与本次自检的审查留痕（.reviews/），没有凭据，请手工删除
   ```

   自检写进夹具的：`src/payment.ts`、`README.md`、`.gitignore`、`.trivium/`（配置与运行时状态）、`.reviews/`（桩产出的审查文档、裁决件、`_meta/`）、`.git/`；桩适配器不碰任何凭据。
5. **渲染**（`renderSelftest`，`:401-418`）：`kept` 为真时原样；否则 `cleanupResidue` 非空时打这一句、**不打**「夹具已清理」；否则原样「夹具已清理。…」。
6. **测试注入口**（计划双审 GLM-01 下沉一层）：`runSelftest(opts, deps = { initFixtureRepo })` 加第二个参数，只给单测换 `initFixtureRepo`（CLI 不传）；真 `buildFixture` 照常 `mkdtemp`、赋 `made.dir`、写文件，最后调 `deps.initFixtureRepo(root)`。理由：§1.3 已核，真实 `buildFixture` 只在磁盘满一类情形下抛，零配额摆不出来；注入点放在 `buildFixture` 的最后一步，生产里的赋值与写文件都在 S1 的执行路径上。`finish` 那一支不靠注入，走真实打包 CLI 的行为级用例（§2.6 S3）。

### 2.3 retention（`retention.ts` + `hooks.ts`）

1. `PruneResult` 加 `removeFailed: { dir: string; code: string }[]`（文档块写明：到期、准入都过了而删不掉的目录；它们落回未到期那条路，计入 `kept`，凭据抹除照走 `admitScrub` / `applyScrub`）。
2. 到期整删改为：

   ```ts
   if ((await cliGroupsConfirmedGone(status)).gone) {
     if (opts.dryRun) { out.removed.push(dir); continue; }
     const left = await tryRemoveTempDir(dir, []);
     if (!left) { out.removed.push(dir); continue; }
     // 删不掉（EV-204）：记账、继续后面的目录；这一个落回未到期那条路——删到一半时凭据副本可能还在，照常抹
     out.removeFailed.push({ dir, code: left.code });
   }
   ```

   之后的 `out.kept++` 与凭据抹除对它照走——与「到期而被 CLI 记录挡下」同一条路（`:231-233` 的注释同步补一句）。**决策四「凭据抹除照做」我的读法是两层**：排在后面的目录照常整删或抹除；删不掉的这一个自己也走抹除（递归删除是删到一半才失败，载体可能正好在没删掉的那部分里）。三侧审查员都支持这一读法；若用户的本意只是前一层，退回「删不掉就 `continue`」只改一行。收尾时向用户说明。
3. **会话启动待办**（`hooks.ts:1660-1770`）：读 `r.removeFailed`，纳入早退条件；在 `pruned` 那一行之后单列：

   ```text
     · 〈N〉 个到期运行目录删不掉：〈dir1〉（〈code1〉）、〈dir2〉（〈code2〉）、〈dir3〉（〈code3〉）〈等 N 个〉——已按未到期目录做了凭据抹除；请人工删除（删掉一部分的目录要再过一个保留期才会自动重试）
   ```

   最多列三个，超出写「等 N 个」——会话启动待办会注入到每个会话的上下文里，权限类成因可能一次几十个；路径与同段其余各行一致不做家目录归一（它们都写原路径）。删不掉的那个目录若抹除也失败，会同时出现在「凭据副本抹除失败」那一行——两件事都是真的，不去重。
   **不承诺「下次会话启动会再试」**（计划双审 CODEX-01）：删掉部分直接子项会刷新目录 mtime，下次会话按 `max(mtime, 心跳)` 判为未到期、不进整删分支，这一行也随之不再出现；什么都没删掉就失败时 mtime 不变，下次会照常重试并再出现。
4. **删掉一部分之后的两种后续形态**（计划双审 CODEX-01、GLM-02；不改代码，写进 §4 残余、§10.5 补句与 RUNBOOK）：`status.json` 还在——下次会话判未到期，落回抹除照常（哨兵已收工的侧跳过），静默保留到下一个保留期再试整删；`status.json` 已被删掉——下次会话 status 为 null，未到期、`admitScrub` 记 `unknown`、不抹，待办里出现的是既有的「状态读不到…请人工检查后删除」那一行。两种都仍有出口（第二种可见，第一种在下一个保留期重试）。
