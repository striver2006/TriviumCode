## 3. 改法

### 3.1 EV-127（D1 取 ②）

- `parse.ts` :225 改为：

  ```ts
  const pathRe = /(?<![A-Za-z0-9_./-])(?:\.\/)*((?:src|lib|app|test|tests|doc|docs|packages|scripts)\/[A-Za-z0-9_./-]+\.[A-Za-z0-9]+)\b/g;
  ```

  含义：路径 token 必须**整段**以已知根目录起头——前一个字符不能是字母、数字、`_`、`-`、`.`、`/`；允许前导 `./`（去掉后再比）。根目录集合与终点规则不变。
- 函数上方补注释：只核「以九个常见根目录起头的 ASCII 路径」；中段出现根目录名不算（EV-127 实测 56 条误报）；`../`、绝对路径、非 ASCII 文件名、其它顶层目录（如 `skills-src/`）不在核对范围——漏报方向，已登 BACKLOG（§6.3）。
- `ReviewIntegrity.evidenceNotInConsulted` 的文档注释同步一句。
- `guard.ts`、`review.ts` 不改：告警文字与去向不变。

### 3.2 EV-128（D2 取 (a)）

**新函数**（`meta.ts`）：

```ts
/**
 * 把被 --cancel 的运行在归档侧收尾。**自身不抛**：任何异常都转成 skipped 并带原因。
 * 两步各自独立判定，可重入：中途被打断时，再跑一次 --cancel 会把没做完的那一步补上。
 */
export async function finalizeCancelledRunMeta(i: {
  layout: ArchiveLayout; stage: Stage; runId: string; lock: TaskLock;
  /** cancelRun 传 goneNow.gone */
  workerGone: boolean;
}): Promise<{ runMeta: FinalizeStep; task: FinalizeStep }>;
type FinalizeStep = { kind: 'written' } | { kind: 'skipped'; why: string };
```

**第一步：run.json**。前提任一不满足即 `skipped`（带原因），不改文件：
1. `workerGone` 为真，即 `workerConfirmedGone` 已确认工作进程不在（C13）。没确认到就不写：进程组里可能还有后代，或 worker 正要写收尾，两个写者会互相覆盖。
2. 主题与阶段已知（由 `cancelRun` 的 `identity` 给出，C1）。
3. 原始 JSON 的 `schema` 是 `trivium.run.v2`。v1 留痕不写：`readRunMeta` 读进来的是**迁移后的内存形状**，写回去会把一份历史文件改成 v2。
4. 能读出且合契约，`status === 'running'`。已是终态（含 C8 那种 run.json 先写完、`status.json` 还没改的窗口）一律不动——「不追溯改写」与 :804 同一口径。

满足时**只改三格**：`status: 'cancelled'`、`finished_at: <now>`、`gate.state: 'cancelled'`（D2 子项 ②）。`artifacts[]`、`snapshot`、`critics`、`guard` 原样；`gate.warnings` 不追加（EV-133 注记 ②：它会被回灌成 `run_warning`）。写前照旧过 run.v2 校验（`writeRunMeta`）。

**第二步：task.json 的运行登记**（D2 子项 ①）。**不依赖第一步是否写了**，独立判定（r1 GLM-01）：
- 重新读 run.json，其 `status` 为 `cancelled`（不论是这一次写的，还是上一次 `--cancel` 写的）才继续；否则 `skipped`。
- 在 `updateTask` 的临界区里按 run_id **精确匹配**：找不到条目 ⇒ 不写盘、`skipped`「task.json 无此运行的登记」（C3 那种中断形态；不新建、不取末条，r1 CODEX-04）；条目 `status` 已不是 `running` ⇒ 不写盘、`skipped`；否则只改这一条的 `status` 为 `cancelled`，其它条目与其它键不动。不走 `registerRun` 的整条覆盖，避免把骨架期以后的其它字段回退。

**失败出口**（r1 CODEX-02 ≡ AGY-01 ≡ GLM-02）：两步各包一层捕获，读、校验、`writeAtomic`、`updateTask` 的任何异常都转成该步的 `skipped`（`why` 带异常首行），函数本身永不抛。只设这一道：`cancelRun` 调用处不再另包，免得两层互为冗余、变异咬不住。

**在 `cancelRun` 里的位置**（r1 CODEX-01 ≡ GLM-01）：

```
:804 终态早退 → 杀进程组 → :842 goneNow 复核 → :844 抹凭据副本
  → 【新】finalizeCancelledRunMeta（workerGone: goneNow.gone）
  → :854 patchStatus（status.json 置 cancelled） → :864 回收锁与闸门
```

放在 `patchStatus` **之前**，中断时的恢复路径：
- 死在新函数第一步之后、第二步之前：status.json 仍非终态 ⇒ 再跑 `--cancel` 走全流程，第一步因前提 4 跳过，第二步看到 run.json 已是 `cancelled`、task.json 仍 `running` ⇒ 补齐。
- 死在新函数之后、`patchStatus` 之前：同理，两步都跳过，`patchStatus` 与回收照常。
- r1 的顺序（`patchStatus` 在前）下，死在两者之间 ⇒ status.json 已终态 ⇒ 再跑在 :804 早退，run.json 永远 running。这是改顺序的原因。

`cancelRun` 播报：两步各一行 `step`——写了说「已把归档里的 run-<id>.json 收尾为 cancelled」「已同步 task.json 的运行登记」；跳过说原因；异常转成的跳过用 `warn`。

同步路径（不经 `--start` 的 `review`）不涉及：status.json 与交接文件只由 `startRun` 写（`run-protocol.ts` :360 交接文件、:371 status.json），对同步运行 `--cancel` 在 C1 第一步就报找不到。

**为什么这不破坏 EV-133 的不变量**：EV-133 说的是「**收尾后**不再更新」。取消轮从来没有收尾——worker 被杀在收尾之前，run.json 停在骨架。`--cancel` 的第一步就是它的收尾，并且只在 `status === 'running'` 时写，写完即为终态，此后同样不再更新：再跑 `--cancel`，要么在 :804 早退（status.json 已终态），要么被前提 4 挡下（status.json 因中断仍非终态）。每份 run.json 仍然是「一份骨架 + 至多一次终态写入」。

**为什么不撞提交锚**：C5——HEAD 里是 `running` 时，锚只要求 `run_id` 不变、已登记条目不少不改；本步只改三格、`artifacts[]` 原样。HEAD 里已是终态时前提 4 挡下、不写。于是「运行中途提交过一次、之后被取消」这种最容易撞锚的序列也能正常提交（§4.2 E4 钉住）。task.json 不在 `_meta/` 下，不受 `immutableChangeReason` 的位置判据约束。

## 6. 风险与边界

### 6.1 EV-127 新判据的两个方向

- **误报**：历史 383 份审查件上只减不增（§2.1）。剩下 96 条里 39 条仓内不存在，基本是意见在描述假想场景时写的示例路径（`src/a.ts`、`src/leak.txt`），与本次无关，属剩余误报（§6.3）。
- **漏报**：不以九个根目录起头的路径不再被核对。旧判据对它们报的是截断后的错名，指向的文件本来就不对。本仓历史上这一类 34 条（§2.2 第二行）全部指向未跟踪的构建产物（`dist/`、`skills/dual-critic/scripts/trivium.cjs`）、仓外路径或示例路径，没有一条是入仓文件；入仓的 `skills-src/…` 那 14 条全都已列进 consulted。所以这次实测里漏报代价为零，但往后审查员若引了 `skills-src/…` 又没列进 consulted，新判据不会报。要补它只能扩根目录集合或从项目树取顶层目录，属收紧，不在本主题（§6.3）。
- 非 ASCII 文件名（主设计本身）新旧判据都不核——字符类不含中文，这是既有漏报，不变。

### 6.2 EV-128 的边界

- **未确认退出时不写 run.json，且之后补不回来**：`workerGone` 为假时第一步跳过，而 `patchStatus` 照旧把 status.json 置为 `cancelled`；此后再跑 `--cancel` 在 :804 早退，这份 run.json 一直留在 `running`。与改前相同，输出会说明原因。不改 :804 的早退语义（它守的是「不追溯改写」），本主题不动。
- **中断的恢复**：新函数排在 `patchStatus` 之前，两步各自独立判定，中断后再跑一次 `--cancel` 即补齐（§3.2）。
- C8 窗口：run.json 已终态、`status.json` 仍 `running` 时，`--cancel` 照旧把 `status.json` 改成 `cancelled`，run.json 不动，两者不一致。`report` 与提交锚都以 run.json 为准。改 `status.json` 那一侧属于既有行为，本主题不动，登记在报告里。
- **`runTerminal` 的结果翻转**（r1 GLM-03）：主题锁用 `status !== 'running'` 判「该运行已终态、锁可回收」。取消轮回写后由「未终态」翻为「终态」，是本主题唯一改变判定结果的读者，**有意**：取消轮不会再有写者，锁可回收是正确结论；`cancelRun` 本来就会回收本 run 的锁，翻转只影响它没回收到的残留锁。
- **其余读者不变**：`gate`、当轮 Driver 判定、Hook 读的「最新可读留痕」都不看 `status`（C7），取消轮仍是最新留痕，与改前相同。要不要让这些读者跳过 `cancelled` 是另一个取舍，本主题不做。
- 历史 4 份 `running`（C10）不回填：是取消、崩溃还是中途放弃分不出来，回填等于替没发生过的收尾作证。
