## 2. 方案

### 2.1 请求面：一处算定（`review.ts`）

- 准备阶段在**可用性检查之前**逐侧算一次 `routed = resolveTier(cfg, critic, stage, cliOverrides[critic] ?? {})`（`mergeCliOverrides` 随之上移，仍只调一次），存进按侧的表；可用性检查与路由循环都取这一份。路由循环里原 `resolveTier` 调用删去。
- 请求：`model: routed.model`；`effort: routed.effort ?? undefined`（字段保持可选，形状不变）；`profile_requested: routed.vendorProfile`；新增 `tier: routed.tier`、`tier_source: routed.tierSource`（`CriticRequest` 两个**必填**字段，见 §2.6）。
- `effortFor` 删除；`types.ts:62`、`review.ts:1978` 两处引用它作对照的注释改指 `resolveTier`。删它不丢「`agents.gemini` 缺段响亮失败」的保障：agy 适配器的 `availability` 与 `run` 仍经 `agentConfigOf` 取段（`agy.ts:275`、`:312`）。
- **为什么与现役逐字相同**（本仓裸 slug）：裸 slug 格子 ⇒ `resolveTier` 的 `effort` 只可能来自「antigravity 段阶段级 effort」回落（`base.ts:1979-1984`，与 `effortFor` 同一判据：注册表 vendor 为 antigravity 且配置段 vendor 也是）；codex / claude / glm 为 null。`vendorProfile` 对 openai 取 `agents.codex.profile`（`base.ts:1986-1997`），对别家为 null——与 `vendorProfileOf` 逐值相同。用例与验收见 §3.1 R 组、§3.4。
- `config.ts:610` `vendorProfileOf` 的唯一消费方就是 `review.ts:1218`（已 grep），随之删除。`agents.codex.profile` 在 `resolveTier` 与 codex 适配器（`authProbe`、`availability` 缺省分支）里仍有直接访问，`config-consumers` 对账不受影响；全量时核一眼。

### 2.3 厂商 profile：可用性检查按本轮解析值

- 接口：`availability(ctx, opts?: { vendorProfiles?: readonly (string | null)[] })`。缺省（不传）= 旧行为，取 `agents.codex.profile`；传了就逐个判（去重、跳过 null）。只有 codex 实现读它，另三家签名照收、忽略。
- `review.ts`：传 `[routed.vendorProfile]`（§2.1 那一份）。
- `preflight.ts` `checkReadonlyCapability`：改收 `overrides` / `tierFlags` / `scope`，逐侧对 `scopeStages(scope)` 的每个阶段用同一个 `mergeCliOverrides` + `resolveTier` 收集解析值（跳过 `missingTier` 与无模型的格——它们由「模型 slug 合法」报）。`--stage all` 时一侧可能有多个厂商 profile，逐个判、逐个报。
- 目录比对（`checkModelSlugs`）与原生枚举（`checkTierCombos`）第 4 步起已按 `routed.vendorProfile`，不改。
- **三处同值的论证**：可用性、目录、`-p` 三处都是 `resolveTier(cfg, critic, stage, mergeCliOverrides(overrides, tierFlags)[critic])` 的 `vendorProfile`——纯函数、同一组输入。`review` 准备阶段里可用性与 `-p` 取同一个对象；`checkModelSlugs` 内部另算一次，输入相同。§3.1 P 组用一个「档位 profile ≠ Agent 配置段 profile、且模型只在前者目录里」的夹具同时断言三处。
- **探活不改**（§1.6 ①）：`authProbe` 是「CLI 与登录态能不能真跑一次」的最小 headless 调用，按配置段 profile 探、按指纹缓存。改为按解析值会让 `--stage all` 下一侧可能探多次（真实配额）、缓存键随档位变。解析出的厂商 profile 有没有凭据，仍由 `availability()` 的 `credentialed` 静态判据守住；「凭据在、但过期 / 被拒」的那一格要到运行期才暴露——写进主设计 11.5 厂商 profile 段作边界，BACKLOG 新登一条（探活按解析出的厂商 profile，触发条件：真实使用档位换家族时撞上）。

### 2.4 claude 原生枚举（探针 + 适配器）

## 5. 风险与遗留

1. **现役行为的唯一预期变化面在档位形态**：配了 tiers 的仓库，gemini 档位没写 effort 时从此不下传阶段级 effort（11.5 原定）；codex / claude 档位里的 effort 从此真下传。本仓无 tiers，不受影响。
2. **claude 探针结论形状变**：旧结论缺 `effort_levels` ⇒ 预检对 claude 的 effort 跳过校验并点名「旧探针结论」，不硬拒；重装后零配额 doctor 即落盘。
3. **front-matter 多五键**：审查员回显这些键会被剥（`ECHOED_ORCHESTRATOR_KEYS` 同批加），不会把整份判死。
4. **回滚代价**（CODEX-01）：本步之后产生的 parse_fallback 侧持久化的是未剥原文（`review.ts:1783`），`gate --check` 重试解析用当时安装的 bundle 的剥离清单（`gate.ts:1346-1350`）。若回滚到本步之前的 bundle，审查员照抄的新五键不会被旧清单剥掉、撞 `review.v1` 根 `additionalProperties: false`，该轮退回 `〈前缀〉-F〈n〉` 回退编号，按回退编号裁决即可；不丢数据。接受此代价。
5. **CriticRequest 两个必填字段**：worker 交接文件由同版本写读；跨版本（旧 `--start`、新 worker）不在支持面内（既有约定）。
6. 坑清单适用项：测试改 `doc/` 时不跑全量；`scratchDir`；`config-consumers` 对账（删 `vendorProfileOf` 后核 `agents.codex.profile` 仍有消费方）；`driver-wiring` 护栏（`overrideReasonFor` 参数次序不动）；变异替换串避开 `$` 特殊模式；凭据样例不写完整字面量。
