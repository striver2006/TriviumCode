## 3. 设计约束（已定事项的落地口径）

> 本节是第 2 步并入主设计的依据。**这里写的是方向与边界，措辞以并入后的主设计为准**；第 1 步的事实若推翻某一条，第 2 步按事实改写并在第 2 步计划里写明偏离。

### 3.1 纪律 6b 的落法（D-6）

档位链路的契约（11.5 档位路由、7.1 旗标、13.1.1 配置形态、6.7.1 字段语义、11.1 思考等级透传、12.1 增行、17.2 增行）**在第 2 步一次性并入**，因为 tiers、旗标、配置、run 字段、适配器回读五者互相咬合，分散并入会在中途出现「旗标已入规范、run 字段语义未定」的半截态。report 聚合与 AC-25 的契约与档位无关，**在各自那一步开头并入**（第 7、3 步）。

### 3.2 事实先于契约

档位契约里有三处取决于实测（claude 有无思考等级机制、codex 的 effort 回读能证到哪层、agy 低中档 slug 的回读形态）。按纪律 1「先探路后编码」，第 1 步先拿事实，第 2 步再写契约；第 1 步结论按纪律 6a 回填主设计 3.6 / 3.7，与第 2 步同版落盘。

### 3.3 run 契约（用户已定）

- 不升 v3；`effort_requested` / `effort_effective` / `tier_source` 在 v2 原地接线；字段**缺席** = M11 之前的旧留痕，**null** = 该侧没有这项事实。
- `effort_effective` 只取回读值，不采信请求值；请求值与生效值分记。
- 旧字段 `effort` 保留并继续写、与 `effort_requested` 同值；schema 描述标为旧名，新读者一律读 `effort_requested`；删不删不在 M11。
- 新增事实照 `unknown_reason` / `after_tree_hash` / `plan_final_check` 先例在 v2 原地扩可选字段；只有要改既有必填字段含义或往封闭节点塞不兼容形状时才考虑升版本，遇到即停下交用户定。

### 3.4 config 契约（D-3）

`config.v2` 原地扩可选键：新增键全部可选，旧配置不改也能跑、行为不变。演进设计 §11 :629-635 与 schema 描述 :470 早已预告这一形态。已知代价：旧构建读到带新键的配置会被 `additionalProperties: false` 拒在预检（零工件），与升 v3 时旧构建的表现相同。

### 3.5 档位数据模型（D-1，主设计 18.1 #17 拍板为「挂 Agent」）

- `agents.〈id〉.tiers` 为 `low` / `medium` / `high` 三键的映射（可缺键），每档是组合 `{model, effort?, profile?}`，可跨模型、跨家族；`effort` 取该模型的**原生枚举**值，缺省表示该 Agent 用模型选择承载档位差异（glm、gemini）；`profile` 只对 openai vendor 有意义（§3.6）。
- `agents.〈id〉.default_tier` 可选，取三档之一。
- **原生 effort 枚举不在配置里手写**（不加 `agents.〈id〉.models`）：codex 由探针从 `debug models` 的 `supported_reasoning_levels` 取并落盘（`probes/codex.ts:321-331` 已在解析，只差落盘）；gemini 由 slug 后缀派生；glm、claude 无此概念（第 1 步若证实 claude 有，再定）。探针拿不到目录时**跳过 effort 校验而非硬拒**（同既有 slug 规则），生效值回读兜底。
- `agents.codex.effort`（阶段级、枚举 low/medium/high、死键）**标 deprecated，不接线**；`agents.gemini.effort` 有真实消费方，保留为「档位表格子是裸 slug 时」的回落。
- `init` 模板**不写** tiers 示例。

### 3.6 厂商 profile 与档位（D-2，EV-22 + EV-27 结构部分）

- 档位条目可带厂商 `profile`：`tiers.high = {profile: deepseek, model: deepseek-v4-pro, effort: max}`，「换家族 = 换档位」。
- 新增 `--profile-codex 〈名〉` 作单次精确覆盖。
- 厂商 profile 的取值次序：`--profile-codex` > 档位条目的 `profile` > `agents.codex.profile` > 不传。
- preflight 核「档位里的模型在该 profile 的模型目录中」（`models_by_profile` 已有，`probes/codex.ts:933`）。

### 3.7 路由优先级（D-8）

1. **命令行**：`--tier-〈id〉` 选档；`--model-〈id〉` / `--effort-〈id〉` / `--profile-codex` 精确覆盖。精确值与档位同时给出时，**按字段合并**——精确值覆盖档位组合里的对应字段，并告警。`--effort-〈id〉` 可单独给，作用于其余各级解析出的模型；值对该模型原生枚举校验。

## 5. 审查要点与你这一侧的镜头

被审对象是一份**还没实施的计划**。这决定了审查的重心与代码审完全不同：

- **现在指出比事后返工便宜几个量级。** 计划阶段最值得找的是「做了会发现方向不对」
  的问题，而不是措辞与格式。
- **不可逆决策优先。** 数据模型、对外契约、迁移与回滚路径、第三方依赖的引入——
  这些一旦落地就很难改。先审它们，再审其余。
- **计划没写的部分也是问题。** 需求里有、计划里没有的，属于遗漏；
  计划里含糊其辞（「适当处理」「必要时优化」）的，属于未决策。两者都要指出。
- **不要替 Driver 重写计划。** 指出「§3 没有覆盖并发回滚」即可，
  不要给出整段替代方案——那会让裁决变成二选一而不是逐条判断。

判断一条意见该不该提，用这个标准：**如果按现在的计划做完，这个问题会不会变成返工？**
会，就提；不会，且只是风格偏好，就不提（但可以写进 `agreed` 或 `not_covered`）。
