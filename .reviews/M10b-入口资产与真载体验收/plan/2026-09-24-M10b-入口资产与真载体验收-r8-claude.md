## 1. 更正 r7 §6 第 2 条

**原文**（r7 §6 第 2 条）：「EV-111（构建标识误报）……**建议在第 4 步之前做，可以省掉 §3.7 的规避**；但它不是第 4 步的前置……」
r7 §3.7 末句的前提「**EV-111 修掉之前**，第 4 步的兼容轮在构建之后不做任何提交」同样隐含「修掉之后规避解除」。

**为什么不成立**：r5 §7.3 白名单行比的是**字段**，即 `snapshot.build.git_head` 对 `snapshot.git_head`，不是告警。
EV-111 只改了告警规则（`buildStampWarnings`：作用面指纹一致时不再比 HEAD），没有改字段。构建之后只要有一次纯文档提交，这两个字段照样不等，白名单行照样判回归。
EV-111 计划 r1 §7 第 2 条提出这个读法，计划双审三侧一致确认（裁决件第 38 行：「r5 §7.3 白名单行比的是字段，r7 §6 第 2 条『可以省掉 §3.7 的规避』不成立」）。

**怎么漏的**：r7 落笔时我只想到「EV-111 消掉那条告警」，没回头看白名单行比的是字段还是告警。改一条判据的语义之前，要先列清所有断言这条语义的落点。

**处置**：r7 §6 第 2 条由 §3 替换；r7 §3.7 由 §2.3 替换。EV-111 本身已结案（§3），它的收益是去掉纯文档提交后的误报噪声，不是解除规避。

## 2. r5 §7.3 白名单「构建标识」行改口径（用户 2026-09-24 拍板）

### 2.1 原文与问题

r5 §7.3 白名单行原文：「`run.json` `snapshot` 旁的安装副本构建标识｜EV-82 小主题落地后新增；claude 轮与 `snapshot.git_head` 一致｜§3.3.2」。

「一致」是等式，正是 EV-111 的误报形态：构建后哪怕只有一次纯文档提交，等式就不成立，等于要求构建后零提交。
r7 §3.4 第 6a 条已经在 T2 判据里把同一个等式放宽为「收口提交或其后代」（r7 修正，CODEX-02），白名单这一行当时没跟着改，只能靠 r7 §3.7 的规避兜着。

### 2.2 新口径（替换 r5 §7.3 该行「取值口径」列）

claude 兼容轮（r5 §7.1 第 1 行：code 阶段，本会话，**本仓模式**）的 run.json 同时满足：

| # | 断言 | 对应 r7 §3.4 |
| :-- | :--- | :--- |
| W1 | `snapshot.build` 非空，且 `snapshot.build.dirty === false` | 第 6a 条后半 |
| W2 | `snapshot.build.git_head` 是 `snapshot.git_head` 或其祖先（`git merge-base --is-ancestor`） | 第 6a 条前半的放宽形态，见下注 ① |
| W3 | `gate.warnings` 不含 r7 §3.4 第 6b 条所列五类构建标识告警（`BUILD_WARN_MISSING`、`BUILD_WARN_DIRTY`、`BUILD_WARN_STALE_INPUTS`、`BUILD_WARN_INCOMPLETE`、`BUILD_WARN_CHECK_FAILED`，按 `build-stamp.ts` 常量前缀匹配）；`BUILD_WARN_HEAD` 容忍 | 第 6b 条，逐字同口径 |

「来源」列改为「r5 §3.3.2；r8 §2.2」。r5 §7.3 表下「取值不符同样判为兼容性回归失败」照旧适用。

**注**：
1. **W2 为什么不是「收口提交或其后代」**：第 6a 条的下界锚在 EV-82 的收口提交上，兼容轮没有对应的收口提交。
   兼容轮要证的是「安装副本就是当前工作树的作用面」，这由 W3 禁止的 `STALE_INPUTS` 与 `INCOMPLETE` 两类直接证明（收尾重算的作用面指纹与构建时一致）。
   W2 只核出处：构建标识来自当前 HEAD 本身或它之前的提交。
   **W2 的误判边界**：HEAD 挪到作用面相同、但不以构建提交为祖先的另一个提交（EV-111 r1 §2 情形 S3：checkout、reset、rebase、amend）时，安装副本内容其实一致，W2 仍判不过。
   第 4 步在 `main` 上顺序提交，不做这几种操作，撞上时重新 build + install 即可（零配额）；
2. **`BUILD_WARN_HEAD` 容忍项在 EV-111 之后空转**：按 EV-111 的新规则，它只会与 `STALE_INPUTS` 或 `INCOMPLETE` 同时出现，而这两类都在 W3 的禁止清单里
   （EV-111 计划 r2 §7 第 1 条；设计 v1.3.38 §6.7.1）。为与第 6b 条逐字同口径，照写不删；
3. **边界同第 6b 条**：W3 比的是收尾时的工作树与构建时刻的作用面指纹，不是安装副本本身；「改作用面 → 重装 → 改回」看不见。启发式，不完备；
4. **不进第 4 步开工钩子**：r5 §11 的钩子管 P-a / P-b / P-c，不管 J3。J3 由第 4 步报告的差异表逐条列 W1～W3 读数（r5 §3.1 J3 行）；
   是否把 W1～W3 写成 evidence 只读脚本的机读断言，由第 4 步子计划定。

### 2.3 r7 §3.7 替换为

> **r5 §7.3 白名单「构建标识」行已由 r8 §2.2 改口径，r7 §3.7 原先的规避解除。**
> 第 4 步 claude 兼容轮在构建之后**可以**有安装作用面之外的提交（文档、evidence、`.reviews/`）；**改了安装作用面**（`src`、`scripts`、`skills`、`package.json`、`package-lock.json`、`tsconfig.json`）
> 就必须重新 build + install 再派发，否则 W3 的 `STALE_INPUTS` 判回归。
> 规避是由改口径解除的：W3 本就容忍 `BUILD_WARN_HEAD`，即使没有 EV-111，改口径后纯文档提交也不再判回归。EV-111 的作用是让那条告警不再出现（去噪），不是本条的前提。
