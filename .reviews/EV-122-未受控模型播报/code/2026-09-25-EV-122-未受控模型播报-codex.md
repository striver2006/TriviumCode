**问题**：unenforcedHint 的 switch 只列枚举里的两个 cause、没有 default 分支，而函数签名声明返回 string。运行时若 cause 落在两值之外，它返回 undefined，模板拼接把它变成字面量「undefined」直接进用户可见的收尾播报。这不是纯理论：CriticResult.model_unenforced 还有一条不经类型检查的入口——TRIVIUM_STUB_CRITIC 的注入串由 readStubConfig 只做 JSON.parse 就断言成 StubConfig（跨进程故障注入是本仓登记的机制），手写的 cause 会经 stub 的 baseResult 原样透传到 judgeSide → renderGuardWarnings。

**依据**：只读复现（导入已构建的 dist/test/src/trivium/guard.js）：unenforcedHint('no_model') 与 unenforcedHint('whatever') 均返回 undefined；把 {requested:'a',effective:'p/b',cause:'no_model',reason:'r'} 喂给 judgeSide+renderGuardWarnings，播报落成「…这一轮不构成真正的双审。undefined」。同文件的 reorderHint（guard.ts:945 起）对同形的不可达档留了防御分支，本函数没有。同一路注入的坏 cause 还会在收尾被 writeRunMeta（src/trivium/meta.ts:365-372，校验不过即 throw）按 run.v2.json 的 cause 枚举判死——我用 EV-112 E2 归档 run.json 在内存里复现过 validateRunMeta 的三条拒（坏 cause / 缺 reason / 多键）。适配器自己产不出这两步（decideModelUnenforced 已把两值之外滤掉，实测 cause='no_model' 与 null 均返回 undefined），故只影响注入面，记 nit。

**建议**：给 unenforcedHint 加 default 分支（返回一句中性文案或空串），与同文件 reorderHint 的防御分支同形；若想更早拦，可在 judgeSide 透传处对两值之外的 cause 做一次运行期窄化，降级为「只陈述事实、不加排查指向」。
