## 1. 现状核实

### 1.1 实遇

EV-112 E2（run `20260924T172304Z`，单侧 glm）：副本源 `~/.zcode/cli/config.json` 暂时不在，审查运行走无副本一支。
run.json：`model_requested: GLM-5.3`、`model_effective: 84044858-…/qwen3.8-max`、`model_route: global`、**`model_override_applied` 字段缺席**；收尾 `message` 为空，守卫一句没说。
glm 侧实际不是 GLM：FR-06 的模型路由与 NFR-06 的异构默认在该侧都不成立，只能靠人对照两个字段发现。

### 1.3 可达性与影响面

①副本源缺失：本机今天不会出现，但任何一台没配 `cli/config.json` 的机器上，glm 侧**每一轮**都会静默跑在个人配置默认模型上。
③限定失败：请求的模型不在副本源的 provider 目录里（例如 profile 写了目录里没有的模型名），同样静默跑在副本默认或回落模型上。
两者今天都只留两个字段、零播报。

## 2. 范围

**做**：
1. zcode 适配器在**没做覆盖**、且回读到的生效模型与请求的 modelId 段不同时，产出新字段 `model_unenforced`（§3.1）；
2. 守卫对该字段播报一句（§3.2）；
3. `review.ts` 把它条件展开进 run.json，`run.v2.json` 补说明（§3.3）；
4. 用例、变异、设计文档、RUNBOOK、BACKLOG 同步（§4、§5）。

**不做**：
- 不改模型覆盖本身，不在副本源缺失时判 glm 侧不可用（那是 EV-122 候选 ②，用户未选）；
- 不对「没回读到生效模型」出新播报：那一格已由 `model_effective_source: unverified` 表达；
- 不扩到 codex / agy / claude 三侧：判据归各家适配器（C4 的模型 id 形态问题各家不同），本题只动 zcode；其余三家是否有同类缺口列为 §6 第 4 条请审查员判断。

## 3. 改动

### 3.1 判定（决策 D1：新字段，推荐 (a)）

- **(a) 新可选字段 `model_unenforced`（推荐）**：`{ requested: string; effective: string; reason: string }`，产出条件四条同时成立：
  没做覆盖（`route !== 'config_copy'`）、请求非空、回读到了生效模型、两者 modelId 段（`zcodeModelTail`）不同。其余一律缺席。
  `reason` 取 `prepareZcodeHome` 给的理由（C1 ①③的原文），告诉读者为什么没做覆盖；
- (b) 让 `model_override_applied` 在没做覆盖时也记 `false`。**不取**：该字段的「缺席＝本次无覆盖尝试」是已写进设计 6.7.1 与 schema 的契约，
  守卫 `false` 那句的措辞是「覆盖没落实」，把「根本没做覆盖」塞进去会让两种成因同形，排查方向相反（一个查 CLI 读取点，一个查副本源在不在）；
- (c) 守卫自己拿 run.json 的 `model_requested` 与 `model_effective` 比。**不取**：判据归适配器（C4），各家模型 id 形态不同，判定层统一比较必然误报（设计 6.7.1 `model_override_applied` 行已写明的口径）。

纯函数 `decideModelUnenforced(attempted, requested, effective, reason)` 与 `decideModelOverride` 并列，二者产出条件互斥（一个要求 `attempted`，一个要求 `!attempted`）。

### 3.2 守卫播报

`guard.ts` 侧摘要透传 `modelUnenforced`；存在时播报（与 `model_override_applied === false` 那句同一通道，**不判失守、不阻断**）：

> glm 侧请求的是 `<requested>`，实际跑的是 `<effective>`：本次没有做模型覆盖（`<reason>`），CLI 用的是它自己的默认模型。
> 该侧结论仍然有效，但模型路由（FR-06）与异构默认（NFR-06）在本侧不成立——若另一侧模型与它同家族，这一轮不构成真正的双审。

### 3.3 run.json

`review.ts` 与 `model_override_applied` 同处条件展开（缺席不压成 null）；`run.v2.json` 的 `$defs.critic.properties` 补 `model_unenforced` 说明（可选、对象、三个字符串）；
`types.ts` 的 `CriticResult` 与 run.json 逐侧类型各加一格；桩适配器加注入口（给集成用例用）。

## 4. 验证

### 4.1 用例

- **纯函数**（`decideModelUnenforced`）：做了覆盖 ⇒ 缺席；请求为空 ⇒ 缺席；没回读到 ⇒ 缺席；modelId 段相同而 providerId 不同 ⇒ 缺席；modelId 段不同 ⇒ 产出、三字段原样。
- **`run()` 副本源缺失**（沿用 `zcode-carriers.test.ts` 的假入口与 `runReview` 助手）：请求 `GLM-5.3`、假入口日志的 `context.model` 为 `p/fake-model` ⇒ `model_unenforced` 产出，`reason` 含「未找到」；
  现有 U4（请求 `fake-model`、回读 `p/fake-model`）⇒ 仍缺席。
- **`run()` 限定失败**（沿用 `zcode-model-selection.test.ts` 的 `runWithFakeEntry`）：现有「负格」用例（请求 `nope-model`、不回读）⇒ 缺席（没回读到）；
  新增一格请求 `nope-model`、回读 `p/other` ⇒ 产出，`reason` 含「副本已建但不做模型覆盖」。
- **守卫**：字段在 ⇒ 播报一句、含 requested / effective / reason；字段缺席 ⇒ 不出；与 `model_override_applied === false` 同时不会出现（互斥），各自那句不串。
- **集成**：桩注入 `model_unenforced` ⇒ run.json 逐侧段原样出现、另一侧缺席、收尾 `message` 含该句（仿 `code-stage.test.ts` 里 `carriers_landed` 那条）。

### 4.2 变异

沿用 `scripts/mutation-check.mjs`，规格与输出进 `doc/05_testing/evidence/ev122-mutation-<日期>/`：
- N1 产出条件去掉 `!attempted`（做了覆盖也产出）⇒ 纯函数用例红；
- N2 比整串而非 modelId 段 ⇒「providerId 不同」那格红；
- N3 回读为空时也产出 ⇒ 纯函数用例红；
- N4 `run()` 不接线（恒缺席）⇒ 副本源缺失那格红；
- N5 守卫不播报 ⇒ 守卫用例红；
- N6 `review.ts` 不写进 run.json ⇒ 集成用例红。

### 4.3 验收（零配额）

EV-112 E2 的 run.json 已经是这一格的真实形态：把它的 `CriticResult` 等价数据（`model_requested: GLM-5.3`、`model_effective: …/qwen3.8-max`、`route: global`、理由「未找到 …」）
喂给 `decideModelUnenforced` 与守卫，断言产出与播报——用 evidence 目录里的只读脚本做，不再挪用户文件、不花配额。
`npm run typecheck && npm run build && npm test` 全绿；`trivium doctor --selftest` 全绿。

## 6. 给审查员的重点

1. D1 选新字段 (a) 而不改 `model_override_applied` 语义 (b)、也不让守卫自己比 (c)，理由是否站得住；

4. codex / agy / claude 三侧有没有同类「没做覆盖、实际模型不同、守卫静默」的缺口，要不要另立条目；
5. §4.3 用 E2 的真实形态做零配额验收是否足够。
