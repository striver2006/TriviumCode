### 1.3 可达性与影响面

①副本源缺失：本机今天不会出现，但任何一台没配 `cli/config.json` 的机器上，glm 侧**每一轮**都会静默跑在 CLI 全局默认模型上。
③限定失败：请求的模型不在副本源的 provider 目录里（例如 profile 写了目录里没有的模型名），静默跑在副本源的 `model.main` 或 CLI 的回落模型上（C8）。
两者今天都只留两个字段、零播报。
**不播报的一格**：③支回落的模型 modelId 段恰与请求相同——此时实际跑的就是请求的模型，不播报是对的（计划双审三侧一致）。

## 2. 范围

**做**：
1. `prepareZcodeHome` 三个 `global` 出口各产出结构化成因 `cause`（§3.1）；
2. zcode 适配器在**没做覆盖**、且回读到的生效模型与请求的 modelId 段不同时，产出新字段 `model_unenforced`（§3.1）；
3. 守卫对该字段播报一句，按 `cause` 给排查指向（§3.2）；
4. `review.ts` 把它条件展开进 run.json，`run.v2.json` 补说明（§3.3）；
5. 预检 `checkZcodeRuntimeSelection` 的指向句补新通道（§3.4）；
6. 用例、变异、设计文档、RUNBOOK、BACKLOG 同步（§4、§5）。

**不做**：
- 不改模型覆盖本身，不在副本源缺失时判 glm 侧不可用（那是 EV-122 候选 ②，用户未选）；
- **不做预检期提示**（CODEX-05 暂缓）：①支在预检期就可判定（`authProbe.fingerprint()` 已取过 `cli/config.json`），收尾播报只能在配额烧完之后出现——E2 那一轮白烧了 16m42s。但「预检期提示、不阻断」是候选 ① ② 之外的另一档，用户只定了 ①，本题不自行扩大。登记为 EV-123 候选，由用户定（§5）；
- 不对「没回读到生效模型」出新播报：那一格已由 `model_effective_source: unverified` 表达；
- **不接线、也不删 `agents.glm.unsupported_override`**（GLM-01）：该键零消费方，EV-30 ⑦ 待裁「接线还是删」。本题的播报在语义上承担了它的 annotate 档（放行、标注）；reject 档若将来接线，要先定它与本播报的先后。这层关系补记到 EV-30 ⑦（§5）；

## 3. 改动

### 3.1 判定（决策 D1：新字段 (a)，计划双审三侧认可）

- **(a) 新可选字段 `model_unenforced`（采纳）**：`{ requested: string; effective: string; cause: 'source_missing' | 'qualify_failed'; reason: string }`，产出条件四条同时成立：
  没做覆盖（`route !== 'config_copy'`）、请求非空、回读到了生效模型、两者 modelId 段（`zcodeModelTail`）不同。其余一律缺席。
  - `cause` 由 `prepareZcodeHome` 给出，是判定与分句的**唯一依据**；
  - `reason` 取 `prepareZcodeHome` 给的理由原文，**只供人读、不参与任何判定、不保证文案稳定**（设计 6.7.1 同写）；
- (b) 让 `model_override_applied` 在没做覆盖时也记 `false`。**不取**：该字段的「缺席＝本次无覆盖尝试」是已写进设计 6.7.1 与 schema 的契约，
  守卫 `false` 那句的措辞是「覆盖没落实」，把「根本没做覆盖」塞进去会让两种成因同形，排查方向相反（一个查 CLI 读取点，一个查副本源在不在）；
- (c) 守卫自己拿 run.json 的 `model_requested` 与 `model_effective` 比。**不取**：判据归适配器（C4），各家模型 id 形态不同，判定层统一比较必然误报（设计 6.7.1 `model_override_applied` 行已写明的口径）。

**`prepareZcodeHome` 的成因**：`ZcodeHomePrep` 新增 `cause: 'source_missing' | 'no_model' | 'qualify_failed' | null`，三个 `global` 出口各填一值，`config_copy` 出口填 null。
`no_model` 在流水线里不可达（C2），只为类型完整；它不会进 `model_unenforced`（请求为空时该字段恒缺席）。

**纯函数与接线**：`decideModelUnenforced(attempted, requested, effective, cause, reason)` 与 `decideModelOverride` 并列，二者产出条件互斥（一个要求 `attempted`，一个要求 `!attempted`）。
`run()` 里的接线实参是

```ts
decideModelUnenforced(overrideAttempted, req.model, modelEffective, home.cause, home.reason)
```

**第二参取 `req.model`，不是 `home.qualified`**（CODEX-03 ≡ AGY-01）：后者在本题的两支恒为 null（C3），照抄相邻 `decideModelOverride` 的写法会让新字段恒缺席；
`req.model` 也与 run.json 的 `model_requested` 同源（C7），守卫文案里的「请求的是 X」与 run.json 对得上。N7 把这一点钉在用例上（§4.2）。

### 3.2 守卫播报

`guard.ts` 侧摘要透传 `modelUnenforced`；存在时播报（与 `model_override_applied === false` 那句同一通道，**不判失守、不阻断**）。
文案**只陈述可观测事实**（CODEX-06），占位与引用方式沿用 C5 的既有告警（AGY-02）：

> `${s.critic}` 侧**本次没有做模型覆盖**：请求的是 `<requested>`，实际跑的是 `<effective>`（`<reason>`）。
> 该侧结论仍然有效，但模型路由（FR-06）与异构默认（NFR-06）在本侧不成立——若另一侧模型与它同家族，这一轮不构成真正的双审。
> ＋按 `cause` 追加一句**排查指向**（不是成因断言）：
> - `source_missing`：先看副本源 `~/.zcode/cli/config.json` 在不在；
> - `qualify_failed`：先看请求的模型名在不在副本源的 provider 目录里（profile 与 `--model-glm` 的写法）。

分句按 `cause`，**不匹配 `reason` 文案**（与 `reorderHint` 同口径，C5）。

### 3.3 run.json

`review.ts` 与 `model_override_applied` 同处条件展开（缺席不压成 null）；`run.v2.json` 的 `$defs.critic.properties` 补 `model_unenforced`：
critic 级可选；对象 `additionalProperties: false`，内层 `required: ["requested", "effective", "cause", "reason"]`（AGY-03，与 `carriers_landed` 同形），
`cause` 为 `enum: ["source_missing", "qualify_failed"]`，`reason` 的 description 写明「只供人读、不保证文案稳定」。
`types.ts` 的 `CriticResult` 与 run.json 逐侧类型各加一格；桩适配器加注入口（给集成用例用）。

### 3.4 预检指向句（CODEX-04）

`checkZcodeRuntimeSelection` 的 `detail` 末句由「跑完看 guard 的『请求的模型没有生效』告警与 trace.json 的 modelSelection.reorder」
改为「跑完看 guard 的『请求的模型没有生效』或『本次没有做模型覆盖』告警，以及 trace.json 的 modelSelection」。
判据、`ok: true`、出项条件都不改。两条通道的分工写进设计文档（§5）：预检那条由 doctor 探针读数驱动、说「大概率」；收尾两条由本次运行回读驱动、说「实际」。

## 4. 验证

### 4.1 用例

- **`prepareZcodeHome` 成因**：副本源缺失 ⇒ `cause: 'source_missing'`；`model` 为空 ⇒ `'no_model'`；限定失败 ⇒ `'qualify_failed'`；限定成功 ⇒ `null`、`route: 'config_copy'`。
- **纯函数**（`decideModelUnenforced`）：做了覆盖 ⇒ 缺席；请求为空 ⇒ 缺席；没回读到 ⇒ 缺席；modelId 段相同而 providerId 不同 ⇒ 缺席；请求短名、回读全限定且 modelId 段相同 ⇒ 缺席；modelId 段不同 ⇒ 产出、四字段原样。
- **`run()` 副本源缺失**（沿用 `zcode-carriers.test.ts` 的假入口与 `runReview` 助手）：请求 `GLM-5.3`、假入口日志的 `context.model` 为 `p/fake-model` ⇒ `model_unenforced` 产出，`requested === 'GLM-5.3'`、`cause === 'source_missing'`；
  现有 U4（请求 `fake-model`、回读 `p/fake-model`）⇒ 仍缺席。
- **`run()` 限定失败**（沿用 `zcode-model-selection.test.ts` 的 `runWithFakeEntry`）：现有「负格」用例（请求 `nope-model`、不回读）⇒ 缺席（没回读到）；
  新增一格请求 `nope-model`、回读 `p/other` ⇒ 产出，`cause === 'qualify_failed'`。
- **守卫**：字段在 ⇒ 播报一句，含 critic 名、requested、effective、reason；`source_missing` 与 `qualify_failed` 各一格，断言各自的排查指向且不串；字段缺席 ⇒ 不出；与 `model_override_applied === false` 同时不会出现（互斥），各自那句不串。

- **集成**：桩注入 `model_unenforced` ⇒ run.json 逐侧段原样出现、另一侧缺席、收尾 `message` 含该句（仿 `code-stage.test.ts` 里 `carriers_landed` 那条）。

**断言口径**：一律断言 `cause` 与结构化字段，**不断言 `reason` 的文案片段**（CODEX-02）；守卫用例对 `reason` 只断言「原样出现」，用注入的任意字符串。
